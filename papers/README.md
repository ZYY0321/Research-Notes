## 2026-10-30 收敛候选：结构树和画面对不上（待实验验证）

上面三篇的规划没有回答"我们的优势在哪"。10-30 核实文献、再问 Opus 之后，收敛到一个候选：**截断检测、开合检测、CUA 的 AX 问题，本质都是结构树（布局树 / AX 树）说的和画面显示的对不上**。测试里，对不上本身就是缺陷；智能体里，对不上是陷阱。

- 软工篇：量化原生 App（鸿蒙、macOS）里对不上的频率、类型和触发因素（折叠是可控的触发），建按控件标注的评测集，再量基于结构树的测试判定器因此误报漏报多少。
- AI 篇：把"这一步要不要花一次视觉核验"做成有代价的决策，在公开 benchmark 上和每步都核验的做法比成功率与额外调用次数。
- 最近的已有工作是 arXiv 2607.04334（只做诊断；缓解办法每个动作多调 1.8–5.5 次模型）。
- 前提还没验证。过程和我的审读见 [日志/2026-10-30.md](日志/2026-10-30.md)，要先跑的实验见 [先跑的实验_结构树与画面一致性.md](先跑的实验_结构树与画面一致性.md)。

## 候选：不限移动端的 AI 想法（2026-10-29 18:19，待验证）

结合 CUA 和移动端两边的现象问 Opus，原文在 `UX-Agent-data--collection/explore-research/材料/2026-10-29_不限移动端的研究想法/`。

最契合的是 C（验证器的分歧结构）和 F（程序化自验证），可以合成一个题目："GUI 智能体的结果什么时候能信"。对比三种验证来源：mac-cua 的程序化评分（有标准答案）、智能体用确定性手段自我验证、视觉模型当判官；量出它们在哪里、为什么分歧，再在移动端开合数据上验证。

立论前要先确认两个现象：
- 同一份规则下，GPT 和 Opus 的真实一致率；
- 在同样卡住的状态下，GPT 挑控件和随机点，谁更容易走到新页面。

（2026-10-30 注：这一节依赖的两个现象都来自我们自己设计有缺陷的实验，不能当动机。F 改为并进上面的收敛候选当组件，不单独成篇。）
