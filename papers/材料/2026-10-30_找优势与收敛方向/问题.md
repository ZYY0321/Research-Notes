你是一位同时在软件工程顶会（ICSE / FSE / ASE）和 AI 顶会（NeurIPS / ICLR / ACL）当过审稿人的研究者。这一轮请你当**反方**：先找每个方向为什么不成立，再说怎么救。不要谄媚，不要为了给出方案而硬凑。

## 0. 上一轮哪里错了（请不要重复）

上一轮你写了一篇仿写摘要，开头是"移动 GUI 自动探索中，大模型介入的时机常导致不公平比较：仅在探索卡住时调用大模型，会使其在最不利状态下被评测"。用户的评价是：这写得很烂，明明是**我们自己的实验做得不好**，却被包装成了研究动机。责任在我给你的证据有误导。下面这些**不是证据，不要再拿来当动机或卖点**：

- "GPT 挑的控件只有 9% 到新页面，脚本随机挑的是 16%"：大模型只在卡住时才调用，两组状态根本不同，这是我们实验设计的缺陷，不是一个发现。
- "GPT 和 Opus 打标只有 69% 一致"：两边用的提示词和规则不一样，不能比。
- "功能命名 89–95% 一致"：这只说明命名稳定，用户认为"命名稳但任务成功率低"没有研究价值。
- 849 组开合打标（fail 266）：是 GPT 打的，人工复核还没做，准确率未知。
- 唯品会一轮 spec 覆盖 10/46：只是一个 App、一轮、200 步。

- 用户的要求（原话整理）：
  - 要定**一个**方向，逻辑完全打通：背景、gap、我们有的资源、前沿的兴趣。
  - 不要重复别人已经有的东西；也不要乱提一个新东西，结果没人关心、或者没解决最重要的问题。
  - 想清楚"我们比别人的优势在哪里，别人为什么做得不好"。是问题定义上的优势，还是算法上的优势？

  - 用户可以安排别人先跑必要的实验。

## 2. 我们实际有的资源（只列核实过的）

1. **鸿蒙真机开合采集**：Mate X5 真机，`uitest dumpLayout` 拿布局树 + 截图，`hidumper` 切折叠态（只准用于开合采集）。自动探索脚本已能过夜无人值守，跑过 28 个商业 App。每次开合测试存折叠前后各状态的截图和布局树，目前约 850 组以上。
2. **截断检测项目**（之前的主线）：用布局树（XML）加截图，滑动复核来判断文字 / 组件 / 图标截断。华为的截断数据和模型**不能开源**，但可以自己重新收数据训练。用户实测 GPT-5.6 零样本判截断"手拿把掐"。规则：没有 XML 的不跑端到端。
3. **macOS CUA 评测集建设（用户在公司 CUA 组的工作）**：基于 AX 树的 cua 框架，任务带程序化打分（检查器）。已核实的真实失败：WPS 每次启动弹登录窗，cua 只能绑到一个 78×40 的小浮条上，看不到文档；WPS 的保护工作表对话框 cua 看不见，复选框没有可读状态（10 项检查过 9 项，就栽在这）；图表对话框一片白；剪映导入面板 cua 不让操作。用的是 claude-opus-5-5，换强模型帮助有限。
4. **用户的知识图谱积累**：本科毕设 Fairy（投过 AAAI）：交互式多智能体手机助手，其中 App Map Learner 跟踪页面变化和引起变化的动作、组件，建成 App 知识图谱，执行中持续积累（自我进化）。还建了 RealMobile-Eval 基准。
5. **mobilegym-mock**：若干复刻 App 的网页版，带人工 spec（如唯品会 46 页），可以程序化注入缺陷。
6. API：GPT-5.6、Claude Opus 5.5 可用，无额度限制。算力：训小模型的 GPU 情况未确认。

## 3. 用户对每个方向的看法（原话要点）

- **方向一（探索 / 测试用例生成）**：别人的探索算法看着很完整，但实际效果怎么样不知道，很多跑不出来。软工的指标就是覆盖率和发现的问题。有没有一种方法能在这上面真正创新？没有的话这个方向就很空。
- **方向二（GUI 状态 / 轨迹分析，类似知识图谱）**：这个本身是很基础的工作。相关论文做到什么程度了？能不能复现、能不能分析？我们本身有知识图谱的工作。"什么样的轨迹值得拿来训练"也属于这里。
- **D（轨迹质量）**：重要但复杂，不是一个完整方向；评判轨迹质量是否可靠，本身也要靠数据证明。我们自己做能做好吗？
- **E（AX 树可不可信）**：光说"有多可信"没有指向一个直接结果，贡献不够。用户提出一条链：怎么生成测试用例 → 怎么衡量质量 → 底层的 AX 树可信度 → 我们的 CUA 框架怎么设计。能不能有一个 benchmark 测模型能不能发现 AX 里的问题？能不能有一个框架：AX 可信就直接用，不可信就用 GUI / 视觉，而且不浪费步骤？
- **F（verify）**：重要，但没有人会专门为这个发一篇文章。如果说别人的 verify 不好、我们提出更好的方法，那要说清别人为什么做不好、我们的优势在哪。

## 4. 本轮核实过的文献（Grok 子 agent 查、我抽查了关键一篇；全表见文末附录）

最关键的一篇我亲自读过原文：

**《Do GUI Agents Believe Their Eyes? Diagnosing State-Belief Reliance on Pixels versus Structure》（arXiv 2607.04334，2026-07，深圳大学，未见代码）**
- 735 个探针，覆盖网页、手机、桌面；其中 225 个是从 38 个在线网站挖出的天然不一致，250 个手机"过期节点"候选来自 Rico 等旧的人工标注数据。冲突主要是**文字值**被结构树改掉。
- 指标 Perception-Fusion Gap：模型单看图能答对，但结构树一冲突就跟着结构走的比例。各家模型普遍偏向结构；在天然的过期快照上跟随过期结构最高 0.88。7B 到 30B 放大，可见性问题好了，文字值偏信反而更重。
- 多步：MiniWoB++ 最多 6 步，第一步信错几乎必然整条失败，自我恢复率至多 0.03。
- 比了四种缓解：像素优先提示（几乎没用，动作层被劫持仍 0.92–0.97）；证书检查（裁图核验，不符就拒绝，消除劫持但拒掉 59–77% 有冲突的动作）；他们的一致性门控（裁图核验，失败就扫屏重新定位）——唯一同时降低劫持和任务出错的，但**每个动作要多调 1.8–2.0 次（MiniWoB++）、3.3–5.5 次（AndroidWorld）模型**。
- 作者自己的结论："没有一种比较过的缓解办法能不付代价地解决问题"；"未来的智能体不仅要跟踪预测的状态，还要跟踪支撑它的通道"。他们把自己定位为诊断，不是防御方法。

其他要点：
- Screen2AX（arXiv 2025）：知名度较低的 macOS 应用里 AX 完整支持只有 33%，99 个最流行应用里 36%。
- Windows Agent Arena（ICML 2025）：同一模型，加 UIA 标记让成功率从 12.5% 到 19.5%；UIA 查询可能要几秒到几分钟。
- OSWorld：截图加 a11y 并不总比单截图好（Gemini-ProV 5.80% → 3.48%）。
- UFO2、Agent S2 都是混合感知，但是固定的合并 / 路由规则，没有"这一步该信哪个通道"的判断与准确率。
- **没有找到**：每一步自动决定用 AX 还是视觉并报告选择准确率的工作；专门标注原生 App AX 树里缺节点、状态读不到、框和画面不一致，并给出模型 F1 的基准。
- 方向二已经很成熟：GUI-explorer（ACL 2025）、UI-KOBE（2026 arXiv，状态图让 4B 小模型 AndroidWorld 58.6%→70.7%）、PG-Agent（MM 2025）、AppAgentX、AutoDroid、FuncDroid（功能流图，仓库写支持鸿蒙 HDC）、ProphetAgent，以及世界模型 ViMo、MobileDreamer（EMNLP 2026 Findings）、WebDreamer，多数开源。
- 方向一的真实表现：没有找到任何对 LLM 测试工具的独立复现。LLM-Explorer（MobiCom 2025）同批 20 个应用、2 小时对比里，GPTDroid 的 activity 覆盖率只有 28.62%，而 GPTDroid 原文报 75%（应用和预算不同）。ASE 2024 一篇统计分析指出故障检测指标即使重复多次也不稳定。鸿蒙上已有 HapTest（FSE 2025 Companion）、HmTest（JCST 2025）。

## 5. 我（主 agent）提出、请你挑战的一个想法

截断检测、开合检测、CUA 的 AX 问题，可能是同一件事：**结构树说的和画面显示的不一致**。
- 测试里，不一致本身就是缺陷：结构说文字完整、画面被截断；折叠后结构还在、画面丢了内容（或反过来，结构过期）。
- 智能体里，不一致是陷阱：结构说有个按钮、画面上没有；结构读不到复选框状态；对话框在画面上、结构里没有。
- 上面那篇论文测了"模型信谁"，但用的是网页文字值的人工改动和旧手机数据，缓解办法太贵。原生 App 里（鸿蒙、macOS）天然出现的不一致是什么样、有多常见、配置变化（折叠、窗口切换）是否会大量制造过期结构，都没人量过。

我不确定这是真洞见还是硬凑，请你判断。

## 6. 请你回答

1. **逐个方向当反方**（一、二、D、E 链、F）：最强的反对理由是什么；别人到底哪里做得不好（有文献依据就说，没有就说"不知道，需要实验"）；我们的优势如果有，是在问题定义、数据 / 平台资源，还是算法上。站不住的直接判死，并说为什么。
2. **评估第 5 节的想法**：是不是真的把几条线串起来；和 2607.04334 相比，我们还剩下什么不重复的、而且审稿人会在乎的东西；"不浪费步骤"能不能变成一个可量化、有前沿吸引力的问题（比如把"选通道"当成有代价的决策，用 AX 树和截图哪里不一致的信号去学或去估计"什么时候该花一次视觉核验"）。如果你觉得不对，就说不对。
3. **收敛到一个方向**：给出完整逻辑链——背景（一两句人话）、gap（必须是别人确实没做、且有人在乎的）、我们独有的资源、为什么现在是时候、核心贡献（不超过三条）、主实验怎么设计（基线、公开 benchmark、指标）。并分别说：它怎么切出一篇软工文章、怎么切出一篇 AI 文章，两篇不要互相蚕食。
4. **先跑的实验**：在押注之前，哪些实验必须先做，用来证伪或确认前提？每个实验写：要回答的问题、怎么做（具体到用哪些现有数据或工具、多少样本）、需要几个人几天、**什么结果出来就放弃这个方向**。用户可以安排别人去跑，所以写得让一个不了解背景的同学也能照做。
5. **D 和 F 放在哪**：作为上面那个方向里的组件还是单独的工作，各需要什么数据才能证明可靠。
6. 你说的每个"没有人做过"，都标注是"附录里核实过"还是"你的印象、需要再查"。

用中文回答，用普通的话，不要堆术语和箭头链。不要写仿写摘要。

### 专项检索结论（只陈述查到与没查到）

检索词包括：accessibility tree unreliable / noisy / incomplete / inconsistency / hallucination，modality selection，hybrid grounding，perception switching。

- 直接测「结构字符串和画面不一致时模型信谁」的，是上面的 arXiv:2607.04334。它覆盖网页 DOM 与 accessibility 树，不单是 macOS AX 或 Windows UIA。
- 量化「macOS 应用 AX 不完整」的，是 Screen2AX 的 33% / 36% 那两组应用统计，外加正文列举的缺元素、框不准、不可见元素仍在树里。
- 量化「加 UIA 框相对纯像素框的任务成功率」的，是 Windows Agent Arena 表 4（12.5%→19.5% 等）。UFO2 做的是 UIA 与视觉框按 IoU 合并，论文主表没有单独给出「混合检测 vs 只用 UIA」的控件召回率。
- OSWorld 表 5 是 a11y only / screenshot only / 二者结合的任务成功率，不是 AX 错误检测准确率。结合后并不总是更高（Gemini-ProV：仅截图 5.80%，截图+a11y 3.48%）。
- 没有打开到一篇已发表论文，其基准任务就是：标出 AX 树上哪些节点缺失、哪些状态读错、哪些框和截图像素不一致，并给出模型在该基准上的 F1。
- 没有打开到一篇论文，其方法是在每一步自动选择「这一步用 AX」或「这一步用视觉」，并在该选择上报告准确率。Agent S2 的 Mixture-of-Grounding 是在视觉定位、OCR、LibreOffice UNO 之间路由，论文写主输入为截图。DiMo-GUI 分开的是文字和图标。LUMOS 默认走 UIA/DOM，视觉对比实验作者写尚未做。
