# SE2：UX 问题导向的 GUI 探索

> 类型：核心 ｜ 归属：论文规划，软件工程第 2 篇 ｜ 状态：维护中（2026-10-29 建）

## 思考方式（软件工程会议）

这是探索方向，赛道拥挤。评价指标通常是覆盖率（activity、代码、功能）、发现的缺陷数、效率，基线是 2024 年以后的探索工具。要说清楚两件事：

- **目标不同**：现有工作的目标是覆盖率或完成任务；我们的目标是尽快走到会出 UX 问题的页面状态。
- **同样的预算下更好**：找到更多不同的 UX 问题，而不只是走到更多页面。

不限于开合。开合、截断、遮挡这些 UX 问题都需要"先走到某个状态，再判"，所以同一套探索方法都能用。

## 已知的空白

- Testing-Survey 的"UX 问题驱动探索"专题里写了：A11yScan 等工作"不是按视觉异常概率自适应搜索"，ReFLAIR 只对已有页面做主动复核。没看到"按 UX 风险来决定去哪"的探索。
- 我们自己的诊断（唯品会 200 步）：
  - spec 46 个页面只覆盖 10 个；
  - 按布局骨架认页面，和真实功能对不上，综合分卡在 73–77%；
  - 停滞判断误触发；
  - GPT 介入去到新页面的比例比随机还低。

  这些都是现有"带偏好的随机游走"的硬伤。

## 方法要素（三个核心问题在这一篇里的样子）

1. **按功能认页面**：每个新页面，让视觉模型给它起功能名。2026-10-29 验证过：同一批 200 步，三遍起名两两一致率 89–95%，35 个模板归并成 28 个功能。之后的去重、"点过什么"、测试名额，都按"功能 + 状态"来记。
2. **按进展判断停滞**：连续 N 步没走到新的"功能 + 状态"才算停滞，不再是"4 步只在两个页面之间"。停滞后回到还有没试过入口的地方，思路参考 TimeMachine 和 LLMDroid。
3. **大模型当 CUA，带着能自动核验的子目标**：比如"到达一个弹层开着、输入框有字、筛选面板打开的页面"；到没到，用脚本自己的状态检测来判。给它看人能读懂的功能记忆，让它规划多步，不是从编号里挑一个控件。
4. **有 spec 的 App**，可以拿 spec 里还没覆盖的页面当目标。这只是加分项，不能依赖它，因为 spec 要人工整理。

## 实验草案

- **App**：真机 Top App，加上唯品会、喜马拉雅这类有人工 spec 的 App。
- **指标**：
  - 以 spec 为参照的功能覆盖率；
  - 每小时找到的、不重复的 UX 问题数；
  - 重复测试率；
  - 停滞误报率。
- **基线**：
  - 经典的：DroidBot、APE；
  - 2024 年以后的：LLMDroid、VisionDroid、GraphDroid、FuncDroid；
  - 我们自己的 v1 和 v2。
- **消融**：分别去掉功能命名、停滞恢复、CUA 子目标，看各自贡献多少。

## 依赖和风险

- 依赖 SE1 的判定器，判错了，"找到的问题数"就没意义。
- 要说清和 FuncDroid 的区别（它把轨迹收成功能流图，再按缺什么去补测）。我们的区别是目标为"UX 风险状态"。
