# AI1：可注入缺陷的 GUI 环境，与会找缺陷的智能体

> 类型：核心 ｜ 归属：论文规划，AI 会议第 1 篇 ｜ 状态：维护中（2026-10-29 建，方向未定，待验证）

## 思考方式（AI 会议）

照 Testing-Survey `reviews/` 里总结的规律来判断：
- **Spotlight / Oral 几乎都是社区能直接拿去用的开放资源**（数据、benchmark、模型、框架），并带一个新的认识，比如规模和效果的关系、失败出在哪一层。
- **要在公开 benchmark 上，用同一个基座比，拉开差距。**
- **要证明数据真的改变了模型**，光有规模不够。
- **新意要落在 GUI 本身的难点上。** 下面几类会被说成"已有流程换了名字"：
  - 先 SFT 再做 RLVR；
  - 过程奖励模型；
  - 规划–执行–反思加失败恢复；
  - 先探索、事后写指令。

**不限于开合。** 只研究一种缺陷，对 AI 会议来说太窄；在复刻 App 里模拟折叠，工作量大、用途窄，也不是真机数据（2026-10-29 用户的判断）。视觉缺陷和功能缺陷的注入则通用得多。

## 想法

1. **环境**：在可重置、可并行、状态可以程序判定的复刻 App 里（mobilegym-mock，浏览器里跑），程序化地注入各类缺陷：
   - 视觉缺陷：文字截断、遮挡重叠、元素缺失、图片拉伸、越界；
   - 功能缺陷：点了跳错页面、状态没保存、输入丢失、按钮失效、勾选不生效。

   每个注入点都有标准答案。
2. **数据**：自动生成成千上万个带标准答案的缺陷实例，再配上探索轨迹，"找到了缺陷"和"没找到"两类。
3. **训练**：训一个小的视觉语言模型当"会找缺陷的智能体"。奖励有两部分：找到注入的缺陷并正确报告（能自动核验），以及走到了新的"功能 + 状态"。
4. **进阶（可选）**：注入的一方也做成智能体，学着把缺陷埋到难被发现的地方，两方自博弈（2026-10-29 Opus 第二版里的 FoldPlay，推广到一般缺陷）。
5. **benchmark**：注入缺陷的复刻 App 有标准答案，再加真实 App。真实 App 用 SE1 收的真机数据和人工标注。

## 新在哪，要核对的

- **GUITestBench**：26 个缺陷、143 个任务，需要执行任务。在 Testing-Survey 的 README 里出现过，是最接近的工作，必须读笔记、说清区别。我们的区别可能在于：缺陷是程序化注入的，规模大得多；环境能拿来训练；还训了智能体。
- **UI-Lens**：只判给定的截图，不探索。
- **MobileGym**：可重置的模拟环境，但目标是完成任务，不是找缺陷。
- **OS-Genesis、Explorer、GUI-ReWalk、UI-Genie**：合成轨迹，目标都是完成任务。
- 研究文件夹 `1020汇报/04_必读文献/B_我们的笔记/` 里有 guitestscape、mai-gym 的笔记，也要对照。

## 怎么回应审稿人最可能的质疑

- **"只在自己的环境里好"**：至少报一个公开参照，比如在已有的缺陷数据或 benchmark 上测发现率，并说明在真实 App 上还剩多少效果。另外确认 AndroidWorld 这类通用能力没有变差。
- **"benchmark 没带来新认识"**：要有分析，比如哪类缺陷最难发现、为什么难（要走多深、要先进入什么状态），模型规模和数据量各有多大作用。

## 2026-10-29 18:05 对照 OpenReview 审稿记录修订（Opus AI 版，原文在 `UX-Agent-data--collection/explore-research/材料/2026-10-29_软工与AI分开的论文方案/`）

**对之前方案的判断**：
- **训练部分不新**："SFT + RL 训一个小 VLM"正中 InfiGUI-R1、GUI-R1、Aguvis 被拒的理由。
- **对抗自博弈不当主线**：它最像 MobileGUI-RL、VistaGUI、WorldGUI，这几篇都是 4 分被拒；而且两个模型一起训、收敛性、从复刻环境搬到真机，任何一环出问题都会塌。最多当一个消融或者加分模块。

**推荐：方案 D，DefectGym**，投 NeurIPS Datasets & Benchmarks。
- **一句话**：现有 GUI benchmark 测的是"完成任务"，没有测"发现缺陷"的。我们做一个能大规模程序化注入、自动核验的 GUI 缺陷发现 benchmark 和训练环境。
- **三条贡献**：
  1. **开放资源**：视觉缺陷（截断、遮挡、越界、混叠）和功能缺陷（跳错页面、状态没保存、按钮失效、勾选不生效）程序化注入复刻 App，每个实例都自带标准答案。这和 AndroidWorld"带程序化奖励的可重置环境"是同一类价值。
  2. **新的认识**：把"缺陷为什么难发现"拆成三个维度，即页面深度、状态依赖（得先做哪些操作才能触发）、截图能不能直接看出来，分层报告各基线的发现率。这对应 VideoGUI 被打 8 分的理由。
  3. **证明数据让模型变好**：训一个 7B 发现智能体，测试集用训练里没出现过的 App 和注入参数，给出数据规模曲线（1K / 10K / 50K）；同时在 AndroidWorld 上报通用能力没有变差。
- **算力和成本**：注入层不用 GPU；生成数据和跑基线大约几百美元 API；只有训练那条要 GPU（它估 8×A100 两三天，是假设）。算力没到位之前，可以先用 GPT 当策略跑零样本基线。
- **第一个月**：
  1. 第 1–2 周：盘点 mobilegym-mock（App × 可注入点 × 缺陷类型）；实现 3 种视觉注入；读 GUITestBench 和 guitestscape，写出差异表。
  2. 第 3–4 周：在 2–3 个 App 上生成 2000 个实例，跑 GPT 零样本，按深度和状态依赖分层统计，这就是图 1；再拿真机截断数据和复刻数据比一比分布有多远。

## 2026-10-29 18:13 GUITester 的短板、开源约束、和 CUA 那边的关系

- **GUITester / GUITestBench 的短板**（Testing-Survey 的笔记 `notes/gao2026guitester.md`）：
  - 只有 12 个 App、26 个真实缺陷，扩成 143 个高度相关的任务；
  - 任务事先造好、必须经过缺陷位置；
  - 没有消融、没有统计检验、没有成本相当的基线，没给裁判和人工的一致率；
  - 没有干净的负例；
  - 不覆盖截断、重叠、错位；
  - 发表在 Findings of ACL 2026。

  这些正好是 DefectGym 的差异点：程序化注入、规模可以扩、含显示缺陷、有干净负例、能自动核验。
- **开源**：DefectGym 建在 mobilegym-mock 上（用户自己的项目），不用华为的数据。真机部分不能用华为的截断测试集当公开集，要自己重新收。投 D&B 时可以不训练，基线用 API 模型。
- **和 CUA 组的工作接得上**：一条轨迹失败了，是应用的缺陷、环境的问题，还是智能体自己的错？这是 CUA 数据质量和 GUI 测试共同的难点。GUITester 把智能体这一侧的两种偏差叫"目标导向掩盖"和"执行偏差归因"；CUA 那边的复盘则发现，大部分失败其实是环境和框架的问题，而且"成功不等于干净"。可以给 DefectGym 的每条轨迹标上"缺陷在应用 / 环境 / 智能体"，当作"新的认识"那条贡献的一部分。证据在 `~/CUA/评测集建设/`（`WPS剪映问题技术说明.md`、`失败证据_1028.md`）。
