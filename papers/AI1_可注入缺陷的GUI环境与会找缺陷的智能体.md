# AI1：可注入缺陷的 GUI 环境，与会找缺陷的智能体

> 类型：核心 ｜ 归属：论文规划，AI 会议第 1 篇 ｜ 状态：维护中（2026-10-29 建，方向未定，待验证）

## 思考方式（AI 会议）

照 Testing-Survey `reviews/` 里总结的规律来判断：
- **Spotlight / Oral 几乎都是社区能直接拿去用的开放资源**（数据、benchmark、模型、框架），并带一个新的认识，比如规模和效果的关系、失败出在哪一层。
- **要在公开 benchmark 上，用同一个基座比，拉开差距。**
- **要证明数据真的改变了模型**，光有规模不够。
- **新意要落在 GUI 本身的难点上。** 下面几类会被说成"已有流程换了名字"：
  - 先 SFT 再做 RLVR；
  - 过程奖励模型；
  - 规划–执行–反思加失败恢复；
  - 先探索、事后写指令。

**不限于开合。** 只研究一种缺陷，对 AI 会议来说太窄；在复刻 App 里模拟折叠，工作量大、用途窄，也不是真机数据（2026-10-29 用户的判断）。视觉缺陷和功能缺陷的注入则通用得多。

## 想法

1. **环境**：在可重置、可并行、状态可以程序判定的复刻 App 里（mobilegym-mock，浏览器里跑），程序化地注入各类缺陷：
   - 视觉缺陷：文字截断、遮挡重叠、元素缺失、图片拉伸、越界；
   - 功能缺陷：点了跳错页面、状态没保存、输入丢失、按钮失效、勾选不生效。

   每个注入点都有标准答案。
2. **数据**：自动生成成千上万个带标准答案的缺陷实例，再配上探索轨迹，"找到了缺陷"和"没找到"两类。
3. **训练**：训一个小的视觉语言模型当"会找缺陷的智能体"。奖励有两部分：找到注入的缺陷并正确报告（能自动核验），以及走到了新的"功能 + 状态"。
4. **进阶（可选）**：注入的一方也做成智能体，学着把缺陷埋到难被发现的地方，两方自博弈（2026-10-29 Opus 第二版里的 FoldPlay，推广到一般缺陷）。
5. **benchmark**：注入缺陷的复刻 App 有标准答案，再加真实 App。真实 App 用 SE1 收的真机数据和人工标注。

## 新在哪，要核对的

- **GUITestBench**：26 个缺陷、143 个任务，需要执行任务。在 Testing-Survey 的 README 里出现过，是最接近的工作，必须读笔记、说清区别。我们的区别可能在于：缺陷是程序化注入的，规模大得多；环境能拿来训练；还训了智能体。
- **UI-Lens**：只判给定的截图，不探索。
- **MobileGym**：可重置的模拟环境，但目标是完成任务，不是找缺陷。
- **OS-Genesis、Explorer、GUI-ReWalk、UI-Genie**：合成轨迹，目标都是完成任务。
- 研究文件夹 `1020汇报/04_必读文献/B_我们的笔记/` 里有 guitestscape、mai-gym 的笔记，也要对照。

## 怎么回应审稿人最可能的质疑

- **"只在自己的环境里好"**：至少报一个公开参照，比如在已有的缺陷数据或 benchmark 上测发现率，并说明在真实 App 上还剩多少效果。另外确认 AndroidWorld 这类通用能力没有变差。
- **"benchmark 没带来新认识"**：要有分析，比如哪类缺陷最难发现、为什么难（要走多深、要先进入什么状态），模型规模和数据量各有多大作用。
