# SE1：鸿蒙多形态设备上显示问题的交互式复核——截断与开合

> 类型：核心 ｜ 归属：论文规划，软件工程第 1 篇 ｜ 状态：维护中（2026-10-29 建，同日把截断检测并进来，开合改为第二种缺陷）

## 思考方式（软件工程会议）

审稿人会问四件事：
1. 问题重不重要？
2. 实证够不够扎实，有多少 App、多少设备、多少问题、怎么分类？
3. 工具好不好用，准确率多少、要多少时间？
4. 找到的真实 bug 有没有被开发者确认？

技术不必新奇。同类文章是靠问题定义、真实场景和真实 bug 中的，文献库里就有：
- **ReFLAIR**（FSE 2026 Research）：网页宽窄两种布局对比，对疑似缺失的内容主动滚动、展开后再判；
- **SUDFinder**（TSE 2026）：系统设置变化引起的显示问题；
- **TouchAlign**（FSE 2026 Industry）：真点一下，看可点区域有没有错位；
- **XBIDetective**（ICSE 2026 SEIP）：跨浏览器视觉差异的语义判断。

## 核心想法

只看一张截图判断显示问题，分不清"真的坏了"和"本来就该这样"。所以先让模型给出候选，再**主动做一个交互去复核**：

- **截断**：滑一下，看被切掉的内容能不能露出来，然后滑回原位。用来区分三种情况：
  - 合法隐藏：设计上就不显示；
  - 可以滑出来：可滚动可达；
  - 真截断：怎么滑也看不全。

  这三类的边界没人系统定义过，这是 10-20 汇报里定的空白。
- **开合**：把屏幕在折叠和展开之间切一次，看展开后的信息是不是没比折叠时少，状态（弹层、输入、勾选）有没有丢。这和旋转测试不同：旋转要求前后等价，开合要求展开后不少于折叠时。

两种缺陷用的是同一个框架：**模型给候选 → 布局树核对 → 针对性的交互复核 → 恢复现场**。

## 为什么值得做

- **多形态设备**：直板、双折叠、阔折叠、三折叠、平板，同一个 App 在不同形态上表现不一样，自动化研究几乎空白。折叠方面只有 MobiSys 2024 一篇海报：3 台机器、20 个 App、人工观察。
- **鸿蒙原生界面（ArkUI）没人研究过**，现有工作都在 Android 或网页上。
- **有华为合作的真实需求和验收。**

## 研究问题草案

- **RQ1 普遍性和分类**：不同形态的设备上，截断和开合问题各有多普遍？分哪几类？截断分"合法隐藏 / 可以滑出来 / 真截断"，开合分 M1–M6。
- **RQ2 交互复核有多大用**：只看截图、加上布局树、再加交互复核，三种做法的准确率和召回各是多少？交互复核排除了多少误报？
- **RQ3 成本**：每页耗时多少？交互复核会不会破坏现场，滑回去以后能不能恢复？
- **RQ4 真实影响**：报给开发者，多少被确认、修复？

## 手上已有的

- **截断**：
  - `UX-Agent/HarmonyArena-fdu_agent` 的三段式流水线（模型 → 布局树 → 滑动，`ux-detect --mode=slide`）；
  - 覆盖五种设备、带布局树的测试集（`UX-Agent/test-set/`）；
  - 9 月验收的运行记录（`UX-Agent/docs/`）。
- **开合**：
  - 28 个 App 的真机采集：852 次开合测试，GPT-5.6 打标 fail 266；
  - 判定标准草案和检测方案；
  - 复核网页；
  - 同事真手折的数据。

## 还缺的

1. **人工标注的标准答案**：截断测试集已经有；开合要从 849 组里抽 200 组人工复核。
2. **用手真折复现**：采集时 hidumper 只改显示，确认的问题要用手真折一次。可以把"命令切屏和真折的一致率"本身写成一个实验。
3. **基线**：
   - 通用多模态模型只看截图（UI-Lens 的设定）；
   - OwlEye、Nighthawk 一类检测器；
   - ReFLAIR 的思路改到原生端；
   - 开合方向，把 RotDroid 改到折叠上。
4. **报给开发者**的真实问题。

## 风险

- 交互复核依赖布局树和真机，没有布局树的页面就跑不了。9 月的规则是"没有 XML 不跑端到端"。
- 开合的口径要合作方确认，比如"等比放大把内容挤出首屏"算不算问题（见验收问题清单）。

## 2026-10-29 18:05 按软工录用论文修订（Opus 软工版，原文在 `UX-Agent-data--collection/explore-research/材料/2026-10-29_软工与AI分开的论文方案/`）

依据是 Testing-Survey 总表里 33 篇软工会议录用论文。

- **截断和开合放一篇**。两者共用"候选 → 布局树 → 交互复核 → 恢复"这个框架，框架能同时管两种缺陷，本身就是贡献；拆开以后，每篇都会显得太薄。
- **暂定题目**：*ProbeCheck: Active Verification of Display Defects on Multi-Form HarmonyOS Devices*
- **RQ 四个**：普遍性和分类；交互复核让准确率提升多少（只看截图 → 加布局树 → 加交互）；耗时和恢复成功率；开发者确认。
- **基线**：只看截图的多模态模型（VisionDroid 一类、UI-Lens）、ReFLAIR、SUDFinder，再加"不做交互"的消融。OwlEye、Nighthawk 是为 Android 写的，移植成本高，可以不比。
- **门槛**：
  | | 勉强能投 | 比较有说服力 |
  |---|---|---|
  | App | 15–20 个 | 30 个以上 |
  | 设备形态 | 3 种 | 5 种 |
  | 开合人工标注 | 200 组 | 200–300 组 |
  | 开发者确认的 bug | 10 个 | 20 个以上确认，10 个以上修复 |

  确认的 bug 数凑不够时，转工业赛道（ICSE SEIP / FSE Industry），用华为验收和部署规模补强。
- **前 4 周**：
  1. 第 1–2 周：开合人工标注 200–300 组（两人交叉）；用手真折复现，算命令切屏和真折的一致率。
  2. 第 3 周：跑"只看截图 / 加布局树 / 加交互"三种变体；尽早通过华为渠道报 bug，开发者回复周期不可控。
  3. 第 4 周：统计 RQ1 的分布，写相关工作。
