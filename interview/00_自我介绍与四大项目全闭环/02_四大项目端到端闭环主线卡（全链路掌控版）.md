## 项目一：小浣熊多模态办公 Agent（AgentV3）—— 架构、轨迹蒸馏、全轨迹 DPO 与 SlideGate 评测论文

### 1. 端到端闭环总图
```text
线上回流与合成需求 ──► AgentV3 四层 Harness + 多阶段 PPT Skills ──► 沙盒代码/HTML生成
        ▲                                                                  │
        │ (4) 训练反哺：SenseNova Flash 284B / Lite                        ▼ (1) 评测与归因
SFT (16.2k 清洗轨迹) ◄── 全轨迹 DPO (Opus 正 vs Flash 负) ◄── SlideGate 基准 (94题工业线 + 240份顶会线)
  + 5.2万张图文版式蒸馏      + OPD 在策略蒸馏 + MTP/FP8
```

### 2. 六大环节核心硬核细节（面试随便问哪环都能接）
1. **运行时架构（AgentV3 + State V3）**：
   - 自研四层编排：`BaseLLM`（统一 OpenAI/Anthropic/Cloudsway 适配，保留 `reasoning_content` 与 `thought signature`）→ `BaseNode`（单轮工具 JSON/Schema 校验与沙盒分发，任何错误封装成结构化 `tool_result` 写回让模型自纠错，不直接崩进程）→ `BaseAgent`（循环与 `finalize` 控制）→ `AgentV3`（调度 `MainAgent`、`SubtaskAgent`、`ReflectionAgent`）。
   - **状态三层分离（State V3）**：`message_records` 存不可变事件事实（`user_input`、`assistant_output`、`tool_call`、`tool_result`、`subtask_summary`），`asset_index` 存上传附件与解析产物，`runtime_control` 存预算 `global_loops`、待执行子任务队列与 `waiting_user_input` 挂起态；每轮调用前动态 `rebuild_compiled_messages()` 编译成模型消息视图。
   - **Skills 与子任务隔离**：主 Agent 按需读取 `ppt-maker/SKILL.md` 等业务 SOP，调 `create_subtask` 将数据解析、大纲设计、逐页 HTML 生成委派给独立上下文的 `SubtaskAgent`（屏蔽 `create_subtask`/`ask_user` 防递归），收尾提取 `<subtask_result>` **原位回填**到主流程最初那条 `tool_call_id` 对应的 `tool_result` 中，保持主推理链连续且不撑爆主上下文。
2. **单页图文设计蒸馏管线（51,981 张）**：
   - **创意模式（18,197 张）**：提取线上高密度生图回流 Query → `gpt-image-2`（1536×864）重绘 → G6 13 类版式分类。
   - **标准模式（33,784 张）**：回流 PPT 只有结构化内容（36,573 页）无视觉设计；将外部 19,150 条粗糙 Prompt 经“正负向词规则粗筛（剩 732 条）+ LLM 蒸馏成纯设计描述卡（剩 495 条 L2）”与 300 条人工精拆 L3 合并为设计池；每页随机抽 5 候选（保底 2 条 L3）交由 Claude Sonnet 语义匹配择优合成约 260 词英文生图 Prompt → `gpt-image-2` 生图 → 规则前置 + Claude Sonnet（`temperature=0`）两级分类入 13 类版式库（high 置信度 88%）。
3. **多轮 Agent 轨迹 SFT 蒸馏与六步修复管线（16,274 条）**：
   - 教师模型 Claude Opus 4.7 跑出 5 批共 16,274 条轨迹（主 + 子任务），通过 `export_trace_to_openai.py` 导出并保留 thinking signature。
   - 训后模型暴露出“写文件不发 `<file_action>` 预播报”和“发完 `<file_action>` 不调工具直接早停”两大顽疾。深挖原始 `result.jsonl` 定位三大根因：① 运行时 `subtask_counter` 缺陷导致 28% 子任务（74% 为最密集使用 `file_action` 的大纲/风格阶段）在导出前丢失，造成严重幸存者偏差；② `0629_query` 批 42.2% 混入残缺版 System Prompt；③ 幸存轨迹中 `write_file` 65%–88.7% 漏发 `<file_action>`，而含 `<file_action>` 的消息中有 12.5%–26.3% 是子任务收尾轮冗余重报或网关解析截断导致的末条悬空消息（训练信号变成 `file_action → EOS`）。
   - 设计 **6 步自动化清洗管线**：注入规范协议段 → 为 `write_file`/`execute_code` 补齐 `<file_action>` 并由 Qwen 结合 `reasoning_content` 与写入代码现编自然摘要（禁泄文件名/工具名）→ 剥离全部末轮悬空块 → C5 目标路径对齐 → 将 5,184 处机械 `<ask_user_answer>` JSON 改写为自然人类确认语 → C1–C5 全检，最终交付无模板 9,901 条 + 模板 6,373 条，C1/C2 100% 合规、悬空率 0%。
4. **全轨迹 DPO 构造与高并发工程排障**：
   - 突破早期“单页抽取 DPO”的局限，在 `dev/wangbo/ppt-skill-v1.1-distill` 分支首次落地**全轨迹 DPO**：正样本 `accept` 为 Opus 4.7 完整成功轨迹（1,879 个主 query），负样本 `reject` 为自研 SenseNova Flash 284B v14 / Flash-Lite 在同批 query、同套 Skills 下跑出的完整轨迹（严格对齐主 Agent、沙盒内 `_html_llm_direct.py` 与视觉审阅三端点）。
   - **经典排障**：双路 64 并发（共 128 路）开跑 8 分钟后雪崩，830 题瞬间失败。排查证实并非远端沙盒 256 会话满载，而是客户端每题高频拉取 `SKILL.md` 写入本机 `/tmp`，叠加 TCP 连接耗尽 Linux 单进程文件句柄（`[Errno 24] Too many open files`），且 `ThreadPoolExecutor` 一次性 submit 全部 470 题形成“旋转门”秒烧题库。通过引入建连波次限流（`SANDBOX_CREATE_WAVE_SIZE=16, GAP=2s`）、控制单机并发上限并以 `deck_html_pages>0`（禁止把 `done_no_html` 混入）作为唯一有效轨迹门禁解决。
5. **后训练全流水线认知（SenseNova Flash 系列）**：
   - 完整路线：`基座继续预训练（代码/DA/PPT域） → 多轮轨迹 SFT → OPD（On-Policy Distillation，学生自采样轨迹 + 教师逐 token 蒸馏，消除暴露偏差） → 全轨迹 DPO / KTO 偏好对齐 → MTP（多 token 预测头加速投机解码） + FP8 量化部署`。
   - 截至 2026-09，无模板模式下自研 `v41 dpo-v2` 达 **0.809**（n=45），逼近商业顶档 Claude Opus 5 的 **0.817**。
6. **工业评测排障与 SlideGate ICLR 2027 论文**：
   - **侦破“假 DPO 退化”**：`step3kdpo_tpl` 看板分 64.6 低于基线 68.7；排查 `content_evaluator.py` 发现旧 Gemini 判分网关偶发返回空串时未抛异常，动态核查项退化为 `dynamic_items == 0`，仅靠 6 条简单通用项打分导致老批 30%–49% 样本内容分静默虚高。加上重试抛错与强制首字符 `{` JSON 约束并全量重判 6 个历史模型后，证实无 DPO 与 DPO 实为 **0.6635 vs 0.6526** 持平，避免了错误回滚训练方向。
   - **SlideGate 论文**：针对传统均分掩盖严重交付硬伤的问题（6 个商业系统 240 份输出中检出 **124 份**阻断失败，但 5/6 既有框架 Mann-Whitney U 检验无显著分差），提出从请求与可解析附件经 3 次独立生成+批评归并冻结 **2,191 条**任务专属核查项，三维解耦报告**指令硬约束满足率 HCR（程序化客观参照优先）**、**内容覆盖+L0/L1/L2深度+三值忠实度**、**逐页 4 类视觉硬伤计数**；内容判定与双盲人标一致率 80.7%/85.6%，视觉排名与设计师偏好 Spearman $\rho = 0.855$。

## 项目二：OpenMobile 与 OpenMobile-2（MobileGym++）—— 可重置混合环境、轨迹合成与多轮 Agentic RL

### 1. 端到端闭环总图
```text
[OpenMobile v1] 随机探索10步 ──► 全局环境记忆(pHash聚类+VLM功能图+语义索引) ──► 跨功能任务合成(2.8k题)
                                                                                    │
Qwen3-VL-8B (AndroidWorld 64.7%) ◄── SFT ── Policy-Switching 轨迹采集 (Learner探索 + Gemini监控触发Expert纠偏, 1.56次恢复/条)

[OpenMobile-2 / MobileGym++]
63个可重置全功能 Mock App + 333个前台原生 MCP 工具 + 业务 Store 差分严格 0/1 Verifier (470变异100%拦截)
   ├──► 评测闭环：Bench 215 锁表 (GUI-only vs Hybrid 同初态对照，揭示小模型 Tool Hurts 模态路由失调)
   └──► 训练闭环：弱探索+强接管合成 11,643 条 SFT 轨迹 + 2,475 道带 Verifier 任务 ──► DAPO 多轮强化学习 → OpenMobile-27B
```

### 2. 核心技术要点与关键实验结论
1. **OpenMobile v1（arXiv:2604.15093）两大核心算法**：
   - **探索与指令生成解耦 + 全局环境记忆（Global Environment Memory）**：用感知哈希（pHash, $\tau=0.95$）聚类屏幕节点，VLM 标注控件功能并构建有向转移图与 Embedding 索引；合成任务时联合当前焦点屏幕、短期记忆（邻接可达屏）与长期记忆（语义相关远端功能，Top-30 多样性过滤），解决单条随机游走无法生成长链路跨功能组合任务的痛点。
   - **策略切换轨迹采集（Policy-Switching Rollout）**：交替运行学习者 $\pi_l$ 与专家 $\pi_e$，由监控器实时检测 $\pi_l$ 偏离或死循环并切换 $\pi_e$ 示范如何从错误状态退回主线，使每条轨迹平均包含 **1.56 次**错误恢复（纯专家蒸馏仅 **0.42 次**），有效克服行为克隆（BC）$p^T$ 级联误差。`Qwen3-VL-8B` 在 AndroidWorld 达到 **64.7%**（远超开源基线 ScaleCUA 的 27.2%）。
2. **OpenMobile-2 / MobileGym++ 为什么要自建 63 个可重置 Mock App 环境？**
   - 真实商业 App（淘宝、微信、美团、携程等）面临三大死穴：① 账号风控与支付不可逆，无法大规模并行 RL Rollout；② 页面动态广告变化不可复现；③ 外部拿不到服务端数据库状态，只能靠 VLM 看截图猜成败，误报极高。
   - 我们按“截图 → 交互 Spec → 反渲染审阅 → React/Flutter + 确定性业务 Store 实现”复刻了 **63 个应用**（中位数 37 个路由、88 条状态转移；如淘宝覆盖搜索→SKU→加购→下单→支付→售后 38 节点 100% 闭环），支持毫秒级确定性 `reset()`、固定模拟时钟，并为 51 个应用挂载了 **333 个前台原生 MCP 工具**（仅暴露当前前台 App 的辅助查询/预填函数，禁止“一键通关答案函数”）。
3. **业务 Store 级 0/1 Verifier 设计与验证**：
   - 彻底抛弃“看模型自称完成”或“纯路由停留判定”：改状态任务直接对初态与终态 Store 做结构化字段差分 + 反向断言（禁止改动无关订单/收藏）；查询记笔记任务同时校验必含锚定事实与禁含易编造干扰词。
   - **验证判定器本身（Meta-Verification）**：空操作审计（初态直判 100% 失败）+ 470 个字段破坏/半途而废变异终态 **100% 拦截（0 假阳性）**；在 369 次实测中成功拦下 **190 次**“模型输出已完成、但底层业务状态未落库”的虚假完成（Hallucinated Completion）。
4. **GUI-only vs GUI+MCP Hybrid 核心实验洞察（面试王炸亮点！）**：
   - 在官方锁表 **Bench 215** 上严格同初态、同裁判对比：
     - **Gemini 3.1**：从 GUI-only 的 **58.6% (126/215)** 跃升至 Hybrid 的 **68.4% (147/215)**（工具救回 33 题，但工具误导害死 12 题）。
     - **小模型模态路由失调（Modality Routing Collapse）**：`Qwen3.5-9B-mcp` 在 GUI-only 上 37.7%，上 Hybrid 仅 39.1%——深入逐题归因发现**工具救回 30 题，却害死 27 题（Tool Hurts = 27）**！典型死因是模型调用了“预填表单/查询函数”后误以为业务已提交，未走完敏感界面确认就直接结束；而纯 GUI SFT 训出的 9B 在 Hybrid 协议下工具调用次数为 0，成绩反而掉到 35.3%。
5. **多轮 Agentic RL（DAPO）训练管线与关键工程约束**：
   - 基于 11,643 条 SFT 轨迹冷启动后，在 2,475 道带 Verifier 任务上运行 **DAPO**（Clip-Higher 非对称裁剪防熵坍缩 + Dynamic Sampling 过滤组内全 0/全 1 无梯度组 + Token-level Loss + 去 KL + 超长软惩罚）。
   - **三个实战铁律**：① 环境异常（App 启动超时、崩溃）必须从 RL batch 分母剔除，严禁记为 0 分奖励污染梯度；② 工具返回与截图属于环境 Observation，设置 `response_mask=0` 不算策略梯度，只对模型生成的 reasoning 与 action/tool_call token 算梯度，且采用 token-in/token-out 避免多轮重分词导致 logprob 失真；③ 针对 20+ 步长程任务终态 0/1 奖励过稀疏的问题，利用可控环境的 Store Diff 拆解中间状态里程碑（State-Milestone Credit Assignment）并抑制超长 thinking 撑爆上下文窗口。

## 项目三：CUA（桌面/移动端 Computer-Use Agent）架构研究与华为 HarmonyOS 多设备 UX-Agent

### 1. 核心架构与技术闭环
1. **桌面端 macOS CUA（Brain–Driver 分层架构、程序化评测与 AX 树失效实证——近期在研主线）**：
   - **系统分层设计**：将 CUA 拆解为上层 **Agent 规划与任务评测层** 与底层 **OS 原生驱动层（Driver）**。驱动层基于 macOS 原生 `AXUIElement`（采集前台焦点窗口无障碍层级树、控件角色/bounds/勾选值）与 Quartz `CGEvent`（鼠标点击、拖拽、组合键注入、屏幕捕获）封装统一 RPC/工具接口；上层负责多模态观察融合、动作安全门控以及**任务级程序化检查器（Programmatic Verifier，直接核查导出文件/配置状态而非只看截图）**。
   - **国产复杂桌面软件一手失效实证（换 `claude-opus-5-5` 也救不了的感知陷阱）**：业界统计流行 macOS 应用完整支持 AX 树的仅约 36%（Screen2AX），我们在真实国产办公与创作软件上抓到了三类典型结构失真：① **焦点小浮窗劫持**（如 WPS 启动弹出登录条，驱动只绑到 `78×40` 的迷你浮窗，整个主文档对 AX 树隐身）；② **控件状态属性缺失**（如 WPS“保护工作表”任务 10 项程序化检查过 9 项，唯独对话框复选框在 AX 树中无勾选状态或漏节点，模型因 Perception-Fusion Gap 盲信结构树去瞎猜坐标点错）；③ **自绘 Canvas / 面板黑洞**（如 WPS 图表设置框一片空白、剪映导入面板拒绝暴露标准 AX 操作）。
   - **技术解法（有代价的通道选择 Cost-Aware Modality Routing）**：如果每步都调多模态模型做裁剪一致性核验，单步调用成本会暴涨 1.8–5.5 倍；因此我们利用 AX 树结构异常特征（窗口面积异常极小、视口大面积无交互叶节点、OCR 文本数与 AX 文本数严重倒挂、或执行点击后树与画面零变化）做轻量级**通道可信度预判**——结构可信时直接走零开销 `element_id` 精确动作，检测到结构残缺或过期时即时切换至高分截图视觉 Grounding，在不浪费步数的前提下打破死循环。
2. **华为 HarmonyOS 多设备 `UX-Agent` V2.0 三阶段主动交互检测算法**：
   - **科学问题**：在直板、双折、阔折、三折（Mate XT）与平板 5 类屏态下检测 UI 截断缺陷时，单张静态截图存在**不可消解的观测歧义**——视口边缘露出一半的文字/卡片，究竟是“容器写死导致的真截断缺陷”，还是“横向 Tab/轮播列表正常可滚动的未展开部分”？纯 VLM 静态检测误报率极高。
   - **三阶段递进流水线（Active Interactive Oracle）**：
     - **Stage 1 视觉高召回提案**：VLM 扫描 `[0, 1000]` 归一化空间输出疑似截断候选框及被切边缘方向（top/bottom/left/right）。
     - **Stage 2 ArkUI 布局树静态几何复核**：映射回物理像素，过滤弹窗背景遮挡与正常省略号；对比节点可见 `bounds` 与原始排版 `origBounds`，向上追溯裁剪父容器——若父容器不可滚动或滚动已触底则直接确认为 `true_truncation`；若有明确滚动余量则消解为 `not_truncation`；静态树无法判定（如自绘/嵌套容器）标为 `unknown`。
     - **Stage 3 主动微滑动探测与原位恢复**：对同方向相邻 `unknown` 候选框分组，避开系统手势边缘与折叠屏铰链中轴线执行反向滑动；若框内像素变化率 $>5\%$ 判为 `scrollable`，否则判为 `confirmed` 真截断；随后反向回滑恢复页面并校验与原图像素差异 $\le 2.5\%$（若滑少/滑过则基于一维平移匹配自动补滑一次，若仍恢复失败标为 `restore_failed` 绝不静默吞掉缺陷），实现接近零误报的工业级验收。
   - **折叠屏开合状态一致性自动探索采集**：结合页面结构模板重合度去重（阈值 0.57）、停滞/循环检测与引导式遍历，自动触发开合态切换并捕获弹窗消失、布局挤压等跨屏态退化缺陷。

## 项目四：LingCoder 多语言代码大模型 —— 数据工程、MoE 集群训练与评测

### 1. 端到端闭环要点
1. **大规模代码数据标签体系与蒸馏（285万–300万条）**：
   - 构建 **Context Tag（应用场景：应用开发 52.7%、算法设计 26.8% 等 9 类）× Task Type（任务形态：代码实现 47%、代码分析 21.6%、代码生成等）** 二维正交分类标准与消歧规则（如区分“带业务包装的算法题”与“真实工程开发题”）。
   - 针对 Python 第三方库与非 Python 稀缺语料，开发基于 AST import 解析 + DeepSeek-V3.2（禁思考模式、多端点负载均衡与断点续传）的代码蒸馏管线。
2. **Qwen3-30B-A3B（MoE）分布式消融训练与排障**：
   - 在 SenseCore 大装置 **4 节点 × 8 卡（32 GPU）** 环境上设计并运行 1A–1F 六语言（Python / C++ / Java / JS / Go / Rust）数据配比消融实验。
   - 实战解决 MoE 训练与转换全链路工程问题：DeepEP All-to-All 通信启动异常、NCCL 多机初始化超时、Checkpoint 保存阶段主机内存 OOM Kill、训练权重转 HuggingFace 格式后 vLLM 加载 MoE 专家权重键名缺失对齐。
3. **多基准评测分析**：
   - 基于 SenseBench 系统评测 HumanEval-X、BigCodeBench、LiveCodeBench、FullStackBench；定位出基座在 Python Plus 达 **89.02** 的同时 C++ 仅 **52–58** 的语言不均衡短板，指导后续多语言合成配比倾斜。
