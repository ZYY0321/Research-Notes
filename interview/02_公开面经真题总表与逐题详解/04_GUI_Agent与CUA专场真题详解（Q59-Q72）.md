### Q59：什么是 Computer-Use Agent（CUA）？完整拆解它的感知—推理—执行—环境反馈闭环与三段式训练范式。
- **核心定义**：CUA 是直接在人类使用的图形用户界面（桌面 OS、浏览器、手机屏幕）上工作的通用智能体。区别于只消费结构化 JSON API 的传统文本 Agent，CUA 以**渲染后的屏幕像素截图与可选无障碍结构树（AX Tree / DOM / XML）**为观测，以**键鼠/触控事件及混合原生工具**为动作，把所有无公开 API 的闭源软件统一纳入自动化版图。
- **单步运行闭环（Observe → Reason → Ground & Act → Verify）**：
  1. **同步观测采集**：底层 Driver（如 macOS `AXUIElement`/Quartz、Android ADB、HarmonyOS `uitest`）捕获屏幕截图与焦点窗口结构树；
  2. **多模态状态推理與规划**：VLM 在交错的图文动作历史序列上输出当前页面理解、上一步动作是否生效确认及下一步子目标思考；
  3. **定位与安全门控执行**：输出绑定控件 ID 或 `[0, 1000]` 归一化坐标的结构化动作，经 Harness 校验边界、陈旧度与权限后注入系统，等待 UI 渲染稳定再采下一帧。
- **现代 CUA 标准三段式训练流水线**：
  1. **Stage 1：GUI 感知与 Grounding 持续预训练**（百万～千万级 UI 截图—控件框—功能描述对，如 SeeClick / OS-Atlas，赋予模型“指哪打哪”与读懂图标语义的底座能力）；
  2. **Stage 2：多轮带反思轨迹 SFT（含错误恢复）**（万级跨应用轨迹，如 OpenCUA 长 CoT 或我们 OpenMobile 的 Policy-Switching 弱探索+强纠偏合成轨迹，建立多步规划与纠错先验）；
  3. **Stage 3：可重置环境下的在线强化学习（Verifier-Driven RL：GRPO / DAPO）**（在数百并发 VM 或可重置应用环境如 MobileGym++ 中靠零误报状态 Verifier 自主探索长程策略，突破模仿学习天花板）。

### Q60：Browser-Use / Web Agent 与桌面/移动端 CUA 在工程部署（容器虚拟化、分辨率、状态同步、登录态与反爬）上有哪些核心细节？
- **核心工程细节五连答（直击 Accio 二面真题）**：
  1. **隔离执行环境选型**：Web 端常用容器化无头/有头 Playwright + Chromium（轻量、单机可起几十并发）；桌面端用 Docker + Xvfb/VNC（Linux）或 QEMU/KVM 虚拟机池（OSWorld 方案）；移动端用容器化 Android Emulator 阵列或像我们 **MobileGym++** 一样将 63 个移动应用编译为高保真可秒级重置的 Web/Host 运行时以支撑大规模高并发 RL Rollout；
  2. **分辨率与坐标空间统一**：不同虚拟显示器 DPI（如 Retina 2x 逻辑坐标 vs 物理像素坐标）不一致会导致点击整体偏移一半！工程上必须在 Driver 层显式对齐物理截图尺寸与系统事件注入坐标系，模型侧统一预测 `[0, 1000]` 归一化相对坐标；
  3. **动作后的动态等待与状态同步（Anti-Flakiness）**：点完按钮网页 AJAX 加载、客户端转圈动画未结束就立刻截图，模型会误判“没点上”再点一次造成重复提交。需结合 DOM `networkidle`、帧间像素差分稳定检测与显式 `wait` 动作；
  4. **DOM 蒸馏裁剪**：真实电商网页原始 HTML 动辄几十万字符，不能原样塞进 Prompt，需过滤不可见节点、只抽取视口及周边可交互语义子树并赋予紧凑数字索引；
  5. **登录态持久化、弹窗清理与人机协同接管**：商业站点/软件有登录态过期、隐私协议首屏拦截（我们在小红书/京东真机探索中实测首屏协议弹窗不处理会导致数百次重启空转）及滑块验证码——工程上需预注入持久化 StorageState/Profile，开局统一挂弹窗清理钩子，遇敏感验证/支付触发 `ask_user` 人类远程接管再恢复会话。

### Q61：为什么不能简单让多模态模型直接回归预测绝对像素坐标 $(x, y)$？主流 Visual Grounding 技术路线是如何演进的？
- **裸预测绝对像素坐标的四大硬伤**：
  1. **强耦合分辨率与设备屏态**：在 `1080×2400` 直板机上学到的 $(540, 1200)$，换到 `1440×3200`、Mac 外接屏或三折叠屏展开态直接全歪；
  2. **文本数字生成的语义鸿沟**：LLM 用离散词表 Token 输出数字 `'5','4','0'`，交叉熵对 `'540'` 和 `'541'` 的惩罚与 `'999'` 一样，缺乏连续空间几何平滑监督，且 ViT Patch 粒度（如 $14\times 14$）与单像素点不匹配；
  3. **单点标注惩罚合法多解**：一个宽 300 像素的按钮点左边和点中间都完全正确，单点回归却把点左边算成误差；
  4. **不可解释且不可跨帧幂等重放**：页面稍微滚了 20 像素，旧坐标就点到别的按钮上了。
- **主流 Grounding 五代演进脉络**：
  1. **Set-of-Mark（SoM，如早期 WebVoyager / OmniParser + GPT-4V）**：先用 DOM 或外部检测器（YOLO + Icon Caption）在图上画编号框，模型只输出编号 `click(12)`；优点是零坐标负担，缺点是检测器漏框则模型彻底瞎眼且遮挡原图细节；
  2. **`[0, 1000]` 相对归一化坐标端到端生成（SeeClick / OS-Atlas / UI-TARS / Qwen2.5-VL）**：与分辨率解耦，配动态高分切片（AnyRes），成为工业界端到端底座主流；
  3. **两阶段粗细缩放（Zoom-in / DiMo-GUI）**：针对 4K 桌面密集小图标，第一轮预测粗区域裁剪放大，第二轮精确定位；
  4. **免坐标视觉 Patch 注意力对齐（GUI-Actor, 2025）**：引入专用 `<ACTOR>` token 直接与图像 ViT Patch Tokens 做空间注意力对齐，一次前向输出整片可点击热力区域并配 Verifier 择优，7B 模型在 ScreenSpot-Pro 上超越 72B 坐标生成模型；
  5. **结构节点优先 + 视觉归一化兜底混合绑定**：有可靠控件树时绑定稳定 `node_id`，无结构时降级视觉区域并做点击前二次 IoU 核验。

### Q62：介绍代表性视觉定位与 CUA 模型：SeeClick、OS-Atlas、UI-TARS（1&2）、OpenCUA、GUI-Actor 各自的核心机制是什么？
- **五篇里程碑代表作速记卡（全在你研究库里）**：
  - **SeeClick（2024）**：开创纯视觉 GUI Grounding 预训练先河，指出通用 VLM 看不准屏幕控件，构建网页/移动定位语料并提出黄金基准 **ScreenSpot**；
  - **OS-Atlas（2024）**：构建最大开源跨平台（Web/Desktop/Mobile）Grounding 动作基础语料库（超 **1,300 万** UI 元素），统一异构平台动作命名空间；
  - **UI-TARS-1 & 2（ByteDance Seed, 2025）**：原生端到端纯视觉 CUA 标杆；2 代核心突破在于构建**数百台虚拟机在线数据飞轮 + System-2 长反思推理 + 稳定化多轮 RL + GUI 与底层 Bash/文件系统混合沙盒**，OSWorld 达 **47.5%**、AndroidWorld **73.3%**；
  - **OpenCUA（NeurIPS 2025）**：构建跨三大 OS、200+ 应用的 AgentNet 标注基建，核心证明了**合成带状态反思的长 CoT（观察变化 → 反思前步 → 规划当前动作）**是开源桌面 CUA 泛化的关键（OSWorld-Verified 达 **45.0%**）；
  - **GUI-Actor（2025）**：提出免文本坐标生成的 **Attention-based Action Head + Grounding Verifier**，仅微调 ~100M 新增动作头（冻结 VLM 主干）即可在跨分辨率高分屏（ScreenSpot-Pro **44.6%**）击败传统巨型坐标生成模型。

### Q63：Set-of-Mark（SoM）、Accessibility Tree（AX 树 / XML / DOM）与纯视觉截图（Screenshot-only）三种观测方案如何权衡？

| 观测方案 | 优势 | 致命短板 | 适用场景 |
|---|---|---|---|
| **纯结构树（AX Tree / DOM）** | Token 省（纯文本）、文字精确无需 OCR、控件自带角色与坐标 | **看不见图像内容/颜色排版**；商业客户端大量自绘/Canvas 节点缺失或过期；巨型网页树极度臃肿 | 结构极其规范的后台表单或轻量 API 化页面 |
| **Set-of-Mark（截图叠框标号）** | 降低通用大模型直接报坐标的难度 | 强依赖前置检测器召回率（漏框即不可点）；密集界面数字标签互相遮盖污染原图 | 不具备原生 Grounding 能力的早期通用闭源 VLM 拼装方案 |
| **纯视觉截图（Screenshot-only）** | **100% 所见即所得（人类能看它就能看）**，跨一切自绘引擎/远程桌面通用，无结构树查询卡顿（Windows UIA 查询有时慢达数秒至数分钟） | 高分图视觉 Token 消耗大；密集微小文字/隐藏滚动属性识别不如原生属性直接 | 经过大规模 Grounding 预训练的现代原生 CUA（如 UI-TARS / OpenMobile） |
| **自适应可信度混合（你的推荐方案）** | 兼顾结构精准与视觉完备，避免盲信坏树被劫持 | 需要通道一致性诊断机制 | 真实复杂桌面（macOS WPS/剪映）与国产移动商业 App |

### Q64：【你的核心优势题】在实际跑桌面 macOS 或移动端国产 App 时，AX 树不可靠具体表现在哪？如何诊断并设计视觉动态兜底框架？
- **核心结论**：绝对不能静态写死“有 AX 树就信 AX 树”！外部实证（Screen2AX 统计流行 macOS 应用仅 **36%** 完整支持 AX；arXiv:2607.04334 证明模型在图文冲突时高达 **88%** 盲信坏结构树且首步信错后自恢复率 $\le 3\%$）与我们自己在 **macOS CUA** 和 **鸿蒙真机（21.2 万个节点统计）** 上的一手实验完全吻合。
- **你亲测抓到的四类真实失真形态（面试讲出来极具杀伤力）**：
  1. **迷你浮窗焦点劫持**：WPS 每次启动弹出小登录条，底层 `AXUIElement` 驱动抓到的前台活跃窗口只有 `78×40` 大小，整个主文档编辑区对 AX 树完全隐身；
  2. **关键状态属性与节点缺失**：WPS“保护工作表”任务 10 项程序化检查过了 9 项，栽在对话框复选框没有可读勾选状态/节点，哪怕换顶配 `claude-opus-5-5` 也会根据残缺树瞎猜坐标连点失败；
  3. **自绘组件黑洞（Canvas / WebView / XComponent）**：WPS 图表对话框在树里一片白、剪映导入面板拒绝暴露标准 AX 操作；鸿蒙大众点评 **25%** 页面含无子节点的自绘 `XComponent`；
  4. **隐形幽灵节点与未裁剪原文误导**：鸿蒙实测 **5.4%** 的节点标着 `visible=true` 实则透明度 `opacity=0`，且 **24%** 被父容器裁掉一半的节点在树里 `text` 字段依然存着未裁切的完整全文！
- **你的高性价比解法：有代价的通道路由（Cost-Aware Modality Routing）**：
  - 文献里的逐动作裁图门控每步要多调 1.8–5.5 次大模型，太贵不可落地；
  - 我们在 Driver 与 Harness 之间加入**零 LLM 开销的通道健康度探针**：① **几何拓扑异常检测**（当前窗口面积占屏比极小如 `78×40`、大片视觉非空白区无交互叶节点、过滤 `opacity==0` 幽灵节点）；② **轻量端侧 OCR 对账**（RapidOCR 检出文字框数量远大于 AX 树文本节点数，说明存在自绘弹窗/Canvas）；③ **闭环动作差分熔断**（对某 AX 节点执行点击后，新帧像素与树 `uiHash` 零变化，立即判定该节点失效，一步无缝切换至纯视觉截图 Grounding 通道，绝不在坏树上浪费第 2 步）。

### Q65：如果让你从零设计一套跨平台 GUI Agent 的 Action Space（动作空间），需要包含哪些原子与复合动作？有哪些安全与幂等考量？
- **四类正交完备动作集**：
  1. **指针/触控类**：`click(target, button)`、`double_click`、`long_press`、`hover`、`drag / swipe(from, to)`、`scroll(target, dx, dy)`（其中 `target` 同时兼容结构 `node_id` 与 `[0, 1000]` 归一化坐标，支持无缝降级）；
  2. **键盘输入类**：`type(text, target?, clear_first?, press_enter?)`（复合“点输入框+清空+输入+回车”，直接把 4 步压缩成 1 步大幅降延迟！）、`hotkey(keys)`（如 `cmd+s`、`ctrl+c`）；
  3. **系统导航类**：`open_app(name)`、`home()`、`back()`、`switch_tab / focus_window`；
  4. **生命周期与控制类（面试加分关键！）**：
     - `wait(ms)`：应对加载动画与异步渲染，把“等不等”纳入显式策略动作；
     - `extract / note(content)`：显式分离**纯读信息记入工作草稿**与**改变外部界面状态**；
     - `ask_user(reason)`：遇登录密码、手机验证码、二次确认支付或权限弹窗主动挂起移交人类，严禁瞎点或死循环；
     - `finish(status="success"|"infeasible", summary)`：必须带明确布尔/枚举状态区分“做完了”与“任务条件本身不可达”，不能只留一段模糊自然语言。
- **执行前安全护栏（Stale Check & 危险动作拦截）**：对于改状态或支付删除类高危点击，执行前一毫秒重新拉取局部快照比对控件位置 IoU / 局部像素哈希（防止大模型思考这 2 秒钟里突然弹出广告框刚好盖在原坐标上造成误点！）。

### Q66：【你的核心实验题】给 GUI Agent 接入原生 API/MCP 工具组成 Hybrid Agent 一定涨点吗？为什么小模型会出现 `Tool Hurts` 模态路由失调？怎么解决？
- **核心结论**：**绝不是简单把 MCP 工具表塞给 GUI Agent 就一定涨点！** 我们在 **MobileGym++ Bench 215**（同一初态、同一模拟时钟、同一业务 Store 裁判）上的严格对照实验揭示了极其鲜明的尺寸分化与 **Modality Routing Collapse（模态路由失调）**：
  - **强模型（Gemini 3.1）**：从 `GUI-only` 的 **58.6% (126/215)** 大涨至 `Hybrid` 的 **68.4% (147/215)**（工具救回 33 题，但仍有 12 题被工具带沟里）；
  - **9B 小模型（`Qwen3.5-9B-mcp`）**：`GUI-only` 37.7%，上 `Hybrid` 仅 **39.1%**——逐题归因发现 **工具虽然救回了 30 道导航繁琐的题，却反过来害死了 27 道原本纯点屏幕能做对的题（`Tool Hurts = 27`）**！此外在 306 个可用工具中有 199 个一次都没被调过（严重工具盲区），而纯 GUI 训出的 9B 在 Hybrid 协议下工具调用为 0、成功率反而掉到 35.3%。
- **三大根因拆解**：
  1. **副作用与提交边界幻觉**：许多 MCP 工具是辅助查询或预填草稿（不直接完成敏感提交），小模型看到工具返回 `{"ok": true}` 就误以为整单业务已落库，直接跳过最后的界面确认按钮调 `finish` 交卷；
  2. **工具返回与界面视觉状态不同步**：后台调函数改了数据但当前停留在旧缓存页面未刷新，模型看着旧截图陷入认知混乱；
  3. **模式偏置**：小模型缺乏对“这一步走 3 下点击更稳，还是调 1 次函数更准”的代价与边界评估能力。
- **针对性解决方案**：
  1. **工具返回显式附带状态与后续界面动作提示**（如返回 `"status": "draft_created_not_submitted"` 并在换状态后自动刷新重截当前页）；
  2. **构造 V4 四类边界训练数据与反事实信用分配**：在同一业务状态节点同时采样纯 GUI 分支与 MCP 分支，对“调完预填函数即早停”构造强负样本（全轨迹 DPO / Milestone RL），让模型真正学会工具的语义等价范围与副作用边界。

### Q67：模仿学习（Behavior Cloning）训 GUI Agent 为什么步数一长就崩（$p^T$ 复合误差）？详解 OpenMobile 的 Policy-Switching Rollout 与全局环境记忆合成。
- **BC 复合误差原理**：行为克隆只在专家完美轨迹访问过的状态分布 $d_{\pi_e}(s)$ 上做监督学习；一旦测试时模型在某步哪怕以 $5\%$ 概率点歪进了一个陌生设置页或误触弹窗（$s' \notin d_{\pi_e}$），模型从未见过怎么点返回退出来，错误步步滚雪球，20 步任务成功率按 $0.95^{20} \approx 35.8\%$ 崩塌。
- **OpenMobile（arXiv:2604.15093）双引擎解法**：
  1. **Policy-Switching Rollout（在线策略切换纠偏，类似自动化 DAgger）**：采集轨迹时不让专家从头包办，而是让弱学习者 $\pi_l$ 先走；独立监控器（Gemini-3.1-Pro）盯着动作历史，一旦检测到 $\pi_l$ 偏离目标、点错入口或陷入重复，立即切换专家 $\pi_e$ 接管执行“返回/关弹窗/重回主线”的恢复动作，恢复后再交回 $\pi_l$。消融证实每条轨迹平均捕获 **1.56 次错误恢复**（纯专家蒸馏仅 0.42 次），直接把“怎么从坑里爬出来”编进了 SFT 数据！

### Q69：GUI Agent 经常出现“嘴上说下单/修改成功，实际根本没生效”（虚假完成），你们的业务 Store Verifier 与变异审计（Mutation Audit）是怎么做到零假阳性的？
- **虚假完成有多普遍**：在我们的 369 次实测验收中，单靠“模型调用完成动作并汇报已办妥”，被底层数据库检查当场拦截的虚假完成高达 **190 次**！
- **零假阳性 Verifier 三层构造法**：
  1. **状态差分断言 + 反向不变性断言（State Diff + Negative Invariant）**：改状态任务直接比对开局前快照 $S_0$ 与结束快照 $S_T$ 的目标业务字段（如订单表新增记录的商品 ID、规格、实付金额动态等于初态最高支出等关系式，不写死常数防背题），**同时反向断言未提及的其他订单、收藏夹、购物车未被误删误改**；
  2. **不绑死过程路径**：不检查模型是否必须经过某个搜索页或必须调某个函数，无论纯点屏幕还是调 MCP，只要终态业务数据完全正确即判 `1`，保证多路径探索完全公平；
  3. **四步元验证（审计裁判代码本身）**：每道题上线前强制跑 **① 空操作审计（$S_T=S_0$ 必为 0）**、**② 正例夹具必为 1**、**③ 约束级自动变异审计（自动篡改目标金额、少填一项或改错对象生成 470 个错误终态，实测 470/470 全部 100% 拒绝，假阳性严格为 0）**、**④ 人工双盲一致性抽检（零误放）**。

### Q70：在折叠屏、平板等多形态设备上做 GUI 视觉/UX 异常检测，单张静态截图为什么分不清“真截断”与“正常可滚动边缘”？讲讲你的三阶段主动交互验证算法。
- **核心痛点（观测不可辨识性 Observational Ambiguity）**：在双折、阔折、三折叠屏（如 Mate XT）等特殊宽高比屏幕上，当横向分类栏、轮播卡片或底部列表在容器边缘只露出半个字/半张图时，**单看一张静态截图，连顶级 VLM（乃至人类）都无法 100% 断定它是“固定高度写死导致的真裁切 Bug”，还是“正常可滑动容器尚未滑出来的边缘”**；甚至加上静态布局树也不够，因为实测鸿蒙树里 `text` 永远存完整原文，且自绘容器不暴露真实滚动余量。
- **华为 HarmonyOS `UX-Agent` V2.0 三阶段主动交互验证管线（Active Interactive Oracle）**：
  1. **Stage 1 视觉高召回候选框提案**：VLM 在 `[0, 1000]` 归一化空间检测所有疑似被切文字/图标/组件及被切方向（top/bottom/left/right），保证高召回；
  2. **Stage 2 ArkUI 布局树静态几何复核**：映射物理坐标，先消解前景弹窗外的背景遮挡框与合法省略号 `...`；再比对节点可见框 `bounds` 与原始框 `origBounds` 并向上查裁剪父容器——父容器不可滚或滚动已触底直接确诊 `true_truncation`；父容器可连续滚且有明确余量直接消解 `not_truncation`；自绘或复杂嵌套无法静态确证的标为 `unknown`；
  3. **Stage 3 主动反向滑动探测与高精度原位恢复**：对同方向相邻 `unknown` 框分组，内收避开系统手势边缘与折叠屏铰链中轴线执行反向滑动——若框内像素变化率 $>5\%$ 说明能滑出，暂判 `scrollable`，纹丝不动则确诊 `confirmed` 真截断；**紧接着执行反向回滑恢复现场**，校验恢复图与原图像素差异 $\le 2.5\%$（若滑少/滑过则用一维平移匹配自动补滑修正一次；若仍 $>2.5\%$ 强制标为 `restore_failed` 保留人工复核，绝不因破坏现场而静默漏报缺陷）！端到端 50 页实测召回达 **96%** 且误报接近零。

### Q71：多轮 GUI Agent 每步塞一张高清截图，20 步下来视觉 Token 撑爆显存且推理极慢，怎么设计历史图像滑窗、分辨率分级与摘要保留？
- **核心账本**：一张 1080P/2K 高清图经动态切片（AnyRes）往往消耗 **1,500–3,000 个视觉 Token**；如果不做裁剪，25 步累积近 6 万视觉 Token，不仅触发显存 OOM、TTFT 飙到十几秒，而且 15 步之前的旧界面截图早已过期，反而干扰当前页定位。
- **工业级三层多模态上下文管理策略（MobileGym++ 与主流 CUA 标配）**：
  1. **近期图像滑窗保留（Image Sliding Window = 最近 $K=2\sim 3$ 帧）**：上下文里**只保留当前最新帧 + 前 1～2 帧高清原始截图**（用来对比刚刚那一下点击到底生没生效、有没有发生局部位移），第 $t-3$ 步之前的历史截图全部从消息列表中剥离；
  2. **结构化动作与状态笔记接力（Textual Action-Observation Trace + Note Tool）**：虽然剥离了 3 步前的旧图片，但**完整保留每一步的文本思考（Thought）与动作记录（Action）**，并提供显式 `note / extract` 工具让模型在跨应用比价（如先看京东价格再去淘宝比价）时把查到的关键数字主动写进常驻文本工作记忆；
  3. **渐进分辨率分级（Foveated / Multi-Res Encoding）**：当前帧用高分辨率保证小图标精准 Grounding，前一帧对照图降采样为低分辨率缩略图（仅需 256 tokens），关键小区域按需局部 Crop 放大。

### Q72：推理型 VLM（带长 Thinking）在跑 CUA 任务时出现“思考太长撑爆上下文”或“过度脑补界面状态（Echo Trap）”，怎么解决？
- **你亲手抓到的真实痛点**：OpenCUA 等工作证明适度反思有助于泛化，但我们在 **MobileGym++** 实测中发现，开启无约束长 Thinking 后，**有 23 道任务直接因为模型每步狂写几千字纠结推理，还没走到第 15 步就把总上下文预算彻底撑爆报错**；且在多轮 RL 中容易陷入 RAGEN 论文指出的 **Echo Trap（回声陷阱）**——模型不看最新截图变化，顺着自己上一轮的错误假设计续脑补循环！
- **四招精准根治**：
  1. **历史轮次 `reasoning_content` 跨轮折叠（Strip Past Thinking）**：当前第 $t$ 步生成时允许模型充分 `<think>`，但进入第 $t+1$ 步拼装历史上下文时，**只保留历史轮次的精简结论摘要与实际执行的 `action`（剥离前 $t-1$ 步冗长的内心纠结草稿，仅在需透传加密 `thought signature` 时保留轻量元数据）**，立省 70%+ 上下文空间；
  2. **按步骤复杂度自适应思考预算（Adaptive Reasoning Effort）**：常规确定性点击（点搜索框、点返回）用短思考（100 tokens 内），只有检测到连续动作未生效、跨应用信息汇总或最终提交核对时才展开深度推理；
  3. **强制视觉锚定思考模板（Grounded Structured CoT）**：规定 `<think>` 第一句必须先客观陈述**“上一动作后当前截图实际发生了什么可见变化”**，打断脱离画面的纯文本自嗨脑补；
  4. **训练侧采用 DAPO Overlong Shaping + 轨迹效率 OE 筛选**：在 SFT 蒸馏和拒绝采样阶段优先挑选 **Outcome Efficiency ($\text{OE}$) 高、可交付后冗余率 $R_{\text{post}}$ 低**的干脆轨迹，抑制无效车轱辘话。
