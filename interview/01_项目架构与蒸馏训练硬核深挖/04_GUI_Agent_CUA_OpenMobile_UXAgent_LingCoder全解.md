## 一、CUA（Computer-Use Agent / GUI Agent）核心架构与技术深水区

### 1. CUA 与传统纯文本 API Agent 的本质差异
- **观测空间（Observation Space）异构且高噪**：文本 Agent 读的是确定性 JSON，而 CUA 面对的是 $W \times H$ 渲染像素截图（Screenshot）、操作系统无障碍树（macOS Accessibility Tree / Android XML / HarmonyOS ArkUI Dump / Web DOM）或两者的融合（Set-of-Mark 编号框）。同一条业务信息在 API 里是一个键值，在 GUI 里可能是几十像素高、受滚动条与弹窗遮挡的局部图形。
- **动作空间（Action Space）连续与离散耦合**：既要决策离散动作类别（`click / double_click / drag / scroll / type / key / wait / ask_user / finish`），又要完成精确的空间定位（Visual Grounding，输出目标节点 ID 或屏幕归一化坐标 $[0, 1000]^2$），还要在混合模式下权衡“点 5 步屏幕”与“调 1 次原生 MCP/Bash 工具”。
- **部分可观测与状态异步（POMDP）**：点击后存在网络加载、动画过渡、权限弹窗抢焦点，`wait` 本身就是关键决策；且单步准确率 $p=0.95$ 在 $T=20$ 步长程任务中若无错误恢复机制，累计成功率 $p^T = 0.95^{20} \approx 35.8\%$ 会断崖下跌。

### 2. 为什么不能无脑信无障碍树（AX Tree / XML），也不能裸预测绝对坐标？（你的一手研究洞见）
- **裸预测绝对坐标的缺陷**：绝对像素 $(x, y)$ 强耦合分辨率（1080P 换到 2K 或折叠屏展开态直接偏航），且不可解释、无法幂等重放。因此视觉定位至少要用 `[0, 1000]` 相对归一化坐标，或采用两阶段粗细裁剪、专用 Grounding 头（如 GUI-Actor 基于视觉 Patch Attention 实现免坐标定位）。
- **国产桌面（macOS CUA）与移动端 App 无障碍树（AX Tree）失真的一手实证（你近期在研主线）**：
  - 在桌面 macOS CUA 体系中，工程上通常采用 **上层规划评测器（Agent Brain + 程序化文件/状态检查器）与底层 OS 原生驱动（基于 `AXUIElement` 树采集 + Quartz `CGEvent` 键鼠注入）解耦** 的架构。业界统计流行 macOS 应用完整支持 AX 的仅约 **36%**（Screen2AX），且最新研究（arXiv:2607.04334）表明多模态模型在画面与结构树冲突时高达 **88%** 概率盲信过期/错误结构树（Perception-Fusion Gap），一旦首步信错自恢复率不足 3%。
  - 我们在实测国产桌面软件（WPS、剪映、PS 等）与移动端 App 时抓到了三类致命结构陷阱：① **迷你浮窗焦点劫持**（如 WPS 启动弹出登录浮条，驱动拉到的前台窗口 AX 树只有 `78×40` 大小，整个主文档完全不可见）；② **关键控件属性/节点漏标**（如 WPS“保护工作表”任务 10 项程序化检查过了 9 项，唯独对话框里的复选框在 AX 树里读不到勾选状态或根本没节点，哪怕换顶配 `claude-opus-5-5` 依然盲猜坐标反复点歪）；③ **自绘 Canvas / WebView / XComponent 黑洞**（如 WPS 图表对话框在树里一片空白、剪映导入面板不暴露 AX 操作、大众点评约 25% 页面含无子节点的自绘容器，且 5.4% 节点 `visible=true` 但透明度为 0）。
- **最优混合架构设计（有代价的通道路由 Cost-Aware Modality Routing + 动作三级安全约束）**：
  1. **轻量级 AX 可信度预判与按需视觉切换（不浪费步数与调用预算）**：如果每一步都额外调 VLM 做截图裁剪一致性门控，单步模型调用次数会暴增 1.8–5.5 倍；因此我们先用零成本结构特征（焦点窗口面积异常如 `78×40`、大片空白容器无叶节点、RapidOCR 文本块与 AX 文本节点严重失配、或点击后连续两步树与像素零变化）即时识别“树失真”，在树可信时走高速精准的 `element_id` 语义动作，树失真时一步切换至高分截图视觉 Grounding，兼顾高成功率与低推理开销。
  2. **动作空间双模兼容与副作用分级**：`target` 同时支持 `element_id` 与 `[0, 1000]` 归一化坐标；显式拆分只读动作 `extract`（失败可自由幂等重试）、状态写动作（执行前重拉局部 bounds 校验 IoU 防动画跳变误点）与 `ask_user`（遇登录弹窗、验证码、支付授权主动挂起求助）。

## 二、OpenMobile（v1）与 OpenMobile-2（MobileGym++）完整技术闭环

### 1. OpenMobile v1（arXiv:2604.15093）：无须人工标注的任务与错误恢复轨迹合成
- **痛点**：开源 GUI Agent 落后闭源大模型 30+ 个点，卡在缺少**跨功能复杂指令**和**错误恢复轨迹**（纯蒸馏专家成功轨迹只有正确路径，学生模型一旦点歪一步就崩）。
- **阶段一：探索与合成解耦 + 全局环境记忆（Global Environment Memory）**
  - 先在 20 个 Android 应用上做轻量 10 步随机游走采集屏幕转换序列；
  - 用 **pHash（$\tau=0.95$）聚类去重**构建状态节点，VLM 提取每个控件功能语义，建立**邻接转移图（短期记忆）+ 全局功能 Embedding 索引（长期记忆，Top-30 多样性检索）**，驱动 LLM 合成跨页面、跨模块的复合任务（2,800 条指令，与 AndroidWorld 测试集高相似占比仅 3.5%，零泄漏）。
- **阶段二：策略切换轨迹采集（Policy-Switching Rollout）**
  - 让弱学习者模型 $\pi_l$ 主跑，监控器（Gemini-3.1-Pro）实时审视动作历史；一旦发现 $\pi_l$ 偏航、误点或原地打转，立即切入强专家模型 $\pi_e$ 接管走回正轨，再交还给 $\pi_l$。
  - **硬核消融数字**：每条轨迹平均捕获 **1.56 次真实错误恢复行为**（纯专家蒸馏仅 0.42 次）；训出的 `Qwen3-VL-8B` 在 AndroidWorld 斩获 **64.7%**（超越开源基线 ScaleCUA 27.2% 两倍以上）。

### 2. OpenMobile-2 / MobileGym++：从静态模仿走向可重置环境、GUI+MCP 混合与多轮 RL
- **环境基建规模**：
  - **63 个高保真可重置全功能移动应用**（新建 35 + 升级 28，涵盖电商、出行、社交、记账、办公等，中位数 **37 个路由、88 条状态转移**），前端界面与确定性业务 Store 强绑定，支持毫秒级干净初态重置与固定模拟时钟。
  - **51 个应用挂载 333 个前台原生 MCP 工具**（其中 29 个厚应用手写 289 个深度工具，运行时**仅暴露当前前台应用的函数表**，且严禁做成“一键返回最终答案”的作弊接口，敏感提交仍须配合界面完成）。
- **业务 Store 级严格 0/1 Verifier（彻底根治“幻觉交卷”）**：
  - 写操作任务直接比对初态与终态业务 Store 的结构化字段差分 + 反向不变性断言（禁止误改其他订单/购物车）；读操作核验笔记中的动态计算关系式与反干扰词断言；**不绑死过程路由**，对纯 GUI 路径与 Hybrid 路径完全公平。
  - **元验证（审计裁判本身）**：空操作审计 100% 判败 + **470 个字段篡改/半途而废变异终态 100% 拒绝（假阳性 = 0）**；在 369 次实跑中精准拦截 **190 次**“模型嘴上说办妥了、实际数据库根本没改”的虚假完成！
- **Bench 215 官方锁表核心发现：`GUI-only` vs `GUI+MCP Hybrid` 的模态路由悖论**
  - **强模型显著受益**：Gemini 3.1 从 GUI-only **58.6% (126/215)** 提升至 Hybrid **68.4% (147/215)**（工具救回 33 题，误用害死 12 题）。
  - **小模型 `Tool Hurts`（模态路由失调）**：`Qwen3.5-9B-mcp` 在 GUI-only 上 37.7%，上 Hybrid 仅 39.1%——**工具救回 30 题的同时害死了 27 题！** 且在 306 个候选工具里有 199 个从未被激活（工具盲区）。核心败因是小模型分不清工具的**副作用边界**（例如调用了只做预填或查询的 MCP 函数，没看清数据尚未落库就直接调 `finish` 交卷），这揭示了混合智能体后训练必须做**反事实信用分配与模态等价性对齐**。
- **大规模训练闭环（11.6k SFT + 2,475 RL 题 + DAPO -> OpenMobile-27B）**：
  - SFT 阶段采用“弱探索 + 强接管”合成 **11,643 条**高质量多模态轨迹（HuggingFace 开源全量数据集达 11.8 万行 / 59.2 GB，模型 `OpenMobile-27B`）。
  - RL 阶段在 **2,475 道**带可执行 Verifier 的任务上采用 **DAPO** 训练：保留最近 3 步高清截图防显存与上下文爆炸，对截图与工具返回设 `response_mask=0`，剔除环境崩溃题防零分梯度污染，并用 Clip-Higher + Dynamic Sampling 解决长链路组内全错无梯度与熵坍缩问题。

## 三、华为 HarmonyOS 多设备 `UX-Agent`：主动交互式验证（Active Interactive Oracle）

- **核心技术贡献**：解决跨 5 类设备形态（直板、平板、双折、阔折、三折 Mate XT）下“视口边缘文字/组件究竟是**真截断缺陷**还是**正常可滚动边缘**”的单帧不可判定问题。
- **V2.0 三阶段算法与工程落地（TypeScript 全栈实现）**：
  1. **Stage 1 视觉高召回候选检测（`detectImage`）**：在 `[0, 1000]` 归一化坐标下召回疑似截断框与被切方向，无框直接判 `ok`。
  2. **Stage 2 ArkUI 布局树几何约束复核（`verifyTextTruncations`）**：过滤前景弹窗外的背景遮挡框与合法省略号；比对控件可见框 `bounds` 与排版原框 `origBounds`，沿父链回溯裁剪容器——不可滚动或滚动到底直接确诊 `true_truncation`，有连续滚动余量直接消解 `not_truncation`，自绘或复杂嵌套静态不可判则标 `unknown`。
  3. **Stage 3 主动微滑动探测与高精度原位恢复（`runActiveSlideVerification`）**：将同行/同边缘带 `unknown` 框合并分组，内收避开系统侧滑返回区与折叠屏铰链中轴线执行反向滑动；框内像素平均变化率 $>5\%$ 暂判可滑，否则确诊截断；随后执行反向回滑恢复现场，要求恢复后全屏像素差 $\le 2.5\%$（超差则用一维平移匹配判断滑少还是滑过并自动补滑修正一次；若仍 $>2.5\%$ 强制标为 `restore_failed` 交人工，绝不漏报）。

## 四、LingCoder 代码大模型（Qwen3-30B-A3B MoE）训练与评测基石

- **数据侧**：建立 285 万条多语言代码语料的 `Context Tag × Task Type` 九宫格消歧规范，并用 AST + DeepSeek-V3.2 蒸馏补齐复杂第三方库调用短板。
- **训练与系统侧**：在 SenseCore 4 节点 × 8 卡（32 GPU）上执行 Python/C++/Java/JS/Go/Rust 六组 MoE 消融训练（1A–1F），掌握 MoE 负载均衡辅助损失、DeepEP 跨节点专家通信排障、大模型 Checkpoint 保存防主机 OOM 以及训练格式转 HuggingFace/vLLM 专家权重映射核验。
