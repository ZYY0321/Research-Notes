## 二、管线 ③ 深度拆解：多轮 Agent SFT 轨迹蒸馏为什么“直接训会训坏”？怎么修？

这是面试官最爱追问的 **“你们蒸馏强模型 Agent 轨迹做 SFT 时踩过什么真坑？”** 标准答案：

### 1. 现象：直接拿 Opus 4.7 导出的 1.6 万条轨迹训 SFT，学生模型出现两个诡异坏行为
- **症状 A（发完就停）**：模型在 `assistant.content` 里输出了 `<file_action>` 预播报块后，不发 `tool_calls` 直接结束本轮，导致任务半途早停。
- **症状 B（干脆不发）**：模型调用 `write_file` 写文件时，跳过系统协议要求的 `<file_action>` 预播报。

### 2. 三层溯源侦破（对照原始 `result.jsonl` 逐字节核验）
最初怀疑是导出脚本 `export_trace_to_openai.py` 截断了数据，但逐字节比对证实**导出脚本完全忠实，病根全在上游采集与生成期**：
1. **运行时子任务丢失 Bug（幸存者偏差）**：旧版运行时 `subtask_counter` 计数覆盖缺陷导致约 **28% 的子任务轨迹在落盘导出前被静默丢弃**，而丢掉的子任务里 **74% 恰好是 `<file_action>` 最密集、最规范的大纲与风格设计阶段**，导致训练集里正例被大幅稀释（仅占全部 assistant 消息的 1.5%–3.8%）。
2. **System Prompt 混入残缺变体**：最大的 `0629_query` 批次（7,887 条）中，**42.2%（3,329 条）** 因运行时组装分支不一致，漏掉了「文件操作预播报协议」完整规则段，只剩一个裸标签名，造成同批数据监督信号自相矛盾。
3. **悬空 `<file_action>` 与漏发并存**：
   - 在幸存轨迹中，`write_file` 调用有 **65.2%–88.7%** 未前置 `<file_action>`（教会模型“可以省掉不发”）；
   - 反过来，在所有包含 `<file_action>` 的消息中，有 **12.5%–26.3%** 同条消息 `tool_calls` 为空，且 **100% 处于轨迹最后一条**！拆分发现 68% 是子任务收尾轮模型违规把上一轮写过的文件重报一遍再接 `<subtask_result>` 终止，21% 是生成期网关解析工具调用失败导致尾巴残留 `</invoke>`。这等于直接喂给模型 `file_action → EOS` 的错误停止信号！

### 3. 六步自动化数据修复管线（`docs/ppt_sft_data_quality/scripts/`）
我们没有简单删数据（删掉会损失宝贵的 Opus 长程规划轨迹），而是开发了 6 步确定性+小模型协同修复流水线：
1. **协议补齐（Q1）**：对 3,329 条残缺 System Prompt 精准在 `## skill / SOP` 锚点前注入规范协议全文。
2. **缺失补全与上下文摘要生成（Q2）**：扫描全部 `write_file` 及可静态解析出写文件目标的 `execute_code`/shell 调用，自动补齐 `<file_action><target>...<action>CREATE/UPDATE<summary>...</file_action>`；其中 `<summary>` 喂入该轮 `reasoning_content` + 进度正文 + 写入代码，调用 **Qwen** 动态生成自然贴切摘要（硬约束禁止泄漏内部文件名、路径、`pptid` 或工具名），合计新增 **10,262 处**。
3. **悬空剥离（Q3）**：剔除全部 **883 处** 无 `tool_calls` 的末轮悬空 `<file_action>` 块（剥离后若整条消息为空则连带删除坏收尾轮 83 条）。
4. **C5 目标对齐**：修复 140 处预播报目标与同轮实际写入文件不一致的错位（重定向或删除纯读孤儿）。
5. **去机械化重写 `ask_user`**：批测采集时自动回复产生了 **5,184 处** 机械 `<ask_user_answer>` JSON 串，全部用 Qwen 改写为保持原确认语义的自然人类口语回复，防止模型上线后对真实用户口语水土不服。
6. **C1–C5 自动化门禁质检**：最终输出无模板 **9,901 条** + 模板 **6,373 条**，C1（协议完整率）100%、C2（`write_file` 预播报覆盖率 10,542/10,542）**100%**、C3（悬空数）**0**、C5（真错配）**0**，Qwen 盲抽合格率 **98%**。

## 三、管线 ④ 深度拆解：Agent 全轨迹 DPO 构造与工程铁律

### 1. 为什么要从「单页抽取 DPO」升级到「全轨迹 DPO」？
早期做 PPT DPO 只抽最后单页 HTML 生成这一步构造偏好对，模型能把单页 CSS 写好看，但在外层多轮 Agent 编排中依然会犯 **DSML 工具协议文本泄漏（把 `<｜DSML｜invoke>` 当普通正文吐出）、路径前缀写错（漏写 `local://`）、`info_pack.json` 反复语法报错自救耗尽 2.5 小时、或未生成页面就虚假汇报完成（`done_no_html`）**。只有对整条多轮决策轨迹做偏好对齐，才能根治长程动作退化。

### 2. 正负样本配对策略（On-Policy / Near-Policy Negative Mining）
- **输入题集**：从 Claude Opus 4.7 成功轨迹库中抽取 `agent=main` 的 **1,879 条**真实复杂 Query（剔除 86 条依赖缺失本地附件的脏题）。
- **Chosen ($y_w$)**：Opus 4.7 在 `ppt-skill-v1.1` 下跑出的完整高分轨迹（含完整 `reasoning_content` 与子任务轨迹，共 10,975 行）。
- **Rejected ($y_l$)**：待对齐的自研底座（如 `SenseNova-Flash-284B-v14` / `Flash-Lite`）在**完全相同的分支代码、相同的工具开关（禁外网波动工具以锁死确定性环境）、相同的 `skills` 模板库**下跑出的自采样轨迹。
- **Loss Mask 关键点**：无论是 SFT 还是全轨迹 DPO，计算序列对数概率 $\log \pi_\theta(y|x)$ 时，**System Prompt、User 输入以及所有 `role="tool"` 的环境返回结果一律设置 `mask = 0`**，只累加模型自身生成的 `reasoning`、文本回复与结构化 `tool_calls` token 的 logprob！

### 3. 三条血泪换来的分布式采集纪律
1. **A+C 双端点强一致**：PPT Agent 主循环调的是主 LLM 端点（A），而沙盒容器内跑 `html_page_generate_batch.py` 调的是脚本内置端点（C）。宿主机的 `export` 环境变量进不了容器，必须物理拷贝 `skills_<model>/` 修改 `_html_llm_direct.py`，否则采出来的轨迹“脑子是自研模型、手写出来的 HTML 却是 Opus”，直接污染偏好信号。
2. **协议兼容性前置探活**：开跑前必须同时测字符串 `content`、**Block 数组 `content`** 以及 `tool_choice={"type":"none"}`——例如实测捕获 `Flash-Lite :208` 在 `tool_choice=none` 时直接报 HTTP 400，严禁私自篡改 `provider` 绕过掩盖端点缺口。
3. **客户端 FD 雪崩防护与终态门禁**：控制单机并发 + `SANDBOX_CREATE_WAVE_SIZE=16` 错峰建会话；回收数据时严禁看 `tqdm ok` 或 `case_done`，只认沙盒回传目录实打实产出非空 `page_*.html`（或 `deck_html_pages > 0`）的轨迹对。

## 四、管线 ② 深度拆解：51,981 张多模态图文设计二次蒸馏（L2/L3 耦合合成）

当业务回流数据“只有文字大纲、没有美学排版描述”时，如何低成本合成高质量多模态图文训练数据？
1. **设计先验提纯（粗糙野生数据 → 纯净设计卡）**：爬取的 19,150 条外部图像 Prompt 充斥画质废话与具体物体名词；先用正负向关键词规则粗筛至 732 条，再用 LLM 剥离具体业务名词、只保留“配色方案 + 网格版式 + 视觉层级 + 图表组件”蒸馏出 **495 条 L2 纯设计卡**，加上人工精拆的 **300 条 L3 设计卡**组成高质量设计池。
2. **LLM 语义择优融合（5 选 1）**：对 36,573 页回流结构化内容，每页随机抽取 5 张设计卡（保底 2 张 L3），让 Claude Sonnet 根据“差旅超支柱状图”“产品发布时间线”等内容语义挑出最匹配的 1 张设计卡，融合改写为 260 词英文生图 Prompt 送入 `gpt-image-2`（1536×864），并附 `content-only` 无设计对照组验证增益。
3. **规则前置 + LLM 兜底 13 类版式打标（G6-01～G6-13）**：封面/目录/过渡/致谢用确定性规则秒判；正文页靠显式消歧规则（如“多栏并列 ≠ 对比页 G6-07”“含坐标轴图表无条件优先归数据图表页 G6-06”）交由 `temperature=0` 的 Sonnet 打标，最终产出 **51,981 张**高质量图文配对资产。

## 五、SenseNova 模型命名背后的完整后训练配方

看到实验看板上的模型名（如 `SenseNova-Flash-Lite-20260727-v39-fp8-step4k-dpov2-mtp` 或 `sensenova-flash-320b-v16-step500-opd-step160-dpo-v2`），一条线串起现代大模型后训练全栈：
1. **Continue Pretrain（域继续预训练）**：按 `coding_ratio` 配比注入代码、数据分析与文档语料，夯实底座结构化生成与代码能力。
2. **Agentic SFT（监督微调）**：用上述清洗后的多轮工具与 Skill 轨迹教会模型私有协议（`<file_action>`、结构化 Tool Call、子任务拆解）。
3. **OPD（On-Policy Distillation，在策略蒸馏）**：短步数（如 `step160`）关键过渡阶段——**由学生模型自己 rollout 采样轨迹前缀，在学生真实走到的状态分布上请求教师模型给出逐 token 概率分布算反向 KL 散度**，专门解决离线 SFT 的 Exposure Bias（一旦偏离专家轨迹就不会自救）。
4. **DPO / KTO（偏好对齐）**：利用全轨迹成对偏好（DPO）或单边好坏标注（KTO）压制伪工具调用、JSON 格式崩溃与幻觉早停。
5. **MTP + FP8（推理架构与精度协同）**：挂载 Multi-Token Prediction 多词预测头在训练期加密监督信号、推理期充当自投机解码草稿头（提速 1.5–1.8×），配合 FP8 量化实现百亿/千亿参数高吞吐在线服务。
