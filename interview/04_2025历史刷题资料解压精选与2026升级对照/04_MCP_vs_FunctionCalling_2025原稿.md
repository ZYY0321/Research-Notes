### 一、 什么是 Function Calling？ \(基础能力\)

**Function Calling** 是一种技术或API特性，它允许大型语言模型（LLM）在对话过程中，识别出需要外部工具或数据来完成任务的时刻，并生成一个结构化的数据对象（通常是JSON格式），来请求执行一个特定的函数。

**工作流程 \(The "How"\):**

1. **用户提问**：用户向LLM提出一个问题，例如“北京今天天气怎么样？”。

2. **模型决策**：LLM通过微调（Fine\-tuning）学会了识别哪些任务是它自身知识库无法完成的。它知道自己没有实时天气数据，因此决定需要调用一个外部工具。

3. **生成调用请求**：模型不会直接回答，而是输出一个结构化的JSON对象，像这样：

```Plain Text
{
  "name": "get_weather",
  "arguments": {
    "location": "北京"
  }
}
```

4. **外部执行**：你的应用程序代码会捕获这个JSON，解析出函数名 `get_weather` 和参数 `location: "北京"`，然后实际执行这个函数（比如去调用一个天气API）。

5. **返回结果**：函数执行后得到结果，例如 `{"temperature": "25°C", "condition": "晴"}`。这个结果被格式化后，再次发送给LLM。

6. **最终回答**：LLM接收到函数返回的天气信息，然后用自然语言向用户回答：“北京今天天气晴朗，温度是25摄氏度。”

**核心特点：**

- **原子性 \(Atomic\)**：它是一个单一、独立的“请求\-执行\-响应”循环。

- **战术性 \(Tactical\)**：它解决了LLM执行具体、单一动作的能力问题。

- **基础构建块**：是构建任何能够与外部世界交互的AI应用的基础。

### 二、MCP协议概述：为AI打造的通用“USB\-C”接口

MCP，全称为“**模型上下文协议**”（Model Context Protocol），是由Anthropic公司于2024年11月25日推出的一个开源标准。它的核心目标是为人工智能（AI）助手和外部数据系统之间建立一个通用的、标准化的连接方式。

您可以将MCP理解为**人工智能应用的“USB\-C”端口。就像USB\-C为不同的电子设备提供了统一的连接和充电标准一样，MCP旨在为AI应用（如Claude或ChatGPT）提供一个标准化的途径，用以连接和交互于各种外部系统，包括：**

- **数据源：** 例如本地文件、数据库、Google Drive等。

- **工具：** 例如搜索引擎、计算器、代码库（GitHub）、项目管理工具（Slack）等。

- **工作流：** 例如特定的提示或自动化流程。

### 三、MCP为何如此重要？

在MCP出现之前，每当需要将AI模型连接到一个新的数据源或工具时，开发者通常都需要进行定制化的开发，这种方式不仅耗时耗力，而且难以规模化。MCP的出现解决了这一挑战，为生态系统中的不同角色带来了显著的好处：

- **对于开发者：** MCP大大降低了构建或集成AI应用时的开发时间和复杂性。开发者不再需要为每一个数据源维护一个独立的连接器，只需遵循MCP这一标准协议即可，从而可以更专注于创造性的工作。

- **对于AI应用和智能体：** 通过MCP，AI应用可以接入一个由数据源、工具和应用程序组成的庞大生态系统。这极大地增强了AI的能力，使其能够获取完成任务所需的上下文信息，从而提升终端用户体验。

- **对于终端用户：** MCP最终将带来功能更强大、更个性化的AI助手。这些AI应用可以在获得授权后，安全地访问用户的个人数据（如谷歌日历、Notion笔记）或企业内部数据，并代表用户执行具体操作，成为真正意义上的智能助理。

### 四、MCP的架构和主要组成部分

MCP的架构设计非常直接，它定义了一种安全的、双向的连接。其核心包含两个主要角色：

**MCP服务器（Servers）：** 开发者可以将他们**的数据源或工具通过MCP服务器暴露出来**。例如，可以为公司的内部数据库或Slack工作区构建一个MCP服务器。

**MCP客户端（Clients）：** AI应用程序（如Claude桌面应用）作为MCP客户端，可以连接到这些服务器来获取数据或调用工具。

为了推动该协议的应用，Anthropic发布了三个关键组成部分：

- **协议规范和SDK：** 提供了详细的技术文档和软件开发工具包，帮助开发者理解并实现该协议。

- **Claude桌面应用的本地服务器支持：** 用户可以直接在Claude桌面应用中连接和测试本地的MCP服务器，方便地将本地数据和系统与AI连接。

- **开源的MCP服务器代码库：** Anthropic提供了一系列预先构建好的MCP服务器，用于连接Google Drive、Slack、GitHub、Postgres等常用系统，帮助开发者快速上手。





### 五、MCP实现流程

#### 高层概述：MCP工作流程类比

可以将整个MCP工作流程想象成一个高效的项目经理（**AI应用**，即**MCP主机**）与多位外部专家（**MCP服务器**）协作的场景。

这位项目经理要完成复杂任务，需要与数据库专家、文件系统专家、天气信息专家等进行沟通。为了避免为每位专家学习一套独特的沟通方式，经理决定采用一套标准化的沟通协议——这就是MCP。

整个协作流程遵循以下四个逻辑步骤：

1. **建立联系与互报家底（握手）：** 经理给一位专家打电话，双方先自我介绍，确认讲的是同一种“语言”（协议版本），并明确告知对方自己各自擅长什么、能做什么。

2. **索要服务菜单（发现）：** 经理问专家：“你现在具体能提供哪些服务？” 专家会提供一份详细的服务（工具）清单。

3. **下达具体指令（执行）：** 经理根据菜单，向专家下达一个明确的任务，并提供所有必要的信息。专家完成任务后，将结果汇报给经理。

4. **获取实时动态（通知）：** 如果专家的服务菜单有变动（比如新增了一项技能），他会主动打电话告知经理，确保经理手里的信息永远是最新的。

接下来，我们将深入技术细节，看看这四个步骤在MCP中是如何实现的。

#### MCP架构中的核心参与者

- **MCP主机 \(Host\):** 指的是AI应用程序本身，例如Claude桌面应用或是一个集成MCP的VS Code编辑器。它负责管理整个流程，决定何时连接到哪些服务器。

- **MCP服务器 \(Server\):** 这是一个提供数据或功能的程序。它可以是连接您本地文件系统的服务器，也可以是连接远程数据库或Sentry、GitHub等API的服务器。服务器可以运行在本地，也可以在远程云端。

- **MCP客户端 \(Client\):** 由主机为它连接的**每一个**服务器所创建的组件。它与一个服务器维持着一对一的专用连接，并负责两者之间的通信。

#### 双层通信架构

MCP的通信被巧妙地分为两层，以实现关注点分离：

1. **传输层 \(Transport Layer\)：** 解决\*\*“如何传输”\*\*的问题。这是消息的物理投递方式。它好比是选择使用“内部快递员”（`Stdio transport`，用于同一台机器上的进程通信）还是“国际物流”（`Streamable HTTP transport`，用于与远程服务器通信）。这一层也负责安全认证和授权。

2. **数据层 \(Data Layer\)：** 解决\*\*“传输什么”\*\*的问题。这是双方对话的具体内容和语言。它规定了所有请求和响应都必须遵循 **JSON\-RPC 2\.0** 格式。这确保了无论使用哪种传输方式，客户端和服务器都能准确理解对方消息的含义。

#### MCP详细工作流程四步走

以下是文档中示例所展示的核心工作流程，重点聚焦于数据层。

##### 第一步：握手（初始化与能力协商）

在进行任何实质性交互之前，客户端和服务器必须建立连接，并相互了解对方的能力。

- **具体操作：** 客户端向服务器发送一个 `initialize` \(初始化\) 请求。

- **交换的关键信息：**

    - `protocolVersion`：双方确认使用兼容的MCP协议版本，避免鸡同鸭讲。

    - `clientInfo`：客户端自我介绍，如“我是 example\-client v1\.0\.0”。

    - `capabilities`（**至关重要**）：双方在此声明各自的能力。

        - **客户端**可能会说：`"elicitation": {}`，意思是“我具备向最终用户请求输入的能力”。

        - **服务器**可能会回应：`"tools": {"listChanged": true}`，意思是“我能提供工具，并且当我的工具列表变化时，我能主动通知你”。它还可能声明`"resources": {}`，表示能提供数据资源。

- **为何重要：** 这一步确保了双方的兼容性，并让AI主机（应用程序）清楚地知道哪个服务器能提供哪种功能，避免了无效的请求。

##### 第二步：发现（“你都能为我做什么？”）

初始化成功后，客户端需要了解服务器当前具体能提供哪些功能。

- **具体操作：** 客户端向服务器发送 `tools/list` \(列出工具\) 请求。

- **服务器的响应：** 服务器会返回一个结构清晰的工具列表。列表中的每一个工具都包含详细的元数据：

    - `name`: 工具的唯一机器可读名称（例如 `weather_current`）。

    - `title`: 人类可读的名称（例如“获取当前天气”）。

    - `description`: 详细描述工具的功能，帮助大语言模型（LLM）判断何时调用它。

    - `inputSchema`: 对工具所需输入参数的严格定义（例如，`location`是必需的字符串，`units`是可选的字符串）。

- **为何重要：** AI主机会收集所有已连接服务器的“服务菜单”，整合成一个统一的“可用能力注册表”。这让底层的LLM能够全面了解自己可以执行哪些操作。

##### 第三步：执行（“请帮我做这件事。”）

当AI根据对话上下文，判断需要使用某个工具时，就会触发执行操作。

- **具体操作：** 客户端向服务器发送一个 `tools/call` \(调用工具\) 请求。

- **请求的细节：**

    - `name`: 要执行的工具的精确名称（例如 `weather_current`）。

    - `arguments`: 一个JSON对象，包含完全符合该工具`inputSchema`定义的输入参数（例如 `{"location": "San Francisco", "units": "imperial"}`）。

- **服务器的响应：** 服务器在本地执行相应的功能（如查询天气API），然后将结果封装在一个结构化的`content`数组中返回。这种格式支持返回文本、图片等多种类型的内容。

- **为何重要：** 这是AI与外部世界交互的核心步骤。通过调用工具，AI能够获取实时数据或执行具体动作，并将获得的结果反馈给LLM，作为生成下一步响应的依据。

##### 第四步：实时更新（通知）

现实世界是动态的——服务器上的工具可能会新增、被修改或暂时不可用。MCP通过通知机制优雅地处理了这种情况。

- **具体操作：** 服务器**主动**向客户端发送一条 `notifications/tools/list_changed` \(工具列表已变更\) 的消息。请注意，这是一个**通知**，不是请求，所以它没有`id`，客户端也不需要对此消息进行回复。

- **客户端的反应：** 客户端收到这个通知后，就明白了自己缓存的工具列表已经过时。它的标准操作是立即回到**第二步**，重新发送一个`tools/list`请求，以获取最新的工具清单。

- **为何重要：** 这个机制使得整个AI系统反应非常灵敏和高效。AI应用无需通过反复轮询（不停地问“有变化吗？”）来检查更新，而是在变化发生时被即时告知。这确保了LLM始终基于最准确的可用能力进行决策。

### 总结

- **Function Calling** 是一个已经广泛应用的技术，让LLM具备了“手”和“脚”，能够操作外部工具。它是实现“能干活”的AI的基础。

- **MCP** 则是一个更前沿的、偏向于AI Agent架构设计的概念，它为LLM装上了“大脑的执行中枢”，指导这些“手”和“脚”如何有条不紊、深思熟虑地协同工作，以完成仅靠单次调用无法解决的复杂任务。

因此，当你构建一个简单的、只需要单步工具使用的应用时（比如聊天机器人查天气），你主要是在使用 **Function Calling**。而当你构建一  个复杂的AI Agent，需要它自主规划、反思并最终完成一个宏大目标时，你实际上是在设计和实现一个 **MCP** 框架，而这个框架的核心执行环节，离不开 **Function Calling** 的支持。
