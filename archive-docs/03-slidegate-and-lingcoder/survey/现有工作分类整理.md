二、按评估任务分类

任务1：文字/文档转PPT生成质量评估

内容质量评估：
- SlidesGen-Bench的QuizBank方法：将生成PPT解析为Markdown，让LLM仅凭Markdown回答预设问题，准确率作为内容质量代理。问题：只检测信息是否在文本层面出现，无法检测信息是否被视觉正确呈现，也无法检测幻觉。
- EvoPresent的ROUGE-L：计算生成脚本与源论文的最长公共子序列。问题：只适用于有明确参考原文的场景（如论文转PPT），不适用于从用户需求自由创作的PPT。
- PresentBench的内容完整性+正确性+保真度：将内容拆成三层分别checklist核查，是目前最严格的内容评估。问题：依赖背景材料，且需要为每个实例定制checklist，构建成本极高，无法大规模推广。
视觉质量评估：
- 公式计算（SlidesGen-Bench）：从截图提取像素级特征，计算色彩和谐度、对比度、视觉节奏等。已知问题：在1326条人类排序数据上验证，与人类偏好一致率仅48.5%，接近随机，失去了作为评估信号的价值。
- LLM-judge（PPTAgent/AutoPresent/PPTArena）：输入截图，让LLM按rubric打1-5分。已知问题：AutoPresent自己报告Layout维度几乎所有PPT都打满分（模型看不出元素是否超出页面边界）；Color维度只能检测文字可读性，无法感知配色美学。
- 细粒度缺陷检测（SlideAudit/PresentBench）：用MLLM做Yes/No判断是否存在特定缺陷。已知问题：PresentBench报告人工标注一致性仅约0.6；SlideAudit的实验显示，在有结构化坐标辅助输入时LLM识别准确率才有显著提升，纯图像输入效果差。

任务2：PPT编辑任务评估

有明确的指令和GT参考，但覆盖的场景非常局限。

PPTArena：使用LLM-judge对"指令遵循度"（0-5分）和"视觉质量"（0-5分）打分。编辑指令类型：修改特定页标题字号、替换图片、调整文本框位置等简单单步操作。已知问题：LLM judge能检测到的编辑失败主要是"过度编辑"（改了不该改的地方）和"布局破坏"，但对于字号是否真的改变了、元素是否精确移动到指定位置，视觉感知能力不足，存在漏判。
PPTC（ACL 2024）：评估LLM通过API调用序列完成多轮编辑指令的能力。有GT参考PPT，用Element Matching/Content Similarity/Color Similarity/Position Similarity计算与GT的差距。已知问题：只能评估"API执行是否正确"，不评估结果是否"好看"；需要预先定义好API序列作为GT，构建成本极高；任务集中在模板编辑而非自由创作。

DECKBench（KDD 2026）：统一单轮生成和多轮编辑，引入DTW软对齐衡量多轮编辑的结构收敛。已知问题：整体没有视觉质量维度，专注文本和结构；多轮指标（ΔDTW）需要GT且逻辑复杂，实际上测的是模型是否"听话"而不是结果是否"好"。

任务3：VLM理解与感知能力评估

这类任务和"生成好的PPT"关系较远，更像是对模型基础能力的诊断。

PPTBench：测LLM能否检测/理解/修改/生成PPT结构（JSON格式），评估指标是Exact Match Accuracy。问题：测的是结构化理解能力，不评估生成的视觉质量。
VLM-SlideEval：三个任务——元素精确提取（F1/IoU）、对几何/颜色/文本扰动的鲁棒性（R²/Spearman）、打乱顺序后重排（Kendall's τ）。已知问题：实验发现当前主流VLM在像素级精确提取上普遍偏弱；对幻灯片特有的几何扰动（轻微位移、细微字号变化）鲁棒性差——这意味着现有VLM-judge在评估精细视觉问题时存在系统性误差，但这个发现在其他评估论文里几乎没有被引用。

三、观察


观察1：越界/遮挡是客观问题，但没有可靠的自动检测方法
越界和遮挡在逻辑上是有明确对错的客观问题（元素是否超出画布边界，是可以精确计算的）。然而在图像输入范式下至今没有可靠解法。

观察2："粒度"与"标注一致性"之间的权衡?没有工作真正解决

很多论文在自己的数据集上报告了较高的human-model alignment，观察数据感觉是因为粗粒度的整体评分（如1-5分）确实更容易让自动方法对齐。
然而发现在人工标注一致性上：PresentBench细粒度checklist的IAA仅约0.6，LecEval中"受众参与度"维度的标注α值只有0.57，远低于"内容相关性"的0.84。这说明越细、越主观的维度，人与人之间本身就难以对齐。
一些论文为了规避绝对打分的不一致，改用"MLLM几选一"的定性方式，但这又限制了数据的可扩展性。

方向：将标注显式拆成两层？——客观层用二元Hard Check（越界/遮挡，有明确对错，预期IAA高）；主观层用pairwise偏好比较而非绝对打分（消除标注者个人基准差异，预期agreement高于细粒度绝对评分）。

观察3：场景约束如何影响评估标准？

PresentBench已经做了逐实例的动态checklist——每个测试样例根据背景材料和生成指令定制专属的核查项目。但仍然存在以下问题：
第一，动态的是"内容核查项"（这个PPT里有没有提到某个数据点），而不是"质量标准的权重"。对于学术PPT和营销PPT，同一份视觉设计的好坏标准是不同的，但PresentBench的视觉设计模块在所有实例里权重相同。
第二，即便有了详细的动态checklist，人工标注者对"满足/不满足"的判断仍然分歧较大。checklist的细化并不能自动提升标注一致性。
第三，场景约束和风格约束（如"面向企业管理者的简约风格"）目前没有工作系统测试——生成的PPT是否真的因为受众不同而调整了措辞密度、视觉复杂度和信息深度？

方向：对同一源文档构造不同场景/受众约束的query变体，让同一批agent分别生成，评估生成结果与场景约束的匹配程度？

---

 观察4：缺陷分类与整体偏好之间缺乏实证关联，影响维度优先级的制定

SlideAudit统计了2400张幻灯片的缺陷频率（布局问题占70.5%，排版43%，色彩13.7%）。哪类缺陷出现时，人类偏好排名下降最多？
这可能是维度设计的前提。如果布局越界导致的偏好下降是色彩不和谐的5倍，那么评估框架里这两类问题应该被区别对待。而现在的方法通常是得到多维度的分数之后直接相加组合。


---

观察5：PPT制作是多阶段工作流，但现有评估割裂了各阶段，全流程评估缺失

PPT制作工作流至少包含两个主要阶段：
阶段一，从头生成：理解用户需求 → 内容规划/大纲生成 → 逐页内容撰写 → 代码/布局生成 → 最终渲染。
阶段二，迭代编辑：在已有PPT基础上，根据用户的具体修改指令（调整风格、替换内容、修改布局等），进行单轮或多轮编辑直到满意。

现有benchmark割裂了这两段：PPTAgent/SlidesGen-Bench/PresentBench只评生成；PPTArena/PPTC/DECKBench只评编辑；没有任何工作把"生成质量 + 后续编辑能否有效改进"作为一个整体任务来评估。
编辑阶段已有工作，但覆盖的指令类型极度有限：PPTArena主要是单步简单编辑（修改某页字号、替换图片）；PPTC关注的是模板级API调用；DECKBench测的是多轮编辑后的结构收敛，且专门针对paper-to-slides场景。
针对更真实的用户编辑场景——"整体风格偏商务，背景色换成白色，第三页内容太密了精简一下"这类复合、模糊的自然语言编辑指令几乎没有系统性评估，也没有对应的数据集。

方向：设计"生成-修复"两阶段闭环任务——第一阶段评估生成质量并记录具体缺陷，第二阶段将缺陷描述转化为自然语言修复指令反馈给agent，评估能否准确修复且不破坏其他页面。

 观察6：能力归因困难，任务难度梯度没有分层

当一个agent的最终输出得分低，无法判断是内容理解能力差、布局生成能力差、还是视觉风格执行差。理想的归因需要控制变量，但现实中的agent接口非常有限。

方向：为同一主题构造只改变约束类型的query变体（无约束基准版、加页数约束、加风格约束、加受众约束）

审稿人视角的定位建议
---

如果目标投稿口味偏 ACL / EMNLP，这项工作的主问题不应表述为“自动判断 PPT 美不美”，而应表述为：

`如何为复杂、多约束的 PPT 生成任务提供可靠、可解释、可分解的评测信号。`

原因：
1. “美学打分”过于主观，且现有证据已经表明公式和通用 LLM judge 与人类偏好的一致性不稳定。
2. 当前最强的资产不是一个现成的审美模型，而是 `query 设计 + 多 agent 输出 + 大规模分页缺陷标注 + 一部分人类偏好数据 + 已可跑通的内容管线`。
3. 对顶会审稿人而言，benchmark 的价值在于回答“什么能力被测到了、为什么这些信号可信、它们能否帮助分析系统短板”，而不是给出一个单一总分。

因此更稳妥的主线是：
- 主线1：内容质量
- 主线2：硬性视觉错误
- 主线3：约束遵循
- 增强层：偏好层 / 美观层
- 后续层：页间连贯性、生成-修复闭环

这也意味着论文的主要实验应优先回答：
1. 现有自动指标中，哪些能稳定对齐人类判断，哪些不能？
2. 不同 agent 在内容、硬错误、约束遵循上是否呈现不同失效模式？
3. 显式建模场景/受众/输入类型后，benchmark 是否能揭示“同一系统在不同真实使用场景下表现差异很大”这一事实？

---

进一步讨论：如何避免“太工程”
---

担心“太工程”的根源，不在于我们做了缺陷检测或评分，而在于论文最后到底回答了一个什么研究问题。

如果论文主问题是：
- “我们能不能判断 PPT 美不美？”
- “我们能不能检测一页里有没有缺陷？”

那确实容易被审稿人理解成工程质检工具。

但如果论文主问题升级为：
- `PPT 是一种长程、多约束、可迭代编辑的结构化多模态文档生成任务，应该如何评估？`

那么整个工作就不再是“图片好坏检测”，而是在定义一种 AI 系统真实工作能力的评测标准。

这时，工作的研究价值来自三件事：
1. 不再只看单页图像，而是看整份 deck 是否完成了用户任务。
2. 不再只看最终结果是否“像 PPT”，而是看内容组织、约束满足、结构错误和后续可修改性。
3. 不再把所有质量问题揉成一个分数，而是拆成能帮助理解模型短板的不同信号。

因此，“工程感”强不强，不取决于你有没有做 hard issue detection，而取决于你有没有把它放进一个更高层的任务定义里。

---

进一步讨论：为什么整体评估必须做
---

这其实是最能把工作拉出“单图片质检”的点。

PPT 不是单张海报，也不是若干独立页面的简单拼接。用户真正关心的是：
- 这份 PPT 的结构是否完整？
- 多页之间的推进是否合理？
- 是否真的围绕给定文档、场景和受众组织内容？
- 是否是一份“可以拿去汇报”的 deck，而不只是几页看起来还行的页面？

因此 deck-level evaluation 不是“补充项”，而是 PPT benchmark 区别于静态图像评测的核心。

可以把它理解为：
- 单页评估回答的是：`这页有没有明显问题？`
- 整体评估回答的是：`系统有没有完成一次真实的 PPT 制作任务？`

后者明显更像 AI benchmark，因为它更接近任务完成、长程规划和多步内容组织。

---

进一步讨论：编辑过程为什么重要，但为什么当前不一定最高优先级
---

编辑过程很重要，因为真实 PPT 工作流天然不是“一次生成就结束”，而是：

用户需求 -> 初稿生成 -> 用户反馈 -> 多轮修改 -> 结果收敛

这和图片生成非常不一样。PPT 更像一个 `iterative document creation` 任务，而不是单轮图像合成。

所以从研究上说，编辑过程的重要性体现在：
1. 它更接近真实使用场景。
2. 它能体现 agent / assistant 是否真正可用。
3. 它把“生成质量”扩展为“生成后能否有效改进”。

但当前不把它放到最高优先级，也是合理的。原因不是它不重要，而是它会显著扩大 scope：
- 需要构建编辑指令数据
- 需要定义“改好了但没破坏别处”的评测协议
- 需要考虑大纲生成、局部修改、风格重写、跨页联动等复杂问题

因此更稳妥的论文路线可能是：
- 第一阶段：先把 `deck-level generation benchmark` 讲清楚，做扎实
- 第二阶段：把 `editability / generation-revision loop` 做成更完整的扩展任务

换句话说，编辑过程应该成为你故事里的“重要前瞻方向”，但不必强行在第一篇里全部做满。

---

进一步讨论：为什么硬性问题检测大家都不太做
---

这不是因为它不重要，反而通常是因为它“重要但难讲、难做、也不容易做得好看”。

可能原因有四类：

1. 技术上确实难。
- 越界、遮挡、细微错位这类问题，看起来客观，但往往是几何级、像素级的细粒度错误。
- 纯图像输入时，现有 VLM/MLLM 对精细空间关系并不稳定。
- 结构化元素、组合对象、图表、文本框叠加之后，规则法和通用视觉模型都容易失效。

2. 论文结果往往不够“漂亮”。
- 这类任务难度高，模型效果往往不会特别好。
- 做出来常常是在证明“现有方法都不行”，而不是展示一个特别亮眼的新分数。
- 这更像 diagnosis paper，而不是典型的“方法大幅领先 baseline”的 paper。

3. 很多现有工作主问题不在这里。
- 有的工作主要讲 paper-to-slides
- 有的讲 instruction following
- 有的讲 API 调用和编辑正确性
- 有的讲偏好学习或 LLM judge

所以即使知道越界/遮挡重要，也不会把论文主线压在这类问题上。

4. 单独讲 hard issue detection 容易显得低层、工程化。
- 如果没有更高层的任务 framing，审稿人会觉得这更像 layout QA 或缺陷检测。
- 但如果它被放在 deck-level benchmark 里，它就变成“解释系统失败原因”的关键证据，而不是整篇论文的全部。

因此更合理的定位不是：
- “我们的主要贡献是做越界/遮挡检测”

而是：
- “我们发现 deck 质量评估中存在一类用户极其敏感、但现有自动评测系统系统性忽略的结构性失败”

这样 hard issue detection 就变成 benchmark 的关键维度和研究论据，而不是孤立的工程模块。

---

当前更推荐的总故事
---

最值得坚持的高层故事，可能不是“美学评测”，而是：

`PPT 生成是一种长程、多约束、可迭代编辑的多模态文档创作任务。`

现有工作的问题在于：
- 很多方法只看单页或局部视觉
- 很多方法只看参考对齐或粗粒度主观评分
- 很少系统评估 deck-level task success
- 几乎没有把 editability 作为核心能力
- 对结构性视觉失败缺乏可靠检测和归因

因此 benchmark 的价值，不是再造一个“总分更准的打分器”，而是建立一套更接近真实工作流的评测框架：
- deck-level success
- page-level structural failures
- constraint-conditioned quality
- future editability / revision capability

如果按这个逻辑写，论文会更像在定义 `AI 是否真的会做 PPT`，而不是在做一个“PPT 质检系统”。

动机
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PPT生成缺乏可靠的评测信号，而不是单纯缺乏“审美打分器”。
现有方法有三类：
  · 公式计算（SlidesGen-Bench）
    → 多个像素级指标加权平均，与人类偏好一致性差
  · LLM-as-judge（PPTEval、AutoPresent）
    → 打分受到提示词影响，标准不稳定，且无法感知细微视觉问题
  · 细粒度缺陷检测（SlideAudit、PresentBench 的 checklist）
    → 标注一致性低；客观失败项与主观偏好项被混合处理

  ↓ 三类方法的共同根本缺陷
缺陷1：没有把“客观失败”与“主观偏好”分开处理。
    越界、遮挡、内容缺失是用户不可接受的结构性错误；
    配色、图文风格、版式丰富度则更接近受场景和受众影响的偏好判断。

缺陷2：没有显式建模真实用户约束。
    现有工作往往只问“像不像参考”或“整体好不好”，
    很少系统评估页数、语言、受众、场景、模板/素材使用等真实约束是否被满足。

缺陷3：难以提供可靠、可解释的系统分析信号。
    一个系统分数低，究竟是内容理解差、视觉结构错，还是没有遵守任务约束，现有方法很难归因。

→贡献一：提出面向复杂多约束 PPT 生成的分层 benchmark 任务定义与评测协议
→贡献二：构建覆盖多场景、多输入类型、多 agent 输出的数据与标注资源
→贡献三：系统验证不同自动信号的人类对齐程度，并用 benchmark 对主流 agent 做误差归因分析
→贡献四（增强项）：在 Hard Check / pairwise 数据充足时，再训练专用评估模型

贡献1：面向复杂多约束 PPT 生成的分层评测框架
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  我们提出 benchmark 的初版应优先覆盖三类核心能力：
  · Content Quality
    是否正确覆盖并使用输入材料

  · Hard Visual Failures
    是否存在越界 / 遮挡 / 内容缺失等结构性错误

  · Constraint Following
    是否满足页数 / 语言 / 场景 / 受众 / 模板或素材使用等明确要求

  偏好层（Aesthetic Preference）作为增强分析层：
  · 在无明显硬错误前提下比较视觉偏好
  · 优先采用 pairwise，而不是不稳定的绝对分数

  基于此框架构建 benchmark：
  多场景 query × 多输入类型 × 多 agent 输出 + deck / page / pairwise 多层标注

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
贡献2：可靠性验证与 human alignment
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  对三类核心信号分别验证：
  · 内容质量：deck 级维度分与人工判断的相关性
  · Hard Check：页级 Precision / Recall / F1 与 IAA
  · 约束遵循：不同约束类型下的准确率或一致率

  论文要显式报告：
  · 哪些自动信号是可信的
  · 哪些自动信号目前仍然不可信
  这本身就是 benchmark 贡献，而不必强依赖一个统一评分模型

贡献3：基于 benchmark 的系统评测与误差归因
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  · 对多个主流 agent 进行统一评测
  · 分析内容错误、结构性视觉错误、约束遗漏三类失效模式
  · 展示不同场景 / 输入类型下系统排名和短板的变化
  · 如条件允许，再补充 reranking 作为“评测具备优化信号”的增强实验

贡献4（增强项）：专用评估模型
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  仅当数据量和工程时间允许时再推进：
  · Stage 1（Hard Filter）：在页级 Hard Check 标注上训练
  · Stage 2（Preference Ranker）：在 pairwise 数据上训练
  注意：模型不是论文成立的前提，而是 benchmark 的增强组件

预期中间结论（人类偏好规律研究）
