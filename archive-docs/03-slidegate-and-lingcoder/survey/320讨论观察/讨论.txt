## 核心问题的诊断

你的困难根源在于：**现有的7类分页缺陷跨越了两种不同性质的问题**，直接和"维度"对应会乱，因为它们本来就不该在同一层级处理：

| 缺陷类型 | 本质 | 应该属于哪层 |
|---|---|---|
| 超出边界、遮挡/重叠、内容缺失（渲染失败）、大片空白（渲染失败）| **客观结构性失败**，有无明确定义，标注一致性高 | Hard Check层（page-level） |
| 图文适配性差、色彩与图片不匹配、色彩可读性差、大片空白（设计问题）| **主观美学偏好**，依赖场景和受众 | Aesthetic层（preference-based） |
| 内容缺失（内容生成失败，非渲染失败）| **内容理解/生成能力** | 内容质量维度（deck-level） |

注意：**"内容缺失"横跨两层**——如果是渲染引擎把内容框画空了，是渲染硬错误；如果是AI根本没生成该有的内容，是内容质量问题。这是你标注时"类间冲突"的来源，也是框架必须分层的根本原因。

## 完整评测框架（可直接交付）

### 框架结构：3轨道 × 2粒度 × 1扩展

```
PPT生成能力评测框架
│
├── Track A：内容质量（Content Quality）          [deck级，语义信号]
├── Track B：视觉结构完整性（Hard Check）         [page级，客观信号]
├── Track C：约束遵循（Constraint Following）     [deck级，规则+语义信号]
│
├── 增强层：视觉美学偏好（Aesthetic Preference）  [page+deck，pairwise信号]
│
└── 全流程扩展：生成-修复能力（Refinability）     [pipeline级，后续扩展]
```

---

### Track A：内容质量

**核心问题**：AI是否正确理解并表达了输入材料/用户需求？

| 子维度 | 来自你的现有标注 | 评估方法 | 数据资产 |
|---|---|---|---|
| 内容完整性 | 整体评分：大纲逻辑、内容满足度、信息使用 | 现有管线（completeness打分） | 873条整体评分 |
| 内容真实性 | 整体评分：内容/图片真实性 | 需要改进（真实性评估不可用） | 873条（部分可用） |
| 内容缺失（生成层面）| 分页标注type1（子集：AI未生成） | 模型打分 + 规则 | 11,000+条（需区分子类） |

**与page-level缺陷的连接**：type1"内容缺失"中，由AI未生成内容导致的→归入本轨道；由渲染失败导致空白→归入Track B。

---

### Track B：视觉结构完整性（Hard Check）

**核心问题**：渲染结果是否存在用户不可接受的结构性失败？

| page-level缺陷类型 | 定义边界 | 性质 | 评估方法 |
|---|---|---|---|
| 超出边界（type4） | 文本/图片超出页面/文本框边界 | 客观，二元 | Hard Check binary |
| 遮挡/重叠（type2）| 有语义影响的遮挡（非创意设计） | 客观，二元 | Hard Check binary |
| 内容缺失（type1，渲染失败子集）| 应有内容的区域空白，渲染问题 | 客观，二元 | Hard Check binary |
| 大片空白（type3，渲染失败子集）| 非设计意图的大面积空白 | 客观，二元 | Hard Check binary |

**数据资产**：11,000+条分页标注，目前全网唯一有GT的布局缺陷数据集  
**评估指标**：Precision / Recall / F1（按类型分别报告）  
**关键发现（已有）**：现有所有自动方法对type2、type4系统性失效（recall 55-57%，accuracy≈15%）→ 这是论文的核心motivation之一

---

### Track C：约束遵循

**核心问题**：AI是否满足了query中的显式约束？

| 约束类型 | 来源 | 评估方法 | 现有数据 |
|---|---|---|---|
| 硬性规则约束（页数、语言、章节数）| query字段 | 规则检测（可靠）| 134条query已有字段 |
| 资源使用约束（是否用了指定图片/模板/文档）| query字段 | 规则 + 视觉对比 | 873条整体评分（"是否搭配上传图片"） |
| 场景/受众约束（商务风、面向管理者）| query字段 | LLM judge（待验证）| 873条整体评分（"内容是否满足需求"） |
| 章节标题与目录一致性 | 整体标注 | 规则 + LLM | 873条整体评分 |

**关键空白**（论文贡献点）：场景/受众约束遵循是现有所有benchmark的完全空白——没有任何工作评估"给管理者的PPT是否真的用了合适的信息密度和措辞"

---

### 增强层：视觉美学偏好

**核心问题**：在无硬错误前提下，哪个更好看？

| 子维度 | 对应page缺陷类型 | 评估方法 |
|---|---|---|
| 图文适配性 | type5（图文适配性差）| pairwise比较 |
| 色彩协调性 | type6（色彩图片不匹配）+ type7（色彩可读性差）| pairwise比较 |
| 视觉风格统一性 | 整体标注：设计风格是否一致 | pairwise比较 |
| 页间节奏 | SlidesGen-Bench公式（趋势参考）| 公式（仅趋势分析，不作主指标）|

**数据资产**：229条pairwise（现阶段只做探索性分析，不作主结果）

---

### 全流程扩展：生成-修复能力（对应mentor关心的全流程）

这部分是框架的"完整性论证"，初版可以定义结构、不要求跑通：

```
用户Query
   ↓
Stage 1：生成质量评估（Track A+B+C）
         → 输出：内容评分 + 缺陷清单 + 约束合规度
   ↓
缺陷→修复指令（自然语言）
   ↓
Stage 2：修复能力评估
         → 核心指标：修复率（缺陷被成功修复的比例）
                     回归率（修复时引入的新问题比例）
                     Refinability = 修复率 / (1 + 回归率)
```

初版只做Stage 1，Stage 2作为"benchmark支持但当前实验待完成"的扩展模块描述。

## 交付时的一个关键判断

"内容缺失"这个type1标注里，**渲染失败 vs AI未生成**的区分，是你整个框架能不能自洽的关键节点。建议在交付框架时，把这个区分作为一个明确的标注子类决策写进去——两个子类用不同评估方法处理，而不是混在一起。如果标注时没有区分，可以在框架文档里说明这是一个"需要在下一轮标注中细化的边界"，这在顶会论文里是正常的限制声明，不影响框架的成立。
