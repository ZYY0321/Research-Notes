# 研究方向核心说辞

---

## 一句话定位

我想做**移动端 GUI Agent 的数据合成**，基于南大程瞰之刚发表的 OpenMobile 框架做后续工作。

---

## 选择动机

GUI Agent 领域现在最核心的矛盾是：闭源 agent（GPT-4o、Gemini）在 AndroidWorld 上能到 70% 成功率，开源只有 30%。这个差距的主要原因不是模型架构，而是**训练数据**——DigiRL 证明了同一个 1.3B 模型换了高质量数据可以从 17% 跳到 67%。所以谁能高效地合成高质量移动端训练数据，谁就能推动开源 agent 追上闭源。

OpenMobile 是目前第一个完整的移动端数据合成框架，4 月 16 号刚挂 arXiv，代码、数据、模型全部开源。它用 2,800 条合成指令把 Qwen3-VL-8B 训到 AndroidWorld 64.7%，接近闭源水平。但这个工作标注的是 "work in progress"，有明确的改进空间——这正好是一个可以接手往下做的时间窗口。

---

## 背景

我做过 AmbiBench（移动端 GUI agent benchmark，三作）和 UI 代码生成（三作），对移动端 agent 的评估流程和数据工程比较熟。程瞰之是 OpenMobile 核心作者，可以直接合作拿到第一手技术支持。同时孙秋实（HKU）做过 OS-Genesis（数据合成的前序工作）和 Process Reward Modeling，可以作为辅助合作者。

---

## Gap 在哪

OpenMobile 解决了"从零到一"的问题，但还有几个明确的 gap：

1. **应用覆盖太窄**：只有 20 个 app、2,800 条指令。真实世界的 app 类型远不止这些，特别是中文 app 生态几乎没有覆盖。
2. **只有单 app 任务**：所有合成的任务都是在一个 app 内完成的。但真实用户需求大量涉及跨 app 协作（查日历→发邮件→订餐厅），跨 app 的轨迹数据极度匮乏。
3. **依赖闭源模型**：错误检测的监控器用的是 Gemini-3.1-Pro-Preview，不是完全开源的 pipeline。
4. **探索策略粗糙**：Random walk 每次只走 10 步，深层功能（需要多步前置条件才能到达的页面）覆盖不到。
5. **没有安全约束信号**：合成的训练数据里不包含"什么操作不该做"的信息，但 agent 能力越强安全风险越大。

---

## 对组里有什么用

1. **环境记忆构建的技术可复用**：OpenMobile 的全局环境记忆（屏幕聚类 + 功能标注 + 语义索引）可以直接用来给组里的 app 建立结构化的 UI 知识库，帮助理解 app 的功能分布和页面关系。
2. **为 benchmark 提供多样化指令**：合成 pipeline 生成的任务指令可以直接补充我们现有 benchmark 的 query 池——覆盖更多 app 类型、更多任务复杂度层次。
3. **为横向提供数据和基础设施**：数据合成的模拟器环境、app 部署流程和轨迹采集工具，和 UX Testing 横向完全共用。
4. **训练数据可共享**：合成的高质量轨迹数据可以给组里其他需要 fine-tune GUI agent 的工作使用。

---

## 可能的创新点

### 主攻：跨 App 复杂任务合成
OpenMobile 的环境记忆目前是每个 app 独立的。如果把多个 app 的环境记忆打通，建立跨 app 的功能关联图，就可以自动合成涉及多个 app 协作的复杂任务指令和对应轨迹。这个方向目前完全没有人做过——GUIOdyssey 有跨 app 的数据但是人工标注的，没有自动合成方案。

### 备选1：去除闭源依赖 + 数据效率
把 Gemini 监控器替换成开源的错误检测模型（可以结合孙秋实的 PRM 做步骤级质量评估），同时研究数据筛选和课程学习策略，用更少的数据达到更好的效果。

### 备选2：安全感知的数据合成
结合程瞰之另一个工作 OS-Sentinel（ACL 2026，移动端 agent 安全框架），在轨迹合成过程中引入安全约束，让合成数据包含风险场景的识别和拒绝信号。

---

## 和横向的关系

横向的 UX Testing 项目和研究方向**共享基础设施，互相支撑，但不是同一个研究问题**：

- **横向给研究的支撑**：横向要在大量真实 app 上部署和运行 GUI Agent，这套模拟器环境、app 管理流程直接就是数据合成需要的基础设施。而且在横向中我会大量观察 agent 的实际失败模式——哪些 app 搞不定、哪些操作类型经常出错——这些观察帮我判断数据合成应该优先补哪些类型的数据。
- **研究反哺横向**：数据合成产出的更强 agent 直接提升 UX Testing 的自动化测试效果。

一句话：横向是下游应用场景，研究是上游能力提升，两者共享环境但各自独立。

## 其他认真考虑过的方向

以下方向都有明确的研究价值，部分可以和数据合成方向互补或作为 Plan B。

### 1. 意图对齐 / 主动交互（AmbiBench 方向延伸）

- **价值**：真实用户的指令往往是模糊的（"帮我订个餐厅"没说哪家、几个人、什么价位），agent 需要主动澄清意图而不是瞎猜。AmbiBench 证明了现有 agent 在这个维度上表现很差，这是一个被验证过的真实问题。
- **优势**：我参与过 AmbiBench，熟悉工程基础和评估框架，上手最快。孙家正在组内可以直接指导。
- **和数据合成的关系**：可以互补——合成包含"模糊指令→澄清→执行"完整链路的训练数据，既是数据合成的一个应用场景，也能推进意图对齐研究。
- **取舍考虑**：这个方向本身成熟度较高，做延伸需要找到足够差异化的角度，比如从评估拓展到方法改进。

### 2. 生产力工具 / 桌面端 GUI Agent Benchmark

- **价值**：Office、PPT 这类生产力场景对 agent 的需求很强，但现有 benchmark 覆盖不足。ScienceBoard 证明了"垂直领域 benchmark"的研究价值（ICLR 2026），说明审稿人认可这个路线。
- **优势**：我有 PPT benchmark 实习经验，理解生产力工具的评估难点（美学、内容质量等非 binary 指标）。
- **和数据合成的关系**：如果后续把数据合成扩展到桌面端，这个方向的 benchmark 经验可以直接迁移过来做评估。
- **取舍考虑**：纯 benchmark 的方法贡献需要额外设计，不能只是"一个新数据集"。需要在评估方法论上有创新（如多维度评分、过程评估等）。

### 3. GUI Agent 鲁棒性（accessibility 退化问题）

- **价值**：有实验数据表明约 50% 的 agent 失败可归因于 accessibility tree 质量问题。这是一个有数据支撑的真实痛点，而且和工业界部署直接相关。
- **优势**：叙事清晰——"agent 不应该依赖不可靠的 accessibility 信息"。与程瞰之的 GUI-Actor（坐标自由定位）在思路上相关，有合作空间。
- **和数据合成的关系**：如果合成数据时有意引入 accessibility 退化的场景，可以训练出对信息缺失更鲁棒的 agent。
- **取舍考虑**：需要构造不同质量梯度的 accessibility 环境，工程量较大，但问题本身很扎实。

### 4. 步骤级评估框架

- **价值**：目前几乎所有 benchmark 只看最终任务成功率（binary），完全不评估中间步骤质量。一个 agent 走了 20 步完成任务和走了 5 步完成任务，在当前评估下得分一样。这个 gap 两篇主要 survey 都明确指出了。
- **优势**：与孙秋实的 Process Reward Modeling（ACL 2025）直接对接，合作路径清晰。资源需求相对低，不需要大规模训练。
- **和数据合成的关系**：步骤级评估可以直接作为数据合成的质量过滤模块——用 PRM 给合成轨迹的每一步打分，过滤低质量步骤。两个方向天然结合。
- **取舍考虑**：步骤级标注的标准如何定义（什么算"好的一步"）是核心难点，需要想清楚。

### 5. GUI Agent 安全性

- **价值**：随着 agent 能力越来越强，误删文件、泄露隐私、被恶意指令操控的风险越来越大。两篇主要 survey 都将安全性列为最紧迫的开放挑战。目前几乎没有专门的安全性 benchmark 和防御方法。
- **优势**：程瞰之的 OS-Sentinel（ACL 2026）是少数相关工作之一，可以在此基础上深入。安全是审稿人普遍认可的重要话题，叙事容易讲通。
- **和数据合成的关系**：可以自然结合——在数据合成中引入安全约束场景，训练 agent 在完成任务的同时学会识别和拒绝危险操作。
- **取舍考虑**：独立做安全偏评估方向，和数据合成结合做则可以有方法贡献。

### 方向之间的关系

这些方向不是互斥的。数据合成是一个**底层能力**，上面可以叠加多个研究维度：

```
                    ┌─ 意图对齐（模糊指令的合成数据）
                    ├─ 跨 App 任务（多 app 协作的合成数据）
  数据合成 pipeline ─┼─ 安全约束（包含风险场景的合成数据）
                    ├─ 步骤级质量（PRM 过滤合成数据）
                    └─ 鲁棒性（accessibility 退化场景的合成数据）
```

选数据合成作为主线，是因为它**可以向上对接多个研究问题**，一篇论文做完后自然拓展到其他方向，而不是只能做一件事。

---

## 未来拓展

数据合成是一个有延展性的方向，第一篇论文做完之后可以继续拓展：

1. **Scaling law 研究**：合成数据量 vs agent 性能的关系曲线，找到 cost-effective 的最优数据量
2. **跨平台迁移**：把移动端的数据合成方法迁移到桌面端（Windows/Mac），结合 OS-SYMPHONY 的框架
3. **自我进化闭环**：agent 用合成数据训练 → 用训练后的 agent 探索更多功能 → 合成更高质量数据 → 循环迭代，做成全自动的数据飞轮
4. **领域特化**：针对特定垂直领域（金融 app、医疗 app、教育 app）做专门的数据合成和 agent 训练
5. **结合 RL**：OpenMobile 试了 RL 效果不显著，但可能是奖励模型的问题——结合 PRM 做更好的步骤级奖励可能打开 RL 的上限

---

## 总结

> 移动端数据合成是 GUI Agent 领域当前最大的 gap。OpenMobile 刚打开局面但有明确改进空间。我有移动端 agent 的经验基础、有作者的直接合作渠道、有横向项目提供的基础设施支撑、资源需求可控。这个方向有方法贡献（不只是数据集）、有明确的创新切入点、有合理的时间线、有 Plan B、有未来拓展空间。
