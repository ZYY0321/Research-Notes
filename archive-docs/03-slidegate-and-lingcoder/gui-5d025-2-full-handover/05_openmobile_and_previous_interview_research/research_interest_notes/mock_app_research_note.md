> 用途：为 OpenMobile V2 应用扩展方向保留一份可迁移的上下文说明，便于在新工作区继续调研、部署验证和表格维护。
> 更新时间：2026-05-25

---

## 1. 当前任务目标

当前的重点不是先讨论 V2 要做哪些实验，而是先为“应用扩展”铺路，具体包括：

1. 广泛搜集可能符合要求的开源 mock / 高仿 Android 应用项目。
2. 优先关注能在模拟器中运行、能走通核心 UI 流程的项目。
3. 尝试下载、部署、验证少量高优先级项目的实际效果。
4. 对照 MobileWorld 的路线，判断哪些项目更适合后续扩展。
5. 最终形成一张完整表格，持续维护。

---

## 2. 当前对任务的理解

### 2.1 目前更像是在做“训练数据场景扩展”

当前关注点更偏向于：

- 给 agent 提供更多真实感更强的 App 场景；
- 让轨迹能在模拟器里走通；
- 不一定要求像 benchmark 那样做严格的数据库级成功验证。

也就是说，现阶段更关心：

- 能不能安装到模拟器；
- 能不能跳过真实账号登录；
- 页面是否有真实内容或 mock 内容；
- 一条任务轨迹能否从头走到尾。

### 2.2 与 MobileWorld 的不同

MobileWorld 更偏 benchmark / 可复现评测环境，强调：

- 使用别人的开源项目；
- 自己部署这些项目已有的后端；
- 通过 Docker 把环境统一起来；
- 通过数据库 / 本地存储 / callback 做确定性验证。

而当前调研的目标更偏“轨迹采集前的应用筛选”，所以不必一开始就要求：

- 必须有数据库可查；
- 必须具备严格评测逻辑；
- 必须完整复现 MobileWorld 的评测基础设施。

但 MobileWorld 的应用选择思路仍然非常值得借鉴：优先找**可控、可部署、可长期维护**的开源替代项目，而不是直接依赖真实闭源 App。

---

## 3. 当前筛选标准

当前更适合用来筛项目的标准如下：

### 3.1 核心硬条件

1. 尽量**不需要真实账号登录**。
2. 能在 Android 模拟器环境中运行。
3. 页面里有可用内容，不是纯静态空壳。
4. 核心 UI 流程能走通。

### 3.2 当前可接受的内容来源

- 本地假数据
- 项目自带 mock server
- 项目自带完整后端
- 真实 API（但这类项目通常会被账号问题卡住）

### 3.3 当前不强制的条件

- 不强制要求数据库验证任务完成
- 不强制要求完整 benchmark 评测逻辑
- 不强制要求 Docker 化

## 4. 当前已经形成的关键判断

### 4.1 B 站类场景目前是明显缺口

已发现的 B 站第三方客户端（如 `bilimiao2`、`BiliPai`）功能丰富、与真实 App 相似度高，但问题是：

- 大部分互动功能都需要真实账号；
- 无账号时通常只能浏览、搜索、播放；
- 不适合做“无登录前提下的完整互动轨迹采集”。

因此，B 站类目前仍是一个待解决缺口。

### 4.2 短视频 / 电商 / 外卖 / 社区方向已有较多候选

这些方向已经找到一些可用或潜在可用的项目：

- 短视频：有不依赖账号、本地假数据驱动的抖音/TikTok 类项目
- 电商：有高仿京东、带 mock server 的项目
- 外卖：有仿美团、带后端的项目
- 社区：有仿小红书、带完整后端的项目

### 4.3 当前最适合的阶段性策略

先做三层筛选：

1. **广泛搜集候选**
2. **按表格字段统一初筛**
3. **只对高优先级项目做下载部署验证**

不要一开始就对所有项目做完整复现和环境搭建。

## 5. 关于 MobileWorld 路线的当前理解

### 5.1 MobileWorld 的核心路线

MobileWorld 并不是自己从零写 App，而是：

1. 找功能类似的开源项目；
2. fork 或直接使用这些项目；
3. 部署这些项目本来就有的后端；
4. 把模拟器、后端、数据库等统一放进 Docker 方案里；
5. 在需要时再做确定性验证。

典型例子：

- Mattermost 替代微信/Slack 类 IM/协作场景
- Mastodon 替代微博/Twitter 类社交场景
- Mall4Uni 替代淘宝/电商类场景

### 5.2 “自己部署后端”是什么意思

不是自己从零写后端，而是：

- 使用别人已经开源好的后端代码；
- 在自己的机器或服务器上把它跑起来；
- 让模拟器里的 App 访问自己本地的服务，而不是访问真实互联网服务。

### 5.3 Docker 在这里的作用

Docker 主要是让环境更容易统一和迁移：

- 后端程序放进容器
- 数据库放进容器
- 必要时模拟器环境也一起编排

这样可以做到：

- 换机器更容易迁移
- 团队协作更容易复现
- 避免本地环境安装杂乱

但对于当前“先做轨迹采集候选筛选”的阶段来说，Docker 不是第一优先级。

## 6. 工作区与平台的当前建议

### 6.1 Windows 更适合的部分

- GitHub 项目搜集与阅读
- Android Studio + 模拟器交互验证
- APK 安装和手动试跑
- 笔记、表格、截图整理

### 6.2 Linux 更适合的部分

- Docker / docker-compose
- 自建后端服务
- MobileWorld 路线复现
- 批量脚本与长任务

### 6.3 当前建议

当前阶段更建议：

- **Windows 作为主工作区**：搜集、表格维护、模拟器交互验证
- **Linux 作为副工作区**：Docker 化、后端部署、MobileWorld 路线复现

## 9. 当前优先级建议

### 9.1 第一优先级：适合尽快下载验证

1. `jd_mall_flutter`
2. `running-libo/Tiktok`
3. `MeiTuanAndroidApp`

原因：

- 无需真实账号
- 核心 UI 流程较明确
- 适合先验证“轨迹能否走通”

### 9.2 第二优先级：适合长期方案研究

1. `Mattermost Mobile`
2. `Mastodon Android`
3. `Mall4Uni`

原因：

- 更贴近 MobileWorld 路线
- 更适合后续做完整环境方案
- 更有长期扩展价值

### 9.3 当前明显问题项

- B站方向：与真实 App 相似度高，但账号问题严重
- 微信方向：现有高仿项目过老，且常依赖外部 SDK

## 10. 下一步建议

建议下一步按下面顺序推进：

1. 先把这份总表继续维护起来。
2. 先选 2 到 3 个高优先级项目做下载和运行验证。
3. 对每个已验证项目补上：
   - 截图
   - 实际运行是否成功
   - 核心 UI 流程是否真的走通
   - 是否适合轨迹采集
4. 与此同时，单独整理一份 MobileWorld 路线的复现清单：
   - 用了哪些开源项目
   - 后端如何部署
   - Docker 作用是什么
   - 哪些部分值得直接借鉴
