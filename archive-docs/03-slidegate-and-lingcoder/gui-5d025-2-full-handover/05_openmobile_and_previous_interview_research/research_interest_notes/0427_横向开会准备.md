# Part 1：基础知识补齐（让你问得专业）

## 1.1 折叠屏设备与UI适配基础

### 折叠屏的三种形态
- **折叠态（Folded）**：外屏可用，尺寸接近普通手机（~6.5寸）
- **展开态（Unfolded）**：内屏打开，接近小平板（~7.5-8寸）
- **半折叠/悬停态（Half-folded / Hover）**：中间状态，角度~90-150°

### 华为折叠屏产品线（你要有概念）
- **Mate X系列**（外折）：Mate X/Xs/X2/X3/X5/X6
- **Pocket系列**（纵向折叠，竖向翻盖）：Pocket/Pocket 2/Pocket S
- **Mate XT**（三折叠）：业界首个三折，2024发布，展开后~10寸
- **鸿蒙OS（HarmonyOS/鸿蒙Next）**：华为自研，折叠屏适配API和Android不同

**这一条记住**：华为2024年发的**Mate XT三折叠**是**UI适配地狱**——同一app要适配单折/双折/全展开三种状态，bug率远超双态折叠屏。如果他们的课题涉及Mate XT，研究价值和落地价值都会更高。**开会可以问一句他们覆盖哪些机型**。

### UI适配的核心挑战
折叠屏app开发要处理**配置变更（configuration change）**——屏幕尺寸/宽高比/DPI变化时UI要重绘。常见做法：
- **ResponsiveLayout**（响应式布局）：根据屏幕宽度自动切换布局
- **断点（Breakpoint）**：比如<600dp用手机布局、600-840dp用平板布局
- **Fold API**（Android Jetpack WindowManager）：系统提供折叠感知API

**bug的根本来源**：开发者没处理好上述API，或者不同厂商API不一致（华为鸿蒙有自己一套）。

## 1.2 折叠屏UI bug 分类（对齐行业标准）

这是你开会里提问和讨论要用的**分类坐标系**：

| bug类型 | 典型表现 | 检测方式 | VLM准确率 |
|--------|---------|---------|----------|
| **截断（Truncation）** | 文字/图标/按钮被裁切，显示"..."或半截 | 静态视觉检测 | **低**（他们在攻克的就是这个） |
| **错位（Misalignment）** | 元素位置错、相互重叠、跑出屏幕 | 静态视觉+结构检测 | 中 |
| **留白过大（Excessive Whitespace）** | 展开后中间大片空白，像拉伸的手机UI | 静态视觉+像素比例 | 较高 |
| **布局断裂（Layout Break）** | 元素错乱、堆叠、跑版 | 静态视觉 | 中 |
| **未适配（No Adaptation）** | 展开后还是手机UI，完全没用到大屏空间 | 静态视觉+布局分析 | 高 |
| **响应式异常（Responsive Issue）** | 折叠/展开/旋转时UI不重绘、闪烁、丢状态 | **动态交互检测**（静态看不到） | VLM做不了 |
| **交互失效（Interaction Break）** | 按钮点不到、滑动卡顿、焦点丢失 | **动态交互检测** | VLM做不了 |
| **旋转异常（Rotation Bug）** | 竖屏→横屏时布局错 | **动态交互检测** | VLM做不了 |

**核心洞察**：前5类是**静态bug**（一张截图能看出来），后3类是**动态bug**（必须在交互过程中才能触发）。**VLM只能做静态bug，agent才能做动态bug**——这是agent的主要价值。

## 1.3 华为方面的技术语境

### 鸿蒙/HarmonyOS相关
- **ArkUI**：鸿蒙的UI开发框架（类似Android的Jetpack Compose）
- **ArkTS**：鸿蒙的开发语言（TypeScript扩展）
- **HAP/HAR/HSP**：鸿蒙应用打包格式
- **Ability**：鸿蒙的app组件（类似Android的Activity）

**你需要问**：**测试目标是Android版本还是鸿蒙版本**？这直接影响能用什么工具（Android有UIAutomator/Appium生态；鸿蒙有自己的DevEco Studio和hdc工具）。

### 华为测试工具生态
- **DevEco Testing**：华为自研测试工具
- **MagicCapture**：华为内部UI抓取工具（可能）
- 如果他们已经在用某套工具，你的agent要能对接

## 1.4 当前团队的VLM路线分析（你要理解他们做了什么）

### 他们做的事
1. 收集折叠屏截断样本（截屏 + 标注"哪里截断了"）
2. 微调Qwen（大概率是**Qwen2-VL-7B**或**Qwen2.5-VL-7B**，这是目前中文UI理解最好的开源VLM）
3. 用微调后的模型做截断检测

### 这条路线的天花板
1. **只能看静态截图**——动态bug（类型6/7/8）根本检测不了
2. **需要大量标注**——每种新bug类型都要重新收集
3. **无法给复现步骤**——检测到了但不知道怎么触发的
4. **无法主动探索**——只能被动看给它的图，不能主动去app里找bug
5. **泛化差**——在App A上微调，换App B就掉点

### agent能补什么（你后面要说的话）
1. **主动探索**：让agent自己操作app，触发折叠/展开/旋转等状态切换
2. **动态bug检测**：agent能做序列操作，看到静态看不到的bug
3. **可复现报告**：agent输出"从XX页面，做了YY操作，出现ZZ bug"
4. **闭环**：VLM做感知，agent做决策，两者结合

**关键一句（记住）**：**"VLM微调是感知层优化，agent补的是决策层和交互层。这两层是互补的，不是替代关系。"**——这句话能避免他们觉得你在否定之前的工作。

## 1.5 GUI Agent做UI测试的技术栈基础

如果话题谈到"agent具体怎么做"，你要能接住。四大组件：

1. **感知层（Perception）**
   - 截图 + view hierarchy（Android的UIAutomator dump）
   - VLM理解UI（可以直接复用他们微调的Qwen）
   - OmniParser式的结构化解析

2. **决策层（Decision）**
   - 基于当前状态决定下一步操作
   - 参考工作：Mobile-Agent-v2（NeurIPS 2024, arXiv:2406.01014）、AppAgent（arXiv:2312.13771）

3. **执行层（Execution）**
   - Android: UIAutomator/Appium发送点击/滑动/输入事件
   - 鸿蒙: hdc shell或DevEco自研接口
   - **折叠屏特殊**：需要能模拟折叠/展开事件（模拟器的`adb shell cmd device_state state`或真机API）

4. **oracle层（判断是否bug）**
   - VLM判断"当前屏幕是否异常"
   - 运行时断言（app是否crash、白屏）
   - 业界参考：**Trident**（arXiv:2407.03037）——三智能体（Explorer/Monitor/Detector）检测非崩溃功能bug

## 1.6 相关工作速查（能引用的论文）

**GUI测试 + LLM方向**：
- **GPTDroid** (ICSE 2024, arXiv:2310.15780)：把GUI测试建模为Q&A，LLM回答下一步操作
- **DroidAgent** (arXiv:2311.08649)：agent自主设置语义任务目标做测试
- **AutoDroid** (MobiCom 2024, arXiv:2308.15272)：LLM驱动的Android任务自动化
- **Trident** (arXiv:2407.03037)：多模态LLM + 三智能体检测非崩溃功能bug（**最贴你要做的事**）
- **VisionDroid**（同Trident，可能是别名）

**GUI Agent基础**：
- **Mobile-Agent-v2** (NeurIPS 2024, arXiv:2406.01014)：三agent分层
- **AppAgent** (arXiv:2312.13771)：自探索+文档知识库
- **CogAgent** (CVPR 2024, arXiv:2312.08914)：18B VLM做GUI理解

**折叠屏相关**（**少，但这恰是你的机会**）：
- 学术界基本无专门针对折叠屏的agent/测试工作（我调研范围内未见）
- 工业界华为/三星/谷歌有内部工具但不发论文

# Part 4：会议中三个关键发言时机

## 时机1：听他们汇报进展时
**策略**：多听少说，做笔记。可以问澄清性问题（"刚才说的准确率是在哪个测试集上？"）。

**不要**：不要评价他们之前工作的好坏、不要急着提方案。

## 时机2：讨论到"下一步要做什么"时
**发言模板**：
> "我想确认一下我的理解——现在VLM这边做的是感知层的工作，主要针对静态可视的bug类型（截断、错位这类）。合作方最终要的应该是一个**能主动发现并复现折叠屏bug的系统**。那GUI agent在这里的角色，我初步理解是做两件静态VLM做不了的事：
> 一是**主动探索**——自动执行折叠/展开/旋转/返回这类状态切换序列，去触发那些只在交互中出现的bug（响应式异常、旋转bug）；
> 二是**可复现报告**——自动记录'从哪个页面做了什么操作触发了什么现象'，这个对测试工程师定位问题很关键。
> 我这个理解对吗？还是你们对agent的角色有别的设想？"

**这段话的作用**：
- 显得你理解了VLM的角色（感知层），也理解agent的角色（决策+交互层）
- **不否定他们之前的工作**，反而把他们的工作升级为"更大系统里的一个模块"
- 让他们自己点头确认角色，后面方案设计你主导权更大

# Part 6：几条心态提醒

1. **今天不谈论文**——横向发论文本来就难，你开场表态也明说了"重点对齐进展"。不要在第一次会议就暴露"我想发paper"的心思，容易让人觉得你功利。论文的事等项目推进一段后再看能不能顺带产出。

2. **不要否定VLM路线**——他们前期投入很大，你否定他们=得罪团队。你的定位是"在VLM基础上加agent层"，不是"用agent替代VLM"。

3. **多问少答**——你是来摸清情况的，不是来证明自己多厉害的。显得专业的方式是**问到点子上**，不是**说得多**。

4. **华为对接方才是真甲方**——记住你们组的学长/老师的决策会受华为影响。所以"华为要什么"这个问题最关键，一切技术方向都要服务这个。

5. **你的杠杆在"agent方向的专业度"**——这是整个项目里除你之外可能没人深入的领域。守住这个信息差，你就有话语权。

# Part 7：术语速查（万一别人说你没听懂）

| 术语 | 含义 |
|------|------|
| VLM (Vision Language Model) | 视觉-语言模型，如Qwen-VL/GPT-4V |
| View Hierarchy | Android的UI层级结构（xml形式） |
| Accessibility Tree | iOS/Web的无障碍树，类似view hierarchy |
| UIAutomator | Android自动化测试框架 |
| Appium | 跨平台移动自动化测试工具 |
| Activity Coverage | 测试覆盖的activity数量/比例 |
| State Coverage | 测试覆盖的UI状态数量 |
| Oracle | 测试里判断"对错"的机制 |
| Flaky Test | 结果不稳定的测试（有时过有时不过） |
| Crash Reproduction | 崩溃复现 |
| Responsive Layout | 响应式布局 |
| Configuration Change | Android里屏幕旋转/尺寸变化触发的配置变更 |
| Fold State | 折叠屏的状态（折叠/展开/半折叠） |
| DevEco Studio | 华为鸿蒙开发IDE |
| ArkUI / ArkTS | 鸿蒙的UI框架/开发语言 |
| HAP (Harmony Ability Package) | 鸿蒙应用包格式 |
| pHash (Perceptual Hash) | 感知哈希，基于像素相似性的图像指纹 |
| VLM微调 (Fine-tuning) | 在预训练VLM基础上用特定数据训练 |
| SFT (Supervised Fine-Tuning) | 监督微调 |
| LoRA | 低秩适配微调方法 |
