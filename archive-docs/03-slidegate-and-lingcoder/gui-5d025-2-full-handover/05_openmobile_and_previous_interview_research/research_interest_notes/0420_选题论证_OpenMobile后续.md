## 一、为什么选 OpenMobile 后续？

### 1.1 领域 Gap 明确
- 开源 mobile agent 与闭源差距巨大（30% vs 70%），**核心瓶颈是训练数据**
- 移动端数据合成是当前**最大空白**：Web 端已有 AgentTrek（ICLR 2025 Spotlight），移动端 pipeline 仍稀缺
- DigiRL 证明高质量数据可让 1.3B 模型从 17.7%→67.2%，数据的价值已被充分验证
- OpenMobile 刚发表（2026.04.16，work in progress），多个后续方向空白

### 1.2 与个人背景契合

| 维度 | 匹配度 | 说明 |
|------|--------|------|
| 已有经验 | ✅ | AmbiBench 三作（移动端 GUI agent benchmark 积累），熟悉移动端 agent 评估 |
| 合作者 | ✅ | 程瞰之是 OpenMobile 核心作者，可直接合作 |
| 资源需求 | ✅ | 数据合成方向不需要大规模 GPU（主要是模拟器+API调用），符合资源约束 |
| 时间周期 | ✅ | 框架已开源，不需从零搭建，1年内可产出 |
| 组内协同 | ✅ | 复旦彭鑫组有 UX Testing 横向项目（真实 app 数据），孙家正有 AmbiBench 工程基础 |

### 1.3 对比已有方向选项的优势

## 二、具体可做的后续方向

### 方向E1：跨App复杂任务合成（⭐⭐⭐ 首推）

**问题**：OpenMobile的任务主要是单App内操作，跨App任务数据极度匮乏（GUIOdyssey仅8,334 episodes）

**做法**：
- 利用OpenMobile的全局环境记忆，在不同app间建立语义关联
- 合成涉及多App协作的工作流数据（如"查日历→发邮件→订餐厅"）
- 建立跨App任务的质量评估标准

**论文叙事**：
> 现有数据合成方法只能生成单app任务。我们发现跨app任务是真实用户的核心需求但数据最稀缺的维度。我们扩展OpenMobile的环境记忆机制，实现首个自动化的跨app任务合成pipeline，在[benchmark]上将agent跨app成功率提升X%。

**评估**：
- 创新性：⭐⭐⭐（新问题+新方法）
- 可行性：⭐⭐（需要设计跨App记忆关联，但有OpenMobile框架支撑）
- 发表前景：⭐⭐⭐（GUIOdyssey在2024年发表说明该方向有需求）
- GPU需求：低（主要是模拟器和API调用）

### 方向E2：去闭源依赖 + 数据效率提升（⭐⭐ 推荐）

**问题**：OpenMobile的监控器依赖Gemini-3.1-Pro-Preview，且2,800条指令规模有限

**做法**：
- 训练轻量级开源错误检测模型替代闭源监控器
- 研究数据筛选/课程学习策略，用更少数据达到更好效果
- 结合孙秋实的Process Reward Modeling做步骤级质量过滤

**论文叙事**：
> OpenMobile的数据合成流程依赖闭源模型作为监控器。我们提出完全开源的替代方案，同时通过[具体方法]提升数据效率，以X%的数据量达到Y%的原始性能。

**评估**：
- 创新性：⭐⭐（改进型工作）
- 可行性：⭐⭐⭐（明确的技术路线）
- 发表前景：⭐⭐（需要足够大的性能提升）
- 合作点：与孙秋实（PRM）天然契合

### 方向E3：安全感知的数据合成（⭐⭐ 推荐）

**问题**：OS-Sentinel做了安全评估，OpenMobile做了数据合成，但两者未结合

**做法**：
- 在轨迹合成中加入安全约束和风险场景
- 合成包含"危险操作识别与拒绝"模式的训练数据
- 验证安全训练数据对agent安全行为的影响

**论文叙事**：
> 现有mobile agent训练数据不包含安全约束信号。我们将安全风险场景融入数据合成pipeline，使agent在提升任务能力的同时学会识别和拒绝危险操作。

**评估**：
- 创新性：⭐⭐⭐（交叉创新）
- 可行性：⭐⭐（需要定义安全场景）
- 发表前景：⭐⭐⭐（安全是热点，审稿人认可度高）
- 合作点：程瞰之有OS-Sentinel经验
