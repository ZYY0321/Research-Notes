## 三、选题一：GUI Agent Memory

### 3.1 为什么现在做

**Memory 方向整体仍是蓝海**，NeurIPS 2024/2025 各约 10–20 篇，ICLR 2025 约 10 篇，相对于 agent 总投稿（数千篇）仍是小众。GUI 域的 memory 研究更是几乎空白。

四重结构性壁垒把竞争者挡在外面，但对你反而是机会：

| 壁垒 | 通用域的难点 | GUI 域的反转 |
|------|------------|------------|
| 无公认 benchmark | LOCOMO/LongMemEval 才刚出 | GUI 有明确"状态"概念，可评估 |
| 被 RAG/long-context 淹没 | 需正面打赢 RAG | GUI 状态非文本，RAG 天然不够用 |
| 需长时间部署才显价值 | 学术界做不起 | UX Testing 横向项目提供真实部署场景 |
| 工程基础设施门槛 | 学术界精力不够 | 横向数据直接可用，无需从头搭 |

### 3.2 Memory 研究脉络（2023–2025 标志性工作）

| 时间 | 工作 | 核心贡献 | 备注 |
|------|------|---------|------|
| 2023 | Generative Agents（UIST 2023, 2304.03442） | memory stream + reflection + planning 三件套 | 认知架构模板 |
| 2023 | Reflexion（NeurIPS 2023, 2303.11366） | 失败经验转自然语言存 episodic buffer | 无需训练 |
| 2023 | Voyager（2305.16291） | skill library 作为 procedural memory，代码形式存技能 | Minecraft |
| 2023 | MemoryBank（AAAI 2024, 2305.10250） | 引入艾宾浩斯遗忘曲线 | |

| 2023 | **CoALA**（2309.02427） | **框架论文：working/episodic/semantic/procedural 四类记忆，对齐 ACT-R/SOAR** | 你的理论来源 |

### 3.3 GUI Agent 现有 Memory 设计及其局限

| 工作 | Memory 设计 | 关键局限 |
|------|------------|---------|
| AppAgent（2312.13771） | 文档式知识库，UI 元素功能写成自然语言 | 静态、无版本管理，UI 一变失效 |
| Mobile-Agent-v2（NeurIPS 2024, 2406.01014） | memory unit 跟踪任务进展 + reflection agent | 只是"当前任务便签"，无跨任务持久化 |
| OS-Copilot/FRIDAY | declarative + procedural 混合 | procedural 是 Python 代码库，对 GUI 界面状态无直接表征 |
| OpenMobile（pHash） | 感知哈希聚类视觉相似屏幕 | 对动态内容完全失效（广告/推荐/时间戳） |

**五个共同缺陷：**
1. 把 memory 等同于"历史 prompt 拼接"或"知识库文档"
2. 缺乏 UI 状态的结构化表征
3. 没有考虑 UI 版本漂移
4. 跨 app 迁移几乎无人做
5. 记忆质量本身不被评估，只评估下游任务成功率

### 3.4 五个切入点的 Gap 与可行性

| 切入点 | 是否有人做过 | 可行性 | 风险 |
|--------|------------|--------|------|
| **多模态 UI 状态表征**（视觉+结构+功能融合作为 memory key） | 三者分别做过，三元融合未检索到 | 高 | 难点在 fusion 方式与评测 |
| **功能等价性状态合并** | Web 端有 DOM state abstraction（Synapse 等），Mobile 端几乎空白 | 中高 | 需 LLM-as-judge 或 contrastive learning |
| **层次化记忆（ACT-R 三层）** | CoALA 是框架，GUI 实证工作未检索到 | 中 | 容易被批"incremental over CoALA"，必须绑定 GUI 专属机制 |
| **增量式记忆更新（app 升级后）** | 几乎完全空白；软工的 GUI test repair 同源但未结合 LLM | 中高 | 最大挑战是数据——需同一 app 多版本 UI 配对数据 |
| **记忆质量可评估性** | LongMemEval/LOCOMO 是下游任务指标；直接度量 memory 本身非常稀少 | 高 | 适合作为 side contribution |

**推荐组合：**
- **最安全**：切入点 2（功能等价合并）+ 切入点 5（memory 质量评估），讲"GUI 环境下 memory 的表征与评估"一体化故事
- **最高收益**：切入点 4（UI 演化下的迁移），若拿到多版本数据，几乎无竞争
- **雷区**：切入点 3 单独做，容易被打回

### 3.5 "多模态融合表征"的文献推导依据

> 这不是拍脑袋的设计，而是文献 gap 直接推导出的机会：
> 1. CogAgent（CVPR 2024, 2312.08914）证明视觉 embedding 对 GUI 有效
> 2. WebAgent 系列/Synapse 证明 DOM/AXTree 结构 embedding 对 web agent 有效
> 3. AppAgent 证明 LLM 生成的功能描述对零样本 UI 理解有效
> 4. **三者分别 work，但无人做融合** → 三路融合是文献 gap 直接推导的机会

做法参考：类似多模态 retrieval 里的 late fusion 或 MoE fusion，现成方法可套。

### 3.6 大厂是否已垄断？

**没有垄断，恰恰相反：**
- Mem0、Letta、LangGraph 都是通用 memory 框架，不针对 GUI
- 大厂 GUI agent 工作（AITW/Ferret-UI/UFO）均不专门做 memory，在此维度和学术界水平接近
- OpenMobile 的 pHash 方案本身就是 hand-wave（学长的判断是对的）

**小团队可产出的创新点：**
- 问题定义层：提出"GUI memory 质量"的度量框架
- 方法层：多模态融合 state encoder（工程量可控，无需大规模训练）
- 评估层：首个 GUI memory benchmark（参考 SWE-bench 路径）

## 四、选题二：Bug-oriented Planning（GUI 测试 × AI 顶会）

### 4.1 核心空白

**目前基本没有以"GUI Agent × Testing"为核心卖点的 AI 顶会论文。**

- AI 顶会相关工作（SeeAct/CogAgent/WebArena/OSWorld/AndroidWorld）均以任务完成率为唯一指标，不测 bug
- AgentBench、τ-bench、TheAgentCompany 都没有"软件测试作为评测任务"
- **这个"空"就是机会**

### 4.2 两条路线

**路线 A：测试场景 Benchmark**（推荐先做）

- 成功先例：SWE-bench（ICLR 2024, 2310.06770）→ SWE-Agent（NeurIPS 2024, 2405.15793）
- 对标：SWE-bench → 代码修复；你 → GUI bug discovery，概念对称
- 投稿目标：NeurIPS D&B track（SWE-bench 正是走这条）、ICLR、ISSTA/FSE
- 包装要点：**避免"Android testing"字眼**，用"GUI agent robustness under adversarial/stateful environments"这类 framing

**路线 B：Bug-oriented Framework**（第二步）

- 风险：AI 顶会审稿人可能嫌"应用性强"
- 规避：把 bug discovery 抽象成通用 AI 问题——"sparse, delayed, partially-observable reward 下的 agent exploration 问题"，测试只是 instance
- 可借鉴：curiosity-driven RL（ICM, Pathak 2017）+ coverage-guided fuzzing 的 energy scheduling

**强建议：先 A 后 B**。先发 benchmark 在 NeurIPS D&B（学长 OK、风险低），再用自己 benchmark 评自家 framework 发方法会——**一个课题撑两篇**，对专硕毕业极为友好。

### 4.3 "测试场景太细分"的顾虑——不成立

AI 研究者不做测试的原因：不熟悉软工 oracle 问题、缺少高质量 bug 数据集、指标不标准化——**不是不屑，是门槛**。

破解方法：
1. 把问题抽象成通用 agent 能力维度（exploration / memory / robustness / causal reasoning）
2. Benchmark 覆盖多种 app 类别，强调"代表性"
3. 标题避免"Android testing"

参考：Kang et al., "LLMs are Few-shot Testers"（ICSE 2023, 2209.11515）—— 软工会对 AI 方法友好。

### 4.4 四个具体空白故事线

| 空白 | 核心问题 | 技术路线 | 投稿目标 |
|------|---------|---------|---------|
| Bug-oriented Exploration | 现有 agent 的 exploration reward 全是"任务完成"，遇异常会绕过而非深挖 | curiosity-driven RL + LLM critic 识别"可疑状态" | NeurIPS/ICLR（方法）或 ISSTA（应用） |
| 状态覆盖率 × 任务完成率双目标 | 两者部分冲突（完成任务倾向走最短路径，不利探索） | Pareto-optimal policy 或多目标 RL；构造双目标基准 | NeurIPS D&B + ASE |
| 可复现 UI 状态表征 | LLM agent 非确定性 + app 随机性 → bug 报告难复现 | view hierarchy hash + visual embedding + 操作序列签名 | FSE/ICSE（软工更认） |
| 跨 app 版本鲁棒性 | app 升级后 UI 变化，已学策略崩溃 | 构造"同一 app 多版本"语义对齐数据集 + few-shot adaptation | NeurIPS D&B / ICLR / ISSTA |

## 五、Planning 方向补充（选题二的理论支撑）

### 5.1 AI 顶会为何偏好"long-horizon + 可验证中间步骤"

四个 reviewer filter 叠加：
1. **短任务天花板**：GSM8K/HotPotQA 已被 GPT-4/Claude 饱和，短任务一个 CoT 就够，planning 模块变 overhead
2. **Planning 必要性 argument**：只有 long-horizon（WebArena/OSWorld）才能证明"不做规划真跑不通"
3. **可验证中间步骤 = 可诊断性**：ICLR 近年强烈偏好"interpretable by design"
4. **Compositionality 理论诉求**：long-horizon 天然测 systematic generalization

### 5.2 Planning 方向八个未解决的真实问题

1. **执行监控与回滚**：Reflexion 是 episode 级反思，步级失败检测仍缺可靠信号
2. **子目标分解粒度**：ADaPT（2311.05772）递归按需分解缓解，但何时停止仍 open
3. **闭环反馈稀疏**：GUI 环境反馈（截图/DOM diff）高维噪声大，现有方法多依赖任务完成信号 → sparse reward
4. **长 horizon 错误累积**：OSWorld 上 50+ 步任务成功率 <20%（Xie et al., NeurIPS 2024, 2404.07972）
5. **可验证性**：LLM 生成的 plan 缺乏形式化语义，无法做 soundness check
6. **多 agent 协作规划**：MetaGPT（ICLR 2024, 2308.00352）展示分工有效，但角色冲突/共享信念一致性无 principled 方案
7. **计算成本**：LATS 每节点一次 rollout，成本是 ReAct 的 10–100 倍，实际部署不可行
8. **Planning 与 Memory 结合**：检索何时触发、如何不污染 plan 上下文仍不清楚

## 六、Training-free 增强（稳定后备路线）

### 6.1 为什么列为优先切入（五个硬条件匹配专硕）

1. 无 GPU 门槛（调 GPT-4o/Claude API 即可）
2. 实验周期短（一个 idea 2–4 周跑完）
3. Novelty 门槛友好（组合创新被接受）
4. 对比实验明确（固定主干 LLM，变量干净）
5. 2025–2026 正处顶会热点（Jason Wei、Noam Brown 公开定性"inference compute is the new frontier"）

### 6.2 关键论文（2024–2026）

| 论文 | 核心发现 |
|------|---------|
| OpenAI o1 System Card（2024.09） | 首次系统展示 inference-time reasoning 的 scaling law |
| Snell et al.（2408.03314） | DeepMind：同等 FLOPs 下小模型+长推理可超 14× 大模型 |
| Brown et al.（2407.21787）"Large Language Monkeys" | coverage 随样本数 log-linear 增长 |
| s1（2501.19393） | 1k 样本 SFT + "budget forcing" 逼近 o1-preview |
| DeepSeek-R1（2501.12948） | R1-Distill 提供 training-free 部署基础 |
| Chen et al.（NeurIPS 2024, 2403.02419） | inference scaling 的理论边界 |

### 6.3 GUI 域证据：training-free 能从 30% 推到 45%+

- Agent-S（ICLR 2025, 2410.08164）：hierarchical planning + 经验记忆，OSWorld 20.58%（vs Anthropic 11.21%），完全 training-free
- Mobile-Agent-v2：比 v1 提升 ~14%（NeurIPS 2024）
- UI-TARS（SFT 方法）AndroidWorld ~46%，纯 prompt GPT-4o 约 30%，training-free 方法把差距缩到 5pp 以内

### 6.4 被拒的典型模式（要躲开）

1. "换 prompt 涨点"型——无机制解释，easy reject
2. 只在一个 benchmark 上刷榜，缺乏 generalization
3. 没控制 inference token 数，算力不公平
4. Novelty 仅是"组合 A+B"且无理论分析或意外发现

## 七、各方向关键顾虑回应

### Q1：为什么必须绑定固定场景？

不是必须绑定，但绑定更稳。绑定 UX Testing 场景有三个增益：
- **评估有抓手**：bug 复现率、状态覆盖率是天然的 memory 质量代理指标
- **数据可得**：横向项目直接提供，别人拿不到
- **差异化护城河**：别组做不了（没有测试背景和真实项目）

折中方案：**主方法做通用 GUI memory 机制 + 在 UX 测试场景做重点实验验证**，两全其美。

### Q2：软工文章看上去只是 trick，讲不出故事？

关键在 framing：
- 软工场景是 **instance**，核心 claim 是通用 agent 能力（exploration policy / sparse reward / long-horizon planning）
- 标题和 intro 先讲 AI 问题，测试只是最有说服力的验证场景
- 类比：SWE-bench 的故事不是"软件修 bug"，而是"LLM 能否解决真实工程问题"

### Q3：要不要开辟全新方向（如 memory）？

**是，但要有策略**：
- Memory 对你来说不是"开辟新方向"，而是"在 GUI agent 已有积累上往纵深走一步"
- 不需要从零开始，CoALA 的框架 + 横向项目的数据 + UX Testing 的评估场景 = 三个现成资产
- 风险：比卷 benchmark 周期长；收益：若做成，是组内无人有的独特积累
