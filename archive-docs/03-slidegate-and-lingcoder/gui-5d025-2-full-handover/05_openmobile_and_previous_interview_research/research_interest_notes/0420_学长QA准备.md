## Q1：计算资源够吗？实验需要什么？

### 回答

OpenMobile 论文没有明确写资源需求，但从方法细节可以推算出三块成本：

**① 数据合成阶段（主要是API费用，不吃GPU）**

| 组件 | 用途 | 估算 |
|------|------|------|
| Gemini API | 屏幕功能标注、任务合成、专家轨迹采集、质量评判 | 主要开销，估计数百~低千美元量级 |
| OpenAI embedding API | 环境记忆的语义索引（text-embedding-3-large） | 较低 |
| Android 模拟器 | 随机探索 + 轨迹采集（CPU/内存密集，不需GPU） | 普通服务器即可 |

- OpenMobile 合成了 2,800 条指令 / 34,000 步，这个规模的 API 调用不算大
- 如果做后续工作，可以复用他们已开源的数据集作为起点，不需要从零合成
- **Gemini 可以换成开源模型**（Qwen2.5-VL-72B等），用组内/学校GPU跑，省API钱

**② 模型训练阶段（需要GPU，但规模可控）**

| 参数 | OpenMobile原文 |
|------|--------------|
| 基座模型 | Qwen2.5-VL-7B / Qwen3-VL-8B |
| 训练方式 | SFT（LLaMA-Factory） |
| batch size | 32 |
| learning rate | 1e-5 |
| epochs | 3 |
| 自我进化轮数 | 3轮 |

- 7B/8B模型的SFT在 **4×A100 (80GB)** 上几个小时可以完成
- 数据量只有 ~34K步，不是大规模预训练，是轻量级SFT
- 论文也试了RL但发现在动态benchmark上没有显著提升，所以**SFT就够**
- 如果资源紧张，可以用 LoRA 进一步降低显存需求

**③ 评估阶段（模拟器+推理）**

- 在 AndroidWorld 上评估，跑3次取平均
- 推理用 vLLM 部署，单卡A100可跑7B/8B模型
- 主要消耗是模拟器时间，不是GPU

### 总结一句话

> "数据合成主要花API钱不花GPU，训练是7B模型的轻量SFT几个小时搞定，整体资源需求远低于预训练类工作。最贵的Gemini监控器未来可以用开源模型替代。"

## Q2：预计创新点和时间线？

### 回答

**创新点取决于具体切入角度**（需要和程瞰之沟通后确定）：

| 方向 | 创新点 | 一句话pitch |
|------|--------|------------|
| 跨App任务合成 | 扩展环境记忆到app间关联，首次自动合成跨app工作流数据 | "OpenMobile只能合成单app任务，真实用户需求是跨app的" |
| UX Testing数据合成 | 从'完成任务'到'发现bug'，设计缺陷发现型探索策略 | "现有合成数据都是正常操作，没有人教agent怎么找bug" |
| 安全感知合成 | 将安全约束融入合成pipeline，训练数据中包含风险识别信号 | "agent越强越危险，但没有训练数据教它什么不该做" |

**时间线**

| 阶段 | 时间 | 产出 |
|------|------|------|
| 调研+跑通pipeline | 5-7月（2个月） | 复现OpenMobile，熟悉代码和数据 |
| 方法设计+初步实验 | 7-10月（3个月） | 核心方法实现，初步实验结果 |
| 补充实验+写作 | 10-12月（2个月） | 完整实验，初稿 |
| 投稿 | 2027年1月 | 目标ACL/EMNLP 2027 |

> "前两个月跑通基础设施和复现，中间三个月出核心结果，最后两个月补实验和写论文。一年一篇的节奏。"

## Q3：有什么困难和风险？

### 回答

| 困难 | 严重程度 | 应对方案 |
|------|---------|---------|
| **竞争风险**：OpenMobile 4月刚发，别人也会跟进 | ⚠️ 高 | ① 和作者直接合作拿先发优势；② 选差异化角度（UX Testing / 安全），别的组没有我们的横向数据和SE背景 |
| **程瞰之2026年毕业**，合作窗口可能只有几个月 | ⚠️ 中 | 前期密集合作把pipeline和核心idea跑通；后续独立推进或转向孙秋实合作 |
| **模拟器环境不稳定**：Android模拟器经常崩溃、app更新导致UI变化 | ⚠️ 中 | OpenMobile已有成熟的模拟器管理代码可复用；选稳定的app版本固定 |
| **合成数据质量难保证**：自动合成的任务/轨迹可能有噪声 | ⚠️ 中 | OpenMobile已有质量过滤机制（去重+评判）；可结合PRM做步骤级过滤 |
| **评估不够convincing**：benchmark数字提升可能不大 | ⚠️ 低 | 选新维度做评估（跨app成功率 / bug发现率 / 安全拒绝率），不只比task completion |

> "最大风险是竞争。应对方式是走差异化——UX Testing方向别人做不了，加上和作者直接合作的先发优势。"

## Q4：别人是怎么做数据合成的？Gap在哪？

### 回答

**现有数据合成方法分四类：**

| 方法 | 代表工作 | 做法 | 问题 |
|------|---------|------|------|
| **人工标注** | AITW (Google, 2023) | 真人操作手机录轨迹，715K episodes | 成本极高，标注一致性差，不可扩展 |
| **LLM合成** | AgentTrek (ICLR 2025) | 从Web教程自动生成轨迹，$0.55/条 | **只针对Web端**，移动端不适用 |
| **逆向探索** | OS-Genesis (ACL 2025) | 先随机操作再反推任务 | 单轨迹生成，无跨功能组合能力 |
| **在线RL** | DigiRL, UI-TARS | Agent在线试错+奖励模型 | 计算成本极高，需要数百台虚拟机 |

**OpenMobile的改进**：在OS-Genesis基础上加了全局环境记忆（跨功能组合）+ 策略切换（错误恢复信号）

**仍然存在的Gap：**

1. **应用覆盖太窄**：OpenMobile只有20个app、2,800条指令——真实世界有数百万app
2. **只有单app任务**：没有跨app工作流（如"查日历→发邮件→订餐"），而GUIOdyssey证明这是核心需求
3. **依赖闭源模型**：监控器用Gemini，不是完全开源
4. **没有安全约束**：合成的数据不包含"什么操作不该做"的信号
5. **探索策略太简单**：Random walk 10步，覆盖不了深层功能（如需要登录→设置→高级选项的多步前置条件）
6. **没有面向测试的数据**：所有合成都是"完成用户任务"，没有"发现界面缺陷"类型的数据

> "一句话总结：移动端的数据合成OpenMobile刚开了头，但在覆盖度、任务复杂度、开源程度上都有明确的空间。特别是跨app和面向测试这两个方向完全没人做。"

## Q5：（补充）为什么不直接做benchmark？你之前做AmbiBench不是更熟吗？

### 回答

> "Benchmark我确实更熟，但有两个考虑：
> 
> 第一，**benchmark本身不是贡献，背后的方法论才是**。纯benchmark论文越来越难发顶会了，审稿人要看到insight和方法。数据合成方向天然有方法贡献。
> 
> 第二，AmbiBench是孙家正一作的工作，在此基础上延伸存在一作归属和'简单延伸'的风险。OpenMobile后续是独立方向，一作没有争议。
> 
> 当然，如果数据合成的实验结果不理想，我有评估benchmark作为备选——比如'GUI Agent在UX Testing中的能力评估'，这个结合横向项目比较稳。"

## Q8：（补充）如果结果不好怎么办？Plan B是什么？

### 回答

| 情况 | Plan B |
|------|--------|
| 数据合成的性能提升不显著 | 转做**分析型工作**：为什么某些类型的合成数据有效/无效，提供数据合成的设计指南 |
| 跨app合成太难实现 | 退回**单app扩展覆盖度** + 做scaling law分析（数据量vs性能的关系） |
| 和程瞰之合作不成 | 联系孙秋实做PRM+数据质量过滤方向；或独立做F2（UX Testing评估benchmark） |
| 整个数据合成方向竞争太激烈 | 转**F2：GUI Agent在软件测试中的能力评估**——纯benchmark工作，风险最低，与组最匹配 |

> "最保底的Plan B是做benchmark（F2），结合横向的UX Testing场景评估现有agent的测试能力。这个不依赖性能提升，只要设计好评估维度就能发。但优先还是冲方法贡献。"
