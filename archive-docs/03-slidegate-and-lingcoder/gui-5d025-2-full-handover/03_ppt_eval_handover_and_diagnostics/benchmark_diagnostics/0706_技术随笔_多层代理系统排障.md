# 一个 500 背后：str 和 list 的区别，藏在你看不见的那一层

> 随笔 · 记一次接新模型端点时的排障

## 现象

把一个新训好的模型端点接进一套现成的 agent 系统。手动测端点是通的——发一句简单的话，正常返回。可一旦让 agent 真跑起来，**第一次调用就 500**，而且稳定复现。中间层只透传回来一句笼统的"内部服务错误"，没有堆栈，端点返回体也只有一行"Internal Server Error"，什么线索都没有。

一边是"我手动测明明是好的"，一边是"agent 一跑就崩"。矛盾就摆在这——**成功和失败之间一定有个变量，得把它找出来。**

## 怎么查的

思路很朴素：既然简单请求成、真实请求崩，那就**从能成功的最简请求出发，逐步向真实请求逼近，看哪一步翻车**。二分。

**先做加法。** 从最简的成功请求起步，把 agent 真实请求里那些"又大又复杂"的特征一个一个加回去——因为直觉总觉得是这些重东西压垮了端点：把输出上限调到最大、把系统提示塞到上万字、挂上一整串工具定义、加上缓存标记、补上各种协议头和参数。一项一项加，每加一项测一次。结果**全部返回 200**。请求再大、工具再多、参数再满，端点都稳稳的。**直觉方向完全错了——重不是原因。**

加法走到头都没能复现，说明触发点在我还没碰过的某个维度上。这时候换个方向：**改做减法。** 不再从简单请求往上堆，而是**拿那个必崩的真实请求，反过来一个字段一个字段地删，看删掉哪个它就不崩了**。加法是"什么让它崩"，减法是"去掉什么它就好"，两头夹逼。

减法很快收敛。真实请求和我那些成功请求之间，还剩一个我一直没单独动过的地方——消息内容字段的**结构**。把它单独拎出来做对照：

- 同一句话，内容字段是**纯字符串** → 成功
- 同一句话，内容字段是**结构化数组**（`[{类型: 文本, 文本: "..."}]`）→ 崩

其他一切保持不动，只翻转这一个维度，成败就跟着翻转。为了坐实，又补了两步：一是**反复重放**，确认不是偶发抖动而是稳定复现；二是做个**净化对照**——把那些"重"的特征全部去掉、只留数组内容，它**照崩**。这就排除了"是数组和某个别的因素组合起来才崩"的可能，把变量锁死成唯一一个：**内容字段的形态**，跟长度、工具、参数统统无关。

到这还有个疑点没解开：**我传给中间层的，明明是字符串。** 那个数组是哪来的？如果停在"大概是某处转的"这种自洽猜测上，就到不了根因。于是打开中间层的调试输出，去看它**实际发到端点的请求体**——

原形毕露：我交进去的是字符串，中间层在发送前，把它规范化成了目标协议的**标准结构化格式**（那种 `类型 + 文本` 的数组）。**上游写的，和端点收到的，根本不是同一个东西。**

## 本质是什么

这不是谁写错了代码，而是一个协议层面的错配：

- 通用的 SDK / 兼容层，为了对接不同后端，会把用户五花八门的输入**统一规范化**成目标协议的标准形态。内容字段从字符串升格成结构化数组，是这个协议的标准表达，也是这类中间层的**既定行为**——它没错。
- 而这个新端点在实现请求解析时，只处理了"内容是字符串"这一种简单情况，直接拿去拼接；一旦遇到结构化数组，拼接逻辑就崩了。**它没有完整实现协议该支持的输入形态。**

所以根因一句话：**中间层按协议标准把内容规范化成了数组，而端点只认字符串、没实现数组分支。** 手动测之所以一直是好的，是因为手动请求走的是最朴素的字符串形态，恰好避开了这条没实现的路径；agent 经由中间层，必然是数组形态，也就必然踩中。

顺带一提，另一个协议兼容口对同样的输入报的错更直白——它没有闷头 500，而是明说了一句"构建输入时期望字符串、却拿到了列表"。同一个根因，换一层皮，信息量差很多。**当一个入口把错误咽掉时，试试它旁边的入口。**

## 那，沙盒/执行环境有没有关系？

**没有关系。** 这一点值得单独说，因为很容易误判。

这套系统里确实有个沙盒执行环境，模型调用也确实有一条链路是在沙盒内部发起的。排查早期我甚至专门验证过"从沙盒内部能不能连到端点"——能。于是很自然会想：会不会是沙盒这一环的网络、转发、封装出了问题？

但崩溃的那条链路，其实是主体直连端点的，**根本不经过沙盒**。沙盒内那条是另一条独立链路，而且它发的是最朴素的字符串请求，压根不碰那个会触发 bug 的数组形态。把沙盒牵扯进来，纯粹是因为它在场——**"在场"不等于"相关"**。真正的分界不是"哪些组件参与了系统"，而是"崩的那一次请求，具体流经了哪一层"。锁定到具体那条路径，无关的组件自己就排除了。

## 收尾

回头看，这个 bug 的全部难度都在一句话上：**你以为你发的，和实际发出去的，不是一回事。** 多加一层通用中间件，就多一层"善意的改写"；它替你把请求规范化成标准形态，方便了 99% 的对接，也在剩下 1% 没完整实现协议的后端上，制造了一个手动测永远复现不出来的坑。

排它的关键动作就两个：**用受控变量把差异逼到唯一**，然后**打开中间层、看它到底发了什么**——而不是盯着自己写的那份输入，或者去怀疑那些只是"恰好在场"的组件。
