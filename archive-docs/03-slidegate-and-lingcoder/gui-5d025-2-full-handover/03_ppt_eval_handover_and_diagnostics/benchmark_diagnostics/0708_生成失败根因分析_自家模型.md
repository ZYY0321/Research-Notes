# 生成失败根因分析（自家训练模型）

> 2026-07-08。范围：仅自家训练模型的失败 case（flashv1_1 / flash4k / step3kdpo / step3kdpo_tpl），共 **20 个**。
> 数据源：`output/<batch>/<case>/result.jsonl` 的 `message_records`（结构化 tool_call / tool_result / assistant_output 全轨迹）。
> 复现脚本：`xhx_agent_v3/scripts/analyze_failures.py`；机器可读明细：`xhx_agent_v3/benchmark_failures_analysis.jsonl`。

---

## 0. 一句话结论

**20 个失败里 19 个是同一个根因：模型在某一轮没有产出「框架能识别的结构化 tool call」，于是 agent 循环判定该轮无工具调用 → 直接终止，最终没有 HTML 产物。** 只有 1 个是长表不收敛（话痨）。

这**不是**渲染管线 bug，也**不是**超时；`error` 全为 null。是**模型侧工具调用稳定性 / 收尾纪律**问题——典型的弱模型缺陷，且**自家最弱的 flashv1_1 占了 12/20**。

---

## 1. 失败分布

| 失败模式 | 数量 | 含义 | 典型 case |
|---|---|---|---|
| `textform_toolcall` | **12** | 末轮把 tool call 吐成**纯文本/畸形语法**，框架没解析到→当作「无调用」终止 | flashv1_1 seq_1006、flash4k prod_c40ab9ac |
| `premature_report_stop` | 4 | 末轮用 `<report>`/`<response>` 输出**自然语言大纲/宣告**（"现在开始生成…"）就停，没真正发起调用 | step3kdpo prod_c40ab9ac、step3kdpo_tpl seq_1472 |
| `narrate_then_stop` | 3 | 末轮纯自然语言宣告下一步（"两个产物已产出，现在继续…"）但没发起调用 | flashv1_1 seq_1559 |
| `verbose_no_converge` | 1 | 超长表附件，202 次调用 1507s 仍不收敛（话痨） | flashv1_1 seq_1495（考勤大表） |

按模型：flashv1_1=12、flash4k=4、step3kdpo=2、step3kdpo_tpl=2。

> 前 3 类（19 个）本质是**同一件事**：一轮结束时没有有效结构化调用 → 循环终止。区别只在「那一轮吐了什么」。

---

## 2. 根因详解

### 2a. `textform_toolcall`（12 个，最主要）— 工具调用格式不稳定

模型**知道**要调什么工具、参数也基本对，但**没按框架的结构化协议发**，而是把调用**当普通文本打印**出来。框架的 agent 循环看不到结构化 tool_call，就认为"这轮模型没调工具、说完了"→ 终止。观察到 4 种畸形语法，且**同一模型会混用**：

1. **特殊 token 泄漏 `<｜DSML｜tool_calls>`**（flashv1_1 seq_1006 / e4794450 / 1784）
   - 例：末轮 `<｜DSML｜invoke name="executeshell"><｜DSML｜parameter …>` —— 训练用的对话标记（DSML 全角 `｜`）直接漏进输出。
2. **杜撰标签 `<file_action>`**（flashv1_1 seq_1025 / 1081 / 1190 / 1293 / 18bf8df6）
   - 模型自己编了个 `<file_action><target>…</target><action>CREATE</action>` 的伪协议来"写文件"，框架里根本没这个工具。
3. **标准 `<invoke>` 纯文本**（flashv1_1 seq_1408，17s/3轮，最快）
   - `<tool_calls><invoke name="read_file">…</invoke></tool_calls>` 以纯文本吐出，一次结构化调用都没成功过。
4. **`<function=xxx>` 畸形 + 工具名拼错**（flash4k prod_5a2ddcda / c40ab9ac / seq_1690，prod_603992e9）
   - `<tool_call><function=execute_shell_ommand>`、`<function=todtolist_update>`、`<function=execute_shellcommand>` —— 工具名本身拼错（`ommand`/`todtolist`/漏下划线），是**工具调用能力弱**的直接证据。

> 关键观察：这些 case **前面很多轮是成功的结构化调用**（seq_1025 前置 27 次、prod_18bf8df6 前置 22 次），只是**在某一轮突然退化成文本**。即"能调对，但不稳定"，越到后期上下文越长越容易崩。

### 2b. `premature_report_stop`（4 个）— 用报告代替动作

模型把**应该触发子任务/脚本**的地方，写成了 `<report>`/`<response>` 里的一段自然语言（例：step3kdpo prod_c40ab9ac 直接在 `<report>` 里写完整分镜脚本大纲；seq_1472 写完 markdown 版 PPT 目录就停）。**它以为"输出内容"= "完成任务"**，但下游要的是 HTML 产物。step3kdpo（DPO 模型）占了一半，倾向于"多说、早交付文字"。

### 2c. `narrate_then_stop`（3 个）— 说了下一步却没做

末轮是"现在先补建立必要的入口材料，再继续分发后续流程。"这类**宣告**，然后 turn 结束、没有调用（flashv1_1 seq_1559：85 轮、1425s 干了很多活，最后一句话收尾没落地）。step3kdpo_tpl seq_0154 则是**反问用户要参数**（16s 就停），在无人值守批测里等于卡死。

### 2d. `verbose_no_converge`（1 个）— 大表话痨

flashv1_1 seq_1495（考勤大表 xlsx）：202 次调用、607 条记录、1507s，反复读文件/演算就是产不出结构化产物。这条与判分侧的 q1495 同源（三值忠实度也话痨到抛错）。**超大表格附件是自家弱模型的公认死穴**。

---

## 3. 对照：这是"早停"，不是"超时"

flashv1_1 正常 done 的**中位时长 1218s**。而失败 case：
- 一半在 **17–460s** 就停了（textform / premature / narrate），**远早于正常完成时间** → 是模型主动"说完就停"，不是跑不完。
- 少数长的（1425 / 1507 / 1870s）是干了很多活后**在收尾一步崩掉**，前功尽弃。

---

## 4. 结论与建议

**根因归属：模型侧，非管线侧。**
1. **工具调用协议不稳定（占 60%）**：flash 系（尤其 flashv1_1）在长上下文后期会把结构化调用退化成文本 / 特殊 token 泄漏 / 工具名拼错。→ 训练侧重点：**工具调用格式的鲁棒性**（长轨迹后期尤甚），清理 DSML 特殊 token 泄漏。
2. **收尾纪律差（占 35%）**：用 `<report>` 自然语言代替真实动作、宣告下一步却不执行。DPO 模型更明显（更爱输出文字）。→ 训练侧：强化"动作而非叙述"，抑制过早"交付感"。
3. **大表不收敛（1 个）**：超大 xlsx → 话痨。→ 数据侧/prompt 侧：大表预处理或强约束。

**给评测/看板的提示**：这些失败 `error=null`、`terminal_class` 为 `render_suspect`/`done_no_html`，dashboard 上应把这两类单独标注为"生成失败"，避免与低分正常产物混淆。
