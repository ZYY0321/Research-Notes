## 三、看板/pipeline 侧的三个改进点

### 1. runs.json 已登记但无 scores 的显示逻辑

**现状**：dashboard 直接把 gpt56sol_* 两条列出来但内容为空，看起来像"bug 或数据丢失"。

**建议**：在 dashboard `/api/index` 拉数据时，若 `batch_summary.json` 中 `deck_scorable_ratio < 5%`（或某阈值），加状态徽标 `no_scorable`（灰色，附一行"生成侧未落地 HTML 页，未跑判分"），而不是让卡片空着。

参照现有守卫（`server.py:170 _effective_scan_root()` 对陈旧 deck_root 的处理）的做法：**在 dashboard 侧明确表达"知情但无产物"，比"看起来像 bug"更好**。这条与 `0708_dashboard核查与DPO模板混乱归因.md` §一 的思路一致。

### 2. auto_pipeline 早退时的信号回吐

**现状**：`.autopipe.log` 只有一行 `... exited @ ...`，不写为什么退（0 cases vs 47 skipped 只在 stdout 里）。

**建议**：早退时 append 一段结构化 JSON 到 runs.json 对应条目里（如 `{"skipped_reason": "no_scorable_deck", "scorable_cases": 0, "total_cases": 47}`），dashboard 直接读，不用去 grep 日志。

### 3. 早期告警：批级 abort 门槛

**本次代价**：notpl 批跑了 **15h44min / 46 case**，全 fail，才知道模型不调 init 脚本。如果 runner 加一条"首 3 case 都无 `pptid_<UUID4>` 则 abort 全批"的守卫，可以省 15h。

这条与生成侧 §5.2 的建议是一体的，实现在 runner 侧（`benchmark/scripts/` 或 agentv3 `run_batch` 入口）。
