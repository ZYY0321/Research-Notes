# 一次"成功"的失败：我是怎么揪出新模型接入的三个坑的

> 技术随笔 · 2026-07-06 · 关于 PPT 生成 agent 接入新模型 `checkpoint-2200` 的一次排障

## 缘起

组里训了个新模型 `flash-v1_1-fp8-step2k`，扔过来两个地址，一句话：「测测效果」。

任务看起来很标准：接进 PPT 生成 agent，端到端跑一遍（生成 → 打分 → 上看板）。有现成的交接文档、有跑通过的老模型做参照。按说改两处配置、跑个 smoke 就完事。

结果这个 smoke，让我连续踩了**三个性质完全不同的坑**。有意思的是：**每一个坑，如果只看最表层的成功/失败标志，都会得出错误结论**。记录下来，因为它挺能说明"为什么不能相信绿灯"。

---

## 坑一：一个 3.6 秒的"成功"

改完配置，跑单题 smoke。结果秒出：

```json
{"terminal_class": "done", "success": true, "duration_s": 3.64,
 "deck_html_pages": 13, "deck_png_pages": 0}
```

`success: true`，`done`，13 页 HTML。如果就此上报"跑通了"，就掉坑里了。

**三个不对劲的地方，我是这么想的：**

1. **3.64 秒生成 13 页 PPT？** 我有参照系——老模型那轮单题动辄十几秒到几十分钟。一个要"规划→写十几页 HTML→复核"的任务，3.6 秒物理上不可能。**异常的快，比异常的慢更可疑**，因为慢至少说明在干活。

2. **`turns: 1`**。一轮就结束，意味着 agent 没经历"生成→自检→重写"的循环。

3. **`deck_png_pages: 0`**。13 个 HTML 页，却 0 张渲染图。而打分要靠图。

单看任何一个都能自我说服（"也许模型快呢"、"也许 png 单独渲染"）。但三个凑一起，指向同一个结论：**它根本没生成，是捡了现成的**。

**去拿实锤**，而不是继续猜。查产物的 `mtime`：

```
page_001.html mtime: 2026-07-02 17:46   ← 今天是 07-06
```

деck 是四天前老模型跑同一道题留下的。再看一个细节坐实：

```
conv_id        = batch_seq_0007_7986a5   （这次的会话）
deck_scan_root = batch_seq_0007_4df70b   （指向的产物目录 —— 对不上）
```

**根因**：sandbox 是所有历史生成**混放的共享目录**。agent 起来跑 seq_0007，deck 扫描逻辑按题号匹配，扒到了四天前那次的产物就报了 done。3.6 秒是因为它真没干活。

**教训**：`terminal_class: done` 是**流程终态**，不是**产物验收**。在一个有缓存/共享状态的系统里，"成功"标志和"真的做了这件事"是两回事。验收要看**产物的物理属性**（mtime、数量、大小），不是状态字段。

**方法论沉淀**：以后所有生成任务的验收标准，从「done」改成「done **且** png>0 **且** 耗时合理 **且** 产物是本次新生成的」。这条后来直接写进了交接文档。

## 坑二：500 里没有信息，就自己造信息

清掉旧数据、换独立输出目录重跑。这次 agent 真调模型了——然后**第一次调用就崩**：

```
litellm.InternalServerError: AnthropicException - Internal Server Error.
（重试 3 次，全 500，放弃）
```

litellm 只透传了一个 `InternalServerError`。500 的 body 只有 21 个字节：`Internal Server Error`。**没有堆栈，没有原因**。

这时候有两条路：把这句话甩给模型侧「你端点 500 了」，或者自己定位。前者大概率被反问「什么请求？我这好好的」——因为**我手动 curl 一句 "say PONG" 是 200 的**。成功和失败之间一定有个变量，得找出来。

**思路：既然真实请求崩、简单请求不崩，那就从简单请求出发，逐步向真实请求逼近，看哪一步翻车。** 二分法。

我先怀疑"重"的因素（这是直觉，但直觉要验证）：

| 变量 | 结果 |
|---|---|
| max_tokens 拉到 128000 | ✅ 200 |
| system prompt 塞 16000 字 | ✅ 200 |
| 带上 11 个工具定义 | ✅ 200 |
| 带 cache_control（prompt caching） | ✅ 200 |

**直觉全错了**。重的东西都扛得住。那就把真实请求一个字段一个字段拆开测。最后逼到一个最小对照：

```
content 是字符串 "say PONG"                        → 200
content 是数组 [{"type":"text","text":"say PONG"}]  → 500
```

**就它**。同一句话，content 从字符串换成数组 block 格式，必崩。

**再拿一个更会说话的证人**：同一个端点还开了 OpenAI 兼容口，我用它发数组 content：

```json
{"error":{"message":"Failed to build prompt: sequence item 0:
  expected str instance, list found","code":400}}
```

anthropic 口闷头 500，openai 口把话说明白了：**端点内部把 content 当字符串直接拼 prompt，遇到 list 就崩**。

**一个中途的自我纠正**：定位到根因后，我一度以为是我们 agent 代码里的 prompt-cache 逻辑把 content 包成了数组（代码里确实有一段给 system 打 cache 标记时会转数组）。但这不对——那段只转 system，而崩的是 user content。**不能停在"看起来合理"的解释上**。我开了 litellm 的 debug，抓到实际发出去的 wire 请求：

```
我传给 litellm 的 content = "字符串"
litellm 实际发出的 content = [{"type":"text","text":"..."}]   ← 它转的
```

铁证：是 **litellm 的 anthropic provider 在发送时，把 content 规范化成了 Anthropic 官方标准的 block 数组格式**。这是标准行为，改不了、也不该改——**该修的是端点**（老端点就支持这个格式，所以老模型能跑）。

**教训**：
- **一个模糊的错误（500 无 body）不是终点，是起点**。客户端拿不到堆栈，就用"受控变量逼近"把不确定性一点点消掉，直到剩一个最小可复现差异。
- **给下游报 bug，要给能复现的最小案例 + 原始报文，不是给结论。** 我最后交给模型侧的是两行 curl（一行崩一行不崩）+ wire 级请求体 + 那句 openai 的 400。他不用信我，自己跑一遍就看到。
- **别停在第一个自洽的解释上。** "是我们 cache 逻辑转的"听起来很合理，但一抓 wire 就证伪了。合理 ≠ 正确。

## 坑三：真做了，但没做完

端点修复后第三次 smoke。这次 agent 跑了 **55 秒**——终于像在干活了。但结果：

```json
{"terminal_class": "done", "duration_s": 54.96, "deck_png_pages": 0}
```

又是 png=0。但这次和坑一**性质完全不同**，得区分开——不能因为"又是 png=0"就以为是同一个问题复发。

查轨迹：55 秒里 agent 读了 skill、建了工作目录、正准备写 task_pack/info_pack……然后 `--max-turns 8` 到头了，**被截断**。它卡在"准备阶段"，还没进入逐页 HTML 生成，自然没有 png。

**同样是 png=0，坑一是"根本没干活（复用旧的）"，坑三是"在认真干、但没干完"**。区分二者的证据：坑一 3.6 秒 / 1 turn / 产物是旧的；坑三 55 秒 / 走满 8 turns / 有本次新建的工作目录和轨迹。

根因：这题偏重（并购财务尽调，要大量结构化表格），8 轮不够。换了道轻量题、把 max-turns 提到 20 再跑——现在正常推进到大纲阶段了。

**教训**：**相同的表层症状（png=0）可以来自完全不同的根因**。不看过程只看结果，会把"没做完"误诊成"没做"，然后白白去查错方向。症状是用来分诊的，不是用来下结论的。

## 回头看：方法论

三个坑，三种性质——**误报的成功、无信息的失败、被截断的成功**——但排查手法是同一套：

1. **不信绿灯，验产物。** 状态字段（done/success）是流程自报，产物属性（mtime/数量/耗时）才是事实。二者对不上时，信后者。

2. **异常的"顺"和异常的"卡"同样可疑。** 3.6 秒的成功比报错更危险，因为它伪装成好消息。

3. **模糊的错误用受控变量逼近。** 从能复现的最简情况出发，逐个加变量，直到锁定唯一差异。直觉（"是不是太重了"）用来排序尝试，不用来下结论。

4. **抓到"现场"再定性。** 拿不到堆栈就开 debug 抓 wire 请求。别用"看起来合理"代替"我看到了"。

5. **相同症状不等于相同病因。** png=0 出现两次，根因一个是复用旧产物、一个是轮次截断。分诊靠过程证据。

6. **报 bug 给最小可复现案例，不给结论。** 让对方能自己重现，比你说一百句"确实崩了"都有用。

说到底就一句话：**在一个有状态、有缓存、多层代理（agent→litellm→端点→sandbox）的系统里，任何单一信号都可能骗你。交叉验证，直到证据链闭合。**
