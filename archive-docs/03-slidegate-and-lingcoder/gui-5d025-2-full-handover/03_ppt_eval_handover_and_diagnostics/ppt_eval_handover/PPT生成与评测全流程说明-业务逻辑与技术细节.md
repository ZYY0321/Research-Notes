# PPT 生成与评测：Agent 执行循环、PPT Skills 与模型评分

整个系统可以理解为三部分：**Agent runtime 负责让模型持续调用工具完成任务；PPT Skills 告诉模型制作演示文稿应遵循什么步骤；评测程序把生成页面交给裁判模型，按预设标准打分。** 从用户输入到最终结果，主线就是：需求与附件 → 整理参数和材料 → 确定风格或模板、生成大纲 → 按页生成 HTML → 检查并交付 → 截图评分。

先看 Agent。它的核心是一个常见的 harness，也就是包在模型外面的执行程序。程序把系统提示词、用户需求、已有对话和工具定义交给大模型；模型返回文本或工具调用；程序解析输出，检查工具名和参数是否合法，执行工具，再把执行结果交回模型。模型根据结果决定下一步，重复这个循环，直到任务结束、需要用户确认或达到运行限制。后续轮次会携带已有结果，并不是每轮都重新开始。

```text
准备消息与可用工具定义
    ↓
调用大模型
    ↓
解析输出
    ├─ 调用工具 → 校验参数 → 执行 → 将结果写回消息 → 再调用模型
    ├─ 需要确认 → 保存状态 → 收到答案后继续
    └─ 完成交付 → 返回结果
```

项目中的这套循环由自己编写的 `BaseNode`、`BaseAgent` 和 `AgentV3` 实现，模型接入通过 `BaseLLM` 封装 LiteLLM。工具校验、错误处理、状态保存和调用次数限制，都属于这层执行保障。主 Agent 要分派工作时，会调用 `create_subtask`；调度器用独立上下文运行子 Agent，完成后把返回结果接回主 Agent。主、子 Agent 当前使用同一个主模型配置，分工主要靠任务说明和上下文区分。核心编排没有交给 LangChain 或 LangGraph。

PPT 的具体业务步骤则写在 Skills 里。一个 Skill 包含 `SKILL.md` 流程说明，以及阶段说明、提示词和 Python 脚本。主 Agent 先从技能目录看到名称、用途和位置，判断任务需要制作 PPT 后，读取 `ppt-maker/SKILL.md`。所谓“使用 Skill”，就是模型读懂这份流程，再按步骤调用相应工具、读取下一份说明或启动脚本。Skill 规定业务顺序，runtime 负责真正执行这些动作。

例如用户说：“根据季度销售表，为管理层做一份10页经营复盘，说明业绩变化、主要问题和下一步行动，使用无模板模式。”`ppt-maker` 首先把这段话整理成明确的制作参数：主题是什么、给谁看、什么场景、多少页、什么语言、是否用模板、有哪些附件。参数缺失时可以向用户确认；有表格或报告时，则按需要委派文件解析、数据分析任务。这个阶段要把材料整理到足以支持大纲，而不是让页面生成时再临时猜测原始数据。

整理结果主要放进两份文件：`task_pack.json` 是任务参数表，`info_pack.json` 是可用素材包。假设销售表中的四季度销售额分别为100、120、90、150万元，下面展示它们的含义。这些数字仅作教学示例，字段也只摘取关键部分。

```text
task_pack.json：要做什么
  主题：季度销售经营复盘
  受众：管理层
  页数：10页
  模式：无模板
  要求：覆盖业绩变化、主要问题和行动建议

info_pack.json：依据什么来做
  季度数据：Q1=100，Q2=120，Q3=90，Q4=150，单位万元
  分析结论：全年460万元，Q3环比下降25%
  信息缺口：源表没有提供下降原因，不能直接断言原因
```

接着，主 Agent 按模式读取无模板或模板 Skill，并按其中的步骤派发子任务。无模板模式先生成 `style_spec.json`，把“什么风格”落实成整套共用的配色、字体和布局规则；再结合任务参数、素材和风格生成 `outline.json`，确定每页讲什么、用什么形式呈现。**风格是整套的视觉规则，大纲是逐页的内容方案。** 例如两份文件中的片段可以是：

```json
{
  "design_concept": {"core_theme": "清晰的蓝白经营分析风格"},
  "color_palette": [
    {"role": "background", "hex": "#FFFFFF"},
    {"role": "primary", "hex": "#2563EB"},
    {"role": "accent", "hex": "#F59E0B"}
  ]
}
```

上面是风格片段，意思是白色背景、蓝色主要图形、橙色强调重点。下面是大纲中第3页的片段，意思是本页要用季度图表说明Q3回落，并提醒原因尚待核查。示例均省略了其他必填字段。

```json
{
  "page_id": "page_003",
  "page_number": 3,
  "title": "Q3销售回落，Q4恢复增长",
  "page_goal": "展示季度变化，重点关注Q3环比下降25%",
  "layout": {
    "category": "two_column",
    "custom_description": "左侧季度销售柱状图，右侧关键结论"
  }
}
```

如果用户选择模板模式，相应步骤就是先确定每页对应哪种已有模板布局，写入 `template_map.json`，再安排大纲。例如季度趋势页选择“左图右文”模板。大纲生成后需要确认；再根据各页需要整理已有图片，写出 `asset_map.json`，记录图片该用在哪页、实际文件在哪里。比如第2页需要用户上传的门店照片，就将这个图槽关联到真实图片路径。当前流程复用已有图片，缺图时按无图方案处理。

到这一步，按页生成所需的信息已经齐全。切片脚本把整套材料拆成每页一份输入，包含共同风格或参考模板、本页大纲和本页资源。随后页面生成子任务运行批量 Python 脚本，由脚本并发调用页面模型，生成 `page_001.html`、`page_002.html` 等文件。以第3页为例，模型接到的任务相当于：“按蓝白风格，左边画100、120、90、150的季度柱状图，右边写Q3下降25%，用橙色强调Q3，返回完整HTML。”主 Agent 负责流程推进，脚本负责逐页调用和保存，页面模型负责具体HTML/CSS实现。

生成脚本会做页面结构检查，失败时带着检查原因尝试重出。无模板模式还会截图，让视觉模型复核页面，发现遮挡、溢出等问题时按需改写一次；模板模式没有这套截图复核与改写步骤。最后检查页面是否齐全并返回交付状态。这里生成的“PPT”实际是一套可逐页展示的HTML页面和资源，当前制作流程不要求输出 `.pptx` 文件。

生成之后，独立评测程序将最终HTML及资源整理成评测输入，通过浏览器渲染成截图，再调用裁判模型。**核心评分方式就是人事先写好标准和prompt，让视觉LLM看页面、按标准给出判断与分数。** 单页视觉评分通常一页一次调用，同时返回多个维度；全套与内容评测则使用多页截图、用户需求和适用的源材料。生成阶段的自检用于修改产物，独立评分用于评价最终产物，两者要分开理解。

单页评分分三个层面。“硬性检查”看有没有裁切、遮挡、明显空框或图片失真等基本交付问题；“细粒度美观”看对齐、间距、组件样式、文字清晰度、字号层级和行距这些具体细节；“高层美观”看整页的视觉主次、阅读顺序、风格协调和整体完成度。例如销售图没有任何遮挡，硬性检查可以通过；但标题、图表和结论间距混乱，会影响细粒度美观；所有区域同样抢眼、第一眼不知道先看哪里，会影响高层美观。这些基础判断主要由模型看图完成，“硬性”不代表代码已经通过几何计算证明结果。

程序将硬性检查的通过情况、细粒度的0～2档位、高层美观的0～3档位换算到0～1，再跨页汇总，按 `page_score = 0.35×硬性检查分 + 0.40×细粒度美观分 + 0.25×高层美观分` 计算。全套分 `deck_score` 则看页面连在一起是否结构完整、篇幅分配合理、风格一致，以及材料覆盖或整体内容质量。例如每页都好看，但整套没有行动建议，仍会影响全套与内容评价。

内容分 `content_score` 依据通用清单和模型根据本题生成的动态清单，检查是否满足用户需求。L0、L1、L2可以理解为基本要求是否成立、是否有具体细节、是否适合任务场景。例如“行动建议”只写一个标题不够，还要有具体动作，并针对Q3异常。存在源材料时，再让模型核查事实忠实度：“Q3为90万元”有直接依据，“全年460万元”是合理计算，“因为竞争对手降价而下滑”则没有当前材料支持。覆盖度关注该讲的是否讲到，忠实度关注讲出的是否有依据。

各项结果最后由代码按权重汇总。当前基础公式是 `overall_score = 0.30×page_score + 0.35×deck_score + 0.35×content_score`。例如三项分数分别为0.80、0.75、0.90，总分就是0.8175。需要注意，部分内容通过率、忠实度等统计值也直接采用模型返回结果，代码没有统一从逐项判断重新计算。因此，这是一套按固定标准组织的模型裁判评测，分数仍然受judge、prompt、截图与材料处理质量影响。

批量评测就是对固定题集重复上述过程：每个模型跑47道无模板题和47道模板题，固定工具范围等条件，自动处理必要确认，保存生成轨迹和评分记录。最后按题目对齐产物与分数，汇总到看板、模型卡和总分表。结果同时报告生成成功数、评分覆盖数和质量分，才能区分“能否稳定完成任务”和“完成后质量如何”。页面、大纲及工具轨迹用于回查问题发生在哪一步。
