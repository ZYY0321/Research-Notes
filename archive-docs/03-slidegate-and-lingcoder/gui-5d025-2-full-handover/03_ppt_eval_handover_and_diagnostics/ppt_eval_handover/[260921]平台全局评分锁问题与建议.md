# 测试平台全局评分锁：问题说明与改进建议

> 本文解释命令行评测中“等待全局评分锁”的含义、当前实现的问题，以及后续可以怎样改进。
>
> 盘点时间：2026-09-21  
> 本文只分析现有实现并提出建议，不删除评分锁文件，不绕过平台评分流程。

## 1. 先说结论

当前平台的全局评分锁本身不是普通的“文件占用标记”，而是 Linux 内核提供的进程锁。它的设计目的，是让全机所有评分任务共享一个评分队列，避免多个任务同时调用裁判模型、写评分结果或执行汇总时互相干扰。

现在主要问题是：

1. 所有平台任务和命令行任务竞争同一把全局锁。
2. 评分任务在拿锁前会无限等待，用户看不到排队位置、当前持有者和预计等待时间。
3. 拿到锁后，锁的持有范围很大，包含评分前准备、裁判调用、结果重算、汇总和部分交付物刷新。
4. 锁文件本身没有记录 owner。只看文件是否存在，无法判断锁是否正在被进程持有；这属于平台评分锁协议没有配套状态记录。
5. 终评分重派发目前没有明确次数上限；如果只差一个始终无法评分的 case，监控可能周期性重新发起评分，反复竞争全局锁并重复消耗裁判模型资源。

当前实现实际等待时间主要取决于当时谁已经持有全局锁、该任务还要持锁多久，以及等待进程之间的竞争顺序。

### 1.1 问题分析



| 问题 | 当前实现 | 应归到哪里 |
|---|---|---|
| 为什么要限制同一时间只能有一个正式评分流程 | 所有评分入口共用 `automation/tasks/_global_scoring.lock` | 平台评分流水线的整体设计 |
| 谁在申请这把锁 | 平台侧的 `automation/pipeline.py`、批量评分脚本，以及命令行的 `score.py` 都会申请 | 各个评分入口共同遵守的协议 |
| 为什么等了很久仍看不到排队信息 | 当前评分调度没有统一记录队列、owner、等待时长和超时状态 | 平台评分调度和状态记录机制 |
| 为什么只看锁文件无法知道谁持有锁 | `flock` 的持有状态由 Linux 内核维护，锁文件通常只是承载锁的空文件 | 平台锁协议缺少 owner/状态登记；命令行不能仅凭文件存在状态判断 |
| 为什么锁可能被占用很长时间 | 持锁范围覆盖裁判调用、结果重算、汇总和看板刷新 | 平台评分流水线的锁粒度设计 |

主要问题是：平台侧为什么长期不释放锁、平台是否有其他任务持续占用锁，以及平台是否记录了可查询的排队状态。



## 2. 什么是全局评分锁

可以把评分服务想成只有一条入口的窗口：

```text
平台任务 A ─┐
平台任务 B ─┼──> 全局评分锁 ──> 裁判模型/评分器 ──> JSONL 与汇总
命令行任务 ─┘
```

谁先拿到锁，谁就可以进入评分区；其他任务必须等待。当前代码中的锁文件是：

```text
/home/gui-5d025-2/zyy/xhx_agent_v3/automation/tasks/_global_scoring.lock
```

可以把这个文件理解成评分区门口的同一把门：平台评分进程和命令行评分进程都使用这扇门，谁先对这个文件执行成功的独占 `flock`，谁就暂时拥有进入评分区的资格；其他进程对同一个文件申请独占 `flock` 时就会等待。

因此，命令行中的 `LOCK_EX` 不是“再去占用一个命令行自己的锁”，而是“申请占用平台约定的那一个全局评分锁”。在当前仓库里，平台侧批量评分代码 `automation/pipeline.py` 也会对同一个 `_global_scoring.lock` 执行 `LOCK_EX`。命令行和平台评分进程竞争的是同一个内核锁。8770 看板本身主要负责登记和展示，通常不是直接持有这把评分锁的进程。

“锁文件是空文件”是正常的。它的文件内容不承担“已锁定”这个信息，文件只是给多个进程提供一个固定的、可共同打开的对象。真正的锁定状态由 Linux 内核记录在进程打开的文件描述符上：

```text
空文件：提供一个固定的锁对象
flock：向 Linux 内核申请这个对象的使用权
LOCK_EX：申请独占使用权，同一时刻只能有一个进程成功持有
```

所以，不能用“文件里有没有内容”或“文件是否存在”判断评分是否正在运行。判断标准是某个进程是否仍然持有这个文件描述符对应的内核锁。

在命令行评分入口中，`score.py` 会执行类似下面的逻辑：

```python
with global_lock.open('r') as lock:
    print('等待全局评分锁；等待期间不能称为已经打分')
    fcntl.flock(lock.fileno(), fcntl.LOCK_EX)
    # 获得独占锁后，才真正开始评分
```

`LOCK_EX` 表示独占锁：同一时刻只能有一个评分流程持有它。

这个锁文件通常是一个空文件。真正的状态不是文件内容，而是某个进程是否通过 `flock` 在内核中持有了这个文件描述符。因此：

- 文件存在，不代表当前一定有人持锁；
- 删除文件不能安全地“解除”一个已经被进程持有的锁；
- 持锁进程退出后，内核会自动释放锁；
- 如果持锁进程一直活着但内部卡住，其他任务就会一直等待。

## 3. 它和生成锁有什么区别

生成和评分保护的是不同资源，所以使用不同的锁。

### 3.1 生成锁

正式生成脚本使用每个测试目录下的模式锁：

```text
$CTL/formal_notpl.lock
$CTL/formal_tpl.lock
```

启动形式大致是：

```bash
flock -n "$CTL/formal_${MODE}.lock" run_batch_and_export.py ...
```

它主要防止同一个测试的同一个模式被重复启动，或者两个生成进程同时写同一个输出目录。模板模式和无模板模式使用不同锁，因此可以并行生成。

### 3.2 评分锁

评分使用全机共享的：

```text
automation/tasks/_global_scoring.lock
```

它主要保护共享的裁判服务、评分资源以及评分结果处理流程。平台历史实现已经把全机评分设计成一次只跑一套评分队列，评分器内部再使用有限数量的 worker。

所以当前行为是：

```text
生成：每个测试、每个模式单独加锁，可以并行
评分：所有测试共用一把全局锁，跨任务串行排队
```

这不是因为模板模型和无模板模型不同，也不是因为主模型不同，而是因为它们进入了同一个共享评分基础设施。


## 4. 当前实现的具体问题

### 4.1 没有统一的可观测队列

当前锁文件没有 owner、task ID、mode、开始时间或心跳信息。`flock` 只提供互斥，不提供业务层队列管理。

因此即使看到 `_global_scoring.lock`，也不能从文件中直接知道哪个任务持有它。必须额外检查进程、日志和文件描述符，而且不同评分脚本的日志位置也不完全统一。

### 4.2 全局锁范围过大

当前 `_score_mode_unlocked` 包含：

- `build_benchmark_eval.py` 生成评分输入；
- 调用裁判模型；
- 重算 JSONL；
- 生成汇总报告；
- 更新本地模型卡和交接材料；
- 请求看板刷新。

这些操作并不都需要互斥。例如，不同 run 使用不同的结果目录和不同的评分 JSONL，很多准备和汇总工作可以在锁外完成。现在全部放在锁内，会把每个任务占用全局评分窗口的时间拉长。

### 4.3 外部网络调用被放在全局锁内

裁判模型调用可能因为网络、服务负载或单题复杂度变慢。只要评分进程仍然存活并持有锁，所有后续任务都会等待。

如果持锁进程内部没有超时、重试失控或异常处理不完整，就会出现“进程还活着，但后面的任务一直等”的情况。此时锁文件看起来仍然正常，问题却已经从普通排队变成持锁任务异常缓慢。


### 4.4 监控和重试需要分开看

当前平台控制器确实有一个长期轮询的 `monitor_loop`，大约每 120 秒检查一次生成、评分和进程状态。它不是“每个 PPT 一个永远运行的监控进程”，而是通常每个任务挂一条监控线程；服务重启后，还会根据 `state.json` 给仍处于 running 的任务重新挂监控。

如果某个生成进程一直活着，但始终没有产生有效 HTML 或没有写出 `batch_done`，监控线程会持续轮询，任务可能长期处于未完成状态。这一层是监控生命周期没有明确失败上限的问题。

生成阶段的基础设施续跑有明确上限，但只在 `auto_resume_infra=true` 时启用：默认最多 `max_infra_resume_passes=3` 次，每次续跑至少间隔 300 秒。它只处理 `infra_failed` 和没有终态的中断类情况，不会自动反复重跑确定性内容失败或 `other_error`。

评分阶段则存在更值得注意的区别：`monitor_loop` 在终评分任务结束后，如果发现覆盖不完整或评分返回失败，会在下一轮重新派发终评分；当前代码没有给这种“终评分派发次数”设置上限。因此，一个始终无法覆盖的 case 可能导致监控线程周期性重新发起评分，每次重新发起都会再次竞争全局评分锁。

主要问题是后台评分失败后没有进入最终失败状态，而是继续创建新的评分流程。

这会形成实际的资源浪费，而不只是让用户多等一会儿。`skip_done=true` 会跳过已经成功写入结果的 case，所以后续轮次通常不会把整批 47 个 case 全部重新计费；但是那个缺分 case 仍会被反复送入评分器。如果失败发生在裁判请求、响应解析或内容判分阶段，重复轮次就可能重复消耗 token、重复占用裁判并发，并且每轮都在全局锁内运行，继续阻塞其他任务。如果失败发生在模型调用之前，则可能不消耗 token，但仍会产生重复调度和锁竞争。

例如，47 个 case 中有 46 个已经成功、1 个始终失败时，当前逻辑可能是：

```text
评分 46 个成功结果，剩 1 个缺分
        ↓
monitor_loop 等待约 120 秒
        ↓
再次启动评分，skip_done 跳过 46 个，重试缺分 case
        ↓
仍然缺分
        ↓
重复上述过程，直到人工干预或问题偶然恢复
```

因此，这一项应视为当前全局锁问题中的高优先级问题：外层评分重派发必须有最大次数或最大时长；超过阈值后，应把失败 case 标记为 `scoring_blocked` 或 `needs_triage`，保存最后错误和尝试次数，释放全局锁，让其他任务继续评分。之后由人工确认原因，再对缺失 case 做一次定向续评。

评分器内部本身也有重试，但它和外层监控重派发不是一回事。通过当前 `pipeline._score_mode_unlocked` 进入官方评分时，会设置：

- 单次裁判请求最多尝试 3 次（`GEMINI_MAX_RETRIES=3`、`GEMINI3_EVAL_MAX_RETRIES=3`；这里的 3 包含首次请求）；
- 内容 JSON 解析或空响应的外层快速重试默认是 6 次，即 `CONTENT_CHECKLIST_GEN_RETRIES=5` 加首次调用；
- 评分配置使用 `skip_done=true`，后续评分轮次会跳过已经写入的结果，只尝试未完成部分。

## 5. 后续建议修改与优先级

修改顺序应该先处理“会不断产生新评分任务、持续消耗 token、长期占用全局锁”的问题，再处理等待过程是否容易观察。终端显示等待本身不是主要故障，它只是把后台锁竞争暴露出来；最优先要限制的是第四节 4.4 中外层监控的无限重派发。

### 5.1 P0：给外层终评分重派发增加明确上限

平台监控需要为每个 `task_id + mode` 保存终评分状态，例如：

```json
{
  "final_score_attempts": 2,
  "max_final_score_attempts": 3,
  "last_score_started_at": "...",
  "last_score_finished_at": "...",
  "last_error": "...",
  "missing_case_ids": ["..."]
}
```

每次真正启动一轮终评分时，计数加一；单纯等待全局锁不应重复计数。达到最大次数，或达到配置的最大总时长后，监控应停止自动派发，把该模式标记为 `scoring_blocked` 或 `needs_triage`，记录缺失 case、最后错误和评分日志路径，并让当前评分流程正常释放锁。

后续需要恢复时，只对缺失 case 做定向续评，不要重新自动提交整套终评分。这样可以避免“47 个 case 中只缺 1 个，却让平台无限重复启动评分”的情况。

### 5.2 P1：把坏 case 从整批评分状态中隔离出来

当前只要评分覆盖不完整，外层就可能把整套评分视为未完成。建议把结果状态拆开：

```text
整批评分：已完成 46/47
缺失 case：1 个
缺失原因：裁判请求失败 / 响应解析失败 / 输入异常
该 case：自动重试中或已转人工处理
```

已经成功评分的 case 应保持可用；单个 case 达到重试上限后，应进入明确的失败或待处理状态，不能继续触发整批自动重派发。这样既能保留阶段性结果，也能释放全局评分资源给其他任务。

### 5.3 P1：缩小全局锁的保护范围

可以把评分流程拆成锁内和锁外两部分：

```text
锁外：准备输入、检查已有结果、读取缺失 case
锁内：真正调用共享裁判资源、写入需要互斥的共享结果
锁外：重算本任务汇总、生成交付物、刷新看板
```

具体能否移出全局锁，需要确认 benchmark 结果目录、缓存和汇总脚本是否存在跨任务共享写入。确认安全后再调整，不能直接删除锁或简单缩短 `with flock` 代码块。

### 5.4 P1：建立真正的评分队列和状态记录

全局锁只能提供互斥，不能提供队列。平台应增加一个统一的评分任务记录，至少包含：

- task ID、mode 和缺失 case 集合；
- 提交时间、进入队列时间、获得锁时间、评分开始和结束时间；
- 当前状态：`queued`、`running`、`partial`、`succeeded`、`blocked`、`failed`；
- 当前 owner、PID、评分日志路径和心跳；
- 外层派发次数、单 case 尝试次数和最后错误。

这样平台和命令行都提交到同一个队列，由调度器决定顺序；评分进程不再直接无限竞争裸 `flock`。`flock` 可以继续作为 worker 的底层保护，但不再承担队列、优先级和失败恢复职责。

### 5.5 P2：完善网络调用和内层重试的边界

内层模型请求已经有重试配置，但还需要把每次评分的超时、重试次数、退避时间和 token 使用量写入日志。一个 case 在请求失败、响应为空、JSON 解析失败或写结果失败时，应记录不同的失败类型，避免所有问题都被外层当成“还没评分完”而重复提交。

如果评分进程长时间没有心跳，平台应先把它标记为异常持锁任务，再由明确的恢复流程处理，不能让一个失去进展的进程无限持有全局锁。

### 5.6 第四节问题的优先级

| 优先级 | 对应问题 | 建议先改什么 | 直接收益 |
|---|---|---|---|
| P0 | 4.4 监控和重试无上限 | 限制终评分外层重派发次数/总时长，单个坏 case 超限后转 `needs_triage` | 立即阻止无限抢锁和重复消耗 token |
| P1 | 4.4 单个坏 case 拖住整批 | 按 case 隔离失败，保留已完成分数，支持定向续评 | 避免 1 个坏 case 反复重跑整套流程 |
| P1 | 4.2 全局锁范围过大 | 将准备、汇总和交付物刷新尽量移到锁外 | 缩短每次持锁时间，减少后续排队 |
| P1 | 4.1 没有统一可观测队列 | 建立统一任务状态、owner、PID、心跳和队列顺序 | 能知道谁在排队、谁持锁、为什么失败 |
| P2 | 4.3 外部网络调用在锁内 | 固定请求超时、内层重试和心跳，区分网络失败与内容失败 | 降低单个慢请求长期占锁的风险 |
| P2 | 4.1 锁文件容易误解 | 提供诊断命令或状态接口，明确文件存在不等于持锁 | 减少误删锁文件和错误判断 |
