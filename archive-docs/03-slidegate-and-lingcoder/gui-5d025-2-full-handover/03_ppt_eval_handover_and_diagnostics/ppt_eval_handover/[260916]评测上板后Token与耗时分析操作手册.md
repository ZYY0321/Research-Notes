# 评测上板后：Token 与耗时分析操作手册

## 1. 用途和执行时机

在自动化生成、评分、上板结束，正式产物停止写入后，使用已有文件分析 Token 消耗和时间成本，输出两个逐 case 附件：**Token 消耗附件**和**时间成本附件**，均提供 Markdown、CSV、JSONL 格式。

分析脚本：[automation/analyze_completed_run.py](../automation/analyze_completed_run.py)。只需 Python 3 标准库，不调用模型，不重新生成、评分或上板。

旧 `performance_report.md` 只统计主轨迹 `main.json`，漏掉子任务中的大量 HTML 生成和 review 调用，导致请求数、Token 和请求耗时统计偏低。

## 2. 自动化评测后的数据在哪里

以项目根目录 `/home/gui-5d025-2/zyy/xhx_agent_v3` 为起点：

| 数据 | 位置 | 用途 |
|---|---|---|
| 自动化任务状态 | `automation/tasks/<task_id>/state.json`、`latest.json`、`latest.md` | 定位本次正式生成目录 |
| 正式生成目录 | `output/testset_v2_<task_id>_<mode>_<时间戳>/` | 每个模式对应一个分析输入；notpl 为无模板，tpl 为模板 |
| 批次及逐 case 实际耗时 | `<生成目录>/batch_summary.json` | `total_duration_s` 为整批实际耗时，`results[].duration_s` 为单 case 实际耗时，单位均为秒 |
| 主轨迹 | `<生成目录>/<case_id>/main.json` | 主 agent 执行记录，包含它直接执行的大纲、HTML 等调用 |
| 子任务轨迹 | `<生成目录>/<case_id>/subtask_*.json` | 子 agent 执行记录，必须与主轨迹一起统计 |
| 完整结果及初始输入 | `<生成目录>/<case_id>/result.jsonl` | 用 `case.query` 匹配评分记录 |
| 评分 JSONL | `../benchmark/results/industry_v2_<task_id>_<mode>.jsonl` | 提供每个 case 的 overall_score 总分 |

看板链接用于识别运行，不是 Token 数据源；输入必须来自同一批正式产物，不混入 smoke 或其他时间戳的运行。

以下示例对应本次 **merge 后的 `20260913_045152` 运行**，两个模式各 47 个 case。

```bash
ls ../benchmark/results/industry_v2_ppt_outline_merge_v39_dpov2_mtp_20260911_tpl.jsonl
```

四个文件都应存在；各 case 的主轨迹、子任务轨迹保留在生成目录中，无需复制。

## 4. 第二步：运行分析代码

在上一步的项目目录中执行：

```bash
ANALYSIS_OUTPUT=$(mktemp -d "$PWD/automation/tasks/ppt_outline_merge_v39_dpov2_mtp_20260911/analysis_delivery_XXXXXX")

python3 automation/analyze_completed_run.py \
  --run notpl=output/testset_v2_ppt_outline_merge_v39_dpov2_mtp_20260911_notpl_20260913_045152 \
  --run tpl=output/testset_v2_ppt_outline_merge_v39_dpov2_mtp_20260911_tpl_20260913_045152 \
  --scores notpl=../benchmark/results/industry_v2_ppt_outline_merge_v39_dpov2_mtp_20260911_notpl.jsonl \
  --scores tpl=../benchmark/results/industry_v2_ppt_outline_merge_v39_dpov2_mtp_20260911_tpl.jsonl \
  --output "$ANALYSIS_OUTPUT" \
  --label 'Merge 后评测 Token 与耗时分析（20260913_045152）'

printf '附件目录：%s\n' "$ANALYSIS_OUTPUT"
```

| 参数 | 含义 |
|---|---|
| `--run MODE=PATH` | 模式名称及正式生成目录，可传多个模式 |
| `--scores MODE=PATH` | 同名模式的评分文件；可省略，省略后不影响 Token 和时间分析 |
| `--output PATH` | 分析输出目录；必须是新目录或空目录，上述 mktemp 命令每次自动创建新目录 |
| `--label TEXT` | 报告标题 |

分析其他批次时，替换生成目录、评分文件、输出目录及标题即可。默认评分字段为 `overall_score`；缺失评分留空，不按 0 分处理。

脚本成功结束后才使用附件；如报错，先解决错误。后续命令在同一终端执行；若重新打开终端，先把 `ANALYSIS_OUTPUT` 设为刚打印的实际输出路径。

## 7. Token 和时间的统计含义

### 通用字段

| 表头 | 含义 |
|---|---|
| mode / case_id | 生成模式 / 测试用例编号；notpl 为无模板，tpl 为模板 |
| stage | 阶段：outline 大纲生成、html_generate 页面生成、html_review 页面审查、image_generate 图片生成、image_filter 图片筛选 |
| model / request_id / sources | 调用模型 / 请求标识 / 原始轨迹文件路径 |
| coverage_status | incomplete_or_suspect 表示存在覆盖问题；unverified 表示未触发检查，但也未证明完整 |
| coverage_notes | 覆盖问题代码，分号分隔；具体来源见 issues.json |

### Token

Token 来自 API 返回的 `usage`，统计主轨迹和全部子任务轨迹中已保存的响应；不按原始用户输入字符数或最终回复长度估算。

| 表头 | 含义与单位 |
|---|---|
| prompt_tokens | 输入 Token：系统提示、用户输入、历史消息、工具结果等完整请求上下文，单位：token |
| completion_tokens | 输出 Token：模型正文、工具调用等，以及服务计入输出的思考部分，单位：token |
| total_tokens | API 返回的总 Token，通常等于输入加输出，单位：token |
| usage_count | 有有效 usage 的响应数，单位：条；不是全部模型调用次数，也不是页数 |
| response_count | 已扫描并去重的响应事件数，含没有有效 usage 的事件，单位：条 |
| token_scope | observed_tool_usage_only 表示仅统计已保存的工具模型用量 |

完全相同的响应事件按 case 去重；同 request_id 但内容不同的响应仍保留。没有观测数据时 Token 留空，不能按零成本理解；主/子 agent 未保存的推理用量、截断日志、无 usage 的失败请求和评分调用不在总量中。

### 时间

时间单位均为**秒**，字段后缀 `_s` 即表示秒；优先用 `wall_duration_s` 了解单 case 实际等待时间。

| 表头 | 含义 |
|---|---|
| wall_duration_s | 单 case 生成任务的实际耗时，来自 batch_summary；包含模型等待、工具执行，不含评分和上板 |
| batch_wall_s | 整个模式批次生成任务的实际耗时，来自 batch_summary.total_duration_s |
| wall_time_status | batch_recorded 表示有有效实际耗时记录；missing 表示缺失 |
| started_at / completed_at | 单 case 的开始 / 完成日期时间，保持原记录格式 |
| seconds | 请求级明细中的单次模型调用耗时 |
| timed_response_count | 有有效 seconds 的响应数，单位：条 |
| sum_s | 已观测模型响应耗时之和；并发可能重叠、日志遗漏可能少计，不等于实际耗时 |
| mean_s | 已观测单次模型响应耗时的算术平均值 |
| p50_s | 单次响应耗时中位数，约一半请求耗时不超过此值 |
| p95_s | 单次响应耗时第 95 百分位数，约 95% 请求不超过此值，用于观察慢请求 |
| max_s | 已观测响应中最慢一次的耗时 |

阶段字段按“阶段名 + 指标名”命名：例如 `html_generate_total_tokens` 为页面生成总 Token，`html_generate_p95_s` 为该阶段的单次响应耗时 P95；阶段 `sum_s` 不是阶段墙钟时间。P50/P95 使用线性插值。

`summary.json` 的 `case_wall_stats` 则统计**单 case 实际耗时**：其中 mean_s、p50_s、p95_s、max_s 分别为 case 实际耗时的均值、百分位数、最大值，sum_s 为所有 case 实际耗时之和；不要与请求级同名字段混用。

**各 case 实际耗时之和、模型请求耗时之和、整批实际耗时是三个不同指标。** Token 记录不完整时，batch_summary 中有效的 case 实际耗时仍可单独使用。
