## 一、生成侧问题

### 1. 弱模型失败形态多样（render_suspect / done_no_html）
自家训练模型（尤其 flashv1_1-step2k）失败率高：flashv1_1 **12/47 失败**，flash4k 4/47，step3kdpo 系各 2/47；Opus 系几乎不失败。失败时 `error` 都是 null（不是崩溃，是轨迹自然结束但没产物 / 产物渲染不了）。已识别的失败模式：
- **文本形式 tool call**：模型吐 `<tool_calls><invoke name=...>` 纯文本而非结构化工具调用，agent 框架不识别 → 说完就停、没产物（典型：flashv1_1 seq_1408，17秒/3条消息）。**根因是弱模型工具调用能力差**，是评测结论本身，不是流程 bug。
- **大数据表话痨**：超大 xlsx 附件 + 多页，模型陷入逐条自然语言演算、产不出结构化结果（seq_1495 考勤表，1507秒/405条消息）。
- **干活多但渲染不出**：几十条消息但最终 no_html/render_suspect，需逐个看停在哪。

> 详细失败根因分析是**待办**（见下），本轮只识别了模式。

### 2. 转换脚本漏洞：空壳 html 进打分
`build_benchmark_eval.py` 的 `scan_pages` 只判 `page_*.html` 文件存在、**不查是否为空**。模型产 1 字节空壳 html 会被当正常页收进打分 → 给污染性低分（如 step2k seq_0206 overall 0.17）。**待修**：过滤 <100 字节空壳页；全空则该 case 按失败计、不进打分。

### 3. 已知配置坑（来自 0707 总纲，仍有效）
- max-turns 必须 20（默认 8 不够，重题被截断成 done_no_html）。
- 用独立新 OUT 目录（sandbox 混放会复用旧 deck 报假 done）。
- 端点必须实现「数组 content」，否则 agent 每次调用必崩。

## 二、打分侧问题（本轮重点，已修）

### 内容分静默虚高 bug（核心发现）
判分网关返回空时，`content_evaluator.py` 把「失败」当「0 条动态检查项」继续打分 → 内容分只由易过的通用项决定 → **虚高，且全程不报错**。
- **影响**：老批 6 模型 30~49% case 中招（走旧 Gemini 网关，不稳）；新批 3 模型 0 中招（走 TokenHub Claude）。混排 → 新模型被系统性压低，一度误判「DPO 退化」。
- **判据**：`content_eval_dynamic_items == 0`。
- **已修**：加快速重试 + 失败抛错（不静默降级）；三值 prompt 强制 JSON。已全量重判老批统一口径。
- **DPO 真相**：干净重判后 DPO 与无 DPO 基本持平，之前的「64.6 低于无 DPO」是基线虚高假象。

### 判分网关
旧 Gemini 网关（34.96 / cloudsway）已全禁用，判分改用 **TokenHub Claude sonnet-4-6**。跑判分必带 `WANGBO_CLAUDE_BASE`/`WANGBO_CLAUDE_KEY` 等环境变量（见总纲/交接文档）。

### 各维度可靠性（解读机器分时记住）
| 维度 | 可靠性 |
|---|---|
| page_score / hard_check（渲染/硬检查） | ✅ 高 |
| deck / aesthetic（结构/美观，VLM主观） | 🟡 中，趋势可信、细排名慎信 |
| content（内容） | ⚠️ 修复前局部不可靠，修复+重判后可信 |
| overall 大档位 | ✅ 可信；分差<3 的细排名慎信 |
