## 四、几个坑（下次注意）

### 坑 1：TokenHub 判分网关的 auth key 与老 34.96 网关不同
- `benchmark/config.py` 里 `WANGBO_CLAUDE_KEY` 默认值 `sk-6m1qhS3...` **是老 34.96 网关的 key**，走 TokenHub 时会 401
- TokenHub 需要 `<REDACTED_API_KEY>`（`config.py` L30 `TOKENHUB_API_KEY` 默认值）
- 走 TokenHub 时必须**同时**设 `WANGBO_CLAUDE_BASE=https://tokenhub.sensetime.com` **和** `WANGBO_CLAUDE_KEY=<TokenHub 那把 key>`（否则 401 无限重试死循环）
- `benchmark/scripts/build_checklist_lib.py` 已经把这两个 env 都设好，可以参考

### 坑 2：`GEMINI_MAX_RETRIES=0` = 无限重试
- config.py L81 默认 `GEMINI_MAX_RETRIES=0` 意味着**无限重试**
- 一旦 401 / 404 / connection error，会死循环打网关
- 我做 checklist 库预生成时遇到过：47 并发 + 无限重试把网关限流打爆
- 解决：降并发到 8，或者环境变量 `GEMINI_MAX_RETRIES=3 GEMINI_REQUEST_TIMEOUT=120` 显式覆盖

### 坑 3：`conda run` 会缓冲 stdout
- 我用 `conda run -n ppt-eval python script.py` 时 log 一直空的以为脚本挂了
- 实际是 `conda run` 缓冲了 stdout
- 修复：`conda run --no-capture-output -n ppt-eval python -u script.py`
- **`-u` 参数**（unbuffered）也要加，不然 Python 自己也会 buffer

### 坑 4：sandbox 里有历史模型的 HTML 残留，dashboard 递归扫描会混算
- Dashboard 之前显示 "OTTO 50% 成功"是 bug——它递归扫 sandbox 里所有 `*.html` 当成 OTTO 的产物，实际里面有 2026-07-08 老模型运行的残留
- 目前 dashboard 已经改为按 `batch_summary.json.results[].deck_dir` 过滤，应该修好了
- **验证方法**：看某个明知失败的 OTTO case（如 prod_1eaed984）在 dashboard 上的页数——应该显示 0，不是几百

### 坑 5：run_batch 的 sandbox 不清理，磁盘会满
- 每次跑批都建新的 `output/sandbox/batch_<case>_<hash>/`，不删旧的
- 我这次跑了 5 个批次 × 47 case × 每 case 几百 MB，磁盘吃了 200+ GB
- **建议**：定期清理 `output/sandbox/` 里 30 天前的目录，或者跑批完成后自动清理
