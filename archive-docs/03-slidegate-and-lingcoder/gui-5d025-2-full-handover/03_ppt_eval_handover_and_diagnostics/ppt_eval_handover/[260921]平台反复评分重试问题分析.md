# 平台反复评分重试 Case 根因与占比分析

## 1. 结论

本报告分析当前仓库中的平台监控日志，重点回答两个问题：哪些 case 会让外层监控不断重新发起评分，以及这些 case 为什么长期拿不到最终分数。

结论如下：

1. 反复重试的直接触发条件是：评分主进程正常结束并返回成功状态，但监控对结果做完整性验收时发现“已生成的有效 PPT 中仍有 case 没有评分结果”，或者有效生成数仍低于最低要求，于是把本轮标记为 `final scoring incomplete`，下一轮继续发起评分。这里的“主进程正常结束”只说明评分任务整体没有被 kill、没有因未捕获异常或环境错误而中断，不代表每个 case 都拿到了分数。单个 case 的裁判失败通常会被评分程序捕获、记录并跳过，因此可能出现“主进程成功退出，但部分 case 没有分数”。
2. 当前统计到 939 条 `final scoring incomplete` 记录，来自 20 个任务、32 个任务模式组合。这里的“记录”是监控重试事件，不是不同 case 的数量。
3. 939 条记录中，778 条（82.85%）属于存在缺失评分结果，161 条（17.15%）属于没有缺失评分但有效生成的 case 数量低于最低验收数量 40。这里的 40 指“至少要有 40 个有效生成 case”。前者是“有 case 没有分数”，后者是“有效生成结果数量不足”，两者都会触发外层重试。
4. 在日志中能够定位到具体失败 case 的 41 个“任务模式 + case”组合里，`q1495` 占 34 个（82.93%）。它跨多个模型、模板模式和无模板模式重复出现，因此更像是 case、输入负载和裁判评估链路共同触发的问题，不能简单归因于某一个被测模型。
5. `q1495` 最常见的明确错误是 ContentEvaluator 返回结果缺少必需字段 `statistics`。这表示裁判结果没有通过当前 JSON 结果校验；它不是“被测模型没有生成 PPT”这一类错误。日志中还同时出现 429、400、403、504 和超时，说明部分重试还受到裁判服务限流、请求失败或长请求超时影响。
6. 因此，真正造成长期占用评分资源的链条是：单个 case 评分失败 → 本轮只少一个或少几个分数 → 外层监控认为整批未完成 → 重新进入全局评分锁 → 内层再次对未完成 case 重试 → 仍失败后再次回到第一步。


不过任务 `sensenova-flash-284b-vision-v16-20260908-sft-step400-dpo-v2_tpl` 中，q1495 曾出现过一次 `statistics` 缺失的裁判错误，但后续已经生成有效评分记录。任务最后一次外层重试记录是 `generated=35`、`unique_scores=35`、`missing_generated_scores=0`，触发原因是有效生成 case 数量低于 40。

## 2. 统计范围和口径

本次统计基于以下仓库数据：

- `automation/tasks/*/monitor.log` 中的 `final scoring incomplete` 记录；
- 同一批任务日志中的 `[错误]`、`ContentEvaluator`、429、超时和基础设施错误；
- `data/PPT-Testset-mini-0427/manifest.json` 中的 case 输入文件说明；
- `automation/pipeline.py` 中监控重试和评分启动逻辑。

需要区分三个口径：

- **重试事件**：一条 `final scoring incomplete` 日志，表示外层监控至少准备再次发起一次评分。它可以由同一个 case 连续产生很多次。
- **任务模式**：同一个模型任务的 `notpl` 或 `tpl` 运行，例如 `xxx_notpl` 和 `xxx_tpl` 是两个模式。
- **失败组合**：一个“任务模式 + case”组合，例如 `some_model_tpl + q1495`。只有能从 `[错误]` 日志中定位到 case 时才计入这一项。

所以，下面的 939 是重试次数级别的统计；41 和 34 是去重后的失败组合统计。不能把它们直接理解成 939 个不同的 case。

举例来说，如果一批有 47 个 case，其中 42 个生成了有效 PPT，且只有 2 个 case 没有评分，那么有效生成数量已经超过 40，但这 2 个 case 仍然会导致最终验收不通过。后续评分配置使用 `skip_done: true`，正常情况下会跳过已经有有效分数的 case，主要继续处理这 2 个缺分 case。问题在于当前外层监控没有为这 2 个 case 设置最大失败次数；如果它们每次都因同一个原因失败，整批任务就会一直处于未完成状态，并周期性重新发起评分。

## 3. 外层监控为什么会不断重派

当前 `automation/pipeline.py` 的监控逻辑大致是：

1. 生成阶段结束后，监控启动某个模式的 final scoring；
2. 评分主进程运行结束并返回成功状态后，监控重新统计已生成 case 和已评分 case；单个 case 的失败不一定会使主进程失败；
3. 监控进行结果完整性验收：有效生成数必须达到 40，并且每个有效生成 case 都必须有评分结果；
4. 只要仍有 `missing_case_ids`，或者有效生成数小于 40，就说明“程序运行结束了，但结果验收没有通过”，于是记录 `final scoring incomplete ...; retry`；
5. 下一次监控轮询发现该模式仍未完成，就再次启动评分。

关键代码位置：

- 评分完成后的完整性检查：`automation/pipeline.py:1348-1380`；
- 下一轮重新启动 final scoring：`automation/pipeline.py:1399-1400`；
- 评分进程内部使用最多 4 个 evaluator worker：`automation/pipeline.py:758-778`。

这里的“结果验收没有通过”不是单纯指文件格式错误，而是指评分结果没有达到平台定义的完整性条件，主要包括：某个已生成 case 没有写入有效分数，或者有效生成结果总数少于 40。某个 case 没分数的直接原因可能是裁判返回格式不符合要求，例如缺少 `statistics` 字段，也可能是 429、超时等请求失败。内层重试先结束并返回；真正造成无限或长时间重复的是外层监控没有给 final scoring 设置最大尝试次数，也没有把“这个 case 已经连续失败多少次”作为终止条件。


## 4. 重派无限制存在的问题

一个 case 的内层裁判重试达到上限后，当前评分进程通常会结束该 case，并继续处理其他 case。只要评分进程整体没有崩溃，外层监控随后会看到“整批还有缺失分数”，再次启动评分。

下一次评分使用 `skip_done: true`，通常会跳过已经存在有效分数的 case，重点再次处理缺失 case；但缺失 case 会重新请求裁判。因此，外层重派发不会每次都把 47 个 case 全部重新计费，但会持续消耗失败 case 的裁判请求、内层重试次数、评分进程和全局评分锁等待时间。

如果监控线程长期存活且没有 final scoring 最大尝试次数，那么一个始终不能得到有效 `statistics` 的 case 就可能让任务长期处于未完成状态，并周期性重新竞争全局评分锁。

这会产生两类实际影响：

- **持续消耗 token**：一个缺分 case 在一次评分进程内可能先经过多次裁判快速重试；如果本轮仍失败，外层监控下一轮又会再次请求这个 case。假设每轮都触发 6 次内层重试，外层重复 10 轮，就可能对同一个 case 发起约 60 次裁判请求。即使最终都没有有效分数，这些请求仍可能消耗输入 token、输出 token和接口额度。
- **持续占用评分资源并造成阻塞**：每轮评分都要重新进入全局评分锁，启动评分进程并等待 worker 处理。失败 case 越多、重派轮次越多，评分任务占用锁和评分 worker 的时间越长；其他平台任务和命令行评分只能继续等待全局锁，于是一个或几个异常 case 会把局部失败扩大成全机评分排队。



## 5. 结论和定位优先级

建议按以下顺序排查和修改：

1. **先处理外层监控的无限重派发**：为每个任务模式设置 final scoring 最大尝试次数、单 case 最大失败次数和退避时间；达到上限后写入明确的 `score_incomplete` 或 `score_failed` 终态，不再自动占用全局评分锁。
2. **把缺生成和缺评分分开处理**：`generated < 40` 时应检查生成任务和 HTML 质量，不应继续当作评分缺分重试；`generated >= 40` 但存在缺分时才进入评分补偿。
3. **给每个缺失 case 记录失败原因**：至少保存 case ID、最后错误类型、累计尝试次数、首次失败时间、最后失败时间和下一次重试时间。这样可以直接看出是 schema、429、超时还是基础设施问题。
4. **重点修复 ContentEvaluator 的 schema 处理**：对 `statistics` 缺失、非 JSON、截断 JSON 和服务错误分别记录，不要全部归为“评分失败”；必要时保存裁判原始响应摘要，便于判断是模型输出、上下文过大还是网关返回错误。


结论：历史日志中存在少数case长期拿不到可接受的裁判结果；外层监控把“缺一个分数”或“有效生成数量不足”当成整批继续重试的理由，且没有最终失败上限。
