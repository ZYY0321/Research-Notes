## P0：环境与 Bench 内部必须先统一

2. **实验章节仍是 TODO，主张没有方法学承载。** `chapters/04_experiments.tex:7` 只有 “TODO: Write the experiments.”，但摘要已经给出训练数据、RL、三套 benchmark 分数以及 hybrid 结论。至少需要补：数据/训练设置、评测协议与模型版本、每个分母、主表（GUI-only/Hybrid）、步数统计、工具调用统计、误差/置信区间或多次运行说明、消融与失败案例。否则环境章中的设计无法和结果闭环。

3. **“每道任务以业务写入为终点”与当前候选清单不一致（可通过删题解决，不是环境机制问题）。** 工作 manifest 的 `v6.case_35` 题面是“最近的有评分的咖啡馆在附近2公里内同类评分里排第几”，单 App、纯查询/问答，没有业务写入；而环境章 `03_MobileGym++.tex:82`、`:86` 和 `:91` 把业务写入说成正式任务的必要条件。最终锁表前把这类 QA 移出，或单独标为 query split；在当前草稿中不要用“所有正式任务”预先锁死未定分母。

4. **当前工作 manifest 是 215，但最终分母仍可缩减；正文的 116/84 是设计目标而非已核实统计。** 当前 `official.json` 有 215 条（214 个主任务和 1 个秘书任务），章内 `03_MobileGym++.tex:94` 仍写“约 200，其中约 116 单应用、84 跨应用”。这在候选阶段可以保留为目标，但最终应从 checker 逐题生成唯一的单/跨/信使分层，并在正文、表格、图和实验分母只引用同一个 manifest。

## P1：主张需要收敛或补证据

5. **应用数量的集合关系没有定义。** 正文说 64 个可安装、35 个新构造（`:20`、`:39`），摘要说“覆盖 over 110 applications”；应用覆盖图中心写 110+，图中 mock 与 emulator 的柱子相加看起来是 64+46。需要明确：64 是否全部 mock、46 是否 emulator、是否有重叠、35 是 64 的子集还是另一个集合。建议给出 `mock / emulator / newly built / total unique` 的集合公式，并统一“64、110+、35”四个数字的语义。

6. **工具目录数字和运行统计混用了。** 摘要称 300+ tools across 50 apps；环境章称约 52 apps，但未给 catalog 总数。当前冻结统计是 215 题中 406 次调用、110 种被调用工具、306 种候选工具、199 种从未调用（`bench215-gemini-hybrid-tool-freq.json`）。这些不是“catalog 中 300+ 工具 across 50 apps”的证明。应从发布版 catalog 生成精确的 `apps / declared tools / callable tools` 数字，并把“声明规模”和“本次轨迹实际调用”分成两张表。

7. **Hybrid 效果不能从当前材料写成因果提升。** Gemini 冻结结果是 GUI-only 126/215=58.6%，Hybrid 147/215=68.4%；工具调用统计为 119/215 题至少调用一次。固定同一题同一初态是好设计，但仍是单模型、单次 paired run，且 33 道 GUI 挂/Hybrid 过、12 道反向，存在工具覆盖、验证不一致和搜索循环。正文应写 paired outcome / association，报告 33/12 的 discordant counts 和按任务类型的 breakdown；不要直接说“tools cause improvement”。9 月 9 日会议纪要把 Gemini 概括为“约 60%”，可作为会议摘要，不能替代锁表的 58.6/68.4。

8. **“same rights as GUI / same business functions”需要逐项可验证。** `03_MobileGym++.tex:68-70` 是强机制断言，但现有审查已记录工具不写 store、返回队列与 UI 不同步、直飞字段写入不稳等问题（`bench215-已看55-论文点.md`）。建议附录给出工具→业务函数→store path→checker path 的映射，并把未修复项列为 limitation；不能用“严格子集”“同权”概括所有 300+ 接口。

9. **“固定时间/动态项”是优势，但要把协议写清。** 当前官方 manifest 写的是 `2026-07-12 Sunday`，任务包也说明各 suite 使用 simulated time。正文 `:94-97` 应明确时间基准、时区、reset 顺序和版本锁定；否则“明天/本周五”“排行榜第一”类任务无法复现。对外材料中的“训练数据与测试集相似度正常、无过拟合风险”目前只有会议纪要一句，不能在论文里当已证实结论，除非给出相似度方法与结果。

### §2 App-native tools（约 0.35–0.45 页）

### §3 MobileGym++ Bench（约 1.15–1.30 页）

按“任务合同 → 难度来源 → 组成与质量 → 协议”四小段写：

1. **任务合同：** `instruction + initial_state + checker`，题面只写用户目标；checker 只读终态和允许变化路径。
2. **核心任务形态：** 单 App 长链与跨 App 取值写回。跨 App 的严格定义应改为“目标写入发生在一个 App，且其值依赖另一个 App 的运行时业务状态”；不要求两个 App 都发生写入。仅通知/复述不算。

## 目前章节的逻辑主线（审阅结论）

主线是成立的：**可扩展的 mock 商业世界 → 业务 store 可验证 → 同一世界提供 GUI 与工具两条通道 → Bench 用相同任务合同比较两种走法。** 当前问题主要是段落顺序和主张粒度，而不是研究问题本身。

需要优先改的逻辑点有三个：

- 环境优势应落在“商业对象可重置、可跨 App 关联、可程序化检查”，而不是泛称“更真实”。
- Bench 优势应落在“用户目标终态和跨 App 取值写回可验证”，而不是宣称现有基准都没有跨 App 或工具。
- 工具的角色应保持“可选的第二通道/试验特性”，不能在环境章中暗示所有任务都因工具而设计或必须使用工具。

## 后续写实验章时，你需要提供给我的材料

不需要先补整章文字；只需按下面的最小数据包给我即可：

1. **训练设置表：** 12K SFT、2K+ RL 的来源、App/任务是否与测试集去重、模型版本、训练步数/超参、训练和评测时间。
2. **评测 manifest：** 最终题数、每题 ID、单/跨/信使标签、领域/App 标签、是否 GUI 可解、版本号和排除列表。
3. **结果表：** 每个模型×模式的成功数/分母、每题结果、均值步数定义、步数上限、错误/超时数；若只有一次 run，明确写 single-run。
4. **Hybrid 诊断：** 工具调用题数、调用次数、成功/失败调用、GUI→Hybrid rescue 与反向数量，并标出 verifier/environment issue。
5. **质量证据：** 每个 App 的 reachability/checker 测试汇总；任务 gold GUI path 或人工可解记录；修题后是否重跑及敏感性估计。
6. **三张可复现清单：** App catalog（mock/emulator/new 的集合）、tool catalog（声明工具数与实际可调用数）、checker schema/allowed paths。

有了这六项，实验章可以只写 1.5–2 页主结果，详细题单、工具频率、失败案例和 verifier 例子全部下沉附录，不会反过来挤占环境与 Bench 的三页预算。

## 可直接采用的核心表述（在数字冻结后）

> MobileGym++ is a resettable browser-hosted world of mock commercial applications. GUI actions and selected app-native calls operate on the same application state, while task success is determined from a versioned terminal-state checker. MobileGym++ Bench evaluates the resulting commercial workflows under a common manifest; GUI-only and hybrid runs use the same task, initial state, and checker, with any query-only tasks reported as a separate split.
