In-app tools

Agents can use both graphical actions and function calls in the same environment. MobileGym++ places the two channels on the same application state, so a task can move between them while preserving the same business objects. GUI-only remains a complete setting; Hybrid supplies another route through the same world.

Approximately 52 applications expose a function interface under their own namespace. A call is available when its application is in the foreground and occupies the same action slot as a tap, swipe, or text input; at most one action executes per step. The functions act on the application's business state. They cover selected business operations, while saving, payment confirmation, password entry, and contact selection may still return to the GUI. Prefill calls create drafts, and the final business write is checked in the same store as a GUI write.

A mixed workflow can therefore switch between applications: the agent first obtains task information from one app, completes a GUI operation in another, and returns to the first app for an exposed business operation. GUI-only and Hybrid use the same task, initial state, and terminal check, allowing the two completion paths to be compared directly.

# 三、0904框架讨论

我们这项工作肯定跟 scaling 有关系。从 existing 这些 bench 的缺点起笔——AndroidWorld、MobileWorld，以及 CUA。他们本身那个探索环境太小。过渡到如果我们想探索更多的环境，比如说 APP，那么就会面对各种各样的阻碍。

第一，这些 APP 本身 anti-bot：采数据的时候，APP 直接拒绝在虚拟机里面运行。后面我们是真机采集，但真机采集有很多缺点。第二，如果用真实的这种 APP 来采集，相当于我们在实验的过程中对真实的世界造成影响，这个影响可能是不好的。因此，要去 scalable 地探索这个 mobile 的这些环境，其实离不开制造这样的所谓 mock 或者 pseudo apps。这是第一个阶段的引入：先引入 APP 和环境之间的关系。

第二个，在构建这个环境的过程中，considering existing 这些 CUA 在执行效率、接口形式、以及一些 future 的场景，这些 APP 本身可以 beyond human-like、beyond pure human-like operation，然后比较自然地引出我们在它的基础上拓展出 MCP、CLI。不要把它跟整个工作、或者说整个环境绑定得太深，把它写成一个 extend 出来的东西：纯 GUI 完全 OK；为了面向未来，为了让这个 benchmark 或者说让这个环境能够 long live，我们还额外做了这些事情。它是一个 plus，专门用于面向未来的研究。

第三，假设未来 mobile 上面也获得了 CLI、MCP 的能力，那么它会比纯 GUI 好多少，实验章再回答。

再拓展到下一句：我们要让它能够支持 both academia 和 industry。这条路径上需要开源以后用一些接口，它本身会有一些 transaction，比如说下单、支付，这样的一些可判定的点；针对前面的 APP 做 design。环境内部的 APP 及其扩展，以及它的入选和它的 verifiable，基本上就把最主要的贡献一一 cover 掉。我们要 differentiate from previous two works。批判前人点到为止，不要骂得太狠：verifier 不可靠，纯用 LM judge 会有假阳，在线的网站 offline 以后不可能再用 verifier。点一下，引申到我们要做一个给社区可以用的、对 academia 和 industry 都有用的东西，然后引入刚刚的三点。

这部分结束以后，再引入里面这些 APP 的业务领域：整个环境、software 的部分建设好了以后，再讲我们在选取、制造的时候都考虑到了真实、多样、稳定。再把 AndroidWorld 抽一次：他们可能只 cover 了 system default 的 APP；我们可能有一个 diversity 和 exploration depth 的 leap，这就是支持我们去做完整的业务闭环，以及可扩展性。收一下。有了环境加 APP、APP 内部的 MCP、以及 verifiability 这几个以后，再回过头来扣一下：我们在制造它的时候也考虑到了真实世界的情况，所以里面复现的商业 APP 会有逻辑闭环。然后再往后讲 eval、data、bench，后面基本上就是平铺直叙。

¶1 可控环境中的商业任务缺口

本段核心：真实、多样、稳定，能被程序化验证的商业业务状态

论点

new：gap：探索环境太小，如果模拟机？如果真机？我们需要scale，因此，我们需要mock

1. 移动智能体的评测目前分在两条路上：一条在物理设备上运行真实应用，换来界面与网络的真实，代价是状态难以重置与并行；另一条在可控环境中运行可复现的应用，换来重置与判定，代价是应用大多止于系统工具与开源客户端。
2. 后一条路上的应用选取以可离线、免登录作为入选标准，以开源通讯软件替代商业通讯服务，或只提供函数接口而不提供图形界面；由此可被程序化检查的终态集中于系统级状态，而完成一次下单、记下一笔支出、改一次行程这类商业结果尚缺少可判定的落点。
3. 本章给出的回应是 MobileGYM++：一个运行在浏览器中的移动环境，以真实、多样、稳定为验收目标，复现商业应用的完整业务闭环，覆盖七个业务领域的 64 个可安装应用，以及可整体导出与恢复的初始状态与只读取业务状态的程序化判定。
4. 环境建立在 MobileGym 之上：运行时、状态序列化与重置、应用间跳转与程序化判定沿用前作，本轮扩建的是其中承载的内容与新增的调用通道，即成规模的商业应用与应用内开放工具调用。

论点

1. 前作 MobileGym 提供了一套完整的可控运行时：整机运行在浏览器标签页内，各应用维护自己的结构化状态并据此渲染界面，应用间的跳转、剪贴板与系统广播已经打通，整机状态可导出为一份记录并按该记录恢复，多个实例可同时推进而互不干扰。
2. 本轮工作在同一套运行时上完成两处扩建：把可复现的商业应用铺开到具备领域覆盖的规模，并在这些应用内部开放一组与界面同权的函数调用。
3. 新构造的应用复现的是业务闭环而非界面外观：商品与订单、支出与预算、行程与改签、会话与消息各自作为对象存在于应用自己的业务库中，被界面渲染，也被判定读取。
4. 智能体一侧的接口保持不变：观测为屏幕像素，不含辅助功能树，也不能直接读取业务库；动作沿用离散的点击、滑动、输入与导航，工具调用与之同级，每步至多执行一个动作。

说明

简要写「平台能力」与「观测与动作空间」两节。因为是继承内容。

「复现业务闭环而非界面外观」：如果只说复刻了多少个界面，体现不出来工程量，体现不出我们做了更多可判定的商业终态。

¶3 业务状态上的程序化判定new：< 共识，不用太多笔墨 >

本段要立住的观点：成败只由业务状态的前后差分决定。关键词：终态可自动检验、解法无关。

论点

1. 任务绑定初始状态，结束时对整机状态取一次差分，检查目标业务字段是否被写成要求的样子。
2. 由此，判定既不依赖模型裁判，也不与单一参考轨迹比对：完成同一件事的不同路径在同一套判定下等价。
3. 检查以关系而非常量写出：一条支出记录的金额需与刚刚完成的那次支付一致，一条日程的标题需包含所选车次的编号；常量只出现在初始状态中，不出现在判定里。
4. 任务在目标字段之外声明允许变化的状态路径，其余差分作为意外改动单独记录，与任务成功分开报告。
5. 一道任务被计为跨应用，当且仅当判定在至少两个应用中读到业务写入；查询后转述，或仅向另一个应用发出一条通知，不计入跨应用。

说明

全章准备写重的一段，因为它是别的方法不容易复制的

「不依赖模型裁判」正面写出来，但写在第 2 句而不是全章第一句。参考：AppWorld 写基于状态的程序化评测并指出参考匹配脆弱，AndroidWorld 写奖励来自系统状态因而比匹配表层界面变化更耐久，前作写确定性、细粒度、不依赖视觉语言模型评判。我们要论证的不是「状态判定更好」这件已成共识的事，而是「我们的状态里装的是商业业务字段」。措辞上不沿用 system state，那是操作系统侧，我们读的是应用业务库。

¶4 规模、结构纵深与领域覆盖

本段观点：关键词：交互数量多、交互链路深、设计领域丰富。

论点

1. 有多少应用，每个应用是否厚到足以承载多步任务，这些应用是否覆盖了不同类型的业务。
2. 数量上，环境收录 64 个可安装应用，其中 35 个为本轮新构造的商业客户端。
3. 纵深上，新构造应用导航声明的中位规模为 37 条路由、175 个可交互动作与 88 条跳转，自根页面起算的交互深度中位为 3；作为纵深参照，前作中结构最厚的应用为 100 条路由、265 个动作、深度 7。深度中位为 3 意味着多数任务的最短界面路径需要跨越若干层级，任务的步数下界由页面结构而非指令长度决定。
4. 覆盖上，应用按出行、购物、金融、内容、社交、办公与生活服务七个领域铺开，各领域承载不同类型的业务对象与不同的终态形式，包括下单、记账、建立行程、发送消息与加入收藏，因而无法用同一套判定模板套完。
5. 与同类可控环境的差别最终落在判定能读到什么之上：本环境的判定读取应用自身的业务库，而不是系统侧状态或界面控件树，商业结果因此可以进入评测；比较表按商业应用覆盖、状态是否可完整读写、判定是否读取业务状态、是否支持跨应用、应用内工具是否与界面写入同一份状态五个维度列出，真机路线置于表下单独说明。

§2 应用内工具

¶1 开放工具调用new：《extend，分析分析》

本段要立住的观点：引入应用内工具，是因为现有评测无法在同一个世界里检验智能体何时该点界面、何时该调接口的能力；本环境把工具做成同一份业务状态上的第二条写入通道。

论点

1. 智能体已经普遍具备调用函数接口的能力，但现有评测把这件事切成了两半：图形界面环境几乎只评点击与输入，接口型环境又没有可以点的界面，于是「何时该用界面、何时该调接口、调用之后如何回到界面确认」这一类行为无处被检验。之前讨论过，bonus用于展现我们模型调工具的能力？另一个点是就是前瞻性试验。
2. 本环境因此在应用内部开放工具：约 52 个应用在各自的命名空间下暴露一组函数式接口，智能体可以列出并调用当前前台应用的接口，调用与点击处于同一动作空间，每步至多执行其一。
3. 这些接口作用于应用自己的业务库，与界面操作经由同一组业务函数写入同一份状态，因而是同一个世界中的第二条通道，而不是绕过界面的外部服务。
4. 接口所覆盖的操作是界面可达操作的严格子集：支付确认、密码输入与联系人选择仍只能在界面上完成，预填类调用只生成草稿而不产生业务写入，保存仍需回到界面。
5. 每道正式任务都保留一条仅使用界面即可完成的路径，判定对两类解法完全相同；纯界面解法与界面—工具混合解法因此可以在同一任务、同一初始状态、同一套判定下直接比较。

¶2 一次调用的形态

本段观点：用一件完整的事说明工具写入与界面写入落在同一对象上，且调用不能替界面把事做完。

论点

1. 一次典型的混合解法这样发生：智能体先调用记账应用的接口读回当前可用的预算，再切到购物应用的界面挑选商品并完成支付，最后调用记账应用的接口把这次支出写入指定账本。
2. 支付环节无法由接口完成，因为密码输入只存在于界面上；记账环节则两条路径都成立，界面上的保存与接口调用生成的是同一条记录。
3. 判定在两种情形下检查同一组业务字段，因而不区分这条支出是点出来的还是调出来的。

¶4 领域构成与规模
