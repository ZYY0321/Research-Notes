\subsection{35 high-fidelity commercial applications}

The 35 applications added above were implemented from the corresponding real apps through a human-annotator and coding-agent pipeline: annotators collect screen recordings and long screenshots; the agent reproduces the client; humans check the result against the real device and send revisions back through the same tools. Details are in Appendix~\ref{app:mgpp-build}.

The newly built applications have sufficient richness and interaction depth. On these clients, the median navigation declaration is 37 routes, 175 interactive actions, and 88 transitions; median interaction depth from the root is 3. As a depth reference, the thickest application in MobileGym has 100 routes and 265 actions, and its deepest terminal takes 7 steps to reach. The function channel is described in Section~\ref{sec:mgpp-tools}.

\subsection{Realistic cross-application workflows}

One resettable device hosts several commercial applications, each maintaining its own live business state: orders, expenses, itineraries, contacts. These objects change with on-screen actions and leave a trace in device state. Existing commercial-app settings on physical devices or emulators typically keep that state inside a single app: they do not offer a controllable, resettable cross-app workflow in which clipboard, broadcasts, or inter-app navigation rewrite another application's own business objects.

Clipboard, system broadcasts, and inter-app navigation connect the apps. A workflow can leave the current app, enter a second app, and rewrite that app's own business objects: a payment in shopping can produce a matching expense in bookkeeping; a selected train number in the calendar can enter an itinerary app for a change; an address from contacts can enter a checkout flow. The second app therefore receives a real business write, not only a forwarded message.

A cross-app workflow runs end to end on one device snapshot, so the device can be reset to the same initial snapshot and the identical cross-app write can be executed again under the same conditions.

\subsection{Hybrid GUI and app-native tool use}

GUI-only is already a complete setting: every official task can be finished with taps, swipes, and text input alone. Existing evaluation, however, separates GUI-only worlds from API-only worlds, so one question has no single place in which it can be tested: when should an agent operate the interface, when should it call an app-native tool, and how does it return to the interface to confirm the result. For this reason MobileGym++ exposes app-native tools on the same application state that the GUI acts on. This channel is experimental: Hybrid is an optional second completion path, not a requirement.

We design app-native tools per application, following what that application's business objects actually require; hereafter we call them tools. Approximately 52 applications expose tools while in the foreground, and a tool call occupies the same action slot as a tap, swipe, or text input, with at most one action per step. A tool is scoped to the objects of its own application rather than being a generic export of the GUI: many tools are lookup or search over that application's structured state, used to locate and organize records that would otherwise require deep page-by-page navigation. Writes that commit an irreversible business outcome — saving, payment confirmation, passwords, contact selection — still go through the GUI, and prefill produces a draft only. Both channels write the same app-owned store. Hybrid is therefore compatible with GUI-only rather than a replacement for it: every official task retains a GUI-only path, and the two paths share the same task, the same bound initial state, and the same checker.

\subsection{MobileGym++ Bench}

Existing mobile-agent benchmarks evaluate GUI operation; some extend that setting to cross-application workflows, and others add tool interaction on top of it. MobileGym++ Bench asks a different question: whether an agent can carry out commercial writes to completion inside resettable mock commercial applications. Task length comes from locating, filtering, confirming, paying, and writing back across apps.

\textbf{Task design.} Tasks are organized around executable user goals and checkable terminals. Core tasks close with a business operation such as placing an order, posting an expense, creating an itinerary, sending a message, or modifying an app object. The result of that operation lands in the application's own business state. A single-app task reaches that write only after locating and filling fields across deeper pages. Instructions use user-goal language and do not name widget labels, tool namespaces, or checker fields.

In a cross-application task, the value needed for a write is present in another app's live state rather than written as a fixed constant in the instruction. The agent must identify the source, carry the value across the app boundary, and write it into the correct field; the checker verifies the relation between the resulting business fields.

\textbf{Scale and composition.} The current set contains 215 tasks across seven business domains: 109 mention one app, 74 two, 27 three, and 5 four. Tasks are distributed over multiple applications and business objects, so evaluation is not dominated by a handful of apps.

\textbf{Evaluation protocol.} Each task has three parts: a natural-language user goal, a bound initial state, and a programmatic terminal check. Success is decided by a programmatic checker: it reads the before/after diff of application business state, does not read the trace or screenshots, and does not use a model judge; different routes that accomplish the same write are equivalent. Allowed state paths are declared, and other mutations are recorded separately from success. The primary metric is task success rate. GUI-only and Hybrid are evaluated on the same tasks, initial states, and terminal checks. Mean steps on successful trajectories measure interaction efficiency conditional on completion; because failed trajectories often reach the step cap, we also report the success rate and the fraction reaching the cap to separate efficiency from reliability.
