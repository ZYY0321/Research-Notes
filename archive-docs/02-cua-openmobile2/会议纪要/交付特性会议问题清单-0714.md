### 决策 1 · 我们做的到底是"环境"还是"数据集"

**问题的本质**

现在的仓库是一个能跑的原型,可以让人手工过任务;但"能跑"到"能交付给研究者刷训练数据",隔着一个接口层与一轮覆盖率补齐。不厘清定位,后续所有工作项排不出优先级。

**证据链**

- 同类环境定位差异巨大:AndroidWorld / OSWorld 是"环境 + 任务集",WebArena 是"环境 + benchmark",AndroidControl / AITW 是"纯轨迹数据集"。三种定位对应完全不同的核心产物
- 我们的独家优势——`getState()` 无损结构化状态读出——同时可以支撑三种定位,但每种定位需要补齐的下游不同
- 文献大势(《Beyond Next-Token Prediction: An RLVR PoC for Tool-Use Agents》):**可验证性正在成为环境的标配门槛,不是加分项**。这意味着定位不管选哪个,走查脚本铺开都是硬门槛,不能省

**三条路径与后果**

| 路径 | 核心产物 | 必做集合 | 不必做 | 对标 |
|---|---|---|---|---|
| A · 数据合成环境 | 一套可跑的模拟器 + 无损轨迹录制 | 走查脚本铺开、反向断言、多场景数据 | gym 接口、HTTP、稠密奖励、task schema | AndroidControl / AITW |
| B · 通用评测平台 | 定义好的任务集 + 判定 + 排行榜 | 走查脚本铺开、反向断言、gym 接口、统一 task schema、防泄题 | HTTP、稠密奖励 | AndroidWorld / WebArena / OSWorld |
| C · 开源 RL 训练环境 | 环境可被 verl/OpenRLHF 直接调 | 走查脚本铺开、反向断言、gym 接口、HTTP、种子重现、稠密奖励 | task schema 可延后 | AppWorld + gym API |

**建议**

**优先选 A,预留 B 的兼容路径,C 视外部需求触发**。理由:A 的必做集合 100% 覆盖 B/C 的公共基础;补齐 A 之后,走 B 只需增加 gym 接口与 task schema(合计 6 至 11 人天),走 C 只需增加 HTTP、种子重现、稠密奖励(合计 6 至 9 人天)。倒过来先做 B/C 会强行绑定接口形态,反而失去灵活性。

**如果没时间做完整 A**,需要现场砍范围——但**走查脚本铺开(P0)与反向断言(P1)是三条路径共同的硬门槛,不可砍**。

### 决策 2 · 独家优势 `getState()` 从 2/24 到全覆盖,是否本轮必做

**问题的本质**

`getState()` 是我们相对所有同类环境的结构性护城河——AndroidWorld 要从 adb + SQLite 抠状态,OSWorld 要跑代码读文件,WebArena 退化到字符串匹配。**我们一个函数就拿到全量结构化 state**。但这个优势目前只落地了 2/24(Kapi、Taobao 有深度走查),19 个应用完全没有断言。

这是本次汇报中**最大的"已有优势未兑现"**。

**证据链**

- 同类环境对判定层的定位:AndroidWorld 的 `is_successful()` 是纯函数、state-based、durable reward;OSWorld 的 evaluator 拆成 getter + func + expected 三段解耦;AppWorld 更进一步做 collateral-damage 反向断言。**判定层是环境交付的核心产物,不是附属品**
- 卡皮 gate4 复现实验(`docs/kapi-replication/ai-gate4-reproduction-report-0710.md`)证明:一份深度到位的 walkthrough 一次跑 20 至 30 条断言,63% 的走查 finding 可以直接命中,零假阳性
- 判定层同时卡住三条下游:RL reward、评测台、数据质量。**不铺开走查,后续三条路都走不通**
- 反向证据:GUI-G1 论文实测 agent 会输出巨大 bounding box 蹭中目标——**任何单向 include 断言都会被作弊过关**,必须补 include+exclude 双向约束

**改动路径**

- 铺开范围:5 至 8 个核心应用做深度覆盖,每应用 30 至 50 条断言
- 与反向断言同步做,不然事后回补每条 walkthrough 都要重写
- 与静态死按钮扫描配合(卡皮 3 条 finding 一发命中)

**成本对照**

| 项目 | 工作量 | 说明 |
|---|---|---|
| 深度铺开 5 至 8 应用 | 20 至 30 人天 | 每应用 3 至 5 人天 |
| 规范化模板 | 5 人天 | 一次性投入 |
| 反向断言规范 | 1 人天 | 与铺开同步 |
| 死按钮 lint | 1 至 2 人天 | AI 自查,不通知同学 |
| **合计** | **27 至 38 人天** | |

**建议**

**本次会议必须给出明确答复:是否投入这 27 至 38 人天。**

- 若投入:锁定铺开的 5 至 8 个应用名单,交给主线一人集中做
- 若不投入:需要明确对外承认"平台层完备,判定层未兑现",接受在同类环境比较中被判定层拉低评分

**如果答复不明,后续所有工作项排不上优先级**——因为其他 P1 特性(跨应用、多语言、多场景)的价值都依赖判定层可用。

### 决策 3 · 24 个新增应用中跨应用调用为 0,是承认现状还是先补齐

**问题的本质**

**这是本次汇报最尴尬的一个数字**。

- 平台系统层的 intent 机制、chooser、`startActivityForResult` 全部完备
- 但 24 个新增复刻应用中,已接入跨应用调用的实例数为 0
- 平台既有的 2 例真跑通实例(12306 唤起支付宝、Bilibili 唤起微信支付)都属于早期基础应用,不在本轮新增范围内

**证据链**

- AppWorld 定位为独门武器的"跨应用编排 + 副作用检查":9 应用共 457 API 天然编排出复杂任务。**跨应用是构建复杂任务的基础,不是可选项**
- 我们的独家能力(读多应用 state)只有在真实跨应用任务上才能兑现——单应用任务判定,同类环境都能做
- 反向断言(#33)的价值 100% 依赖跨应用场景:"用微信付淘宝订单"这类任务,exclude 断言必须扩到跨应用范围

**两条路径**

| 路径 | 动作 | 时间 | 后果 |
|---|---|---|---|
| 承认现状 | 汇报口径明确"平台层完备,应用层未落地" | 0 人天 | 短期诚实,但对外交付时跨应用无法作为卖点 |
| 先补齐再对外 | 补 3 至 5 条典型路径,在 5 至 8 个新应用落地 | 5 至 10 人天 | 有真实跨应用样本可展示,反向断言的价值可兑现 |

**建议**

**先补齐后再对外**。理由:

- 跨应用是同类环境比较中的高价值维度,承认为 0 相当于自愿放弃这一优势
- 5 至 10 人天成本可控,与决策 2 的走查铺开可以打包做(补跨应用时同步写走查)
- 配套加"每个新应用至少接入 1 条跨应用调用"的构建流程检查,防止今后新应用再次归零

### 决策 4 · MCP 封装是主动做,还是等外部需求触发

**问题的本质**

MCP 与 RL 训练对接是**两条完全不同的对外接入路径**,不要混淆优先级。选错会浪费 6 至 10 人天,选对可以显著降低外部接入摩擦。

**证据链**

- 1:1 先例存在:mobile-mcp 已把 iOS/Android 模拟器包成 MCP server,暴露 launch/tap/swipe/type/screenshot/get_state 六工具。**技术可行性无风险**
- 我们的独家优势(结构化 state 读出)恰好是 MCP get_state 的最佳形态——Playwright MCP 用 accessibility snapshot,我们用 `getState()` 是无损上位替代
- PoC 工作量:骨架 1 天 + 6 工具 2 至 4 天 + get_state 结构化 2 至 3 天 + 隔离 1 至 2 天 = 6 至 10 人天

**两种用法完全不同**

- **用法一(对内)**:整个环境包成 MCP server,让外部通用 agent(Claude Desktop 等)通过标准协议驱动我们环境。**这是"最低摩擦的对外交付方式"**
- **用法二(对内容)**:被复刻的应用内部提供 MCP 工具,制造 GUI+CLI 混合任务。研究前沿方向,但工作量 L 级,建议不在本次讨论范围

**判断标准**

MCP 值不值得做,答案完全取决于一个问题:**是否有明确的外部接入方**。

| 场景 | 判断 |
|---|---|
| 已有外部研究团队询问接入 | 立刻上马用法一,6 至 10 人天 |
| 有对外演示/评测台需求 | 立刻上马用法一 |
| 只是自家 pipeline 内部刷数据 | 不做,直接 Python 函数调用更省 |
| 与 RL 训练对接混淆 | RL 对接走 HTTP + gym 语义,不走 MCP,别绑一起 |

**建议**

**本次会议直接确认:是否已有明确外部接入询问**。若无,不做;若有,单独拉一条 sprint 做,不与决策 2/3 竞争资源。

### 决策 5 · 构建流程是否补足自动检查(gate),让所有 P1 落地

**问题的本质**

这是**元问题**——决定前面四条决策的落地质量。

**关键观察数据**

| 规范类型 | 落地方式 | 遵守率 |
|---|---|---|
| 禁 `Date.now()` / `new Date()` | ESLint 自动卡住 | **24 / 24 = 100%** |
| 时间冻结走 TimeService | ESLint 自动卡住 | **24 / 24 = 100%** |
| 多语言(页面禁硬编码中文) | 只在 AGENTS.md 里写 | **16 / 24 = 67%** |
| 跨应用调用 | 只在 handbook 里写 | **2 / 24(且 2 例都是老应用)= 0%** 覆盖新应用 |
| runtime_walkthrough | 只在 pipeline-v3 里写 | **5 / 24 = 21%,深度 2 / 24 = 8%** |
| 三选一原则(能点必响应) | 只在 handbook 里写 | 卡皮 gate4 走查发现 3 条违反 |

**结论**:**能不能自动检查,直接决定规范的执行率**。ESLint 卡住的一律 100% 遵守,只写文档的执行率停在 8% 至 67%。

**证据链**

- 决策 2 中提到的"判定层未兑现"根源在此——走查脚本从来没进入构建流程的强制检查项
- 决策 3 中提到的"跨应用为 0"根源也在此——handbook 有规范,pipeline-v3 没门槛
- 79 反馈里 8 位造应用同学明确表达过:文档写了但容易忽略,只有构建报错才会立刻改

**改动路径与影响面**

需要加入自动检查的四条 gate:

- "页面禁硬编码中文" · ESLint 规则 · 1 人天
- "每个新应用至少接入 1 条跨应用调用" · pipeline-v3 检查 · 1 人天
- "新应用上线前必须提交 runtime_walkthrough" · pipeline-v3 检查 · 1 人天
- "新代码禁用 `Math.random`" · ESLint 规则 · 0.5 人天

**关键约束:所有 gate 只约束新代码,不追溯老代码**。老应用的历史积累项由主线一人集中补齐,不打扰 8 位同学。

**两条路径后果**

| 路径 | 后果 |
|---|---|
| 补足 gate | 新应用特性交付率从 60% 至 70% 提升至 90% 以上,决策 1 至 3 的 P1 才能真正落地 |
| 不补 gate | 继续依赖手工提醒,每个新应用都要重新踩一遍相同的坑,交付率维持现状 |

**建议**

**必补**。不然前面所有决策都会在半年后再次出现在同样的会议上——因为老应用问题只会被替代成新应用的相同问题。

## 五、当前主要阻碍

1. **规范落地依赖构建流程门槛而非文档提醒** —— ESLint 卡住的规范 100% 遵守,仅写文档的规范 60% 至 70%。除非补足自动检查,否则永远重复"文档写了 → 执行率低 → 事后返工"循环
2. **协作成本约束下可行动作有限** —— 通知 8 位同学的成本高,只能优先选"仅约束新代码"或"AI 自查"路径,历史积累项(T-04、T-12)只能由主线一人集中处理
3. **人工走查自动化上限为 63%** —— 36% 属于视觉审美与产品语义类判断,机器无法替代。走查流程时长下限已定,人力不可省
