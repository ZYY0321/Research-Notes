# MobileGym 全量环境交付与 GUI + Tools 设计

> 2026-08-19。这份是面向不熟悉内部流程的听众的汇报骨架，不使用“Sonnet 审查”、“代码核销”等内部术语定义环境价值。

## 1. 这次交付的是什么

我们建设了一套面向移动 Agent 训练与评测的轻量级仿真环境：它包含可真实交互的 App、可重置的业务数据、系统级能力、高层用户任务、结构化状态观测，以及 GUI-only / GUI+Tools 两种执行方式。

| 交付项 | 数量/状态 |
|---|---:|
| 新复刻 App | 31 |
| 业务类型 | 内容社区、效率、电商、本地生活、出行、求职、通信、云盘等 |
| 当前保留任务 | 218 |
| App 业务 Tool | 137 |
| 系统能力 | 支付、分享、相册、剪贴板、动态时间、App 跳转与返回 |
| 任务级重置 | 已有环境和 App 状态重置基础 |
| 结构化状态 | `__SIM__.getState()` 可读 OS 和 App 业务状态 |

## 2. 环境本身的六个关键特性

### 2.1 Realistic：真实业务流，不只是页面外观

- App 从真实截图和操作路径中提取页面、入口、选项和数据结构。
- 用户操作会改变持久化业务状态：订单、草稿、评价、关注、收藏、日期、权限和消息等不是 toast 或局部动画。
- 支持支付、分享、相册等移动系统交互，并要求从系统页返回后保留原 App 上下文。
- 默认数据保留业务分布、规格、价格、日期和状态差异，而不是重复的占位条目。

### 2.2 Diverse：多应用、多业务、多状态和多难度来源

- 31 个 App 横跨多种业务领域，不会只学到单一电商或社交模板。
- 任务覆盖查询、比较、编辑、发布、支付、退款、日程、协作、权限与系统交互。
- 难度不只来自步数，还可来自信息分散、多条件约束、冷门入口、返回链、状态依赖和跨 App 协作。
- 需诚实说明：当前每个 App 主要还是单套默认数据；“同 App 多种 seed/空态/极端数据”是下一步的多样性增强，不在本次冒充已完成。

### 2.3 Reproducible：同任务可重置、可重放

- 每条任务可在执行前重置 App 持久化状态、文件系统和 OS 状态。
- 模拟时间在 App 数据初始化前注入，“今天、明天、下周一”可在固定时钟下重现。
- 轨迹保留截图、动作、Tool 输入输出、路由和执行结果，可回放失败点。
- 需诚实说明：全局确定性 RNG 与所有时间/随机调用的强制 lint 仍是完整论文复现的加强项。

### 2.4 Scalable：轻量并行的 Web 移动模拟器

- 相比每个 rollout 启动完整 Android VM，Web 环境可通过 browser context/tab 级命名空间隔离并行执行。
- App、OS 能力、任务和 Tool 都按注册机制扩展，新 App 不需要重写整套运行器。
- 已有批量任务运行、双模式轨迹采集和本地产物管理。

### 2.5 Verifiable：可直接读取业务真相

- `__SIM__.getState()` 能直接读取 OS 和 App store，不需要从截图 OCR 或 DOM 文案反推订单、收藏、评价等业务结果。
- 理想的 verifier 是 `check(before, after, params)` 纯函数：既验该改的字段，也验其他对象没有被误改。
- 这是环境最重要的结构性优势之一，可同时支撑 benchmark judge、RL reward 和自动质检。
- 需诚实说明：结构化状态基础已有，但 218 条任务的完整语义 verifier 尚未全部完成，因此当前实验不宣称最终成功率。

### 2.6 Hybrid-capable：GUI 与 App Tool 共享业务世界

- Tool 不是环境外的第二套伪数据；它与 GUI 调用同一业务层和 store。
- Tool 可以查找对象、返回稳定 ID、导航或准备草稿；GUI 继续设置复杂选项、确认敏感操作并收尾。
- Runtime 只暴露当前前台 App 的 Tool，避免所有 App Tool 一次性挤占上下文。
- GUI-only 与 Hybrid 共用任务、默认数据和状态判定基础，便于研究 Tool 在什么地方帮助或误导 Agent。

## 3. 任务设计：单独一节，不与环境特性混在一起

任务题面应是用户目标，不是测试脚本。难度不能只用“多点几下”构造，而要沿下列轴组合：

1. **链路长度**：一个真实目标跨越多个页面和状态阶段。
2. **信息分散度**：条件分布在搜索结果、详情、订单、消息或设置中，Agent 需要维持跨页记忆。
3. **决策密度**：同时满足价格、日期、规格、状态、距离等多个约束，但仍保证唯一或可判定的答案。
4. **入口稀有度**：覆盖长按、二级设置、消息跳转、物流详情、草稿箱等冷门路径。
5. **状态依赖**：前一操作的结果会改变后续可见入口和可选对象。
6. **跨 App/系统协作**：支付、分享、相册、文件、联系人等跳转后需返回原业务链。
7. **状态闭环**：不只到达页面，还要让创建、编辑、支付或删除的结果可在其他视图回读。

当前 218 条任务是该方向的第一轮产物；它们已经比一步查询更长、覆盖更广，但跨 App 比例和全量 verifier 仍需在下一阶段定量补齐。

## 4. Tool 设计：单独一节

Tool 的研究问题不是“有 Tool 一定更好”，而是：**App 愿意开放哪些能力、开放到什么粒度，Agent 如何在 Tool 与 GUI 之间协作和恢复。**

- **选择性开放**：不应默认每个 App 有完整 API，也不应强制每条 Hybrid 轨迹调 Tool。
- **粒度介于点击和整任务之间**：查询、筛选、获得 ID、准备多字段草稿通常有价值；一键包办完整用户目标会把规划问题消掉。
- **敏感收尾保留 GUI**：支付、发布、删除、选规格等环节可要求用户可见确认。
- **Tool 输出要能接续 GUI**：需返回稳定实体 ID、已写字段和可导航目标，而不只是一段文本摘要。
- **动态暴露**：前台 App 决定当前 Tool 集，可将 Tool 选择干扰和上下文占用作为独立设计变量。

6. 建立了逐任务检查台，供内部查看题面、轨迹、错误、Tool 与人工备注；它当前是 QA 工具，不作为对外核心卖点。

## 6. Opus 5 从轨迹中归纳出的研究观察

我们先从 224 条轨迹审查中排除 0-step infra、单纯 wrong-app、没有任务进展等噪声，再将信息分最高的 24 条交给 `claude-opus-5` 做跨 App 归纳。完整请求、原始回复、解析 JSON 和 usage 全部保存，不只保留我们的转述。

### 观察 1：结构化 Tool 的“空结果”会被赋予过高权威

Mail 案例中，GUI 能看到目标邮件，Tool 搜索却没有返回它；Agent 最终相信 Tool 并宣称邮件不存在。这表明查询 Tool 需要返回索引范围、截断标记和空集语义；“Tool 没查到”不应默认等于“世界中不存在”。

### 观察 2：动态 Tool 暴露不能代替目标 App grounding

现有 Runtime 会按前台 App 动态暴露 Tool，但如果 Agent 一开始打开了错 App，“错 App 的 Tool 可正常调用”反而会加强错误确信。因此需要将题面 App、`current_app` 和 wrong-app 恢复信号明确对齐。

### 观察 3：“Tool 准备草稿→GUI 提交”是高价值模式，但最后一步最容易断证

Daysmatter 中 Tool 一次准备 notebook/repeat/reminder/pinned，轨迹从 14 步缩短到 7 步；但 Tool 返回 `persisted=false`，最终持久化仍依赖 GUI 保存。设计上应保留 GUI 确认，同时增加保存回执/实体快照，并让 verifier 区分 `prepared` 与 `persisted`。

### 观察 4：Tool 使用率不是越高越好

一些任务的目标是设置、通知、权限或敏感写入，现有 Tool 只覆盖内容或订单查询；Agent 选择纯 GUI 是合理边界，不是必然失误。因此要先判断 Tool 与任务目标的 relevance，再分析 Agent 是否漏用 Tool。

### 观察 5：零 Tool call 的双模式差异是 GUI 方差，不是 Tool 效应

无 Tool 任务中，既出现 Hybrid 17 步完成而 GUI-only 在 picker 循环至 45 步，也出现方向相反的 Hybrid 滚动失败/GUI-only 7 步完成。这些差异不能写成 Tool 收益。Tool-effect 必须限定在“Tool 真正作用于关键路径”的 episode，并且需要多次采样报告区间。

> 边界：以上为轨迹证据，不是成功率结论。完整 Opus 输出及我们对每条的“采纳/修正后采纳”记录见 `13-Opus5轨迹洞察-原文与采纳.md`。

## 7. 会议演示顺序

1. 打开一个具有订单/编辑/返回链的 App，展示操作不只是页面跳转，而是真实改变 store。
2. 展示 `getState()` 中对应业务字段的 before/after，解释 state-based verifier 为什么是环境优势。
3. 演示一条 Tool 准备数据、GUI 确认收尾的 Hybrid 链路。
4. 打开两个 App 功能电路图样例，用图展示 screen/action/data/Tool/OS 的关系；明确它是后续环境可解释性方向，不宣称已全量完成。
5. 最后用 2–3 个轨迹案例讲 Tool 粒度、Tool/GUI 一致性和 verifier 闭环的设计启示。

## 8. 当前边界（被追问时说）

- 218 条任务的完整语义 verifier 未全覆盖，所以不报无根据的最终成功率。
- 当前数据多样性主要是多 App、多业务和单 seed 内的丰富状态，还不是同 App 多 seed 参数化。
- 功能电路图目前只有样例和实验性数据，尚未生成 31 App 全量可交互图。
- 重跑结果需区分 Agent 自报 COMPLETE、运行器 clean 和最终语义成功。
