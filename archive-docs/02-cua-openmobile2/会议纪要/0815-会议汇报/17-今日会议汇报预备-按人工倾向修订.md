# 今日会议汇报预备（按人工倾向修订）

> 这不是实验结论终稿，而是从环境交付、Opus 5 分析、Sonnet 4.6 反驳和人工判断中筛出的会议可讲内容。

## 一、先修正口径

### 可以直接讲

1. 环境定位与现有工作的关系，但一句话定位还需要继续打磨。
2. 环境的已交付能力：31 个新复刻 App、218 条保留任务、137 个 App Tool，覆盖多领域、持久业务状态、系统能力、动态时间、重置与轨迹留存。
3. 终态语义验证是环境最值得重点展示的特性：检查应该变的字段，也检查不应该变的字段，不依赖 Agent 自报 COMPLETE，也不绑定唯一点击路径。
4. 轻量化与可扩展性可以讲，但应展示重置、并发 rollout 和实际运行规模，不宣称尚未测量的加速比。
5. Tool 和 GUI 的分工设计可作为独立一节：Tool 适合结构化检索、稳定 ID 和草稿准备，GUI 适合浏览、敏感操作与用户可见确认。这是设计选择，不是已被实验证明的最优分工。

### 需要降级或暂时不讲

1. “GUI 和 Tool 共享状态”不是单独的论文贡献。它是系统实现正确的前提，应放在 System Design 中。
2. “开放度是可配置实验变量”不能按已完成贡献来讲。当前交付的是固定 Tool 配置；只有实际生成多个开放档位并运行对照，它才成为实验变量。
3. “有意留出没有 Tool 的能力”是项目假设和环境设计，不是研究发现。
4. Opus 的观察 1–3 主要解释了为什么做实验、如何修实验，不应包装成现在已得到的论文结论。
5. Opus 的五个 RQ 多数过于技术细节，今天不宜作为主线。可作为会后实验设计备选。

## 二、更稳妥的环境定位候选

MobileGym 是一套面向移动 Agent 的轻量、多应用、可重置环境：它保留真实移动业务中的长链路、跨 App 协作和系统能力，同时提供 GUI 与 App Tool 两种交互通道和可直接检查的业务终态，用于构建可复现、可验证的移动 Agent 任务与对照实验。

这句话先突出环境交付能力，不宣称尚未完成的“开放度因果实验”。

## 三、与现有环境比较时要突出什么

- 对 AndroidWorld：突出 Web 移动世界的轻量重置、并发 rollout 以及可直接读取结构化业务终态；不否认真实 Android 的系统真实性优势。
- 对 AppWorld：突出不只是 API 世界，而是保留 GUI 导航、可见确认、支付/分享/相册等系统交互，并允许 Tool 与 GUI 组合。
- 对 GUI-only Computer Use benchmark：突出 App 级结构化 Tool 与终态业务字段验证，而不是“它们没有共享世界”。
- 对 Tool-only benchmark：突出 Tool 之后仍需 GUI 浏览、确认或系统交互，可以研究通道分工和 handoff。

## 四、终态语义验证为什么值得重点讲

1. 任务验收针对“业务结果”，不强制 Agent 走唯一路径。
2. 可以对 before/after state 做字段级 diff。
3. 除了目标字段，还能检查 collateral damage，例如不应被取消的收藏、不应被清空的购物车。
4. 可以量化 Agent 自报 COMPLETE 与真实终态之间的 overclaim gap。
5. 当前应如实表述：验证机制和部分检查基础已存在，218 条的完整语义 verifier 尚未全部补齐。

## 五、新 Hybrid 实验的阶段性观察

当前运行目录为 `0815-delivery-218-hybrid-gemini31-r1`。截止本文更新：

- 已产生 174/218 条结果；125 COMPLETE、39 ABORT、10 MAX_STEPS。
- 只有 20/174 条任务调用过 App Tool，共 44 次调用。
- Tool 调用时序呈现两类：Broadcast、Daysmatter、Dianping 部分任务在第 2–4 步使用 Tool；Cainiao 002、Daysmatter 003、Slack 006 等在第 22/41/28 步才调用，已无法改变前半段关键路径。
- 因此“Hybrid 优势不明显”尚不是 Tool 无效的结论。当前首先表明：有效 Tool 暴露/调用的样本太少，且很多调用发生过晚。
- 本轮尚未形成同一修复后环境的完整 GUI-only 对照，也没有 218 条完整 verifier，不应比较成功率或宣称因果优势。

### 为什么新 App 上优势可能不明显

1. 许多任务已给出唯一对象和清晰入口，GUI 本身已能直达，结构化查询 Tool 缺少改写路径的空间。
2. Tool 是否出现、Agent 是否认识其用途、返回字段是否正好满足任务，都可能在 invoked 之前卡住。
3. 一些 Tool 只做导航或准备，任务的长表单、确认、返回链仍由 GUI 完成，因此总步数差异不会大。
4. 当前 COMPLETE 是 Agent 停止声明，不是已验证结果；步数更少也可能只是提前宣称完成。
5. 现有任务虽然更真实，但不一定集中在 Tool 理论上最有优势的信息分散、批量比较、稳定 ID 定位等场景。

## 六、今天建议的汇报主线

1. **交付了什么**：App、任务、Tool、领域、系统能力和可重置运行基础。
2. **为什么不只复刻页面**：任务需要跨页面、持久状态、返回链、系统能力和真实业务数据。
3. **如何保证可验证**：展示 state diff 和 collateral-damage 检查，并说明完整 verifier 仍是下一阶段重点。
4. **Tool 设计是什么**：展示一个结构化检索/草稿准备后交给 GUI 确认的案例，不宣称总体收益。
5. **目前得到的方法论启示**：不能只问 Tool “有没有”，应分成 available、invoked、useful、changed critical path；这是后续实验的分析框架，不是已定稿的研究结论。

## 七、不建议今天直接抛出的 RQ

- “开放度如何影响成功率”：当前没有实际多档开放度实验。
- “Tool 可见性时序是否影响调用”：可以作为内部诊断假设，但对外过于细节。
- “题面是否显式指名 App”：是实验控制和任务设计问题，不应成为主 RQ。

如果会上需要一个更高层的后续问题，可说：

> 在真实移动任务中，什么样的 App 能力适合以结构化 Tool 开放，什么样的操作仍应保留在 GUI，以及如何用终态语义验证公平比较两种通道？

这是方向性问题，不声称当前已有完整答案。
