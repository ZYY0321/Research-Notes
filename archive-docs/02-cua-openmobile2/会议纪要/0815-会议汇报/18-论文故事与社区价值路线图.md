# 论文故事与社区价值路线图

> 本文档讨论的是论文主张，不是环境验收报告。它综合了现有工程、0727 会议记录、近期相关工作以及一次 Sonnet 评审；其中 Sonnet 的事实错误已人工校正。
>
> **状态更新（2026-08-23）：** 本文推荐的 provider-side capability exposure 主线已被研究负责人否决，不再作为当前论文主线。训练社区导向的二轮 Sonnet 咨询和人工核验见 `../0823论文写作-Sonnet咨询/`；本文仅保留为方向演化记录。

## 一、先给结论

你现在的问题不是“工作量不够”，而是已有资产还没有被压缩成一个可证伪、可实验、能与相关工作拉开距离的科学问题。

“真实、多样、稳定”必须保留，但它们主要回答环境是否可信、是否值得使用，单独不足以构成论文的新颖性。更有机会成为论文主线的是：

> **当移动 App 逐步向 Agent 开放结构化能力时，App 提供方应该开放哪些能力、开放到什么粒度，以及这些选择如何随任务类型和业务状态而变化？**

这和“Agent 能不能调用 Tool”不同。已有工作多数从 Agent 侧研究给定 Tool 后如何选择 GUI 或 Tool；我们的环境更适合从 App/平台侧把 Tool 暴露方式当作实验变量，在相同 App、相同任务、相同初始状态和相同 Verifier 下做反事实对照。

建议使用一个对外容易理解的术语：

- 中文：**交互通道适配性**，或论文中更学术地写作“模态可供性”。
- 英文：**interaction-modality affordance**。
- 含义：一项子任务在视觉判断、结构化检索、状态修改、用户确认等方面，天然更适合 GUI、Tool，还是二者协作。

最值得验证的假设不是“Tool 越多越好”，而是：

1. Tool 的价值取决于任务 affordance 和当前业务状态；
2. 不完整或语义错配的 Tool 可能比没有 Tool 更有害；
3. 对于视觉判断和敏感确认，GUI 不是 Tool 缺失时的临时兜底，而是任务语义的一部分；
4. 最有效的 Hybrid 往往是 Tool 定位/检索/准备，GUI 审阅/微调/确认，而不是用一条 Tool 封装整个任务。

## 二、现有资产到底是什么

目前已经形成的不是一批静态页面，而是一套逐渐闭环的移动 Agent 世界：

- 31 个新复刻 App，覆盖电商、出行、内容、办公、健康、效率等类别；
- 218 条新探索任务；整合分支另有 76+79 条已有语义 Verifier 的主任务；
- GUI-only 与 Hybrid 可在同一环境中切换；
- App Tool 与 GUI 读写统一业务 Store，而不是维护两套互不相干的数据；
- 支持固定模拟时间、任务前重置、支付/分享/相册等系统能力；
- 已形成“环境、任务、Tool、Verifier”四资产联合验收，以及 Agent 错误、环境错误、题面错误、Verifier 错误的归因流程；
- 任务框架已经有参数槽位、criteria、expected changes、状态访问器和正负例检查的基础。

这些资产的研究意义不在数量本身，而在于它们允许做真实 App 上很难做的可控干预：

```text
同一 App + 同一任务语义 + 同一初始状态 + 同一 Verifier
                         │
             改变 Tool 暴露方式或数据分布
                         │
           比较 GUI / Tool / Hybrid 的因果差异
```

要特别诚实地区分当前交付状态：218 条新任务目前还没有完整语义 Verifier，因此它们是任务候选与功能覆盖资产，不能直接当作可靠的 RL reward 或论文成功率。论文主实验应先选择一批 Verifier 完整的代表任务，而不是等待 218 条全部完美才开始。

## 三、为什么“真实、多样、稳定”不够，但仍然重要

### 3.1 它们是可信度主张，不是核心科学发现

- **真实**：真实用户目标、真实业务状态、返回链、跨页面和系统能力，而不是只复刻视觉样式。
- **多样**：App 领域、任务链路、数据密度、查询/写入/视觉/敏感操作等维度的多样，而不是只报 App 数量。
- **稳定**：可重置、固定时间、确定数据、统一 Store 和终态验证，保证错误可以复现。

它们非常适合放在 Environment/System 章节，并用于回答“为什么社区能信、能复现、能训练”。但审稿人还会追问：借助这套环境，我们发现了什么以前难以发现的规律？

### 3.2 更好的四个环境关键词

建议对外将环境特性概括为：

1. **业务真实**：包含持久状态、长链路、跨 App 与系统交互；
2. **可控可重置**：初始状态、时间和能力暴露均可配置；
3. **终态可验证**：直接检查业务结果和 collateral damage，不依赖 Agent 自报完成；
4. **双通道可干预**：GUI 与 App Tool 作用于同一世界，可形成严格对照。

“多样”作为规模和覆盖维度展开；“稳定”落到可重置和可验证，而不是作为抽象形容词。

## 四、相关工作已经做到了哪里

| 方向 | 代表工作 | 已有能力 | 对我们的约束 |
|---|---|---|---|
| 动态移动任务 | [AndroidWorld](https://arxiv.org/abs/2405.14573) | 116 个程序化任务、动态参数、初始化/成功检查/清理；任务变体会显著影响结果 | “多初始化、参数化任务”本身不是新颖性 |
| 长链路、跨 App、MCP | [MobileWorld](https://arxiv.org/abs/2512.19432) | 201 任务、20 App、62.2% 跨 App、MCP 增强、后端数据库验证 | “移动端 + MCP + DB 验证”本身不够 |
| 移动 GUI 与快捷方式 | [MAS-Bench](https://arxiv.org/abs/2509.06477) | 139 任务、11 App、88 个 API/deeplink/RPA shortcut | “Hybrid 能加速 GUI”已经拥挤 |
| 桌面 GUI+Tool | [OSWorld-MCP](https://arxiv.org/abs/2510.24563) | 158 个 Tool、7 App；发现强模型 Tool 调用率仍低 | 不能把“首次评测 Tool 使用”作为主张 |
| GUI/CLI 严格对照 | [GUI vs. CLI](https://arxiv.org/abs/2606.24551) | 440 个匹配任务，使用相同目标、状态和终态 Verifier；补齐 skill coverage 后 CLI 明显提升 | Sonnet 所说“它用了不同任务集”是错误的；我们的区别必须更具体 |
| GUI-Tool 路径学习 | [ToolCUA](https://arxiv.org/abs/2605.12481) | 训练 Agent 在关键节点选择 GUI 或 Tool，并构造交错轨迹 | “什么时候切换通道”的 Agent 侧故事也已经存在 |
| 自动任务生成 | [AutoPlay](https://arxiv.org/abs/2509.25047) | 基于探索生成 20k 移动与 10k 桌面任务，并用执行器/Verifier 过滤和训练 | “截图/轨迹送给模型自动生任务”不是充分差异 |
| 自动环境与 Evaluator | [InfiniteWeb](https://arxiv.org/abs/2601.04126) | 自动构建功能 Web 环境、任务和可验证 evaluator，且报告迁移收益 | “自动造环境+任务+奖励”也已经拥挤 |
| 合成移动环境 | [SimuWoB](https://arxiv.org/abs/2605.25160) | 后端无关的 Web 移动模拟、120 个长链路任务、自动奖励与真机样本对比 | 重建流水线需要保真度或迁移数据才能成为主贡献 |
| Agent 探索找 Bug | [GUITester](https://arxiv.org/abs/2601.04500) | 将导航和缺陷判断拆开，研究环境问题与 Agent 错误的归因 | “用轨迹发现 Bug”适合做 QA 方法，不足以单独撑主线 |

因此，我们不应声称：

- 最大、最真实或最多样；
- 第一个移动 GUI+Tool benchmark；
- 第一个自动生成任务和 Verifier；
- 第一个让 GUI-only 与 Hybrid 使用相同任务；
- Tool 总能提升性能。

真正仍有空间的窄问题是：**App 能力的提供方如何设计 Tool contract，以及 Tool 价值如何受任务 affordance 和业务状态分布影响。**

## 五、推荐的论文主线

### 5.1 一句话主张

> We build a controlled mobile agent world to study provider-side capability exposure, and show that the utility of app tools is conditional on task affordance and business-state distribution; incomplete or mismatched tools can be less effective—or more harmful—than GUI-only interaction.

中文可说：

> 我们构建了一套可控移动 Agent 世界，系统研究 App 提供方应当如何开放结构化能力；Tool 的价值并非固定，而取决于任务类型、业务状态和 Tool contract，错误的开放方式甚至可能不如纯 GUI。

注意：“show”只有实验完成后才能使用。立项和组会阶段应写成“we ask / we hypothesize”。

### 5.2 三层贡献结构

#### C1：交互通道适配性分类

把任务拆成具有操作定义的 affordance，而不是只按 App 类别或任务长度分组。

| Affordance | 典型需求 | 更自然的通道 | 示例 |
|---|---|---|---|
| 视觉/空间判断 | 比较外观、识别画面、拖拽、局部微调 | GUI | 美颜强度、图片裁剪、地图位置、商品图片比较 |
| 结构化检索/聚合 | 精确过滤、稳定 ID、长列表、跨字段计算 | Tool | 查找本月生日联系人、筛多个约束的订单、统计待办 |
| 草稿与批量准备 | 多字段填充、批量候选、可撤销准备 | Tool → GUI | 准备订单/评价/邮件草稿，再由 GUI 审阅 |
| 敏感或用户可见确认 | 支付、发送、发布、分享、删除 | GUI | Tool 选择对象和填草稿，GUI 完成最终确认 |
| 探索式选择 | 目标本身尚不明确，需要浏览后决定 | GUI 为主，Tool 可辅助召回 | 逛餐厅、挑播客、看推荐内容 |

这里“美颜 App 更适合 GUI”的说法需要进一步精确：不是整个 App 都适合 GUI，而是**视觉效果判断和局部操作**是 GUI-native；搜索目标照片、读取元数据、批量定位素材仍可能是 Tool-native。论文应分析子任务，而不是给整个 App 贴标签。

#### C2：Tool 暴露作为 App 侧可控干预

对同一能力建立多个 exposure profile：

- `E0 GUI-only`：没有 App Tool；
- `E1 query/navigation`：只开放检索和导航；
- `E2 query+draft`：允许构造草稿或 prepare，但不能完成敏感提交；
- `E3 direct mutation`：允许 Tool 直接修改业务状态；
- `Ebad incomplete/mismatched`：字段缺失、查询语义过窄、对象标识不一致或 handoff 不完整。

研究问题不只是成功率谁高，而是：

- 哪种 affordance 从哪一级开放中获益？
- Tool 是否改变了关键路径，还是仅被调用但没有用？
- direct mutation 是否提高效率却增加 collateral damage？
- Ebad 是否诱导 Agent 走上错误路径，产生负收益？
- Agent 能否识别 Tool 不适合当前任务并主动回到 GUI？

#### C3：统一业务终态支持因果评估

统一 Store 不是单独的“大发明”，但它是上述实验可信的技术基础：

- 同一 task instance 可以在多个 exposure profile 下运行；
- GUI 和 Tool 对同一实体、字段和约束产生结果；
- Verifier 不关心具体路径，只检查最终业务状态；
- 可以检查 noop、partial completion、wrong entity 和 collateral damage；
- 可以区分 Tool 被暴露、被调用、产生有效信息、改变后续路径、决定成败。

## 六、多初始化怎样从配套功能变成研究变量

简单地给每个 App 多放几套随机 seed 不够，因为 AndroidWorld 已经有任务参数化和初始化逻辑。更有价值的设计是定义**业务状态分布**，并用它研究 Tool 价值何时发生变化。

建议至少定义：

| 状态 Profile | 特征 | 能检验什么 |
|---|---|---|
| Empty | 无历史、无草稿、无收藏 | Agent 能否正确进入 cold-start；Tool 是否无用 |
| Sparse | 目标少、干扰少 | GUI 短路径基线 |
| Dense | 长列表、多历史、多候选 | 精确检索和聚合 Tool 是否开始显著有益 |
| Ambiguous | 多个同名或相近对象 | 稳定 ID、字段完整性和澄清能力 |
| Conflict/Edge | 券冲突、库存不足、过期状态、权限限制 | Agent 是否能处理约束，Tool 与 GUI 是否给出一致语义 |

关键假设可以是：

> Tool utility is state-conditional. 同一个查询 Tool 在 5 条记录时可能没有收益，在 500 条记录时可能成为关键路径；视觉判断则不会因为列表变长就自然适合结构化 Tool。

这样“多初始化”就不是数据装饰，而是论文实验中的第二个自变量：

```text
任务 affordance × Tool exposure × 业务状态 profile
```

## 七、任务 + Setup + Verifier 自动生成是否值得做

值得，但不能只说“用 Sonnet/GPT 自动生成”，因为 AutoPlay、InfiniteWeb 和 AndroidWorld 都已经覆盖了相邻方向。

我们最有机会的技术差异是 **verifier-by-construction**：从同一个机器可读的 App 表示共同编译任务参数、初始状态和 Verifier，而不是先生成题面，再让另一个 LLM 猜怎么判。

### 7.1 App Circuit 不应只是可视化

建议的中间表示包含：

- `screen / ui_state`
- `action / transition`
- `data_entity / data_field`
- `tool / os_capability`
- `reads / writes / invokes / returns_to`

它必须真正服务于编译链：

```text
App Circuit + typed store schema
       ├── 生成可达路径与任务候选
       ├── 生成初始状态和干扰项
       ├── 生成 Tool exposure variants
       ├── 生成 expected state diff
       └── 生成 Verifier + mutation tests
```

如果图只是把 route JSON 画漂亮，它是演示资产；如果它驱动了上述五项，它才是系统贡献。

### 7.2 需要证明的不是“能生成”，而是“生成得可靠”

建议比较三种输入：

1. Prompt + screenshot；
2. screenshot + navigation graph；
3. App Circuit + typed state schema + screenshot。

衡量：

- 人工接受率；
- 任务可执行率；
- 目标唯一率；
- Setup 成功率；
- Verifier mutation score；
- noop、partial、wrong entity、collateral damage 的拒绝率；
- 人工修改时间。

这比只报告“生成了多少任务”更有说服力。

## 八、最小可行实验，不需要先把 218 条全做完

建议先做一个论文级最小闭环：

### 8.1 样本

- 选择 6–8 个状态丰富且 Tool 较完整的 App；
- 选择 30–50 条有可靠语义 Verifier 的任务；
- 每种 affordance 至少 8–10 条，并覆盖不同 App；
- 每条任务先支持 sparse/dense，部分任务再加入 ambiguous/conflict。

### 8.2 条件

- 主对照：E0、E1、E2、E3；
- 风险实验：只在小规模任务上加入 Ebad；
- 2–3 个不同模型，每个 task instance 至少 3 次重复；
- 使用同一模拟时间、同一初始 snapshot、同一 Verifier。

### 8.3 指标

- state-verified success，而不是 Agent `COMPLETE`；
- 成功条件下的步骤数和时延；
- Tool `available / invoked / useful / critical-path / harmful` 五级归因；
- first useful Tool call step；
- Tool→GUI handoff 成功率；
- collateral damage rate；
- 错误类型：grounding、planning、tool schema、handoff、state conflict、premature completion；
- 状态 profile 改变后性能下降幅度。

### 8.4 三个最重要的实验问题

1. **适配性预测**：affordance 标签能否预测 Tool 带来的收益？
2. **状态条件性**：Tool 收益是否在 dense/ambiguous 状态显著放大？
3. **错误暴露代价**：Ebad 是否比 E0 更容易导致错误完成、循环或 collateral damage？

### 8.5 一个能在会上快速讲清的 Demo

选择一个同时含检索和用户确认的任务，例如：

> 在大量订单中找到符合多个约束的一单，准备退款原因和凭证，但由用户在 GUI 中确认提交。

并排展示：

- GUI-only：可完成，但在 dense state 下查找较长；
- query+draft Tool：快速定位并准备内容，GUI 显示确认，成功；
- incomplete Tool：漏掉订单状态或选错稳定 ID，导致 Agent 被误导；
- direct mutation：很快，但若 Tool contract 不检查约束，可能产生额外状态修改。

这个案例比“Tool 帮忙少点几步”更能体现提供方设计问题。

## 九、三条可选论文路线

### Route A：App 能力开放与交互通道适配性（推荐）

- 主问题：什么能力应以什么 Tool contract 暴露？
- 环境角色：可控反事实实验平台；
- 最关键补建：exposure profiles、affordance 标注、语义 Verifier；
- 风险：如果“错配有害”和“状态条件性”没有显著数据，故事会退化为设计经验；
- 适合当前资产：最高。

### Route B：Verifier-by-construction 的 Benchmark Factory

- 主问题：能否从 App Circuit 和 typed state 自动生成任务、setup 和可靠 Verifier？
- 最关键补建：Circuit IR、编译器、mutation tests、与 prompt-only/graph-only 的对照；
- 风险：AutoPlay 和 InfiniteWeb 已经很强，必须以 verifier correctness 而非规模竞争；
- 适合当前资产：中等，可能发展成第二篇或系统论文。

### Route C：从截图/录屏到可训练移动世界

- 主问题：AI 辅助重建能否低成本产生高保真的功能环境和可迁移训练数据？
- 最关键补建：构建成本、视觉/行为保真度、QA 发现率、真实设备迁移；
- 风险：InfiniteWeb 和 SimuWoB 直接构成竞争，且目前缺少严谨保真度数据；
- 适合当前资产：作为 System 章节很好，作为唯一主线风险较高。

建议论文结构以 Route A 为主，Route C 解释环境如何建成，Route B 作为扩展或未来工作。不要三条同时争主贡献。

## 十、社区为什么会觉得它有用

社区价值不能只说“App 多”。一个真正可发布的包应让不同研究者拿来做不同事情：

1. **Agent 研究者**：在相同任务上研究 GUI/Tool 编排、handoff、错误恢复和长程记忆；
2. **Tool/API 设计者**：比较 query、navigation、draft、mutation 等 contract 的收益与风险；
3. **训练研究者**：生成具有终态奖励的 GUI、Tool 和交错轨迹，用于 SFT/RL；
4. **Benchmark 研究者**：利用多状态 profile 测鲁棒性，而非只在单一默认 seed 上排名；
5. **环境构建者**：复用 App 模板、统一 Store、系统能力和 Verifier 测试规范；
6. **软件 QA 研究者**：利用轨迹和状态 diff 区分 Agent、环境、题面和 Verifier 错误。

对外发布时最有用的不是一个静态任务列表，而是：

- App 模板与结构化 schema；
- scenario/profile 配置；
- Tool exposure 配置；
- task/setup/verifier 定义；
- verifier mutation tests；
- GUI-only/Hybrid baseline；
- 可重置运行脚本和可审计轨迹。

## 十一、你的贡献应该怎么准确表达

你的贡献不是“人工检查了很多 App”这么弱，也不应只写成执行工作量。更准确的研究贡献包括：

1. **把环境、任务、Tool、Verifier 从四条松散流水线收敛成一个闭环**，并明确同一业务实体和字段必须跨 GUI、Tool、Store、Verifier 一致；
2. **发现任务可运行不等于 Agent 能完成、Agent COMPLETE 不等于终态正确**，推动从轨迹印象切换到语义状态验证；
3. **通过大规模逐条审查形成错误归因体系**：环境断链、题面歧义、数据缺失、Agent wrong-app、Tool 缺口、Verifier 风险不能混在同一个失败率里；
4. **从具体 Bug 中抽象出论文问题**：Tool 是否被调用并不等于有用，GUI 和 Tool 的价值受任务 affordance、数据密度和 handoff contract 影响；
5. **建立可交付的质量门槛和审计工具**，使环境不仅能展示，还能被别人复现、训练和评估。

这些不是论文之外的杂活。Benchmark 论文最难的工作之一，就是把“看起来能跑”变成“结果可以被信任”。不过，论文仍需要把这些工程判断转化为可测变量、对照条件和实验证据；你的资产已经够多，下一步应减少继续铺量，集中证明一两个关键命题。

## 十二、Sonnet 评审：可采纳与需纠正的部分

### 可采纳

- 当前工程资产很强，但“环境很大”尚不是科学主张；
- 最有潜力的是 modality affordance 与 selective capability exposure；
- 多初始化必须变成业务状态分布；
- App 重建流水线若没有保真度评估，应作为支撑贡献；
- 任务/Verifier 自动生成不能与 AutoPlay、InfiniteWeb 只比规模；
- 先完善一批语义 Verifier 和多级 exposure，再做主实验。

### 必须纠正

- GUI vs. CLI 并非使用不同任务集；它明确使用相同目标、状态与终态 Verifier。我们不能用这一错误对比宣称更强因果控制。
- “现有工作都把 Tool 当成单向正干预”过强。已有工作已经讨论 skill coverage、Tool 调用率和路径选择。更精确的差异是：**我们把 provider-side Tool contract、暴露粒度和业务状态条件作为联合实验变量。**
- “错配 Tool 比无 Tool 更差”目前是有价值的假设，不是已经被现有 218 条轨迹证明的结论。
- 不能预先写 Cohen's κ、统计功效或显著性结果；这些必须在标注和实验后计算。

Sonnet 原始输出保存在 `artifacts/paper-story/sonnet-raw.txt`，只作为内部 brainstorming 证据，不应直接进入论文。

## 十三、建议的实施优先级

### P0：现在就做

1. 从现有任务中挑 30–50 条状态可验证、Tool 机会明确的任务；
2. 定义 affordance 标注指南，并由两人独立标注；
3. 为选中任务补齐语义 Verifier 和 mutation tests；
4. 把 Tool 暴露改成配置，而不是固定注册结果；
5. 给每个选中任务至少建立 sparse/dense 两个 state profile。

### P1：主实验需要

1. 运行 E0/E1/E2/E3，少量加入 Ebad；
2. 对每次 Tool 调用标注 useful、critical-path、harmful；
3. 做 affordance × exposure × state 的混合效应分析；
4. 产出 2–3 个并排可视化 case，而不是只展示总成功率。

### P2：有余力再做

1. 将 App Circuit 从静态图变成 task/setup/verifier 编译输入；
2. 对任务+Verifier 自动生成做三种输入消融；
3. 测量 App 重建成本、行为保真度和真实设备迁移；
4. 扩大到全部 218 条，而不是一开始就把全部任务设为阻塞项。

## 十四、下一次组会可以怎么讲

不要先讲“我们有很多 App”。建议用下面这条线：

1. 未来 App 不会一次性开放全部 API，而会逐步、选择性地向 Agent 开放能力；
2. 现有工作更多关注 Agent 在已有 GUI/Tool 中如何行动，但 App 提供方不知道应该开放什么；
3. 我们构建了一个可重置、终态可验证的移动世界，使同一任务可以在不同能力暴露下做反事实实验；
4. 我们提出按视觉、结构化检索、草稿准备、敏感确认等 affordance 分析 Tool 价值；
5. 下一步将验证 Tool 收益是否随任务类型和业务状态变化，以及错误 Tool 是否比没有 Tool 更危险；
6. 环境交付、31 个新 App、任务和统一 Store 是支撑这项研究的基础，而不是故事终点。

一句最简版本：

> 我们不只想评测 Agent 会不会用 Tool，而是想回答未来 App 应该把什么能力、以什么粒度开放给 Agent；为此，我们构建了一个能控制 Tool 暴露、业务状态并直接验证终态的移动实验环境。
