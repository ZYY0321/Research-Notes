# 0815 Tools 全量实验：实验定位与工作方式

时间：2026-08-15  
状态：新实验，任务设计中，尚未跑批  
位置：本地“不要上传-修bug”目录，不上传 GitHub

## 0. 这份文件给谁看

这份文件是给**任务设计者（Codex/设计 Agent）和人工审题者**看的内部实验说明，不会放进正式任务 prompt，也不会给执行任务的 Agent 阅读。

正式执行 Agent 只能看到自然语言任务题面；下列内容必须隐藏：

- 推荐或可能路径；
- 需要覆盖哪些功能点；
- Store 字段、实体 ID 和 Tool 名；
- “操作后去哪里检查”的测试性指令；
- verifier 和历史 Bug 来源。

如果“再去订单页确认”“检查两个页面是否一致”本身不是用户真实目标，就不能写进公开题面，只能作为隐藏判定。用户确实要求查看订单、整理记录或继续处理后续业务时，才可以自然地出现在题面中。

本阶段没有调用外部模型 API。设计依据来自本地代码、导航声明、Store、App Tools、已有任务和文档。后续即使调用模型 API，也不会用一次请求要求模型读完整个 App；一个 App 要分阶段生成事实材料，再基于压缩后的功能图设计任务。

## 1. 实验目标

这不是 0808 全量验收的附属工作，也不是 V4 原有任务的简单扩写，而是一轮新的 GUI + App Tools 全量实验。

核心问题是：当任务更接近真实用户表达、链路更长、途中包含更多选项和功能点时，Agent 能否正确组合 GUI 与 Tools 完成任务；同时，这些轨迹能否充分暴露 App 的数据、状态、导航和系统接入问题。

本轮不预设“每个 App 必须几条”“必须几条历史 Bug 回归”。任务数由 App 实际具备的功能、数据丰富度和可判定性决定：

- 功能少的 App 不强行凑题；
- 功能复杂、路径丰富的 App 可以多设计；
- 历史问题只用于启发任务，不作为配额；
- 同一任务应尽可能自然地经过多个功能点，而不是把单点测试机械拼接起来；
- 先形成任务池给人工详细审查，审查通过后才实现判定、冒烟和跑批。

## 2. 与 V4 和 0808 实验的区别

| 维度 | V4 / 0808 常见做法 | 0815 新实验 |
|---|---|---|
| 任务核心 | 查字段、比数值、写 Notes、一步状态修改 | 完成一个真实业务目标并确认后续结果 |
| 长度 | 多为短链路或跨 App 信息搬运 | 一个 App 内多页面、多选项、多状态的完整链路，也允许自然跨 App |
| 功能覆盖 | 一条任务常集中在一个 Tool 或字段 | 一条任务自然经过搜索、筛选、详情、选择、动作、返回、复核等多个功能点 |
| 判定 | 最终文本或单字段成功 | 多个业务字段、实体身份及跨页面一致性联合判定 |
| 历史 Bug | 可直接做回归题 | 只作为风险线索，不限制题目组成 |
| 任务数量 | 先规定总数再填充 | 先看功能图和数据，再决定保留多少题 |
| 失败价值 | 主要看 SR | 同时归因 App Bug、Tool 缺口、任务问题、Agent 能力问题 |

## 3. 先建立“App 功能电路图”

仓库其实已经有一部分基础：每个 App 的 `navigation.declaration.ts` 被平台定义为静态分析、导航图生成和任务生成的 source of truth；`navigation_declaration_analyzer.mjs` 可以生成 nav graph JSON。一些复刻 App 还维护了 `docs/<app>-replication/spec.json` 交互矩阵。

但目前并不是每个 App 都有完整 `spec.json`，现有 nav graph 也主要表达“页面和 UI 状态如何连通”，没有完整表达：

- 一个动作读写哪些 Store 字段；
- 同一个实体会在哪些页面再次出现；
- App Tool 能查询、导航或准备什么；
- 哪些步骤必须走 GUI；
- 支付、分享、相册、剪贴板等系统能力如何返回；
- 哪些动作形成一条有业务意义的状态链。

因此本实验先为每个 App 生成扩展的 **Feature Circuit Graph（功能电路图）**。它不是单纯截图，而是一份可视化和结构化数据共用的图：

```text
[页面/界面状态]
   ├─用户动作/选择─> [页面/弹层]
   ├─写入─> [Store 实体.字段]
   ├─调用─> [OS 支付/分享/相册/剪贴板]
   └─可由─> [App Tool 查询/导航/准备]

[Store 实体.字段] ─被读取于─> [订单/收藏/历史/个人页/消息等页面]
```

每个 App 的机器可读图至少包含五类节点：`screen`、`action`、`state`、`tool`、`os_capability`；边至少包含：`navigate`、`select`、`writes`、`reads`、`invokes`、`returns_to`、`tool_access`。

### 一次请求是否能看完一个 App

不把完整 App 代码塞进一次请求。正确做法是分四次事实提取，每一步产出结构化中间结果：

1. 导航提取：解析 declaration，生成页面、UI state、transition 和可达性图；
2. 状态提取：解析 Store actions 和消费者，得到动作—字段—读取页面关系；
3. Tool/系统能力提取：解析 definitions、handler、manifest 和 OS 调用；
4. 数据提取：只提取可用于任务的实体类型、候选数量、区分字段和关联关系，不复制整个 defaults。

最后把四份小图合并。任务设计 Agent 读取的是合并后的功能电路和少量必要事实，而不是重新吞全部源码。每张图还要保留源码位置，遇到疑点可以按需回查。

## 4. 任务设计流程

### A. 先生成并审查功能电路，不立即写题

逐 App 检查当前集成环境中的：

- `manifest.ts` 和系统能力声明；
- `navigation.declaration.ts`、页面和弹层关系；
- store/defaults 中的实体、状态与关联字段；
- App Tools 的 definitions、返回字段、过滤边界和写操作；
- 历史实验任务与轨迹覆盖了什么、遗漏了什么；
- 《口语描述.TXT》《验收反馈跟踪.md》中记录的风险是否仍能从当前实现中看到。

输出功能电路图 JSON、简化可视图和覆盖统计。若 declaration 与实际代码不一致，先记录差异，不把错误声明当事实。

### B. 从真实用户目标生成任务池

不按模板凑题。优先选择下列天然适合长链路的业务：

- 先比较或筛选，再对符合条件的对象执行操作；
- 操作中需要选择规格、日期、地址、支付方式、分类、优先级等多个选项；
- 完成后需要从订单、历史、收藏、日程、个人页等处确认；
- 用户已有旧状态，新的操作不能误伤已有购物车、收藏、任务或记录；
- 同一个实体会经过搜索结果、详情、会话、订单等多个页面，必须始终保持身份一致；
- 支付、分享、相册、剪贴板等系统操作完成后还要回到来源 App 继续；
- 包含取消、返回、重新进入、编辑、退款或重复操作等真实后续。

### C. 人工审题后再写 verifier

审题时允许大幅修改题面、前置状态和目标，不急着保留数量。只有同时满足以下条件才进入实现：

1. 用户真的可能这样提出需求；
2. 使用了该 App 的特色功能，而非换个 App 名也成立；
3. 当前种子数据支持目标；
4. 存在清晰、稳定、不过度依赖文案的判定方式；
5. 难度来自信息和业务组合，不是藏按钮或故意绕路；
6. 与已有任务相比有新的功能覆盖或新的组合关系。

## 5. 任务设计 Agent 主提示词

```text
你是 MobileGym GUI + App Tools 实验的任务设计者。请为指定的新复刻 App 构建一批真实、较长、功能覆盖丰富且可稳定判定的候选任务。不要先规定数量，也不要为了数量凑题。

你必须先完整检查当前集成环境中该 App 的 manifest、导航声明、页面、组件、store/defaults、App Tools definitions/index，以及已有实验任务。再把口语验收记录当作风险线索，而不是直接照抄成回归题。文档中的“已关闭”也不能替代对当前代码和可运行界面的确认。

先输出 App 功能图：
- 有哪些真实业务入口和页面；
- 每个入口允许用户选择什么；
- 动作写入哪些实体和字段；
- 结果会在哪些其他页面被读取；
- 哪些地方涉及支付、分享、相册、剪贴板、系统时间或跨 App 返回；
- App Tools 能查询或修改什么，哪些仍必须通过 GUI；
- 哪些功能之间可以自然组合成一个用户目标。

然后生成候选任务池。任务必须遵守：
1. 用自然用户语言描述结果和必要约束，不写逐点击教程，不透露内部 ID 或判分字段。
2. 优先设计会自然经过多个页面、多个选项和多个功能点的链路。常见长度为 8–20 个有效动作，但不为步数硬拼功能。
3. 任务可以是单 App，也可以在业务上合理时跨 App；禁止为了显得复杂而机械加入 Notes 或微信转发。
4. 操作完成不能立刻结束。只要业务上合理，就要求从订单、历史、收藏、个人页、另一个入口或重新进入 App 后确认结果。
5. 任务要包含足够明确的约束来避免歧义，例如指定商品和规格、目标日期范围、排序规则、地址标签、是否保留购物车旧商品、是否允许替代方案。
6. 不要求每个 App 固定题数。功能少就少出，功能多且链路差异明显就多出。删除重复、只能测同一字段或只有展示意义的题。
7. 不把看到 Toast、打开非首页、写一条 Notes、调用一次 Tool 当作任务完成。
8. 不凭真实 App 常识假设当前 mock 已实现。若一个很真实的任务当前走不通，保留为“有实验价值但需确认可执行”，并说明卡点；不要偷偷把任务改简单来迁就 App。
9. 每条任务分为两个对象输出：`public_instruction` 只能包含用户目标和必要业务约束；`private_design` 才能包含可能路径、功能覆盖、关键选择、最终状态、跨页面一致性、verifier、初态、风险和与已有任务的差异。绝不能把 private_design 拼进正式 prompt。
10. 明确区分失败来源：App Bug、App Tool 缺口、任务/种子设计错误、Agent 操作或推理错误、系统能力问题。

最后输出覆盖图，说明当前任务池覆盖和未覆盖了哪些页面、功能、选项、写操作、系统能力及返回路径。不要修改 App，不要提交代码，不要直接跑全量实验。
```
