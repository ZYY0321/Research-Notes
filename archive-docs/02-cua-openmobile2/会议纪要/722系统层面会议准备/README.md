## 1. Demo 要对齐的「最好环境」长什么样

7/15 口径不是只做四条补丁，而是：**先在官方 app 上把统一能力做透 → 跟进造 app → 最后合版成一个环境**。  
7/14 汇报则把「交付环境」拆成：**已交付底座 + 未兑现护城河 + 视定位才做的 RL/MCP 壳**。

因此 demo 必须让人一眼看出三层，而不是只演示「我补了英文」：

| 层 | 会议里的定位 | Demo 怎么交代 |
|---|---|---|
| **L0 底座（已交付，要亮出来）** | getState / reset / tab 隔离 / 剪贴板 / 轨迹录制 / TimeService / 一键静态包 | 开场 30–60 秒：同一条任务里顺带展示，不单独立项开发 |
| **L1 本轮兑现（护城河，必须做成）** | **已有任务的可验证判定**（含必要 exclude）、多语言落地、多场景注入、新 app 跨 app、系统级统一管理、构建侧轻量 gate | **演示主体**；对应「统一做」四条 + 构建流程 |
| **L2 预留（会上口头边界）** | gym 五元组 / HTTP env / 稠密奖励 / MCP / 全量 Math.random 迁移 | 明确「最好环境」含接口预留，但本 demo **不做**；等定位选 B/C 或外部需求 |

### 判定 / 验证脚本：会后已收窄的口径（重要）

对齐 7/14 周会原文：**「无需全量操作验证脚本，随任务配套即可」**；7/15 也是「初步根据**常见任务**提供验证脚本」。

| 要 | 不要 |
|---|---|
| 针对**已有 / 将交付的任务**写成功判定（读 getState → include，跨 app 时加 exclude） | 为每个按钮、每个页面写「全功能 walkthrough」并当作交付物 |
| 证明环境**能**做任务级可验证（示范任务上跑通即可） | 显式对外交付「每 app 一份完整 runtime_walkthrough 产品」 |
| 示范 app 上挑几条代表性任务把判定写透，作为合版模板 | 把「5–8 app × 30–50 条断言」当成本轮必须交的数量指标 |

**会上怎么说：** 交付的是「任务可判定的环境」；验证逻辑挂在任务上，不是另交一套覆盖全部 UI 的脚本包。现有 `runtime_walkthrough` 只作内部自检/示范加速，**不是对外交付清单上的独立项**。

### 两类检查不要混（2026-07-22 再澄清）

| | **交付可验证（主线）** | **构建期检查（辅线）** |
|---|---|---|
| 干什么 | 数据和任务：store 真变 → 任务能判定；多套初始数据仍可判定 | 合版前评估后续改动成本、有哪些坑 |
| 不是 | 用来检查「app 写得咋样」并当交付物 | 不是验证脚本交付包 |

`scan_binding_risks` 属于辅线。多数据属于主线。详见 `./口径与多数据现状.md`。

### 数据绑定：任务验证真正卡的点（比「有没有脚本」更重要）

判定读的是 store，不是屏幕文案。因此：

- **前端硬编码 / 只改本地 useState**：UI 可以「看起来变了」，`getState` 不变 → 任务判定 **FAIL**（这是能力，不是缺陷）。
- **Demo 必须展示**：操作前后同一字段的 store diff（如 `cart.length` / `reimburse`），证明验收的是后台真值。
- **多套数据**：复用已有 `env.set_state`；命名场景在 `bench_env/scenarios/`。**已 smoke + showcase_acceptance 跑通，可宣称真实可展示。** 用 `python -m bench_env.scenarios.smoke_test` / `showcase_acceptance` 验收。

展开说明与 RL 取数简表见：`./数据绑定与RL取数.md`。

**一句话会议口径：**

> 最好可交付形态 = L0 底座可现场调用 + L1 在示范 app 上跑通（**store 真变可判定**、可切语言/主题/数据、可跨 app 且能抓副作用）+ 构建侧有轻量自动检查。验证随任务配套；硬编码骗得了眼睛骗不过 getState。L2 按定位另开。

## 2. 对照文档的覆盖缺口（相对上一版 demo 计划）

上一版已覆盖：注入、中英文、跨 app×1、任务判定。对照 0714/715 后，**还不够「最好环境」**，缺下面几块（判定项已按会后口径收窄）：

| 缺口 | 出处 | 为何必须进 demo | 本轮怎么补 |
|---|---|---|---|
| **L0 底座串场** | 汇报 §1–3、§10、§17 | 听众容易以为我们只有「补洞」；底座才是差异化前提 | 演示脚本固定：reset → 操作 → getState →（可选）看 trajectory 目录 |
| **系统主题/深色 + 语言 =「统一管理」** | 715「系统语言、主题、共享数据」；汇报主题/深色已交付 | 只切语言不够；要证明 OS 一处开关、多 app 跟随 | locale + darkMode/theme 同场切换两枚示范 app |
| **共享数据不止剪贴板** | 715；汇报 §11 ContentResolver 新 app 0 处 | 「统一管理」若只有 clipboard，深度不够 | 示范 app 至少 1 处读系统通道（相册选图 / 通讯录 / 分享落盘），剪贴板作辅 |
| **跨 app 要「典型路径」不是凑一条** | 汇报 §9：相册选图、短信分享、通讯录选人 | 最好环境应展示可复制的路径模板 | 电商链：支付或分享；记账链：分享/选图；老链 12306→支付宝作对照片 |
| **任务级判定 + store diff（含必要 exclude）** | 714「随任务配套」；数据绑定 | 证明可验证；**能抓前端假变** | 示范任务 before/after `getState`；跨 app 任务加 exclude |
| **构建流程 gate（合版质量）** | 715「推进构建流程」；汇报阻碍 1；T-05/T-10 | 最好环境 = 能力 + 不会被下一批 app 冲垮 | `scan_binding_risks` + 中文硬编码提示；**不上全量 walkthrough 门槛** |
| **数据绑定审计** | 715；「硬编码 UI vs store」 | getState 护城河的前提 | 静态 hint + 任务级 store diff 演示（见 `数据绑定与RL取数.md`） |
| **多套数据 = 已有 set_state + 场景 JSON** | 汇报 §8；715 | 训练多样性；不打扰造 app | `bench_env/scenarios/*` + `apply_scenario`；不必新 API |
| **DATA_VERSION** | 汇报 §5 | 注入/改种子时旧缓存失效 | 示范 app 确认有版本号；切换场景前 reset 或升版本，口头说明 |
| **皮肤色相** | 汇报重新定位 | 不要当训练卖点吹 | Demo **不讲**或一句带过：仅评测 OOD，非本轮卖点 |
| **RL 薄壳 / MCP** | 汇报 §13、决策 3 | 避免 demo 范围膨胀 | 会上用「L2 边界」说清：本环境先做到可合成+任务可判定 |

仍 **故意不做**（避免假全面）：全功能验证脚本铺开、显式交付 walkthrough 包、全量 30 app 同等深度、独立 E2E、LLM 视觉 judge、MCP、HTTP env、稠密奖励。

## 4. 演示脚本（建议 6–8 分钟，按「最好环境」叙事）

**现场入口：** `http://localhost:3000/?deck=1`（左说明 / 右模拟器）。下列步骤已映射到演示台条目按钮；仅跨 app 支付/分享等仍需在右侧手点。

### 4.1 开场 · L0 底座（约 1 分钟）

1. 条目「底座」→ Reset / 打开淘宝 / 读 cart.length。  
2. 一句带过：tab 隔离、轨迹落盘为已交付底座。

### 4.2 主体 · L1 任务判定与数据（约 2.5 分钟）

3. 「多套初始数据」→ 一键空购物车 → 打开购物车看空态。  
4. 「任务级可验证」→ 右侧加购 → 再读 cart.length。  
5. 划界：验证挂任务；RL 用同一份 store。

### 4.3 主体 · L1 模板化与统一管理（约 1.5 分钟）

6. 「系统语言」一键 en/zh；「深色」一键开关。  
7. 「共享数据」：剪贴板 + 读相册数量 + 打开咔皮分享页。

### 4.4 主体 · L1 跨 app（约 2 分钟）

8. 「淘宝→支付宝」按条目手点步骤走完；「分享微信」同理。  
9. 口述 Judge + exclude。

### 4.5 收尾 · 构建与成本（约 1 分钟）

10. 「构建期扫描 / 验收脚本」复制命令；每条底部有 **~20+ app 成本** 可改备注。

## 5. 工程落地顺序（在 `codex/system-env-showcase` 上）

按依赖做；每步都对应演示脚本里的一节。

| 顺序 | 工作包 | 主要落点 | 完成定义 |
|---|---|---|---|
| A | L0 串场清单 | 演示备注，少改代码 | reset/getState/trajectory 路径写进点击清单 |
| B | 已有任务的判定（store diff + 必要 exclude） | 任务 judge；淘宝已有 `AddItemToCart` 等 | 示范任务稳定可判定；**演示 before/after store**；不追求功能全覆盖 |
| C | 命名场景 + `apply_scenario` | `bench_env/scenarios/`（底层已是 `set_state`） | empty / 混合场景可注入；app 无感 |
| D | 中英 + 主题跟随 | `strings*.ts` + 页面 hook；确认 OS locale/dark | 现场切换两 app 生效 |
| E | 跨 app 典型路径 | 示范 app intent + 系统目标 | 新复刻侧 ≥1 条真跑通（支付或分享/选图） |
| F | 共享数据示范 | ContentResolver 或系统分享落点 | 不止 clipboard |
| G | 构建期改动评估（辅线） | `scripts/scan_binding_risks.mjs` | 出 hint 供合版成本评估；**不计入交付验证** |
| H | Store 审计 | 扫描 useState 藏业务字段 | 示范 app 清单清零或注明例外 |
| I | 包装 | 点击清单 / 短录屏 + 成本表实测 | 开会可讲 |

**拆 PR 建议（做通后再拆也行）：**

1. 公共：`inject_state` + 扫描工具 → 保持在本 system 分支或再切 `codex/system-state-inject`。  
2. 各示范 app 业务改动可随后按 app 拆 PR。

## 6. 其他 app 合版成本（示范实测粗估）

| 能力 | 示范上做一次（实测感） | 复制到「有任务要交付」的 app | 主链路仍断（721 B/C） |
|---|---|---|---|
| 已有任务判定（含必要 exclude） | ~0.3–0.5 天/任务（含场景 prepare） | 同左，只写要交的任务 | 先修链路再写该任务判定 |
| 中英文全量 | 淘宝 ~1 天（605 keys）；咔皮 ~0.5–1 天 | 有 strings 骨架则 ~0.5 天；从零 1–1.5 天 | 同左 |
| 主题/深色跟随 | ~0.3 天/app（colorsDark + token 替换） | ~0.2–0.3 天 | 同左 |
| 跨 app 一条典型路径 | 支付 ForResult ~0.5 天；分享 SEND ~0.2 天 | 0.5–1 天（看是否已有 queries） | 常先补 filter/结果页 |
| 吃上注入 | 环境侧已有；场景 JSON ~0.5h–0.5 天/app | 0.5 天内 | store 乱则先审计 |
| ContentResolver/分享 | ~0.3 天（挂已有页） | 0.3–0.5 天 | 视产品是否有入口 |
| 扫描类 gate | `scan_binding_risks` 已可用 | 自动 | 自动 |

**7/31 建议承诺：** 数量 + 主链路可用；L1 = 示范闭环证明能力；验证只保证「已挂任务可判定」，不承诺全功能脚本、也不把 walkthrough 包当交付物。
