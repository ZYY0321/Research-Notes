## 1. 现状整理（开会先说这段）

### 1.1 数量

| 类别 | 数量 | 说明 |
|---|---|---|
| 业务 App（`apps/`） | **约 32 个** | 含淘宝、咔皮、微信、支付宝、美团等；扫描清单见汇报台「合版成本」表 |
| 系统 App（`system/`） | **约 14 个** | 相册、设置、浏览器等，一般不按「业务负责人」派 L1 |
| 你本地尚未合入 | **约 3 个** | 合入后总数会再涨；合入前不要把总数说死 |

约 **8 人**并行写业务 App（认领制）。公共能力与合版约定由系统侧（你）收口。

### 1.2 质量（两极分化）

| 层级 | 现状 | 代表 |
|---|---|---|
| **示范已接满 L1** | 语言/深色/多场景/跨 App/任务判定在示范链路上可演示 | 淘宝、咔皮（本轮 showcase） |
| **可用但未接 L1** | 主链路大体能点，但未系统接英文/深色/场景 JSON/任务判定 | 部分早期较完整的 App |
| **仍有 P0/P1（721 走查）** | 导航返回坏、假交互、主业务空壳、搜索/筛选结果错、数据不联动 | 走查写到的约 11 个：百词斩、Flomo、唯品会、拼多多、Boss、喜马拉雅、豆瓣、番茄 ToDo、美柚、微博、微信读书等 |
| **未系统走查** | 「没写到 ≠ 没问题」 | 其余未进 721 分 App 记录的 |

721 共性结论（合版前仍成立）：

- 验收不能只看「按钮有反应」——要看列表/统计/动态是否真变，返回是否回得去。
- 状态应进统一 Store；硬编码/本地 useState 会骗过眼睛、骗不过任务判定（`getState`）。
- 长期记录类种子往往只有一天，周/月统计天然废。

**结论一句话：** 环境侧 L1 能力在示范 App 上已经能交付演示；**全量 30+ App 的质量与接入进度差很大**，不能默认「示范通了 = 大家都能下周接完」。

### 1.3 L1 接入可行性（能不能接、卡在哪）

| L1 项 | 环境是否已具备 | 接到其他 App 是否可行 | 主要卡点 |
|---|---|---|---|
| 系统语言 / 深色开关 | **已具备**（OS 一处切，App 跟随） | **可行** | 要补 `strings.en`、页面用 hook；英文往往比中文长，会换行/撑破布局 |
| 多套初始数据（场景 JSON） | **已具备**（`setState` + `bench_env/scenarios/`） | **可行，但必须负责人写** | 每个 App 的 Store 字段形状不同，系统无法代写「空购物车/空账单」以外的业务补丁 |
| 跨 App 支付 / 分享 | **通道已具备**（Intent、支付宝收银台、微信转发） | **有需求才接，可行** | App 要声明 `queries` 并按示范调用；无支付/分享主链路的 App 可暂缓 |
| 共享相册 | **通道已修通**（双写 + Gallery） | **有保存/选图需求才接** | 对照咔皮分享接一行即可量级 |
| 任务级判定 | **模板 + 示范任务已有** | **可行，随任务配套** | 不做全功能 walkthrough 包；谁交付哪条任务谁写 `check_goals` |
| 主链路假交互整改 | 不属于「接开关」，是业务质量 | **必须负责人改** | 不先清 P0，接了语言/场景也训不稳 |

**可行性总结：**

- **轻量统一项**（接 locale/dark、对照示范补分享/相册调用）：系统出规范后，负责人按模板改，单 App 通常 **半天到一天半**量级（视文案量）。
- **必须负责人原创的项**（本 App 场景 JSON、英文字符串与换行布局、任务判定、P0 主链路）：系统只能给示范和检查清单，**不能代替 8 人写业务**。
- **不建议**：在 P0 导航/假交互未修前，强行要求全量 App 同等深度接满 L1——成本会从「接能力」变成「先救活 App」。

### 1.4 本轮示范证明了什么（对外一句话）

> 系统层已经提供：多场景注入、语言/主题统一开关、跨 App Intent、相册共享、任务级判定模板。淘宝 + 咔皮证明「新复刻 App 可以按同一套接满」。其余 App 的差距主要在业务质量与是否按规范接入，而不是环境 API 还不存在。

## 2. 总表（现状 / 缺口 / 主责 / 怎么改）

| 事项 | 现状 | 缺口 | 主责 | 怎么改 |
|---|---|---|---|---|
| 质量分层与盘点 | 示范 2 个已接 L1；721 约 11 个有明确 P0/P1；总数约 32 业务 App | 缺一份持续更新的「谁先接 L1 / 谁先修 P0」优先级表；你还有约 3 个 App 未合入 | **系统侧** | 你维护分层表与合入后总数；各负责人按统一模板回传「本 App 一条高频链路是否跑通」 |
| 主链路 / 假交互 / 导航返回 | 721 共性：能点但不联动、返回卡死、空壳 Tab | 多数问题仍在业务页，未按可训练主链路收口 | **各 App 负责人** | 按 721 里本 App 条目改页面与 Store；系统只提供验收口径（走通链路 + getState 真变），**不代写业务页** |
| 统一 Store + 多数据场景 | 注入通道已有；淘宝有 vip_active / new_empty / checkout_ready 等示范 | 多数 App 没有场景 JSON，或 Store 分散在组件里导致无法注入 | **各 App 负责人** | 系统提供目录约定与示范 JSON；负责人按**本 App 真实 Store 字段**写 1～2 个场景，并保证首页/我的等主表面跟着变（不能只改一个数组） |
| 中英切换 + 深色 | OS 开关已通；示范 App 已接；扫描表能看缺口 | 多数未接；接英文后大量换行/截断 | **各 App 负责人**（接文案与布局）；开关本身 **系统侧** | 系统发：接法说明、未翻译 key 扫描、文案宜短规范、淘宝/咔皮模板。负责人补全 `strings.en` 并改本页布局；**英文换行不归系统代改 20+ App** |
| 跨 App 支付 / 分享 / 相册 | 路由、支付宝、微信转发、相册双写已在示范跑通 | 有需求的 App 未声明 queries / 未调用 | **系统侧** 维护通道；**负责人** 补本 App 调用 | 无支付/分享可暂缓。有需求的对照淘宝结算→支付宝、咔皮→微信/存相册，在本 App 补声明与调用 |
| 任务级判定脚本 | 示范有 CheckoutCartItem、PayOrderWithAlipay 等 | 多数将交付任务还没有 `check_goals` | **各 App 负责人** | 系统提供 Judge 模板与示范任务；负责人**只为自己要交付的任务**写判定（init↔curr + 规则），不做全 UI walkthrough 包 |
| 合版与目录约定 | 认领清单已约定「只 PR 本 App」 | 仍有人误改公共文件、漏场景目录 | **系统侧** 定规矩；**负责人** 遵守 | PR 只含 `apps/<App>/`，以及本 App 的 `bench_env/scenarios/<app>/`、`bench_env/task/...`；公共锁文件/新依赖先群里同步 |

## 3. 协作怎么跑（写细：谁先做什么、交什么）

### 3.1 分工口诀（避免「双方一起改」含糊）

1. **同一套改法能套到 ≥3 个 App**（例如接 locale API 的步骤、场景文件目录、相册双写两行）：由**系统侧先写规范/模板，必要时你批量改示范或出补丁说明**；负责人按文档操作，而不是 8 人各自问 AI 猜。
2. **只有某一个 App 才懂的内容**（商品字段、账单结构、假按钮背后该不该写 Store）：**该 App 负责人改**；系统不代写。
3. **示范 App 上暴露出来的「环境能力」问题**（时钟与种子错月、相册通道、Intent 路由）：**系统侧先修、先归类**；确认是业务独有写错再转负责人。
4. **英文换行 / 文案过长撑破**：**负责人主责**。你提供「宜短、关键可截断」规范，并用淘宝/咔皮改成样子给大家抄；你不负责替 20 多个 App 改每一句英文。

### 3.2 推荐工作流（系统侧 → 负责人 → PR）

下面按时间顺序写。核心一句：**先由你发齐规范与模板，再让负责人动手；不要先派活再补格式。**

**第 0 步 · 系统侧准备（你做，开会后尽快）**

你需要准备并丢到群里的材料（缺哪项都会变成 8 人反复问）：

1. **场景规范**：目录必须是 `bench_env/scenarios/<app小写>/<场景名>.json`；附上淘宝 `vip_active` / `new_empty` 两个对照例子，并写明「场景是对统一 Store 的补丁，首页和我的要能看出差别」。
2. **语言/深色接法**：如何加 `strings.en.ts`、如何用现有 hook、深色如何跟系统开关；附「英文尽量短、按钮区允许省略号」两条排版要求；附扫描命令或缺口表（谁缺英文表、谁页面没接 hook）。
3. **任务判定模板**：直接点名可复制的示范文件（如 `CheckoutCartItem.py`），说明判定读 `getState`、要写清成功条件，以及「不做全功能 walkthrough」。
4. **PR 范围说明**：只允许改本 App 目录 + 本 App 场景/任务；禁止 `git add .`；改到 `package-lock` 等公共文件必须先群同步。
5. **（可选）优先级表**：哪些 App 本周先修 721 P0，哪些可以开始接 L1；避免所有人同时既救火又接语言。

**第 1 步 · 负责人认领本周范围**

每个负责人只确认两件事：

- 本周自己哪些 App **先修 P0 主链路**（若 721 点名了，优先）；
- 哪些 App **开始接 L1 的哪几项**（建议最少集：接语言或深色之一 + 1 个场景 JSON；有支付/分享再接跨 App）。

不要默认「一个 PR 把 L1 全接满 + 把所有 P0 修完」。

**第 2 步 · 负责人按规范改代码（交什么）**

| 若本周目标包含… | 负责人应提交的具体产物 |
|---|---|
| 中英 / 深色 | 本 App 的英文表与页面接入；切到 English / 深色后，**首页和至少一个二级页**可看、无大面积重叠（换行需自己收文案或改样式） |
| 多数据 | 至少 1 个场景 JSON；文档或群消息里写清「切换后应看到什么」（例如购物车空、昵称变了） |
| 跨 App / 相册 | 对照示范改本 App 调用；能手走通一条 |
| 任务判定 | 为自己要交付的任务增加/补全 `check_goals`；能说明成功时 store 哪几个字段变了 |
| P0 主链路 | 按 721 回传格式：链路步骤、修前修后、返回路径 |

**第 3 步 · 负责人自检（开 PR 前）**

1. 模拟器里切英文、切深色，看主表面是否崩版。  
2. 若有场景：注入或按你们约定的方式加载后，首页/我的是否**肉眼可区分**。  
3. 若有任务：按任务步骤手走一遍，再跑判定（或说明如何跑）。  
4. `git status` 确认没有误加别人的 App 或整个 `node_modules`。

**第 4 步 · 开 PR / 你合版**

- 负责人开 PR，描述里写清：改了哪个 App、接了 L1 哪几项、场景名、任务名。  
- 你合版时重点看：是否碰到公共层、场景是否真改到 Store、有没有把假交互留在主链路。  
- 小问题（接法写错、目录放错）：你可以直接改或评论指出规范哪一条；**业务对不对**仍回负责人。

### 3.3 出了 bug 怎么派（控沟通成本）

负责人报 bug 时只要：**App 名 + 现象 + 截图/录屏**（不要先猜该谁改）。

你先归类：

| 归类 | 谁改 |
|---|---|
| 时钟/种子错位、相册写了看不见、Intent 打不开、示范模板缺陷 | **系统侧**统一修或出补丁 |
| 本 App 按钮不改 Store、返回错页、英文某句太长 | **该 App 负责人** |
| 同一类问题出现在 ≥3 个 App | **系统侧**出统一修法或脚本，再通知大家套用 |

## 4. 工期粗估（口径）

| 范围 | 粗估 |
|---|---|
| 两示范接满 L1（已做，作参考） | 约 **1 人日**量级可复现路径 |
| 约 20 个 App 只做「接语言+深色 + 1 场景 + 1 任务」且主链路基本可用 | 系统侧协调/出规范约 **2～3 天**；负责人合计约 **20～40 人天** |
| 先清 721 第一批 P0，再叠 L1 | 再加数天到数周，按优先级砍：先可训练主链路，再全量美观与文案 |

会上建议说法：环境能力已具备且示范可证；全量成本取决于各 App 基线质量，以及负责人是否按你发的规范交场景/文案/判定，而不是再造一套 OS。
