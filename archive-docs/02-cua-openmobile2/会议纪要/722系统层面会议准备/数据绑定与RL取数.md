# 数据绑定可验证性 + RL 取数（简析）

> 配合 `README.md`。回答：「任务验证对数据要求高，前端硬编码时我们能不能验出后台变没变？」以及 RL 要拿什么。

---

## 1. 为什么数据是任务验证的前提

任务判定读的是 `__SIM__.getState().apps.<id>`，不是截图像素、也不是 DOM 文案。

因此成立条件只有一条：

> **业务真值必须在统一 store 里，并且交互必须改 store。**

若前端硬编码（列表写死在 JSX、点了只改本地 `useState` / 只 toast），会出现：

| 现象 | getState 看到什么 | 任务判定结果 | 含义 |
|---|---|---|---|
| UI 看起来变了，store 没变 | 字段不变 | **FAIL（正确）** | 抓到「假交互 / 死按钮 / 硬编码 UI」 |
| store 变了，UI 仍显示旧硬编码 | 字段已变 | **PASS（但人眼觉得没变）** | 绑定断了：判定能过、演示难看，需修 UI 订阅 |
| 两边都变 | 字段变 | PASS | 健康绑定 |

**结论：能验证。** 这正是相对「只看屏 / 只看文案」环境的优势——硬编码骗得了眼睛，骗不过 `getState`。  
**展示重点不是「脚本很多」，而是「同一操作前后 diff store」。**

---

## 2. Demo 里建议怎么展示（比空讲规范更狠）

固定三拍（电商加购或记账报销均可）：

1. **操作前**打印 `cart.length` / `bills` 某字段。  
2. **点击**加购或报销开关。  
3. **操作后**再打印同一字段；任务 `check_goals` 断言 `+1` 或 flag 翻转。

口头一句：

> 如果页面把购物车写死在前端、点加购只改高亮，这一步判定会红——我们验收的是后台真值，不是看起来像。

可选对比（若时间够）：挑一个 721 走查里「筛选项只有高亮、结果不变」的反例口述，说明合版前要用任务判定卡住这类问题。

注入场景同一叙事：

- `set_state` 注入 `cart: []` 或 `bills: []` → 再跑同一条任务 → 证明判定吃的是 **可切换的真数据**，不是一份写死的 defaults 幻觉。

> 环境层能力已有：`env.set_state` ↔ `__SIM__.setState`（文档里的 inject_state 即此，不必再造同名 API）。本轮补的是 **命名场景 JSON + 演示用法**。

## 3. 构建侧怎么提前抓「可能验不出」的风险

静态扫描（轻量，不替代任务判定）：

- 页面里业务味 `useState`（`bills`/`cart`/`orders`/`list`/`messages`…）→ 疑似藏业务态  
- `pages/` 里中文硬编码（未走 `res/strings`）→ 多语言与「文案当数据」风险  
- 超大内联数组字面量 → 疑似硬编码种子

运行时仍以 **已有任务的 before/after store diff** 为准；扫描只负责合版前预警。

---

## 4. RL 需要拿的数据（简单版）

对齐当前定位「先可合成 + 任务可判定」，RL 侧最少要能稳定拿到：

| 数据 | 来源 | 用途 |
|---|---|---|
| 每步截图 | trajectory 已有 | 视觉观测（agent 只看这个） |
| 动作序列 | trajectory 已有 | 行为克隆 / RL action |
| **结构化 state（至少 init + 终态； ideally 逐步）** | `get_state` | **reward / success**；不含则只能稀疏人工或 VLM 糊 |
| 任务成功谓词 | 任务 `check_goals`（读 store） | 0/1 或里程碑分的依据 |
| 可重置 + 可注入初始态 | `resetState` + `set_state(scenario)` | 同任务多分布、避免过拟合单份 defaults |
| seed（后续） | RandomService 迁移 | 论文可复现；本轮只口头预留 |

**不需要本轮就交：** 逐步稠密 reward、gym 五元组壳、HTTP 远程 env——那些是 L2。  
**本轮只要证明：** 任务终态能从 store 判定 + 初始态可注入切换 → RL 的 reward 骨架就有了。

---

## 5. 和「验证随任务配套」怎么共存

- 不为全功能写脚本；**每条要交付的任务**必须能回答：成功时 store 哪几个字段必变、哪些必不变（exclude）。  
- 若某任务依赖的字段根本不在 store（硬编码）→ 任务不可交付，先修绑定，再挂判定。  
- 这比「每 app 50 条 walkthrough」更贴合 714 口径，且直接服务 RL。
