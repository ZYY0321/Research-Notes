## 一、结构化状态读出

### 1.1 能力描述

平台提供 `__SIM__.getState()` 接口,可在运行时同步返回一份完整的结构化 JSON,涵盖操作系统层与所有已加载应用的业务字段。该接口不依赖屏幕像素、DOM 快照或数据库外部访问,直接从内存状态管理层导出。

### 1.2 现有产物

在浏览器控制台执行 `await __SIM__.getState()`,以已加载卡皮记账后返回结构为例:

```json
{
  "os": {
    "activeTaskId": "kapi",
    "tasks": [...],
    "locale": "zh-CN",
    "settings": { "darkMode": false, "wallpaper": "..." },
    "hardware": { "battery": 87, "network": "wifi" },
    "providers": { ... }
  },
  "apps": {
    "kapi": {
      "bills": [
        { "id": "b_001", "amount": 32.5, "category": "food",
          "note": "工作日午餐", "reimburse": false, "date": "2026-07-10" },
        { "id": "b_002", "amount": 128.0, "category": "transport",
          "note": "打车报销", "reimburse": true, "date": "2026-07-11" }
      ],
      "categories": [...],
      "_activeBillId": null,
      "monthlyBudget": 3000
    }
  }
}
```

24 个应用均已接入该接口,导出字段与业务语义一一对应。相较于依赖 adb 调用底层数据库、依赖 accessibility tree 抓取 DOM 或依赖屏幕字符串识别的方案,本方案在字段完整性与访问延迟上均具备优势。

### 1.3 判定

**完全做好,24/24。**

## 六、可验证判定脚本(runtime_walkthrough)

### 6.1 能力描述

对每个应用编写一份运行时走查脚本,通过"触发交互 → 读取 store → 断言字段变化"三段式,自动判断应用行为是否符合预期。同一份脚本既可用于构建阶段的自检,也可作为 RL 训练时的奖励函数骨架。

### 6.2 现有产物

以卡皮 W3 断言"点击报销开关后 `reimburse` 计数应加 1"为例:

```python
def w3_toggle_reimburse(page, state_before):
    page.click('[data-action="bill.reimburse.toggle"][data-bill-id="b_001"]')
    state_after = get_state(page)
    r0 = sum(1 for b in state_before["kapi"]["bills"] if b["reimburse"])
    r1 = sum(1 for b in state_after["kapi"]["bills"] if b["reimburse"])
    assert r1 == r0 + 1, f"reimburse count expected {r0+1}, got {r1}"
```

单次执行卡皮走查脚本输出 20 至 30 条 PASS/FAIL 条目,全部通过表示应用复刻质量达标。

### 6.3 现有状态

- 有骨架的应用:5/24(Kapi、Vipshop、Taobao、TaobaoShangou、FanqieTodo)
- 深度到位的应用:2/24(Kapi、Taobao)
- 剩余 19 个应用未编写任何走查脚本

### 6.4 判定

**只有骨架。** 建议先对 5 至 8 个核心应用补齐深度覆盖(每应用 30 至 50 条断言),同时规范化脚本模板并将其纳入应用上线的强制门槛。预计工作量 20 至 30 人天。

## 十三、评测框架与 RL 训练接口

### 13.1 能力描述

`bench_env` 提供环境异步接口,包含 `reset` / `step` / `get_state` / `close`,以及完整的观察对象(截图字节流、当前路由、结构化状态、步索引)、动作词表(15 种动作,已对齐 AndroidControl JSONAction 规范)、五家 agent 适配(autoglm / uitars / gui_owl / gelab / human)。

### 13.2 与主流训练库对接的缺口

主流 RL 训练库(verl、OpenRLHF、RLLib)约定 `env.step(action)` 返回五元组 `(obs, reward, terminated, truncated, info)`。当前 `bench_env.step()` 返回自定义 `StepResult`,缺 `reward` 与 `truncated` 两字段。外部研究者接入需要自行改写训练代码。

**改动方案**:新增 `bench_env/env/gym_wrapper.py`,约 100 行 Python,在 `bench_env` 之外封装 `asyncio.run` 转同步 + `done` 拆分 + 每步调用 evaluate 生成 reward。**不改任何底层代码**。工作量 1 人天。

### 13.3 跨机器训练支持缺口

主流大规模 RL 训练部署形态为"GPU 集群训练 + CPU 集群跑环境",训练端通过 URL 调用环境端。当前 `bench_env` 无 HTTP 层,仅支持单机 Python 内进程调用。

**改动方案**:新增 `bench_env/server.py`,基于 FastAPI 提供 `POST /reset` 与 `POST /step`,内部维护 session_id 到 env 实例的映射池。约 150 行 Python。工作量 2 至 3 人天。

### 13.4 稠密奖励缺口

现有 task 均采用稀疏奖励,仅在任务终止时给出 0 或 1 分。对于超过 5 步的长任务(如"给张三转账 100 元",涉及聊天列表 → 好友页 → 转账页 → 输入金额 → 确认多步操作),稀疏奖励下 RL 通常难以收敛。

**改动方案**:task base class 新增 `compute_reward(obs)` 接口,task schema 新增 `milestones: [{predicate, reward}]` 字段,judge 每步匹配并累加。挑长任务补充里程碑,单页导航任务不加。工作量 5 人天。

### 13.5 判定

**基础接口完全做好,与主流训练库对接的三个薄壳缺失。** 是否投入取决于本轮定位:若面向外部 RL 训练用户则三项均为必做,若仅内部合成轨迹则可延后。

## 遗留问题

以下问题在本次汇报范围内未获得完整解决,列出待跟进:

1. **可验证判定深度不足**:24 个新增应用中仅 2 个应用的 runtime_walkthrough 达到深度覆盖标准,剩余 22 个应用的判定质量距离对外交付水准差距较大。若不投入 20 至 30 人天集中补齐,判定基础设施将成为整个平台对外交付的关键瓶颈。

2. **新增应用的跨应用调用为 0**:平台跨应用框架完备,但 24 个新增应用中无一例真实接入。若仅以现状对外交付,平台的跨应用能力实际上仅具备系统层框架,不具备应用层验证过的真实用例。

3. **随机数不可复现位置数量大**:代码库内散落约 92 处旧写法。在接入 RL 训练前,需要一次集中迁移;若不迁移,同一 seed 下环境初始状态不完全可复现,影响训练可重复性与论文投稿。

4. **英文覆盖不完整**:24 个应用中 8 个应用完全无英文文案,平台的语言切换能力在这 8 个应用上不生效。面向英文研究社区交付时该缺口需要提前补齐。

5. **多场景初始数据不支持**:24 个应用均只支持单一默认数据,训练泛化所需的场景切换能力当前完全不具备。

6. **反作弊断言未启用**:所有现有 walkthrough 均为单向 include 断言,未编写 exclude 断言。若沿用当前判定投入 RL 训练,存在 agent 通过输出巨大点击框或绕过正常流程作弊过关的风险。

## 当前阻碍

1. **规范落地依赖构建流程门槛,而非文档提醒**:观察表明,ESLint 卡住的规范(如禁 `Date.now`)在 24 个应用中 100% 遵守;仅写入 handbook 与 AGENTS.md 但未加自动检查的规范(如多语言硬编码、跨应用调用、三选一原则)频繁被违反。若不将多语言、跨应用、走查脚本、随机数等规范同样纳入构建流程自动检查,后续任何新增能力都会重复"文档写了 → 执行率低下 → 事后集中返工"的循环。

2. **规范补齐存在协作成本约束**:任何需要通知 8 位造应用同学中断当前节奏的改动均需慎重评估。目前的判断是优先选择"仅约束新代码"或"由 AI 自查"的实现路径,避免打断现有开发流。

3. **人工走查流程较长且部分不稳定**:AI 复现人工走查的命中率经卡皮实验实测为 63%,其中 36% 属于视觉审美与产品语义类判断,机器无法替代。走查流程的时长压力短期内无法通过全自动化解决。

## 待决策事项

以下三个问题需要在本次会议(或后续专项讨论中)明确方向,决策结果将直接影响后续开发投入的优先级:

### 决策 1:平台对外交付的定位

三个选项对应完全不同的 P0 集合:

- **选 A:数据合成环境**——用户在环境中自行合成任务与轨迹。P0 集合仅需要走查脚本铺开
- **选 B:通用评测平台**——用户跑分比较模型能力。P0 集合需要走查脚本、gym 接口对齐、反作弊断言、统一 task schema
- **选 C:开源 RL 训练环境**——用户直接接入 RL 训练库跑训练。P0 集合需要走查脚本、gym 接口对齐、HTTP 跨机器、种子重现、稠密奖励

### 决策 2:是否补足构建流程自动检查

若补,可预期新增应用的特性交付率从当前 60% 至 70% 提升至 90% 以上,并使多语言、跨应用、随机数、走查脚本等 P1 特性获得可落地路径。若不补,现有规范执行率维持在当前水平。

### 决策 3:MCP 封装是否等待外部需求触发

将平台包装为 MCP server 以接入外部通用 agent(如 Claude Desktop)的工作量约为 6 至 10 人天。若无明确外部接入方询问,现阶段直接使用 Python 函数调用更为经济。是否投入待外部需求出现后再定。
