## 3.1 A gap in controllable commercial applications

【原文 · 9/11 的 3.1 整节】

Mobile agents are moving from system utilities and open-source clients into a larger commercial application world. Travel booking, online shopping, personal finance, and local services are the settings agents need to cover. To scale training and evaluation in these settings, an environment must support diverse applications, repeatable execution, and outcomes that can be checked directly.

One path runs real applications on physical devices, gaining interface and network fidelity but making state difficult to reset or parallelize and introducing real-world side effects. The other runs reproducible applications in a controllable environment, making reset and evaluation straightforward but often concentrating on system utilities and open-source clients. Existing work has advanced mobile GUI interaction, controllable state, and cross-application tool use separately; our focus is to place mock commercial applications, resettable business state, and terminal checks in one mobile environment.

MobileGym++ is a browser-hosted mobile environment that carries commercial workflows in controllable mock applications. It contains 64 installable applications, 35 newly built in this round, spanning travel, shopping, finance, content, social, office, and local services. Goods and orders, expenses and budgets, itineraries and changes are live objects in the applications' own stores: actions on the screen change them, and tasks end by checking the resulting business state. The runtime extends MobileGym, inheriting serialization, reset, inter-app navigation, and programmatic evaluation while expanding the application content, domain coverage, and in-app calling channel.

## 3.2 35 high-fidelity commercial applications

【原文 · 9/11 的 Platform and expansions 整节】

Platform and expansions

The predecessor already supplies a complete controllable runtime. The device runs inside a browser tab; each app keeps a structured store and renders its UI from that store; the clipboard, system broadcasts, and inter-app navigation already connect apps; the full device state can be exported as one record and restored from it; many instances can run at once without interfering. On the agent side, observations remain screen pixels. There is no accessibility tree, and the agent cannot read the business store. Actions remain discrete taps, swipes, typing, and navigation; at most one action executes per step.

On that same runtime we expand the domain coverage of reproducible commercial clients and open an in-app function channel in a subset of applications. Newly built apps reproduce a business loop rather than a skin: the object model and state transitions are fixed first, then the business functions and pages are implemented around them. Goods and orders, expenses and budgets, itineraries and changes, conversations and messages are maintained as application state, rendered by the UI, and checked at task termination. Each app is walked through by a human and exercised by automated regression before it is used for tasks. The function channel is described in Section 3.4.

【原文续 · 9/11 的 Scale, depth, and coverage 整节，深度和表留在 3.2】

Scale, depth, and coverage

The environment ships 64 installable applications, 35 of them newly built commercial clients, organized by the seven domains above. Each domain carries a different object type and a different terminal form---placing an order, posting a ledger entry, creating an itinerary, sending a message, adding a favorite---so the same checker template cannot cover them all.

Count alone is not enough; each app must be deep enough to carry a multi-step task. On the newly built clients, the median navigation declaration is 37 routes, 175 interactive actions, and 88 transitions. As a depth reference, the thickest application in MobileGym has 100 routes and 265 actions, and its deepest terminal takes 7 steps to reach. Median interaction depth from the root in this environment is 3: the shortest GUI path of a typical task already crosses several layers, and the step-count lower bound comes from page structure rather than from the length of the instruction. ## 3.4 Hybrid GUI and app-native tool use

【原文 · 9/11 的 In-app tools 整节】

In-app tools

Agents can use both graphical actions and function calls in the same environment. MobileGym++ places the two channels on the same application state, so a task can move between them while preserving the same business objects. GUI-only remains a complete setting; Hybrid supplies another route through the same world.

Approximately 52 applications expose a function interface under their own namespace. A call is available when its application is in the foreground and occupies the same action slot as a tap, swipe, or text input; at most one action executes per step. The functions act on the application's business state. They cover selected business operations, while saving, payment confirmation, password entry, and contact selection may still return to the GUI. Prefill calls create drafts, and the final business write is checked in the same store as a GUI write.

A mixed workflow can therefore switch between applications: the agent first obtains task information from one app, completes a GUI operation in another, and returns to the first app for an exposed business operation. GUI-only and Hybrid use the same task, initial state, and terminal check, allowing the two completion paths to be compared directly.

【改成 · 现在 3.4 整节】

Hybrid GUI and app-native tool use

GUI-only is already a complete setting. To support longer-horizon study we additionally open an app-native function channel on the same application state, so when to use the interface, when to call a function, and how to return to the interface for confirmation can be examined in one world. Hybrid is another completion path, not a requirement.

Approximately 52 applications expose a function interface in the foreground, occupying the same action slot as a tap, swipe, or text input. Functions are a subset of GUI-reachable operations: prefill creates a draft only, while saving, payment confirmation, passwords, and contact selection return to the GUI. Tools are used mainly to locate and organize structured information; both channels write the same state.

## 3.5 MobileGym++ Bench

【原文 · 9/11 的 Programmatic checks 整节】

Programmatic checks on business state

A task binds an initial state; at the end we diff the full device state and check whether the target business fields were written as required. The checker depends on neither a model judge nor a single reference trajectory: different routes that accomplish the same write are equivalent. It reads the app's own business store, so an order, ledger entry, itinerary, or message can directly be the task terminal.

Checks are written as relations, not as constants. An expense amount can equal the payment that just completed; a calendar title can contain the selected train number. Constants appear only in the initial state. A cross-application task carries information from one app's live business state into a related business operation in another app, so the checker can verify the relation between the two stores.

【原文续 · 9/11 的 Benchmark 整节】

Benchmark

Existing mobile-agent benchmarks cover many single-app GUI operations and increasingly include cross-application workflows and tool interaction. MobileGym++ Bench focuses on business workflows in resettable mock applications: tasks require locating, selecting, confirming, and writing back, with the result landing in an application business object. Cross-application tasks additionally carry live information from one app into a related operation in another.

Tasks are organized around executable user goals and checkable terminals. Core tasks close with a business operation such as placing an order, posting an expense, creating an itinerary, sending a message, or modifying an app object. Task length comes from locating, filtering, confirming, paying, and writing across apps, rather than from unrelated steps. Instructions use user-goal language and do not name widget labels, tool namespaces, or checker fields.

In a cross-application task, the value needed for a write is present in another app's live state rather than written as a fixed constant in the instruction. The agent must identify the source, carry the value across the app boundary, and write it into the correct field; the checker verifies the relation between the resulting business fields.

GUI-only is a first-class setting. Every task has an executable GUI path, while Hybrid provides another route through the same world and is evaluated by the same checker. Difficulty comes from application hierarchy, distributed information, constraint combinations, and cross-app write-back. Single-app long chains require locating and filling fields across deeper pages; cross-app tasks additionally require carrying and writing the retrieved value.

Each task has three parts: a natural-language user goal, a bound initial state, and a programmatic terminal check. The checker reads the before/after business-state diff, does not read the trace or screenshots, and does not accept an agent's claim of completion. Allowed state paths are declared so that other mutations can be reported separately from success.

The task set contains approximately 200 tasks organized by the seven business domains. Single-app, cross-application, and messaging tasks are distributed across multiple applications and business objects, so evaluation is not dominated by a handful of apps.

The primary metric is task success rate. GUI-only and Hybrid are evaluated on the same tasks, initial states, and terminal checks. Mean steps on successful trajectories measure interaction efficiency conditional on completion; because failed trajectories often reach the step cap, we also report the success rate and the fraction reaching the cap to separate efficiency from reliability.
