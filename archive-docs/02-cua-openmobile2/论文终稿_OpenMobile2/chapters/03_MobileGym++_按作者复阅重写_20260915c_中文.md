## 3.1 可控商业应用的缺口

移动智能体正越来越多地走向真实商业应用上的现实工作流，例如在携程上订行程、在淘宝上购物，这类任务往往跨度较长、贴着真实用户需求。然而，面向这类商业应用的训练与评测环境仍然明显缺位，智能体很少有机会在真实的移动使用场景中练习和被评测。

基于真机或安卓模拟器的路径会碰到登录、重置和现实副作用等问题，难以支撑大规模训练；已有的仿真应用工作则往往只覆盖一小部分商业应用，也很少同时提供可重置的业务状态~\citep{rawles2025androidworld,kong2025mobileworld}。

我们构建了 MobileGym++：一个在浏览器中运行的移动环境，在可控的仿真应用中承载商业工作流。运行时扩展自 MobileGym~\citep{wu2026mobilegym}，保留其在重置和程序化评测上的优势，同时大幅扩展领域覆盖、应用数量与丰富度，以及对真实跨应用工作流的支持。观测仍然只有屏幕像素，环境不提供辅助功能树，智能体不能读取业务状态；设备状态可以导出、恢复，多实例可并行运行。本轮我们新建了 35 个商业应用，连同前作一共 64 个即可使用的应用，覆盖出行、购物、财务、内容、社交、办公和本地服务七个领域。每个应用维护一份业务状态，例如订单、预算和行程；这些状态随交互变化，任务据此核验所得结果。

## 3.3 真实的跨应用工作流

同一台可重置设备上安装着多个商业应用，它们各自维护一份活的业务状态：购物应用里有商品和订单，记账应用里有支出和预算，日历里有行程与改签，通讯录里有联系人和地址。这些对象随屏幕上的操作实时改变，并在设备状态中留下痕迹。

剪贴板、系统广播和应用间导航把这些应用连接起来。一条工作流可以离开当前应用、进入第二个应用，并在第二个应用中改写它自己的业务对象：购物应用中完成一次支付，可以在记账应用中生成一笔对应的支出；日历里选定的车次编号，可以进入行程应用参与改签；联系人里的一个地址，可以被带入下单流程。第二个应用的业务状态因此发生真实写入，而不仅是接收消息。

跨应用推进的每一步都作用在同一份可重置的设备状态之上，因此同样的工作流可以反复重放。

## 3.4 Hybrid GUI 与应用原生工具使用

纯 GUI 已经是一个完整的设置。为面向更长期的研究，我们在同一份应用状态上额外开放一条应用原生函数通道，使「何时用界面、何时调接口、调用后如何回到界面确认」可以在同一个世界里被检验。Hybrid 是另一条完成路径，不是通过条件。

约 52 个应用在前台暴露函数接口，与点击、滑动、输入占用同一个动作槽。函数是界面可达操作的子集：预填只出草稿，保存、支付确认、密码和联系人选择仍回 GUI；工具主要用于定位和整理结构化信息，两条通道写入同一份状态。

## 3.5 MobileGym++ Bench

现有移动智能体基准已经把单应用的界面操作评得相当充分，也越来越多地加入跨应用工作流和工具交互~\citep{rawles2025androidworld,kong2025mobileworld}。MobileGym++ Bench 关注智能体能否在可控商业环境中办完长程、真实、跨应用的商业任务。任务的难与真都不来自人为堆步数，而来自业务本身：所需信息分散在若干应用当时的业务状态里，约束需要组合满足，完成的关键值要跨应用带过去写回。

**任务设计。** 任务围绕可执行的用户目标和可检查的终态组织。核心任务以一次业务操作收束，如下单、记账、建立行程、发消息或修改应用对象。该操作的结果落在应用自身的业务状态里。单应用任务要完成这次写入，仍需穿过较深的页面层级去定位和填写。题面用用户目标表述，不点出控件文案、工具命名空间或检查字段。

跨应用任务中，写入所需的值存在于另一个应用当时的状态里，而不是作为固定常数写在题面里。智能体必须识别来源，把值带过应用边界，并写入正确字段；检查器验证所得业务字段之间的关系。

**规模与构成。** 当前任务集包含 215 道任务，覆盖七个业务领域。其中 109 道任务涉及一个应用、74 道涉及两个应用、27 道涉及三个应用、5 道涉及四个应用。任务分布在多个应用和业务对象上，评测不会被少数应用主导。

**评测协议。** 每道任务由三部分组成：自然语言用户目标、绑定的初始状态和程序化终态检查。成败由程序化检查器判定：它读取应用业务状态在任务前后的差分，不读取轨迹或截图，也不使用模型裁判；不同路径完成了同一次写入，视为等价。允许变化的状态路径会被明确声明，其余变更与成功分开记录。主要指标是任务成功率。GUI-only 和 Hybrid 在同一批任务、同一初始状态和同一终态检查下评测。成功轨迹的平均步数衡量在完成条件下的交互效率；由于失败轨迹通常会达到步数上限，我们同时报告成功率和达到步数上限的比例，以区分效率与可靠性。
