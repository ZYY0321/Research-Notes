# 对组内几套出题与验证方案的看法

组内目前有四套与出题、验证相关的方案或建议：以真实材料构建角色环境再出题的方案（刷榜方向），以工作流加编码智能体批量造题的二阶段管线（造数据方向），任务结束后接入智能体检查的验证建议（框架方向），以及证据不足记空值、过难的判据拿掉的评估修复（测评方向）。本文逐一说明每套方案的要点、我们认同的部分、放到 Photoshop、Mail、Figma 这类应用上会遇到的问题，以及需要向方案作者确认的事。结论先写在这里：四套方案的方向与我们的观察一致，可以直接借用的是「读取与判定分离」「评分器上线前先被测试」「证据不足记空值」三条原则；需要补上的是归属检查、过程记录，以及商业闭源应用上状态读取这一步。

## 一、以真实材料构建角色环境再出题

**方案要点。** 先收集软件文档、操作教程和真实材料，由智能体构建一个有背景、有历史、信息自洽的角色工作环境，例如一个财务专员的电脑里不只有一张待填的表格，还有交易记录、费用政策、往来邮件和历史台账；再由智能体在这个环境里寻找真实的工作需求作为任务。评分拆成读取器和判定器：读取器读应用状态和已保存的结果，能精确计算的用确定性代码判断，需要理解表达或视觉内容的才交给模型裁判，并且必须有客观标准。读取器和判定器写完后，由独立的智能体用七类样例测试：正确结果、合法等价写法、未完成的初始状态、漏掉一项关键要求、数值正确但对象关联错误、使用旧版本或破坏应保留的内容、状态不可读。成功的初始化、读取器和判定器脚本放入素材库复用。会上报告的结果是误判率控制在 5% 以内，DeepSeek 两批的平均步数分别约 63 步和 39 步，但难度偏低、准确率偏高。

**我们认同的部分。** 读取与判定分离、评分器上线前先被独立测试、成功组件进素材库复用，这三条与我们这周的结论完全一致，可以直接作为我们入库检查的骨架。任务从环境中长出来、而不是从功能清单逐项翻译，也正好对应二阶段批量造题时「规模一大就模板化」的问题。

**放到我们的应用上会遇到的问题。**

1. **七类测试里没有归属这一项，而角色环境会放大归属风险。** 七类测试中的「初始状态」检查的是什么都没做的环境，没有检查「环境里原本就有一份合格结果」的情况。角色环境刻意加入历史文件、旧邮件、历史台账，环境里原本就存在合格结果的可能性比空白环境更大。我们在 Mail 上已经实测过：邮箱里原来就有一封合格的草稿，模型什么都不做，评分就是 1 分。建议补一类测试：在环境中预置一份合格的旧结果，不做任何操作，评分必须判为未通过；或者在题面中写入本次运行独有的内容。
2. **方案依赖的前提是状态能读，而这一步恰好是商业闭源应用的难点。** 方案收集的材料涉及的应用多数是开源软件，例如 GIMP、Shotcut、REAPER、MuseScore、FreeCAD、KiCad，文件格式公开，读取器容易写。Photoshop 的部分文档状态要在应用运行时通过脚本接口查询，Figma 的组件、原型和评论在云端，Mail 的草稿在服务器上，读取器要按应用分别实现。我们整理的各应用可取状态可以直接给这套方案用。
3. **读取通道要与智能体可用的工具分开。** 方案提到把可验证的沙盒交互整合为专门的 MCP。如果被测智能体也能调用同一个 MCP，任务就可能退化成「读一下就做完」，这也是会上「全靠 MCP 就能做完的任务偏简单」那条意见的另一面。读取通道应当只给评分方。
4. **难度问题的两个原因可以一起解决。** 方案自己发现了难度下降的原因：角色构建时把本该由智能体判断的内容直接写下，例如日历里哪个时段有空，任务就变成照着执行。方案也指出了冲突：题面写简单、评分写严，误判会增多。我们的看法是，误判增多是因为评分检查的是一个具体取值（例如「15:00」），而题面只给了一个要求（例如「找一个空闲时段」）。只要评分检查的是要求本身，即由读取器从同一个环境中算出所有满足要求的取值，再判断模型的结果是否落在其中，并用多种合法取值作为等价做法测试评分，题面就可以写简单，误判也不会增多。
5. **用于训练数据时还需要过程记录。** 作为评测，只看结果即可；作为训练数据，还要知道轨迹是怎么做的。方案用带终端的智能体采集，轨迹中会有相当一部分走命令行，需要按事件记录标注路线，并检查答复是否如实说明了手段。

**需要确认的事。** 5% 的误判率是在什么样例上测的，是人工判定还是另一个模型判定，是否包含假阴性；七类测试是否计划补上归属；读取器 MCP 是否对被测智能体可见；素材库里已有的读取器是否覆盖 Photoshop、Mail、Figma。我们这边的 23% 是对抗构造的伪造产物被放过的比例，与 5% 不是同一种量，不能直接比较。

## 二、以工作流加编码智能体批量造题的二阶段管线

**方案要点。** 给定每个应用的工作流，由编码智能体结合工作流和文件系统，生成较高层次的业务任务，例如把 SVG 转成演示文稿并结合表格中的信息。小规模的 8 道质量不错，扩到 200 道后变得模板化，任务也偏简单。方案作者认为原因在于现有功能集成的能力有限。让智能体先在环境中探索再出题也考虑过，但现有的模型服务不能直接接收文件，需要在环境里探索，速度慢，所以暂时没有采用。

**我们的看法。**

1. **模板化需要先能测量。** 判断两道题是否同质，不能只看题面措辞，应当看它们的操作序列和证据字段是否相同。我们第二轮出题时同质题只做了标注、没有删除，「不同功能的题数」因此虚高。建议对 200 道题按「用到的功能组合 + 证据字段」去重后再看实际数量。
2. **多样性的来源可以借用上一节的角色环境。** 工作流是固定的，从固定工作流生成，规模越大越容易重复；不同的真实材料和角色背景会带来不同的需求。两套方案可以结合：工作流决定功能覆盖，角色材料决定任务内容。
3. **探索的成本可以放在离线一次完成。** 不必每道题都让智能体探索环境。可以每个应用离线探索一次，产出这个应用的可取状态清单和可复用的读取器，之后批量出题时直接引用。这样既能出「先查状态再判断」的题，又不增加每道题的成本。
4. **入库检查同样适用。** 这套管线是否同时生成评分和自检用例，评分出自哪个模型，有没有空跑和预置旧结果检查，都可以用《出题规格与入库检查》第六节的问题对照。

**需要确认的事。** 管线是否生成评分；200 道题涉及哪些应用；「功能集成的能力限制」具体指什么，是工具不够还是模型不会用；今天如果分享这套技能，最好能看到几道生成的题和对应的评分。

## 三、任务结束后接入智能体检查

**建议要点。** 任务结束后接一个智能体进入环境检查结果，或者在关闭应用之前加一段脚本读取应用当时的状态，再交给模型判断。Figma、Blender 这类应用有官方接口，可以参考。

**我们的看法。** 这条建议里其实有两种做法，成本和可靠性不同。第二种「关闭前用脚本读取状态再交给模型判断」，就是第一节的读取器加判定器，结果可复现、成本低，应当作为首选。第一种「每条轨迹都接一个智能体去检查」，能处理事先没有写好读取器的情况，但每条轨迹都要多跑一个智能体，结论不完全可复现，还会受到被测模型自述的影响。比较好的分工是：让智能体在离线阶段探索环境、为每一类任务写出读取器，批量评分时运行确定性的读取器，只有读取器覆盖不到的部分才在收工后交给验证智能体，而且它要满足只读、不看自述、逐条给证据、允许弃权这几条要求。

还要说明一点：会上提到 Figma 的状态都和 MCP 连着，我们实际验证的是 Figma 的只读 REST 接口，节点树和评论能读到；MCP 这条路还没有测。

**需要确认的事。** 框架能否在被测模型收工后、虚拟机销毁前插入一个读取或验证步骤；读取结果和验证记录能否随轨迹回传。

## 四、证据不足记空值、过难的判据拿掉

**方案要点。** 测评方向修复评估链路时，证据不足的记为空值，不计为失败也不计为成功；评估器误判时保留原始分数并标注，不计入模型能力；有一些判断价值低、又太难评的判据直接拿掉；同一个模型裁判重复判两次，结果可能一次空值、一次成功。

**我们的看法。** 空值单列、误判保留原分并标注，可以直接沿用，我们的六种评分结果类别就是在这个基础上细分的。拿掉判据时要同步修改题面，否则就会出现「题面写了的要求评分没有检查」，在训练数据里这等于告诉模型这条要求可以不做。模型裁判重复判断不一致，说明校准时除了假阳性和假阴性，还应当报告同一条轨迹重复判断的一致率。

**需要确认的事。** 拿掉判据的任务，题面是否同步修改。
