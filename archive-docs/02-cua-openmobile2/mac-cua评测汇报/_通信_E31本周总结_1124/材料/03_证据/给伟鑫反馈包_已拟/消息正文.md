**1. Mail：评分和清理用的 AppleScript（`osascript`）在集群虚拟机里一直超时（需要你们帮忙查原因）**
- 背景：Mail 草稿题的评分，是用 `osascript` 去读草稿箱里有没有这封邮件；题开始前，准备脚本也用 `osascript` 清理旧邮件（"清理脚本"见下）。
- 现象：5 道草稿题（run `run-3ecd969052324da7817c87e8505e4f31`，main 环境）模型都在 Mail 里写好并存进草稿箱了，评分却是 0。5 份评分记录内容一样：`reason=applescript`，`error=TimeoutExpired`，`records=0`，`reads=4`。评分代码每次读草稿最多等 15 秒、总共最多 60 秒（约读 4 次），`reads=4` 说明 4 次都超时，一次没读到。
- 准备阶段也是：探针 run（`run-b399a4cb1cea44d9bbd832908f0434ee`）的准备日志是 `e31-mail-clear attempt=1/2 error=TimeoutExpired`（见附件）。我们抽到的其他 Mail 题准备日志也是这样，但没有逐批统计，请以探针为准。
- 涉及的批次（都在 main 环境）：评分超时的直接证据在 `e31-ds-sfb-v2-mailfigma-main-1123`（`run-3ecd969052324da7817c87e8505e4f31`）；最干净的复现是单题探针 `e31-probe-main-mail-1123`（`run-b399a4cb1cea44d9bbd832908f0434ee`，题 `mail-draft-save`），建议先看这个。另外 `e31-ds-sfb-gen-mailfigma-main-1123`（`run-7ff26b2d562d4f059f4a833efab2e128`）和 `e31-ds-sfb-gen-mail-rest-main-1123`（`run-43d4603421e44beab675cb5ea3209df7`）里的 Mail 题也是 0 分，但评分原因没拉到，不能算已证实。
- 对照：同一道题在我们自己的生产 Mac 上评分是 1 分、`osascript` 读草稿正常，所以问题在集群虚拟机，不在题。
- 清理脚本是什么：每道 Mail 题开始前跑一段 AppleScript，删除所有账户的草稿箱和已发送里主题含 "E31" 的邮件（别的不动），跑 2 遍，每遍最多等 60 秒，中间隔 12 秒。目的是让每次起点干净，评分不会读到上一次留下的草稿。
- 我们的猜测（没验证）：虚拟机里第一次用 `osascript` 控制 Mail 会弹 macOS 自动化授权框（"osascript 想控制 Mail"）或被隐私权限拦住，没人点，调用就卡到超时。
- 请你们在一台 main 环境的虚拟机里查三步：① 运行 `osascript -e 'tell application "Mail" to get name of every mailbox'`，看是秒回、卡住还是弹框；② 运行 `sqlite3 ~/Library/Application\ Support/com.apple.TCC/TCC.db "select client,service,auth_value from access where service='kTCCServiceAppleEvents'"`，看有没有对 Mail 的授权；③ 如果是授权框，能不能在镜像里预先授权。
- 还有一点不确定：另外 7 道 Mail 草稿题也是 0 分，但我们没拿到它们的评分原因，不能算已证实是超时。
- 我们自己做：邮箱账号由我们自己准备，不用你们管；Mail 草稿题在你们查清之前先只在生产机上跑。
