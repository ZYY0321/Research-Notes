# 周五讨论前的补充：漏了什么、周会怎么接、先做什么

## 先说结论：四块之外漏了两头，周会里有四处没承接

**漏的上游：这批数据到底要教什么行为。** 四块都在问"数据是否可信"，没有一块问"目标行为是什么"。周会上这是个活的分歧。

- 晨阳造数据时在任务上加模板，"限定它 CLI 为主，CLI 解决不了再用 GUI"。
- 一晨却说："如果他所有操作都可以在 MCP 或者用 click 的办法就做的话，相对来说这个任务就比较简单，或许我们后面做数据的重点也不是在这个方向。"
- 你们的成对题复盘是同一件事的证据：脚本直写，被堵的版本也满分。

路线策略不定，"用脚本算不算好轨迹"就没法回答。难度也属于这一头，周会后半段几乎都在谈它，你们的材料只在"阶段二方向"带了一段。

**漏的下游：训练反馈。** 晨阳说第一阶段"这一周就做一个收尾"，理由是数据"已经涵盖的已经足够多，也足够全"，而且已经在 3.8 上训练测试（39 个任务完成 7 道，"有一些工具它会调用错误"）。你们的材料却说可评分题每道都能被伪造骗过、归属没人查。两边对同一批数据的判断是冲突的。材料里也没有一条证据说明这些质量问题进训练后有没有害。mentor 很可能第一句就问这个。

**周会有、材料没接的：**

1. **mock 路线。** 彭创的 Electron mock 同时碰到你们三块问题：账号、并发、状态可读（"用后端的网页状态……也是一个过程级的"评测）。《应用环境与账号》只写了"飞书暂不生产"。
2. **MCP 读状态。** 一晨建议任务结束、关应用之前"自己加一个 script 去获取它当时的 state"。你在会上说"figma 应该挺好做，因为它所有状态都跟 MCP 连着"。验证文档只写了 REST。这条还是挂在你名下的 action item。
3. **泽豪的难度发现，和你们"题面每条要求对应一条判据"正面相撞**（见出题一节）。
4. **评测集要跟着你们的题走。** 鸣谦说后面扩 Figma、Photoshop、飞书，"跟着晨阳那边造数据去走"。训练题和评测题同管线、同评分器，评分缺陷会一起继承。

另外两点小的。陈瀚在会上没有发言，只有晨阳转述和周会材料里的署名项，别当成他的表态引用。AI 纪要把 PS 写成"产物存储在云端"是错的，你们文档的说法（状态在应用内，靠脚本查）才对，别被纪要带偏。

## 一、出题

**立场。** 取证方式在写规格时就定。出题、评分、正反例分角色。入库前过五项检查。

**周会怎么接。**

- 晨阳的第二阶段：小规模 8 道"质量还是 OK 的"，扩到 200 道就"比较模板化……也是比较简单的"。让 agent 进环境探索出题"比较慢"，所以没走。
- 泽豪找到了变简单的机制：角色构建时把该由 agent 判断的东西直接写明，任务"变成只需要按照这个指令写出来的方法进行执行"。
- 泽豪也点出了冲突："如果题目上写得简单一点，评分上做严格的话……误判的一些情况就会增多。"

**可能调查不周。**

- **"题面与判据一一对应"没区分要求和取值。** "找个空闲时间开会"是写明的要求，具体哪个时间应该由评分器从环境算，不该写进题面。不做这个区分，你们的原则会被读成"题面写得越细越好"，正好是泽豪要改掉的。
- **"先约束还是先覆盖"可能是个假二分。** 115 道不可评分是相对当前读取能力说的，MCP 接通后 Figma 那部分可能直接变。
- **成对题停了，但"察觉受阻并换路"没有替代方案。** mock 的后端过程校验可能就是。
- **数字口径自己打架。** 可评分题数在几份材料里是 81、86、107，总题数是 196、227。你们自己写了"对外只引用清单上的数字"，周五之前先自己做到。

**证据。**

- **读材料（问泽豪）：** "误判率 5% 以内"是怎么测的，在什么样例上测的，七类测试里有没有归属这一类。它和你们的 23% 不是同一种量，不问清楚会被拿来直接比较。
- **小实验：** 取十道泽豪式"留给 agent 判断"的题，评分器从环境状态推期望值，跑七类样例加归属测试。这直接回答"降低题面明示度会不会抬高误判"。
- **小实验：** 挑十道 Figma 不可评分的核心功能题，试接 MCP 读取，看多少能变成可评。它决定"偏向易验证功能"这个代价是否真的存在。

**建议与改口条件。** 取证方式是规格的必填字段，但不拿来筛功能。写不出取证的进"待读取器"清单，不进训练包，也不计入覆盖数。如果 MCP 实验读不到关键状态，就得接受一阶段分布偏斜，把这些功能留给 mock 或人工。

## 二、环境与账号

**立场。** 账号方案先于出题。环境故障记空值。偏离题意的绕行判未完成。每条轨迹记后端和框架版本。

**周会怎么接。**

- PS 并发，晨阳的态度比你们松："任务量如果没那么多的话，其实也是能接受的。"
- 飞书有反例。一晨："我在本地跑的时候……保存下来，发现也可以，但也有可能是因为我没有跑并行。"晨阳转述陈瀚"可以一直挂着"，代价是状态"会一直累积"。所以飞书的真问题是登录态和环境重置二选一，不是文档写的"登录无法自动化"。
- 3.0 的弹窗有两条相反的信息。一晨说权限弹窗"现在应该是有一个提示"，又说鸣谦发现"一些弹窗在 3.0 这个版本里没有办法被操作"。
- 广文杰和一晨的观察支持"后端改变行为"：新版 driver 的 CUA "一直能成功，所以它就一直试下去"，旧版"试一下就容易失败了，就转而用另一种"。
- 林强要按晨阳的模板改 skill 描述，这又是一次版本变化。

**可能调查不周。**

- **没区分两种障碍。** 授权框、登录窗是真实用户也会遇到的，正确行为是处理它或如实报告。团队被锁、driver 点不到是我们环境独有的。前一种如果 3.0 能看见，就从缺陷变成可教的场景，"把输出目录移出桌面"反而删掉了它。
- **版本记录少一项。** 应该加上提示词模板和 skill 版本。周会说明路线主要是被 prompt 拉动的。
- **mock 的代价没评估。** 彭创自己承认 AXTree"比真实 APP 要稍微简单一点"，任务"难度还不太够"。
- **未登录 PS 在集群能做什么，** 你们自己写了没测。

**证据。**

- **小实验：** 用 3.0 重跑 PS 存桌面的几道题，看授权框能否被看见和点击，结束通知进程的行为是否消失。它决定这类绕行是该过滤还是该修环境。
- **小实验：** 飞书挂机不重启，加开跑前基线，跑十道，看登录能撑多久、累积状态是否干扰评分。
- **小实验：** 同一模型同几道题，在 mock 飞书和真飞书各跑一遍，比失败类型。这决定 mock 数据能不能当训练主力。

**建议与改口条件。** 每个应用在三条路里选一条：账号隔离、挂机加基线、mock。飞书走 mock，但留一小组真飞书题检验迁移。"改在他人文件里完成"判未完成，团队被锁的那次运行记环境阻断，不记 0。如果 mock 与真应用的失败类型差得远，mock 就只能当跨应用长任务的补充。

## 三、结果验证

**立场。** 按结果存放位置取证。评分器两个误判方向都要测。归属单独验证。裁判限用并校准。原始产物必须留。

**周会怎么接。**

- 晨阳承认过滤"就是根据它的 verify 结果"，而 verify"判定过宽"。
- 一晨给了三条路：轨迹中间状态交给 agent 判、视频抽帧、MCP 取状态。
- 你当场反驳了第一条："它以为它执行了，然后实际上没执行成功，但他在轨迹里说他已经执行了。"这和公开研究的结论一致，站得住。
- 泽豪引 OSWorld 的做法，"让任务最后提交一个产物出来"。这和你们"保存是自然一步才可改题"的原则有张力。
- 鸣谦那边是反向操作："有一些 rubric 可能觉得它太难，我们就直接拿掉了。"她还提到同一裁判判两次，结果一次成功、一次像是 null（转写为"闹"，我按 null 理解）。

**可能调查不周。**

- **MCP 是把双刃剑。** 评分器能用它读，agent 也能用它写，那题目就退化成一晨说的"比较简单"的那类。读取通道和 agent 可用工具要分开讨论。
- **归属只提了基线，也承认基线能被改，但没给出路。** 便宜的做法有两个：基线存在虚拟机之外；题面内容带本次运行的随机串，旧结果天然不合格。
- **真实假阳性率其实手头有一个估计。** Figma 41 次通过里 9 次与题面不符，只是人工只看了 3 张。
- **验证文档对剪映说得偏满。** 文档说抽帧"能核验大部分剪辑类要求"，你自己在会上说转场"只检查最终导出的视频文件，是难以检查的"。
- **单色误杀靠逐题写豁免，扩不了量。**
- **鸣谦拿掉判据时题面有没有同步删，** 否则就是在制造你们说的"题面写了、评分没查"。

**证据。**

- **读已有材料：** 把 Figma 那 41 张人工看完。这是最便宜的真实假阳性数，决定对抗审计的结论要不要打折。
- **小实验：** 在 Mail 草稿题上加随机串，重跑原来的三种情形，看预置旧草稿是否归零。
- **小实验：** 接 Figma MCP 读一条评论、一个组件，确认能读、能和基线做差。这也是周会的 action item。

**建议与改口条件。** 收录分两级。状态读取加归属通过的，进主训练集。靠裁判的单独打标，校准前不当成功标签。只显示在屏幕上的状态不单独成题。如果人工复核后真实假阳性很低，优先级从防伪造转到归属和误杀。

## 四、轨迹质量

**立场。** 未说明手段的，改写答复后可收。迎合评分的判未完成。遮盖要先能定位。质量信息随轨迹交付。

**周会怎么接。**

- 晨阳说过滤的两个问题"已经是解决了"，loss mark 也开始支持。也就是遮盖的管道有了，瓶颈只剩你们说的定位不稳。
- 鸣谦对 DeepSeek 的描述对应你们的第四类：遇到异常"就会一直重试，导致超时……两极分化"。
- 她还提了一类你们没有的：模型"只返回了推理，就是没有工具调用"，框架提前退出。这算模型问题还是框架问题，会影响它记 0 还是记空值。
- 一晨说 DeepSeek"非常喜欢用那个 GUI"，晨阳说"只能通过 prompt 来拉回"。

**可能调查不周。**

- **这一块证据最弱。** 规模数字几乎全是模型标注，而标注三次结果不一，换判断模型后合格数差一大截。"推断评分"明确写出来的只确认了一例，别把它讲成一大类。
- **改写答复有副作用。** 推理里写着"不必提及"，答复却交代了，会训出推理和答复矛盾的样本。要改就把那段推理一起遮盖。更省事的做法是这类题只收本来就如实说明的模型的轨迹。
- **晨阳"已解决"的是哪两类问题，** 和你们六类怎么对应，没问过。
- **路线没进必填字段。** 一批"GUI 数据"里多少其实是 CLI 轨迹，现在答不出来。

**证据。**

- **人工金标：** 分层抽一百条左右（应用、模型、路线），人工标是否完成、归属、是否如实说明、首个出错步。这一份同时校准评分器、裁判和标注，是整份材料最缺的东西。
- **训练对照（要晨阳配合）：** 同一批数据原样、遮盖、过滤各训一个小规模版本，看是否如实说明和重试行为有无差别。
- **读材料（问晨阳）：** 平台现有过滤规则，以及一阶段哪些批次已经进了训练。

**建议与改口条件。** 生产方只把硬门槛：完成、归属、未偏离题意。过程类问题作为标签交付，由使用方取舍。未说明手段的先隔离，不急着批量改写。如果训练对照显示过程瑕疵对行为没有可见影响，这块就降级成只打标签，精力还给验证。

## 最该先做的 3 件事

1. **人工看完 Figma 那 41 张，顺手抽几条 Mail 和 PS。** 当作金标集的第一片。周五就能拿出一个人工确认的真实假阳性数，而不是模型标注的。
2. **做 Figma MCP 读取加随机串归属的半天小试。** 它同时回答三件事：不可评分题能救回多少，归属怎么解，周会的 action item。
3. **周五前各问晨阳、泽豪一个问题，并把题数口径统一成一份清单。** 问晨阳：哪些批次已进训练，过滤规则是什么。问泽豪：5% 怎么测的，有没有归属测试。否则 mentor 一追问，口径先乱。
