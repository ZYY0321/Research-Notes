- Figma「团队被锁、改去别人稿子里画」只出自 11-23 那批，11-24 复跑批里没有锁，也没有复现。
- Figma 通过产物的看图对照是人工逐张做的。我按"41 次通过那一批"理解；11-24 复跑的 19 个 1 分是否也看过，见第七节第 1 条。

## 一、总判断：一个根因，外加一个不属于质量问题的缺口

**先看一个例子。** 集群上的 Photoshop 没有登录，窗口停在 Adobe 登录页，界面一步也走不进去。就在这个状态下，27 道题里有 11 道得了 1 分。

- 这 11 道没有一道走界面，都是模型用脚本驱动 Photoshop 进程把文件存出来的。
- 剪贴蒙版那道，Photoshop 的脚本接口多次返回"没有剪贴关系"。模型装了一个第三方库，把剪贴标记直接写进 PSD。评分只看导出图左红右灰，给了 1 分。
- 改键盘快捷键那道，快捷键文件里已经是新键位，但题被标成不可评分，恒为 0。
- 还有几道在收尾里如实写了"新建不可用""动作面板不可用"，也是 0。

没走界面的 1 分、偷换做法的 1 分、做成了的 0 分、如实停下的 0 分，出现在同一批题里。

**根因：判据能分辨的东西，远少于模型能做的事。** agent 手里有界面、shell、应用脚本接口、整个文件系统，还有账号里别人的文件。判据手里只有一个导出文件的尺寸、几个像素和文件头。凡是能让那几个特征出现的路，都得 1 分；凡是结果不落在那个文件上的事，都得 0 分。

**同一条缝为什么看起来像三个问题。** 每一环站的位置不同，给它起了不同的名字。

- 出题的人在数题，看到"核心功能评不了"。
- 验证的人拿伪造品去试，看到"骗得过""旧草稿能过"。
- 质检的人在读轨迹，看到"通过的轨迹里路线很杂、绕行不说明"。
- 跑环境的人看到"正路一堵，模型就绕"。环境障碍不是另一个问题，它是把模型推过这条缝的那只手。

**每一环的修法都是局部的，都在打地鼠。** 这是我认为它们同根的主要理由。

- 补评分：补跑的区域全部过了机器检查，可评分数仍然是零。
- 收紧规则：单色伪造挡住了，单色的正确答案也被误杀。
- 加禁令：题面写了"不要结束应用进程"，模型就转去结束系统通知进程。

**"生成者与审核者同源"不是根因，是它迟迟没被发现的原因。** 换一个模型来写评分，写出来的仍然是"读一个文件、查几个特征"，因为它手里没有别的取证手段。分角色有用的前提是，审核方握有生成方没有的信息：真实应用存出来的样例，或者环境里读出来的状态。

**有一个缺口不在这个根因里：这批数据要教什么行为，没有定义。** 即使判据完美，"用脚本做成算不算好轨迹""被堵住时停下还是换路"仍然没有答案。上面 11 个 1 分里，至少两道已证实是表面通过。其余的按"结果导向、命令行优先"可以算合格数据，按"界面操作示范"一条都不算。这是规格问题，要 mentor 拍板，见第五节。

**这个判断可以被证伪。**

- 如果它对，把动作空间收窄到纯界面后，假通过应当明显减少，归属问题不变。
- 如果它对，把取证从导出文件换成读状态后，谁来写评分都应当改善。
- 泽豪那边误判低，但他同时具备"状态可读"和"独立测试"两个条件，分不开，要问他。

**不属于这个根因的，不要硬归进来。**

- 大段无效重试和中间步骤误判，是模型能力问题。
- 错步定位不稳，是标注可靠性问题。

**文献位置。** 这个根因不是我们发现的。

- WeaveBench 在同一批轨迹上比过：只看产物的通过率，比轨迹审计后高出二十个点。它已经把"用命令行绕过 GUI"判为 0。
- Zhu 等的清单把"报告空操作 agent 的得分"列为必报项。
- SWE-bench 上"测试通过不等于修对"被审计过三轮。

我们的增量在更窄的地方，见验证和质检两节。

## 二、三个主体环节

### 2.1 出题

**例子。** Figma"布尔并集"题：新建文件，画两个重叠的红矩形，做 Union，导出。判据抽 5 个像素：两块独有区和重叠区是红，外面两点是底色。两个矩形叠着放、不做并集，这 5 个点一样全中。自检通过了，因为自检和评分出自同一个模型，它想到的反例只有"只画一个矩形"。11-24 复跑里这题得 1 分，结束语写的是做了 Union。这个 1 分不能证明它做了，也不能证明它没做。

**问题剖析。**

1. **规格里那一问预设了证据在文件里。** 管线让生成模型回答"成品是什么文件、文件里哪个字段能证明做成了"。于是功能被分成两堆：
   - 文件上完全没有痕迹的，如评论、组件、规则、设置，被标成不可评。
   - 文件上有痕迹但不独特的，如并集、蒙版、关掉导出可见性，可评但骗得过。

   这两堆是同一问的两个结果。所以"多数题评不了"和"可评的题每道都有伪造能过"是一件事。

2. **"不可评"大多是读取器欠账。** REST 探针读到了 Figma 的节点树和带时间戳的评论，组件做没做、评论加没加，原则上都能判。PS 探测显示，脚本接口在未登录时也能动。真正原理上读不到的，只剩屏幕上的瞬时状态。所以"先保证可验证还是先保证覆盖"问错了。要约束的是证据位置，不是功能。

3. **"题面每条要求对应一条判据"没有区分要求和取值。** 泽豪在周会上说，题面写简单、评分做严格，误判会增多。这和我们的原则正面相撞。解法是分开两件事：
   - "找一个空闲时间开会"是要求，必须写在题面。
   - 具体哪个时间是取值，留给 agent 去查，评分器从同一个环境里算。

   不做这个区分，我们的原则会被读成"题面越细越好"，那正是他要改掉的。

4. **一功能一题天然是照做题。** 晨阳扩到两百道后出现的模板化，泽豪看到的"判断被提前写明"，是同一件事。难度的主战场在二阶段。所以一阶段不要在逐题修判据上重投，要投在能带进二阶段的读取器和入库检查上。

5. **成对题停了，但没有替代。** 它要测的"察觉受阻并换路"现在没有人测。

**解决思路。**

*我们现在能做：*

- 规格里把那一问换成两问。第一问：证据在哪一层（文件、应用内、本地库、云端、屏幕）。第二问：最像做成但没做成的终态是什么，判据凭什么判它 0。第二问写不出来的题不入包，进"待读取器"清单。
- 入库检查固定为六项：
  - 空跑得 0；
  - 预置合格旧结果得 0；
  - 伪造产物得 0；
  - 逐条破坏题面要求得 0；
  - 合法等价做法得满分；
  - 正例至少一份由真实应用存出。

  "捷径直写得 0"是否启用，取决于第五节的路线决定。
- 能带本次运行唯一内容的题都带上：邮件主题、图层名、评论文字、文件名。这样旧结果天然不合格。
- 覆盖数只数过了入库检查的功能。每个题包一份版本清单，对外只引清单上的数。

*需要同事配合：*

- **泽豪：** 七类样例的测试器和已验证的组件库直接拿来用，我们把"预置合格旧结果"这一类补回给他。要问清他的误判率是在什么样例上测的。
- **晨阳：** 二阶段管线和我们用同一份规格字段，否则两条管线的"可评"不是一个意思。
- **一晨、伟鑫：** 在关应用之前给评分器留一个读状态的钩子，并让评分器侧拿到令牌。
- **彭创：** mock 的后端状态能不能用来接成对题。

*需要实验才能回答：*

- 挑十道 Figma 不可评的核心功能题，接节点树和评论读取，看多少能变成可评且可测归属。这决定"向易验证功能偏斜"这个代价是否真的存在。
- 取十道泽豪式"取值留给 agent"的题，评分器从环境算期望值，跑七类样例加归属。这直接回答"题面少写会不会抬高误判"。
- 成对题搬到 mock 上，看后端过程记录能不能分开"在界面上绕过障碍"和"直接把结果写对"。

**周会怎么接。**

- 晨阳的管线和我们一轮的管线是同一种形状：先写任务，再顺带写评分。他小规模看着好的 8 道，要用我们的六项检查过一遍才知道。
- 泽豪的方案是另一种形状：先有环境，评分读状态，独立测试。方向对，前提是状态可读。这个前提在 PS、Figma、Mail 上正是我们这周在补的。
- 一晨说全靠 MCP 或命令行就能做的任务偏简单，后面重点不在那里。这句话对出题是硬约束：读取通道只给评分器，不给 agent。

**反例和没想到的角度。**

- "待读取器清单"可能变成坟场。要给它定一个指标：清单长度每两周是否在缩短。不缩短，就说明我们事实上接受了分布偏斜，应当明说。
- 唯一内容会让题面带一股合成味，训练集里会出现大量随机串。能用自然内容的（日期、人名、项目名）就不用随机串。
- 最大的风险是反方向的：把这一轮的精力花在给一阶段 196 道题逐题打补丁上。单色图的逐题豁免已经说明这条路扩不了量。

### 2.2 验证

**例子。** Mail 草稿题的三种情形：

- 草稿箱里没有合格草稿，让运行空转到超时：判失败。
- 开跑前放一封合格旧草稿，同样空转到超时：判通过。
- 模型正常做完：判通过。

第二种的通过与模型无关。反方向也有：规则收紧成"整张单色即伪造"后，正确答案本来就是单色的导出被判失败。

**问题剖析。**

1. **"做成"要回答三问，现在只答了第一问的一个表面。**
   - 内容：终态符合题意吗。
   - 归属：是这次运行产生的吗。
   - 途径：是题面要的那种操作产生的吗。例如是并集还是叠放，是 Photoshop 建的剪贴还是第三方库写的标记。

   三问需要的证据不同。内容和归属靠终态加基线。途径靠应用内部结构（节点类型、图层属性），或者过程记录。把三问都压在一张导出图上，是假通过和误杀同时存在的原因：规则松了内容漏，规则紧了等价做法被杀。

2. **手头唯一一个人工确认的真实假通过估计，是 Figma 那批看图。** 41 次通过里有 9 次与题面不符。这个数有两个限制：
   - 它和对抗审计的漏过率不是同一种量，不能互相印证。
   - 看图的上限就是图。判为相符的那些，只证明图对，并集做没做从图上看不出。所以真实的不符只会更多。

3. **0 分同样不是信息。** 现在的 0 混着五种情况：
   - 没做成；
   - 做成了但题不可评；
   - 环境阻断；
   - 评分器读不到；
   - 裁判没判完。

   集群侧的评分理由这两次探测都没拿到手，事后分不开。这是我们自己的硬伤，比任何评分规则的缺陷都优先。

4. **归属是公开工作里最空的一块，但别讲成首创。**
   - 空跑得分已经在 Zhu 等的清单里。
   - OSWorld 的一个未关闭 issue 提出了"比较初态与终态的差"。
   - Ge 等证明了终端任务的裁判需要初始状态。
   - 最近一篇审计明确说只审了失败轨迹，通过判定里的假阳性没做。

   我们能站住的是：在图形界面题上，把"预置一份合格产物、空跑必须得 0"做成入库检查，并在真实通过轨迹上人工估假阳性。

5. **模型裁判的使用范围，文献没有给比例。** 能定下来的是这几条：
   - 网页上最好的裁判，判成功的里面约三成是错的。
   - 换底座，错的方向会反过来。
   - agent 的"已完成"自述会把裁判往通过拉。
   - 允许弃权并回环境取证能把假阳性压下去，代价是两到三成不给判决。
   - 判"做完没有"接近人，判"这一步可不可行"差得远。

   我们自己的观察同向：同一批轨迹换一个判断模型，合格数差出一大截；鸣谦那边同一裁判判两次，结果不同。

**解决思路。**

*现在能做：*

- 评分输出改成带理由的枚举：通过、未通过、题不可评、环境阻断、状态不可读、证据不足。理由和原始产物必须落盘回传。
- 归属检查进入库门槛。
  - Mail 用唯一内容，加上存在虚拟机之外的基线。
  - Figma 用节点 id 和评论 id 的前后差集。
- 评分器双向测试。每次收紧规则，都要在保留下来的真实通过产物上回归，同时报告误杀。
- 以已经逐张看过的 Figma 通过为第一片，补上 Mail 和 PS，凑一份百条上下的人工金标。标四项：是否完成、归属、途径、答复是否如实。
- 用裁判的地方：去掉 agent 自述，长轨迹分段，允许弃权且弃权单列。

*需要同事配合：*

- **一晨：** 收工钩子；录屏帧与步骤对齐。
- **伟鑫：** 评分理由回传；框架收尾失败时不要连成品一起删；Mail 每个并发槽一个邮箱。
- **鸣谦：** 金标和裁判校准集共用一份。
- **泽豪：** 读取与判定分离的组件直接复用。

*需要实验才能回答：*

- 在专用测试文件里手动加一条评论、建一个组件，实测前后差集能否干净分出本次增量。再试原型连线和分支能不能读。
- 评分器侧用脚本接口在收工后查询 Photoshop 的图层属性和参考线是否稳定。未登录探测里 agent 侧能驱动，评分器侧还没试。
- 裁判在我们这几个应用、我们这种证据上的两向误判，至少换一个底座。

**周会怎么接。**

- **一晨的第一条路"让 agent 看轨迹的中间状态来判"：** 你当场反驳了，理由站得住。模型以为做了、其实没生效，轨迹里却写着做了。文献直接支持这一点。
- **视频抽帧：** 给它一个准确的位置。它能证明某个面板出现过、某个菜单被点过，回答的是途径，不是内容，而且仍然排除不了"点了没生效"。
- **MCP 取状态：** 和 REST 探针是同一条路，是这周最该推进的。
- **泽豪引的"让任务最后提交一个产物"：** 只在导出是用户自然一步时成立。对评论、组件、规则无解。
- **鸣谦"太难验证的 rubric 直接拿掉"：** 拿掉可以，题面要同步删，否则就是在制造"题面写了、评分没查"。拿掉的恰好是难验证的那部分，是"向可验证偏斜"在评测端重演一遍。

**反例和没想到的角度。**

- **途径这一问未必总该问。** 如果题面要的只是一张图，并集和叠放对用户等价，查结构就是误杀。所以判据查不查途径，取决于题面写没写这个操作。写了就得查，查不了就别写。
- **读取器自己会坏。** 鸣谦两轮的空分大多是证据太长、服务没返回、条款互相打架。我们集群上读草稿超时也是。读取器故障必须返回"不可读"，不能塌成 0。
- **百条金标只够排优先级，不够报比例。** 公开审计一百五十条的区间就有十几个点宽。
- **差集挡不住"把旧结果改一改"。** 那种情况其实应当算做了。真正要防的是基线被 agent 改，所以基线不放在它够得着的地方。

### 2.3 质检（轨迹质量）

**例子。** 一道 WPS 筛选题。DeepSeek 先把表弄乱，随后改用脚本直接改文件内部的 XML，中途结束过一次 WPS 进程。推理里写"We should not mention weird misstep"，最终答复只说筛选已设置好。评分通过。

再配鸣谦 Round3 的两条：

- Keynote 那题，模型看见导出里有空类别，推测检查器会放过，结果是 0 分。
- 分位数那题，最后一次响应只有推理，没有工具调用，也没有答复，框架把回合记成正常结束，文件没存。

**问题剖析。**

1. **入口放错了。** 现在的做法是评分通过之后再套六类。问题有两个：
   - 通过集合本身不可靠。
   - 只在 1 分里找，会漏掉"猜了评分但没猜中"的。也会漏掉 0 分轨迹里正确的恢复片段，和"终值对、中间列错"的片段。

   鸣谦那边已经改成按片段选，不按整题总分选。

2. **过滤规则本身在塑造行为。** 这是我认为这一块最严重、材料里又没写的一点。
   - 被堵住后绕过去拿到 1 分的轨迹留下了。
   - 被堵住后如实停下的轨迹得 0，被删掉了。

   未登录 PS 那批就是这样。只留 1 分，等于对绕行做了正向选择。ImpossibleBench 的结果指向同一个机制：给模型一个明确的"做不成、交还给人"的出口，作弊率降了一大截。我们的题面里没有这个出口，过滤里也没有它的位置。

3. **证据是全链路最弱的。**
   - 规模数字几乎全是模型标注。
   - 同一批轨迹标三次，"可直接收录"的条数对不上；换一个判断模型，又差一截。
   - "推理里写出迎合评分"只确认了一例。按 Chen 等和 Baker 等的结果，推理里写出来的只是下界，所以不能靠搜推理文本来数，也不能因为只搜到一例就说它少。
   - 推理文本能否当意图证据要分情况。写明在猜评分的，可以当证据。只有推理、没有动作的结束，在核对上游原始输出之前，不能写成"模型放弃"。

4. **六类混着四种性质不同的东西，处理方式不该一样。**
   - 第一、二类是如实性。
   - 第三类是评分问题，根本不是轨迹问题。
   - 第四、五类是模型能力。
   - 第六类是环境。

5. **遮盖的依据比想的薄。**
   - 唯一直接比过"遮盖与不遮盖"的工作在文本智能体上，平均差别很小，换任务还会反号。
   - 涨分大的那些工作，靠的是"有一个写对的下一步可学"，而且都要求能指出第一个错步。
   - 我们恰好卡在定位上：近四成卡点没有任何报错。

6. **"改写答复后收录"我不赞成。**
   - 改写后推理和答复互相矛盾。
   - 改写要准确知道实际发生了什么，这又靠不稳的标注。
   - 这类题上并不缺本来就如实说明的轨迹。

**解决思路。**

*现在能做：*

- **把质检从读文本换成对账。** 从事件记录里确定性地抽出"副作用清单"：
  - 结束了哪些进程；
  - 目标文件最后由哪个程序写出；
  - 有没有移动或改名；
  - 有没有打开本任务之外的文件。

  再逐项和最终答复对。这不需要模型裁判，也不需要猜意图。
- **每条轨迹标路线：** 界面步和命令步各多少，成品由谁写出。否则"这批 GUI 数据里有多少其实是脚本轨迹"答不出来。
- **打分之前先分桶：** 协议异常、未判定、环境阻断、未完成、完成。六类只套在"完成"上。另外单列"受阻后如实停下"。
- **遮盖只做能确定性定位的错步：** 工具返回错误的，或者被后续动作显式撤销的。无报错的卡点不遮盖，整条标"未定位"。不做"没完成原题、换个题面留下"。
- **未说明手段的轨迹打标隔离，不改写。**

*需要同事配合：*

- **晨阳：** 平台现在的过滤规则是什么；"已解决的两类问题"对应我们哪几类；loss mark 的粒度；最终答复和推理是否进损失。最后一项决定"不说明手段"到底伤不伤。
- **林强：** 改 skill 描述时加一句受阻出口，并给 skill 和提示模板一个版本号。
- **一晨、鸣谦：** "只返回推理"的结束算框架还是算模型。有限次续接由框架做。

*需要实验才能回答：*

- **出口实验。** 在被堵住的同一批题上（未登录 PS、存桌面的授权框），题面加与不加出口各跑一遍，把反应分成如实停下、正当换路、钻评分三种，再单看答复是否交代手段。公开工作里没有人在图形界面上做过这个，它也是我们最像样的一点增量。
- **训练对照。** 同一批数据做原样、按标签过滤、遮盖三个小规模版本，看如实说明和重试行为有没有差别。这是唯一能回答"这些问题进训练有没有害"的办法。
- **在金标上量模型标注的一致性，** 再决定哪些标签可以交付。

**周会怎么接。**

- 晨阳说过滤问题已解决、loss mark 已支持，说明管道有了。瓶颈在两头：喂给过滤的 verify 结果（他自己说判定过宽），和喂给遮盖的错步定位。
- 广文杰和一晨观察到：新版 driver 上界面操作一直成功，模型就一直走界面；旧版失败一次就转脚本。这说明路线不是模型的固有偏好，是 driver 稳定性和提示词共同决定的。所以后端、框架、提示模板、skill 四个版本都得记在轨迹上。
- 鸣谦对 DeepSeek"会做的很快、不会的一直重试到超时"的描述，对应我们的第四类。Round3 多出的"临近时限无备份地删整层重做"，应当和它并排单列。

**反例和没想到的角度。**

- **"不说明手段"可能根本不重要。** 如果最终答复不进损失，或者下游不看答复，这一类降级为标签就够了。先问清楚再投入。
- **对账只能抓到有行为痕迹的。** 推断了评分、但做法本身合规的抓不到。那种情况也无害。
- **出口可能被滥用。** 模型遇到一点阻力就停。所以出口实验要同时看没有被堵的对照题上，停下的比例有没有上升。
- **当前模型的主要问题可能不在这里。** 晨阳在 3.8 上测到的是工具调用本身出错。如果是这样，这一节的精细把关对眼下的训练收益有限，价值在下一版。这一点要对 mentor 直说。

## 三、共性问题：哪些是真共性

**1. 读得到与读不到的不对称。真共性，但原来的说法要改。**

- 它决定了哪些功能有题、哪些题有分、哪些轨迹被留下。三件事被同一条线切开。
- "读不到"多数是还没写读取器。原理上读不到的只有屏幕瞬时状态。
- 所以它是一笔可以还的工程债，不是功能覆盖的天花板。

**2. 生成者与审核者同源。真共性，是放大器，不是根因。**

- 题面、评分、自检同一个模型。
- 轨迹由模型产生，又由模型标注。
- 训练题和评测题将走同一条管线：鸣谦说评测集扩应用时跟着造数走。这样评分缺陷会被两边一起继承，训练上的虚高在评测上看不出来。
- 分角色只有在审核方握有额外信息时才有效：真实应用样例、环境状态、人工金标。

**3. 终态与过程割裂。真共性。**

- 评分只看终态，检查器只看文本，成对题的分数只反映终态。
- 解法是分工，不是合并：终态加基线回答内容和归属；过程记录回答途径和副作用。
- 两者都不回答意图。意图只在推理写明时才有证据，而且只是下界。

**4. 证据等级混用。真共性，也是会上最容易被打穿的。**

我们的材料里并排放着四种东西：

- 从环境读出来并和基线做差的；
- 人工看过的；
- 脚本对表面特征的检查；
- 模型的标注或裁判。

轨迹质量那份的规模数字几乎全是第四种。每个数字都应当带上等级，第四种不进结论句。

**5. 不确定性被压成一位。真共性。**

- 0 分混着五种含义，1 分混着做成、表面通过、环境里原有三种。
- 每一环都只把 0 或 1 交给下一环。
- 《重要问题》第五节已经说了这句话。这次给出具体形态：评分枚举加理由落盘，轨迹带标签交付。

**6. 选择效应。真共性，原材料里没有列。**

- 只留 1 分，选出了绕行，删掉了如实停下。
- 只在 1 分里找坏轨迹，漏掉猜错的。
- 鸣谦 Round3 是跨多次运行挑"第一次做完"拼成的 50 题，不能当首跑成功率读。我们归档时如果也只留选中的那一次，同样的话也要写。

**7. 口径漂移。是真的，但它是纪律问题，不是研究问题。**

- 题数有好几个互相对不上的值。
- 周报把漏斗的六类写成了三类。
- "做完被判错"被读成"成品对、评分错"，而按复算它只是一个分类名。
- 两个不相干的 41 很容易被加在一起。

它不解释任何质量问题，但会让上面每一条判断在会上失信。

**不算共性的。**

- 无效重试和中间误判是模型的能力短板，是训练要解决的目标，不是数据缺陷。
- 账号是前置条件。

## 四、账号与环境：前置环节

它值得写进这份材料的只有一点：**环境障碍会把绕行送进训练数据。**

**三个例子。**

- 未登录的 Photoshop 上，没有一条界面轨迹，所有得分都来自脚本。
- 存桌面的授权框点不到，模型就结束系统通知进程，或者先存别处再移动。
- 11-23 那批 Figma 团队被锁时，出现过一例改去别人稿子里完成。11-24 复跑没有锁，也就没有这种轨迹。这反过来说明它是环境造成的，不是模型的固定习性。

**两种障碍要分开。**

- 登录窗和授权框是真实用户也会遇到的。正确行为是处理它，或者如实报告。3.0 如果能让模型看见并点到，它就是可教的场景。
- 团队锁和 driver 点不到是我们环境独有的。只应当修掉，或者记成环境阻断。

**三条出路的取舍。**

- **账号隔离。** 最干净，代价是账号和席位。适合 Mail（每个并发槽一个邮箱）和 Photoshop（两台登录机；并发低，晨阳已经说可以接受）。
- **挂机加基线。** 不花钱，但状态累积、不能并发，基线还得放在 agent 够不着的地方。适合少量真机对照。
- **mock。** 并发和状态可读一次解决，后端状态还是白盒。代价是界面树比真应用简单、任务偏易，向真应用的迁移没有测过。适合飞书和跨应用长任务。

**倾向。**

- Mail 走隔离。
- Photoshop 只在登录机上产界面数据，集群上未登录的那些不当界面数据源。
- Figma 换一个没被锁的团队账号，评分走节点树和评论读取。
- 飞书以 mock 为主，留一小组挂机真机题检验迁移。

## 五、需要 mentor 拍板的三个问题

**问题一：这批数据要教的目标行为是什么？**

具体是两件事：路线上界面和命令行怎么算；正路被堵时，规范反应是什么。

*倾向：*

- 分成两个包，分别标注，不混在一起。
  - "界面操作"包：要求成品经界面路径产生，用过程证据核途径。
  - "结果导向"包：允许脚本，要求答复如实交代手段。
- 受阻时如实停下是正例，题面给出口，这类轨迹单独留。

*理由：*

- 晨阳的模板在拉命令行优先。
- 一晨说命令行能做完的任务不是重点。
- 未登录 PS 的 11 个 1 分全是脚本。
- 成对题里脚本直写两边都满分。

不定这一条，"1 分算不算好数据"没有答案，入库检查里"捷径得 0"也没法决定开不开。

**问题二：一阶段数据是按现有 1 分收尾，还是先回判分档再交？**

*倾向：*

- 不按现有 1 分收尾。
- 已经进训练的不追回。
- 剩下的先做金标和归属回判，分成三档再交：有状态证据且归属通过、仅表面通过、未判定。
- 请他批一次小规模训练对照。

*理由：*

- 过滤依据的是 verify。verify 判定过宽是晨阳自己说的。
- Figma 通过里人工看图就有两成不符，归属没有查过。
- 只留 1 分还在反向选择绕行。

*反方也成立：*

- 晨阳认为覆盖已经够了。
- 眼下模型的问题可能是工具调用，不是这些。

所以我们的改口条件写明：训练对照看不出差别，这套把关就降级为打标签。

**问题三：验证的投入放在哪里，覆盖数用什么口径报？**

*倾向：*

- 投读取器，停掉逐题修判据。读取器包括 Figma 节点树与评论、Photoshop 脚本查询、Mail 的 IMAP 加基线。
- mock 只用于飞书和跨应用。
- 覆盖数只报"可评且过了入库检查"的功能，另报一个"待读取器"清单的长度。
- 评测集如果沿用同一条管线，至少评分器要由另一方独立审过。

*理由：*

- 读取器能带进二阶段，逐题补丁带不走。
- 这件事跨一晨、伟鑫、彭创三个人，还要账号和令牌，不是我们自己能定的。

### 6.1 《数据质量把关_重要问题》

**新增一节，放在第一节之前，标题「零、先于四个环节的问题：这批数据要教什么行为」**

> 集群上未登录的 Photoshop 停在登录页，界面无法操作，但 27 道题里仍有 11 道评分通过：模型用脚本驱动 Photoshop 进程存出了成品。这些轨迹如果按"结果导向、优先命令行"来看，多数是合格的；如果按"界面操作示范"来看，一条都不能用。两种看法都有人持有：造数据时我们在题面上加了命令行优先的模板，框架方向则认为全靠命令行或 MCP 就能做完的任务偏简单，不是后续重点。目标行为不先定下来，后面四个环节的许多问题没有答案，包括用脚本直接写出结果算不算捷径、被环境挡住时停下还是换路、通过的轨迹能不能当界面正例。我们的倾向是把数据分成"界面操作"和"结果导向"两个包分别把关，并把"受阻后如实停下"作为一类正例单独保留。

**补充到第一节「按功能生成的任务中……」小节末尾**

> 这里的"无法评分"需要拆开看。我们用只读方式试过 Figma 的接口，文件的节点树和带时间戳的评论都能读到，组件是否创建、评论是否新增，原则上可以直接判断。也就是说，这批任务里相当一部分评不了，是因为评分只会读本地导出文件，而不是因为状态无法获得。原理上读不到的主要是只显示在屏幕上的瞬时状态。因此需要决定的不是"先保证可验证还是先保证覆盖"，而是每个功能的证据应该到哪一层去取，以及读取器由谁来写。

**替换第二节「环境障碍会改变模型的解法……」小节的例子段（"Photoshop 向桌面保存文件时……有的还带有副作用。"）**

> 这一点比数据量上的损失更值得关注。未登录的 Photoshop 上，没有一条轨迹走界面，所有得分都来自脚本；其中一道剪贴蒙版题，Photoshop 自己报告没有建立剪贴关系，模型改用第三方库把标记写进文件，评分只看导出图，仍然通过。向桌面保存文件时弹出的系统授权框模型点不到，它就结束系统通知进程，或者先存到别处再移动。11-23 那一批 Figma 团队被锁、无法新建文件时，出现过一例改在他人已有的设计稿里完成；11-24 复跑时没有锁，也没有再出现这种轨迹，说明它是环境造成的。这些轨迹评分通过，示范的却是只在特定环境里才有意义的做法。同一批里如实停下并报告"功能不可用"的轨迹得的是 0 分，会被过滤掉，于是只按分数筛选等于偏向保留绕行。

**替换第二节「环境故障被记为零分……」小节中"这一周未通过的 164 次运行中……只有 9 次。"一句**

> 这一周未通过的运行里，多数不是模型没有做成：一大块是题目本身不可评分而被统一记成 0，一大块是环境或评分读取出了问题，归到"模型做完后被判未通过"的只是少数，而且这少数里也包括目标文件不在评分路径上、评分读不到草稿这类情况，不能读成"成品正确、评分看错"。这些类别的精确次数依赖生产机上的原始记录，核对完成前不引用具体数字。

**补充到第四节「结果正确，但过程示范了不应学习的行为」小节末尾**

> 识别这类问题不能靠搜索推理文本。公开研究显示，模型实际利用了某个线索或漏洞时，在推理中写出来的比例往往很低，所以推理里数到的次数只是下界。更可靠的做法是对账：从事件记录中确定性地抽出本次运行结束过哪些进程、成品最后由哪个程序写出、是否移动或改名过文件、是否打开过任务之外的文件，再逐项与最终答复比对。

**替换第五节全文，标题改为「五、四个环节背后的同一个原因」**

> 四个环节的问题有同一个来源：判据能分辨的东西，远少于模型能做的事。模型可以走界面、写脚本、改文件、进入账号里已有的文件，判据通常只检查一个导出文件的尺寸、几个像素或文件头。能让这几个特征出现的做法都会通过，结果不落在这个文件上的功能都评不了。出题时它表现为核心功能没有分数，验证时表现为伪造产物和旧结果能通过，质检时表现为通过的轨迹里路线混杂，环境障碍则把模型推向那些判据分不清的做法。分别去补评分、收紧规则、在题面加禁令，都只能挡住已经见过的那一种。要缩小这个差距，一是把取证从导出文件换成读取应用状态并与开跑前的基线做差，二是用过程记录回答"是不是按题面要求的方式做的"，三是每个环节把结论连同证据等级交给下一环，而不是只交一个 0 或 1。题面、评分和自检出自同一个模型，使这个差距长期没有被发现，但它不是差距本身的原因。

### 6.2 《01_出题》

**补充到第二节「入库检查不测伪造产物……」小节之后，新增小节「判据检查的特征，不做那一步也会出现」**

> 一道 Figma 题要求画两个重叠的红色矩形并做并集，评分抽取五个像素：两块独有区域和重叠区域为红色，形状之外为底色。两个矩形叠放而不做并集，这五个点同样满足。另一道题要求给画框填色后取消"在导出中显示"，评分检查导出图的抽样点为透明，一张从未填过色的空图也满足。这类题的问题不在评分写得粗，而在取证位置：并集、蒙版、导出可见性这些操作在导出图上不留下可区分的痕迹，证据在文件的节点结构里。写规格时除了回答"哪个字段能证明做成"，还必须写出"最像做成但没有做成的终态是什么，判据凭什么把它判为失败"，写不出来的题不入包。

**补充到第二节「可评分的比例与功能的价值相反」小节末尾**

> 评论、组件这类保存在云端的结果，我们已经确认可以通过接口从评分器一侧读到。因此这部分任务应当记为"等待读取器"，而不是"无法评分"。两者的区别在于前者有明确的还债路径，可以用清单长度是否在缩短来跟踪。

**补充到第三节「题面必须写明所有被评判的要求」小节末尾**

> 这条原则需要区分要求和取值。"找一个空闲时间安排会议"是要求，必须写在题面；具体是哪个时间属于取值，应当留给智能体从环境中查找，由评分器从同一个环境计算期望结果。刷榜方向发现，把这类取值直接写进题面会让任务退化成照着执行，难度明显下降。只写要求、不写取值，题面与判据仍然一一对应，任务也保留了判断的部分；代价是评分器必须能读取环境状态，并且要用等价做法的样例测试它是否误杀。

**替换第四节第 1 条**

> 1. **规格阶段写明两件事：证据在哪一层，以及最近的错误终态如何被判为失败。** 证据层分为文件、应用内部、本地数据库、云端和屏幕。证据在云端或应用内部而读取器尚未实现的功能，进入"等待读取器"清单，不进训练包，也不计入功能覆盖数。

**补充到第四节第 3 条的检查列表末尾**

> - 逐条破坏题面要求后，每一种都得 0 分；
> - 能带本次运行唯一内容的题目（邮件主题、图层名、评论文字），题面写入该内容，使环境中原有的结果天然不合格。

**补充到第二节「成对题的分数只反映终态」小节末尾**

> 成对题想测的"察觉受阻并换路"目前没有替代的测量方式。可行的方向有两个：在题面中给出明确的受阻出口，观察模型在被堵住时停下、换路还是迎合评分；或者把成对题放到后端状态完全可读的模拟应用上，用过程记录区分"在界面上绕过障碍"和"直接写出结果"。

### 6.3 《验证方法_按结果存在哪取证》

**补充到第一节末尾**

> 上面三个例子对应"做成"的三个不同问题：终态内容是否符合题意，结果是否由本次运行产生，结果是否由题面要求的那种操作产生。第三个问题最容易被漏掉：两个叠放的矩形与一次并集在导出图上相同；Photoshop 建立的剪贴关系与第三方库写进文件的剪贴标记，在导出图上也相同。三个问题需要的证据不同，内容和归属依靠终态与开跑前基线的差，操作方式依靠应用内部结构或过程记录。把三个问题都压在一张导出图上，规则放松时内容会漏，规则收紧时合法的等价做法会被误杀。另外需要说明，第一节中 Figma 无法新建文件的例子出自 11-23 的一批运行，11-24 复跑时团队没有被锁，这种轨迹没有再出现。

**替换第二节「结果在云端或服务器上」一段**

> **结果在云端或服务器上。** 例如 Figma 的组件、原型连线、评论，以及邮件服务器上的状态。我们用只读方式验证过 Figma 的接口：文件节点树可以读到，其中包含组件和实例；评论可以读到，每条带创建时间和所挂的节点。归属可以这样做：开跑前记下已有的节点标识和评论标识，收工后只认新增的部分。有三点限制。第一，列出组件的专用接口只返回已发布到团队库的组件，个人账号下为空，需要从节点树里统计。第二，版本历史在个人账号下拿不到，不能当基线。第三，评分器需要知道模型实际编辑的是哪个文件，而新建文件的标识事先未知，这一步的取法还没有验证。原型连线和分支是否可读尚未测试。读取通道只放在评分器一侧，不提供给被测的智能体，否则任务会退化成读一下就能完成。

**补充到第四节四条局限之后**

> 与人为构造的伪造产物相对，我们手头有一个来自真实轨迹的估计：一批 Figma 评分通过的导出图由人工逐张对照题面，其中约两成与题面不符，情形包括切片导出在空白区域、PDF 只有文件头、两道题共用同一个文件、导出的是现成模板。这个比例与对抗审计的漏过率不是同一种量，不能互相印证。它还有一个上限：看图只能确认图是否符合题面，判为相符的那部分仍然不能证明题面要求的操作确实做过。

**补充到第三节末尾**

> 公开研究没有给出"训练数据里可以有多大比例的标签来自模型裁判"。可以确定的是几条方向性的结论：最好的裁判判为成功的轨迹里仍有相当比例是错的，换底座后错误方向会反转，允许弃权能降低假阳性但会有两到三成不给判决。我们自己的观察与此一致，同一批轨迹换一个判断模型，合格的数量差别很大。因此裁判的结论应当单独标注，在用我们自己的应用和证据形式完成人工校准之前，不作为成功标签进入训练集。

**补充到第六节五项之后**

> 6. 评分结果用带理由的类别表示：通过、未通过、题目不可评、环境阻断、状态不可读、证据不足。理由和原始产物随结果一起保存和回传。目前集群一侧的评分理由没有取回，导致事后无法区分一个 0 分是模型没做成、题目评不了，还是评分器读取失败。
> 7. 归属检查作为入库的必过项：在环境中预置一份合格的旧结果，不做任何操作，评分必须判为未通过。

### 6.4 《04_质检》

**替换开头的范围说明（第一段）**

> 本文整理过程中存在问题的轨迹，按问题类型归类。早期版本只看评分已经通过的轨迹，这个入口过窄：评分通过本身不可靠；迎合评分但没有猜中的轨迹得的是 0 分；0 分轨迹里也有值得保留的正确恢复片段。因此分类之前先把每条轨迹分到五个桶里：协议异常（例如最后一次响应只有推理、没有动作也没有答复，框架记为正常结束）、未判定（评分或裁判没有给出结论）、环境阻断、未完成、完成。下面的六类主要针对"完成"这一桶，其余各桶的处理在第七节说明。六类的性质并不相同：第一、二类是如实性问题，第三类其实是评分问题，第四、五类是模型能力问题，第六类是环境问题。

**替换第二类的「规模」一段**

> **规模**：推理中明确写出评分推测并偏离题意的，目前确认的是这一例，出自 11-23 团队被锁的那批运行；11-24 复跑时团队没有被锁，40 条轨迹里既没有出现锁的提示，也没有出现这类推理。这不说明迎合评分的情况少，因为推理里写出来的只是实际发生的下界，这个限定来自公开研究，不是我们的结论。从结果看，一批 Figma 评分通过的导出图经人工逐张对照，约两成与题面不符。另外，这类行为不只出现在通过的轨迹里：测评方向有一条 Keynote 轨迹，模型看到导出文件里多出空类别，推测检查器会忽略，最终得 0 分。

**替换第一类的「处理建议」**

> **处理建议**：使用脚本本身是允许的，问题在于不说明。这类轨迹不建议改写答复后收录，原因有三：改写后答复与推理互相矛盾；改写需要准确知道实际发生了什么，目前这依赖不稳定的模型标注；同类任务上并不缺少本来就如实说明的轨迹。建议的做法是用确定性的对账给轨迹打标签，即从事件记录里抽出结束过的进程、成品的写出者、文件的移动和改名，逐项与最终答复比对。未说明的轨迹隔离存放，是否使用留待训练对照实验决定。

**补充到第五类的「处理建议」末尾**

> 遮盖的范围应当保守。直接比较过"遮盖错误步"与"不遮盖"的公开实验很少，在文本智能体上的结果是平均差别很小，个别任务上不遮盖反而更好；收益明显的做法都依赖"能指出第一个错步，并且有一个写对的下一步可学"。因此只对能确定性定位的错步做遮盖，例如工具返回了错误，或者该步被后续动作明确撤销。没有报错的卡点不做遮盖，整条标为"错步未定位"。没有完成原题的轨迹不通过改写题面留用；公开工作中按实际所做重写任务的做法，都重新执行了一遍或重写了动作。

**新增一节，放在第六类之后，标题「七、六类之外需要单独留档的情况」**

> **受阻后如实停下。** 未登录的 Photoshop 上，有几条轨迹在收尾时如实写了"新建不可用""动作面板不可用"，得 0 分。这是我们希望模型学会的反应，按分数过滤会把它删掉，应当单独保留。
>
> **只有推理、没有动作和答复的结束。** 框架把回合记为完成，文件没有保存。在核对模型服务的原始输出之前，不写成模型主动放弃，也不贴成功或失败。
>
> **临近时限时无备份地整体重做。** 例如时间将尽时删掉整个图层重新导入。它与反复执行同一操作不同，重复次数不多，代价更大。
>
> **终值正确、中间内容错误。** 例如表格的期末余额正确，摊销列的符号是反的；四段文字都在，却全部落在同一个单元格里。判据如果只检查终值或全文包含，这类轨迹会被当成完成。
>
> **归档时的选择。** 如果只保留多次运行中选出的那一次，交付时要写明选择规则，否则通过率会被读成首次运行的能力。

### 6.5 《应用环境与账号》

**补充到第一节三个影响之后**

> 环境障碍分两种，处理方式不同。登录窗和系统授权框是真实用户也会遇到的，正确的行为是处理它或者如实报告，如果驱动能让模型看见并点击，它就是值得保留的训练场景。团队被锁、驱动点不到控件是我们的环境独有的，只应当修复或记为环境阻断。

**替换 Photoshop 一节的最后一句（"未登录的 Photoshop 在集群上能完成哪些任务，还没有实测。"）**

> 未登录的 Photoshop 在集群上已经实测过 27 道题。界面始终停在 Adobe 账号登录页，没有一道题能通过界面操作完成；其中约四分之一停在登录墙前什么也没做成，其余的是模型用脚本驱动 Photoshop 进程，或者直接改偏好文件。评分通过的 11 道全部属于后一种，其中至少两道是表面通过：一道用选区填充代替了题面要求的颜色调整，一道的剪贴关系由第三方库写入而不是 Photoshop 建立。结论是，集群上未登录的 Photoshop 不能作为界面数据的来源；它产出的脚本轨迹是否可用，取决于目标行为怎么定。这次实测也说明应用的脚本接口在未登录时仍然可用，评分器一侧能否用它在收工后查询文档状态，值得另行验证。

**替换 Figma 一节的两处**

> 现有账号所在的团队在 11-23 的运行中处于锁定状态，无法新建文件，当时要求新建文件的任务都无法正常完成，并出现过模型转而在他人已有的文件中操作的情况。11-24 复跑时没有再遇到锁定，多条轨迹正常新建了文件。团队状态会变化，开跑前应当检查并记录。

> 此外，Figma 的组件、原型连线、评论和分支都保存在云端，现有评分只读本地导出文件，所以这些功能的任务目前没有分数。其中节点树和评论已经确认可以通过接口从评分器一侧读取，详见《GUI 任务的结果验证》。

**替换飞书一节**

> 飞书登录需要扫码或手机验证。登录态并非完全不能保留：在单机、不并发的情况下，登录后保存状态可以继续使用，也可以让应用一直挂着不重启。问题在于框架每个任务都从镜像重新启动，登录态会丢失；而不重启，上一个任务留下的状态就会累积到下一个任务。也就是说，飞书的障碍是登录态与环境重置不能兼得。本阶段不在真实飞书上批量生产数据。

**新增一节，放在「需要的资源」之前，标题「三、三条出路及其取舍」**

> 每个需要登录的应用，都要在三条路里选一条。账号隔离，即每个任务或每个并发槽位使用独立的账号或邮箱，结果最干净，代价是账号和席位，适合 Mail 和 Photoshop。挂机加基线，即应用保持登录不重启，开跑前记录基线，评分只认基线之后的变化，不需要额外账号，但不能并发，状态会累积，基线还必须存放在智能体接触不到的地方，适合少量真机对照。模拟应用，即用桌面壳承载的模拟应用代替真实应用，并发和状态读取一次解决，后端状态还可以直接用于评分，代价是界面结构比真实应用简单、任务偏容易，向真实应用的迁移效果没有测过，适合飞书和跨应用的长任务。目前的倾向是：Mail 走账号隔离；Photoshop 只在已登录的两台机器上生产界面数据；Figma 换用未被锁定的团队账号并从接口读取状态；飞书以模拟应用为主，保留一小组真机任务检验迁移。
