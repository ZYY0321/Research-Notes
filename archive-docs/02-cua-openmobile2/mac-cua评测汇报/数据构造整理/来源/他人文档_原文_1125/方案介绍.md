# 方案介绍

# 流程简述

**先用真实材料构建一个人的工作环境，再围绕这个环境设计任务、实现并验证评分器，最后让执行模型进入独立沙盒完成任务，记录操作过程，并筛选可信的成功轨迹。**

它包含两部分：前半部分是**任务与环境的自动化构造**，后半部分是**模型执行轨迹的采集与检查**。

## 角色构建

### 背景构建

基于构建的环境，可以拟定需要构建的角色，由Agent在环境中探索，收集合适的材料，并进行适当的修改与适配，也可以加入适量无关邮件、旧项目和历史文件，使环境更接近实际工作状态，构建一台真实的办公电脑。由角色方向、真实材料、应用能力，以及可以参考的初始化脚本，得到一套具有背景、历史和实际工作内容的角色环境。

例如，构建一个财务专员，不能只有一张等待填写的表格，还应有与工作相关的交易记录、费用政策、往来邮件、历史台账，以及能够解释当前待办事项的业务背景。

目的是保证设备中各个文件之间逻辑连贯，信息之间自洽，可以将已有的材料有序地组织起来，同时不让任务出现多个互相冲突的答案，也为出题提供大方向。

### 初始化环境

除了构建角色背景，还需要编写初始化代码，可以基于已有的代码和接口进行修改，导入需要的文件，完成后在沙盒中验证初始化正确。

## 任务设计

基于已有的角色环境，Agent 在这一环境里寻找真实的工作需求，形成不同任务。

在其中可以学习一些任务示例，同时控制任务难度，保证任务合理性。

## Reader和Verifier实现

Agent根据任务要求和评价方式编写Reader和Verifier，Reader负责读取实际应用状态和已保存的结果，Verifier负责判断。将可验证的沙盒交互整合为专门的MCP，需要查找接口时可以在沙盒探索，评分从本质上可以分成两种方式：

1. 能明确计算的内容，优先用确定性代码检查。例如文件是否存在、修改的是不是正确客户、金额是否一致、公式是否仍然存在、是否有重复记录、要求保留的内容有没有被破坏。

2. 需要理解表达或视觉内容的部分，调用 LLM Judge。例如，说明文字是否准确表达了要求，或者实际截图中是否满足明确的布局、内容和对应关系。判断必须有客观标准，不评价“是否好看”“是否专业”等主观偏好。

## Reader和Verifier验证

编写完Reader和Verifier后，由独立的Agent出题测试验证：

测试按任务风险选择，主要包括：

- 正确结果是否能通过。

- 合法的等价表达、顺序或公式是否能通过。

- 初态没有完成任务时，是否会被误判成功。

- 漏掉某一关键要求，是否会被识别。

- 数值表面正确，但对象关联错误，是否会被识别。

- 使用旧版本附件、破坏保留内容等问题，是否会被发现。

- 文件损坏或状态不可读时，是否正确返回错误状态。

大部分测试在本地批量完成，控制成本。只有必须依赖真实应用的部分放进沙盒，例如打开、保存、重新打开、实际截图、Reader 回读，以及与控制服务共存。检查者先依据规格和材料形成预期，再看实现。发现实质问题后，交还回去修复，再重新验证。

## 轨迹采集

任务设计完成后开始轨迹采集：先尝试用DeepSeek\-V4\.1\-Flash \+ Claude Code进行采集

## 分析与整理

对轨迹采集中存在的问题可以进行分析，调整出题难度和任务节点数量。对于成功的初始化、Reader、Verifier脚本，可以整理后放入素材库，后期复用。
