# 评估修复

修复后补评，**30 条为 1 分、1 条为 0 分、1 条仍 null**。**剪映变速仍 null。**

根据 Claude、Sol、DeepSeek 三份 Round2 报告，合并相同现象后如下。共 34 条原始 null（有两条是setup问题，所以评估问题是 32 条），涉及 18 道题。所有修改位置均指 backup 的 \~/mac\-cua/ 仓库；表格记录相对原始代码的实际修复、修改原因和本轮最终验证。本轮只验证非剪映任务，完成状态见表格最后一列；剪映本轮不改、不验证，原始轨迹保留。

1. 单步证据太长，Judge 尚未调用就报错。共 14 条。能不能统计一下实际证据字符长度？到底单步有多长？chrome单步为什么会这么长?是因为要输入图片？要输入 AX？

- **AX 等页面文本很长。** 例如 Sol ECMAScript 最大步骤来自 `GoogleChrome.getAXStateAndScreenshot()`，当时是 EtherCalc 表格窗口，AX 包含大量行、单元格、静态文本和可执行动作。仅 `result` 序列化后就有 62,782 字符。

- **图片编码混入文本。** DeepSeek 地图和飞机题的 `result` 保存了完整 `direct_response` JSON，里面包含 `input_image` 和 `data:image/png;base64,...`。这些图片编码被当成文本计长，分别撑到了约 24\.5 万和 8\.3 万字符。

2. Judge 已调用多次，但最后综合评分时超限。共 2 条。为什么Judge有多次调用？综合文本之前模型的输入？输出？文本内容是什么？

- 原来的代码采用两条独立规则：文本：每批最多 **60,000 字符**。图片：每批最多 **8 张**。文本批次与图片批次分别发给 Judge，最后再汇总各批判断。

综合阶段的输入主要包括：

- 原始 rubric；

- 每批 Judge 输出的 `pass / fail / unknown`、理由、证据引用；

- 每批实际提供过哪些证据；

- 图片出现顺序与关联步骤；

- 哪些工具调用缺少可观察结果。

**它主要综合前面模型的审查输出，以及评估器补充的覆盖信息，并非简单重新发送全部原始轨迹。** 前面各批通常都会评同一组 rubric，因此批次越多，重复条目和理由越多，综合文本就会膨胀。

原始步骤和截图

→ 多批文本审查、图片审查

→ 汇总各批审查结果

→ 对有疑问的评分项定向复核

→ 按规则计算最终分数

3. 最终复核只收到首步或一张图片，把已有结论变成 unknown。共 4 条；Sol GPU/ECM 补评也遇到同类问题。为什么轨迹中有动作和图片，没有全部输给模型？

原来的最终复核会根据前面结论引用的证据编号，抽取一个局部证据集，而不是重新读取整条轨迹。已观察到的异常包括：

- 只选中了 `step-1`；

- 只给了一张被引用的图片，\`steps=\[\]\`；

- 提供了动作，却没有提供动作之后的成功状态或持久化检查。

而每次 Judge 调用是独立请求，**它不会自动记得前面几次看过的截图和步骤**。因此，前一轮认为有支持，后一轮收到的证据不足，又变成 unknown。

4. 业务内容基本通过，但“全程没有禁止操作”仍为 unknown。共 7 条。统计有多少任务/rubrics出现了“全程没有禁止操作”的规则。这个规则是什么？是否需要删除？

**`kind=prohibition`****、\`id=no\_forbidden\` 的评分项。**规则本身还明确区分：

- 自动弹出登录窗口，不等于完成登录；

- 打开导出窗口后取消，不等于完成导出；

- 缺少过程覆盖时返回 unknown。

导出的问题后端已解决。规则可删除

5. Judge 连续三次返回不合要求的结构化结果，所有业务项 unknown。共 1 条。能不能深入解析一下原因？

Sol 剪映音频题已经核实：**三次响应都是 ****`finish_reason=content_filter`****。**

实际链路是：

服务端过滤输出

→ 没有正常完整的评分结果

→ 旧评估器把它归入结构化输出不合格

→ 要求重新输出合法 JSON

→ 再次被过滤

→ 三次后报结构化输出失败

6. 初始化失败，Agent 没有启动，评估也未运行。共 2 条。setup为什么会失败？能不能避免？

两条记录虽然都表现为 Agent 未启动，但证据详细程度不同：

- **Sol Numbers**：初始化处理通讯录权限提示时，\`get\_window\_state\` 被 Driver 拒绝，窗口状态读取失败，setup 随之退出。

- **Claude Numbers**：现有记录是 `guest.response_unavailable`。这是“没有拿到客体响应”的外层症状，还不足以确定内部究竟是应用、Driver、进程退出还是通信问题。

检查还发现，旧初始化脚本调用的 Driver 是 **0\.25\.0**，而已验收的新镜像 Driver 是 **0\.38\.0**。新旧返回格式和操作投递方式存在差异。不过，**不能因此直接认定版本差异就是两次历史失败的唯一原因**：旧脚本在后来的新克隆中也曾成功。

7. ECMAScript 补评后仍为 null：10\.1、10\.2、10\.3 的实体定位不通过。与前面的同一任务重合，不增加 null 数量。Sol 原工具输出已截断，部分完整标题不可见。为什么会截断？
