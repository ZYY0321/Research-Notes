## 1. 对我们这次汇报最有用的三条

### 1.1 泽昊的「方案介绍」和我们这周的「验证流程」是同一件事，而且他已经有了现成的测试清单

文件：`方案介绍/方案介绍.md`。流程是：先用真实材料构建一个人的工作环境 → 围绕环境设计任务 → **实现 Reader（读应用状态）和 Verifier（判断）** → 由独立 Agent 出题测试验证 → 用 DeepSeek-V4.1-Flash + Claude Code 采集轨迹 → 整理复用。

「Reader 和 Verifier 验证」一节列了 7 项测试：正确结果能通过；合法等价表达能通过；初态没完成时不会被误判成功；漏掉一个关键要求能被识别；数值正确但对象关联错误能被识别；用旧版本附件、破坏保留内容能被发现；文件损坏或状态不可读时返回错误状态。**这 7 项几乎就是我们要补的「验证门」**（我们现在做到的：假产物对抗，相当于第 3 项的一部分；没做到的：合法等价表达、对象关联错误、状态不可读）。评分原则也一致：能算的用确定性代码，需要理解的才用 LLM judge，判断必须有客观标准。

对汇报的用处：这周我们自己摸出来的「怎么验证」，可以说成「和泽昊已经在做的 Reader/Verifier 方案同向，我们补的是 GUI 应用侧的实测（假阳性、假阴性、归属漏洞）」。我不知道泽昊那边的 Reader/Verifier 对 Photoshop、Mail、Figma 这种状态在应用里的软件做到什么程度，要问他。

### 1.2 鸣谦这边也遇到了「评分器让数据不可信」，并给出了处理口径

- Round2（DeepSeek Hybrid，First50，50 题）：28 个 1 分、8 个 0 分、14 个 null；**null 单列，不当 0 分也不当成功**；有效评分成功率 28/36 = 77.78%，全任务得分率 28/50 = 56%。8 个 0 分里有 1 个已复现的评估误判（Excel 日期表示变了，排序和整行内容没错），保留原始 0 分但标注误判。14 个 null 里 9 个是 Chrome 任务卡在评估容量限制。
- 「评估修复」：34 条原始 null（其中 2 条是 setup 问题，所以评估问题 32 条，涉及 18 道题）。原因包括：单步证据太长、Judge 未调用就报错（14 条，原因是 AX 文本很长，以及图片的 base64 编码被当作文本计长）；综合评分超限（2 条）；最终复核只收到首步或一张图把已有结论变成 unknown（4 条）；业务内容通过但「全程没有禁止操作」仍为 unknown（7 条）。修复后补评 **30 条为 1 分、1 条为 0 分、1 条仍 null**，剪映变速保留 null。文中强调「不是降低通过门槛」，核心是让任务要求、足够证据、评估器如何用证据统一起来；其中有她「明确批准的规则变化」，不能全部称为原评分规则下的纠错。
- Round1 的核心提醒：服务与评估故障已经足以影响排名；**Preview 10 批全空分、食品库存旧路径 9 批空分，后者修了收集路径后为 1 分，「不能当模型进步」**。

对汇报的用处：我们的「1 分不等于做成」不是孤例。他们的口径（null 单列、误判保留原分并标注、不把评估故障当模型能力）可以直接借来，作为我们 Mail/Figma/纯色图问题的对照。注意区别：他们的问题主要是评估器的**容量与证据选取**；我们的主要是评分**规则本身**（旧草稿能过、纯色真导出被误杀、题面与判据对不上）。

### 1.3 鸣谦这边给了「面向 DeepSeek 的造数据方向」，可以和我们的数据质量问题对着看

文件：`First50 Round2 · DeepSeek Hybrid 轨迹分析.md` 第 4.1 节（DeepSeek 是被训练模型，不是 teacher）。六个方向：①输入目标与不可变字段保护（优先级最高；编辑前建副本或基线、操作后逐字段对比）；②精确数值与尺度变化；③对象和要求的绑定（加入「文字都存在但放错对象」的负例）；④完整而独立的核验（奖励最少必要检查，不奖励日志长度）；⑤有界的 GUI 恢复；⑥计划到执行及终止判断（加入「只有计划」的对照）。数据筛选一条：**原始 1 分仍需检查；零分但评分错的可作「正确执行＋错误评分」的分析样本，不能当负例动作；null 暂不作为成功标签。**

对汇报的用处：这几条和我们的发现能对上：①对应我们 Mail 归属漏洞（旧草稿能过，需要基线）和 `preview-packet` 类问题；③对应我们「题面和判据对不上」（要求绑定对象，判据只看全文包含）。「原始 1 分仍需检查」是同一立场，可以说我们的验证状态地图就是在做这件事。
