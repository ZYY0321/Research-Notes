# 桌面应用 GUI 训练任务的出题方法：现有做法、暴露的问题与可借鉴的方案

## 一、两轮出题的做法

### 第一轮：一题一功能的基础题及其变体（11 月上中旬）

第一轮面向 WPS 表格、剪映、美图秀秀三个应用，共出了 522 道基础题。每道题只考查一个功能。题面只写要求的结果和输出文件名，不写菜单路径；不禁止使用命令行，但结果必须经过应用本身产生。评分对照合成素材的已知规律来判断：剪映看导出的视频，美图看保存的图片，WPS 看由 WPS 保存的文件。

在这批基础题之上，又做了四种变体：
- **命令行优先版：** 同一批题换成「优先使用命令行」的提示，专门收集用命令行完成的轨迹。
- **新应用短题：** 用来先验证 Obsidian、OBS、LibreOffice、Numbers、Keynote 等应用能在这套框架里跑通。
- **成对题：** 同一个目标出两道，一道从正常起点开始，一道在起点故意堵住其中一步，用来观察模型能否察觉受阻并换一种做法。
- **体检题：** 每个应用一道，只检查点击、拖拽、输入、组合键等基本操作能不能用。

### 第二轮：从官方功能分组批量生成（E31，11-22 起）

第二轮面向 Photoshop、Mail、Figma，改为由一条生成管线批量出题：
1. 按各应用官方帮助文档的功能分组，切成 48 个区域。
2. 每个区域由生成模型写出规格：这个功能在界面的哪一步，成品是什么文件，文件里哪个字段能证明做成了。
3. 再把规格落成四个文件：题面、初始化脚本、评分脚本、自检用例。
4. 经过机器检查和后处理（统一题面前缀、Mail 清理脚本、同质题标注）后入包。

主题包共 196 道，其中可自动评分的 81 道。之后又迭代了四次：
- 补跑第一轮空缺的区域；
- 为一部分能读取文件的「不可评分题」补上评分；
- 修正环境问题后重新打包 Photoshop 题；
- 收紧评分规则。

## 二、暴露的问题

### 可评分的比例与功能的价值相反

196 道题里有 115 道无法自动评分，而且集中在核心功能上：Figma 的组件、原型、协作、分支保存在云端，Mail 的规则和设置保存在服务器或应用内部，打印和设置面板的状态只显示在屏幕上。能评分的大多是「绘制后导出」这一类。补跑空缺区域能补上被遗漏的题，但补不上「结果读不到」的题：补跑的几个区域题目都通过了机器检查，可评分的数量仍然是零。

### 出题、评分和自检出自同一个模型

自检用例与评分由同一个模型写出，所以「自检全部通过」只能说明它们彼此一致，不能说明评分正确。有一道题的自检把一张整张纯色的图当作正确样例，而对抗审计证明，正是这种纯色图能骗过评分。

### 入库检查不测伪造产物，也不核对题面与判据是否一致

机器检查能挡住两类问题：题目装不起来，以及评分函数写反了。它挡不住另外两类：题面写了但评分没查，以及伪造产物也能拿到满分。这两类恰恰是本周发现的主要问题。

后来补做的对抗审计中，107 道可评分题每一道都至少有一种伪造产物能拿到满分。另外，在 86 道可评分题里，有 28 道题面要求的关键内容评分没有检查。例如题面要求密送，评分只检查主题和正文。

### 评分不区分本次产物与环境中原有的内容

评分检查的是「环境里现在有没有这个结果」，而不是「这次运行有没有做出这个结果」。所以环境里原有的合格内容也能骗过评分：开跑前就存在的合格旧草稿、他人已有的设计稿、模型自己可以修改的基线文件。

### 环境前提没有写进题包

下面这些前提只在实际运行时才暴露出来，每一项都至少浪费了一个晚上或一个批次：
- 应用是否已登录；
- 初始化脚本能用哪些库；
- 输出目录是否会触发系统授权框；
- 需要哪个版本的驱动。

它们都不是题目本身的错，却都被记进了题目的成绩。

### 题包缺少版本清单，题量口径不唯一

管线在两天里改了四次，每次改完都没有给题包和数字标版本号。结果，规格数、通过检查数、可评分数各自出现了好几个互相对不上的值。同质题（同一操作的不同问法）只做了标注、没有删除，「不同功能的题数」也因此虚高。

### 成对题的分数只反映终态

成对题的本意是比较两个版本的差距，看模型受阻后能否察觉并换路。但复盘发现：什么都不做，两个版本都得 0 分；用脚本直接写出目标结果，两个版本都得满分，被堵住的版本也一样。所以这组题的分数分辨不出「在界面上绕过了障碍」和「直接把文件写对了」。这批题已经暂停扩量。

## 三、可借鉴的方案

### 以真实材料构建工作环境，再围绕环境设计任务（刷榜方向）

这个方案先收集软件文档、操作教程和真实材料（邮件、日历、财务表格、文档、多媒体项目等），由 agent 构建一个有背景、有历史、信息自洽的角色工作环境，再在这个环境里找真实的工作需求作为任务。评分拆成两部分：一部分读取应用状态，另一部分做判定。评分器写完后，由独立的 agent 用正确结果、等价写法、未完成的初始状态、遗漏一项要求、对象关联错误、旧版本内容、状态不可读七类样例去测试它。验证通过的初始化脚本和评分组件放进素材库复用。

对我们的启发有三点：
- 出题时就同时设计评分，并且由出题以外的角色来测试评分；
- 任务从真实环境中的需求长出来，而不是从功能清单逐项翻译；
- 成功的组件要积累、复用，不要每道题从零生成。

它的前提是应用状态可以读取。这在 Photoshop、Figma、Mail 上恰恰是难点，需要按应用补充读取方式，并加一项「结果是否由本次操作产生」的测试。

### 题面必须写明所有被评判的要求（测评方向）

测评方向在修复评估时坚持了一条原则：凡是智能体完成任务必须知道的要求，都要写在题面里，不能变成隐含的扣分条件。同时区分「编辑过程」和「最终由哪个应用保存」，不把两者混为一条要求。我们早期「文件必须由 WPS 保存」这条隐含要求，正好是这条原则要防止的情况。

### 阶段二的方向

阶段二要求跨应用的任务、真实的初始文件和更多样的初始状态。按我们这两轮的经验，这三点都会让任务结果更分散，更难落在一个可以直接读取的文件里，所以验证方式必须在出题时一起设计。

### 公开基准的做法

近期的长程桌面基准不再只报二值的「完成或未完成」：有的为每道题设置多个检查点，报告部分得分；有的把题拆成有顺序的子目标，分别判断。这种做法的好处是，一道题即使没有全部完成，也能定位卡在哪一步，适合跨应用的长任务。

## 四、对下一轮出题的含义

1. **把「结果存放在哪里、用什么方式取证」提前到写规格的阶段。** 写不出取证方式的功能，要么换一种任务设计，要么明确记为暂不覆盖。
2. **出题、评分、正反例和评分审核由不同角色承担。** 正例至少有一部分来自真实应用。
3. **入库前必须通过的检查：**
   - 空跑得 0 分；
   - 用捷径直接写结果得 0 分；
   - 伪造产物得 0 分；
   - 合法的等价写法得满分；
   - 环境中预置合格的旧结果时，得 0 分。
4. **把环境前提写进题包，每个题包附一份版本清单，** 对外只引用清单上的数字。
