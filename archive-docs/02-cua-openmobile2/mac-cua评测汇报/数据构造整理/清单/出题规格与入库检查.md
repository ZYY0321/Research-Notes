# GUI 训练任务的出题规格与入库检查

本文给出一道桌面应用 GUI 训练任务在写规格时必须回答的问题，以及进入题包之前必须通过的检查。它可以直接作为出题流程或出题技能的验收标准，也可以用来审阅一套已有的出题流程。两轮出题暴露的问题，例如核心功能评不了分、伪造产物能拿满分、环境中原有的结果能骗过评分、题面要求评分没有检查，几乎都可以在规格和入库阶段挡住；一旦进入批量生产，就只能在质检阶段逐条补救。

## 一、规格必填字段

| 字段 | 要回答的问题 | 说明 |
| --- | --- | --- |
| 功能与数据目的 | 考查哪个功能；这道题是为了保底（不遗忘）、补覆盖（新功能、新应用）还是提难度（真实业务） | 三种目的的验收方式不同，混在一起只能用题数和通过率报告，分不出补的是哪一种 |
| 目标路线 | 这道题收的是界面操作数据，还是结果导向数据 | 两者的合格标准不同：界面数据不接受脚本直接写出结果，结果导向数据接受，但要求如实说明手段 |
| 结果存放层 | 结果落在哪一层：可解析的文件、尚未解析的文件、应用内部、本地数据库或配置、云端、仅显示在屏幕上 | 决定取证方式，见《各应用取证方式与评分结果类别》 |
| 证据字段 | 哪个字段能证明做成了 | 写到具体字段，例如 PSD 中的图层结构、xlsx 中的单元格值、Figma 节点树中的组件 |
| 最像做成但没做成的终态 | 最容易与完成混淆的错误终态是什么，判据凭什么把它判为失败 | 写不出来的题不入包。例如两个叠放的矩形与一次并集在导出图上相同，这道题就不能只看导出图 |
| 题面要求与判据的对应 | 题面中的每一条要求对应哪一条判据，或者明确标注「不评」 | 评分不能检查题面没有写的要求，题面写了的要求也不能漏检 |
| 要求与取值分开 | 题面写的是要求还是具体取值 | 「找一个空闲时间安排会议」是要求，必须写在题面；具体是哪个时间属于取值，应当由模型从环境中查找，由评分器从同一个环境算出期望结果。把取值写进题面，任务会退化成照着执行 |
| 本次运行的唯一内容 | 能否在题面中写入一个本次运行独有的内容，例如邮件主题、图层名、评论文字 | 环境中原有的结果因此天然不合格，是成本最低的归属保障 |
| 环境前提 | 是否需要登录、初始化脚本依赖哪些库、输出目录是否会触发系统授权框、需要哪个驱动版本 | 这些前提只在运行时暴露，会被记进题目的成绩，必须写进题包 |
| 无法完成时的出口 | 环境中确实无法完成时，模型应当怎样报告 | 没有这个出口，按分数过滤会只留下绕过去拿到分的轨迹 |

## 二、入库前必须通过的检查

| 检查 | 做法 | 期望结果 | 不通过时 |
| --- | --- | --- | --- |
| 开跑前空跑 | 初始化完成后、模型开始之前评一次分 | 未通过 | 这道题记为环境问题，修正初始化后再检查 |
| 预置合格旧结果 | 在环境中放入一份合格的旧结果，不做任何操作，评分 | 未通过 | 评分不区分本次产物，需要加基线或唯一内容 |
| 伪造产物 | 由出题以外的模型构造「看似完成、实则未完成」的产物 | 未通过 | 补判据，同时检查收紧后是否误杀等价做法 |
| 逐条破坏题面要求 | 从正确终态出发，每次只破坏一条要求 | 每一种都未通过 | 补上对应判据，或在题面中删掉这条要求 |
| 合法的等价做法 | 换一种操作路径或导出方式，内容正确 | 通过 | 判据过严，放宽或改取证位置 |
| 真实应用产生的正例 | 至少一部分正例由真实应用保存，而不是由脚本按书面条件生成 | 通过 | 判据依赖了脚本生成的特征，需要修正 |
| 脚本直写捷径 | 仅对界面数据包：不经应用界面，用脚本直接写出目标文件 | 未通过，或能被过程记录识别 | 这道题不能用于界面数据包，可以转入结果导向包 |
| 题面与判据一致 | 逐条核对第一节中的对应关系 | 没有漏检，也没有超出题面的判据 | 修改题面或判据 |

## 三、角色分离

出题、写评分、构造正反例、审核评分这几个环节不应由同一个模型完成。题面、评分和自检出自同一个模型时，自检通过只能说明三者彼此一致，不能说明评分正确：曾有一道题的自检把整张纯色的图当作正确样例，而纯色图正是能骗过评分的伪造产物。分角色有效的前提是审核方掌握生成方没有的信息，例如真实应用保存的样例、从环境中读出的状态、人工判定的结果；只是换一个模型来写同样「读一个文件、查几个特征」的评分，作用有限。

## 四、题包版本清单

每个题包附一份版本清单，记录规格数、通过检查数、可评分数、同质题去重后的功能数，以及生成管线的版本。生成管线改动后，题包和数字同时更新版本号。对外只引用清单上的数字。

## 五、真实业务题的最低验收

真实、复杂的业务题至少满足三条：题面不含具体取值和结论；判据在「最像做成但没做成」的终态上判为失败；合法的等价做法得满分。题面写简单之后误判容易增多，原因通常是评分检查的是一个具体取值，而题面只给了一个要求。评分应当检查要求本身：由读取器从同一个环境中算出所有满足要求的取值，再判断模型的结果是否落在其中，并用多种合法取值作为等价做法测试评分。当前单元格级判据最完整的是 WPS 表格，适合最先尝试，所得数据按结果导向标准把关，不作为界面正例。

## 六、审阅一套出题流程或出题技能时对照的问题

1. 它的输出里有没有「结果存放层」和「证据字段」？没有的话，生成的评分大概率只会读导出文件。
2. 它会不会写出「最像做成但没做成的终态」，并用这个终态测试评分？
3. 题面中的每条要求能否对应到判据？过程约束（例如「只用界面操作」「不得结束应用进程」）如何对应？
4. 题面写的是要求还是取值？
5. 自检用例和评分是否出自同一个模型？正例有没有来自真实应用的？
6. 有没有开跑前空跑和预置旧结果这两项归属检查？
7. 环境前提是否写进了题包？
8. 同质题是去重还是只做标注？题量是否有版本清单？
9. 可评分的比例在各功能上是否均衡？评不了的功能是记为「无法评分」，还是记为「等待读取器」并有明确的补齐路径？
10. 规模扩大后是否模板化？同质题按「用到的功能组合 + 证据字段」判断，而不是按题面措辞判断。
11. 环境中是否刻意放入了历史文件、旧邮件这类背景材料？背景越丰富，环境里原本就存在合格结果的可能性越大，归属检查越不能省。
12. 读取状态的通道是否对被测模型可见？如果可见，任务可能退化成「读一下就做完」。
