# 任务构造与判定

本节压缩已交付的 `docs/task-and-verifier-handoff/`（`00`–`04`），并补上验收阶段写过、交接目录未单独成章的闭环单位。扩写任务或接奖励时打开原稿，不要只靠本页。判定用于过滤监督轨迹，并作为强化学习的零一奖励：必须读业务状态，不能信赖模型自报完成。

一个应用的验收单位（题、函数、判定不能拆开交）：默认数据与场景数据；固定模拟时间；来自用户目标的任务；稀疏函数（辅助检索或预填，不代替整题、不泄漏答案）；读状态的判定；仅界面与混合在同一任务实例、同一初态、同一时钟、同一判定下各跑；写入后从另一页面、函数或状态快照回读。数据、界面、函数、判定对同一实体标识不一致，视为环境债，先修再训。

**已部署判定** 表示运行器能按终态执行断言。**已证明正确** 还需要正例、反例、近错终态与真实成功轨迹。Agent 成功率不能证明判定正确。

## 1. 一条任务最少包含什么

`instruction` + 涉及的应用 + 开局准备 + 候选函数 + 终态目标 / 额外检查 + 预期允许改动的路径。

每条从干净初态开始，不依赖上一条留下的订单。有写入的任务，初态直接判定必须失败。函数不得做成「一次调用即整题完成」的答案接口；敏感提交仍走界面。

公开题面只写自然语言目标。逐步点击、状态字段名、路由、函数名、判定器、内部编号、标准答案均不得出现在题面中，放入隐藏设计或检查代码。

本项目不做指令模糊度分级。日期窗口、排序字段、集合是「全部 / 恰好 N / 至少一个」、禁止改动的对象，须在题面中说清。难度不靠句子变长或多点几下。可稳定验证的来源包括：跨应用传递事实、排序与聚合、时间推理、条件分支、多渠道写入一致、集合完备、干扰项消歧。

## 2. 两套已跑通的造题流程

新复刻应用铺开，优先复用 **0815**。要测量「函数在何种任务形状上有用」，复用 **自建 V1–V4 的 spec**。官方已挂函数的应用走 `MOBILEGYM_HYBRID_GUIDELINE.md` 的五层契约（题面 / 开局 / 环境 / 函数面 / 判定），生成与审查分离，并单独门禁「仅界面可完成」。不要把 0815 的 31 个新应用硬套到官方线上。

### 2.1 0815：事实包 + 截图生成（218 条）

采集 → 生成候选 → 人审 → 写成 spec 与判定 → 冒烟 → 界面与混合各跑一遍。一次只做一个应用。输入是压缩事实，不是整仓源码：导航与可达性、实体与可写字段、函数参数与明确不支持项、真实种子编号（禁止编造不存在的商品）、关键页截图（筛选、详情、订单、支付、草稿、设置；动态路由必须用真实编号）。对照结论：截图加精简结构，比只摘要或只截图更少编造功能。

生成当时用 Claude Sonnet、温度 0。输出拆成公开题面与隐藏设计（路径、字段、判定意图、不可执行点）。先多后删：重复、只打开页面、只查一个字段、数据不支持、换应用名仍成立的万能题。原文存档，审查稿另存。

审查闸门（生成与执行必须分开）：题面是否像用户目标、有无检查腔；功能在页面 / 写入 / 系统能力上是否有证据；对象当前状态是否允许；搜索词与规格是否在默认数据中；能否独立开局；多步是否服务同一目标；界面与函数如何分工、会否一函数做完整题；判定能否区分错实体、错规格、只做一半。结论为接受、改写、补数据、修应用或拒绝。

当时 31 个应用、224 个候选删 6，留 218。这 218 条已补入声明式语义契约并完成首轮变异审计，不再停留在只有题面。后续应用真实成功轨迹与复杂正例夹具校验边界，而不是重写一套判定。

### 2.2 自建 V1–V4：人定类别后写 spec（已交付的 76 条属 V4）

先定类别，再对照默认数据与函数说明逐条核对，在 `hybrid_tools_selfbuilt_v*/defs/specs_<应用>.py` 中写 spec。查询类用笔记包含 / 不包含；写入类用额外检查读状态差分。冒烟后两种模式各跑一遍；失败先归因环境、题目、判定，再归因模型。

V1 的 78 条多为点名比较后记笔记，两种模式成功率都虚高。V2 三个杠杆：走没有函数覆盖的入口；全量多约束筛选并放置干扰项；应用 A 的事实写入应用 B，尽量读 B 的状态而非只读笔记。V3 三个轴：先看到关键信息再绕路后使用；名称相似的错入口且不给消歧；去掉笔记脚手架、直接对状态做差分。**不做模糊指令。**

V4 四类边界用于让界面与函数的差异可被看见，而不是堆导航：

- 对象已在购物车 / 收藏 / 订单中，按编号核对，不要重新搜索；
- 一次写入多个结构化字段；
- 函数返回聚合或最值，任务要的是具体子项；
- 搜索函数必填关键词，任务却要求无关键词全量扫描。

当前交付的自建 V4 为 76 条，判定经过空操作审计。实现入口：`hybrid_tools_selfbuilt_v1/base.py`，模板目录 `hybrid_tools_selfbuilt_v4/defs/`。

官方 Hybrid V1–V6 的难度来源见指南，与上列杠杆并列，不另发明一套。

新应用若要接入：按 0815 做事实包 → 生成公开题面与隐藏判定意图 → 人审可执行性 → **不要停在题面**，按下一节写成检查并做空操作、正例、近错变异。若目的是比较界面与函数，额外标 V4 四类，避免退回「搜三个名字记笔记」。发现数据与界面不一致的检查顺序：默认数据 → 富化后的状态 → 界面列表/详情是否可达 → 按钮是否写入状态 → 函数是否读同一份字段 → 判定是否只看路由 → 重置后第二次运行是否串局。同一节点反复失败、函数与界面冲突、目标数据找不到、写入后回读失败，优先于纯视觉问题。

同一任务若只有一个写死实体，模型容易背题。设计上希望参数或场景数据可换；**现行评测复跑并不启用多种子**，换实体须同时改默认数据、题面与判定。

## 3. 判定写什么

| 任务类型 | 判法 |
|---|---|
| 改了业务状态（下单、记账、收藏、事件、加购） | 必须对比开始前与结束后的字段。笔记最多辅助，不能当唯一依据。 |
| 信息写入笔记 | 包含锚定事实，同时用不包含挡住最易编造的干扰词。并尽量核对函数返回字段与界面是否同一份数据。 |
| 明确要求其它对象不动 | 反向断言：其它订单、购物车、收藏不变。 |

不检查是否调用了某个函数、是否经过某条路由（除非题面本身是打开某页）。同一终态允许界面或混合两条路径。

关系式从初态计算左边、从终态验证右边，不把关键常数写进题面或判定。例：最大一笔支出记入账本，判定比对初态最大值与新账单，而不是写死金额；购物实付记账同理。开局时目标若已满足，必须先破坏，否则空操作会通过。不要在判定中重算一套与界面不一致的价格逻辑，使用应用已有字段。

**该严：** 错对象、错金额、错日期、错规格、漏做写明的子任务、动了禁止动的对象、只完成一半。  
**不该严（假阴性，不能当训练信号）：** 同义、空格标点、分数写法、时间戳差数小时、金额一分钱级格式差、题面未要求的隐藏路径（必须先搜索、必须用某函数）。  
**不该松：** 只含关键词而后半胡编；初态已满足；用到达某页代替写入。

原则：指令明确的结构化要求要严；表达形式要松；未写进题面的不要偷加。

自建套件复用 `hybrid_tools_v1/verifier.py` 的声明式目标，以及 `EXTRA_CHECKS` 中按任务编号读取状态做差分。官方线走 `BaseTask.check_goals`，规则见 `TASK_AUTHORING_GUIDE.md`、`TASK_CODE_SPEC.md`、`add-a-task.md`。

## 4. 如何验证判定本身

成功率不能证明判定正确：过松抬高成功率，过严打死做对的轨迹。

早期两套使用过不跑执行模型的脚本（`hybrid_tools_selfbuilt_v1/`）：

1. 空操作审计。初态与终态相同且无作答，必须全部失败，否则泄漏。笔记类用其包含条件拼一条显然正确的笔记，必须通过；状态类须手工构造正确终态。曾发现瑞幸购物车数量被当成商品编号，正确答案永远不可满足。
2. 函数与默认数据一致性。把历史轨迹中函数返回的标量对回默认数据，抓「函数与界面不是同一份数据」（环境问题，不是模型能力）。

官方线要求离线正例、反例、缺字段测试。`TASK_TESTING_GUIDE.md` 的表述是：没有测试的判定就是未验证的赌局。

218 条另有约束级变异：由断言自动构造正确终态，再破坏字段、集合成员或部分完成条件。470 个错误终态全部被拒绝；语义约束覆盖约 98.53%。187 条自动正例通过；31 条复杂终态通用构造器尚不能完整合成，须专用夹具或真实成功终态补证。**不能据此宣称已获人工金标准。**

冒烟下限：初态判定失败；改为目标态通过；只改错对象或只完成一半失败。

旧集人工对照：30 条 × 两种模式共 60 次，与人同向约 87%；「人认为未完成、判定放行」为 0。不一致主要是过严。215 上无同等规模新抽查。369 基础设施验收拦住过约 190 次「模型称完成、库未通过」。

已知会伤害奖励的情况：开放文本因标点失败；判定仍绑定必须停在某搜索页（惩罚合法函数路径）；美团进店崩溃、打开应用超时、日历卡在秒级（环境先停，不应记为模型失败）；页面只改界面未写回状态（两条路径一起误判）；上下文被长思考撑满（约 23 条会报错；改上下文步数后的补测不可与原 215 混报）。模型把星期反推成 2020 年，属模型错误，判定按 2026 锚点为公平。

## 5. 奖励与诚实边界

成功标志为稀疏零一奖励。子检查通过比例是终态断言比例，不是逐步关键帧，可作粗提示，不能代替成功。声明外改动先记录，不宜立即当作失败。不要奖励自报完成、不要奖励「调用过函数」、不要仅因步数少给分（低成功率会早停）。

| 说法 | 实际 |
|---|---|
| 环境能读状态 | 系统层可以。执行模型不能。 |
| 369 条已有判定 | 可执行。不等于每条已获人工金标准。 |
| 218 条可直接训练 | 须按逐项断言与真实终态筛选。31 条复杂正例未自动补齐。 |
| 按手册生成判定一定对 | 不保证。必须对默认数据、必须跑正反例。 |
| 界面与函数共用状态故判定自动公平 | 设计目标；若某页只改界面，两条路径会一起误判。 |
| 语义原语自动组合、题面一改判定跟随 | 未交付。新任务必须新写并审计判定。 |

制作监督或强化学习数据：优先选取真实轨迹中逐项断言通过、终态可追溯的样本。不要把自报完成、单一总分或「契约已部署」当作正确标签。纳入奖励前至少做第 4 节冒烟四步。
