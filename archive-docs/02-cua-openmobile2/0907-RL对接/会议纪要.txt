本次会议对齐 Open Mobile V2 项目的当前进度、阶段目标、分工安排与时间节点，内容如下：
- 项目当前进展与核心目标
  - 现有阶段成果
    - SFT 阶段达标：当前 3.527b 模型在 pass3 指标上已达 90 分，SFT 阶段效果符合预期，无需再投入核心资源优化
    - 混合调用能力验证：仅用 700 条 MCP+GUI 混合轨迹混训两轮，模型已初步掌握 MCP 调用逻辑，具备进一步优化基础
    - 环境适配完成：张荧滢搭建的环境可直接迁移至 MobileGym，潘正源已完成全流程适配，无需额外跨方支持
  - 问题定位与优化建议：潘正源指出此前 SFT 训练效果不佳的核心原因是学习率设置过高，建议调整至 1E-6 或 1E-7 区间即可
  - 核心优化方向：放弃纯 GUI 方向优化，重点通过 RL 提升 MobileGym 系列得分，强化 GUI+MCP 混合调用效果，接受指标小幅波动
- 数据与算力筹备安排
  - 训练数据迭代计划
    - SFT 数据更新：闫晨阳已将 GUI+MCP 混合调用轨迹扩充至 1700 条，预计次日即可输出对应训练版本，直接供 RL 环节使用
    - RL 数据筛选规则：RL 环节无需过量数据，结合目标积木与原有 160 条数据，合计 500 余条即可满足训练需求，闫晨阳将完成质量筛查
    - RL 数据补充建议：潘正源提出可将过往训过的 GUI only 数据纳入 RL 数据集，进一步提升 MCP 相关指标的表现
  - 算力资源保障：闫晨阳将在次日为潘正源提供 32 张显卡资源，全部算力优先保障 RL 环节，SFT 阶段不再占用核心算力
- 评测体系与 Bench 优化安排
  - 现有验证方案说明
    - 验证流程逻辑：当前任务验证采用 LLM as judge 方案，通过模型交叉评估验证有效性，可识别严重误判、环境及工具问题
    - 验证方案优化建议：闫晨阳建议张荧滢可尝试 OS reward 框架开展评判，对比现有方案的实际效果，进一步提升验证准确率
  - Bench 迭代要求
    - 现有 Bench 状态：MobileGym++ 最新版共 215 条任务，仅完成自动两轮筛选，尚未开展逐条核查，需重点排查漏报、误报问题
    - Bench 调整规则：若后续需补充 Bench 任务，优先采用单任务补测方式，避免全量重跑所有模型，减少重复工作量
  - 评测分工安排：张荧滢将负责基线模型、训练中模型的相关指标评测，闫晨阳将统一提供模型调用 API，无需评测方单独部署
- 关键时间节点与分工确认
  - 核心时间节点对齐
    - RL 迭代节点：潘正源确认，次日拿到训练好的 GUI+MCP 模型后，基于现有 500 余条数据，可在周四前输出首版 RL 优化模型
    - 版本交付节点：项目 DDR 版本需在 9 月 15 日前完成输出，距离 9 月 18 日的摘要截止日仍有一周缓冲时间，可灵活补充实验
- 三方分工确认
  - 闫晨阳职责：统筹项目整体进度，负责训练数据迭代、算力资源协调、基线 API 输出，同步各方进度
  - 潘正源职责：全权负责 RL 环节的调优与迭代，按节点输出对应版本模型，及时同步训练过程中的问题
  - 张荧滢职责：负责 MobileGym++ Bench 的逐条核查，完成各版本模型的指标评测，及时反馈评测结果
