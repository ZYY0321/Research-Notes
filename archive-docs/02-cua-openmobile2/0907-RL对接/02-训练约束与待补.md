# 训练约束与待补

## 0. 跟早期文档对齐时会踩的分叉

根目录 README 面向 369 交付，默认会话是每步重写的 XML。215 写死 `qwen35_session`（见 `00` §4.2）。按 README 默认跑 215，协议已经不同。Kimi 有独立适配，评测条件（每步一个动作、只暴露前台函数、同一判定）保持一致，消息格式不同。

缺 1.4GB 资源包、用 `npm run dev` 跑评测、开着系统代理、并行工人共用一个浏览器页上的函数客户端，都会造成「能跑但轨迹脏」或静默失败。

## 1. 动作、观测、泄漏

每步：界面总入口（点、滑、键入、打开应用、回桌面、结束），或当前前台应用的一个函数（仅混合模式）。桌面、最近任务、控制中心不提供应用函数。

主观测为截图。混合模式另有本轮函数表与上一次调用的固定形状返回（名称、是否成功、输出或错误）。换页或打开草稿会补截图。现行评测只保留最近 3 步观测。

题面不写待抄数值；关系式在判定代码中，不进入观测。函数说明不得写与某条任务重合的例句。截图中的价格与订单号是环境真相，须由模型读取或查询。题单不含期望金额。内部出题总表与作者备注不得进入训练。

步数上限常见为 15 / 30 / 45 / 60。未做成局均步约 26–32，做成局约 18–22。步数低不等于成功。

## 2. 函数面（避免高估混合收益）

可安装应用 64 个；对外口径约 52 个带函数；注册表为 51 个应用、约 333 个命名函数。运行时只暴露前台应用。

约 29 个应用为手写，每个 5–14 个函数（合计约 289）。约 22 个为同一模板，每个仅搜索与列表（合计 44），包括美团、拼多多、闲鱼、微博、滴滴、菜鸟、BOSS、Keep、优酷等。215 中约 68 条只落在后一类。混合模式零次应用函数调用、却与纯界面一成一败的，是点法方差，不能记为函数有效。接口未报错不等于用对返回值。

比较「会否使用函数」应在手写较厚的应用、以及跨应用取值写入的子集上统计。全表调用率可被乱调一次刷高。出题阶段不预标「适于用函数」再只训练该子集，与「正式任务必须保留界面路径」冲突；可在跑完后切子集分析。

将应用函数挂入服务端函数列表可能使小模型更容易调用，须作为对照实验单独报告，不能与现行 215 合并。

## 3. 主表怎么报

同一题单、同一初态、同一判定：仅界面成功率与允许调用函数的成功率并列。辅表：至少调用过的题占比、调用未报错占比、两侧平均步数。不加权合成总分。仅训练混合、仅报告混合，缺少对照。仅界面仍是一等设定。

其它评测或真机轨迹的视觉与动作先验可以复用；本环境的零一奖励绑定本仓库字段名，不能共用。

环境先停（美团进店、打开应用超时、日历秒级、判定自身报错）应从训练分母剔除，记为零会污染梯度。

## 4. 开训前建议补的，与不要做的

可立即做：冻结评测名单（215 或从其再删环境故障 / 过严假阴性后另存，此后不向该名单训练）；对训练候选做初态失败 / 目标态通过 / 近错失败；标签只用成功标志；过程指标分开看，不合成加权分。

判定：放宽开放文本与「必须停在搜索页」；为 31 条补正例夹具或真实成功终态；在 215 的厚应用与跨应用条目上抽一轮人工对照（目标仍是零误放）；将变异审计扩到 215。

环境：修或删除会崩的题，再进入奖励。界面与函数必须走同一业务动作。

不要：删除混合不涨分的题来抬指标；预筛「只留适合调函数」；给调用次数加正奖励；等待环境自动出题且判定跟随；在仅有两个函数的应用上继续铺单步题；把 369 口头成功率当基线；用换商品名冒充增广。

优先增广的任务形状：一侧取证一侧写入、两侧写入（实付记账）、多源进入同一条记录、会议 / 文件 / 邮件 / 日历。增广时默认数据、题面、检查、正反例必须同时修改。
