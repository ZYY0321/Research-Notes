本次会议围绕移动端 GUI + Tools 混合调用 Agent 配套 Benchmark 构建工作开展交接与方案对齐，内容如下：
- 项目背景与核心定位：    - 行业路线共识
- 路线争论结论：近半年 GUI Agent 领域存在 GUI 与 CLI 路线之争，当前行业共识为未来通用 Agent 采用二者混合调用模式，GUI 作为无 CLI 场景的兜底方案。
- 现有基准差异：现有 MobileWorld 仅支持外部 MCP 调用，AndroidWorld 仅支持纯 GUI 操作，AppWorld 仅支持纯 MCP 调用，均未覆盖 APP 内混合调用场景。
[图片]
  - 项目定位说明：属于前瞻性试验性工作，模拟未来 APP 渐进式开放接口的真实状态，无需严格匹配现有商用 APP 的真实接口开放规则。
  - 可行性验证案例：以音乐 APP 新建歌单任务为例，未开放创建歌单 Tools 时采用 GUI 操作，后续环节调用对应 Tools 完成，最终通过 GUI 点击播放收尾。
- Tools 设计与环境基础能力
  - 环境选型优势
    - 底层特性适配：基于 MobileGym 底层构建，其底层数据结构化存储、功能函数可复用的特性，可保障 Tools 调用与 GUI 操作的执行结果完全一致。
    - 状态一致性保障：所有操作均直接修改底层统一存储的数据库，可避免函数调用与 GUI 操作导致的页面数据状态不一致问题，仅需少量校验即可。
  - Tools 设计规范
    - 粒度定义标准：定位为 APP 内原子业务能力，而非完整任务封装，覆盖粒度介于单步点击与全功能调用之间，优先开放查询、导航类能力。
    - 覆盖度设计逻辑：不追求全功能覆盖，刻意保留部分功能无对应 Tools，避免所有任务均可通过单条或少量 Tools 直接完成，保障混合调用必要性。
  - Tools 开发与配置
    - 开发方式说明：全部 Tools 由 Code Agent 生成，仅需做合理性校验，无需人工逐行编写，当前已完成 20 个 APP 共 200 余个 Tools 开发。
    - 最终规模规划：最终目标扩展至 60 个 APP 共约 500 个 Tools，单 APP 平均配置 10 个左右 Tools，按功能分为查询、导航、写入等多个类别。
    - 动态推送逻辑：Runtime 不会全量推送所有 Tools，仅根据 Agent 当前所在前台 APP 推送对应 APP 的可用 Tools，降低无关 Tools 对 Agent 的调用干扰。
- Agent Runtime 与评测模式设计
  - Runtime 实现逻辑
    - 指令适配规则：在原有纯 GUI 操作的 System Prompt 基础上，追加当前可用 Tools 的调用说明，要求 Agent 以 XML 格式返回调用指令，由 Runtime 统一解析执行。
    - 执行逻辑对齐：Tools 调用的执行逻辑与原有点击、输入等 GUI 操作无本质差异，无需额外改造核心执行链路，仅需补充对应解析模块即可。
  - 双评测模式支持
    - 模式切换逻辑：同一套任务、环境初始化、Verifier 规则同时支持纯 GUI 与 GUI+Tools 混合调用两种评测设置，仅需通过开关切换即可，无需重复构建任务集。
    - 训练数据采集：环境支持一键切换两种模式，后续分别采集纯 GUI 与混合调用的 Agent 执行轨迹，可直接用于后续模型的 SFT 与 RL 训练。
- Benchmark 构建与迭代规范
  - 迭代闭环流程
    - 标准迭代链路：采用「Code Agent 生成任务 → 强模型执行 → 校验错误 case → 迭代修正」的闭环流程，每版任务需迭代 3-4 轮保障合理性。
    - 错误校验规则：需人工抽检模型错误 case，区分模型能力不足导致的错误与环境、指令、Verifier 问题，优先修正后者避免误判。
  - 核心设计原则
    - 指令设计标准：采用与 AndroidWorld、OSWorld 对齐的高层次自然语言指令，不做 step by step 步骤说明，无需引入用户交互询问逻辑。
    - 结果校验逻辑：Verifier 完全基于环境底层数据校验，不绑定具体执行路径，优先避免 Agent 合理完成任务却被误判为失败的问题。
    - 经验复用要求：可借鉴过往真机 Benchmark 构建经验，合理引入任务约束条件，优化指令与 Verifier 的对齐逻辑，提升任务的合理性与区分度。
  - 迭代进展与目标
- 当前版本状态：已完成 V1 至 V6 共 6 个版本迭代，当前 V6 版本包含 76 个任务，覆盖 20 个 APP、200 余个 Tools，强模型当前成功率约 80%+。
- 参考资料支持：将同步提供 CUA Desktop 基准相关文章、OSWorld V2 任务设计录屏作为参考，辅助理解长程任务的设计逻辑。
- 最终规模要求：最终任务总量控制在 150-200 个即可，无需追求数量，逐步增加长程跨 APP 任务占比，引入合理干扰项提升任务难度。
[图片]
    - 难度调整目标：通过增加任务约束、拉长执行链路等方式，最终将强模型评测成功率压至 60%-70% 区间，保障不同模型间的区分度。
  - Verifier 设计要求
    - 对齐规则说明：需与指令内容严格对齐，不得追加指令未提及的校验项，针对时间格式、文本表述差异做容错处理，避免不必要的严格校验。
    - 评测方式选择：当前阶段暂不引入 LLM 做评测，全部采用规则化校验逻辑，仅在涉及复杂文本匹配场景时，再评估是否引入 LLM 辅助校验。
  - 其他设计规范
    - 环境初始化规则：每个任务执行前动态加载专属初始化数据，固定环境时间为某工作日上午 9 点，避免动态时间导致的任务失效问题。
    - 防泄露要求：需避免 Tools 描述中出现与 Benchmark 任务重合的示例，防止任务信息泄露，所有迭代过程的典型问题与修复轨迹均已归档可查。
