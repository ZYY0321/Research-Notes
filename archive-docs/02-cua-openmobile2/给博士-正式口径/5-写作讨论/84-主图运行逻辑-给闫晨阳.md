## 1. 这个环境是什么

MobileGYM++ 是跑在浏览器里的手机模拟器。页面是一个 React 单页应用，外壳看起来像 Android：状态栏、桌面、最近任务、返回键、输入法。外壳下面同时装着操作系统层和几十个第三方 App。评测进程用 Playwright 打开这个页面。发给模型的观测主要是截图，外加本轮允许调用的函数表。模型看不到整机业务数据。

整台「手机」的业务真相不在像素里，而在一份可以整机读出、整机写回的结构化状态里。操作系统把这份状态挂在页面全局对象上：读的时候得到一个大 JSON，里面有操作系统字段（时钟、设置、硬件）和 `apps.<应用标识>` 下面每个 App 自己的业务对象。重置或灌初态，就是把这份 JSON 换掉。任务开始前记下它，任务结束后再读一遍，两份 JSON 一对比，就知道这局改了什么。

### 1.1 每个 App 自己的业务状态库

每个 App 在自己的目录里维护一份内存业务库。实现上是 Zustand：页面从这份库渲染，按钮和表单的写入走库上的业务函数，不另开一套后端。启动时用 `data/defaults.json` 灌进去账号、订单、会话、商品、账单这些初态；有的 App 还会在加载时补全展示字段，例如支付宝会给转账记录补上类别和展示标题。评测读到的 JSON，就是这份库序列化之后的样子。

所以「库里有账单流」不是比喻。支付宝库里有一个转账记录数组。账单页列表读的是这个数组。搜索账单的工具过滤的也是这个数组。判定要看花了多少钱，读的还是这个数组。界面点一下、工具调一次、判定查一次，三件事落在同一份对象上。

这件事决定了后面几乎所有设计：

- 界面和工具只要走同一套业务函数，终态就会对齐，不需要两套判定。
- 任务是否做成，看库里有没有出现该出现的写入，不看模型点过哪、调过哪个函数。
- 工具禁止直接整库覆盖。整库覆盖只留给任务准备和整机重置。工具必须调用界面已经在用的那个加购、发消息、建笔记。
- Agent 读不到这份库。它只能看截图，或者通过工具拿到库里被故意裁短过的摘要。

导航也是结构化的。每个 App 有一份路由、跳转和可点动作的声明。静态分析、出题、深度统计都读这份声明，不靠从源码里扫字符串。

操作系统层负责任务栈、返回、跨 App 跳转、剪贴板、通知、权限、统一时钟、定位。时钟固定在 2026-07-12 09:00:00。所有日期计算必须走时间服务，页面里不能自己取墙钟。相对日期按这个锚点算。每个任务开始前加载该题自己的初态，避免上一题或真实日期把题判废。

Python 侧把这个页面收成三个动作：重置、走一步手势、读观测。自己接训练循环时用这三个接口即可。判定仍读各题声明的字段，和走哪条动作路径无关。

### 1.2 一局开始时状态怎么就绪

一条任务被创建之后，环境按固定顺序灌好，再把第一张图交给模型：

1. 整机重置，只预载本题用到的 App。
2. 把这些 App 打开一次。业务库是第一次挂载才建立的；重置会清掉本地存储，不先打开，后面读到的是空库。
3. 若 defaults 不够，例如缺某个联系人，在这里补。补的是库里已有结构上的增量，不是为了控难度另塞一套假表。
4. 再读整机 JSON，从里面抽样本题参数：哪一笔支出最大、发给哪个联系人。
5. 参数定了之后再改一层。若目标是「把某开关打开」，而 defaults 里这个开关本来就是开的，这里必须先把它关掉，否则模型一步不走也会被判过。
6. 回到桌面，拍第一张图。同时把此时的整机 JSON 存下来，作为判定的「开始前」。

### 1.3 App 怎样被装进这台模拟器

操作系统不维护一份手写花名册。一个 App 只要在约定目录里交出清单文件、入口组件、业务库、初态和导航声明，编译时就会被扫进去，出现在桌面上。人侧的复刻过程是：对着真机定范围、录屏截图、答选择题、审核、走查；代码由模型写，机器检查覆盖率和空按钮。走查卡三条：看着能点的就必须能点或明确标未开放；同一组控件不能一半能用一半装死；宁可不做，不要做错。主列表默认不少于五条，刷新不丢。工具和任务都是在这份已经可点、可重置的业务库上往后挂，而不是另起一套数据。

## 3. 工具

这一节是主图和章节里「MCP / 工具」需要的背景。环境章本身不把混合调用写成环境存在的理由；混合调用是这套世界上的一个试验性能力。第一作者需要知道：为什么要挂工具、协议长什么样、一个工具从想法到实现怎么走、返回什么、和界面如何共用业务库。

### 3.1 为什么要挂工具

近半年移动 Agent 有一条清楚的行业判断：通用 Agent 会在界面操作和程序接口之间混用，界面用来兜底那些没有接口的步骤。现有基准把这两件事拆开了。有的只给外部服务接口，例如地图、代码托管、网页抓取，和手机里那个 App 的订单、购物车、账单不是同一份数据。有的只给纯界面。有的只有接口、没有可以点的界面。本环境要做的是第三种中间态：模拟商业 App 逐步开放一部分自己的能力，模型和人一样既可以用手指点，也可以调用这个 App 当前开放的那几个函数。开放清单不需要和市面 App 的真实接口一一对应，这是前瞻试验，不是复刻某家开放平台。

工具的动作空间是界面能做完的事情的严格子集。正式题必须存在一条只靠点击、输入就能做完的路径。工具是捷径，不是必要条件。支付数字键盘、联系人选择器这类确认步骤，任何情况下都不做成工具。因此同一道题可以只开界面跑一遍，也可以同时打开工具再跑一遍，判定读的是同一份业务库，两条轨迹可以直接比。

当时对齐过的粒度：工具是 App 内的原子业务能力，介于「点一下」和「一条函数做完整道题」之间。优先开放查询和打开页面。刻意留一部分功能没有对应工具，避免所有题都能靠一两条函数做完。运行时不把全部工具推给模型，只推当前前台 App 的，减少乱调。工具描述里不要写和某道题重合的例子。

和外部服务式接口的差别在协议层也成立。组里口头说 MCP，指的是「模型可以调函数」这件事。本环境的函数住在 mock App 自己的业务库上。若将来要接 MCP 传输，只做名单和调用的协议转换，不在适配层重写查询、不直接改库、不读判定答案。

### 3.2 底层：名单怎么来、调用怎么走、模型看见什么

浏览器里另有一个全局对象，只做两件事：按 App 列出工具，以及按名字调用。启动时只登记说明和参数格式。第一次真正调用，才加载实现和对应的业务库。只跑界面的评测不会执行工具业务代码。

一次调用的路径是：模型按本轮协议发出函数名和参数 → Python 适配器解析 → Playwright 进到页面里等待调用结束 → TypeScript 注册表找到该 App 的实现 → 实现去调这个 App 已经在用的查询函数、库动作或正常路由 → 返回一份固定形状的结果 → 若这次调用会换页或打开草稿，立刻再截一张图给模型。

成功和失败都是结构化结果，不会把实现异常堆栈丢给模型：

```text
{ callId, name, ok: true, output }
{ callId, name, ok: false, error: { code, message } }
```

名字固定成 `应用标识__动词_对象`，例如 `calendar__search_events`。每条工具带参数的 JSON Schema，以及给运行时看、一般不塞进模型函数字段的注解：这次是不是只读、会不会打开页面、会不会只预填不保存。模型通常看不到这些注解。OpenAI 函数调用和 MCP 都没有「会不会换页」这种标准字段。所以会不会打开页面、草稿有没有写入、要不要看新截图，必须写在工具的自然语言说明里。

每轮只执行一个调用。界面工具和截图不能并行。返回里即使带了路由字符串，也不能用路由代替截图，因为下一步若要点按钮，模型需要真实画面。

运行时先问操作系统：桌面、最近任务、下拉控制中心有没有盖住。盖住则本轮函数表里只有手势入口，没有任何 App 工具。没有盖住，则只列出当前前台那一个 App 的工具，加上始终存在的手势入口。手势入口覆盖点击、双击、长按、输入、滑动、拖拽、系统键、按名称打开 App、等待、作答、结束。作答只记文字，不结束本局；做完后要再发结束。换到另一个 App，下一轮名单自动换成新前台的。调了本轮名单里没有的名字，或调用时前台已经变了，运行时拒绝执行，业务库不变。

系统提示用叙述告诉模型：你在这个模拟器里；手势始终可用；工具来自当前前台；只许调列出来的函数；每轮只调一个；题面点名某个 App 时用确切名称打开，不要在桌面猜图标；「笔记」指系统笔记，除非题面写了 flomo；工具可能返回一段结构化数据，也可能只负责跳转或预填，之后根据返回和新截图再决定。不同模型只换打包格式，评测条件对齐。

### 3.3 完整例子：日历从想法到返回值

日历是工具设计文档里的参考实现，也是后来扩到其它 App 时反复套用的结构。下面按「为什么要这几个 → 做成了什么 → 调用后库和画面发生什么」写完。

真实日历通常会开放：按关键字搜日程、打开某一天、询问某段时间忙不忙、用系统意图预填一条新日程。它通常不会开放：把所有日程连同备注和闹钟一次性倒给调用方、不经确认直接创建或删除、为某一道评测题定制的「找一个空下午并建提醒」。第一版因此只做五个函数，并且写明故意不做的那些。

**按标题搜索。** 实现不自己扫库，而是调用日历界面已经在用的查询函数，从业务库的事件数组里过滤。返回给模型的不是整条事件，而是裁短后的候选：

```text
调用：calendar__search_events
参数：{ "query": "review", "limit": 10 }

返回 output：
{
  "events": [
    {
      "event_id": "evt_xxx",
      "title": "Project review",
      "start": "2026-07-15T14:00:00+08:00",
      "all_day": false
    }
  ],
  "total": 1,
  "truncated": false
}
```

没有备注，没有闹钟。那些字段还在库里，界面打开详情就能看见，工具故意不给。调用前后事件数组不变。画面不一定换页。

**打开一条或某一天。** 模型拿着上一步的 `event_id`，或直接给一个 `YYYY-MM-DD`。实现走正常开 App 和日历路由，等到目标页画完再返回。返回大约是 `{ "event_id": "evt_xxx", "route": "/event/evt_xxx" }` 或 `{ "date": "2026-07-13", "route": "/..." }`。业务库仍不变。运行时会再截一张图，因为注解标明这次会换页。模型下一步可以在这张图上继续点。

**只问忙闲。** 输入一段起止时间。实现合并事件占用的区间，返回：

```text
{
  "start": "...",
  "end": "...",
  "is_free": false,
  "busy": [{ "start": "...", "end": "..." }]
}
```

没有标题，没有笔记。这是产品上的隐私边界，不是为某道题删字段。

**预填但不保存。** 这是界面和工具边界最清楚的一条。

```text
调用：calendar__prepare_event_draft
参数：{
  "title": "Project review",
  "date": "2026-07-15",
  "start_time": "14:00",
  "end_time": "15:30",
  "description": "Review weekly progress"
}

返回 output：{ "route": "/event/new?...", "persisted": false }
```

实现只是带着参数打开日历自己的新建页，表单被预填。库里的事件数组此时多不出一行。`persisted` 为假，就是在告诉运行时和测试：业务对象还没有被创建。模型必须再在界面上检查提醒、闹钟，点保存。保存走的是页面原来的提交函数。保存之后，事件数组才多一条。再调一次搜索，能搜到刚才那条，因为搜索读的仍是同一份数组。

若只调预填、不点保存，判定去看事件数组，题失败。若分别用纯界面新建一条、和「工具预填再界面保存」走一遍，两条路径的终态在业务语义上应当一致，随机生成的编号可以不同。默认值或提醒不一致，说明工具绕开了真入口。

测试夹具可以整库灌初态；五个日历工具的实现本身不可以。提交前要过 schema、领域单测、调用前后 JSON 差分、浏览器里返回后立刻截图。文档里的完成清单还要求：粒度是原子能力、集合稀疏、说明告诉模型调用后怎么继续、Agent 只通过列出和调用两个接口使用工具。

### 3.4 同一套结构扩到记账单和购物车

日历定下来之后，其它 App 按同一条思路扩：先看用户能理解的能力，再看业务库和页面里的校验，再看真 App 通常开放什么，最后每个 App 留大约 5 到 15 个。优先搜索、定位、打开页、有限结构化查询。其次低风险写入和预填。不做任意改库、不做整题工作流、不为某一题定制函数。

支付宝搜索账单直接读支付宝库里的转账记录数组，过滤方向、时间和关键字，再裁成短记录。一次调用大约返回：

```text
调用：alipay__search_bills
参数：{ "direction": "expense", "limit": 50 }

返回 output：
{
  "direction": "expense",
  "items": [
    {
      "bill_id": "...",
      "title": "转账-正中(刘沐辰)",
      "counterparty": "正中(刘沐辰)",
      "amount": -2500,
      "timestamp": "....",
      "category": "..."
    }
  ],
  "total": 17,
  "truncated": false
}
```

`amount` 为负表示支出。模型要找最大一笔，在 `items` 里比较绝对值即可，不必在账单页上翻。数组本身没有被改写。若模型接着打开系统笔记并调用创建笔记，写入的是笔记库的笔记数组，不是支付宝库。判定两边分开读。

卡皮的预填记账和日历预填是同一边界：预填打开记账表，账本数组不增加；界面点完成之后，账本数组才多一行；再搜索账单，能读到刚记下的那一行。瑞幸加购则是少数直接写入：调用后购物车库里对应规格的数量变成 2。判定检查的是这个数量字段，不是「有没有调过加购」。调过但数量是 1，检查点为：期望 2，实际 1，未通过。

淘宝第一版 14 个：搜索商品和店铺、摘要、比价、读购物车和订单、打开页、加购、预填结算。京东 12 个，结构相近。点评 10 个。微信 10 个，发送文本是直接写入，预填朋友圈不发布。目录里按 App 列了开放哪些、故意不开放哪些。浏览器回归合计约 328 次调用、基础设施失败为零，只说明接口能调通。

扩展顺序在设计文档里是写死的：读该 App 的库、动作、路由、页面逻辑和已有题 → 列出真产品可能开放的能力 → 提出 5 到 15 个候选并标清「只读 / 打开页 / 预填 / 直接写」→ 删掉整题解法和会让界面失去作用的 → 抽界面和工具共用的领域函数 → 登记说明和实现 → 差分和浏览器测试 → 更新目录。实现优先级：先调界面已在用的领域服务，再调带校验的库动作，再把页面里的校验抽成共用，最后才写工具专用逻辑。

## 4. 任务怎样被写出来

外部看到的是一条自然语言和最终过不过。内部必须先回答四个互相卡住的问题，否则这条任务无法稳定复现，也无法同时支持只开界面和同时开工具。

第一，开始时库里必须已经有本题用得到的实体。最大那笔支出必须真的在支付宝的转账记录里；要发给的人必须真的在微信联系人里。实体不在，模型再会操作也做不出可判定的终态。所以初态和题面是绑在一起的：题面不能要求一个库里没有的对象，初态也不能为了「看起来难」偷偷换成另一套数据。

第二，题面只写用户想办成的事，不写第一步点哪里、不写调用哪个函数、不把标准答案写进句子。模型和人听到的是同一句「我想……」。写步骤会把界面路径焊死，工具捷径反而变成「没按说明书走」。写出工具名会泄题。

第三，必须存在一条只靠界面就能做完的路径。否则「只开界面」那一轨从结构上就失败，混合调用也不再是可选捷径。工具可以缩短翻列表、搜记录的时间，但不能变成唯一解。

第四，做成与否必须能从结束时的业务库读出来。下单、收藏、带正文的评价、发消息、改期望、记账、建日程、往笔记里写入指定金额，这些都会在 JSON 里留下差分。只「看看还差多少分」、只打开岗位、五星不写字，库里没有稳定可判的写入，这类题不进正式集。跨 App 也按这个标准：第二个 App 必须有自己的业务终态。查完只发给一个人、第二个 App 只当信使，不当作跨 App 覆盖。

这四件事绑在一起，不是工程口头禅，而是同一条可重置世界里把「用户目标」变成「可重复判定」的最低条件。判定只认用户目标对应的终态字段，不认搜过没有、点过哪、调过哪个函数。指令没提到的字段不要写进检查。时间、金额、日期按模型看完屏幕会怎么写来匹配，不要求补零或固定格式。走了界面还是走了工具，判定函数看不见。

出题时不把某个 App 的全部源码一次塞给模型。每个 App 先收成一份压缩事实：导航声明、状态结构摘要、工具说明、每个集合抽几条实体、少量关键页截图。单 App 题用一份；跨 App 题一次给两到四个 App 的事实，再拼成一个场景。缺实体先补库，再写题。题面、初态、界面路径和判定字段要对齐之后才进候选。当前候选大约二百条，按七个领域铺，还没有锁成正式分母。

## 5. 跑完一局：初始化、逐步交互、判定

同一套题、同一种初始化、同一套判定。开关只决定本轮函数表里有没有当前前台 App 的工具。两种模式可以各跑一遍，供后面训练。每轮只执行一个调用。

### 5.1 初始化结束之后

评测进程为本题建目录，写进题面和涉及的 App。按第 1.2 节灌好初态、固定时钟、抽好参数。第一张图是桌面。此时系统层盖着，函数表里只有手势。开始前的整机 JSON 已经存好。

### 5.2 每一步系统和模型之间传什么

运行时先看桌面、最近任务、控制中心有没有盖住。盖住则仍然只有手势。打开了某个 App，才把这个 App 的名称、说明、参数格式和手势拼成本轮函数表。模型同时看到题面、第几步、上一轮函数返回、当前截图。

模型回一个函数。名字是手势入口，就译成点击或输入，Playwright 执行后再截图。名字是某个 App 工具，就再确认一次前台和名单，等待页面里的调用结束；若这次会换页或打开草稿，新截图一定给模型。解析失败不改库，进入下一轮。步数用尽或模型宣布结束，本局停。常见上限 45 步，一部分题用过 60 步。

### 5.3 停下来之后怎样判

本局停住以后，评测进程再向页面要一次整机 JSON，和开始前那份放在一起。判定入口是 `task.evaluate`，输入只有三样，都来自观测里的状态，不来自轨迹：

```text
JudgeInput
  apps_init  = 开始前 getState()["apps"]     # 例如 apps.alipay.transferRecords、apps.notes.notes
  apps       = 结束后 getState()["apps"]
  os_init / os
  answer     = 模型通过手势「作答」写下的文字，没有作答则为空
```

走了界面还是走了工具、调过哪些函数名，这里都看不到。`evaluate` 分两步，对应结果里两个独立布尔值。

**第一步：目标检查，决定 success。**

调用本题自己的 `check_goals`。它必须返回一组检查点，每一个都带四个字段：`field`、`expected`、`actual`、`passed`。缺 `passed` 框架会直接报错。`expected` / `actual` 会写进日志，所以不能写成 `expected=True, actual=None`，要能看出期望的是哪笔订单、哪段正文。

全部 `passed=True` 则 `success=True`。进度 = 通过条数 / 总条数。任何一条失败，目标就不算达成。检查函数里如果抛错，例如开始前的支付宝库里没有转账记录可算最大值，记的是判定自身出错，不是模型没做成。

检查点怎么从 JSON 里取数，由各 App 的访问器做，不在任务类里手写遍历。支付宝访问器读的是 `apps.alipay.transferRecords`：`delta < 0` 的是支出，绝对值最大的那条就是「最大支出」。笔记访问器读的是 `apps.notes.notes`：按 `updatedAt` 取最新一条，标题加正文拼成一段文本再做包含或抽数字。微信发消息则比较开始前、结束后的会话，看是否多出一条指向指定联系人、且正文含指定片段的消息。

两种常见形态：

- 状态直查。结束后库里某个字段等于期望值。瑞幸加购失败时检查点就是：`field` 为购物车指定规格的数量，`expected` 为 2，`actual` 为 1，`passed` 为假。
- 写入笔记。在结束后的笔记数组里找新建或指定标题的那一条，标题加正文必须包含给出的词；有的题还要求不能出现另一组词。找不到笔记则 `actual` 为 `no notes`，`passed` 为假。

**第二步：意外改动检查，决定 clean。**

把开始前和结束后两份 `{apps, os}` 做树状差分。对象数组按元素上的 `id` / `wxid` / `mid` 等编号对齐，报告新增、删除、同一编号下字段变化、以及共同元素的相对顺序变化。扁平字符串或数字数组按多重集合比，路径写成 `某数组[+=值]` / `[-=值]`。

题目事先声明一份允许变化的路径。新建笔记的题声明的是 `notes.notes`，框架会补成 `apps.notes.notes`。路径匹配规则：完全相等算允许；差分路径是声明路径的子路径也算允许，例如声明了 `apps.notes.notes`，新建整条笔记及其 `content` / `updatedAt` 都算预期；反过来，若声明的是某个子字段、实际新增了整段对象，也算预期。另外还有一批全局忽略路径：时钟、桌面是否可见、任务栈、最近任务、软键盘、桌面分页、最近活跃时间戳。这些随开关 App 会变，不算用户目标。

滤完还在的差分记进 `warnings`，每条是 `{field: 路径, before, after}`。`warnings` 为空则 `clean=True`。`success` 和 `clean` 分开记：笔记金额写对了，但顺手改了支付宝里不该动的字段，目标仍算达成，本局记为不干净。看消息容易带上已读时间，转账容易带上回单，搜索容易带上搜索历史，收藏容易带上收藏编号；这些路径必须写进允许列表，否则会出现在 `warnings` 里。

评测落盘的一行大约是：`success`、`clean`、`progress`、`issues`（全部检查点，过的和没过的都在）、`warnings`、停因、步数、本局调过的函数名。汇总成功率只看 `success`，不看模型有没有宣布完成。

若干情况对应到上面两步的具体数据：

- 开关目标已经等于初态：`check_goals` 在空跑时也会全过。准备阶段必须先把该字段翻成相反值。
- 只看不写：结束后笔记数组、订单数组与开始前相同，包含检查的 `actual` 为 `no notes` 或仍是旧正文，`passed` 为假。
- 五星没有正文：若检查只看「评了」，库里只有星级没有字符串，写不进可区分的 `expected`。正式题把检查落在正文长度或话题词上。
- 指令没提的字段不进 `check_goals`。支付宝记笔记那题不检查当前路由，也不检查有没有调过搜索账单。
- 金额：从笔记正文抽出所有数字，与期望值比绝对值，容差 0.01。`2500`、`2500元`、`2,500` 都能过；写成 `200` 则抽出的数字对不上。
- 环境缺 `transferRecords`：访问器抛错，结果带 `judge_error`，不是 `success=False` 那种模型失败。

## 6. 完整一局：支付宝最大支出写入系统笔记

题面后来收成第一人称用户目标：把支付宝里金额最大的那笔支出花了多少记到笔记里。涉及支付宝和系统笔记。一次对照跑：只开界面 12 步通过；同时开工具 5 步通过，先后调了搜索账单和创建笔记。审计里的真实数据：最大支出是「转账-正中(刘沐辰)，2500 元」。有模型把往来 10000 当成最大，也有模型找对了人却写成 200。

**库里事先有什么。** 支付宝业务库的转账记录数组里已经有多笔、金额不同。系统笔记库的笔记数组为空，或不含这个金额。准备阶段不另灌一套假账单。抽样时读转账记录，算出最大支出的金额和标题，填进内部参数。题面不出现 2500。

**界面路径。** 打开支付宝，进入账单，在列表里比较金额，打开笔记，新建一条，把金额写进去。

**工具路径。** 打开支付宝后，本轮名单出现搜索账单等函数。调用后得到第 3.4 节那种短列表，在 JSON 里比较绝对值。再打开笔记，名单换成创建笔记。调用后笔记数组多一条，正文带上 2500。支付宝的转账记录数组全程可以不变。

**逐步。** 桌面上只有手势。打开支付宝之后，搜索账单第一次出现在名单里；此时编造创建笔记会被拒绝。调用搜索账单，转账记录不变，返回短列表。打开笔记之后，支付宝工具从名单消失，创建笔记出现。创建笔记写入笔记库。模型宣布结束。

只开界面的对照局没有这两条函数，模型在账单页和笔记页用点击、输入完成同样的写入。判定收到的仍是开始前和结束后两份 JSON。

**判定读哪两段 JSON。** 开始前从支付宝库取出 `transferRecords`，筛 `delta < 0`，按绝对值取最大一条。审计数据里这条是「转账-正中(刘沐辰)」，`delta` 为 `-2500`。展示名优先用加载时补好的 `displayTitle`，否则用对方名称。结束后只看笔记库的 `notes` 数组，按 `updatedAt` 取最新一条，把标题和正文拼成一段文本。本题声明允许变化的路径只有 `notes.notes`。支付宝转账记录不在允许列表里；搜过账单若写下搜索历史，会出现在 `warnings` 里，`clean` 为假，但不翻 `success`。

**两条目标检查，必须都过。**

```text
检查 1
  field:    largest_expense_target
  算法:    最新笔记文本是否包含「转账-正中(刘沐辰)」这段展示名
  expected: contains ['转账-正中(刘沐辰)']
  actual:   笔记正文前 120 字；缺词时附上 missing
  没有新笔记: actual = "no notes"，passed = false

检查 2
  field:    largest_expense_amount
  算法:    从最新笔记文本抽出全部数字，是否存在与 2500 相差不超过 0.01 的数
            （也接受绝对值相等，避免写成 -2500）
  expected: { "number": 2500, "tolerance": 0.01 }
  actual:   抽到的数字列表
  没有新笔记: actual = "no notes"，passed = false
```

两条都过则 `success=True`，`progress=1`。写成往来 10000：检查 1 可能因没写对展示名失败，检查 2 抽出 10000，对不上 2500。找对了人写成 200：检查 1 过，检查 2 的 `actual` 为 `[200]`，`passed` 为假，进度 0.5。只在支付宝里看出来、用文字作答说出 2500、笔记数组没变：两条都是 `no notes`，`success` 为假。开始前笔记里已经写着这个金额和对象：必须先清掉或换一条，否则空跑两条都过。

不检查当前路由，不检查 `transferRecords` 有没有变，不检查调过哪个函数。`issues` 里会留下上面两条的完整记录，过和没过都在。

同一套结构落在瑞幸加购上，检查点落到购物车字段：`expected` 为 2，`actual` 为 1，`passed` 为假。落在卡皮记账上，只预填不保存则账本数组与开始前相同，目标检查失败；界面保存后再读，同一行出现在结束后的账本数组里。
