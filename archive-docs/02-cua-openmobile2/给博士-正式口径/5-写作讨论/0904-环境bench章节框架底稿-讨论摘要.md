# 章节框架：MobileGYM++（环境 / 工具 / 基准）

**这份文档怎么用。** 每一段只有**论点**进论文：编号句子按正文顺序写，逐句可直接落笔。**说明**与**讨论**只在会上用，不进正文；说明写别人怎么写、我们是什么情况、为什么这样排，讨论只列真正需要当场拍板的取舍。会上按节序翻，讲到基准第五段时把购物支付记账那条任务摊开。

**数字口径。** 可安装应用 64 个；本轮新构造 35 个；约 52 个应用提供工具定义；新构造应用导航声明中位为 37 条路由 / 175 个可交互动作 / 88 条跳转，交互深度中位 3；纵深参照取前作中结构最厚的应用，为 100 条路由 / 265 个动作 / 深度 7；基准设计规模约 200 条（约 116 条单应用、84 条跨应用）。不写「120+」，不把内部双跑分数当正式结果，不写「首个」一类表述。逐应用明细、动作清单、工具协议与参数规范全部进附录。

**三页切法（按重排后的节重估）。** §1 环境约 1.5 页（四段）；§2 应用内工具约 0.5 页（两段）；§3 基准约 1.1 页（六段）。相对上一版，与现有环境的关系并入开场缺口段，平台能力与观测动作各压成一条论点，局限压成协议段末尾一句，均不单独成节。

## 0. 开场（按 2026-09-02 孙秋实口述；尽量用原句）

**本段要立住的观点**：他原话是「如果要我引入，我肯定会从 existing 这些 bench 的缺点」；「真实、多样、稳定」是环境 software 建好以后再扣回去的，不是第一句。**关键词：探索环境太小、anti-bot、mock / pseudo apps、beyond pure human-like、plus。**

带引号的是他的原词。括号里的字只为把口语句连上，不改意思。现有 §1 ¶1 的「三项验收目标」放到这段之后，不要抢开场。他说「按照我口述的部分来写，肯定不会出错」。

**连起来的一段**

我们这项工作肯定跟 scaling 有关系。要引入，从 existing 这些 bench 的缺点起笔——AndroidWorld、MobileWorld，以及 CUA，不是把 MobileGym 的缺点拿来当主靶。他们本身那个探索环境太小。过渡到如果我们想探索更多的环境，比如说 APP，那么就会面对各种各样的阻碍。第一，这些 APP 本身 anti-bot：采数据的时候，APP 直接拒绝在虚拟机里面运行。后面我们是真机采集，但真机采集有很多缺点。第二，如果用真实的这种 APP 来采集，相当于我们在实验的过程中对真实的世界造成影响，这个影响可能是不好的。因此，要去 scalable 地探索这个 mobile 的这些环境，其实离不开制造这样的所谓 mock 或者 pseudo apps。这是第一个阶段的引入：先引入 APP 和环境之间的关系。

第二个，在构建这个环境的过程中，considering existing 这些 CUA 在执行效率、接口形式、以及一些 future 的场景，这些 APP 本身可以 beyond human-like、beyond pure human-like operation，然后比较自然地引出我们在它的基础上拓展出 MCP、CLI。不要把它跟整个工作、或者说整个环境绑定得太深，把它写成一个 extend 出来的东西：纯 GUI 完全 OK；为了面向未来，为了让这个 benchmark 或者说让这个环境能够 long live，我们还额外做了这些事情。它是一个 plus，专门用于面向未来的研究。第三，假设未来 mobile 上面也获得了 CLI、MCP 的能力，那么它会比纯 GUI 好多少，实验章再回答。

再拓展到下一句：我们要让它能够支持 both academia 和 industry。这条路径上需要开源以后用一些接口，它本身会有一些 transaction，比如说下单、支付，这样的一些可判定的点；针对前面的 APP 做 design。环境内部的 APP 及其扩展，以及它的入选和它的 verifiable，基本上就把最主要的贡献一一 cover 掉。我们要 differentiate from previous two works。批判前人点到为止，不要骂得太狠：verifier 不可靠，纯用 LM judge 会有假阳，在线的网站 offline 以后不可能再用 verifier。点一下，引申到我们要做一个给社区可以用的、对 academia 和 industry 都有用的东西，然后引入刚刚的三点。

这部分结束以后，再引入里面这些 APP 的业务领域：整个环境、software 的部分建设好了以后，再讲我们在选取、制造的时候都考虑到了真实、多样、稳定。再把 AndroidWorld 抽一次：他们可能只 cover 了 system default 的 APP；我们可能有一个 diversity 和 exploration depth 的 leap，这就是支持我们去做完整的业务闭环，以及可扩展性。收一下。有了环境加 APP、APP 内部的 MCP、以及 verifiability 这几个以后，再回过头来扣一下：我们在制造它的时候也考虑到了真实世界的情况，所以里面复现的商业 APP 会有逻辑闭环。然后再往后讲 eval、data、bench，后面基本上就是平铺直叙。

**论点（仍用他的词）**

1. 「总起一段讲 CUA 的大背景，然后收束到 Mobile，再讲到 Mobile 上的这个探索、eval、采集。他们现在被这些环境 bound 住。」
2. 「Existing 这些 bench……他们本身那个探索环境太小。」点名 AndroidWorld、MobileWorld；MobileGym 的缺点不是主靶。
3. 「如果我们想探索更多的环境，比如说 APP，那么就会面对各种各样的阻碍。」第一：「APP 本身 anti-bot……直接拒绝在虚拟机里面运行。」后接：「真机采集有很多缺点。」
4. 「如果用真实的这种 APP 来采集，相当于在实验的过程中对真实的世界造成影响。」因此：「要去 scalable 地探索这个 mobile 的这些环境，其实离不开制造 mock 或者 pseudo apps。」「这是第一个阶段的引入：先引入 APP 和环境之间的关系。」
5. 「这些 APP 本身可以 beyond pure human-like operation，然后比较自然地引出 MCP、CLI。」「不要绑定得太深」；「写成一个 extend 出来的东西」；「纯 GUI 完全 OK」；「它是一个 plus。」
6. 「支持 both academia 和 industry」→「transaction，比如说下单、支付，这样的一些可判定的点。」「环境内部的 APP 及其扩展，以及它的入选和它的 verifiable」，把最主要的贡献 cover 掉。
7. 「Differentiate from previous two works。」批判「点到为止」：verifier 不可靠，LM judge 有假阳，在线网站 offline 以后不能再用 verifier。引申到「给社区可以用的、对 academia 和 industry 都有用的东西」，引入刚刚的三点。
8. Software 建好以后，再讲「选取、制造的时候都考虑到了真实、多样、稳定。」「他们可能只 cover 了 system default 的 APP；我们可能有一个 diversity 和 exploration depth 的 leap」，「支持我们去做完整的业务闭环。」有了「环境加 APP、APP 内部的 MCP、以及 verifiability」再「回过头来扣一下」：制造时考虑到真实世界，所以「复现的商业 APP 会有逻辑闭环。」

**说明**

原文在实录 12:27–18:23，工具那几句在 24:31–25:56。瞰之说「引入会平顺很多」；秋实说「按照我口述的部分来写，肯定不会出错」。方法章「背景还是要有一点，否则上来大家看不懂你为啥要造」。判定「是大家的一个共识，反而不需要放太多的笔墨」；「懂行的人一看就知道你这是一个 programmatic verifier」。多种子他只是提一下，开场不写。后面 eval / data / 训练是另起一段，本章开场收到「逻辑闭环」即可。

**讨论**

- **A（推荐）。** 章节最前面就用上面这一段。现有 ¶1 改成这段之后的后续。
- **B。** 这段只给 introduction。他原话是方法章也要有一点背景。
- **C。** 开场不写 MCP，留给环境里「专门讨论我们这个 special design」的 part。他原话是第二阶段就要「比较自然地引出」。

## §1 环境

### ¶1 可控环境中的商业任务缺口

**本段要立住的观点**：真实、多样、稳定这三项目标，只有落在能被程序化判定的商业业务状态上才同时成立；现有可控环境缺的正是这一层。**关键词：缺口、三项验收目标、可核对。**

**论点**

1. 移动智能体的评测目前分在两条路上：一条在物理设备上运行真实应用，换来界面与网络的真实，代价是状态难以重置与并行；另一条在可控环境中运行可复现的应用，换来重置与判定，代价是应用大多止于系统工具与开源客户端。
2. 后一条路上的应用选取是被各自论文明写下来的设计选择：以可离线、免登录作为入选标准，以开源通讯软件替代商业通讯服务，或只提供函数接口而不提供图形界面；由此可被程序化检查的终态集中于系统级状态，而完成一次下单、记下一笔支出、改一次行程这类商业结果尚缺少可判定的落点。
3. 三个评测缺口由此产生，并贯穿本章：商业应用的业务终态无法被判定读取；应用内的工具调用与界面操作没有一个共同的世界可供对照；需要在多个应用之间取值并写回的长程任务因而无题可出。
4. 本章给出的回应是 MobileGYM++：一个运行在浏览器中的移动环境，以真实、多样、稳定为验收目标，并把这三项分别落到可核对的事情上——复现商业应用的完整业务闭环，覆盖七个业务领域的 64 个可安装应用，以及可整体导出与恢复的初始状态与只读取业务状态的程序化判定。
5. 环境建立在 MobileGym 之上：运行时、状态序列化与重置、应用间跳转与程序化判定沿用前作，本轮扩建的是其中承载的内容与新增的调用通道，即成规模的商业应用与应用内开放工具调用。

**说明**

开场必须回到验收目标的三个词，但三个词不能空转，所以第 4 句让每个词各带一件可以核对的事：真实对应业务闭环，多样对应七领域 64 个应用，稳定对应可恢复的初始状态与程序化判定。上一版把「状态可读写可以直接当评测方式」写成第一段主观点，位置和措辞都不对：读者还不知道这是什么世界，就先被要求接受一个评测立场。现在的处理是把「不依赖模型裁判」的立场留到第三段的判定契约里正面写，开场只写「判定读取业务状态」这一事实。

第 1、2 句负责把对照面画出来，同时替掉原来那一节「与现有可控环境的关系」。别人写缺口都用可核对的事实：OSWorld 用「要么没有交互环境、要么被锁在特定应用」两个属性切开对手；AndroidWorld 先点出把轨迹与人类演示比对的做法不能代表真实表现，再给出自己的替代；AppWorld 写现有工具基准多为简单函数序列、许多工具只读不写、大量基准依赖模型裁判或单一标准答案；MobileWorld 直接说 AndroidWorld 已接近饱和且缺电商与企业协作品类。我们讲别人缺什么时，只引用他们自己写下的入选标准，不用「不够真实」这类评价词。真机路线用第 1 句半句带过，承认它换到了真实应用与真实网络，代价出在可控性上，不展开。

第 5 句必须点名 MobileGym，并且写清楚继承边界。审稿人对着前作一查就知道运行时、跳转、重置、判定都是既有能力，含糊其辞是硬伤。MiniWoB++ 的做法可以照搬：直接叫出前作名字，明说运行底座未改，只补更难的任务与新增内容，读者反而知道该拿什么和什么比。跨应用能力属于继承，本章不单独开节去卖，正文任何一处都不把它写成本轮贡献。

**讨论**

- **A（推荐）。** 按缺口、别人的设计选择、三个缺口、我们的回应、继承边界这五句写。缺口在前、主张在后，环境和基准共用同一组缺口，第三节不必再另起一套动机。
- **B。** 先亮环境，再补缺口。气势更足，但环境章开头就成了系统介绍，缺口段挪到基准节又会与任务动机重复，全章的推进逻辑会散。
- **C。** 正文一家不点名，只放比较表。省行数，但第 2 句会退回「现有工作没有同时满足以下四条」这类并列否定，正是这一轮要改掉的写法。

### ¶2 在 MobileGym 之上的扩建

**本段要立住的观点**：本轮扩的是内容与通道，不是底座；把继承一次说清，篇幅让给商业应用与工具。**关键词：同一运行时、复现业务闭环、两处扩建。**

**论点**

1. 前作 MobileGym 提供了一套完整的可控运行时：整机运行在浏览器标签页内，各应用维护自己的结构化状态并据此渲染界面，应用间的跳转、剪贴板与系统广播已经打通，整机状态可导出为一份记录并按该记录恢复，多个实例可同时推进而互不干扰。
2. 本轮工作在同一套运行时上完成两处扩建：把可复现的商业应用铺开到具备领域覆盖的规模，并在这些应用内部开放一组与界面同权的函数调用。
3. 新构造的应用复现的是业务闭环而非界面外观：商品与订单、支出与预算、行程与改签、会话与消息各自作为对象存在于应用自己的业务库中，被界面渲染，也被判定读取。
4. 智能体一侧的接口保持不变：观测为屏幕像素，不含辅助功能树，也不能直接读取业务库；动作沿用离散的点击、滑动、输入与导航，工具调用与之同级，每步至多执行一个动作。

**说明**

这一段吸收了原来的「平台能力」与「观测与动作空间」两节。平台能力压成第 1 句，因为它是继承内容，单独成节会被读成把前作能力当自己的贡献；观测与动作压成第 4 句，因为它只需要交代两件事：智能体看像素、看不到业务库，以及工具与点击同级。信息隔离这一句不能省——整段都在讲库可读可写，读者会自然怀疑智能体是否也在读库。

「复现业务闭环而非界面外观」是第 3 句的落点，也是后面规模段的前提：如果只说复刻了多少个界面，规模就是工程量；说复刻了业务对象，规模才等于更多可判定的商业终态。措辞上不要写成我们提出了状态表示或业务状态机制，那是前作的分层状态与序列化，本轮变的是库里装的对象类型。

统一冻结时间不在这一段出现。任何可控环境都能固定时间，它只是评测协议里的一项设置，放到基准最后一段用半句交代。加固细节（禁止直接取系统时间、以网址参数钉住模拟时间）属于工程质量，进附录。

**讨论**

- **A（推荐）。** 保持四句独立成段，放在缺口段之后，读者先知道我们站在哪、继承了什么，再看规模和判定。
- **B。** 把第 1 句并入上一段末尾，本段只留三句。可省约四行，代价是缺口段变长且焦点从「缺口」滑向「系统介绍」。若工具节要加长，这是第一顺位的压缩位置，压时必须保住第 2 句的两处扩建。
- **C。** 做一张「能力 / 来自何处 / 本轮是否变化」的对照表放正文。对审稿人友好，但正文已计划一张与同类环境的比较表，两表挤在一页半内过满，建议放附录并在正文末尾一句指引。

### ¶3 业务状态上的程序化判定

**本段要立住的观点**：成败只由业务状态的前后差分决定，因此同一任务的所有正确解法都成立、所有"看起来做完了"的解法都不成立。**关键词：终态可验、解法无关、不认自报。**

**论点**

1. 判定问的是世界最后变成了什么样，而不是智能体走过哪些步骤：任务绑定初始状态，结束时对整机状态取一次差分，检查目标业务字段是否被写成要求的样子。
2. 由此，判定既不依赖模型裁判，也不与单一参考轨迹比对：完成同一件事的不同路径在同一套判定下等价，而智能体自行声明完成不进入判定；一条在界面上看似完成、却未写入目标字段的轨迹判为失败。
3. 检查以关系而非常量写出：一条支出记录的金额需与刚刚完成的那次支付一致，一条日程的标题需包含所选车次的编号；常量只出现在初始状态中，不出现在判定里。
4. 任务在目标字段之外声明允许变化的状态路径，其余差分作为意外改动单独记录，与任务成功分开报告。
5. 一道任务被计为跨应用，当且仅当判定在至少两个应用中读到业务写入；查询后转述，或仅向另一个应用发出一条通知，不计入跨应用。

**说明**

这是全章最该写重的一段，因为它是别人不容易复制的设计选择：商业业务对象同时被界面渲染、被工具写入、被判定读取。规模会被追上，领域覆盖也会被追上，这一条不会。若要在本段与数字段之间取舍，宁可少报两行统计。

「不依赖模型裁判」必须正面写出来，但写在第 2 句而不是全章第一句。2026 年的读者看到浏览器里的模拟手机，默认会猜我们在比截图相似度或请模型打分；不主动否掉，读者会替我们填最差的假设。别人的句式可以借：AppWorld 写基于状态的程序化评测并指出参考匹配脆弱，AndroidWorld 写奖励来自系统状态因而比匹配表层界面变化更耐久，前作写确定性、细粒度、不依赖视觉语言模型评判。我们要论证的不是「状态判定更好」这件已成共识的事，而是「我们的状态里装的是商业业务字段」。措辞上不要沿用 system state，那是操作系统侧，我们读的是应用业务库。

第 5 句把跨应用的定义**一次钉死**，全文只用这一套说法，任务表统计口径必须按这套定义重算或分档报，不允许文档内部出现第二种定义。会上要主动说明：当前任务表按较松的口径统计，与这条定义存在缺口，处理方式见讨论。少数任务的判定在使用中补齐过字段解析，这属于判定质量的已知问题，登记在案，不写成模型失败。

**讨论**

- **A（推荐）。** 五句写满，关系式在第 3 句写出一行具体形态，阈值与字段名进附录。这样读者立刻明白判定并不预先知道答案，只知道答案该从哪里来。
- **B。** 意外改动按现行口径与成功率分开报，因为允许变化路径的声明尚未覆盖全部任务，直接判整题失败会把判定未写全的部分算到模型头上；AppWorld 的做法是附带损伤直接判失败。是否与其对齐，今晚拍。
- **C。** 跨应用统计的缺口有三种处理：分两档报（两侧均有写入 / 读出后写回），改分子只报严格口径，或放宽正文定义。放宽会使「每个被点名的应用都要有独立业务终态」这一主张作废，不建议。

### ¶4 规模、结构纵深与领域覆盖

**本段要立住的观点**：规模由四件可核对的事支撑——应用数量、单个应用的结构纵深、领域与终态形式的多样、判定能读到的对象类型与他人不同。**关键词：够多、够深、够杂、读得到。**

**论点**

1. 说明一个环境的规模需要同时回答三个问题：有多少应用，每个应用是否厚到足以承载多步任务，这些应用是否覆盖了不同类型的业务。
2. 数量上，环境收录 64 个可安装应用，其中 35 个为本轮新构造的商业客户端。
3. 纵深上，新构造应用导航声明的中位规模为 37 条路由、175 个可交互动作与 88 条跳转，自根页面起算的交互深度中位为 3；作为纵深参照，前作中结构最厚的应用为 100 条路由、265 个动作、深度 7。深度中位为 3 意味着多数任务的最短界面路径需要跨越若干层级，任务的步数下界由页面结构而非指令长度决定。
4. 覆盖上，应用按出行、购物、金融、内容、社交、办公与生活服务七个领域铺开，各领域承载不同类型的业务对象与不同的终态形式，包括下单、记账、建立行程、发送消息与加入收藏，因而无法用同一套判定模板套完。
5. 与同类可控环境的差别最终落在判定能读到什么之上：本环境的判定读取应用自身的业务库，而不是系统侧状态或界面控件树，商业结果因此可以进入评测；比较表按商业应用覆盖、状态是否可完整读写、判定是否读取业务状态、是否支持跨应用、应用内工具是否与界面写入同一份状态五个维度列出，真机路线置于表下单独说明。

**说明**

第 1 句是这一段的写法本身：先声明凭哪几点说服人，再逐点给证据。上一版只报数字，读者读完的反应是「所以呢」。数字要有意义需要参照点和结论：参照点取前作最厚的那个应用，结论是「每个新构造应用有足够结构承载多步任务」。深度中位 3 必须点出来并解释，因为它直接对应任务的最短步数下界，深度为 1 的应用出不了需要规划的题。

多样性最容易写成空话，所以第 4 句写两层：先列七个领域，再让每个领域对应不同的业务对象与终态动词，把「领域」从标签变成「判定要读的字段类型不同」。这也是我们与只报应用数的工作的差别：AppWorld 支撑多样性的是人物与人际关系这一维，不是应用数；MobileWorld 用多应用题占比与平均步数这类比值说话。比值天然带参照，比绝对数稳。

比较表的五列里，「判定是否读取状态」这一列多数同行都成立，必须保留——只列自己赢的维度会显得刻意，保留这一列反而说明我们承认同行做对了什么。最后一列是我们最能独占的一列，取值写短语而不用对勾：外部工具服务 / 接口即动作、无图形界面 / 应用内函数、与界面同库。真机不进表体，进表体就要比商业覆盖，那一列我们不占优；表下一句承认它换到了真实应用与真实网络即可。

数字口径重申：对外新构造报 35，64 是可安装，约 52 是带工具的；不写 120+，不引用内部双跑分数，不写「丰富多少倍」，不借用他人任务数当分母。约 200 条属于基准节，本段不提前透露。

**讨论**

- **A（推荐）。** 正文同时给中位三元组、纵深参照与领域—终态对应，比较表放正文，逐应用明细进附录。
- **B。** 只报中位、砍掉纵深参照。更安全，不会引出「你们不是比前作浅」的追问，但读者失去量级锚点，无法判断 37 / 175 是厚是薄。
- **C。** 统计全部丢附录，正文只留领域与比较表。更像研究少像工程报告，但「商业客户端做得深」这一主张会变空，不建议全丢。

## §2 应用内工具

### ¶1 开放工具调用

**本段要立住的观点**：引入应用内工具，是因为现有评测无法在同一个世界里检验智能体何时该点界面、何时该调接口；本环境把工具做成同一份业务状态上的第二条写入通道。**关键词：同一世界、第二条通道、界面可达子集。**

**论点**

1. 智能体已经普遍具备调用函数接口的能力，但现有评测把这件事切成了两半：图形界面环境几乎只评点击与输入，接口型环境又没有可以点的界面，于是「何时该用界面、何时该调接口、调用之后如何回到界面确认」这一类行为无处被检验。
2. 本环境因此在应用内部开放工具：约 52 个应用在各自的命名空间下暴露一组函数式接口，智能体可以列出并调用当前前台应用的接口，调用与点击处于同一动作空间，每步至多执行其一。
3. 这些接口作用于应用自己的业务库，与界面操作经由同一组业务函数写入同一份状态，因而是同一个世界中的第二条通道，而不是绕过界面的外部服务。
4. 接口所覆盖的操作是界面可达操作的严格子集：支付确认、密码输入与联系人选择仍只能在界面上完成，预填类调用只生成草稿而不产生业务写入，保存仍需回到界面。
5. 每道正式任务都保留一条仅使用界面即可完成的路径，判定对两类解法完全相同；纯界面解法与界面—工具混合解法因此可以在同一任务、同一初始状态、同一套判定下直接比较。

**说明**

第 1 句是全节的前因后果，也是这一轮新增贡献在本章唯一的立足处，不能像上一版那样直接从「约 52 个应用在自身命名空间下暴露」开口。缺口的写法与开场那三条一致：不是「别人没有工具」，而是「工具与界面的选择行为没有一个共同的世界可以评」。

我们与三类做法都不同，这是可以说、别人说不了的：把外部服务接入并让部分任务不用工具几乎做不完，等于把工具当成一根新的能力轴，其效果会直接体现在成功率里；只提供接口而没有界面，则无法比较通道选择；已有工作把「混合动作空间会让模型困惑」列为一条待解问题，说明这个决策点本身已被承认。我们的工具是同一世界里的另一条路，不是新能力，因此才能构成受控对照。这一句也是第三点贡献在三页里的核心主张。

第 4 句是防止工具退化成旁路的约束，必须写出来；也正因为工具可选，实验报告不能只看一个成功率，报告口径在基准最后一段预告。约 52 的分母是本章的应用集合，不与 64 混用。协议、参数、工具分类进附录。

**讨论**

- **A（推荐）。** 本节从约 0.35 页提到约 0.5 页，把第 1 句的缺口与第 5 句的可对照性都写足，页面从环境第二段和第四段各挤几行。理由是第三点贡献需要一句设计主张，不能只有机制描述。
- **B。** 维持约 0.35 页，缺口与对照留给引言与实验章。省页，但会上「第三点贡献在环境章为什么这么轻」这个问题仍会被问到。
- **C。** 把工具降为环境节内的一段。会使「与界面同库的工具」被读成实现细节，不建议。

### ¶2 一次调用的形态

**本段要立住的观点**：用一件完整的事说明工具写入与界面写入落在同一对象上，且调用不能替界面把事做完。**关键词：同一条记录、支付留在界面。**

**论点**

1. 一次典型的混合解法这样发生：智能体先调用记账应用的接口读回当前可用的预算，再切到购物应用的界面挑选商品并完成支付，最后调用记账应用的接口把这次支出写入指定账本。
2. 支付环节无法由接口完成，因为密码输入只存在于界面上；记账环节则两条路径都成立，界面上的保存与接口调用生成的是同一条记录。
3. 判定在两种情形下检查同一组业务字段，因而不区分这条支出是点出来的还是调出来的。

**说明**

例子的落点是「读回同一条记录」，不是列举函数名。工具与界面共享同一状态这件事在上一段已经用一条论点写过，这里只做一次可见的演示，三句写完即止。不抛出内部应用名，也不展开参数与返回结构，这些进附录。

**讨论**

- **A（推荐）。** 走预算、支付、记账这条线，与基准节精写的任务互相呼应，读者读到基准时已经熟悉这条业务链。
- **B。** 改走日程预填这条线：接口可以搜索、打开、预填一条日程，但库中事件数量并不增加，必须回到界面保存。更能演示第 4 条约束，但需要多一句解释「预填不等于写成」。若更在意「工具不能替界面把事做完」，换这条。

## §3 基准

### ¶1 基准所考察的能力

**本段要立住的观点**：基准由三个未被评到的缺口反推而来——通道选择、跨应用取值与写回、由业务流程本身撑起的长程。**关键词：三个缺口、终点是业务写入、真实来自流程。**

**论点**

1. 现有移动智能体基准已经把单应用的界面操作评得相当充分，未被评到的是另外三件事：智能体在拥有接口时能否选对通道并在调用之后回到界面确认，能否在多个应用之间把一件事从看见做到办成，以及能否在一段由业务流程本身决定长度的任务中不丢失中间结果。
2. 基准据此设计：每道任务以一次业务写入作为终点，仅完成查询、仅打开页面或仅以文字复述结果的任务不进入正式集合。
3. 任务的真实性来自流程而非题面措辞：一道任务之所以长，是因为它必须经过挑选、确认、支付与回写这些真实存在的环节，而不是因为人为叠加了步数。
4. 任务的跨应用性来自取值关系：完成任务所需的关键数值往往不写在指令里，而存在于另一个应用当时的业务状态中，判定检查的正是两个应用的业务字段是否对齐。
5. 纯界面解法是本基准的一等公民，界面—工具混合解法是同一世界中的另一条路径，两者被同等报告，后者不作为前者的消融。

**说明**

上一版把「关键数值不在指令里」当成唯一主张，与我们已经定下的任务特点脱节，也与同行普遍强调的真实、长程、跨应用不接轨。现在的排法是：第 1 句给三个缺口，第 3、4 句分别把「长程」和「跨应用」落到可核对的机制上，「关键数值不在指令里」降为跨应用性的具体形式而不是全节标题。这样既保住了这条设计确实存在的独特性，又不至于让读者觉得我们只测一件很窄的事。

同行的动机段都从缺口出发：有人指出现有环境要么无交互、要么受限于单一领域；有人指出把轨迹与人类演示逐步比对不能代表真实表现；有人指出工具基准多为简单函数序列且大量依赖模型裁判；有人指出既有基准已接近饱和且缺少若干业务品类。我们的三条缺口与这些不冲突，且第一条目前少有人正面评。措辞上不写「首个」，写「很少被作为任务设计原则」即可。

有两条不写进正文，会上口头交代：指令歧义与主动澄清不在本工作范围内，正式任务的用户目标是完备的，缺的只是需要在环境中查得的数值；来自另一应用的硬性数值约束目前还没有成体系的一批任务，只能作为演示能力展示，不作为已铺开的原则。

**讨论**

- **A（推荐）。** 三条缺口并列，通道选择列第一位，与全文第三点贡献呼应。
- **B。** 把跨应用取值放第一位、通道选择放第三位。任务侧更好讲，但会削弱工具这条新增线在基准里的存在感。
- **C。** 只写两条缺口（取值与长程），通道选择完全交给实验章。省行数，但基准与工具节之间就没有承接。

### ¶2 判定契约

**本段要立住的观点**：一句话说清厉害在哪——成败只由业务状态差分决定，因而所有正确解法都被接受、所有自我声明的完成都被拒绝。**关键词：终态可验、解法无关、不认自报。**

**论点**

1. 每道任务由三部分构成：自然语言表述的用户目标、绑定的初始状态，以及施加在终态上的程序化检查；三者随任务一同发布。
2. 契约的关键在于检查的对象：判定只读业务状态的前后差分，不读轨迹、不读截图、不接受智能体自行声明的完成。
3. 跨应用任务在同一份整机状态中分别读取两个应用的业务字段，使「两件事是否对得上」成为可判定的问题，而不是需要人工阅读轨迹才能回答的问题。
4. 除目标字段外，任务声明允许发生变化的状态路径，其余差分作为意外改动单独报告。

**说明**

这一段与环境第三段是同一机制的两个面：那里说环境能这样判，这里说基准把这件事写成任务与判定之间的契约并随任务发布。发布这一点要写出来，它决定别人能不能在这张集上复现我们的口径。

第 2 句的三个「不」是这段最值得记住的部分，会上就用这三个词概括。第 3 句要写出契约带来的能力增益，否则读者会觉得只是复述前一节。少数任务的判定在使用中补齐过字段解析，属于判定质量的已知问题，登记在案，不隐瞒也不展开。

**讨论**

- **A（推荐）。** 意外改动按现行口径与成功率分列报告，正文只占一句，白名单机制进附录。
- **B。** 与 AppWorld 对齐，误伤直接判整题失败。口径更硬，但当前允许变化路径的声明尚未覆盖全部任务，会把判定未写全的部分算到模型头上。
- **C。** 判定契约与环境第三段合并成一段。可省约六行，但基准节会失去自己的方法学锚点，讲的时候要往回翻页。

### ¶3 任务特点与难度来源

**本段要立住的观点**：任务从判定关系反向生成，难度来自信息在应用之间的存在形式，而不是步数堆叠。**关键词：先定关系再写题面、三种信息形式、难度分层。**

**论点**

1. 任务的构造顺序与阅读顺序相反：先确定两个应用之间应当对齐的字段，再写出判定，最后才撰写指令，并在指令中以指示替代具体数值，使该数值只能在运行时取得。
2. 跨应用的信息主要以三种形式出现：数值在一个应用中生成、需写入另一个应用；事实存在于不具备事务能力的应用中，而动作必须在事务型应用中完成；同一条记录需要汇聚来自多个应用的字段。
3. 难度由此分层：单应用任务考察在厚页面结构中的定位与填写，跨应用任务额外考察取值的准确与写回的完整，多来源任务再叠加中间结果的保持。
4. 每道任务在入库前由人工走通一条仅使用界面的路径，以验证其在给定初始状态下可解；该路径不作为参考解提供给智能体，任务撰写与验收由不同人员完成。

**说明**

上一版把构造流程写成工序清单，篇幅与重要性不匹配。现在只保留两条对读者真正有用的信息：出题顺序是先关系后题面，以及每题有人工走通的界面通路。前者是「关键数值不在指令里」的唯一工程落点，后者对应同行为每道任务配一段验证解的做法，用于证明任务从初始状态出发确实可解，而不是给模型抄的标准轨迹。

第 2 句的三种形式来自实际出题经验，是这一段真正的内容。会上要主动说明第三种形式目前的弱点：多来源任务的终态常常落在笔记类对象上，业务对象强度不如订单与账目，后续需要把这类终态迁到更硬的对象上。

**讨论**

- **A（推荐）。** 三种形式全写，难度分层用一句带过，不报各层的条数。
- **B。** 三种形式只写前两种，第三种留待正式集合补齐后再写。更保守，但会丢掉「多来源」这一层难度主张。
- **C。** 难度分层报出各层条数。数字更实，但目前第三层条数偏少，报出来反而暴露不均衡。

### ¶4 领域构成与规模

**本段要立住的观点**：任务集按业务领域组织，规模与构成同时说明覆盖广度与跨应用比重。**关键词：按领域不按应用、约 200 条、跨应用按判定级定义统计。**

**论点**

1. 任务按业务领域而非按应用组织，覆盖与环境一致的七个领域。
2. 集合的设计规模约为 200 条，其中约 116 条为单应用任务，84 条为跨应用任务。
3. 每个常用应用至少承载 3 条任务，高频应用承载 5 至 8 条，以避免某个应用只被单一任务覆盖。
4. 跨应用条目仅统计满足判定级定义的任务；仅作为通知信道出现的应用不计入其所属领域的覆盖。

**说明**

按领域组织而不按应用组织，是为了让覆盖主张与环境第四段一致：领域不同意味着终态形式不同，判定模板不能复用。第 3 句防止「应用很多但每个只出一题」的质疑。

会上必须先说清两件事，不要等被问：一是社交领域目前任务偏少，需要补；二是当前任务表按较松口径统计跨应用，与第 2 节钉死的判定级定义存在缺口，严格满足两侧均有写入的数量明显低于表上数字。填补缺口不能靠同一骨架换皮，也不能靠只作通知信道的任务，否则定义自我作废。正式集合的分母尚未锁定，正文写「约」，不写候选数量，不写「筛选中」。

**讨论**

- **A（推荐）。** 分两档报：两侧均有业务写入者计为跨应用，仅在第一个应用读出事实、在第二个应用写入者单列为一类并另行命名。正文定义只管前一档，缺口摆在明处，已出的题不必推翻。
- **B。** 只报严格口径，跨应用数字相应下调。口径最干净，但数字对外不好看，且与设计目标 84 条的差距需要解释。
- **C。** 放宽正文定义以匹配现有统计。等于作废「每个被点名的应用都要有独立业务终态」这条主张，不建议。

### ¶5 一条典型任务

**本段要立住的观点**：这条例子要说明的是判定验的是两个应用之间的关系，而不是一串操作是否被执行。**关键词：题面给指示、判定验关系、两类失败划边界。**

**论点**

1. 一道代表性任务要求智能体在购物应用中选定指定型号与规格的商品，使用平台补贴完成支付，随后在记账应用的指定账本与分类下按这次实际支付的金额记入一条支出，并在备注中标明来源与商品。
2. 指令中不出现任何金额：商品标价不是答案，实际支付金额只有在补贴生效后于支付流程中产生，只能在运行时读取。
3. 两个应用各自产生业务写入，判定检查订单与指定型号规格匹配、记账条目的金额与本次支付金额在容差内相等、备注包含指定来源，并把允许变化的状态路径限定在这两个对象之内。
4. 两类失败界定了判定的边界：支付已完成而记账未写入的轨迹判为失败，说明判定要求两侧均有写入；账本、分类与备注均正确而金额抄错的轨迹同样判为失败，说明判定检查的是取值而非路径。

**说明**

这条例子被选中，是因为它同时满足四个条件：两侧都是无争议的业务对象；需要写回的数值是运行时算出来的而不是题面给定的；判定是关系式；这两类失败都在实际轨迹中出现过。第 4 句是全段的观点所在，没有它这一段就只是复述题面。

正文只写「该任务存在一条人工走通的、仅使用界面的路径」，不报任何成功率。另一条涉及更多应用的长程演示任务不进正文，会上摊开，必要时进附录；它目前不在正式集合的分母内，写进正文会被追问在 200 条里的位置。

**讨论**

- **A（推荐）。** 正文只精写这一条，带两类失败。三页内若精写两条，每条只剩两句，等于没有例子。
- **B。** 换成多应用长程任务的降级写法，去掉不计入跨应用的通知环节，保留多来源取值与预算约束两层。冲击力更强，但需要当场确认能否压进约四分之一页，且该题不在正式分母内。
- **C。** 例子放附录，正文只留一句形态说明。省页最多，但基准节会全程停在机制层，读者无法判断任务的真实难度。

### ¶6 结果报告方式与可复现协议

**本段要立住的观点**：工具是可选捷径，单一成功率读不出与工具有关的结论，因此报告口径必须并列两列并附效率指标。**关键词：两列成功率、不合成总分、初始状态与时间基准可复现。**

**论点**

1. 主表在同一批任务、同一初始状态与同一套判定下并列报告两列成功率：纯界面解法与界面—工具混合解法，二者在表中地位相同，后者不作为消融项。
2. 辅表报告工具调用覆盖率、调用成功比例，以及两类解法各自的平均步数；失败轨迹常在到达步数上限前终止，平均步数须与成功率联读。
3. 意外改动作为独立一列报告；成功率、调用率与步数不加权合成单一榜单。
4. 可复现协议随基准发布：所有任务自同一份初始状态记录恢复，各应用共用同一固定时间基准，使指令中的相对日期在任意一次执行中指向同一天；判定脚本与初始状态一同公开。
5. 环境目前提供单一初始数据配置，仿真界面的保真度亦弱于物理设备，这两点限定了本基准所能支持的结论范围。

**说明**

第 1 至 3 句必须写在环境章，否则读者会默认混合解法那一栏只有一个成功率，实验章再改口就晚了。原因在于我们的正式任务保留了纯界面路径：一个模型可以完全不调工具而在混合设定下取得不低的成功率，成功率回答「事情有没有办成」，回答不了「会不会用工具」和「工具有没有省步数」。把工具做成接近必要条件的工作可以只看成功率，我们的出题方式不同，照搬会读不出任何结论。不合成总分的理由是权重没有依据，且会把「界面很强、不用工具」与「调用很勤、经常失败」压成同一个数。

第 4 句用半句交代固定时间基准，不把它写成环境特性，也不单独占论点位置。第 5 句把局限压成一句放在协议之后：这一章不设局限小节，需要主动承认的是最可能被审稿人自己发现的两条——单一初始数据配置，以及仿真保真度弱于真机。前者要写成方法学取舍并说明我们因此不报告同一任务在不同数据实例下的一致性；后者是这类工作的标准表述，主动承认比被问出来强。判定自身的漏判与误判尚未在大量真实轨迹上系统度量，会上口头登记为已知问题，不给未经测量的数字。

**讨论**

- **A（推荐）。** 环境章用三到四句写清报告承诺，空表放实验章。环境章负责口径，实验章负责数字，成本约 0.1 页。
- **B。** 环境章完全不写报告方式。省页，但留下读者以为只有单一成功率的误读风险。
- **C。** 环境章直接画空表。最清楚，但三页内一张空表代价高，除非砍掉与同类环境的比较表。
- **D。** 局限是否再补一句「多数据实例的一致性列为后续工作」。补上更完整，但容易被读成承诺，建议不写承诺，只写现状。
