# 轨迹审查方法论（可复用于每一批新实验）

## 为什么需要这套东西

一批全量实验（hybrid + gui_only）跑完就是几十到上百条轨迹。逐条人工看不现实；
把所有轨迹原样丢给 LLM 子agent读一遍也不现实——太贵，而且大部分轨迹只是
"正常复用已验证过的模式"，值不回读它的成本。

所以审查分两层，而且**第二层必须强制多维度输出，不能只顺着最先想到的一个
角度写完就收工**（这是本文档要长期维护的硬约束，见下面"审查目标"一节）：

- **第一层（免费、秒级、确定性脚本）**：只读 `results.jsonl`（跑批时已经记录好的
  candidate_tools / 实际调用的工具 / success / steps / stop_reason / warnings 等）
  加上对应 suite 的 spec 源码（声明的候选工具、goal 种类、有没有 extra_check），
  用固定规则给每条任务打标记，自动分诊出"正常"和"值得细看"，并写清楚"为什么
  值得细看"。**不碰 trace.json、不碰截图，所以对几百条量级也是秒级的。**
- **第二层（只处理第一层标出来的少数轨迹，五维度强制框架）**：读被标记任务的
  `trace.json`（本身是纯文本：每步Thought+Action+工具反馈+路由变化，不需要
  截图）+ 对应的 spec / app_tools 定义 / defaults.json，**同时**给出五个独立
  维度的结论（见下文），产出结构化报告。执行方式见下。

这样每跑完一批新实验，流程是固定的三步：跑脚本 → 看标记清单 → 按同一套
prompt模板复核被标记的任务，不用每次都从头设计"该看什么、怎么分工"。

## 第一层：`trajectory_audit.py`

位置：`bench_env/task/hybrid_tools_selfbuilt_v1/trajectory_audit.py`（放在 v1
是因为其它 suite 都复用它的 `base.py`/`spec()` 约定，不代表只能审 v1）。

用法：

```bash
python3 bench_env/task/hybrid_tools_selfbuilt_v1/trajectory_audit.py \
  --suite hybrid_tools_selfbuilt_v4 \
  --hybrid runs/full-v4-hybrid-<ts> \
  --guionly runs/full-v4-guionly-<ts> \
  --out runs/audit-v4.json
```

支持 `--suite/--hybrid/--guionly` 三元组重复传参，一次跑完多个 suite（v1~v4 已验证）。

标记清单：

| 标记 | 含义 |
|---|---|
| `tool_declared_unused` | 候选工具一次都没被调用（**注意**：这条假阳性率不低，见下方"本轮教训"） |
| `tool_used_then_gui_fallback` | 用过候选工具，之后一长串纯GUI操作 |
| `low_tool_utilization` | 非mobile_use调用占比很低，名义hybrid实质接近gui_only |
| `no_hybrid_step_advantage` | hybrid步数 >= 对应gui_only步数 |
| `hybrid_worse_outcome` | hybrid失败但gui_only成功（工具帮倒忙候选，**注意**：多数案例最终查明与工具本身无关，见下方教训） |
| `hybrid_failed` / `gui_only_failed` | 该模式失败 |
| `*_near_maxsteps` | 步数逼近预算上限 |
| `*_judge_error` | judge本身报错 |
| `hybrid_warnings` | 出现声明之外的状态变化（一般是浏览历史等副作用，多为良性，但要抽查） |
| `declared_state_change_not_diff_checked` | **硬规则**：spec声明会改变某个非notes的app状态，但只有notes_note goal、没有extra_check——这处状态变化从未被真正diff过 |

2026-08-10 对 v1~v4 全部183条任务跑的结果：`declared_state_change_not_diff_checked`
命中 **0** 条——确认"状态类任务必须做state diff，不能只信notes文本"这条自律
规则被严格遵守。其余标记的汇总计数见 `runs/trajectory-audit-v1to4.json` 的
`merged_flag_counts`。

## 审查目标：五个维度必须都回答，不能只查出一种结论

这是本轮被明确纠正的一点：**不能看了轨迹之后只检查出"一个环境问题"或"一个
模型失败"就结束**。每条被标记任务，第二层复核必须**同时**给出下面五个维度
的结论——即使某个维度"不适用"，也要写明"不适用，因为……"，禁止留空/跳过：

| 维度 | 要回答的问题 | 结论应该导向的具体产出 |
|---|---|---|
| 1. `tool_boundary` 工具使用边界 | 工具到底有没有被用上、用对没用对；没用上是模型问题还是工具设计本身帮不上忙；是否是已知四类（idinhand/state_direct/field_mismatch/query_scan_mismatch）之外的新边界 | 新边界类型 → 补进 `04-难度升级与跨App设计备忘.md`；审计脚本本身的分类错误（见下方教训）→ 改进 `trajectory_audit.py` |
| 2. `env_bug` 环境/App bug | 有没有观察到疑似bug（GUI卡死反复点无效元素、入口缺失、组件渲染缺字段等），给出具体页面/组件线索 | 属实 → 在worktree里立刻修、走patch流程推主分支（本轮：修了Kapi日期选择器、Luckin新增地址表单bug） |
| 3. `failure_mode` 任务难度与模型失败点 | 失败/步数异常具体错在哪一步、什么原因（记忆丢失/字段混淆/幻觉编造/操作绕远/GUI摩擦/"低成本笔记捷径早退"等） | 归类进已知失败模式库；新模式 → 补进备忘录 |
| 4. `verifier_risk` 验证脚本完整性 | 这条任务的verifier判定条件是否过严（正确措辞被误判失败）、过松（错误/编造答案也能通过）、或能被幻觉蒙混过关 | 属实 → 立刻改spec文件（本轮：修了 memory_03 的"10"子串误匹配"硅谷101"假阳性bug） |
| 5. `cross_mode_signal` 跨模式对比 | 有hybrid和gui_only两条轨迹时，工具相对纯GUI到底有没有带来实质优势（步数更少/成功率更高）？没有的话为什么？ | 汇总"工具真有优势/工具中性/工具帮倒忙"三类的实际占比，这是回答"混合模式到底值不值"这个核心问题的直接证据，不能只靠个别案例定性 |

### 本轮（2026-08-10）暴露的两条审查方法论教训（下次要注意）

1. **`tool_declared_unused` / `hybrid_worse_outcome` 这两个第一层标记的假阳性率
   都不低**，第二层复核时不能直接采信：
   - `tool_declared_unused` 常见假阳性：①GUI本身已经暴露答案字段，走候选工具反而多余；
     ②模型用了**没被列入candidate_tools、但实际更好用的"兄弟工具"**（比如
     broadcast任务候选`get_episode_summary`，模型用了`list_up_next`一次拿到全部字段，
     效果更好但审计脚本看不到）——第一层脚本只认`candidate_tools`集合，看不到这种情况。
   - `hybrid_worse_outcome`：本轮luckin/ctrip/dianping/edgenav/recovery合计约8条里，
     **绝大多数的"变差"根因跟工具返回值/工具设计完全无关**，而是"hybrid模式下模型更容易
     用`notes__create_note`当低成本早退捷径、跳过应有的核实/读屏步骤直接编答案"——
     这是一种新发现的、值得记录的**模型行为模式**（不是工具边界问题），起名
     "notes早退捷径"：给模型一个"记笔记就算交卷"的工具，反而可能降低它认真核对的动力。
   → 下一版 `trajectory_audit.py` 可以考虑：把"用了非候选但同app的其它工具"也计入
   "工具被使用"，避免重复出现这类假阳性。

2. **审查目标要点名"这批共性到底有没有单一根因"，不能满足于逐条罗列**。比如
   luckin那批10条，社区直觉会先怀疑"是不是某个工具的字段命名（`price` vs
   `original_price`）系统性坑了模型"——实际逐条查证后**证伪**了这个猜测（3条
   `hybrid_worse_outcome`没有一条真正调用过该工具），真实根因是`query`必填导致
   全量扫描类任务退化成"猜词"、以及上面提到的"notes早退捷径"。**证伪一个流行
   猜测本身就是有效产出**，不要因为"没找到我以为会找到的问题"就觉得白查了。

## 第二层执行方式

两种机制，效果等价，选哪个取决于当前额度/账号状况：

### 方式A：Cursor Task 子agent（本轮实际使用）

按app分组被标记任务（5~10条一组），用便宜模型（本轮用
`cursor-grok-4.5-high-fast`），把五维度框架整段写进prompt，要求输出结构化
markdown（每任务一段，结论先行；最后一段整批共性小结）。本轮6组、46条任务，
全部并行跑完，产出见同目录下 `audit-broadcast.md` / `audit-ctrip.md` /
`audit-dianping-jingdong.md` / `audit-luckin.md` / `audit-taobao.md` /
`audit-misc-v2v3.md`。

缺点：消耗Cursor自己的agent调用额度。

### 方式B：直接调API，不占用Cursor agent额度（优先推荐，但目前有两个已知阻塞）

脚本：`bench_env/task/hybrid_tools_selfbuilt_v1/llm_trajectory_review.py`。
原理：trace.json本身是纯文本（Thought+Action+工具反馈+路由），不需要截图，
所以直接把它和候选工具的真实签名（从`definitions.ts`原文抠出）拼进一次
chat completion调用即可，走仓库里已经在用的TokenHub网关
（同`tools/test_api.py`），一次性、非agentic，理论上比开agent子进程便宜得多。

```bash
python3 bench_env/task/hybrid_tools_selfbuilt_v1/llm_trajectory_review.py \
  --audit runs/trajectory-audit-v1to4.json \
  --flags tool_declared_unused tool_used_then_gui_fallback low_tool_utilization \
          hybrid_worse_outcome no_hybrid_step_advantage \
  --model gpt-5.4 \
  --out-dir runs/llm-review
```

**2026-08-10 实测的两个阻塞（下次先确认是否已解决，再决定用哪种方式）**：

1. **TokenHub网关上没有Claude/Sonnet系列模型**——查询三把已知key的
   `/v1/models`，只有 `gpt-*`（gpt-4.1~gpt-5.6系列）、`gemini-*`
   （2.5~3.5系列）、`bailian/*`（Qwen/DeepSeek/GLM/Kimi/MiniMax系列），
   没有anthropic/claude。默认用`gpt-5.4`替代（`tools/test_api.py`里验证过
   可用、也是这几个族系里综合能力较强的）。
2. **三把已知key当前都返回 `insufficient_user_quota`**（"超过项目个人限额"）——
   2026-08-10测试时gpt/gemini/bailian三把key全部403，大概率是并发跑批已经
   把额度打满，不是脚本本身的问题。等额度恢复、或者拿到新key/换成真正带
   Claude的endpoint后，直接改`--api-key`/`--base-url`/`--model`三个参数即可，
   其余逻辑不用动。

因为这两个阻塞，本轮实际用了方式A（Cursor子agent）完成，脚本已就绪留给下次。

**2026-08-11 更新：两个阻塞都已解决**——拿到一把新TokenHub key，能访问
`claude-sonnet-4-6`且无quota限制，`DEFAULT_MODEL`已改成这个。同时做了三处
加固：①prompt里明确要求输出内容不能用英文双引号（用「」或单引号代替），避免
模型在正文里写`"XX"`把JSON字符串提前截断；②`call_llm`加了一个启发式修复：
JSON解析失败时，把明显是"字符串内部误写的裸双引号"转义后重新解析一次；
③脚本改成从`TOKENHUB_API_KEY`环境变量读key，不再硬编码进代码（避免提交泄露）。
稳定性测试：同一批broadcast任务连续跑3次，核心结论（工具边界判断、env_bug
线索、失败模式归类）逐字对比高度一致，判定可用于大规模复用。

同时给脚本加了三个新参数，支持"不筛选、全量审查"：`--all`（忽略
`--flags`/`--task-id`，审查audit文件里的全部task_id）、`--chunk-size`
（每个app内部按多少条任务分块调用，默认8，避免单次prompt过大导致模型
输出质量下降）、`--concurrency`（线程池并发调用数，默认4，因为是I/O bound
所以并发有效）。每个批次除了原来的`.json`还会额外产出一份人类可读的`.md`
（每任务五维度分点陈述+本批次共性小结），格式和方式A产出的`audit-*.md`一致。

## 后续每批新实验的操作清单

1. 跑批产出 `runs/full-<tag>-hybrid-<ts>` / `-guionly-<ts>`。
2. 跑 `trajectory_audit.py`，看 `flag_counts` 判断整体健康度（有没有新类型
   问题冒出来、`declared_state_change_not_diff_checked` 是不是还是0）。
3. 先确认方式B（直接调API）的quota/模型是否可用；可用则优先用方式B省
   Cursor额度，否则退回方式A（Cursor子agent+便宜模型）。
4. 按app分组被标记任务，用五维度框架复核（每条任务五个维度都要有结论，
   不能只答一两个）。
5. 汇总结论：属实的env bug立刻修、推主分支；verifier问题立刻改spec文件；
   新发现的工具边界/失败模式/审查方法论教训都补进本文档和
   `04-难度升级与跨App设计备忘.md`；用`cross_mode_signal`维度的汇总数据
   回答"这批任务里工具真有优势/工具中性/工具帮倒忙"各占多少比例。

## 2026-08-10 首次系统跑的结果留档

- 183条任务（v1~v4）→ 一层脚本筛出46条（25%）值得细看。
- 二层复核（Grok高速档，6组并行）找到并当场修复：
  - **App bug**：Luckin「新增地址」页复用「编辑第一条地址」的表单，导致
    `luckin_v4_02`双边卡满步数——已修`apps/Luckin/pages/ProfilePages.tsx`，
    区分新增/编辑两种状态，新增给空白表单。
  - **Verifier bug**：`memory_03`的`contains=["10",...]`被"硅谷101"里的
    子串"10"误匹配，导致真正没写关注节目总数的答案也能通过——已改成
    `extra_check`里做"独立数字10"的正则匹配（不匹配"101"里的"10"）。
- 证伪了一个流行猜测：luckin工具拉低成功率**不是**`price`/`original_price`
  字段命名系统性坑模型；真实根因是`query`必填导致扫描类任务退化成猜词、
  以及下面这条新发现的行为模式。
- 新发现的模型行为模式（非工具边界，是行为模式）："notes早退捷径"——
  hybrid模式下模型有时把"调用记笔记工具"当成任务已完成的信号，跳过应有
  的核实/读屏步骤直接编答案，这是几条`hybrid_worse_outcome`案例的真实根因。
- 候选新边界类型（来自ctrip批次，未最终定论）：`query_phrase_mismatch`——
  自然语言短语query（如"上海到潍坊"）与单字段子串匹配的检索接口不兼容，
  和已知`query_scan_mismatch`相关但不同（这里实体明确，只是短语形式不对）。
- 完整逐任务证据见同目录 `audit-*.md` 六份报告。

## 2026-08-11 全量183条大规模复审（方式B，直接调API）

第一层筛出的46条只是"规则能自动判断值得细看"的子集，不代表其余137条完全
没有可挖的信息（尤其env_bug线索，规则层根本看不到trace内容）。所以这轮用
方式B对**全部183条任务**（不筛选，`--all`）做了完整的五维度复核，而不只是
之前标记出的那部分：

```bash
python3 bench_env/task/hybrid_tools_selfbuilt_v1/llm_trajectory_review.py \
  --audit runs/trajectory-audit-v1to4.json \
  --all --chunk-size 8 --concurrency 4 \
  --out-dir runs/llm-review-full-v1to4
```

- 13个app分组、切成28个批次（每批≤8条），并发4，全程约14分钟，
  **28/28批次JSON一次性解析成功**，无需人工干预。
- 产出位置：`runs/llm-review-full-v1to4/`（不在这个docs目录下，因为这是
  机器产出的原始审查记录，体量大——1.2MB、183条任务、每条五维度结论）。
  每个批次一份`<app>[_编号].json`（结构化，供程序/agent读取）+ 同名`.md`
  （人类可读，每任务五维度分段+批次共性小结），另有`_combined.json`汇总
  全部批次、`_run.log`跑批日志。
- 这轮全量扫描比之前46条子集多看出的疑似env_bug候选（尚未逐条人工确认，
  留给下一步）：jingdong搜索页某分类Tab连续20次点击坐标无响应、
  jingdong评价页笔记跳转的跨App状态丢失、kapi分类编辑页"餐饮"图标点击
  无效、luckin商品列表大量重复滑动仍看不全、ctrip酒店搜索关键词输入区
  点击后路由被强制弹回城市选择页、luckin出现过一次调用空工具名的异常
  记录——这些都还只是LLM复核给出的"疑似"信号，不是已确认结论，下一步
  由人工/agent对照具体`artifact_dir`里的`trace.json`逐条验证再决定是否修。
