## 1. 界面本身难，不是业务不懂

- **Case01**：账单要下滑才看得到最大值，模型倾向只读第一屏。交互难，不是不会找「最大一笔」。
- **Case22**：排序推理对，纯 GUI 新建仍能写错。说明写入手势比比较更脆。
- **Case75 / 日历加号**：先点进某一天再点加号，只能改时间不能改日期。工具能绕开。纯 GUI 的结构性陷阱。
- **Boss07 滚轮**：小时转盘滑过头 / 滑不动，振荡很久，最后靠**直接点数字 10** 才出来。幅度→偏移没有可靠映射。
- **播客 Task04 拖进度条**：理解对，点在 31:15，差约 75 秒。真机上也常见，不是理解错。
- **Flomo08**：思考里已经写明自己在循环，没有换策略（更小偏移或改用工具）。
- **番茄 T04 / T05 / T07**：故意留的导航迷宫；T07 还能从乱跳里爬回来。UI 深度是难度来源。
- **点评 Task01**：收藏菜在「查看全部」后面，你故意藏的。两条都摸到了，说明 GUI 可走但要探索。
- **豆瓣 Task03**：输入没生效时，模型处理很机械。

## 2. 工具有用：省步、绕陷阱、读数稳

- **Case75**：hybrid 用工具绕开日历加号陷阱。
- **滴答 008**：「买菜」用 `search_tasks` + `complete_task`，少约 6 步。GUI 做创建/日期/分享，工具做定位和批量——plus 最干净的切法。
- **倒数日 003**：GUI 搞不定日期之后才切工具，几乎做完。工具是 backup，不是第一选择。问题：为什么不一上来就调？
- **加油记账 GasKapi**：工具失败会加步，再退回 GUI。失败回退也要写。
- **vivo 国补 ShopVivoKapi**：工具读到价格 → 推断补贴已含价 → 跳过多余界面。工具返回值改变后续 GUI 决策。
- **酒店记账 TravelHotelKapi**、**火车日历 TravelTrainCal**：跨 App 运行时取值，工具读数比盯屏幕稳。
- **Case25**：两条轨迹对比鲜明，适合写「工具少导航噪声、推理更稳」。判定里硬编码题面没有的词，要先修再引用。

- **豆瓣 Task02**：`search_subjects` 带条件就是 plus，两条都纯 GUI。
- **菜鸟 002**：`list_stations` / `search_packages` 没人调。你的判断：题就不是按工具设计的，不是模型一定不会。
- **滴滴 001**：看不出混合优势。不是每道题都要会讲 hybrid。
- **豆瓣 Task01**：没用工具，但 hybrid 对「友邻视图该有内容」更坚持。工具**在场**可能抬置信度，不一定改路径。你标了：也可能是波动，先当现象记着。

## 4. 工具语义 / 基础设施（小改优先）

- **Case02**：工具调用不写 store。另：搜「全新」对不上字段；得到空不重搜。判定不该验搜索过程。
- **Case13**：`bilibili__get_ranking` hybrid 返回空。固定「排行榜第一」是 mock 的优点，工具空了这个优点用不上。
- **播客 Task04 / Task08**：`queued: true` 和 `list_up_next` 对不上；API 队列和 UI「待播清单」不同步。先分清是基础设施还是模型没懂两个 list。
- **携程 003**：`flightDirectOnly` 两条路写入不稳，判定绑了单一入口。
- **京东 003**：`search_items` 的 filters 是否写入 taskAudit，和 GUI 点筛选是否同一字段。
- **12306 日历**：年份写错，对工具不友好。

旧轨迹在小改之后：写成当时没调、调错、或返回值不可用，不重跑刷分。

- **hybrid 步数更多有时是波动**：番茄 T01 弹窗绕路，不是规划差。
