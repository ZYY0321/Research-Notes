# 协作与文档更新规范（private 仓库 + collaborator + 分支 PR）

本文件回答反复出现的团队协作问题：
1. 规范一直在更新，**让大家反复重新 clone 不现实**，怎么保证用的是最新规范？
2. 一个人做好一个 app，**怎么让别人看到？直接往 main 推安全吗？**
3. 做 app 时**遇到共性问题**，该怎么统一提、统一收敛？

> ⚠️ 先分清两条 git 路径，别搞混（这是最常见的困惑）：
> - **拉最新规范/别人的成果** = `git pull`（往下拉，随时可做，不用切分支）
> - **交你做好的 app** = 推到你自己的分支 + 开 PR（往上交，由组长审核合并后别人才看得到）

---

## 1. 规范文档是单一来源，只在主仓改

**"规范文档"指这四份**（AI 和人都以它们为准）：

| 文档 | 给谁 | 作用 |
|------|------|------|
| `docs/app-replication-pipeline-v3.md` | AI | 流程 / gate / 三条铁律 / **§10 保真四要素** |
| `docs/APP_REPLICATION_PLAYBOOK.md` | AI | 工程实现（manifest、数据分层、双语、验收清单） |
| `docs/app-replication-handbook.md` | 人（AI 启动读） | 操作手册正文 |
| `演示教学/app复刻操作指南.md` | 人（新同学） | 操作指南 |

**规则**：

- 这四份**只在主仓 `main` 分支修改**。任何人**不在自己的 fork/功能分支里私改规范**——私改会导致 8 个人各拿一份不一样的规范。
- 需要改规范 → 提 PR 改主仓 `main`，由维护者审。改动生效后，所有人下次 `git pull` 就拿到。

## 2. 不用重新 clone —— 每次开工前 `git pull`

大家是直接 clone 主仓来用的，保持规范最新**不需要重新 clone**，开工前拉一下即可：

```bash
# 每次开工前，在项目目录下：
git pull
```

- 它只更新有变动的文件，你本地正在做的 app 不受影响。
- **判断"我的规范是不是最新"**：看 `docs/app-replication-pipeline-v3.md` 有没有 §10；`git log -1 -- docs/` 看规范文档最后更新时间。
- 只有仓库地址变了才需要重新 clone；规范内容更新一律靠 `git pull`。
- （做 app、交成果时才切分支，见下节；拉规范本身不需要切分支。）

## 3. app 工作走分支 + PR，由组长审核合并（不要自己推 main）

**前提（组长一次性做）**：仓库设为 **private**（Settings → General → Change visibility），把每个成员加为 **collaborator**（Settings → Collaborators）。这样只有团队能看到、也才能推分支。

- app 复刻在**各自的功能分支**做（`git checkout -b <你的名字>`，几个 app 都在这条分支上），完成后 `git push origin <你的名字>` 推到**你自己的分支**。
- **任何人都不要 `git push origin main`。** main 是大家共享、始终要能跑的分支，直接推容易连累所有人的 `npm run dev`。
- 到 GitHub 点 **Compare & pull request** 开 PR（base=`main`，compare=你的分支），**由组长审核 + Merge**。合并后别人 `git pull` 就能看到你的成果。
- PR 描述里**必须勾选**下面这段自查（对应 pipeline-v3 §10 / Playbook 验收清单 V8–V11）。有漏项要么补、要么在 PR 里说明为什么降级（按铁律①"宁可不做不要做错"）：

```markdown
## 保真四要素自查（pipeline-v3 §10）
- [ ] ① 外观：有图标；系统顶栏色和 app 主色明暗对应；色值取自真机（记进 design-tokens.md）
- [ ] ② 双语：导航/Tab/主按钮/空态文案接了 useAppStrings，能跟随 OS 语言切中/英
- [ ] ③ 数据：种子数据每主列表 ≥5 条且多样；用户产生的数据走运行时写入，没硬塞进 defaults.json
- [ ] ④ 三条铁律：可见即可点（无静默死区）/ 同组一致 / 宁可不做不要做错
- [ ] 五道机器 gate 全绿（consistency / build_nav / tsc / lint / runtime_walkthrough）
```

> 建议把上面这段放进仓库的 `.github/PULL_REQUEST_TEMPLATE.md`，新建 PR 时自动带出，不用每次手抄。

## 4. 发现共性问题：统一入口，别各修各的

做 app 时发现的问题分两类，处理方式不同：

- **只影响你这个 app 的问题** → 在你自己的分支 / PR 里修，不用惊动别人；也可以直接让陪你做的 AI 改。
- **共性问题**（多个 app 都会遇到，或暴露了规范/框架的缺口，比如"大家都漏做顶栏色"）→ **不要各自在分支里各修各的**，走统一入口收敛：

**共性问题反馈入口：在飞书群/协作文档里发一条**，写清三点：
1. 什么问题；
2. 你在做哪个 app 时遇到的、你觉得别的 app 会不会也这样；
3. 你觉得规范/流程该怎么改。

维护者的职责：把确认的共性问题**收敛进 pipeline-v3 §10 或 Playbook**，让它变成"AI 下次自动做到 + 人验收时自动卡"的默认项——这样同一个坑不会第二次让大家各踩一遍。收进规范后，所有人下次 `git pull` 就自动带上。

---

## 一句话总结

- **规范只在主仓改，大家 `git pull` 就是最新，不用重新 clone。**
- **仓库 private + 全员 collaborator；做 app 走自己的分支，不要自己推 main，开 PR 由组长审核 merge。**
- **共性问题发飞书群/文档，由维护者收敛进规范，而不是各修各的。**
