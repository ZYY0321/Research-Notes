# App 复刻协作流程 v3(草案)

> **版本**:v3.0-draft | **日期**:2026-06-10
> **定位**:本文档定义"人 + AI"协作复刻一个真实 App 的完整流程,目标是交付给**不会写代码的操作员**也能执行。
> 技术细节(目录结构、OS 约束、编码规范)仍在 `APP_REPLICATION_PLAYBOOK.md` v2.0,本文档是它上面的协作层。
> **试验场**:淘宝复刻(`docs/taobao-replication/`)。本文档随实践迭代,淘宝完成后定稿为 v3.0。

---

## 0. 核心设计原则

### 0.0 保真定位(对齐 mobilegym 官方实践)

mobilegym 官方追求**行为保真,不是像素保真**(README 原文),已有 app 全是缩减版
(美团 6 页、微信 12 页、最大的支付宝 50 页),视觉资产大量合成。
本流程在官方基线上加一档:**核心页面视觉锚定真实截图,长尾页面由 AI 按习得的设计规范外推**。
范围必须同样收缩:单 app 目标 30~50 页,先定范围再采素材,范围外一律 wontfix。

### 0.1 Ground truth 是什么

| 层级 | 事实源 | 形式 | 谁产生 |
|------|--------|------|--------|
| 视觉+交互事实 | **链路录屏** | `<app>_images/recordings/` 下的视频 | 人(自然操作录屏) |
| 视觉锚点 | 长截图 | 8~15 张关键页高清滚动截图 | 人(采集) |
| 交互补充 | 答疑记录 | `01-questions.md` 中人的回答(录屏没覆盖的才问) | 人(对着真实 app 验证) |
| 转写层 | **spec.json** | 页面树:节点 → 证据(0..n) + 交互 + 判题条件 | AI(起草)+ 人(审计签字) |
| 实现层 | 代码 | mobilegym app 目录 | AI |

**spec 不是 ground truth,是上述事实的转写;节点划分与画面聚类由 AI 完成,
截图/视频帧是挂在节点上的证据附件,不存在"一图一节点"的对应关系。**

spec 中每条交互必须带 `source` 字段,三档证据等级:

| source | 含义 | 约束 |
|--------|------|------|
| `frame:<视频>@<时间>` / `screenshot:<文件>` | 有视觉证据 | P0 交互必须是此档或 qa 档 |
| `qa:<问题编号>` | 人工答疑确认 | 同上 |
| `inferred:<推断依据>` | AI 按设计规范/品类惯例外推 | 仅允许 P1/P2;审计页中高亮标出,供人重点抽查 |

转写可能出错,所以冻结前必须过人工审计(Gate 2),审计手段是反渲染(见 2.3)。

### 0.2 人与 AI 的分工铁律

- **人不写文档、不写代码、不读 JSON。** 人只做三类动作:**采集**(截图)、**答疑**(选择题)、**审计**(对着真实 app 勾对错)。
- **AI 不做主观判断。** 截图里看不出来的交互行为一律提问,不许猜;完整性一律由机器算 coverage,不许自评"已完成"。
- **spec-first 修复纪律**:任何阶段发现的错误,先改 spec(并注明来源),再改代码。代码永远追随 spec。

### 0.3 v2 两大失败模式的对应解法

| v2 失败模式 | 根因 | v3 机制 |
|-------------|------|---------|
| 前端不像真实应用 | 无视觉基准,AI 凭印象画 | 每个 spec 节点绑定真实截图;实现后 Playwright 截图与真实截图并排比对(Gate 4) |
| 没按文档写完整 | 完整性靠 AI 自觉 | coverage = 代码中实际 `data-action`/`data-trigger` ÷ spec 声明的 interactions,每层机器 gate,<100% 不放行(Gate 3) |

## 1. 流程总览

```
阶段0 采集        阶段1 起草           阶段2 审计·冻结      阶段3 实现          阶段4 验收         阶段5 沉淀
[人 2~3h]   →   [AI]          →    [人 1~2h]  ★Gate → [AI,机器gate]  →  [人 ~1h] ★Gate →  [AI]
照清单截图      读图→spec初稿        反渲染审阅页          spec→骨架→分层实现   视觉比对+走P0链路   流程问题写回
              +疑问清单+缺口清单     人勾对/错/漏          每层跑coverage      问题→先改spec      playbook/模板
                 ↑________________人补拍/答疑循环↑                            ↑____打回循环____↑
```

人工总投入:约 0.5~1 个工作日,集中在三道 Gate(0/2/4),全部不需要技术背景。

## 2. 各阶段细则

### 阶段 0 — 定范围 + 素材采集(人,约 1 小时)

**0a. 定范围(AI 提案,人确认,10 分钟)**:AI 依据品类先验提出范围提案
(目标页数 30~50、范围内模块、wontfix 清单),人确认或增删。范围决定录哪些链路。

**0b. 采集(人,约 1 小时)**:见品类采集协议(电商版:`taobao-replication/00-screenshot-checklist.md`)。
操作员**不做任何"截不截"的判断**,只做两件机械的事:

1. **链路录屏**(主要素材):把范围内的每条核心流程像平时一样自然走一遍,手机录屏。
   小变化、弹层开合、转场全部自动覆盖;营销弹窗直接关掉(反正 wontfix)。
   录屏同时充当交互事实——"点这里发生什么"在视频里直接可见,大幅缩减疑问清单。
2. **长截图视觉锚点**(8~15 张):关键页面滚动长截图,作为高清视觉还原基准
   (录屏帧分辨率不足以做像素级参考)。

**输出**:`<app>_images/recordings/*.mp4` + `<app>_images/anchor_*.jpg`

### 阶段 1 — Spec 起草(AI,无人工)

AI 对录屏抽帧、聚类画面、对照长截图,产出四样东西(放在 `docs/<app>-replication/`):

1. **`spec.json`** — 页面树初稿。**节点由 AI 聚类定义**(同一页面的多个滚动位置/小变化聚为一个节点的 uiStates),证据是附件:
   ```
   {
     "id": "cart.main",
     "evidence": ["frame:r2_cart.mp4@00:12", "screenshot:anchor_cart.jpg"],   // 0..n 个
     "uiStates": ["empty", "items", "editMode"],
     "regions": ["顶栏", "店铺分组列表", "结算栏"],
     "interactions": [
       { "element": "结算按钮", "gesture": "tap",
         "effect": "nav", "target": "order.confirm",
         "transitionId": "cart.checkout.open",
         "source": "frame:r2_cart.mp4@01:03",   ← 证据等级见 0.1,必填
         "priority": "P0" }
     ],
     "links": { "children": [...], "siblings": [...] }
   }
   ```
   校验器规则:P0 交互的 `source` 必须是 `frame/screenshot/qa` 档;`inferred` 只允许出现在 P1/P2,且必须写推断依据。

2. **`design-tokens.md`** — 从锚点长截图提取的设计规范(配色、卡片样式、字号、间距、圆角体系)。所有 `inferred` 页面的视觉生成都受它约束,保证长尾页面风格不跑偏。

3. **`01-questions.md`** — 疑问清单。**只问录屏和截图都回答不了的交互**,选择题化:
   ```
   Q12. 订单列表的订单行长按会发生什么?(请在真实 app 中操作后勾选)
   [ ] A. 出现删除菜单  [ ] B. 无反应  [ ] C. 其他:______
   ```

4. **`02-gaps.md`** — 缺口清单(哪条链路录屏缺失/中断,需补录,最多一轮)。

### 阶段 2 — Spec 审计与冻结(人,1~2 小时)★ Gate

1. 人先完成 `01-questions.md` 答疑 + 按 `02-gaps.md` 补拍 → AI 更新 spec
2. AI 生成**反渲染审阅页**(`review.html`,本地打开):每张真实截图上叠加编号标注框,
   旁边列出该编号的交互描述("①点击→商品详情页 ②左滑→删除按钮")
3. 人拿手机对照真实 app,逐项勾 **对 / 错 / 漏**(漏 = 真实 app 有这个交互但 spec 没写)
4. 错/漏打回 AI 修订,循环直到人签字 → **spec 冻结为 v1.0**,打 tag

> 审计可以抽查(P0 全查,P1/P2 抽 30%),但 P0 必须全查——下游所有机器验证的正确性都建立在这里。
> `inferred` 条目在审阅页中高亮显示,是 P1/P2 抽查的优先对象;人觉得不对的 inferred 条目可当场改答案,等价于一次答疑。

### 阶段 3 — 编译与分层实现(AI,机器 gate,无人工)

1. spec → 生成物:`navigation.declaration.ts` 骨架、交互矩阵(只读视图)、种子数据脚本、feature inventory
2. 按 Playbook v2 的 Layer 0→5 分层实现
3. **每层结束必须通过**:
   - coverage 校验器:spec 中该层 interactions 的 `transitionId`/`dataAction` 在代码中 100% 出现
   - `node scripts/build_nav_artifacts.mjs <App>` 无 ERROR
   - `npx tsc --noEmit` 无错误
4. 每页实现完成后 Playwright 截图(360×800),与真实截图自动拼接成对比图存入 `docs/<app>-replication/visual-diff/`

### 阶段 4 — 人工验收(人,约 1 小时)★ Gate

1. **视觉验收**:翻看 visual-diff 对比图,逐页打分(后续可加 VLM 预筛,人只看低分页)
2. **交互验收**:AI 从 spec 生成 P0 验收脚本(自然语言步骤),人在模拟器里照着走一遍
3. 发现问题 → 判定是 spec 错还是实现错:
   - spec 错 → 改 spec(记录修订原因)→ AI 同步改代码
   - 实现错 → 打回 AI 修复 → 重跑该页机器 gate
4. P0 全部通过 + 视觉无不及格页 → 验收通过

### 阶段 5 — 沉淀(AI,无人工)

1. 本次流程中暴露的问题(清单缺项、疑问清单覆盖不足、工具 bug)写回本文档和品类清单模板
2. 新品类的截图清单模板归档,供下一个同品类 app 复用

## 5. 阶段3 实测补充(淘宝试跑,2026-06-10)

### 5.1 机器 gate 抓到的四类合同违规(全部应进 Playbook 常见坑表)

| 坑 | 症状 | 规则出处 |
|----|------|---------|
| 绑定点用变量传 transition id | 静态分析找不到触发点(TabBar `bindTap(tab.transitionId)`) | AGENTS「ID 必须字符串字面量」 |
| actions 独立导出而非内联 uiStates | `actionsDeclared=0` | 官方 checker 只读 `uiStates[].actions` |
| actionId 命名合同 | ≥3段;select 须 `<prefix>.select.<option>`;input 须 `paramsSchema.value` | check_navigation_declaration_consistency |
| 离散 UI 态键写进 queryParams | 所有 uiState 被当 base 态报错 | checker 把 queryParams 键从离散键中剔除 |

### 5.2 静态 gate 的盲区:运行时崩溃

四道静态 gate 全绿的代码,首次点开商品详情即崩——Zustand selector 返回新数组
(`useStore(s => s.xs.filter(...))`)导致无限重渲染。
**结论:阶段 3 需要第五道 gate「运行时走查」**:Playwright 按 spec P0 交互自动逐条执行,
监听 console error / pageerror,零容忍。与视觉比对共用一次遍历。

> ✅ 已建成并二次验证(2026-06-11,`apps/Taobao/assets/runtime_walkthrough.py`):
> 仅监听报错不够——**死交互(点了没反应)不抛错**,走查必须带**状态断言**
> (effect=state 的交互执行后断言 `__SIM__` 状态真的变了)。该 gate 实战抓到两个静态全绿的真 bug:
> ① 组件 `{...binding}` 展开后被 `onClick={undefined}` 覆盖(左滑删除/移收藏全死);
> ② SwipeRow 在 pointerdown 立即 setPointerCapture,吞掉行内一切子控件 click
> (勾选框/步进器/明细全死)→ 修法:>10px 水平位移确认拖动意图后再捕获。
> 两个都已修复并固化为 W4/W5/W6 回归断言。
>
> **错误发现的人机分工(定版)**:人不需要列错误清单——
> ① 已覆盖交互:走查断言自动回归;② 未覆盖的:人报一句现象(「点删除不行」)即可,
> AI 负责复现→定位→修复→把它变成新断言(本轮即此流程);
> ③ 系统性扫盲:元素普查 + agent 探索/长链任务批量产出死交互清单。人是触发器,不是登记员。
>
> **新做 app 必含:返回可达性断言(2026-07-06 补,源于豆瓣「页面卡死无法退出」根因分析)**:
> 死交互里有一整类是**「返回/关闭」跳错或卡死**——返回被实现成"再压一个新页"(push)而非"退回上一页"(pop),
> 越退栈越深;或返回键被全屏遮罩盖住、进入路径不匹配直接抛异常。这类**静态 gate 原理上看不见**
> (声明/绑定数目都对),**人工审核也抓不到**(审核页白话"点退出→回小组页"语义完全正确,push/pop 的差别在白话层不可见),
> 唯有运行时走查能一抓一个准。因此**每个新 app 的 `runtime_walkthrough.py` 必须包含一条返回可达性断言**:
> > 从若干代表性深层页面出发,连续触发 `system.back`(≤N 次),断言 ① 最终能回到某个 tab 根页;
> > ② 途经的 URL 序列**无环**(不出现 A→B→A→B 打转或越退越深)。
> 逻辑与具体 app 无关,可直接抄进各自的走查脚本;它把"卡死页面"这一整类变成自动回归。

### 5.3 资产管线:装饰性位图(商品图/头像/分类图标等)

**AI 决策规则(必读)**

| 用户是否提供生图 API + key | AI 在阶段 3 的做法 |
|---|---|
| **已提供**(对话里明说、或给了 `base_url`/`api_key`/环境变量如 `TOKENHUB_API_KEY`、`OPENAI_API_KEY` 等) | **优先大批量生图**:实现期尽早跑通资产脚本,把清单里所有需要位图的资源一次性生成 PNG,**不要**默认只用 SVG 占位糊弄过去 |
| **未提供** | 用 `regen_defaults.py` 合成 SVG/CSS/Lucide 占位即可;功能 gate 不受影响,视觉质感降级可接受 |

**「已提供」的判定**:用户主动给了可用的 endpoint + key,或明确说「用我这套生图 API」——不要求用户自己跑脚本,**由 AI 配置环境变量并执行生成**。

**批量生图执行要点**

- 参考实现:`apps/Taobao/assets/gen_item_images.py`(prompt 模板 + 幂等跳过已存在 PNG + 4 并发 + 失败可重跑)
- 新 app:复制该脚本到 `apps/<App>/assets/`,按 `defaults.json` / `design-tokens.md` 列出**全量**待生成清单后一次性跑完(商品主图、店铺 logo、用户头像、分类图标等凡在 UI 里显眼展示的位图)
- 种子数据脚本(`regen_defaults.py`)逻辑:**有 PNG 用 PNG,缺失才回落 SVG**——因此批量生图应在或紧挨 `regen_defaults.py` 首次生成前完成
- prompt 范式(电商主图):`<主体描述>,电商商品主图,专业产品摄影,浅色干净背景,无任何文字无水印`
  (「无文字、无水印、无 logo」必须写,否则生成图常带乱码文字)
- 用户 API 与仓库默认不一致时:用环境变量 `IMAGE_GEN_BASE_URL`/`IMAGE_GEN_MODEL`,key 用 `IMAGE_GEN_API_KEY`(兼容 `TOKENHUB_API_KEY`);**禁止**写进代码或 git。共享模块:`tools/image_gen_client.py`
- 网关偶发 404/超时:脚本幂等,重跑只补缺失项

**安全红线**:生图 prompt **只能描述合成主体**(如「白色蓝牙耳机」),**不得**把 `*_images/` 真机截图、含个人信息的照片上传给生图 API。真机图仅作 spec 证据与视觉比对,不作生图输入。

## 6. V1 之后:迭代模型(回应"瀑布还是迭代")

阶段 0-5 是 **V1 增量**,不是项目的全部——它一次性走完是因为冷启动需要建立全套资产。
V1 验收后进入**迭代循环**,每轮都小而完整:

```
        ┌─────────── 发现(三个渠道,见 6.1)───────────┐
        │                                              │
        ▼                                              │
  spec 修订(specVersion++,标注来源)                  │
        │   证据不足时 → 人工补图/答疑(见 6.2)        │
        ▼                                              │
  实现(仅本轮增量)                                    │
        ▼                                              │
  机器 gate 回归(coverage/静态分析/tsc/lint            │
   + 运行时走查 + 视觉比对)── 全绿 ──→ 人工抽验 ──────┘
```

这就是增量-迭代模型(非瀑布):spec 是持续维护的 backlog,每轮迭代是一个小 sprint,
机器 gate 是回归测试,保证增量不破坏存量。**spec-first 纪律在迭代期同样铁律。**

### 6.1 缺失发现的三个渠道(回应"除了人工还能怎么发现")

| 渠道 | 机制 | 抓什么 | 成本 |
|------|------|--------|------|
| ① 人工走查(Gate 4) | 人在模拟器里按真实习惯用 | 体感差异、行为不符 | 人时,每轮~30min |
| ② **VLM 元素普查**(新工具,待建) | 对每张真实截图问 VLM「枚举所有可交互元素」,与 spec 该节点的 interactions 做差集 | **看得见但 spec 没声明的元素**(本轮漏掉的顶栏搜索图标正是此类) | 全自动,一次 API 扫描 |
| ③ **Agent 探索 + 长链任务**(新 suite,待建) | a) 让 GUI agent 在 mock 上自由探索,记录「点了没反应的死元素」;b) 设计 L3/L4 长链任务跑通率 | 状态联动断裂、深链路走不通 | 全自动,复用 bench_env |

> 本轮"顶栏搜索图标缺失"的根因复盘:spec 起草时这些元素被写进了节点的 `regions`(视觉描述)
> 但没进 `interactions`(交互声明),而 coverage 只对 interactions 计数——**regions 和 interactions
> 之间没有一致性检查**。修复规则:凡 regions 文本中出现可交互元素,必须有对应 interaction 或显式
> wontfix 标注;渠道②的 VLM 普查就是这条规则的机器执行。

### 6.2 人工补图的位置:按需触发,不是固定阶段

迭代发现缺失后,先判断证据是否已存在:
- **证据已有**(61 张截图里能看到该元素/页面)→ AI 直接修 spec + 实现,**不需要人**;
- **证据缺失**(新页面/看不清的交互)→ 生成最小补拍清单(沿用 02-gaps 的"怎么拍"格式)→ 人补 →
  回到 spec 修订。
人工补图是迭代循环里的**按需子步骤**,不是前置阶段——前置全量采集只发生在 V1 冷启动。

### 6.3 AI 自修复的位置:两处,且仅两处

1. **迭代内**:机器 gate(含运行时走查)报红 → AI 修到全绿才能出迭代,人看不到中间过程;
2. **验收打回**:人工/长链任务发现的问题 → 走 6.0 循环(spec 先行)。
自修复**不允许**绕过 spec 直接改行为——那会让 spec 和实现再次脱节,回到 WechatV2 的老路。

### 6.4 长链任务验证(回应"对复杂任务没信心")

复刻的最终标尺不是"看着像",而是 **agent 能在上面完成多长的任务链**。✅ 已建成(2026-06-11):
`bench_env/task/taobao/` suite,按链长分级:
- L2:单页状态变更(加购、收藏、置顶)
- L3:跨 2-3 页(搜索→详情→加购→购物车勾选→结算)
- L4:全链条+约束(「买X寄到学校地址用花呗,下单后立即申请退款」「把购物车里最便宜的商品移入收藏」)
判题直接读 `__SIM__.getState().apps.taobao`(spec 的 judge 字段就是为此准备的)。
长链任务跑通率同时是:复刻完整度的量化指标 + 渠道③的发现工具 + 最终交付的 benchmark 资产。

## 8. Gate 4 人工走查实录与两条新铁律(2026-06-11,用户全量走查)

用户人工走查产出 ~20 项发现,逐项归类后确认:**爬虫(渠道④)只能覆盖其中"死交互"
一类;主体是另外三类**,各有对应机制:

| 类别 | 占比 | 机制归属 |
|------|------|---------|
| 语义错误(有反应但行为错):客服全跳同一店、咨询浮卡固定、找相似跳错 | 3项 | 长链任务/人工;爬虫原理上不可见 |
| wontfix 呈现失败(看似可点但静默死区):金刚区/筛选chips/收藏tab/管理/语音表情/领券中心/快递格/设置stub | ~12项 | **新铁律①**(见下) |
| 设计不一致(同组四格两可点两不可点) | 1项 | **新铁律②** |
| 欠账/普查漏项(详情长图、活动页设置图标、会话头像) | 3项 | 资产管线 + census 粒度教训 |

### 铁律①:可见即可点(三选一)
每个**看起来可交互**的元素,必须三选一:实现 / 从 UI 移除 / 点击给明确反馈(「该功能暂未开放」)。
**禁止静默死区** —— 对人是体验问题,对 agent 是探索陷阱(死区让 agent 无法区分
"功能不存在"和"我点错了")。wontfix 决策必须落到产品行为上,不能只活在文档里。

### 铁律②:同组一致性
同一视觉分组的元素(一行四格、一组 tab)交互能力必须一致:要么全可点、要么全不可点。
混合状态比全部不做更伤可信度。

### 铁律③(用户原话):宁可不做,不要做错
难做的功能(如「找相似」)宁可移除或明确"暂未开放",不要做成错误行为。

> 本轮即时修复:客服按每店动态建会话(ensureShopChat)、咨询浮卡跟随最近浏览商品、
> 消息+菜单未实现项给 toast 反馈、详情场景图生成补齐。
> 其余 wontfix 呈现问题(批量加反馈/移除)列为**迭代 #3**,按铁律①②逐页清理。

## 9. Gate 4 反馈采集协议(2026-06-12 建成,回应"人工打字报 bug 低效")

**问题**:走查发现的问题靠打字描述("XX页面的XX点不了")定位成本高、易遗漏、不可批处理。

**工具**:`tools/feedback_overlay.js` —— 浏览器 Console 粘贴即用的标注层:
1. 走查人点「🔖 标注」进入标注模式(红框提示),此时**点任何元素不触发功能,而是弹反馈卡**
2. 选问题类型(点了没反应/反应错了/样式不像/缺功能/其他)+ 可选一句话
3. 每条反馈自动携带:元素的 data-action|trigger 绑定 id(或「未打标」)、元素文本、

**AI 侧处理协议**:逐条按绑定信息定位 →「未打标」直接归入死区类(铁律①处置)→
有绑定的先跑合同爬虫单点复现 → 修复/wontfix 处置 → 回写 04-findings 表 → 回归 gate。

**SOP 更新**:Gate 4 人工走查 = 开标注层逐页点 + 导出,替代打字清单;
打字仅用于标注层覆盖不了的整体性评价(如"二楼应该下拉进入")。

## 10. 保真四要素:每个 app 的默认必做项(2026-07-01 建成,回应团队共性问题)

**背景**:8 人协作中反复出现四类共性问题——外观没完全还原、没做双语、内置数据太单薄、
文档更新分发混乱。这四项**框架早已支持,但此前只靠 AI 自觉,没写成硬约束,于是普遍漏做**。
本章把它们提升为**与三条铁律同级的默认必做项**:AI 收到复刻指令后无需人再提醒,
阶段 3 一律执行;人在阶段 4 / 阶段 6 验收时照此卡。四项都是"做不到就降级/说明",不是可选。

### 10.1 外观适配(和系统的最基础契合)
manifest 的外观字段框架已全字段支持(`icon`/`iconBackground`/`theme.colors`),
`SystemShell` 已据此驱动系统顶栏/导航栏。硬约束:

| # | 规则 | 卡点 |
|---|------|------|
| A1 | app **必须有图标**(`icon` + `iconBackground`),不得用默认占位 | launcher 里图标不是纯色方块 |
| A2 | **系统顶栏前景色必须和 app 主色明暗匹配**:浅色顶栏配 `statusBarForeground:'dark'`,深色配 `'light'`;顶栏背景应取 app 主色或首屏主色,不得出现"深底黑字/浅底白字"看不清 | 顶栏文字/图标在真机对比下清晰 |
| A3 | 圆角、字号、间距**对着真机截图逐页比**,不能只求"结构对";明显偏差按铁律②同组一致性处理 | 阶段 4 审核页/阶段 6 走查逐页比对 |
| A4 | 首屏主色、背景色、分割线色取自真机取色,不得沿用参考实现(淘宝/卡皮)的色值 | design-tokens.md 记录取色来源 |

工程写法见 Playbook §3.2「manifest 外观自检」。

### 10.2 中英双语 + 外观设置(真实感 + 数据多样性)
框架已提供 `os/useAppStrings(base, en)` + `os/locale`,`manifest.displayNameEn` 全 app 已有,
**但此前无一 app 接入,文案全硬编码**。硬约束:

- 凡 manifest 有 `displayNameEn` 的 app(即全部),**至少把导航/Tab/主按钮/空态文案接入 `useAppStrings`**,
  跟随 OS 语言切换中/英;做不到全量时,P0 链路上的文案优先。
- app 内若真机存在"外观/语言设置"入口,按铁律①处置(实现切换 / 移除 / 明确"暂未开放"),
  不得放一个点了没反应的设置项。
- **理由**:双语与外观变体直接扩大 agent 训练数据的多样性,是这套仿真的价值点之一,不是锦上添花。

工程写法见 Playbook §5.7「双语落地」。

### 10.3 数据分层(内置默认数据 + 运行时可写)
澄清团队疑问"数据要构建时 config 好,还是运行时写入":**两层都要,分工明确**。

| 层 | 位置 | 作用 | 要求 |
|----|------|------|------|
| 构建时种子 | `data/defaults.json`(经 `state.ts` 注入) | app 首次打开就有的内置默认数据 | 每个主列表 **≥ 5 条**且**内容多样**(不同日期/金额/分类/状态,不是复制粘贴同一条);头像/图片为真实观感,非字母占位 |
| 运行时写入 | app store 的 action / OS `ContentProvider` | 用户操作(记一笔、发评论、下单)产生的新数据 | 走正常交互写入 store,刷新不丢(除非触发 `DATA_VERSION` 重置);**不得**把用户产生的数据硬塞进 defaults.json |

即:**默认数据在构建时 config,用户产生的数据在运行时写入**。多样性是构建时种子的硬指标——
单薄或重复的种子数据会让 agent 学不到真实分布。工程写法见 Playbook §5「状态模型与种子数据」。

### 10.4 协作与文档更新(8 人 fork/分支 + PR)
**问题**:规范一直在更新,让 8 个人反复重新 clone 不现实,也导致有人拿旧规范做。
**做法**(详见 `docs/collaboration-and-doc-update.md`):

- **规范文档(本文件、Playbook、handbook)是单一来源,只在主仓 `main` 改**,任何人不在自己分支私改规范。
- 每次开工前 `git pull` 主仓 `main`,拿到的就是最新规范——**不用重新 clone**。
- app 复刻工作在各自 fork/分支做,走 PR 合并;PR 模板内置「保真四要素自查」勾选,漏项不合并。
- 发现新的共性问题 → 按 `collaboration-and-doc-update.md` 的固定入口提(开 issue 或加到共性问题清单),由维护者收敛进本章,而不是各自在分支里各修各的。

## 11. 返回/关闭类交互的建模与优先级(2026-07-06 建成,源于豆瓣「页面卡死」根因分析)

**背景**:豆瓣走查出现「陷入页面无法退出 / 返回跳错」一类卡死。根因分析结论:**不是某个 agent 实现错、
也不是 AI 没看懂图、更不是人工审核失职**,而是「返回/关闭」这类交互在 spec 建模 → 生成 → gate
之间约定不清,导致多个 agent 一致地建模错误。平台合同(`AGENTS.md`)其实早已规定
「返回/关闭必须用 `bindBack()`,不得用自定义 transition」,但这条规则**被覆盖率 gate 的压力盖过了**——
谁把返回键改成 `bindBack` 谁就让"声明的绑定全部保留"这道 gate 掉数,于是 agent 服从了能被机器验证的那条。

**三条约定(spec 起草 + 实现都适用)**:

1. **建模**:元素名含「返回 / 关闭 / 取消 / 退出 / ×」且行为是回到上一页的,**一律用 `bindBack()`**,
   **禁止建模成 `effect:nav` 的前进跳转**。理由:前进跳转是 push(压新页),返回被当 push 会越退栈越深、
   甚至打转卡死;`bindBack` 才是 pop(退回)。目标页写对≠机制写对——这是"栈语义"问题,不是"目标写错"。

2. **优先级(本次根因的核心)**:**平台合同 > 覆盖率 gate**。当"保留全部绑定让 gate 变绿"与
   "返回键必须 `bindBack`"冲突时,**以平台合同为准**:改用 `bindBack`,并在交付报告里列明
   "这几条 back-transition 因合同改绑,声明侧现为 unused(可后续 spec-first 清理)"。
   不允许为了 gate 数目好看而把返回键绑成前进跳转。

3. **验证**:靠运行时走查兜底(见 §5.2 末「返回可达性断言」)——静态 gate 和人工审核对这类**原理上不可见**,
   唯有运行时"连按返回必须回到根、URL 无环"能自动抓住。

> 已写好的 app 不追溯;**新做的 app 按本章执行**,并在其 `runtime_walkthrough.py` 里带上返回可达性断言。
