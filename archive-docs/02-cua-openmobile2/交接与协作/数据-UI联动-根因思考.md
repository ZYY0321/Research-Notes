# 「链路空壳」根因思考：数据-UI 联动缺失

> 日期:2026-07-06 · 待与团队讨论的方向性思考,未定稿、未改任何规范/代码
> 触发:拼多多走查发现搜索/筛选/地址「看着能用、实则失效」;负责人追问「以前好模型不用教就写对,现在不行,为什么」

---

## 1. 一句话本质

拼多多那几个问题（搜索不匹配关键词 / 筛选点了不变 / 地址写死）**不是各自独立的功能 bug,是同一个病**:

> **界面上本该"随用户输入或已选状态变化"的内容,被写成了"定死"的——硬编码常量,或忽略输入的兜底。**

| 表面问题 | 剥开看 |
|---|---|
| 搜索不匹配关键词 | 列表内容没有跟随「搜索词」变化(且 `filtered.length ? filtered : items` 搜不到就显示全部) |
| 筛选点了不变 | 列表内容没有跟随「筛选条件」变化(chips 只是本地 state,不参与过滤) |
| 地址写死 | 商品页地址栏是硬编码字符串,没读 store 的选中地址(而底层 selectAddress 是通的) |

**共同点:该"联动"的地方被写成了"定死"的。** 用一句可复用的常识概括:

> 凡界面上"应随某输入/已选状态变化"的显示内容,其值必须真的**由那个输入/状态推导**(是它的函数),
> 不得是写死常量、也不得是忽略输入的兜底。

这一条,同时覆盖搜索、筛选、排序、地址、规格、购物车数量……以及未来 app 里还没想到的所有联动。
**不需要给每个功能各写一条规矩(那会无限冗余)——缺的是"数据-UI 联动"这一个总概念。**

## 2. 为什么"以前好模型不用教就对,现在不行"

不是模型退化,是**现在的管线恰好把模型最擅长的那部分能力绕过了**。三个叠加原因:

**① 多 agent 拆分 → 模型不再"整体理解一个 app"**
以前让一个强模型"做拼多多搜索",它在一个上下文里同时想数据+逻辑+UI,脑子里带着
"搜索就该匹配关键词、搜不到显示空"的**完整常识**,自然写对。
现在 spec-first + 按模块拆给多个 agent:写 SearchResultPage 的 agent 只看到"这里渲染一个商品列表",
不一定知道"这列表必须真响应上游关键词、搜不到显示空"。**它在补一块拼图,不是在实现一个功能。**
拼图式实现最容易丢的就是跨页面的因果链。

**② 覆盖率 gate 在奖励"错误的对"**
gate 只查"每个声明的交互是否绑定了、能不能点"。于是:
- `filtered.length ? filtered : items`(搜不到显示全部)→ gate 全绿(按钮能点、列表有数据);
- 筛选点了只关抽屉不过滤 → gate 全绿(交互有响应)。
**模型在向 gate 交卷。gate 只问"能不能点",不问"点了对不对",模型就只保证"能点"。**
强模型没有这套 gate 压着时反而凭常识多做一步;有了只看覆盖率的 gate,反而收敛到"满足 gate 的最省力实现"。

**③ spec 语言里根本没有"联动"这个概念**(最深的一层,和豆瓣"返回栈语义缺失"同类)
spec 能描述两种东西:导航(点 A→去 B)、状态(点 A→改某 state)。
但**描述不了"派生关系"**:"列表 = f(搜索词, 筛选条件)"、"地址栏文字 = 当前选中地址"。
spec 没有表达"这个显示值依赖那个输入"的字段。于是 agent 看到的是静态的"一个列表""一个地址栏",
**不知道它们是活的、是别的输入的函数**,当成静态填 → 写死最省事、还过 gate。

> **所以 AI 不是没这个常识,是我们的 spec 语言把这个常识"翻译丢了"。**
> 就像让翻译传话,但你的语言里没有"过去时",再好的翻译也传不出"这件事已经发生了"。

## 3. 不冗余的解法方向(两个通用机制,不是 N 条功能规矩)

在两个地方各补一个**通用概念**,而不是给每个功能立规矩:

**A. spec 语言层(治本):加一个通用的"派生/联动"表达**
让 spec 能标注"这个显示区域是哪些输入的函数"。一个字段,覆盖所有联动场景,不针对具体功能。
(需要设计:字段形态、如何和现有 nav/state 两类共存、生成器如何消费。)

**B. 验收层(兜底):一条通用的元测试**
不针对搜索或筛选,而是:凡标注了联动的地方,喂两个不同输入,结果必须不同。
**结果相同 = 写死了 = 不合格。** 同样一条,覆盖所有联动。
(类比豆瓣的"返回可达性断言":都是把一整类问题变成一条自动断言。)

## 4. 与已固化经验的关系

- 和 pipeline-v3 §11「返回/关闭建模」是**同源问题**:都是"spec 语言表达不了某类语义 → agent 只能猜 → 多 agent 一致猜错 → gate 看不见"。
- 和 §5.2「运行时走查带状态断言」同源解法:静态和人工都抓不住,唯有"改输入看输出变没变"的运行时元测试能抓。
- 差别:§11 缺的是"栈语义",这次缺的是"派生/联动语义"。**可能存在更多同类缺口**(如:随时间变化、随权限变化的显示),值得一并想清 spec 到底还漏了哪几类"语义维度"。

## 5. 待团队决定

- 方向 A(扩 spec 语言)值不值得做?它比加几行规范文字重,动到 spec 表达能力,但属范式内扩展、不推翻现有 nav/state。
- 若暂不扩语言,能否先只做 B(联动元测试)当兜底 + 一条白话原则写进规范?
- 是否先盘一遍"spec 还漏了哪几类语义"(联动/时间/权限/…),一次性想清,避免以后一个个打补丁。
