# 构建流程 & 人工走查优化建议清单

> **视角**:内部造 app 流程(不是外部 RL 交付)。目标 = 让 8 个正在做 app 的同学**更快更稳**地交付。
> **作者**:本会话 agent / **日期**:2026-07-12
> **输入**:`79反馈.md` + `common-pitfalls-from-8-apps.md`(5 类坑)+ `ai-gate4-reproduction-report-0710.md`(63% 实验)
> **约束遵守**:doc-only(未改任何代码);每条改动都做了假阳性/假阴性自审;优先"只改 AI 自检、不改人流程"路线。
>
> **本清单的读法**:每条建议给四栏 —— **证据来源 → 具体动作 → 稳定性判断 → 通知成本**。
> 判定为**稳定且零通知成本**的,已直接写成可合入 `pipeline-v3.md` / `handbook.md` 的补丁段落(见文末 A、B 两块),你看完直接 diff 即可。

## 0. 先回答 79 反馈里最痛的一条:步骤⑥太慢

79 反馈原文拆出来的时间账:

- ①②③④⑤ 人力 **< 1 小时**(fable 5 做①-⑤ + opus 4.8 修);
- ④审核 300+ 表单,实际**只看了 AI 推断的不确定 20-30 条**(这条已在 pipeline-v3 §4 / handbook §④ 固化,不用再改);
- **⑥查改 ≈ 2 小时**,是时间大头 —— "即使 Fable 5 + 精心的技术文档,mock app 总有一些不符合真实 app 的情况";
- 一个 app 前后 **24h**,主因两个:**(a) cc 限额需要 3 个 5h 窗口**;**(b) 改起来慢,"几个功能改 20 分钟"**,用户自己猜测"不确定是网慢,还是文档要求每次改完都走一步检验导致"。

**这条清单能直接减负的部分**:⑥里"具体的死区 / 空回调 / 派生量错"这类(占走查发现的一多半),可以在**⑤结束前**让 AI 自查掉,让人在⑥少看几条。**替代不了⑥本身** —— 36% 的视觉审美 / 产品语义只能人看(见 63% 实验结论)。

**关于 (b)"改 20 分钟"的根因**:见下方**建议 4**,我做了一次机制核对,结论是"每改必检"确实是慢的一个来源,但**不能简单去掉**,给了一个折中(批量改完再统一检验,而不是每个小改都全套 gate)。

## 2. 稳定 + 零/低通知成本的建议(已写补丁,细节)

### 建议 1 · 阶段⑤ AI 自检:空回调硬扫(补丁 A-1)

- **证据来源**:5 类坑之坑一/坑四;63% 实验 Kapi #20(`stats.trend.select.metric` handler = `() => undefined`,`StatsPage.tsx:153`)。
- **实测**(本会话跑的,`trial_apps/mobilegym/apps` 全量):
  - `grep -rnE "\(\) => undefined"` 命中 **3 处**,全是真死回调,**零假阳性**:
    - `Kapi/pages/StatsPage.tsx:153`(#20 本尊,还没修)
    - `Kapi/pages/BudgetPage.tsx:41`、`:80`(`budget.month.input.value` / `budget.day.select.date` 空回调)
- **具体动作**:pipeline-v3 §5 加一条 AI 自检 shell(补丁 A-1)。命中即**硬失败**,不算完成。
- **稳定性判断**:✅ **稳**。这一档零假阳性,可以当硬 gate。理由:`() => undefined` 是模型偷懒留下的占位,没有任何合理用途。
- **通知成本**:**零**。走 AI 自检路线,不发工具、不改人流程。8 个人下次 git pull 到新 pipeline-v3 即自动带上,AI 自己执行。

### 建议 2 · 阶段⑤ AI 自检:toast-only 假回调"疑似清单"(补丁 A-2)

- **证据来源**:坑四;Kapi #12(`categoryDetail.category.select.switch` = `() => toast('可切换查看的分类')`)、#15(`categoryDetail.month.select.period` = `() => toast('上一月')`)。
- **实测(这条是本清单最重要的稳定性发现,请重点看)**:
  - 天真写法 `grep "\(\) => toast\("` 命中 **80 处** —— **绝大多数是合法的铁律① wontfix**(`toast('该功能暂未开放')` / `toast('已复制')`)。**直接当 gate 会把"故意不做"全报成 bug,严重假阳性。**
  - 排除 wontfix 措辞(`暂未开放/敬请期待/已复制/已登录/...`)后仍剩 **18 处**,且**仍然混着两类**:
    - **真 bug**:`上一月`/`下一月`/`切换统计区间`/`可切换查看的分类` —— toast **叙述了本应发生的动作**却什么都没做(Kapi #12/#15 + `SharePage:43` + Flomo `StatsRecordPage:79`);
    - **合法**:`已刷新`/`已反馈`/`已退出登录(mock)` —— 这些 toast 本身就是正确的最终反馈。
  - **判别式**:真 bug 的特征是 **toast 文案在"预告一个没发生的状态变化"**(动词性:切换/上/下/展开),合法的是"确认一个已完成的动作"(完成态:已×)。这个判别式**机器分不干净**。
- **具体动作**:pipeline-v3 §5 把它写成 **"疑似清单"自检**(补丁 A-2)—— AI 列出命中项 + 自己判断哪些像"预告未发生的变化",**报告给人复核,不硬失败**。对应 63% 实验里的"半能抓"档。
- **稳定性判断**:⚠️ **半稳**。**不能当硬 gate**(会误杀 wontfix)。当"筛"用是稳的:把人在⑥要盯的 toast 从 80 条收敛到 ~10 条可疑项。
- **通知成本**:**零**(AI 自检)。

### 建议 3 · 阶段⑤ AI 自检:`Math.random` 拼 id 的"疑似清单"(补丁 A-3)

- **证据来源**:坑四;拼多多 #5(`ensureShopChat` 用随机 id → 导航去 `ch_<shopId>` 找不到)、淘宝 #1/#2(客服 id 不确定性 → 全跳同一家店)。
- **实测**:
  - `grep -rnE "Math\.random"` 全量命中 **71 处**,但**大部分是合法视觉随机**(如 `Alipay/PayPage.tsx:50` 条形码宽度 `Math.random()*4+1`、Bilibili 直播人数)。**天真 grep 假阳性高。**
  - 缩到"用在 id 构造上"(模板串 `` `xx_${...Math.random()}` `` 或字段名含 id):**~14 处**,例如 `Alipay/SubscriptionsPage.tsx:40` `sub_${now}_${Math.random()...}`、`Spotify/SearchInputPage.tsx:25` `it_${...Math.random()}` —— 这些正是坑四"可导航 id 非确定"。
- **现有覆盖核对(重要,避免重复造轮子)**:
  - `AGENTS.md:22` + `eslint.config.js` **已经硬禁 `Date.now()` 和 `new Date()`**(走 `TimeService`)。所以 **`Date.now()` 不用再提,已被 lint 抓。**
  - **但 `Math.random()` 目前没有任何 lint 禁令**。handbook 0709 note 也说了"app 里其他 Math.random 后续分批迁 + 加 lint 禁令(在 R7 立项卡里)"。**即 R7 是正主,本条只是 R7 落地前的 AI 自检兜底。**
- **具体动作**:pipeline-v3 §5 写成"疑似清单"自检(补丁 A-3)—— 只报"`Math.random` 出现在 **id / 会话 / 导航目标** 构造里"的命中,视觉随机不报。
- **稳定性判断**:⚠️ **半稳**。当硬 gate 会误杀视觉随机;当"疑似筛"稳。**长期归 R7 lint**,本条是过渡。
- **通知成本**:**零**(AI 自检)。

### 建议 4 · handbook:"每改必检"松绑为"批量改完再统检"(补丁 B-1)

- **证据来源**:79 反馈"几个功能要他改会改 20 分钟,我不确定是我这网慢,还是文档里要求每次改完都要走一步检验导致比较慢"。
- **机制核对**(本会话查 pipeline-v3 得到):
  - pipeline-v3 §3.3 要求"**每层结束必须通过** coverage / build_nav / tsc";§6.3 要求"机器 gate 报红 → AI 修到全绿才能出迭代"。
  - 这套在**冷启动阶段⑤**是对的(保证分层不塌)。但在**阶段⑥迭代期的小修**,若 AI 对**每个单点小改**都跑一整套 gate + runtime_walkthrough,确实会把"改 3 个功能"拖成"跑 3 次全套自检"。
- **具体动作**:handbook 阶段⑤/⑥ 补一句(补丁 B-1)—— 迭代期允许 AI **把一批相关小改合并后跑一次统检**,而不是每个小改都全套;但**一批结束前必须全绿**(不降低最终门槛,只减少中途跑 gate 的次数)。
- **稳定性判断**:✅ **稳**。这是"松节奏不松门槛":最终 gate 还是全绿才交,只是把 N 次全套 gate 合成 1 次。没有引入假阴性(最后一关照跑)。
- **通知成本**:**低**。改的是 handbook 给人看的一句 + pipeline-v3 一句,不新增工具、不改 gate 本身。
- **注意**:用户自己也没确认是不是"每改必检"导致的慢(也可能是网络 / cc 限额)。补丁措辞写成"允许但不强制批量",不武断归因。

### 建议 5 · handbook 阶段⑥:走查导出加日期后缀防覆盖(补丁 B-2)

- **证据来源**:`交付环境-特性全景-0712.md` 会话记录"上次导出文件被 pull 覆盖了";现状 handbook 阶段⑥ 让导出成固定名 `gate4-feedback.json`。
- **佐证**:仓库里已有正确范式 —— `docs/kapi-replication/gate4-feedback-kapi-0710.md` / `...-0710.json` 就是"app 名 + 日期后缀"命名。说明这个约定已在实践里自发出现,只是没写进 handbook。
- **具体动作**:handbook 阶段⑥ 第 5 步 + pipeline-v3 §9 明确导出路径为 `docs/<AppName>-replication/gate4-feedback-<date>.json`(补丁 B-2),AI 侧处理协议同步。
- **稳定性判断**:✅ **稳**。纯命名约定,无逻辑风险。
- **通知成本**:**低**(改 handbook / pipeline 各一句)。

## A. 可合补丁:`app-replication-pipeline-v3.md` 阶段⑤ AI 自检段

> **合入位置**:pipeline-v3 §5 之后,或 §5.2 运行时走查之后,新增一个小节。
> 下面整段可直接粘。三条 grep 里**只有 A-1 是硬失败**,A-2/A-3 是"疑似清单,报给人复核",这个区分是本会话实测得出的,**请勿把 A-2/A-3 也写成硬 gate**(会误杀铁律① wontfix 和视觉随机)。

```markdown
### 5.4 阶段⑤ 收尾前的 AI 静态自检(2026-07-12 补,doc-only,零通知成本)

AI 在阶段⑤ 认为"代码写完"之前,**必须自跑以下三条静态自检**并在完工报告里附结果。
这是 AI 的自检动作,不是新工具、不改人的流程。依据:9 app gate4 findings 归纳的坑一/坑四,
以及 Kapi 0710 的 63% 复现实验(#12/#15/#20 就是被这几条抓住的)。

**自检 A-1 · 空回调(硬失败,命中即不算完成)**
    grep -rnE "\(\) => undefined" apps/<App>/
凡 `bindAction`/`bindTap` 的回调体是 `() => undefined` 一律报错并修掉。
实测:此模式零假阳性(空回调没有任何合理用途),可作硬 gate。

**自检 A-2 · toast-only 假回调(疑似清单,报给人复核,不硬失败)**
    grep -rnoE "\(\) => toast\('[^']*'\)" apps/<App>/ \
      | grep -vE "(暂未开放|敬请期待|已复制|已登录|已保存|已删除|已收藏|已取消|开发中|模拟)"
命中后 AI **自行判断**:toast 文案是"预告一个本应发生却没发生的状态变化"(如「上一月」「切换区间」
「可切换查看的分类」)→ 这是假回调,修;还是"确认一个已完成的动作"(如「已刷新」「已反馈」)→ 合法,放过。
**不得**把此项当硬 gate:合法的铁律① wontfix(「该功能暂未开放」)会被大量误报。
AI 把可疑项列进完工报告,人在阶段⑥ 只需复核这几条,而不是全部 toast。

**自检 A-3 · Math.random 拼可导航 id(疑似清单,报给人复核)**
    grep -rnE "Math\.random" apps/<App>/ | grep -iE "(\bid\b|_id|Id\b|\`[a-z]+_)"
只关注 `Math.random` 出现在 **id / 会话 / 导航目标** 构造里的命中(如 `sub_${...Math.random()}`、
`ch_<shopId>`)——这类会造成"点进去找不到 / 全跳同一家"(坑四:拼多多#5、淘宝#1)。
```
