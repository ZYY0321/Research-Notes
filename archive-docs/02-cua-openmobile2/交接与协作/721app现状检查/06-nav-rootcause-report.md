# 页面跳转卡死问题 · 根因分析报告

> 日期:2026-07-05 · 供项目负责人 review 用
> 范围:阶段⑥走查发现的「陷入页面无法退出 / 返回跳转错误」一类 bug(gate4 反馈 #2、#5,及后续「支付页卡死」)
> **本报告只做分析与提案,未对项目架构做任何改动**(已实施的临时止血单列于 §6,均为点状修复且已逐一汇报过)。

---

## 1. 结论(TL;DR)

针对你提出的三个假设,逐一判定:

| 假设 | 判定 | 说明 |
|---|---|---|
| ① 底稿对,实现时把组件的跳转绑定写错了 | **基本不成立** | 全程 0 例「手滑绑错 ID」。导航 gate 每轮都是 291/291 转换、409/409 动作、0 错配——9 个实现簇是**忠实地实现了错误的输入**,而不是各自写错 |
| ② 底稿写错了,但没被发现 | **成立,5 例** | spec 把 5 个「返回/关闭/取消」按钮**建模成了前进跳转(effect:nav)**,违反平台合同(AGENTS.md:156「返回/关闭必须用 bindBack,不得用自定义 transition」)。审核页的白话句式无法暴露这类错误(见 §4.4) |
| ③ 底稿不全,没覆盖到这些跳转 | **成立,3 类** | (a) spec 交互模型里**根本没有「返回栈语义」字段**(push/replace/pop),生成器只能猜;(b) 多入口共享页(如影人页可从电影/图书进入)只声明了单一 from/to;(c) 支付结果页没有声明任何返回途径 |

**一句话根因:错误不出在某一个 agent 的某一次实现,而是「返回/关闭」这一类交互在
spec 建模 → 合并 → 代码生成 → 覆盖率 gate 四层之间没有统一约定,且没有任何一道机器 gate 检查"栈语义"。
多 agent 协作把这个约定缺失放大成了一致的、系统性的错误。**

值得强调的反面证据:**ID 层面的多 agent 协作是成功的**——92 节点/701 交互由 8 个起草 agent + 9 个实现 agent 并行完成,跨模块跳转 ID 零错配(靠 spec-contract.md 的 ID 注册表)。失败发生在**没有契约覆盖的语义层**。

## 2. 故障机理:卡死是怎么发生的

三个技术触发器,叠加成用户看到的「陷入页面无法退出」:

**T1 — `go()` 硬抛异常(实现层,L0 生成)**
`apps/Douban/navigation.ts` 原实现:transition 的 `from` 约束与当前 URL 不匹配时直接 `throw`。
凡是把 ‹ 返回键绑到声明式 transition 的页面,只要进入路径稍有出入(如 URL 带了 `?drawer=open`、`?sort=` 等参数,或从未声明的入口进入),点返回=抛异常=按钮死掉,**没有任何出口**。

**T2 — 返回被建模成「前进 push」(spec 层 + 生成层)**
即使 `from` 匹配、不抛异常,`退出答题 → group.detail` 这类"返回"是以 `mode:push` **压入新历史**实现的:
栈变成 `…小组详情 → 答题页 → 小组详情(新)`,越退栈越深;抽屉同理(`?drawer=open` 是一条历史记录,
从订单页返回会先弹回"开着抽屉的主页",用户预期是干净主页)——即 gate4 反馈 #2。

**T3 — 全屏遮罩盖住返回键(个别页面 UI 层)**
支付结果页的验证浮层/失败弹窗是 `absolute inset-0 z-50`,恰好盖住顶栏 ‹;且该页顶栏原本就没放返回键
(spec 的 market.payResult 节点也未声明任何返回途径)。支付流一旦停在中间态,唯一出口被物理遮挡。

## 3. 逐案取证(spec 原文 → 各层行为 → 现象)

### 3.1 五个被建模成 nav 的「返回类」交互(假设②的实锤)

冻结 spec(v1.0.0)共有 **27 个**元素名含「返回/关闭/取消/退出」的交互,其中 22 个正确地建模为
`effect:state`(关弹层/取消勾选等,无恙),**5 个错误地建模为 `effect:nav`**:

| spec 节点 | 元素 | spec 声明 | 证据来源 | 起草模块 | 走查现象 |
|---|---|---|---|---|---|
| group.joinQuiz | 「退出答题」 | nav → group.detail (P0) | frame:1779a1@t0035 | 模块5(小组) | **gate4 反馈 #5**:「跳转的对象是错的」 |
| group.joinQuiz | 「取消」(未通过态) | nav → group.detail (P0) | frame:1779a1@t0042 | 模块5(小组) | 同上 |
| celebrity.all | 左上X关闭 | nav → subject.movie (P2) | frame:f60ef9@t0014 | 模块2(搜索+电影) | 从图书进入影人页时,关闭会跳错目标 |
| subject.intro | 返回按钮 | nav → subject.movie (P2) | **inferred:标准返回,按导航惯例** | 模块2 | 同类 |
| doulist.create | 「取消」 | nav → collect.mine (P1) | IMG_0242 | 模块6(我的) | 同类 |

注意第 4 条:起草 agent 自己都写了 *「inferred:标准返回,按导航惯例」*——它明知这是返回,却按契约
只有 nav/state 两种建模选择,只能选 nav。**契约没有给"返回"留位置,是建模错误的直接诱因。**

有趣的细节:反馈 #5 里 spec 的**语义目标其实是对的**(退出答题确实该回小组详情页)。错的是**实现机制**
(push 前进 vs pop 回栈)——这正说明:错误类别是「栈语义缺失」,不是「目标写错」。

### 3.2 多 agent 建模分歧:同一类按钮,三种写法(协作放大器的实锤)

8 个并行起草 agent 对「返回键怎么写」给出了**三种互不相同**的答案:

| 模块 | 返回键写法 | 下场 |
|---|---|---|
| 模块8(设置) | `effect:nav, target:"back"`(伪目标),并在交付报告里**主动请示**:"如全局契约另有 back 约定请批量替换" | merge_spec.py 认得这个变体(`BACK_TARGETS={"back","_back","__back__"}`),**静默剥除 17 条** |
| 模块3(图书音乐) | sheet 关闭用伪目标 `_back`,报告里也标注了"taobao spec 无先例,合并时可统一" | 同上被剥除 |
| 模块2/5/6 | 写**具体父页面**作为 nav 目标(上表 5 条) | **merge 认不出来,静默放行** → 进入冻结 spec → 生成器忠实产出 transition → 实现忠实绑定 |

即:**两个 agent 发现了契约空白并请示,merge 层只处理了它认识的变体、对另一变体无感知也无告警**。
这是典型的"多 agent 各自合理、合并层缺乏归一化校验"的协作失败模式。

### 3.3 抽屉返回错误(假设③-a:spec 没有栈语义字段)

spec 的交互模型只有 `effect/target/gesture/source/priority`——**没有任何字段表达 push/replace**。
生成器 `scaffold_l0.py` 只能用启发式:`mode = "replace" if to == "/" else "push"`(第 239 行),
抽屉分支当时写死 push。结果:抽屉→订单是 push,返回先回到 `/?drawer=open`。
**spec 没错也没漏这条跳转——是 spec 的 schema 本身表达不了这件事,决策落到了生成器的默认值上。**

### 3.4 支付页卡死(假设③-c + 独立的数据流缺口)

- spec 的 `market.payResult` 节点未声明任何返回途径(支付页通常"该不该能返回"确实是产品决策,但 spec 沉默 = 实现层自由发挥,实现层顶栏放了两个空占位);
- 遮罩组件 `z-50 inset-0` 盖住顶栏(T3);
- 另有一个纯实现缺口:`submitOrder` 只结算购物车勾选项,「立即购买」直购时购物车为空 → **不生成订单、支付状态停在 idle** → 页面显示误导文案且无出口。这一条属于实现层数据流 bug(与导航无关,但同属"卡死"家族)。

## 4. 为什么四道机器 gate + 人工审核都没拦住

| 防线 | 为什么漏 |
|---|---|
| **4.1 spec 校验(merge_spec.py)** | 只校验 P0 证据档位、target 是否在注册表内。「返回建模成 nav」的 target(group.detail 等)完全合法,校验器无从判断"这其实是个返回键" |
| **4.2 导航 gate(build_nav)** | 只数「声明的 ID 是否都被绑定、绑定的是否都声明过」。它不但没拦,反而**反向施压**:实现 agent 的指令是"必须保留桩页全部绑定(291/291)",谁把返回键改成 bindBack 谁就让 gate 掉数。**覆盖率 gate 把错误锁死了** |
| **4.3 平台合同(AGENTS.md:156)** | 明文规定"返回/关闭必须 bindBack",但它排在实现 agent 提示词里"保留全部绑定 + gate 必须绿"之后。指令优先级冲突时,agent 选择了服从可被机器验证的那条 |
| **4.4 Gate2 人工审核页** | 白话句式为 `点击【退出答题】→ 进入「group.detail」页`。**对操作者来说这句话语义完全正确**(退出确实回小组页)。push/pop 的栈语义在白话层不可见,操作者不可能勾"错"。这不是审核失误,是审核页的表达力边界 |
| **4.5 运行时走查(pipeline §5.2 的第五道 gate)** | **豆瓣项目没有建**(taobao/flomo 有 runtime_walkthrough.py)。而"死循环返回/卡死页面"恰恰是静态分析原理上不可见、运行时走查一抓一个准的类别。这是流程上最实质的缺口 |

## 5. 各层责任判定

| 层 | 判定 | 依据 |
|---|---|---|
| spec 起草(8 agents) | **有错(5条),但情有可原** | 契约没规定返回怎么建模;两个模块主动请示了 |
| spec-contract.md(我写的契约) | **主责之一** | 只规定了 nav/state 两类和 ID 规则,没规定「返回/关闭不得建模为 nav」、没有栈语义约定 |
| merge_spec.py | **主责之一** | 对一种 back 变体静默剥除、对另一种静默放行,两边都无告警 |
| Gate2 人工审核 | 无责 | 表达力边界内已尽责(你勾"对"是合理的) |
| scaffold_l0.py 生成器 | 次责 | push 默认启发式合理,但对抽屉场景猜错;对 back 型 transition 无识别能力 |
| 9 个实现 agent | **无责** | 忠实实现 + gate 全绿;个别页(payResult 顶栏无返回、submitOrder 直购)属实现缺口但源于 spec 沉默 |
| gate 体系 | **主责之一** | 覆盖率导向,无栈语义检查,无运行时走查 |

## 6. 已实施的临时止血(均已逐一汇报,未动架构)

1. `navigation.ts` `go()`:from 不匹配从 throw 改为 console.warn + 继续(防陷底线);
2. 上述 5 个返回键在**页面侧**改绑 `bindBack()`(声明里的 5 条 transition 未删,现为 unusedInCode WARN);
3. `scaffold_l0.py` 抽屉分支 push→replace 并重新生成声明(gate4 反馈 #2 已验证修复);
4. 支付结果页重写为无遮罩内联三态 + 常驻返回键;`submitOrder` 直购兜底。

## 7. 解决方案提案(供讨论,均未实施)

**A. 契约/Schema 层(治本)**
- spec 交互模型新增第三类效果:`effect:"back"`(或约定:返回/关闭类一律**不进 interactions**,只写进 regions);
- 为浮层/抽屉/tab 类交互增加可选字段 `stack: push|replace`(spec 表达栈语义,生成器不再猜);
- spec-contract 明文:元素名匹配 `返回|关闭|取消|退出|×` 且 effect:nav 的条目为**建模违规**。

**B. 合并层(机器强制)**
- merge_spec.py 增加 lint:命中上述模式 → **报错拒绝合并**(而非静默剥除/放行);对未知 back 变体同样报错。

**C. 生成层**
- scaffold_l0.py:识别 back 类交互 → 桩页产出 `bindBack()` 而非 transition;声明里不再生成这 5 类边(顺带清掉现在的 5 条 unused WARN)。

**D. gate 层**
- 新增静态 lint(类比 lint_binding_override):禁止 `bindTap('*-back'|'*-close'|'*Cancel-*')` 模式;
- **补建 `apps/Douban/assets/runtime_walkthrough.py`**(移植 taobao 版),新增一条**返回可达性断言**:任意页面连按 system.back ≤N 次必须回到某个 tab 根,且 URL 序列无环——把"卡死页面"这一整类变成自动回归。这是收益最大的一条。

**E. 协作流程层(多 agent 专项)**
- 契约必须覆盖"跨模块必然遇到的建模选择"(返回/弹层关闭/栈语义),起草前用 1 个试点模块跑通归一化再放并行;
- 实现 agent 提示词中明确优先级:**平台合同 > 覆盖率 gate**,并给出出口:"绑定与平台合同冲突时改为 bindBack 并在报告中列明"(等价于把这次的人工善后前置为规则)。

**F. spec-first 收口(修复路径建议)**
讨论定稿后一次性做:spec.json 升 v1.1.0(删 5 条 back-nav 交互、补 `search.results.genreTag` 动作——目前声明 410 vs spec 409 存在漂移)→ 重跑 merge/scaffold → gate 回归 0 WARN。
