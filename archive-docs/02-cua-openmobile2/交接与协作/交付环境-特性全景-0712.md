## 术语区(不熟悉这几个词的话,先看这里)

本文档反复出现 5 个 GUI-agent RL 圈的词。先各展开一段并**贴真实产物长相**,后面正文就不再展开。

### 术语 1:`__SIM__.getState()` / 结构化状态

**它是什么**:一个挂在浏览器 `window` 上的全局函数。任何时候调用,它会**把当前模拟环境里所有东西打包成一个大 JSON 对象**返回给你——不是截图,不是 DOM 树,是**内存里 zustand store 的直接序列化**。

**先解释三个词**:
- **DOM tree**(浏览器"网页结构树"):**呈现层**。描述"屏幕上显示了什么、按钮在哪、有没有那个红色小点"。友军(Playwright / a11y tree)读的是这个。**问题**:同样的数据可以有很多种 DOM 表现——一笔账单在列表里显示、在图表里显示、在详情页显示都不一样。判"这笔账单被标为报销"要跟着页面结构变,页面一改判定就崩。
- **zustand store**(我们用的状态管理库):**数据层**。JS 内存里一个 plain object,记着"业务真相"——`bills[b3].reimburse = true`。**不管**它在页面上怎么显示,数据是这一份。读 store 判"账单被标为报销"跟 UI 长啥样无关。
- **"内存"**:浏览器进程的 RAM。zustand store 是一个普通 JS 对象,活在浏览器 tab 的 JS 运行时里。关掉 tab 它就没了——所以有 `persist` middleware 把它序列化到 localStorage。**这是我们自己写的代码,不是浏览器给的东西,完全可控**。

**这个 JSON 顶层结构**:代码见 `os/simState.ts:256-293` `buildSimState()`:

```js
{
  os: {
    tasks: [...],           // Task Manager 栈里所有 activity
    activeTaskId: 'kapi',
    isLauncherVisible: false,
    runningApps: [...],
    locale: 'zh-Hans',
    time: 1720778400000,
    clipboard: { hasContent: true, type: 'text' },
    notifications: [...],
    launcher: { ... },
    settings: { global: {...}, system: {...}, secure: {...} },
    hardware: { battery: {...}, wifi: {...} },
    permissions: { ... },
    providers: { 'media': [...], 'sms': [...], 'contacts': [...] },
    fileSystem: { ... }
  },
  apps: {
    kapi:    { ... },      // 24 个 app 每个一份
    alipay:  { ... },
    ...
  }
}
```

**真实内容长什么样(细到什么程度)**:F12 敲 `__SIM__.getState().apps.kapi` 大概返回:

```js
{
  bills: [
    { id: 'b1', amount: 35.5, category: 'food',    note: '早餐',    time: 1720778400000, reimburse: false },
    { id: 'b2', amount: 120,  category: 'transport', note: '地铁月票', time: 1720778500000, reimburse: true  },
    { id: 'b3', amount: 88.8, category: 'shopping', note: '',       time: 1720778600000, reimburse: false },
    ... (共 25 笔账单)
  ],
  categories: [
    { id: 'food',      name: '餐饮', icon: 'IcMeal', color: '#FF7D00' },
    { id: 'transport', name: '交通', icon: 'IcBus',  color: '#3F80FF' },
    ...
  ],
  _activeBillId: 'b3',       // 当前详情页正在看哪一条
  monthlyBudget: 5000,
  ...
}
```

**细到什么程度**:每一笔账单的每一个字段(金额、分类、备注、时间戳、是否报销)都能拿到。**不是"看得见的东西",是 store 里所有东西**——包括页面上没显示的字段(比如某个账单的内部 flag、当前详情页正在看哪一条 `_activeBillId`)。

**能完成什么任务的判定**:任何"这个 app 内部数据变化了没"的问题都能答:
- "agent 有没有真的把 b3 标为报销?" → 读 `bills[b3].reimburse`
- "agent 有没有创建新账单?" → `bills.length` 变了没
- "agent 加的账单金额对不对?" → 找新账单看它的 amount
- "agent 有没有顺手改坏别的账单?" → 遍历所有 bill 比 before/after

**读不到什么**:
- 屏幕上的像素(要用截图)
- 动画中间态
- 用户输入到一半还没提交的字段(store 里只有"提交后的态")
- 有些字段设计时没进 store(比如只在 React state 里的 toast 显示状态)—— **这属于 app 复刻规范要约束的**,AGENTS.md 已有类似规定"所有 discrete UI 状态变化必须走 store"

**为什么这个东西是护城河**:友军环境(AndroidWorld / OSWorld / WebArena)想读到"用户当前收藏了哪些商品",要么 adb 抠 SQLite,要么 pyautogui 打开文件读,要么截图 OCR。**我们一行 `getState().apps.kapi.bills.filter(b => b.reimburse).length` 就出答案**——纯函数,ms 级,零假阳性。

**对训练/评测意味着什么**:训练时给 agent 的 reward,评测时判 agent 有没有完成任务,**都可以直接读这个 JSON 的字段做 `===` 比较**。不用截图 OCR,不用 accessibility tree 反推。

### 术语 2:可验证判定 / Verifiable Reward / RLVR

**它是什么**:一个纯函数 `checkSuccess(state_before, state_after, params) → true/false`,只读 getState() 出来的 JSON,不看截图不看动作序列,回答"agent 做完这次操作后,任务算不算完成"。

**具体长什么样(卡皮 W3 报销开关任务)**:参考 `apps/Kapi/assets/runtime_walkthrough.py:63-71`:

```python
# 任务:把某笔账单标记为"已报销"
# 判定:操作前 vs 操作后,reimburse=true 的账单数应该 +1

r0 = await page.evaluate(
    "window.__SIM__.getState().apps.kapi.bills.filter(b => b.reimburse).length"
)
await page.locator('[data-action="billDetail.reimburse.toggle.flag"]').click()
await page.wait_for_timeout(400)
r1 = await page.evaluate(
    "window.__SIM__.getState().apps.kapi.bills.filter(b => b.reimburse).length"
)

# 这一行就是 reward:True 表示任务完成
passed = (r1 == r0 + 1)
```

**为什么叫"可验证"**:因为判定完全由 state 变化决定,不由"agent 说自己完成了"或"截图看起来完成了"决定。**agent 骗不了这个 judge——它没法伪造 store 里的数字**。

**为什么叫"reward"**:训 RL 时,这个 `passed` 直接就是那一步的 reward=1(否则 =0)。评测时,这个 `passed` 就是"pass 率"里那个 pass。**同一段判定代码,训练和评测共用**。

**回归测试 vs Verifiable Reward**:同事写 Kapi/Taobao 的 runtime_walkthrough 时,目的是"验证 app 复刻得对不对"——防空回调、防绑错。**这是"回归测试"视角**。但同一段代码换个包装(把 task template 加上、把 pass/fail 变成 reward=1/0)**就是 RL judge**。写的时候没考虑训练用途,但代码天然可用。

**"可验证"的字段是谁定的?**:**我们自己**。每个 app 的 `apps/<AppName>/state.ts` 里 store 的字段结构就是可读的字段——字段名/含义/类型都是复刻 app 的同事写 app 时定的。所以"可验证判定"依赖的两件事都由我们自己控制:①字段存在(app 复刻时写进 store)②判定代码存在(有人写 walkthrough)。

**有没有业界统一的 judge schema?**:**没有硬性统一,但社区有共识范式**。文献 §三.① 概括的是 AndroidWorld/OSWorld/AppWorld 的做法——每个任务配 `{getter, assert, compareFields}` 三元组:
- **getter**:一行 lambda 说"从 state 的哪里读值",比如 `s => s.apps.kapi.bills.filter(b => b.reimburse).length`
- **assert**:比较规则,比如 `equals` / `greater_than` / `set_equal` / `contains`
- **compareFields**:只有这些字段变化算数,其他忽略(反 hacking 会用)

**我们要不要采用这个范式**:**待决策**——如果我们做 benchmark(定义任务集给别人跑)就要,如果我们只做"数据合成环境"(给别人做 env,任务由用户自己合成)就不必强求。见文档末尾"决策项"。

### 术语 3:静态 lint(空回调 / toast-only)

**它是什么**:不跑代码,直接**用文本搜索或 AST 分析扫源码**,找出违反规则的死代码模式。"lint" 就是代码检查的意思,static = 不用跑起来。

**要抓什么**:handbook 里明确的三选一原则:*"看着能点的就必须能点:真能用 / 从画面里去掉 / 点了提示'该功能暂未开放'"*。**"点了什么都不发生"就是三选一里最糟的第 3 种,应该抓到并要求改成合规的**——要么把功能做了,要么把这个入口从画面去掉,要么弹"暂未开放"。

**要抓的具体形态**:卡皮 0710 走查里 3 条 finding 都是这个坑:
- **finding #20**:统计页 `StatsPage.tsx:153`,"支出/收入/结余"看着是 3 个可切 tab,但 `onChange={() => undefined}` 空回调
- **finding #12**:分类详情页 `CategoryDetailPage.tsx:37`,"上一月/下一月"按钮 `onClick={() => toast('上一月')}`,只弹 toast 不改 state
- **finding #15**:同一文件其他 tab 也有类似 toast-only 问题

**用 grep 一行就能抓**:

```bash
grep -rnE "onClick=\{\(\)\s*=>\s*undefined\}" apps/<AppName>/
grep -rnE "onClick=\{[^}]*toast\(['\"][^'\"]*['\"]\)[^}]*\}" apps/<AppName>/
```

**为什么这个 lint 值得做**:卡皮 22 条有效 finding 里,这一类占 3 条(#12/#15/#20)—— **零假阳性**(不会误报,语法特征就是这两个模式),**零成本**(50 行 python 就能写),**能救人力**(不用人肉走查这 3 条)。

**"零假阳性"的意思**:lint 报告"这里有问题",100% 真的是问题。**不像视觉 diff 或 LLM judge 会误报**——那两种一报警,还要人再看一遍,反而更累。就算你想留一个"占位空按钮",按 handbook 规矩也该改成"点了提示暂未开放",不该留空回调。

### 术语 4:确定性 RNG / 可复现

**背景问题**:训 RL 时,每次 `env.reset()` 应该回到"完全一样"的初始状态,不然模型没法学。学术论文更是要求"给我这个 seed,你能跑出和我一样的结果"——这叫**可复现**。

**"确定性 RNG" 是什么**:一个可以设种子(seed)的伪随机数生成器。给它同样的 seed,它每次生成的随机数序列**完全一样**。反面是 `Math.random()`——Chrome 浏览器的实现,你控制不了它下次给你什么数,**没法复现**。

**我们的现状**:代码里到处都在用 `Math.random()`,一些"用户 ID"、"命名空间 token"、"临时随机名"都是它生成的。举个具体例子——`os/storageIsolation.ts:117`(之前是这样,已改):

```typescript
// 改之前:每次 tab 打开,分配一个不可预测的命名空间
function genNamespace() {
  return `mg:ns_${Date.now()}_${Math.random().toString(36).slice(2, 10)}:`;
  //     ↑ 这里的 Math.random 每次都不一样,导致同一个 seed 下
  //     ↑ 两次运行的 localStorage key 不一样,state 就不一致
}

// 改之后:用可 seed 的 RandomService
import { randomToken } from './RandomService';
function genNamespace() {
  return `mg:ns_${TimeService.now()}_${randomToken(8)}:`;
  //                                    ↑ 同 seed 下生成同 token
}
```

**"日常使用感觉不到,只影响 RL 复现"**:你手动开 app 点来点去、跑走查、看数据,**完全感觉不到差别**。RandomService 目前只影响 tab 命名空间字符,肉眼看不出。**真正的影响在 RL 训练时**——一个训练脚本同 seed 跑两次,现在(还没改的话)两次的 namespace 字符不一样,同一动作下 state 快照不完全一致。改成 seedable 后,同 seed 下同一初始 state,论文可复现。

**"分配一个不可预测的命名空间"是什么意思**:storageIsolation 给多 tab 隔离数据用的。每个 tab 打开时,给这个 tab 分一个前缀名字(namespace),比如 `mg:ns_1720778400_a7k3p9x2:`。所有 localStorage 的 key 都加这个前缀,不同 tab 名字不同数据就不串。**"不可预测"**指:前缀里含 `Math.random()` 的部分,浏览器每次给的随机字符不一样,你没法预测。改成 seedable RNG 后,同一 seed 下这个前缀是确定的。

**"seed 具体怎么作用"**:
- 训练脚本每次 `env.reset(seed=42)` 会调 `__SIM_RNG__.seed(42)`
- 之后所有代码调 `__SIM_RNG__.random()`,**同 seed 下必然产生完全相同的序列**
- 结果:同 seed 下同一初始 namespace / 同一初始 id / 同一初始洗牌顺序 / 同一模拟点赞数 → agent 走同样步骤就得到同样 state,论文可复现

**关于协作**:R7 骨架已建,但**不用现在通知 8 个同学中断去改**——他们现在没在跑 RL,改 92 处 Math.random 是打断节奏。建议做法:
- **现在**:AGENTS.md / pipeline-v3 加"新代码禁 Math.random,用 __SIM_RNG__.random",只约束新代码
- **事后**:接 RL 前一个人集中扫替换,3-5 人天

### 术语 5:稠密奖励 / dense reward / milestone

**背景问题**:训 RL 时,如果一个任务要 20 步才能完成,而你只在最后一步给 reward=1、其他 19 步都是 0,模型基本学不到东西——**稀疏奖励(sparse reward)**。就像教小孩学骑车,只在他骑到终点时说"好棒",中间摔倒不指导,他一辈子学不会。

**稠密奖励是什么**:把长任务拆成若干**里程碑(milestone / checklist)**,每达成一个中间目标就给一点 reward。举例:

**任务**:在微信里给朋友转账 100 元
- **稀疏奖励**(现状):最后转账成功了 → reward=1;失败或超时 → reward=0
- **稠密奖励**(要做的):
  - milestone 1:进入了聊天列表页 → +0.1
  - milestone 2:选中了目标好友 → +0.2
  - milestone 3:打开了转账页面 → +0.3
  - milestone 4:输入金额=100 → +0.2
  - milestone 5:点了确认,余额减 100 → +0.2

**我们的现状**:`bench_env` 只在 episode 结束时调 `task.evaluate()` 出 pass/fail(见 `bench_env/env/base.py:313-350`),**中间步骤没有 reward shaping 的接口**。要加也不难——task schema 加一个 `milestones` 字段:

```python
class TransferMoney(CriteriaTask):
    templates = ["给张三转账 100 元"]
    apps = ["wechat"]
    milestones = [
        {"state_predicate": "route == '/chat/zhangsan'", "reward": 0.1},
        {"state_predicate": "route == '/transfer'",       "reward": 0.3},
        {"state_predicate": "state.transferAmount == 100", "reward": 0.2},
        # 最后一条隐含 = 任务成功
    ]
```

每 step 判定器把每条 milestone 判一遍,累加发给 agent。

**为什么这条重要**:文献 §二.2 引用了 2 篇论文说明"长任务需要 milestone"。我们现在 bench_env 的所有 task 都是稀疏奖励,直接接 RL 训练框架跑,agent 很难学到长链任务。

### 术语 6:gym 语义 / gym.Env

**它是什么**:OpenAI 在 2016 年定的一套 RL 环境接口标准,后来被 Gymnasium(gym 的社区继承者,Farama Foundation 维护)接手成为**事实标准**。所有主流 RL 训练框架(verl、OpenRLHF、RLLib、Stable-Baselines3)都默认环境实现这个接口:

```python
class Env:
    def reset(self, seed=None) -> (obs, info):     # 开始新一轮
        ...
    def step(self, action) -> (obs, reward, terminated, truncated, info):
        # 走一步。返回:
        #   obs         下一步观察
        #   reward      标量数字(这一步得多少分)
        #   terminated  bool,任务是否结束(成功或失败)
        #   truncated   bool,是否被外部强行截断(超时)
        #   info        附加信息 dict
        ...
    def close(self) -> None:
        ...
```

接口定义官方文档:https://gymnasium.farama.org/api/env/

**我们的现状**:见 `bench_env/env/base.py:313-350`:

```python
class BaseMobileEnv(ABC):
    async def reset(self) -> None: ...                     # 缺 seed 参数,返回 None 不是 (obs, info)
    async def step(self, action) -> StepResult: ...        # StepResult = (obs, done, info),缺 reward + terminated/truncated
    async def close(self) -> None: ...
```

差在 3 点:

1. **step 返回值不是 gym 五元组**,缺标量 `reward`,`done` 也没有拆成 `terminated` / `truncated`
2. **reset 没有 seed 参数**,拿到不能复现(和术语 4 关联)
3. **接口是 async 的**——"同步"= Python 里普通 def,你可以直接 `for i in range(N): env.step(a)`;"异步"= async def,要写 `await env.step(a)` 而且需要 event loop 环境。RL 框架大多数是同步的,直接用 async 会报错

**"reward 为什么要从 task.evaluate 里拿出来"**:
- 现在 `bench_env` 只在 episode 结束时调一次 `task.evaluate()` 出 pass/fail
- gym 的 step 每步都要返回 reward——**不是我们没有 reward,只是没暴露在每步返回里**
- 改起来是"每步调一下 evaluate 出中间值"(值可以是 0,可以是中间 milestone,可以是最后的 1)。这是接口形式要求,不是我们缺功能

**"包装容易吗"**:是的,约 100 行 Python 的 wrapper。gym 官方文档有模板照做,**1 人天完成**,没夸张。

**"接口是不是我们要提供的"**:是的。用户 `pip install verl` 后期待环境是 gym.Env 子类。**我们不做,他自己写 wrapper**——大部分人不会写,会直接放弃我们。**做了对手**——`verl.train(env=MobileGymEnv())` 一行搞定。

**关于我们不是 benchmark 也不定义任务这一点**:**gym wrapper 和"是否做 benchmark"无关**——只要外部人想用我们的环境跑 RL(不管任务怎么来),就要 gym 接口。**这条建议上会问一下**:"我们是否需要外部人用 mobilegym 跑 RL 训练?如需要,gym wrapper 必做;如不需要(比如只我们内部用来生成轨迹),wrapper 可缓做"。

### 9. 多套种子/多场景数据切换 ❌ 【重要,以下展开】

**问题背景**:一个 app 现在只有一份 `data/defaults.json`。跑训练时**所有环境实例初始 state 都一样**——都是这份 defaults 生成的初始态。

**为什么这是个大问题**——训练用同一个初始态,agent 只学到"这一种情况"怎么处理。真实用户面对的场景千差万别,agent 不会泛化。举例训"标为报销"这个任务时,你会希望有几种不同初始态:

- **场景 A(空)**:bills 里 0 笔账单——测 agent 会不会报"没账单可标"而不是崩
- **场景 B(常规)**:bills 里 20 笔账单——正常情况
- **场景 C(边界)**:bills 里 1000 笔账单——测长列表滚动能不能找到目标
- **场景 D(冲突)**:bills 里有一笔已经标了报销——测 agent 会不会去误改这条

现在**只有一个 defaults.json 就只能训场景 B**,agent 遇到 A/C/D 都可能出问题。

**三个选项分别是什么**:

**选项 ①:defaults 拆多文件 + URL 参数选**
- 做法:每 app 建 `data/defaults.empty.json` / `data/defaults.normal.json` / `data/defaults.thousand.json`,URL 里带 `?scenario=empty` 决定加载哪个
- 优点:改动最小,前端就能实现
- 缺点:场景写死在 app 里,加场景要动 app 代码;每个场景是完整一份 defaults,冗余
- 影响造 app 同学:要,他们每个人给自己的 app 写多份 defaults

**选项 ②:bench_env pre-inject store snapshot**
- 做法:训练 Python 端持有多个场景的 state JSON,`reset(scenario='empty')` 时把 JSON 通过 `page.evaluate` 直接注入 store,覆盖默认加载
- 优点:app 层完全不改;可以任意组合出新场景;可以由脚本自动生成场景
- 缺点:要在 bench_env 加 inject 接口;要保证注入的 state 和 app store 结构匹配(app store 结构变了要同步)
- 影响造 app 同学:不影响,他们不用管

**选项 ③:fixtures 目录 + task 声明依赖**
- 做法:建 `bench_env/fixtures/kapi/`,里面放各种 state snapshot;每个 task 声明"我需要 fixture=kapi.thousand_bills",task 启动时加载
- 优点:最规整,fixture 可以跨 task 复用;有集中管理
- 缺点:要建 fixture 管理系统;fixture 数量爆炸后要有版本管理
- 影响造 app 同学:不影响,但要有人专职维护 fixtures

**建议**:**先选 ②**——影响造 app 同学最小,又能覆盖多场景需求;规范化后再往 ③ 演进。

**要做什么**:
- bench_env 加一个 `inject_state(scenario_dict)` 接口
- 决定 scenario 存哪(json 文件 / 代码里 dict / 自动生成脚本)
- 加 3-5 个示范 scenario(空 / 常规 / 边界)在 1-2 个 app 上跑通
- 影响造 app 同学:0

**代价**:2-3 人天(选 ② 的话)

### 25. 反 reward hacking(include+exclude 双向) ❌

**先解释 "reward hacking" 是什么**:agent 学会"用不合规的方式骗到高 reward"。经典例子:训一个赛船 agent,reward = 沿途捡到金币的数量。结果 agent 学会**在小圈里转,反复捡同一个刷新的金币**,再也不去终点了——技术上 reward 拉满,但显然不是我们想要的行为。这就叫 reward hacking。

**GUI-agent 圈的具体表现**:文献 §二.2 举了 GUI-G1 的例子——判定用的是"agent 点的位置是否在目标 button 的 bounding box 里",于是模型学会**输出一个巨大的 bounding box**(比如覆盖整个屏幕),这样"点在里面"永远为真,pass 率飙到 100%。

**为什么我们容易被这么钻空子**:我们的 judge 现在都是"某个 state 字段变成了某个预期值"这种**包含式判定**。举例:任务"把账单标为报销",判定 `bills.filter(b => b.reimburse).length > 0`——**只要有任何一笔被标为 reimburse 就过**。agent 学会"把所有账单都标为 reimburse",技术上判定为真,任务算完成,但显然作弊了。

**"include + exclude 双向约束" 是什么**:就是把 judge 从"必须命中什么"扩成"必须命中什么 **AND** 必须不能命中什么"。用上面的账单例子:

```python
# 错(现在的写法)—— 容易被 hacking
def judge_include_only(state_before, state_after, params):
    target_id = params['bill_id']
    return state_after.apps.kapi.bills[target_id].reimburse == True
    # 问题:agent 把 100 笔账单全标为 reimburse,这个 judge 也返回 True

# 对(要做的写法)—— 双向约束
def judge_include_exclude(state_before, state_after, params):
    target_id = params['bill_id']

    # include:目标账单必须变成 reimburse=True
    if state_after.apps.kapi.bills[target_id].reimburse != True:
        return False

    # exclude:其他账单的 reimburse 状态必须保持不变
    for bid, bill_before in state_before.apps.kapi.bills.items():
        if bid == target_id: continue
        if state_after.apps.kapi.bills[bid].reimburse != bill_before.reimburse:
            return False   # 有别的账单被顺手改了,判失败

    return True
```

**为什么这条对我们特别重要**:友军(AndroidWorld/OSWorld)想做 exclude 断言也很难——他们连一个字段是不是被改了都得从 SQLite/文件里抠。**我们能读全量 state,做 exclude 断言就是加几行代码的事**。这是护城河的"深度用法"。

**现状**:我们完全没考虑。Kapi/Taobao 的 walkthrough 里全是 include 式断言,没有一条 exclude。**下一步铺 19 app walkthrough 时,应该从第一条就带 exclude**,不然铺完还要回头改一遍。

**建议动作**:新增立项 R10 · Judge 防作弊范式。产出一份"exclude 断言写作规范",约束新 walkthrough 必须至少写 1 条 exclude。

### 26. 跨 app collateral-damage 反向断言 ❌ 【你觉得有意思,以下展开】

**"collateral damage" 字面意思**:军事术语"附带损伤"。用在这里指:agent 做完某个跨 app 操作后,除了目标 app 的状态变了,**其他 app 有没有被顺手破坏**。

**为什么"我影响一个 app 会伤到另一个"——具体场景**:

任务:"用微信支付淘宝订单 99.9 元"。agent 应该做的:
1. 淘宝里点结算 → 拉起微信支付 → 输密码 → 完成
2. 结果:淘宝订单变 paid,微信余额减 99.9

**agent 可能做出的错事(judge 只看目标 app 就抓不到)**:

- **错误 A · 支付了但用错了 app**:agent 走错流程,支付了 99.9 但是**通过支付宝**(不是微信)——淘宝订单状态对了(paid),但微信余额没动,支付宝余额动了。**judge 只看"淘宝订单=paid"会误判成功**
- **错误 B · 顺手结算了别的**:agent 除了买目标商品,顺手把购物车里另外 3 件也结算了——目标订单 paid,但**购物车里另外 3 件也 paid,微信被扣了 500**。judge 只看目标订单会误判成功
- **错误 C · 触发副作用**:agent 支付时不小心触发了"分享给好友",微信朋友圈多了一条"我买了 xxx"消息——目标完成了,但**产生了不该有的社交副作用**

**collateral damage 断言就是防这些**:除了检查目标 app 该变的(淘宝订单 paid),还要检查:
- 微信余额确实减了 99.9(不是支付宝) —— 防错误 A
- 购物车里其他订单状态没变 —— 防错误 B
- 微信朋友圈没被顺手发帖 —— 防错误 C

**AppWorld 就是这么做的**(文献 §二.2)——他们是纯 API 环境(9 app / 457 API),任务比如"把 Spotify 的这首歌加到 Apple Music 的收藏"。判定不只看 Apple Music 收藏列表有没有这首歌(include),还要看:
- Spotify 里这首歌的播放次数没被顺手改吗?
- Spotify 里其他歌没被删除吗?
- 联系人 app 里的联系人没被顺手动过吗?

**具体应该写成什么样**:参考下面这个跨 app 判定的模板

```python
class Pay12306WithAlipay(CriteriaTask):
    templates = ["用支付宝付这张 12306 车票的款"]
    apps = ["railway12306", "alipay"]

    def judge(self, state_before, state_after, params):
        order_id = params['order_id']
        price = params['price']

        # ==== include:目标 app 该变的 ====
        # 12306:订单状态变成 paid
        order_before = state_before.apps.railway12306.orders[order_id]
        order_after = state_after.apps.railway12306.orders[order_id]
        if order_after.status != 'paid': return False

        # 支付宝:余额减了正确的钱
        bal_delta = state_before.apps.alipay.balance - state_after.apps.alipay.balance
        if abs(bal_delta - price) > 0.01: return False

        # ==== exclude:其他 app 该保持不变的 ====
        # 12306 其他订单状态不能变(防 B)
        for oid, o_before in state_before.apps.railway12306.orders.items():
            if oid == order_id: continue
            if state_after.apps.railway12306.orders[oid].status != o_before.status:
                return False

        # 微信余额不能动(防 A · 应该只有支付宝减了)
        if state_after.apps.wechat.balance != state_before.apps.wechat.balance:
            return False

        # 微信没有新发朋友圈(防 C)
        if len(state_after.apps.wechat.moments) != len(state_before.apps.wechat.moments):
            return False

        return True
```

**为什么这条对我们意义重大**:友军(AndroidWorld / OSWorld)想做这种跨 app 反向断言基本做不到——他们连一个字段是不是被改了都得从 SQLite/文件里抠。**我们能读全量 state,做 exclude 断言就是加几行代码的事**。这是护城河的深度用法,直接对标 AppWorld(AppWorld 是纯 API,我们是 API + GUI 双模态)。

**做什么 · 现状 · 具体区别 · 需要做什么 · 影响**:
- **做什么**:R3(跨 app)立项卡加"3-5 条 collateral-damage 判定示范"产出
- **现状**:跨 app intent 骨架完(12306→Alipay、B站→微信真跑通),但**judge 一条没写**
- **具体区别**:现在的 judge 只有 include(目标 app 状态对);新增的 judge 有 include + exclude 双向(所有相关 app 状态都要对/都要没被顺手动)
- **需要做什么**:选 3-5 条真实跨 app 任务(比如"12306 支付宝付款"、"B站微信支付会员"),按上面模板写 judge
- **影响造 app 同学**:不影响,judge 在 bench_env 层写,不动 app 代码

### 27. 确定性 RNG 全量铺 ❌ 【RL 圈价值最高】

**看不懂"确定性 RNG"?先回术语区 · 术语 4。**

**"92 处 Math.random 散落 apps/" 具体是什么**:仓库主目录跑一次 `grep -rn "Math.random" apps/ os/` 大概能看到 92 个位置(骨架建好后已改的 storageIsolation 那一处除外)。散落形态大概是这三类:

1. **生成随机 id**(占大头)
   ```typescript
   // 记录新账单 / 新聊天 / 新订单时生成 id
   const newId = `bill_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`;
   ```
2. **随机排序 / 洗牌**
   ```typescript
   const shuffled = list.sort(() => Math.random() - 0.5);
   ```
3. **随机模拟数据**
   ```typescript
   // 模拟视频推荐里的"随机点赞数"
   likes: Math.floor(Math.random() * 10000)
   ```

**这些代码为什么伤可复现**:同一个 seed 下,两次跑同一个任务,理论上应该得到完全一样的 state 轨迹。但只要有一处 `Math.random()`,两次生成的 id / 洗牌顺序 / 点赞数就会不一样,state 就有差异。哪怕 agent 每步动作完全一样,`getState()` 都不一样,后续的判定和训练就出问题。

**修复长什么样**:参考已经改好的 `os/storageIsolation.ts:117`(见术语 4 的代码对比)。批量改就是:
1. 每个 `Math.random()` 换成 `__SIM_RNG__.random()`
2. 每个 `Date.now()`(如果还有漏网的)换成 `TimeService.realNow()` 或 `TimeService.now()`
3. `eslint.config.js` 加一条禁令 `no-restricted-syntax` 禁 `Math.random`(参考现有禁 `Date.now` 那一条)
4. 在 `bench_env` 的 reset 里加 `__SIM_RNG__.seed(seed)`,同 seed 全环境一致

**修复代价**:批量 grep + sed + 手工看几个边界情况,3-5 人天。**没有技术不确定性**——骨架已建、模式已定、一处已改。

**汇报口径**:R7 立项卡状态从"骨架已建" → "分批迁移中,预计 X 周内清零"。**这条对 RL 圈用户是"能不能拿来写论文"的一票否决项**——文献 §二.6 直接点名了。

### 28. gym 语义 step 返回 ❌

**看不懂"gym 语义"?先回术语区 · 术语 6。**

**我们现在 step 返回长什么样**(`bench_env/env/base.py` `StepResult`):

```python
@dataclass(frozen=True)
class StepResult:
    observation: Observation   # 有截图 + state + route + step_idx
    done: bool                 # 任务结束了吗
    info: dict                 # 附加信息
```

**gym 期待的样子**(`gymnasium.Env.step` 签名):

```python
def step(self, action) -> tuple[
    Observation,   # 一样
    float,         # ← 我们缺:标量 reward(比如 0.3、1.0、-0.1)
    bool,          # ← 我们只有 done,gym 拆成:terminated(任务成功/失败)
    bool,          #                        + truncated(被外部截断,比如超时)
    dict           # 一样
]
```

**具体差在 3 处**:
1. **缺标量 reward** —— 我们把 reward 藏在 `task.evaluate()` 里,只在 episode 末算一次。gym 每步都要 reward
2. **done 没拆成 terminated / truncated** —— 训 RL 时这俩含义不同:terminated=真正结束(agent 完成/失败),truncated=时间到了不得不停。gym 库很多算法用这个区分
3. **async 接口** —— 我们的 step 是 `async def`,gym 是同步的。要嵌到 asyncio event loop 里包一层才能给 verl 用

**修复长什么样**:加一个 wrapper,不动 base.py:

```python
# bench_env/env/gym_wrapper.py (新文件, ~100 行)
import asyncio
import gymnasium as gym

class GymMobileEnv(gym.Env):
    def __init__(self, async_env: BaseMobileEnv):
        self._env = async_env
        self._loop = asyncio.new_event_loop()
        self._steps = 0

    def reset(self, *, seed=None, options=None):
        if seed is not None:
            # 通过 page.evaluate 调 __SIM_RNG__.seed(seed)
            self._loop.run_until_complete(self._env.seed(seed))
        self._loop.run_until_complete(self._env.reset())
        obs = self._loop.run_until_complete(self._env.get_observation())
        self._steps = 0
        return obs, {}

    def step(self, action):
        result = self._loop.run_until_complete(self._env.step(action))
        self._steps += 1

        # 从 task judge 里算 reward(可以每步都算,支持 milestone;见特性 30)
        reward = self._env.task.compute_reward(result.observation)

        terminated = result.done                        # 任务本身结束
        truncated = self._steps >= self._env.max_steps  # 超步数被截断

        return result.observation, reward, terminated, truncated, result.info
```

**修复代价**:1 人天(不含 milestone 那部分)。**没有技术风险**,gym 库有官方教程照做。

**建议动作**:新增立项 R9 · RL 训练接口对接,把 gym wrapper 作为第一步产出。

### 29. HTTP env server(POST /reset + /step) ❌

**为什么需要这个**:主流 RL 框架(verl、OpenRLHF)期待环境是**独立进程**,通过 HTTP 调用。原因:
- 训练侧(GPU 上跑模型)和环境侧(CPU 上跑 chromium)一般不在同一台机器,HTTP 是跨机唯一选项
- 一次训练要开几十上百个并行环境,每个是独立进程,不能共享 Python 解释器
- 环境挂了要能被上游发现并重启,进程隔离是必须的

**我们现在不能做到什么**:bench_env 现在是 Python 库,得 `import bench_env`,嵌到 verl 的进程里跑。**跨机不能用,并发受 GIL 限制**。

**修复长什么样**:FastAPI 一层壳,不动 bench_env 内部:

```python
# bench_env/server.py (新文件, ~150 行)
from fastapi import FastAPI
from bench_env.env.mobile_gym import MobileGymEnv

app = FastAPI()
envs = {}  # session_id -> env instance

@app.post("/reset")
async def reset(session_id: str, task_id: str, seed: int = None):
    env = MobileGymEnv(task_id=task_id)
    await env.reset(seed=seed)
    envs[session_id] = env
    obs = await env.get_observation()
    return {"observation": serialize(obs), "info": {}}

@app.post("/step")
async def step(session_id: str, action: dict):
    env = envs[session_id]
    result = await env.step(Action.from_dict(action))
    reward = env.task.compute_reward(result.observation)
    return {
        "observation": serialize(result.observation),
        "reward": reward,
        "terminated": result.done,
        "truncated": env.steps >= env.max_steps,
        "info": result.info
    }

@app.post("/close")
async def close(session_id: str):
    env = envs.pop(session_id, None)
    if env: await env.close()
```

**跨机部署时**:训练机器上跑 `verl.train(env_url='http://cluster-node-12:8000')`,cluster-node-12 上跑 `uvicorn bench_env.server:app` + chromium。verl 内部会 POST /reset 和 /step,拿到 gym 五元组直接训。

**修复代价**:2-3 人天。文献 §六说 "隔离与并行我们已做得最好,补 HTTP 壳即可"——**壳是最容易做的部分**,难的隔离/并行(storageIsolation + MultiProcessRunner)我们已经做完了。

**建议动作**:并入 R9 · RL 训练接口对接。

### 30. milestone / checklist 稠密奖励 ❌

**看不懂"稠密奖励"?先回术语区 · 术语 5。**

**我们现在的判定何时给 reward**:见 `bench_env/task/wechat/tasks.py:51-68`。任务 class 里定义一个 `criteria`,类似:

```python
class OpenRadarAddFriend(CriteriaTask):
    templates = ["打开微信雷达加好友页面", ...]
    apps = ["wechat"]
    criteria = {"route": "/radar"}   # ← 全部判定压缩成"最终 route 是不是 /radar"
    optimal_paths = [[
        "home.menu.plus.open",
        "plusMenu.addFriend.open",
        "addFriend.radar.open",
    ]]
```

**问题**:整条任务只有一个 reward 时机——episode 末查 `route == '/radar'`,是的话 reward=1,否则 0。**中间三步(打开菜单 → 打开加好友 → 打开雷达)如果只走对了两步,一样是 0**。

**milestone 补什么**:让 optimal_paths 里的每一步都可以给一点 reward:

```python
class OpenRadarAddFriend(CriteriaTask):
    templates = ["打开微信雷达加好友页面", ...]
    apps = ["wechat"]
    criteria = {"route": "/radar"}
    milestones = [
        # 每达到一个 milestone 给一次 reward,只发一次
        {"predicate": "route == '/plus-menu'",        "reward": 0.2},
        {"predicate": "route == '/plus/add-friend'",  "reward": 0.3},
        {"predicate": "route == '/radar'",            "reward": 0.5},
    ]
```

**判定器每步做什么**:

```python
def compute_reward(self, obs):
    total = 0.0
    for m in self.milestones:
        if m['id'] in self._hit_milestones: continue  # 已发过,不重发
        if predicate_matches(m['predicate'], obs.state, obs.route):
            self._hit_milestones.add(m['id'])
            total += m['reward']
    return total
```

**为什么长任务需要这个**:文献 §二.2 引用 arxiv 2602.11524 和 2602.12268 两篇论文都说明——20+ 步的任务如果只有 episode 末 0/1 reward,RL 学习效率**下降到几乎不可用**。用 milestone 后,pass 率提升幅度在这些论文里是 10-30%。

**修复代价**:base.py 加 `compute_reward()` 接口,现有 22 个 wechat task 补 milestones 字段,约 5 人天。**但只对长任务(≥5 步)必要**,单页跳转任务不需要。

**建议动作**:并入 R9 · RL 训练接口对接。**优先只给 wechat/alipay/taobao 三个复杂 app 的长任务加 milestone**,单页导航任务不加。

## 补充③ 任务 schema 与轨迹

### 31. 统一任务定义 schema ❓ 【待决策 · 上会问一下】

**先明确定位差异**:这条**是可选优化,不是必做**。取决于我们的定位是什么:

- 如果做**数据合成环境**(给别人做 env,任务由用户自己合成)—— **不必**做统一 schema
- 如果做**benchmark 平台**(定义任务集,给别人来跑,发论文用)—— **必做**

按你的表述"我们并没有定义任务,想用这个环境合成任务",偏前者。所以这条**主要是拿到上会问一下**:是否有做 benchmark 的意图?没有就不做。

**为什么要提这条**:因为 bench_env 里已经有 task 定义机制(是 mobile-gym 上游给的),我们没用它。上会说"这个东西有,我们没用"是负责任的口径,免得别人以为我们不知道有这个。

**Python class vs JSON 具体区别是什么**:

**Python class 现状**(`bench_env/task/wechat/tasks.py:51-68`):

```python
class OpenRadarAddFriend(CriteriaTask):
    templates = ["打开微信雷达加好友页面", "Open the Radar Add Friend page in WeChat"]
    apps = ["wechat"]
    difficulty = "L1"
    criteria = {"route": "/radar"}
    optimal_paths = [["home.menu.plus.open", "plusMenu.addFriend.open", "addFriend.radar.open"]]
```

**JSON 化后长这样**:

```json
{
  "task_id": "wechat.open_radar_add_friend",
  "template": "打开微信{feature_name}页面",
  "instantiation_dict": {
    "feature_name": ["雷达加好友", "面对面建群", "扫一扫"]
  },
  "apps": ["wechat"],
  "difficulty": "L1",
  "eval": { "type": "route_match", "route_template": "/{route_id}" },
  "params_map": {
    "route_id": { "雷达加好友": "radar", "面对面建群": "face-group", "扫一扫": "scan" }
  }
}
```

**关键区别在 `instantiation_dict`**——JSON schema 里可以填 3 个 `feature_name`,**自动生成 3 个变体任务**:
- "打开微信雷达加好友" → 判 `route == '/radar'`
- "打开微信面对面建群" → 判 `route == '/face-group'`
- "打开微信扫一扫" → 判 `route == '/scan'`

参数**既进 instruction 又进 judge**——判定的 route 也随参数变。**这就是"海量变体"的机制**:一个模板,填 N 组参数,生成 N 个可判定的任务实例。

**Python class 也能写变体**,但要写 `for feature in features: yield SomeTask(feature=feature)` 这种代码,**每个变体要人手写代码**,不能声明式描述,而且判定逻辑要跟着 for 循环维护。JSON schema 是**声明式**,参数一填自动出变体。

**做什么 · 现状 · 具体区别 · 需要做什么 · 影响**:
- **做什么**:定义 JSON schema + 写 JSON→Task 实例 loader + 迁移现有 22 个 wechat task
- **现状**:bench_env 用 Python class 定 task,变体要写 for 循环
- **具体区别**(见上)
- **需要做什么**:
  1. 定 schema 规范(必填字段、eval 类型、参数替换语法)
  2. 写 loader(约 200 行 Python)
  3. 现有 wechat 22 task 从 class 迁移到 JSON(每 task 半小时)
- **影响造 app 同学**:不影响,他们不用管
- **影响写 task 的人**:改写作方式,不再写 Python class 改填 JSON

**代价**:5-10 人天(loader 1-2 天 + 22 task 迁移每 app 半天)。

**上会建议问的问题**:"我们要做数据合成环境还是 benchmark 平台?两者接口需求不同,决定我们是否需要 JSON 化 task schema"。

### 32. 静态 lint(空回调 / toast-only) ❌

**看不懂"静态 lint"?先回术语区 · 术语 3。**

**卡皮 0710 走查里三条能被这条 lint 抓到的 finding**:
- **#12**:分类编辑按钮点了没反应 → `CategoryDetailPage.tsx` 的 handler 空实现
- **#15**:分类详情页月份 tab 切不了 → `CategoryDetailPage.tsx:37` `handler = toast('上一月')`
- **#20**:统计页"支出/收入/结余"应该是 tab 但切不了 → `StatsPage.tsx:153` `handler = () => undefined`

**能抓到的 pattern**:

```regex
# pattern 1: 空回调
onClick=\{\(\)\s*=>\s*undefined\}
onChange=\{\(\)\s*=>\s*undefined\}

# pattern 2: 只弹 toast 不改 state 的假回调
onClick=\{[^}]*toast\(['"][^'"]*['"]\)[^}]*\}
onClick=\{\(\)\s*=>\s*message\.(info|success|error)\(

# pattern 3: 单行匿名函数没做任何事(需 AST)
onClick=\{\(\)\s*=>\s*\{[\s]*\}\}
```

**跑起来长这样**:

```bash
$ python scripts/lint_empty_handlers.py apps/Kapi
apps/Kapi/pages/StatsPage.tsx:153: EMPTY_CALLBACK on <Tab label="支出">
apps/Kapi/pages/CategoryDetailPage.tsx:37: TOAST_ONLY on <button "上一月">
apps/Kapi/pages/CategoryDetailPage.tsx:39: TOAST_ONLY on <button "下一月">
apps/Kapi/pages/CategoryDetailPage.tsx:30: TOAST_ONLY on <select "category">

Found 4 empty/toast-only handlers. Fix before requesting Gate4.
```

**为什么"零假阳性"**:上面三个 pattern 抓的都是明确的"点了什么都不发生"的**语法特征**。不像"给这个按钮加个反应"这种含义模糊的东西——语法特征存在,就 100% 是问题。哪怕故意用 `() => undefined`(比如"占位符"),那也是应该修掉的。

**修复代价**:一个 python 或 mjs 脚本,50-100 行,1-2 人天。**用户偏好路线是"AI 自查而非新工具"**——见 `docs/不要上传-修bug/交接-构建流程优化-新窗口用.md`。所以脚本可以有,但接入方式是**AI 在阶段⑤自检时自己跑 grep 一句**,不是通知 8 个同学改流程。

**建议动作**:并入 R1 · 阶段⑤ 自检。
