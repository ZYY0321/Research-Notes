## 三、两个流程性发现（今天最重要的产出，不是某个人代码差）

### 发现 1：push 到分支 ≠ 交付，有人代码写了但根本没开 PR

**起因**：用户问"为啥没合并，我看到有 request 都点 merge 了啊，是他们自己没提交吗？"——直接查证 GitHub 的 PR 记录（不是猜，是把每个 PR 对应的 commit 哈希和内容做了逐一比对）：

- `origin/caojialin`（cjl，唯品会负责人）分支上有一个 **07-30 提交，改了 27 个文件、1481 行新增/646 行删除**（"阶段⑤视觉保真优化+收尾"，覆盖购物车、收藏、首页、我的、地址页等），内容用 `diff` 直接对比过，跟 main 上的版本**完全不同**（比如 `FavoritesPage.tsx`，cjl 版本 312 行、main 上只有 137 行，cjl 版本多出品牌订阅/穿搭收藏 tab、倒计时组件等一整套东西）。
- 查了这个分支所有 PR 记录：`caojialin` 分支一共被合并过 **2 次**（PR #9 在 07-09、PR #16 在 07-16）。**cjl 在 07-16 之后又往同一个分支追加了新提交，但再也没有为这些新提交开过 PR**——直接查了 GitHub 上所有 PR 对应的 commit 哈希，没有任何一个包含这份 07-30 的代码。
- **结论**：不是"开了 PR 没人点合并"，是**根本没有提交评审请求**。前两次合并让人（包括环境侧）以为"这个分支已经处理过了"，之后追加的内容就没人注意到、一直躺着。GitHub 的 PR 机制不会因为你有过一次合并记录就持续追踪你后续的新提交——这一步完全没人盯，除非主动去对比分支内容。

**当时验证走过的弯路（也记一下，避免以后重复犯）**：一开始怀疑 Song-WenPo（拼多多）的分支 `songwp` 也有类似情况（16 个未合并提交，07-18 有一个专门的"拼多多 gate4 第6+7轮走查修复"）。但进一步核实：直接对比内容发现，那次提交新增的 `OrderSnapshotPage.tsx` 文件**已经存在于 main**——原因是 Song-WenPo 后来换到了新分支 `songwp-pdd` 重新提交，那个新分支的 PR #17 在 07-21 已经合并，内容其实进去了，只是 git 祖先关系上看不出来（因为不是同一条分支线）。**这是我一开始的误判，已经纠正**：只看"多少天没提交"或者只看单一分支的祖先关系，都会得出错误结论，唯一可靠的办法是**逐个对比实际文件内容**。

### 发现 2：整个仓库没有任何自动化校验/CI，验收全靠人工走查 + 口头自证

`.github/workflows` 目录不存在，PR 合并没有任何强制门槛。负责人说"已满足"就是"已满足"，没人验证。仓库里其实有 **28 个 App 自带 `runtime_walkthrough.mjs/py`**（真实 puppeteer 点击 + 断言脚本），例如唯品会自己就有——但它没能拦住那个 17 天没修的 P0 返回死循环，说明**脚本存在≠被当门槛用**。

## 六、讨论出的后续安排

1. **不再用"多少天没提交"判断谁在干活**，用"有没有开 PR / PR 有没有被合并 / 分支内容和 main 差多少"判断——今天证明前者会误判（拼多多那次我一开始就判断错了）。
2. **48 小时硬窗口**：所有负责人做两件事——①检查自己分支上是否有写好但没开 PR 的东西，开出来；②对着三轮问题清单逐条回复"已修在哪个PR"或"还没修需要多久"。
3. **48 小时后不再等**：没交 PR / 没回复的 App，不管是谁的，直接转 AI 接管，流程和这次唯品会/拼多多/百词斩/大众点评一致。
4. **明确告知所有负责人**："push 到分支 ≠ 交付，只有开 PR 并被合并才算数"，避免唯品会这种情况再发生。
5. **环境侧后续要做、且不需要等 48 小时**：对剩下没被核实过的分支批量跑一次"有没有未开 PR 的内容"扫描，产出准确状态表，代替"猜谁在干活"。
6. **深色模式/双语这条欠账（07-29 那轮，19 个 App）单独拉表跟进，不要和这次的功能性问题混在同一截止日期里**，避免优先级被稀释（唯品会那个 P0 死循环就是被这种混合清单拖了 17 天的前车之鉴）。

### 7.3 新工具：基于声明图的"push 环"静态检测

**为什么需要这个工具**：现有的 `runtime_walkthrough.mjs/py` 是按作者提前写好的路径测试，唯品会筛选页 P0 在它自己的 walkthrough 里活了 17 天，证明"脚本存在 ≠ 覆盖了所有路径"。根本原因是：手写脚本只测作者想到的路径，bug 刚好藏在没人想到要测的路径上。

**原理**：`navigation.declaration.ts` 是整个 App 导航行为的设计图纸。在框架约定里，返回到上一屏必须通过 `back()`/`popTo()`（弹出历史栈），永远不应该靠另一次 `push`。因此，如果 push 模式的 transition 形成了一个有向环（A→B→A 都是 push），用户每走一遍这个环就会在历史栈里净增 N 帧，永远不减，最终表现为"返回一直绕圈"。这个环可以直接从声明图里检测出来，不需要跑浏览器，不需要人工猜测测哪条路径。

**验证过程**（两轮，互相独立）**：
1. 唯品会对照实验：从 `git` 里提取修复前的 `navigation.declaration.ts`，生成旧导航图，运行检测器 → 准确报出 `searchResult.filter-open`/`searchFilter.confirm-open` 这条环（正好是那个 P0 的根因）。用当前修复后的代码生成新图再跑 → 这条环消失，无误报。
2. 喜马拉雅盲测：没有看问题清单，直接对当前代码（已包含 Song-WenPo 两次"fix"PR 的修改）运行检测器 → 独立报出 `/search?q=:q → push → /search-result?q=:q → push → /search?q=:q`，对应边 `home.search-open`（从结果页再次开搜索，push）和 `search.submit`（提交查询，push）——正好是"历史假持久化/返回循环"P0 的结构性根因，且 Song-WenPo 两次"fix"都没有修掉这条。

**对 9 个从未被审查的空白 App 的扫描结果**：

|---|---|---|
| Dida | 无环 | 2 条 target_missing（日历视图切换声明有误） |
| GoogleDrive | 无环 | 干净 |

**闲鱼（Xianyu）已确认真 bug**：

`apps/Xianyu/navigation.declaration.ts` 第 708–716 行，`tabbar.publish-open`（底部"发布"Tab）声明为 `mode: 'push'`，而同一批其他 Tab（`tabbar.message-open` 等）全部是 `mode: 'replace'`。Tab 按钮应用 replace 而非 push，否则每点一次"发布"都会在历史栈里新叠一层，与唯品会筛选页属同类根因。**修改成本极小**：一行字段值从 `'push'` 改成 `'replace'`。

### 7.5 后续安排修正

原六节的"48小时硬窗口"方案在实际操作中可行性存疑（之前"8月7日前"等软截止已被无视多次），调整为以下分工：

- **负责人只做两件事，不再要求自己改代码**：①确认验收单上点名的问题现在真机上是否还在；②顺手走一遍自己的主链路，看到哪里不对一句话记下来发过来。改代码这一步统一由环境侧（AI）处理，效率更高、质量更可控。
- **有未合并内容的（cjl、旧 songwp 分支）**：先问一句"还在弄吗、什么时候能开 PR"，得到明确答复后再决定是让本人继续还是拉进来由 AI 处理，不再空等。
- **没有未合并内容的**（大多数人）：分支是干净的，AI 直接处理，不存在撞车风险。
- **13 个遗留框架 App** 已排除出验收范围，待博士确认后正式记录。
