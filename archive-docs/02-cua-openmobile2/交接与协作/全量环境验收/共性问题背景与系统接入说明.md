# 共性问题背景与系统接入说明

配套文档：《验收反馈跟踪.md》2026-08-08 节（共性问题总表 + 系统接入检查 + 各 App 问题清单）。**修问题以跟踪文档为准，本文档解释"为什么"**，供有兴趣的负责人和环境侧讨论时参考。

---

## 1. 这套 App 是干什么的，为什么修 bug 的标准不一样

这套 App 不是产品，是 **GUI agent 的实验环境**。我们在上面做三件事：

1. **收集数据**：让 agent（或人）在 App 里执行任务，记录"看到什么界面 → 做了什么操作"的轨迹，用来训练模型。
2. **设计任务**：比如"把一件蓝色 XL 的卫衣加入购物车""给帕梅拉的帖子点关注""退掉某一单"。任务要有明确的、可程序化验证的完成标准。
3. **评测**：agent 跑完任务后，脚本读 `store.getState()` 判断任务是否完成。**判分不看界面截图，看 store。**

所以普通产品问"体验好不好"，我们只问两个问题：

- **这个 bug 会不会让做对了的 agent 被判失败？** 比如 agent 正确地点了"关注"，但状态没写进 store，验证脚本读出来是"未关注"——这就产生了一条假的失败数据（假阴性）。这种数据混进训练集，模型会学到"点关注是没用的"；混进评测集，我们分不清是模型不行还是环境坏了。
- **这个 bug 会不会让某类任务根本没法设计？** 比如点任何一个商品都跳到同一个商品页，那"找到 X 商品并购买"这类任务就没有区分度——agent 随便点都"对"，这类任务直接作废。

反过来，纯视觉瑕疵（圆角不对、字体偏大）既不影响判分也不影响任务设计，可以先放。优先级的来源就是这两条：

- 🔴 **必须修**：会让任务无法完成，或完成了无法验证
- 🟡 **建议修**：会缩小可设计的任务范围，或降低数据可信度
- ⚪ **暂不处理**：不碰上面两条的，先放

## 2. 八类共性问题：背后的原因



### 2.1 操作结果没有真正落进 store 🔴

界面上"看起来成功了"，但状态只存在于某个页面的 `useState` 或一个 toast 里，没有写进统一 store；或者写了但少填了字段；或者写了但只有一个视图去读它，别的视图还是硬编码的初始值。

判分读的是 `getState()`，没落库 = agent 做对了也判失败，这是所有问题里对数据污染最直接的一类。典型形态有三种：

- **只改本地状态**：京东微信支付成功回来无任何标识（京东支付/白条有）；苏宁消息红点不消、清空聊天无效。
- **写了但字段不全**：滴答清单四象限新增任务没传 `dueTs`，而"今天"视图筛的是 `dueTs <= now`，任务"存在但看不见"，只在收件箱里。
- **写了但只有一个视图读**：Keep 关注帕梅拉后帖子页显示"已关注"，个人主页显示"未关注"——一个视图读 store，另一个硬编码。

**期望**：P0 主链路每个关键操作写入统一 store；影响各视图可见性的字段（时间戳、分类、优先级）填齐；所有视图读同一份数据。**自查**：操作后切走再切回，结果还在吗？同一状态在两个页面展示，两边一致吗？

### 2.2 跳转参数硬编码 🔴

跳转时没把 id 带过去（或带了写死的值），点列表里任何一条进去都是同一个固定对象。"找到特定对象并操作"是一大类任务，所有入口通向同一个对象，这类任务就没有区分度，评测无效。

实例：京东申请退款无论从哪个订单进都是同一件固定商品、"修改地址"跳空白新增页、"立即购买"结算整个购物车；腾讯视频演职员都跳同一个演员；猫眼电影和演职人员错配。

**自查**：同一个列表点第 1 条和第 2 条，进去的内容必须不一样。每种列表都试一次。

### 2.3 返回死循环与死路 🔴

导航栈管理不对，两种表现：两个页面互相 push 返回来回横跳；错误状态页没有任何可点元素，彻底被困。agent 退不回根节点，这个 session 后面的所有任务作废——这是单个 bug 能造成的最大面积数据损失。

实例：唯品会筛选是独立页面，返回陷入"商品页→筛选页"循环（已修，改成 BottomSheet 后连带修好了参数丢失）；腾讯视频推荐列表连续点进新剧无限叠层；猫眼选座"订单信息缺失"页没有任何按钮（死路，比循环更严重）；菜鸟返回只回上一页不回主功能页。

**期望**：任意路径连按 5 次返回能回首页；错误页必须有返回或重试按钮；筛选用页内弹层不新开页面；Tab 切换一律 `mode: 'replace'`。**自查**：走到最深页面连按返回数次数；刻意触发错误态看还有没有能点的东西。

### 2.4 搜索/筛选叠进导航栈 🔴

搜索/筛选的每次操作都往历史栈叠一层，而不是页内状态变化。agent 取消搜索要逐层弹出历史，学到"取消→取消→取消才能回家"的错误模式；且搜索态下底部 Tab 常常消失，agent 失去所有快速导航手段。

实例：Keep 搜"跳绳"再搜"帕梅拉"，取消按 4 次才回主页，全程 Tab 消失；番茄小说同根因，且搜索是它的主链路，几乎绕不开。

**期望**：搜索的清空/取消是页内状态变化，取消一次直接回搜索前页面；底部 Tab 始终可见。**自查**：连续搜两个词，点取消——一次就该回去。

### 2.5 按钮无响应 / 反馈只有 toast / 界面突变 / 弹层被遮 🔴

agent 和环境之间"动作→反馈"的约定被破坏，四种形态：

- **点了没反应**：京东搜索框出不了键盘、购物车无删除入口；百词斩阅读页切集/字号/播放全无响应；Slack 加号无响应。agent 点了正确的按钮却毫无反馈，会反复重试；训练数据里这一步的正确动作看起来是无效的。
- **反馈只有 toast**：agent 靠截图感知世界，截图有延迟，toast 消失后无法区分"成功""失败""没发生"。滴滴货运链路的"功能未开放"就只有短暂 toast。
- **界面突变**：小日常编辑打卡后页面滚回顶端，agent 以为目标区域消失而重新搜寻。
- **弹层被遮**：小日常"⋯"菜单被底部 Tab 遮住，agent 再点一次反而把弹层关掉，陷入"点→看不到→再点→关掉"循环。

**期望**：核心链路按钮必须有实际响应，且以持久的界面变化呈现（状态标签、列表项、页面跳转），toast 只能作附加提示；操作后页面停在结果附近；弹层 z-index 高于底部导航栏。非核心功能可以标"暂未开放"，核心链路不行。

### 2.6 多条路径要都通、且结果等价 🔴

同一功能有多个入口，有的断了，有的走完结果不一样。任务描述写的往往是最自然的那条路——路断了，agent 按正常思路走被判失败，功能明明存在（假阴性）；结果不等价更隐蔽，agent 选了看起来更快的路，走完规格不对，验证失败，错的是环境。

实例：Keep"管理日程→添加训练"只能从空的想练清单选，此路不通；猫眼想看清单里的演出点不进订票，必须回首页重搜；苏宁快捷加号加默认规格 vs 详情页选规格。

**自查**：对每个核心功能，刻意找第二条路走一遍，比较两条路的最终 store 状态是否相同。

### 2.7 筛选/排序不跟当前上下文 🟡

筛选/排序不作用于当前搜索词和品类，而是跳到一批无关内容；或切父级 Tab 后子筛选残留。"在当前结果里筛出特定商品"是一大类任务，筛选乱跳则结果无法预测，任务无法设计也无法验证。

实例：唯品会搜"裙子"点颜色 Tab 跳到鞋子；大众点评餐厅 Tab 筛了"日料"，切到奶茶咖啡 Tab 筛选还挂着；京东搜索结果的综合/推荐/筛选栏无效；滴滴订单筛选点任何一个都是"暂无相关订单"。

**期望**：筛选/排序只作用于当前上下文；切父级 Tab 时子筛选自动清空；筛选后列表有可观察变化。

### 2.8 环境与真实 App 的偏差 🟡

哪怕功能都能走通，环境和真机的偏差本身就是污染，三种：

- **初始状态不对**：淘宝闪购没设任何条件，首页默认就显示"夜间远距离配送"。任务设计默认 App 处于正常起点。
- **数据太少太同质**：京东几乎全是电子类商品、冰箱评论里混着电脑和食品评论；腾讯视频各剧评论区雷同；大众点评只有美食，"玩乐"Tab 里还是食物。"找价格最低的""搜某类食物"这类任务要求候选项足够多且不同。**购物类 App 可直接复用拼多多的商品数据扩品类**（现有 App 里丰富度最高）。
- **真机自动的步骤变成手动**：滴滴下单后不自动跳"司机已接单"，要手动点蓝字。agent 要么无限等待，要么把这次手动点击学成必要步骤——环境教出来的错误行为会迁移到真实 App 评测。

## 3. 系统能力接入：为什么要走标准接口

系统层（模拟 OS）已经具备支付、分享、相册、剪切板能力，但设计上**只能调用 App 在** `manifest` **里主动声明、并走标准接口的功能**。如果 App 自己写一套私有分享/复制逻辑，系统层扫描不到、无法介入，这个功能对评测框架就是"不存在"的。

具体后果：agent 执行"复制快递单号"后，验证脚本读的是**系统剪切板**——App 私有实现只改了自己内部的状态，系统剪切板永远是空的，做对了也判失败。分享、相册、支付同理：评测要验证的是"这件事在系统层面真的发生了"，不是"App 里弹了个成功提示"。

所以规则只有一条：**App 里只要有分享/复制/选图/支付的入口，就必须走标准接口**；入口存在但不接标准接口，比没有入口更糟（agent 会反复尝试一个永远验证不了的操作）。标准调用方式和检查提示词见跟踪文档 2026-08-08 节。

几个待环境侧统一的事项：支付密码是否统一"任意 6 位通过"（优酷疑似只认 123456，agent 无从知道密码）；各 App 默认地点是否统一；生图版权（出现过迪士尼内容，是否全换虚构）。

## 4. 合并与修改

现有流程本身没有大问题，本轮暴露的主要是两点

1. **改动要及时开 PR、及时合**。这轮出现过分支从旧节点切出、合并时和 main 上的系统接线冲突的情况（京东），自动合并还引入过一个不报冲突、只在运行时崩溃的悬空引用；也有负责人把上千行改动堆在个人分支不开 PR，人联系不上时险些作废。→ 提 PR 前先合最新 main；改完当天开 PR（draft 也行），以 PR 为唯一交付信号。
2. **点名的问题要及时修、及时更新状态**。唯品会的 P0 返回死循环 07-21 就点名，挂了 17 天；豆瓣、Flomo 代码早修好了但跟踪表还挂着"待处理"。→ 定期把问题清单按 App 拆条发群里 @负责人，只发 🔴 和截止日期；点名后若干天无回应的，由 AI 代修并抽查后合并关闭（本轮对点评、唯品会、拼多多已这么做过）；合并时由合并人顺手更新跟踪表。
