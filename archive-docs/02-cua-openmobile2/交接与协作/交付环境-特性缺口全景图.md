# 从原型到「可交付的训练数据环境」· 特性缺口全景图

> 日期:2026-07-08 · 供负责人系统思考 + 开会用 · 未改任何代码/规范
> 定位:现在的仓库是一个**能跑的原型**;要交付给 research community 刷 GUI-agent 训练数据,
> 需要按"环境产品"的标准补一批特性。本图把四个来源合成一张地图:
> ① 7.7 会议需求 ② 负责人提的三个新问题 ③ 已核实的代码现状 ④ 研究者视角 + 文献趋势(2026-07)
> **现状列均已实地核实到文件级,非推测。**

---

## 0. 一句话判断

**地基比想象的好,缺的是"覆盖率"和"面向研究者的接口层"。**
OS 框架(intent、状态持久化、重置、隔离、i18n)大多已实现;真正的缺口在两处:
(a) **规范/gate 没强制,导致能力只有少数 app 用了**(可验证 2/21、跨 app 少数在用);
(b) **面向"数据消费者(研究者)"的接口从未建**(轨迹记录、任务定义格式、金标准判定、打包版本化)。
即:**从"开发者能跑"到"研究者能用来批量产数据",隔着一个接口层 + 一轮覆盖率补齐。**

## 2. 研究者视角:除了会上说的,他们还会要什么(启发维度)

站在"拿这个环境做 GUI-agent 研究"的人的角度(文献趋势佐证见括号):

1. **可复现/确定性**——同起点跑一百遍状态一致。时间不能用真实 Date.now(仓库已禁,✔)、随机要种子化。研究者最恨数据不可复现。
2. **金标准(verifiable reward)**——每个任务自带可编程成功判定。*(文献:RLVR 已扩到 tool-use agent「Beyond Next-Token Prediction: An RLVR PoC for Tool-Use Agents」;没有 verifiable reward 就喂不了 RL——这就是「数据可验证」是 P0 的根本原因。)*
3. **结构化观测+动作空间**——a11y 树/DOM 语义 + tap/type/swipe 动作,不只截图。
4. **任务定义规范格式**——研究者自己批量定义任务,不改你的代码。
5. **规模化并行 + RL 框架对接**——会议原话"复现 agentic RL"。
6. **真实性 & 多样性**——*(文献:「Unveiling the Fragility of Static Training in Tool Use」——单套数据训出的 agent 一换界面就崩;这是模板/跨app多样性为何是核心资产的直接证据。)*
7. **版本化 + 文档**——论文里要能写清"用的是本环境 vX",附能力矩阵与已知局限。

> 文献大势:agent 环境正批量涌现(FootsiesGym/PCBWorld/AGI Maze 等「XxxWorld」范式),
> 且社区在往"环境自带验证/修复"走(「Making Failure Safe: Constrained Verifiable Agent Framework」、
> 「Mnemosyne: Validating and Repairing AI-generated Workflows」)。**可验证性正在成为环境的标配门槛,不是加分项。**

## 3. 专节:MCP 能不能提供?(负责人特别问的前沿点)

MCP(Model Context Protocol)对本环境有**两个完全不同的用法,别混淆**——这也是一个有差异化的创意点:

**用法一(对内):把整个环境包成一个 MCP server,给外部 agent 当"手机工具"**
- agent 通过 MCP 调用 `open_app / tap / type / read_screen / get_state / reset` 等工具来操作这部手机。
- 价值:任何支持 MCP 的模型/框架(Claude、各类 agent runtime)**不改代码就能驱动你的环境**——这是最低摩擦的"交付给社区"方式,等于给环境配了一个标准 USB 口。
- 现状:你已经有 __SIM__/__SIM_QUERY__/simInput/__BENCH_STORES__ 这些内部 API,**把它们包一层 MCP server 即可**,不用重写内核。改动量 M。
- 这直接呼应会议的"GUI/CLI 混合特性":MCP 工具调用就是 CLI 侧,屏幕操作是 GUI 侧,同一环境两种接口。

**用法二(对内容):让被复刻的 app 内部提供 MCP 工具,制造"GUI+工具混合任务"**
- 例如:一个 app 既能手点、也暴露 MCP 工具,任务要求 agent 混合使用两种手段——正是会议问的"GUI/CLI 混合"。
- 这是更研究前沿、更实验性的方向,可作为差异化特性(别的 mobile 环境大多只有纯 GUI)。改动量 L,建议 P2 探索。

**结论**:用法一(环境作为 MCP server)**性价比高、且能显著降低交付门槛,值得认真考虑**;用法二当研究亮点储备。

## 4. 建议的推进顺序(不推翻现有范式,分层加)

**第一批(P0,交付前必须,多为规范+逐app补齐)**
1. **可验证 + 数据-UI联动**:把"每 app 必须有 runtime_walkthrough + 联动元测试(改输入断言输出变)"写进规范并逐个补——一箭双雕解决拼多多类问题。
2. **可记录**:建一层轻量 action+state 事件流记录(训练数据本体,现在完全没有,最该补)。
3. **任务定义格式**:定一个任务 schema(初始态+指令+成功判定),对齐 MobileGym/AndroidWorld。
4. **模板·数据**:把 data 加载链从"硬编码单套"改成"可选套",支持多套种子。
5. **跨 app 交互**:规范要求核心 app 声明 intentFilters + 实现"分享出去",补齐覆盖。

**第二批(P1,显著提升价值)**
6. 可重置固化进评测流程 + 确定性(随机种子)核查。
7. 模板·语言补全覆盖 + 运行时切换验证。
8. 观测/动作接口文档化 + 规模化并行验证 + RL 框架对接。
9. 打包版本化 + 能力矩阵 + 已知局限清单。

**第三批(P2,差异化/探索)**
10. MCP server 封装(用法一)——建议提前到 P1 评估,交付门槛收益大。
11. MCP 混合任务(用法二)、外观多套。

## 5. 需要负责人拍板的几个方向

- **P0 这五项,先做哪个?** 我建议"可验证+联动"和"可记录"最先——前者堵住拼多多类质量漏洞,后者是训练数据的本体(现在竟然完全没有记录机制)。
- **MCP server(用法一)要不要提前到 P0/P1?** 它可能是"交付给社区"最省力的接口,值得单独评估。
- **任务定义格式**要不要直接对齐 AndroidWorld/MobileGym 的既有 schema(便于跨环境比较),还是自定义?
- 这些特性里,哪些是"交付前硬门槛",哪些可以"v1 先发、后续迭代"?——建议据此定 v1 交付范围。
