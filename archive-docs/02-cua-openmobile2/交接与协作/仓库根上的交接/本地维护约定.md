## 这条线是什么

环境侧要最终提供 **tooluse**，这里已有部分 Hybrid / App Tools 实现与评测资产。

当前阶段约定：

- **可以、也需要**有反馈和本地尝试（例如这周给团队一点进展）
- **主交付仍是环境 feature**（在 `../mobilegym-env-showcase`）
- 未到可交付前：**以本地尝试为主，不必急着 push**；有复现/协作需求再开分支上传

## 建议这周的「有反馈」做法

1. 按根目录 `MOBILEGYM_HYBRID_*.md`、`MOBILEGYM_REPRODUCTION.md` 跑通现有 Demo  
2. 写一页判断：能跑什么、卡点、与完整环境 feature 的缺口、下一步想扩的 2～3 个工具  
3. 可选：一次很小的尝试（多挂 1 个只读 tool / 修小问题），证明能下手但不拖环境主线

向同事可对齐的一句话：

> 主线是完整环境 feature；tooluse 同步摸现有 Hybrid、给反馈和一次小尝试。环境收口后再把工具扩展接上去。

## 日常怎么用

```bash
cd ~/Desktop/mobilegym-mock-tooluse
# 需要试 tooluse 时另开一个 Cursor 窗口打开本目录
```

- 试验用独立分支名，例如：`yingying/tooluse-try`（避免长期堆在脏掉的 `main` 上）
- 本地试坏了可以丢弃；**给别人复现时再** `push -u origin <branch>`
- 优先改：`app_tools/`、`hybrid_tools_*`、根目录 Hybrid 文档  
- 尽量少和大改 `system/` 环境底盘抢同一批文件（那是 env-showcase 的活）

## 和 env-showcase 的关系

| | `../mobilegym-env-showcase` | 本目录（tooluse） |
|--|----------------------------|-------------------|
| 优先级 | **P0** 完整环境 feature，推远端 | **P1** 本地尝试 + 阶段性反馈 |
| 真源 | 环境正式改动以那边 push 为准 | 工具试验先本地 |

以后同步 / 合入都方便，例如：

```bash
# 把远端已完善的环境拉进本仓再继续扩工具
git fetch origin
git merge origin/system/env-showcase   # 或 rebase，按团队习惯

# 或：本仓工具成果推分支，向 env-showcase / 主干提 PR
```

真正费劲的不是两个文件夹，而是两边同时大改同一批环境文件——按「环境推远端、tooluse 先本地」即可。
