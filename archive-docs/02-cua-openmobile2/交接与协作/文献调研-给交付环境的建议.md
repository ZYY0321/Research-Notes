## TL;DR(给赶时间的人)

1. **我们最大的护城河已经握在手里:`__SIM__.getState()` 能读结构化全量状态。** AndroidWorld/OSWorld 要费劲从 adb+SQLite/文件里抠状态,WebArena 甚至退化到字符串匹配答案——我们一个函数就拿到。**但这个优势只落地了 2/21(只有 Kapi/Taobao 有断言走查),是最大的"已有优势未兑现"。**
2. **如果只做三件事**(排序见 §5):① 可验证判定铺到全覆盖 ② 建轨迹记录格式 ③ 任务定义 schema 统一 + 多套种子数据(配确定性 RNG)。
3. **MCP 可行、有 1:1 先例(mobile-mcp)、1–2 周 PoC**,但**除非要"外部通用 agent 接入 / 对外评测台",否则暂缓**——它和 RL 对接是两条不同的路,别混淆优先级。

## 一、同类环境能力对比表(我们 vs 主流)

| 环境 | 任务格式 | 成功判定 | 观测 | 动作 | 跨 app | 多样性 | 交付 |
|---|---|---|---|---|---|---|---|
| **AndroidWorld** | Python 类,setup+参数化 template+success-check | state-based 读设备真实状态(SQLite/文件),durable reward | 截图+UI elements(a11y) | JSONAction 14 类 | 20 app+可挂 MiniWoB++ | 参数随机实例化(百万级变体) | git+pip+setup.py;Docker;需 AVD |

| **AppWorld** | Supervisor+Instruction+Initial State(DB+时间快照) | **state-based 单测,含 collateral-damage 反向检查** | 无 GUI,API/代码 | apis.{app}.{api}() | 9 app/457 API 天然编排 | ~100 虚拟用户 | pip install+download data;test 藏答案 |

## 二、六个维度各自最值得借鉴的点(附来源)

### 1. 同类环境
- 判定读"状态"而非"界面"是最大护城河,坚持。来源 https://arxiv.org/abs/2405.14573 、https://arxiv.org/abs/2404.07972 、https://arxiv.org/abs/2307.13854
- "指令模板+实例化字典+判定"绑同一 schema,一个模板产海量变体且判定随参数对齐。来源 https://github.com/web-arena-x/webarena 、https://github.com/google-research/android_world
- 交付看齐社区:pip + 语义化版本 + 数据/代码分离下载 + 防泄题 split(test 只给难度元数据、藏 ground-truth)。来源 https://github.com/xlang-ai/OSWorld 、https://github.com/StonyBrookNLP/appworld

### 2. 可验证奖励(RLVR)
- 判定=纯函数 checkSuccess(before, after, params)→bool,只读 getState(),不看截图/动作序列(对齐 AndroidWorld is_successful())。来源 https://github.com/google-research/android_world/blob/main/docs/tasks_guide.md
- 抄 AppWorld 的 collateral-damage 反向断言 + AndroidWorld 的 before/after 只比关心字段:既验"该变的变了",也验"不该变的没变"。来源 https://arxiv.org/abs/2407.18901
- **主动堵 reward hacking**:GUI-G1 实测模型会输出超大 bounding box 蹭中目标——任何"越宽松越易得分"的判定都会被利用,模糊"包含即过"要补 include+exclude 双向约束。来源 https://arxiv.org/abs/2505.15810
- (进阶)被动 LLM judge 不准,趋势是"主动探测式"验证(ProRe https://arxiv.org/abs/2509.21823);长任务用 milestone/checklist 补稠密奖励(https://arxiv.org/abs/2602.11524 、https://arxiv.org/abs/2602.12268)。

### 3. MCP 封装
- 1:1 先例 mobile-mcp 已把 iOS/Android 模拟器包成 MCP,暴露 launch/tap/swipe/type/screenshot/list-UI-elements。来源 https://github.com/mobile-next/mobile-mcp
- get_state/read_screen 应输出结构化 UI(元素 id/文本/类型/bbox)而非只给截图(对齐 Playwright MCP accessibility snapshot),决定 agent 是"确定性点 id"还是"猜坐标"。来源 https://github.com/microsoft/playwright-mcp
- 动作后等 UI 稳定再返回新 state;把 BACK/close 作一等工具并在 get_state 暴露"是否可返回"(呼应我们豆瓣卡死/返回 gate 教训)。来源 https://modelcontextprotocol.io/specification/2025-06-18/server/tools

### 4. 轨迹记录
- 事实标准 schema:episode 头 + 交错的(观测,动作)序列,观测数=动作数+1;动作是判别式 action_type+参数,词表对齐 AndroidControl/AndroidWorld JSONAction。来源 https://github.com/google-research/google-research/tree/master/android_control 、https://raw.githubusercontent.com/google-research/android_world/main/android_world/env/json_action.py
- 观测层用截图 + getState() 完整快照替代别人的近似 a11y 树/DOM(无损上位替代),截图仍留供视觉训练/回放/坐标 grounding。来源(AITW 仅截图不足) https://github.com/google-research/google-research/tree/master/android_in_the_wild
- 结果层记 before/after state diff,做奖励/状态化评测/自动标注三用(对齐 WebArena program_html 读真实 DOM)。来源 https://raw.githubusercontent.com/web-arena-x/webarena/main/evaluation_harness/evaluators.py

### 5. 多样性
- 多样性对泛化有量化收益(5–20%、明确 scaling law,AutoWebWorld/Video2GUI);但 WebFactory 证明"10 个高质量可验证网站可匹敌大量粗放环境"——**宁精勿滥**。来源 https://arxiv.org/abs/2602.14296 、https://arxiv.org/abs/2605.14747 、https://arxiv.org/abs/2603.05044
- "同一 app 多套种子数据"有直接先例(ShopGym 多可重置实例、AutoWebWorld 29 环境),要求可重置/可验证/可检查。来源 https://arxiv.org/abs/2605.16116
- 多语言被 SOTA 主动采用且有效(AgentCPM-GUI 中英双语);多主题外观先例最弱、但反面证据强(外观漂移伤泛化,Continual GUI Agents)——建议**轻量外观扰动**而非全套主题。来源 https://arxiv.org/abs/2506.01391 、https://arxiv.org/abs/2601.20732
- **多样性优先级**:种子数据多样(空/少/多/超长/边界/空态) > 任务/状态覆盖(含异常/返回可达性) > 多语言 > 轻量外观扰动。

### 6. 可复现与规模化(调研直接读了我们的代码)
- **确定性 RNG 是当前最大缺口**:Gymnasium 事实标准是环境持有内部 PRNG、reset(seed) 播种、绝不直接调全局 Math.random。**我们 `os/storageIsolation.ts:117` 的 genNamespace() 直接用了 Math.random()**,是不确定性根源。来源 https://gymnasium.farama.org/api/env/
- 接 RL 需标量 reward + gym 语义 (obs, reward, terminated, truncated, info);**我们 `MobileGymEnv.step()` 现返回自定义 StepResult,无标量 reward、无 terminated/truncated 二分**。verl 的 create/execute/release 生命周期恰好对应 reset/step/close。来源 https://verl.readthedocs.io/en/latest/advance/agent_loop.html 、https://gymnasium.farama.org/api/env/
- **隔离与并行我们已做得最好**(三级浏览器隔离、MultiProcessRunner、storageIsolation 的 tab/load 命名空间、restart 复用进程只重建 context)。补 POST /reset + POST /step 无状态 HTTP env server 即可对接 verl/OpenRLHF。来源 https://github.com/ServiceNow/BrowserGym

## 三、P0 特性各给一个"参考谁、怎么做"

**① 可验证(2/21 → 全覆盖)** — 参考 AndroidWorld is_successful() + OSWorld getter/func/expected 解耦 + AppWorld collateral-damage。
做法:每任务配 `{getter, assert, compareFields}` 三元组 + before/after 快照,纯函数读 getState() 出 0/1;判定只约束终态语义、不约束路径;模糊断言补 include+exclude 双向约束防 reward hacking。getter/比较器(exact/includeExclude/setEqual/numberInRange)跨任务复用,降低 21 app 铺开的人力。

**② 可记录(无 → 建轨迹格式)** — 参考 AndroidControl(两级指令) + WebArena program_html。
做法:JSONL,episode 头(goal/device/eval 谓词) + 每 step `{observation(截图+getState 完整快照+state_hash), action(target_id 语义 + x/y 坐标 + 原始 simInput + 可选 thought), result(state_after_hash + state_diff + transition_ok)}`。一份轨迹同时供 SFT / 状态化评测 / 自动质检。我们的 getState()+simInput 让这份 schema 是公开数据集的无损上位替代。

**③ 任务定义 schema(硬编码 → 统一)** — 参考 WebArena intent_template+instantiation_dict+intent+eval;OSWorld 声明式 evaluator。
做法:模板/实例化参数/判定绑进同一 JSON;参数既进指令又进 judge,判定用同一份 params 生成 reference,防 judge 与指令漂移。一个模板覆盖无数变体。

**④ 多套数据(单套硬编码 → 多种子)** — 参考 ShopGym/AutoWebWorld;WebFactory(少而精)。
做法:优先级 P0 种子数据多样 > 任务/状态覆盖 > P1 多语言(已 15/21 双语,低成本补) > P2 轻量外观扰动。前提:每套可重置/可验证/可检查。**需配套确定性 RNG**:加 SeedService(`__SIM_RNG__.seed()` 播种 mulberry32/xorshift + monkey-patch 全局 Math.random),reset(seed) 时播种并冻结时间(`__SIM_TIME__.setSimulatedTime(t,false)`),实现"同 seed+同 config→同初始态"。

**⑤ 跨 app(框架已有、部分在用)** — 参考 AppWorld(断言涉及的所有 app 状态,含副作用)。
做法:跨 app intent 任务的判定要读**所有相关 app 的 getState()**,既验目标 app 终态,也对来源 app 做 collateral-damage 断言(如"从 A 分享到 B 后 A 的数据没被破坏")。把 intent 框架从"部分在用"推到全覆盖,轨迹里记录 intent 跳转边界。

## 四、MCP 封装最终判断

**可行性:高,有 1:1 先例(mobile-mcp),PoC 约 1–2 周。** 我们是 web 端模拟器,只需写一层 adapter:MCP server ⇄ 现有 JS/HTTP API。工作量:server 骨架 ~1 天、6 工具接 API ~2–4 天、get_state 结构化输出+等 UI 稳定+返回可达性 ~2–3 天(最耗时最影响成败)、session/reset 隔离+错误处理 ~1–2 天。**最大风险不在协议,在 get_state 能否输出高质量结构化 UI——而这正是我们 pipeline-v3 state 建模的现成优势。**

**值不值得(关键决策点):**
- 若目标是**让外部通用 agent(Claude 等任意 MCP host)标准化驱动我们的环境 / 对外可复现评测台 / 演示** → 值得,零改造接入整个 agent 生态。
- 若短期**只是自家 pipeline 内部脚本刷数据/跑复刻回归** → MCP 是额外抽象层,直接函数调用更省;等出现"外部 agent 接入 / 多 agent 复用 / 对外演示"需求时再包。
- **注意**:RL 训练对接(§二.6 的 HTTP env server,gym 语义)与 MCP(agent 驱动)是**两条不同的路**,别混淆优先级。

## 五、如果只做 3 件事(最提升交付价值)

排序依据:证据强度 × 是否卡住下游 × 是否发挥独有优势(无损 state) × 性价比。

**第 1 件:把"可验证判定"从 2/21 铺到全覆盖,定成 `{getter, assert, compareFields}` + before/after 快照的统一范式。**
这是我们相对所有同类环境的结构性护城河(别人拿不到 state,我们能),却只落地 2/21——最大的"已有优势未兑现"。它同时卡住 RL reward、评测台、数据质量三条下游。配套堵 reward hacking(include+exclude)与 collateral-damage 反向断言。

**第 2 件:建轨迹记录格式(截图 + getState 完整快照 + simInput + before/after diff,动作词表对齐 AndroidControl)。**
"无轨迹记录"是交付给训练社区的硬门槛——没轨迹就没有可训练/可评测的产出。我们独有的 getState()+simInput 让这份 schema 是公开数据集的无损上位替代,一次落地同喂 SFT / 状态化评测 / 自动质检。与第 1 件共用 state 基建,边际成本低。

**第 3 件:任务定义 schema 统一(模板+实例化+判定绑定) + 多套种子数据(配确定性 RNG)。**
把"硬编码单套"升级为"一个模板产海量可验证变体",是多样性 scaling law 里最便宜的一档。确定性 RNG(换掉 storageIsolation.ts:117 的 Math.random)是"同 seed→同初始态"的前提,也是可复现回归 gate 的基础,一并做掉。

**暂缓:** MCP 封装、标量 reward/gym 适配、HTTP env server、多外观主题。前三者取决于"是否要外部 agent 接入 / 是否马上接 RL 框架";多外观主题证据最弱、成本高,留后。

## 六、与我们已固化经验的呼应

- 调研反复独立指向我们已有的两条教训:**返回可达性**(MCP get_state 要暴露"是否可返回"、轨迹 diff 可检测卡死)和**数据-UI 联动**(可验证判定 + before/after diff 正是抓"搜索/筛选/地址失效"这类的机器手段)。说明我们此前 pipeline-v3 §5.2/§11 和《数据-UI联动-根因思考》的方向,与文献主线一致。
- 一个反直觉但重要的点(WebFactory):**多样性不是盲堆皮肤,少而精、可验证、闭环 > 多而滥**。这修正了"模板越多越好"的直觉——优先把有限模板做成可验证的。
