## 1. 建设背景

折叠屏、平板和大屏设备在窗口尺寸、屏幕比例、横竖屏状态以及折叠形态上存在差异。同一个应用页面在不同设备状态下可能出现大图大字、页面内容截断、视频或图片拉伸、横屏适配异常、控件避让异常和页面布局重排等问题。传统人工测试需要在多个设备上重复执行相同操作，过程依赖个人经验，难以保证页面状态一致，也难以保存能够复核的证据。

GUIAgent 多设备 UX 检测系统将页面导航和 UX 检测放在同一条可追踪链路中。Agent 接收任务目标和操作指令，通过设备执行器完成应用启动和页面操作；观察器在每个动作后采集截图和页面结构；页面确认模块判断目标页面是否已经到达；UX 检测模块对目标页面进行单截图判断，并根据需要使用结构化页面信息完成辅助验证；结果模块保存全过程证据并生成验收统计。

## 2. 设计目标

系统的首要目标是使验收任务从统一的任务描述开始执行，而不是要求测试人员预先把应用停在某个页面。系统需要支持高级指令和低级指令两种输入方式。高级指令用于评价 Agent 对任务目标的理解和路径规划能力，低级指令用于评价已经明确动作条件下的控件定位和设备执行能力。

系统的第二个目标是将页面到达和 UX 检测分开判定。Agent 只有在页面确认模块判断目标页面到达后，才能提交该页面的 UX 检测结果。页面没有到达、页面状态不稳定或截图无效时，任务只能计入导航或环境结果，不能被当作 UX 检测漏报。

系统的第三个目标是适配验收集不断增加的 UX 问题。当前验收范围包含大图大字、页面截断、视频或图片拉伸、横屏适配、避让异常及其他多设备体验问题。检测器通过统一的模型结果和证据接口接收问题类型，新增问题类型不改变 Agent 的导航流程。

系统的第四个目标是保留完整证据。每个结论都应能回溯到任务指令、设备状态、动作轨迹、目标页面截图、页面结构、模型原始响应、验证过程和最终结果。汇总指标不能脱离逐任务明细单独存在。

## 3. 功能需求

系统应支持任务加载、应用启动、点击、滑动、输入、按键、屏态切换、截图采集、页面结构采集、目标页面确认、UX 问题检测、结果验证和验收报告生成。任务支持高级指令和低级指令，页面确认支持页面路径、标题、文本和控件组合。模型输出必须经过结构校验，检测结果必须保存截图、页面结构、原始模型响应和最终判定。

## 4. 非功能需求

每个动作平均响应时间小于等于 3 秒，单步最大响应时间不超过 5 秒；排除网络和资源等非模型因素后，三层界面 UX 检测端到端时间小于等于 10 秒。低级指令页面到达准确率达到 95%，高级指令页面到达准确率达到 80%，成功到达检测页面后的 UX 问题发现准确率大于等于 95%。系统应具备稳定性、可追溯性、可扩展性和配置安全性，失败任务不能丢失已有证据。

## 5. 可行性分析

HarmonyOS HDC 和 uitest 能够提供应用启动、设备操作、截图和页面结构导出能力；视觉模型能够从目标页面截图发现 UX 候选；页面结构和动作轨迹能够为目标页面确认及结果复核提供证据。系统可以在真机和 DevEco 模拟器上运行，新增应用、设备或问题类型通过任务配置接入。正式验收依赖已解锁设备、可复位初始状态、稳定应用数据和可访问模型服务，环境不满足时生成环境失败记录，不把失败写成检测结论。

## 6. 验收范围

验收范围从任务初始化开始，包含设备连接、应用启动、初始状态恢复、页面导航、目标页面确认、屏态切换、页面截图、UX 检测、结果验证和报告生成。系统不负责修改被测应用，不负责生成应用业务数据，也不以模型训练结果替代应用页面的实际运行结果。

被测应用可以是普通手机应用，也可以是支持平板、折叠屏或多窗口的 HarmonyOS 应用。每个任务应声明目标设备和需要执行的屏幕状态。单屏、展开、半折、横屏等状态属于任务环境条件，不能在执行过程中根据模型判断临时改变。

验收不要求系统预先知道所有未来测试样本的源码结构。测试集只需按照统一任务和真值接口提供目标页面、截图约束、问题标签和预期结果，Agent 和检测器按照同一流程执行。

## 7. 总体架构

系统由任务管理、Agent 决策、设备执行、页面观察、页面确认、UX 检测、证据归档和统计报告八个逻辑部分组成。任务管理器读取任务并创建运行编号；Agent 决策模块根据目标和观察结果选择下一步动作；设备执行器将动作转换为 HDC 或 uitest 操作；页面观察器同步采集截图、页面结构和设备状态；页面确认模块判断是否到达目标页面；UX 检测模块完成问题发现和证据验证；证据归档模块保存中间产物；统计模块计算验收指标。

```text
任务定义与初始状态
          ↓
Agent：任务理解、路径规划、动作选择
          ↓
设备执行器：启动、点击、滑动、输入、按键、屏态切换
          ↓
观察器：截图、UI dump、页面路径、设备状态
          ↓
页面确认：目标页面规则匹配
          ↓
UX 检测：单截图模型判断与必要的结构验证
          ↓
证据归档：轨迹、截图、模型结果、最终 verdict、统计
```

Agent、页面确认和 UX 检测之间通过结构化对象通信。设备执行器不负责判断页面是否正确，模型也不负责替代页面确认。每个模块只对自己的结果负责，避免工具调用成功、模型自然语言回答和最终验收结论相互混淆。

## 8. 任务定义

任务定义包含任务编号、应用信息、设备信息、初始状态、指令类型、任务目标、动作指令、目标页面条件和 UX 验收要求。高级指令描述需要完成的页面任务，低级指令描述单步动作或动作序列。两种指令可以指向同一个目标页面，但统计时使用不同的指标分母。

目标页面条件可以由页面路径、页面标题、关键文本、稳定控件标识、必要控件组合和禁止文本组成。页面规则应尽量选择能够从 HarmonyOS 页面结构或页面文本中稳定获得的条件。仅凭模型自述“已经到达”不能作为验收证据。

UX 验收要求描述检测时使用最终单张截图还是允许额外交互验证、需要检测的设备屏态、问题类型和真值范围。单截图要求下，模型请求只能携带规定的目标页面截图，不得把 UI dump、前后截图或人工标注框一并发送给模型。

## 9. Agent 决策设计

Agent 采用观察驱动的循环。每轮循环先读取最近一次页面观察，再根据当前任务目标、已完成步骤和动作历史选择一个动作。动作执行完成后，系统重新观察页面，Agent 不得使用上一轮截图推断当前状态，也不得仅凭设备命令返回成功判断页面发生了预期变化。

Agent 的任务状态由初始化、应用启动、页面观察、动作选择、动作执行、页面确认、UX 检测和结果上报组成。页面未到达时继续执行导航动作；页面到达后停止普通导航并进入检测；设备错误、应用启动失败、动作预算耗尽或任务超时后进入失败上报。

高级指令任务允许 Agent 根据当前页面选择路径，但每次仍然只能执行一个注册动作。低级指令任务按照任务给出的动作约束执行，并在每一步后检查观察结果。动作参数必须经过执行器校验，点击和滑动坐标必须落在设备屏幕范围内，输入文本必须经过长度和字符校验。

Agent 可以维护短期动作历史，用于识别页面无变化、重复点击和错误路径。历史信息只作为下一步决策依据，不得直接覆盖页面确认结果。任务结束必须调用显式结果上报接口；没有结果上报、发生超时或工具出现致命错误时，运行器应生成失败结果。

## 10. 页面到达确认

页面确认模块接收页面路径、截图、UI dump 中的文本、id 和 key，并按照任务目标页面规则进行匹配。必要规则全部满足且禁止条件均不满足时，页面判定为到达。页面信息缺失、规则冲突或只满足部分条件时，页面判定为未确认。

页面确认输出包括 `reached`、匹配规则、未满足规则、置信度和观察快照编号。置信度用于诊断，不得单独替代必需规则。页面确认结果必须写入动作轨迹和最终任务结果。

页面确认应能够排除相似页面。例如同一个应用的首页、列表页和详情页可能包含相同商品标题，目标页面规则应组合页面路径、页面标题和关键控件，避免只凭一段文本确认页面。对于无法从 UI dump 获得页面路径的应用，可以使用稳定文本和控件组合，但必须在任务定义中记录该降级方式。

## 11. 多设备和屏态处理

设备管理模块在任务开始时读取设备型号、系统版本、屏幕分辨率、连接状态和当前屏态。屏态切换由设备执行器完成，切换后等待页面渲染稳定，再重新采集截图和页面结构。不同屏态必须使用不同的快照编号，不能复用切换前的截图或 UI dump。

普通设备只执行任务规定的默认状态；折叠设备按照任务配置执行单屏、展开或其他规定状态。若屏态切换失败、设备尺寸变化但截图仍使用旧状态，系统应将该屏态标记为环境失败或未确认，并保留切换命令和设备返回信息。

多设备检测的结果既可以按每个屏态分别输出，也可以在任务级别汇总。任务级别汇总必须保留每个屏态的原始结果，不能用一个屏态的正常结果覆盖另一个屏态的问题结果。

## 12. UX 检测流程

UX 检测在页面确认成功后启动。系统先保存目标页面截图和页面观察，再将规定的截图输入视觉模型。模型负责从当前可见页面发现验收范围内的 UX 候选，输出整体状态、问题类型、问题区域和必要的验证建议。模型原始响应必须原样保存，解析后的结构化结果单独保存。

检测结果不能直接由模型自然语言决定。模型输出需要经过字段校验，包括整体状态、问题类型、坐标格式、坐标范围和问题列表结构。字段缺失、坐标非法、问题类型不在任务允许范围内或整体状态与问题列表冲突时，结果标记为未确认。

对于能够从单张截图直接判断的问题，系统保留视觉结果作为主要证据。对于需要确认页面结构、滚动关系、控件边界或设备状态的问题，系统可以使用 UI dump 和规定的验证动作辅助判断。辅助验证不得修改模型原始结果，所有修订都通过独立的最终 verdict 字段记录。

## 13. 问题判定原则

系统将模型输出视为候选，不把候选自动等同于缺陷。最终判定依据问题类型和任务要求确定。对于页面视觉上已经明确出现的问题，检测器应保留截图区域和模型框；对于需要结构解释的问题，验证器应记录使用的页面结构证据；对于证据不足或页面状态不稳定的问题，输出未确认。

问题区域统一采用原图坐标和归一化坐标保存，并记录图像宽高和坐标来源。模型输入使用缩放预览图时，模型返回的坐标必须映射回原始截图，再转换为系统统一坐标。任何坐标转换失败都应终止该候选的可靠判定。

文字截断只是验收范围中的一种问题。对于大图大字、图片或视频拉伸、横屏布局、避让异常和其他问题，模型输出可以使用相同的 `issue_type`、`bbox`、`evidence` 和 `verdict` 接口。检测器的公共流程保持不变，问题类型的具体规则由验收集和相应验证器定义。

## 14. 数据流和结果模型

一次任务运行由唯一 `runId` 标识，任务内每个页面状态由 `snapshotId` 标识。动作轨迹关联动作前后的快照，模型结果关联目标页面快照，布局或交互验证关联同一个目标页面和候选编号。这样可以避免不同屏态、不同页面或不同重试结果互相覆盖。

```json
{
  "runId": "run-20260913-0001",
  "taskId": "task-001",
  "instructionLevel": "high",
  "app": {"bundle": "example.app", "version": "1.0.0"},
  "device": {"model": "foldable", "state": "expanded", "width": 1256, "height": 2760},
  "targetPage": {"requiredTexts": ["商品详情"]},
  "navigation": {"reached": true, "steps": 3},
  "detection": {
    "overall": "bad",
    "issues": [{"issue_type": "ux_issue", "bbox": [100, 200, 800, 400]}]
  },
  "evidence": {"snapshot": "snapshot.png", "layout": "snapshot_window.json"}
}
```

任务结果至少包含导航状态、UX 状态、设备状态、模型调用状态、错误信息、动作耗时、端到端耗时和证据路径。任务级结果不覆盖屏态级结果，也不覆盖模型原始结果。

## 15. 性能设计

动作响应时间从执行器发出设备动作开始计算，到动作完成后的页面观察完成为止。系统记录每个动作的开始时间、结束时间、截图耗时、UI dump 耗时和模型耗时。平均动作响应时间应不超过 3 秒，单步最大响应时间不超过 5 秒。

端到端检测时间从目标页面确认成功开始，到最终 UX verdict 和证据文件写入完成为止，验收要求不超过 10 秒。网络、设备资源、应用自身加载和模型服务不可用等排除项必须单独记录，不能直接从总耗时中删除。

性能优化采用截图和 UI dump 并行采集、模型请求复用已完成的截图、减少重复页面检测和限制重试次数等方式。优化不能改变单截图输入约束，也不能通过跳过页面确认或减少证据保存来获得表面上的耗时达标。

## 16. 异常和恢复

设备连接失败时，系统记录设备列表和连接错误；应用启动失败时，记录 bundle、ability 和设备返回信息；屏幕锁定时，任务标记为环境前置失败；截图或 UI dump 失败时，保存已经成功的证据并停止依赖该证据的后续阶段。

模型超时、HTTP 错误和结构解析错误分别记录。允许重试时，重试必须使用同一个 `snapshotId` 和输入图片 hash。备用模型只能用于联调，若验收要求固定模型，备用模型结果不得进入固定模型的准确率统计。

页面无变化、控件未找到和错误页面可以触发有限恢复，例如重新观察、重新打开应用或回到任务约定的安全起点。恢复动作需要由任务配置允许，不能在未知状态下任意返回或清除数据。恢复失败后任务进入未确认或导航失败，并保留恢复轨迹。

## 17. 验收指标和统计口径

低级指令页面到达率为正确到达目标页面的低级指令任务数除以低级指令任务总数；高级指令页面到达率为正确到达目标页面的高级指令任务数除以高级指令任务总数。两项指标分别统计，不得合并成一个到达率。

UX 问题发现指标只在页面确认成功、目标截图有效且模型调用符合要求的任务上计算。验收报告同时给出准确率、精确率、召回率和未确认比例，并列出 TP、FP、FN、TN、unknown 的样本数。未确认不能静默归入正常页面，也不能同时计入 FN 和 TN。

性能指标单独统计平均动作耗时、最大动作耗时、模型请求耗时、截图和 UI dump 耗时、页面确认耗时以及端到端耗时。功能链路贯通、页面导航达标、UX 检测达标和性能达标是四个不同结论，必须分栏展示。

## 18. 测试实施

测试实施分为设备冒烟、导航验证、单截图检测、辅助验证和正式验收五个阶段。设备冒烟确认应用能够安装启动、设备状态能够切换、截图和 UI dump 能够保存；导航验证确认高级和低级指令能够到达目标页面；单截图检测确认模型输入符合验收约束；辅助验证确认问题证据能够回溯；正式验收使用冻结任务、冻结模型和人工真值计算指标。

每个阶段都保留原始日志和失败结果。测试人员不能只保存通过样本，也不能用重新运行后的结果覆盖第一次失败结果。重试产生新的 `runId`，原运行继续保留。

## 20. 交付物

设计阶段交付本说明书、任务字段定义、页面规则定义、结果结构定义和验收统计模板。测试阶段交付设备环境清单、任务执行轨迹、目标页面截图、模型原始响应、辅助验证结果和逐任务状态。终验收阶段交付冻结版本信息、指标汇总、失败样本、未确认样本、异常说明和可复核证据目录。

任何只包含模型截图而没有任务输入、页面到达证据、设备信息和人工真值的材料，都只能作为演示材料，不能作为正式验收结论。

## 21. 功能需求详细说明

### 21.1 任务接收与校验

任务管理器从 JSON 或数据库读取验收任务，生成不可重复的 `runId`。任务读取后依次校验应用标识、设备类型、指令内容、目标页面规则、检测模式和超时参数。校验通过后生成运行快照，保存任务原文和校验结果；校验失败时只生成输入错误记录，不启动应用。

任务目标与动作指令分开保存。目标回答“最终要到哪里、检查什么”，动作回答“本轮允许执行什么”。高级任务可以没有预先给出的完整动作序列，低级任务可以包含明确的逐步操作。两类任务使用同一执行器和同一页面确认模块。

### 21.2 观察与页面状态

观察器在动作完成后同时请求截图和页面结构，并为两份结果分配相同的 `snapshotId`。截图记录原始尺寸、文件 hash 和采集时间；页面结构记录 dump 原文、解析状态和页面路径。设备折叠状态、窗口尺寸和应用前后台状态与快照一并写入。

当截图和页面结构的采集时间差超过配置阈值，或屏态在两次采集之间发生变化时，快照标记为不一致。模型可以使用有效截图继续做联调，但该快照不能用于依赖 UI dump 的正式指标。

### 21.3 Agent 动作闭环

Agent 每一轮接收任务目标、当前快照、已完成步骤和最近失败原因。模型输出一个结构化动作，执行器验证动作类型和参数后调用设备。执行器返回结果后，观察器重新采集快照，页面确认模块判断目标是否满足，Agent 再决定继续导航或结束导航。

动作执行失败时不自动重复原动作。系统先检查设备状态和页面是否变化，再根据任务允许的恢复策略选择重新观察、重新定位、回到安全起点或终止任务。每次重试都写入独立的动作记录，记录重试原因和前后快照。

### 21.4 目标页面确认

页面确认采用必需条件全部满足、禁止条件全部不满足的规则。路径条件用于区分页面层级，文本条件用于识别页面标题和关键内容，稳定标识用于识别按钮、输入框和商品卡片。页面规则可以设置最小证据数量，避免只凭一个通用文本确认页面。

页面确认结果包含规则明细。每条规则分别记录匹配值、匹配来源和失败原因；当规则之间冲突时，结果为未确认。未确认不会触发 UX 正式统计，但会保留最后一张截图和 UI dump 供导航问题分析。

### 21.5 UX 检测和结果验证

UX 检测器首先对目标页面截图进行模型推理，模型只负责发现验收集允许的问题和问题区域。解析器将模型输出转换为统一结构，并校验问题类型、bbox、置信度和可选验证建议。布局验证或交互验证只处理模型已经发现的候选，不重新生成未在模型结果中的问题。

最终判定由模型证据、页面证据和任务验证要求共同决定。模型明确发现且截图证据充分的问题可以直接保留；需要确认滚动、控件归属或设备状态的问题进入辅助验证；无法确认的问题保留为未确认。原始模型结果永远不被后处理覆盖。

## 22. 非功能需求详细说明

### 22.1 性能测量方法

动作耗时从执行器发出动作命令开始，到动作后截图和页面观察完成为止。模型耗时从请求发送开始，到结构化响应解析完成为止。端到端检测耗时从目标页面确认成功开始，到最终结果和证据索引写入完成为止。每个时间段都写入任务结果，汇总时可以区分模型、设备和应用耗时。

### 22.2 准确性和统计方法

导航准确率以页面规则判定为准，不以 Agent 自述为准。UX 准确性以人工真值为准，不以模型置信度为准。正式报告同时给出任务总数、有效样本数、未确认数、TP、FP、FN、TN、precision、recall、accuracy 和 unknown rate，保证验收人员能够复算结果。

### 22.3 稳定性和恢复

系统应支持批量任务连续执行。单个任务的失败、超时或模型错误写入终态后，调度器继续执行下一个任务。设备清理和应用重置应有明确的开始和结束记录，清理失败时暂停批量执行并提示人工复位，不能继续在未知设备状态上执行后续任务。

### 22.4 可维护性

任务规则、设备配置、模型配置和结果 schema 分离保存。规则变化不需要修改设备执行器，设备变化不需要修改模型解析器。每次运行记录代码版本、任务版本、模型版本和提示词版本，便于问题复现和版本回滚。

## 23. 可行性分析详细说明

### 23.1 技术路线可行性

HarmonyOS HDC 和 uitest 提供设备连接、应用启动、触控输入、截图和页面层级导出能力，能够满足动作执行和状态采集要求。视觉模型适合处理截图中的布局、文字和图片问题，页面结构适合处理控件存在性和布局关系。两类信息结合后，可以同时支持页面导航和 UX 问题检测。

### 23.2 工程实现可行性

系统采用模块化接口。任务管理器输出结构化任务，Agent 输出结构化动作，执行器输出设备结果，观察器输出快照，页面确认输出到达状态，检测器输出 UX 结果。任一模块替换时，只要保持接口字段不变，就不会影响其他模块。该方式适合在测试集持续增加时迭代。

### 23.3 环境和资源可行性

系统可运行在真机或 DevEco 模拟器。模拟器适合批量回归和故障复现，真机适合验证折叠机构、系统输入法和真实渲染差异。正式验收需要预先准备可安装应用、解锁设备、可复位初始状态、可用测试数据和稳定模型服务；这些条件由测试环境建设侧提供。

### 23.4 进度可行性

设计阶段可以先冻结任务格式、结果格式、页面确认规则和指标口径，再等待测试集补齐具体应用与页面。测试集数量增加只会增加任务实例，不会改变主流程。已有样本用于验证接口和证据归档，不能替代最终测试集的准确率统计。

### 23.5 主要风险

风险包括模型服务不可用、页面数据为空、页面路径不稳定、屏态切换后渲染未完成、截图和页面结构不同步以及视觉问题无法由布局树解释。系统通过任务前置检查、快照一致性校验、阶段级错误码、原始证据保留和未确认状态处理这些风险。风险发生时必须保留事实和证据，不能用默认成功值填补结果。

## 24. 验收执行顺序

正式执行按照设备检查、应用启动、任务导航、页面确认、目标截图、UX 检测、必要验证、结果归档和指标汇总的顺序进行。每一步都有输入、输出和终止条件。页面确认失败时停止当前任务的 UX 检测；模型结构错误时停止当前候选的后处理；设备异常时停止当前任务并执行清理。

验收人员复核任务时，应先查看任务输入和页面到达证据，再查看模型原始响应，最后查看最终 verdict 和耗时。报告中不能只展示带框截图，也不能把调试用的人工框选结果当作模型输出。

## 28. 接口和状态约束

| 接口 | 请求关键字段 | 响应关键字段 | 失败状态 |
|---|---|---|---|
| Agent action | type、args、reason | actionId、status、elapsedMs | invalid_action、tool_error、timeout |
| Snapshot | runId、snapshotId、deviceState | imagePath、layoutPath、hash | screenshot_failed、layout_failed |
| Page Oracle | targetPage、snapshot | reached、matchedRules、failedRules | page_not_reached、insufficient_evidence |
| UX model | image、prompt、model | overall、issues、usage | model_timeout、http_error、schema_invalid |
| UX verdict | issue、layout、validation | verdict、confidence、evidence | unknown、verification_failed |

任务状态只能按 `INIT → DEVICE_READY → APP_READY → OBSERVED → NAVIGATING → PAGE_REACHED → DETECTING → VERIFIED → ARCHIVED` 顺序推进。设备错误、页面未到达和模型结构错误可以从相应状态进入 `FAILED`，但已经写入的快照和动作轨迹不能删除。重试必须创建新的 attempt 编号，并保留原始失败状态。
