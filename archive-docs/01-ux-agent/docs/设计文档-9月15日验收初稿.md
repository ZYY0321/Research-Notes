## 1. 建设背景与问题定义

折叠屏、双折叠、三折叠和平板会改变应用的可用宽度、窗口高度、分栏方式和交互区域。同一个页面在单屏、展开、半折和横屏状态下可能出现不同问题：标题或按钮被裁切，图片/视频比例失真，内容被底部导航或键盘遮挡，页面没有响应横屏布局，或者页面切换后仍保留错误的窄屏布局。传统人工测试需要逐设备打开应用、逐步操作和截图，问题定位依赖经验，难以形成可重复的统计结果。

本项目建设一个运行在 HarmonyOS 真机或模拟器上的 GUI Agent。Agent 接收自然语言任务，理解目标，选择下一步动作，通过 HDC/uitest 启动应用并执行点击、滑动、输入和返回；执行器完成动作后，观察器返回新的截图和 UI 树；Agent 根据动作前后的变化决定继续导航还是确认已到达目标页面；到达目标页面后，Agent 再调用 UX 检测器判断当前页面是否存在多设备 UX 问题。当前阶段以“文字截断及其误报过滤”为主要落地点，并为大图大字、横竖屏、键盘避让、固定覆盖层等问题保留扩展接口。

项目不是自动修复应用，也不是替代华为官方测试服务。它的交付目标是：在给定设备、应用和评测集上，稳定到达目标页面，发现页面中的 UX 问题，给出可回溯的证据，并用统一指标证明结果。

## 2. 建设目标与成功标准

### 2.1 业务目标

1. 用高级指令描述任务目标，用低级指令描述具体动作，使页面到达任务能够被统一执行和评估。
2. 覆盖直板、平板、双折叠、宽折叠和三折叠设备的不同屏态。
3. 将“模型看起来像截断”与“布局/滚动能够解释的可恢复裁剪”区分开。
4. 对每条结果保存原始截图、模型 bbox、布局证据、滑动前后状态和判定理由。
5. 输出一份可由验收人员复核的报告，而不是只有模型截图的演示页。

### 2.2 验收成功标准

| 类别 | 指标 | 目标 |
|---|---|---:|
| 页面到达 | 低级指令正确到达目标页面 | ≥95% |
| 页面到达 | 高级指令正确到达目标页面 | ≥80% |
| UX 检测 | 成功到达检测页面后，正确发现 UX 问题 | ≥95% |
| 响应时间 | 每个动作平均响应时间 | ≤3 秒 |
| 响应时间 | 单步最大响应时间 | ≤5 秒 |
| 端到端 | 三层界面内完成一次检测 | ≤10 秒 |

“正确”必须以冻结评测集中的人工真值为准。对无法确认的结果保留 `unknown`，并单独报告其数量；不得为了提高准确率把 unknown 静默算成正确或错误。

## 3. 需求分析

### 3.0 探索阶段与验收阶段的关系

本项目包含两个不同目的的运行阶段。探索阶段不是验收阶段的替代品。探索阶段允许 Agent 在给定应用和初始页面中自主浏览，记录页面层级、可操作控件、设备状态变化和疑似 UX 问题，用于构建任务、截图、轨迹和人工标注。验收阶段不再允许 Agent 任意探索，而是从冻结的高级指令或低级指令开始，按照同一初始状态复现目标页面，再对该页面执行检测。

因此，“到达商品卡片”与“检测商品卡片上的问题”是两个连续但可分开的动作。页面到达指标回答的是 Agent 是否找到了正确的商品卡片；UX 指标回答的是到达后是否正确发现卡片上的截断、拉伸或遮挡。探索阶段可以发现商品卡片并产生样本，验收阶段必须用任务指令稳定复现该商品卡片。两阶段共用同一套截图、UI 树、动作和结果数据格式，但统计分开进行。

探索阶段的产物是页面图谱、动作轨迹、候选问题和人工标注；验收阶段的产物是任务成功/失败、目标页面快照、检测 verdict、耗时和统计结果。这样既解释了为什么前期需要“探索收数据”，也解释了为什么最终验收必须“根据指令到达页面”。当前仓库已经有通用任务执行和工具轨迹文件，但尚未实现目标页面 oracle、高低级指令字段和正式到达率统计；这些是接入团队测试集时需要补充的验收层。

### 3.1 用户角色

**测试集/环境构建人员**：构建缺陷 App、页面状态、设备或模拟器配置，并提供测试集和人工真值。
**项目执行人员**：配置模型和设备，运行任务，分析日志，生成验收材料。
**验收人员**：根据任务目标、低级/高级指令、截图证据和统计结果复核系统是否达标。
**模型服务维护人员**：维护校园网内 UX 检测接口和模型版本。

### 3.3 F01：设备连接与识别

系统启动时调用 HDC 查询目标设备，并根据设备属性识别形态。`device-profile.ts` 已实现以下映射：物理型号前缀 `ALT/ICL/DEL`、模拟器产品型号 `Mate X5/Mate X6/Mate X7` 和设备类型 `foldable` 对应双折叠；物理型号前缀 `HOP`、模拟器产品型号 `Pura X Max` 和设备类型 `widefold` 对应宽折叠；物理型号前缀 `GRL` 和设备类型 `triplefold` 对应三折叠；`phone/tablet` 归入普通设备。识别结果包括 `formFactor`、屏幕分辨率和可用 fold state。

识别失败时系统不能默认当作三折叠；应记录设备原始信息并退化到单屏检测。验收报告必须记录设备型号、系统版本、HDC 版本和最终命中的设备规则。

### 3.4 F02：应用启动与复位

运行器根据任务中的应用名或 bundle/ability 启动被测 App。每个任务开始前将设备恢复到约定初始状态；任务结束后通过返回和回到 Home 的逻辑清理会话，避免前一个任务的页面栈影响下一个任务。启动失败、应用闪退、黑屏和权限弹窗均记录为环境/执行失败，不进入 UX 准确率分母，除非验收方明确要求将其计入页面到达率。

### 3.5 F03：自然语言任务执行与页面到达

高级指令只说明目标，例如“进入编辑页面并检查多设备 UX 问题”；低级指令拆成“打开应用”“点击编辑”“点击名称输入框”等单步动作。Agent 在动作循环中读取当前截图和简化 UI 树，选择 `harmony_open_app`、`harmony_tap`、`harmony_swipe`、`harmony_type_text` 或 `harmony_press_key`。

目标页面判定由评测集定义，而不是由模型自由解释。判定条件可包含页面标题、稳定 id/key、特定控件存在、页面路径和截图区域。这个 oracle 当前尚未在 `src/types.ts` 和 `runner.ts` 中实现，现有代码只接收一个 `task` 字符串并记录工具调用；因此“只有满足目标页面条件后才计入 UX 分母”是本设计新增的待实现能力，不是现有代码已经完成的功能。

### 3.6 F04：单步闭环观察

每个动作完成后，运行器保存动作开始时间、动作结束时间、截图时间、UI dump 时间和错误信息。`image` 模式只采集截图；`layout` 和 `slide` 模式必须采集与截图对应的 UI 树。截图和 UI 树通过同一 snapshot id 关联，禁止在折叠切换或页面变化后复用旧布局树。

若设备切换状态后仍在渲染，系统应等待稳定条件或记录渲染等待时间；如果无法确认截图和 UI 树属于同一页面，快照标记为无效，不能拿来证明检测正确。

### 3.7 F05：多屏态遍历

`ux-detection.ts` 按设备形态取得状态配置。普通设备不切换；双折叠和宽折叠执行 `single/dual`；三折叠执行 `single/dual/triple`。底层优先使用 `DEVECO_HOME/tools/emulator/Emulator -foldedState`，失败后调用 `hdc shell hidumper -s 4607` 的回退指令。每种屏态单独保存截图、布局树、模型结果和最终结果。

多屏态遍历是一次 UX 检测调用内部行为，不应由 InputValidationAgent 把“单屏检查”“展开检查”“三屏检查”拆成三个重复 UX 步骤，否则会造成重复日志、空目录和不必要的模型调用。

### 3.8 F06：图片模型检测

模型阶段接收截图和固定检测提示词，返回 `pred_json`，其中包含 `overall` 和 `issues`/`pred_bbox_issues`。模型只负责发现疑似区域，不负责判断该区域是否能通过滚动恢复。原始响应原样写入 `model_result.json`，用于追溯模型漏报、误报和 bbox 偏移。

当前 `detectImage` 默认使用 DashScope 兼容接口，默认 base URL 为 `https://dashscope.aliyuncs.com/compatible-mode/v1`，支持用 `UX_DETECT_BASE_URL` 覆盖，并请求 `/chat/completions`。没有校园网或模型不可用时，系统使用 `UX_DETECT_FIXTURE` 或保存的模型 JSON 运行离线验证。你提供的 lemon `/detect` 是另一种 multipart 上传接口，若验收指定该服务，需要新增适配器完成图片上传、`pred_json` 解析和错误码转换；不能把它写成当前代码已经直接接通。离线 fixture 结果与在线模型结果必须分开统计。

### 3.9 F07：布局树验证

布局验证器将模型 bbox 统一转换到 layout 坐标，展平 ArkUI `children` 树，建立父子索引、祖先链、稳定 id/key 和 Text 候选。验证器优先选择真正被裁切的 Text，而不是简单选择 IoU 最大的文字节点。

判定过程如下：

1. 收集与 bbox 相交且可见的 Text、TextInput、Button、RichText 等候选。
2. 检查 Text 的 `bounds` 与 `origBounds` 是否存在显著隐藏尺寸。
3. 向上寻找第一个与 bbox 同边缘对齐的 clip、viewport、Scroll、List、Grid、WaterFlow、Swiper 或 Tabs。
4. 根据边界语义判断移动整个 Text 是否能让字符进入可见区域。
5. 将结果通过 `issue_index` 绑定回模型原始 issue，避免过滤数组后下标错位。

连续滚动视口仍有容量时为 `not_truncation`；局部不可滚裁剪、Text 自身裁剪、Swiper/Tabs 页面切换或滚动到边界仍裁切时为 `true_truncation`；owner 歧义、动态槽位、无 Text 证据或容量未知时为 `unknown`。

### 3.10 F08：主动滑动验证

`slide` 模式只处理 layout 阶段仍为 unknown 的候选。系统根据被切方向选择反向滑动，从 bbox 中心计算安全起点和固定距离；滑动后等待惯性停止，再截图并重新 dump UI 树。系统通过稳定 id/key 比较同一 Text 的滑动前后 `bounds/origBounds`，而不是重新请求模型。

滑动能使同一 Text 完整进入 viewport，则过滤为可恢复；滑动后仍保持相同裁剪关系，则保留为真实截断；截图失败、状态恢复失败、页面发生跳转或前后基线不一致，则保留候选并标记验证失败。多个候选必须在同一基线下逐个验证，恢复失败不得把偏移误当成滑动证据。

### 3.11 F09：结果归档

一次运行目录至少包含：`snapshot.png`、`snapshot_window.json`、`snapshot_ui-tree.txt`、`model_result.json`、`layout_result.json`、`slide_result.json`、`snapshot_ux.json`。`image` 模式不生成布局和滑动产物；`layout` 模式不执行设备滑动；`slide` 模式保存全部阶段结果。

每个 issue 必须包含 issue id、bbox、问题类型、屏态、模型原文、layout verdict、slide verdict、最终 verdict、证据路径和耗时。阶段失败时保留已产生的结果并设置 `overall=unknown`，不能用空数组掩盖异常。

### 3.12 F10：统计与验收

页面到达指标以任务为单位计算：

```text
低级指令到达率 = 正确到达目标页面的低级任务数 / 低级任务总数
高级指令到达率 = 正确到达目标页面的高级任务数 / 高级任务总数
```

UX 检测至少报告：

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
Accuracy  = (TP + TN) / (TP + TN + FP + FN)
```

验收单要求“正确发现 UX 问题 ≥95%”时，报告正文明确采用的分母和 unknown 处理规则，并附逐案例明细。耗时报告平均值、最大值和 P95，且区分动作执行、截图/UI dump、模型服务、layout 验证和 slide 验证耗时。

## 4. 非功能需求

### 4.1 性能需求

单步响应时间从动作请求发出到动作结果及闭环观察结果可用开始计时。模型调用、截图传输和 UI dump 的时间分别记录。对端到端三层界面检测，起点为进入目标页面并完成稳定快照，终点为最终 verdict 写入结果文件；网络和设备资源因素按验收方约定单独扣除并在报告中说明。超时任务必须保存部分日志，不能只返回“失败”。

### 4.2 准确性与保守判定

模型输出不直接作为最终真值。layout 和 slide 阶段用于降低误报；任何验证阶段失败都遵循“不能确认就不删除”的原则。`unknown` 是合法的中间结果，不代表代码异常。标注集必须包含正例、负例、可滚动误报、固定底栏遮挡、图片文字、省略号、无 Text 的 WebView/Canvas 和页面切换等边界案例。

### 4.3 稳定性与可恢复性

任务失败后应能回到设备 Home 并继续下一个任务；单个任务的模型超时不得导致整个 benchmark 进程丢失前面结果。折叠切换失败时记录设备状态，禁止继续用未知状态截图作为某一屏态结果。滑动恢复失败时保留原始 issue 并将该任务标记为需复核。

### 4.4 可维护性与可扩展性

主流水线只有一套，通过 `--mode=image|layout|slide` 选择执行截止阶段。模型检测、布局验证、折叠切换、主动滑动和报告生成保持独立模块。新增任务只修改 JSON；新增设备只扩展设备规则；新增 UX 类型通过问题类型、提示词和验证器接口扩展，不复制 runner。

### 4.5 安全与数据管理

模型 URL、API Key、账号和测试 App 登录信息不得写入 Git、报告或截图。在线模型只发送必要的截图；运行目录按时间和任务 id 隔离。报告中只保留环境变量名和模型版本，凭据由本地部署人员管理。

## 5. GUI Agent 总体设计

### 5.1 Agent 的组成

本系统的核心不是单次截图分类，而是一个观察—决策—执行闭环。大脑是 OpenCode 会话中的视觉语言模型和 `prompts/gui-orchestrator.txt`，负责理解任务、读取当前观察、选择一个下一步动作和判断是否结束。观察器负责获取截图、简化 UI 树、页面路径和设备状态。执行器是 HDC/uitest 工具集合，负责把动作变成真实的启动、点击、滑动、输入或按键。页面判定器负责确认当前页面是否满足任务定义的目标条件。UX 检测器负责在目标页面上运行 image、layout、slide 三阶段。轨迹记录器保存每轮观察、决策、工具调用、工具结果、页面状态和耗时。

### 5.2 Agent 的运行闭环

```text
任务目标
  → 大脑读取任务与当前观察
  → 选择一个动作
  → 执行器调用 HDC/uitest
  → 观察器返回截图和 UI 树
  → 大脑比较动作前后状态
  → 页面判定器检查目标页面
       ├─ 未到达：继续下一轮
       └─ 已到达：调用 UX 检测器
  → 多屏态检测、结果上报、轨迹归档
```

`prompts/gui-orchestrator.txt` 已经规定了 Agent 的基本行为：每次工具调用后必须查看新的截图和 UI 树；不能因为工具返回成功就假设页面已经变化；点击、输入和滑动使用 0–1000 坐标；成功、失败或阻塞时都必须调用 `harmony_report_result`。`runner.ts` 负责创建 OpenCode session、发送任务、监听工具事件和结束会话。

### 5.3 大脑、执行器和观察器

大脑只负责决定“下一步做什么”，不直接执行 shell 命令。执行器只负责校验参数、调用 HDC 并返回设备结果，不负责理解自然语言。观察器同时提供截图和结构化 UI 树：截图用于确认视觉布局、图标、弹窗和解析缺口；UI 树用于读取文本、稳定 id/key、bounds、clickable、scrollable 和层级关系。

当前执行器由 `harmony_open_app`、`harmony_tap`、`harmony_swipe`、`harmony_type_text`、`harmony_press_key`、`harmony_ux_detect` 和 `harmony_report_result` 组成。每个动作之后自动产生新的观察，Agent 必须基于新的观察选择下一步动作。

### 5.4 页面判定器与 UX 检测器

页面判定器是导航 Agent 与 UX 检测器之间的接口。它回答“是否已经到达任务指定位置”，不回答“页面是否存在 UX 问题”。判定条件由任务提供，可组合 `pagePath`、稳定 `id/key`、目标文本、必需控件和截图区域。当前仓库尚未实现这个 oracle；`src/types.ts` 的任务结构和 `runner.ts` 的输入仍主要是一个自然语言 `task` 字符串，因此页面判定器属于本次设计新增的待实现模块。

UX 检测器是 Agent 的领域工具，不是 Agent 本身。Agent 负责把页面带到正确状态并在正确时机调用 `harmony_ux_detect`；UX 检测器负责各屏态采集、视觉模型、布局验证和主动滑动。这样页面到达率和 UX 识别率可以分别计算，也能避免把“没到商品卡片”误算成“商品卡片没有问题”。

### 5.5 轨迹记录器

一条导航轨迹应包含任务输入、初始设备状态、每轮截图和 UI 树、模型决策、工具名、工具参数、工具输出、页面判定、UX 检测调用和最终结果。当前 `runner.ts` 已写入完成的工具调用和任务 steps，并在结果中记录 actionSteps、observeSteps、toolCallCounts 和模型信息；当前缺少观察文件路径、动作起止时间、页面 oracle 结果和结构化失败原因。后续应先补齐轨迹采集和回放，再决定是否进行提示词优化、行为克隆或模型微调。

### 5.6 系统分层

```text
任务层：任务 JSON、高级/低级指令、目标页面和真值
执行层：runner、benchmark、Agent prompt、MCP 工具
设备层：HDC、uitest、截图、dumpLayout、折叠状态切换
检测层：VLM bbox、TextTruncVerifier、主动滑动
证据层：截图、UI 树、JSON、日志、统计报告
```

### 5.7 运行时序

```text
读取任务
  → 连接并识别设备
  → 启动/复位 App
  → Agent 读取截图/UI 树并选择动作
  → 执行动作并记录耗时
  → 判断是否到达目标页面
  → 为每个屏态采集同一 snapshot 的截图和 UI 树
  → VLM 输出疑似 bbox
  → layout 静态验证
  → 对 unknown 候选执行 slide 验证
  → 汇总多屏态结果
  → 写入 JSON/截图/报告
  → 上报成功或失败并复位设备
```

## 7. 可行性分析

### 7.1 技术可行性

技术链路已经在仓库中形成闭环。HarmonyArena 的 `runner.ts` 能通过 MCP 工具执行应用打开、点击、滑动、输入、返回和结果上报；`benchmark.ts` 能隔离运行多条 JSON 任务并生成 `benchmark-results.jsonl` 和 `summary.txt`。`ux-detect-runner.ts` 已实现 `--mode=image|layout|slide`，能创建运行目录、采集截图和 UI dump、调用检测编排并分别保存模型、layout、slide 和总结果。

文字截断验证不是只依赖视觉模型。布局验证器已经实现 norm1000/image/layout 坐标转换、布局树展平、Text 候选绑定、clip owner 选择、Scroll/Swiper/Tabs 语义、固定覆盖层排除、省略号防御和 unknown 规则。当前 TypeScript 回归测试 15/15 通过；showcase 已生成 31 条 C/N/U 构造案例；仓库还保存了青商城和京东商城页面的真实截图、UI 树和报告。因此软件实现具备接入团队缺陷 App 的条件。

### 7.2 设备与模拟器可行性

代码已经不是只支持单一手机。设备规则覆盖直板/平板、双折叠、宽折叠和三折叠；折叠状态模块支持单屏、双屏、三屏及半折组合。模拟器路径由 `DEVECO_HOME` 注入，优先调用 DevEco Emulator CLI，失败时回退 hidumper。只要团队提供同一套 DevEco SDK、模拟器镜像、HDC 和设备启动方式，即可复现状态切换；真机则需要 HDC 可连接、设备解锁、允许调试和对应的系统服务。

设备侧的主要风险不在“能否写调用代码”，而在截图时机和状态一致性：折叠切换后页面可能尚未渲染，截图缓存可能仍是上一屏，滑动恢复可能留下偏移。设计中因此使用独立 snapshot id、状态切换后的稳定等待、截图/UI 树配对检查和失败保留策略。正式验收需把这些环境时间单独记录，不能用静态截图替代。

### 7.3 模型服务可行性

当前代码已有 DashScope 兼容模型适配器和 fixture 适配器。你提供的 lemon `/detect` 服务属于另一套接口，若最终验收使用它，需要补充 adapter 和联调测试。两种服务都可以统一转换成内部 `pred_json`，因此可以先在无校园网环境完成数据结构、布局验证、报告和回归测试，再在校园网环境测真实模型；在线接口、模型版本和网络条件必须写入运行配置。

模型服务的工程风险包括网络不可达、超时、返回格式变化、bbox 坐标空间错误和模型把图标/空白/图片文字误框为 Text 截断。系统通过响应标准化、坐标空间声明、原始响应保存和 layout/slide 复核降低风险；模型服务本身的准确率仍必须用团队正式标注集测量，不能用 31 条构造 case 直接外推到验收数字。

### 7.4 数据与评测可行性

仓库已有 31 条构造案例和真实商城页面证据，足以先验证统计脚本、报告格式和检测流程。团队提供缺陷 App 后，只需按同一数据结构补充任务目标、低级指令、高级指令、目标页面条件、设备屏态和 UX 真值。评测集按正例/负例/unknown、设备状态、问题类型和页面复杂度分层，能够直接计算页面到达率、UX precision/recall/accuracy 及耗时。

数据风险是标注口径不一致。相同的视觉现象可能是文本截断、可滚动裁剪、固定底栏遮挡或页面切换。设计要求标注人员先给“问题是否存在”和“问题类型”，再给 bbox 和可复核证据；unknown 不得被强行标成负例。评测集冻结后，任务文件和标注文件生成 hash，报告记录版本。

### 7.5 进度可行性

9 月 15 日前可独立完成设计文档、代码架构说明、离线案例章节、环境接入说明和评测表模板；这些不依赖校园网模型或团队缺陷 App。9 月 15 日后接入团队环境，先跑 3–5 条冒烟任务，确认设备识别、状态切换、截图/UI 树配对和模型响应，再扩展到全量。9 月 30 日前重点不是继续扩展算法，而是冻结数据、跑全量、处理失败任务、统计指标和整理证据。

### 7.6 主要风险及应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 校园网外无法访问模型 | 无法测在线模型 | 先用 fixture 完成离线链路；进校园网后复跑模型 |
| 缺陷 App/设备晚到 | 无法做真机验收 | 先用商城/设置案例跑通；环境到位后只替换任务和 app |
| 折叠切换后截图错配 | 误报/漏报 | snapshot id、稳定等待、截图/UI 树同时采集 |
| 模型误框图标或空白 | 误报 | layout owner、overlay、unknown 和 slide 复核 |
| 滑动后页面未恢复 | 假阴性/假阳性 | 每次验证前建立基线，恢复失败保留 issue 并标记失败 |
| 类型检查/运行时版本漂移 | 无法启动 | 锁定 Node/tsx/依赖版本；记录 commit 和环境 |
| 样本量不足 | 指标不可信 | 报告同时列出样本数、逐条结果和置信限制 |

## 8. 测试与验收方案

### 8.1 测试层级

1. **单元测试**：坐标转换、布局解析、Text 绑定、owner 判定、overlay 过滤和空输入。
2. **离线集成测试**：截图 + UI 树 + fixture，验证 image/layout/slide 三种模式的产物和最终 verdict。
3. **设备冒烟测试**：打开 App、点击、滑动、截图、dumpLayout、折叠状态切换各至少一条。
4. **正式评测**：冻结团队测试集，重复执行并生成统计报告。
5. **回归测试**：对失败案例和边界案例重新运行，确认修复没有降低其他类型结果。

### 8.2 真实问题场景

### 8.3 验收报告结构

最终报告按以下章节生成，并为每个结论附数据来源：

1. 项目概述、目标和范围；
2. 验收依据和指标定义；
3. 软件、模型、设备、系统和网络环境；
4. 系统架构、模块职责和运行时序；
5. 测试集版本、任务结构、标注规则和真值；
6. 页面到达率统计（高级/低级分开）；
7. UX 检测统计（TP/FP/FN/TN、precision、recall、accuracy、unknown）；
8. 单步平均/最大/P95 和端到端耗时；
9. 按设备、屏态、问题类型的分层结果；
10. 典型成功、误报、漏报、unknown 和环境失败案例；
11. 已知限制、未完成项和复现步骤；
12. 附件清单：任务 JSON、日志、截图、UI 树、模型响应和结果 JSONL。

## 11. 验收原文归档及设计响应

以下内容按照本项目收到的验收要求原文归档，后面的“设计响应”说明系统如何实现或还缺什么。

**验收要求一：**“评测集每个任务中，当开发者以任务目标加低级指令作为任务输入时，正确到达页面的准确率应该达到 95%。”

**设计响应：**任务文件必须同时保存任务目标、低级指令、目标页面判定条件和最终页面快照。Agent 在 `src/runner.ts` 中通过 OpenCode 会话调用 HDC 工具执行动作；每个动作之后返回截图和简化 UI 树。当前仓库已有任务执行和 benchmark 机制，但正式评测还需要团队提供带有“目标页面”和“页面成功判定”的测试集。现有任务多数只有自然语言 `task` 字段，不能直接证明 95% 页面到达率，因此目标页面真值是必须补充的数据字段。

**验收要求二：**“评测集每个任务中，当开发者以任务目标加高级指令作为任务输入时，正确到达页面的准确率应该达到 80%。”

**设计响应：**高级指令是对任务目标的概括，系统需要将其拆解成动作序列并在动作循环中完成。当前 HarmonyArena 已具备自然语言任务执行能力和动作轨迹记录，但仓库没有独立的“高级指令正确率”统计字段，也没有把高级指令与低级指令配成同一条评测样本。正式评测集需要增加 `instruction_level`、`high_level_instruction`、`low_level_instructions` 和 `target_page` 字段，报告分别统计两种指令的到达率。

**验收要求三：**“在评测集每个任务中，成功到达检测页面后，GUI Agent 正确发现 UX 问题的准确率应大于等于 95%。”

**设计响应：**页面到达由 Agent 负责，UX 检测由 `ux-detection.ts` 负责，两者以目标页面快照作为接口。检测链路已经实现 image、layout、slide 三个阶段；layout 通过 UI 树验证模型 bbox，slide 对 unknown 候选执行主动滑动。正式统计需要将页面到达失败任务排除在 UX 检测分母之外，并把 TP、FP、FN、TN、unknown 和问题类型写入验收报告。当前仓库的 31 条 showcase 是开发验证集，不等价于团队正式评测集。

**验收要求四：**“每个任务执行中，GUI Agent 执行每个动作的响应时间平均小于等于 3 秒，单步最大响应时间不超过 5 秒。”

**设计响应：**动作请求、HDC 执行、截图/UI 树返回和 Agent 下一步决策必须分别记录时间戳。当前 `runner.ts` 已有任务级日志和超时处理，但还没有形成满足验收格式的动作耗时汇总表。正式运行时需新增动作级 CSV/JSONL 统计，并区分设备动作时间、观察采集时间和模型决策时间。

**验收要求五：**“排除网络和资源这类非模型因素，在检测被测 APP 的三层界面中的 UX 问题时，端到端时间小于等于 10 秒。”

**设计响应：**三层界面在本项目中对应一次目标页面稳定快照、模型检测和布局/滑动复核。屏态遍历不能被重复拆成多个 UX 步骤，否则会重复请求模型并放大耗时。端到端计时应从目标页面稳定快照开始，到最终 verdict 写入结束；网络请求、设备渲染和文件传输时间单独记录并按验收约定排除。当前代码已经有阶段边界，但需要在团队环境中补采真实耗时。

## 12. 指令到页面、轨迹和微调范围

“根据指令到达对应位置”属于本项目设计范围，不是 UX 检测之外的附属工作。它决定检测页面是否正确，直接影响 95% 和 80% 两项页面到达指标。设计上，任务目标和指令进入 Agent；Agent 通过观察截图/UI 树选择工具；每次工具调用生成一条轨迹记录；当目标页面条件满足时才进入 UX 检测。

当前代码已经具备轨迹的基础形态。`runner.ts` 会保存任务上下文、工具调用和结果，`benchmark.ts` 会保存每个任务的运行结果，MCP 工具返回截图/UI 树作为下一步观察输入。但当前仓库没有发现独立的轨迹数据集、轨迹质量标注、行为克隆训练脚本、LoRA/监督微调脚本或轨迹微调配置。因此“轨迹微调”不能在设计文档里伪装成已经实现的功能。

本项目现阶段应把轨迹微调定义为后续增强项：首先保存成功轨迹和失败轨迹；其次给失败轨迹标注失败原因，例如目标识别错误、点击坐标错误、返回键误用、折叠状态选错、页面等待不足；最后再决定采用提示词约束、动作示例检索、行为克隆或模型微调。要继续做这部分，需要团队提供已有轨迹格式、成功/失败标签、可训练模型和训练脚本；在这些材料未到位前，最小可交付是完成轨迹采集、回放和质量分析，而不是声称已经完成微调。

## 13. 当前代码与需求的差距

代码已经覆盖设备连接、应用启动、点击/滑动/输入、截图/UI 树观察、三阶段 UX 检测、结果归档和 showcase 回归。代码尚未完全覆盖验收所需的三件事：第一，正式评测集中的高级/低级指令配对及目标页面真值；第二，按验收口径输出动作级响应时间和端到端耗时；第三，轨迹质量标注与微调训练流程。这三项应在设计中写成明确的后续实现任务，并向团队索取现有测试集、轨迹数据和历史会议结论。
