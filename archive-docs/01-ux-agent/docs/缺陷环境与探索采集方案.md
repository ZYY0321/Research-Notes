# 缺陷环境与探索采集方案

## 一、目标

在团队缺陷 App 尚未交付时，先用仓库已有 HarmonyOS App 和可控页面构造出一套能跑通的探索—验收闭环。该闭环不冒充最终验收数据，作用是验证任务格式、轨迹记录、页面判定、UX 检测、证据归档和统计脚本。

## 二、探索采集流程

探索从固定初始状态开始。Agent 先打开应用，观察截图和 UI 树，逐步浏览首页、列表、分类、详情、购物车、我的、编辑页、弹窗和输入页。每个动作保存操作前后截图、UI 树、工具名、坐标、输入参数、耗时和页面变化。发现疑似 UX 问题后，人工标记问题位置、问题类型、设备状态和复现动作。探索结束时形成一个可复现任务，而不是只保存一张问题截图。

一个完整样本至少包含：初始状态、动作序列、目标页面说明、目标页面判定条件、每种屏态快照、人工 UX 真值、模型候选和复现备注。

## 三、验收回放流程

验收运行读取冻结任务，不允许根据结果临时修改指令。Agent 从初始状态执行高级指令或低级指令，直到目标页面判定条件满足或任务失败。只有目标页面确认成功后才启动 UX 检测。检测结果与探索阶段人工真值比较，分别统计页面到达率和 UX 识别率。

## 四、建议构造的缺陷页面

第一类是商品卡片标题裁切。页面展示长商品名，卡片宽度在单屏和折叠展开状态下变化，使标题最后一个字被卡片边界裁掉。该场景用于验证 bbox、Text、局部 clip 和不可滚容器判定。

第二类是可滚列表误报。列表底部只显示部分商品标题，但向上滑动后完整显示。该场景用于验证 layout 阶段过滤和 slide 阶段恢复，不应被判为真实截断。

第三类是固定底栏遮挡。底部导航或购物车栏覆盖背景列表文字；底栏自身文字完整。该场景应归为背景遮挡，不计入文本截断。

第四类是输入框和键盘。点击商品搜索或编辑输入框，弹出键盘后保存按钮或输入文字被遮挡。该场景用于验证动作触发后的页面状态，而不是只对初始截图检测。

第五类是横屏布局。横屏后标题、按钮和图片仍按竖屏尺寸布局，出现截断、重叠或图片拉伸。该场景用于验证旋转/状态切换后重新采集截图和 UI 树。

第六类是折叠状态重排。单屏使用单列卡片，展开态应改为双列或三列；缺陷版本保持旧布局或出现中缝遮挡。该场景用于验证 foldState 配对和页面布局变化。

第七类是弹窗和侧栏。弹窗自身标题被裁掉，背景页面文字被弹窗遮挡。系统应只审查弹窗自身文字，排除背景遮挡。

第八类是 WebView/Canvas 自绘文字。截图中可看到文字，但 UI 树没有 Text 节点。系统应保守输出 unknown，不能因为无法绑定 Text 就强行判定正常或截断。

## 五、需要团队明天确认的五句话

第一句：你们最终验收的任务，是已经给定目标页面的“检测任务”，还是要求 Agent 从自然语言目标自行操作到页面后再检测？

第二句：探索阶段产生的页面、动作轨迹和人工问题标注，是否就是验收阶段任务集的来源？如果是，团队现有文件在哪里？

第三句：每个任务的“到达页面”由什么判定，是页面截图人工确认、UI 树中的 id/key、pagePath，还是三者组合？

第四句：当前所说的“轨迹微调”具体是保存并回放轨迹、优化提示词，还是要训练/微调一个动作模型？已有轨迹和脚本在哪里？

第五句：验收使用的设备和缺陷 App 是否已经固定，还是需要我们先用现有商城/设置 App 构造一套替代环境？
