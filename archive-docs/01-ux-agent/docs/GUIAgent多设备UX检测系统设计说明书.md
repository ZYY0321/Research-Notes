## 1 文档概述

### 1.1 编制目的

本文档用于说明 GUIAgent 多设备 UX 检测工具的建设目标、需求、系统架构、核心算法、接口、运行方式和验收方法。文档面向项目交付和验收，不描述具体代码实现、实验过程或内部开发记录。

系统以任务为入口，自动完成应用启动、页面找寻、目标页面确认和多设备 UX 问题检测。设计目标是将页面导航能力、页面结构分析能力、视觉识别能力和验收报告能力组合为一套可重复执行的工具。

### 1.2 系统范围

系统覆盖以下工作范围：

1. 读取应用、设备、任务、指令和目标页面规则；
2. 连接 HarmonyOS 真机或模拟器并识别设备状态；
3. 根据高级指令或低级指令执行页面操作；
4. 通过页面规则确认目标页面；
5. 在手机、平板、折叠和多折叠屏态下采集页面快照；
6. 检测大图大字、页面截断、媒体拉伸、横屏适配和避让异常；
7. 输出问题类型、问题区域、设备屏态和证据；
8. 统计页面到达率、UX 问题发现准确率和响应时间；
9. 生成逐任务报告和项目验收报告。

系统不负责修改被测应用，不改变被测应用的业务数据和页面代码。

### 1.3 术语和缩写

| 术语 | 定义 |
|---|---|
| GUIAgent | 能够理解图形界面、规划路径并调用设备操作的智能代理 |
| 高级指令 | 对整个任务目标的概括性自然语言描述，仅定义要完成什么 |
| 低级指令 | 对任务中单个具体操作的自然语言描述，对应一步可执行动作 |
| 目标页面 | 任务规定的 UX 检测页面 |
| 页面确认 | 通过页面标题、文本、控件和结构判断是否到达目标页面 |
| 页面快照 | 同一采集时刻的截图、页面结构、窗口信息和设备状态 |
| 屏态 | 直板、横屏、展开、折叠、半折或分屏等显示状态 |
| 三层界面 | 应用入口、二级功能页面和三级目标页面组成的任务路径 |

## 2 建设背景与目标

### 2.1 建设背景

折叠屏、平板和大屏设备改变了应用的窗口尺寸、可用显示区域和交互方式。应用页面需要在不同设备和屏态下保持内容完整、比例正确、层次清晰和操作可用。实际使用中，设备适配问题通常集中在页面布局而非单个控件，包括文字尺寸过大、图片或视频比例改变、内容在容器边界处截断、横屏后布局没有重排以及系统栏或键盘遮挡关键操作。

传统人工测试需要测试人员在多台设备上重复打开应用、执行操作、切换屏态、观察页面并记录问题。不同人员的操作路径和观察标准容易产生差异，问题截图、页面状态和设备条件也难以保持一致，导致复现和验收成本较高。

GUIAgent 多设备 UX 检测工具将自然语言任务执行与 UX 检测结合起来。系统先把应用带到指定页面，再在规定设备和屏态下进行页面检测。导航、观察、问题分析和报告生成采用统一任务编号和页面快照关联，从而形成完整的验收链路。

### 2.2 建设目标

系统面向 TOP 225 应用典型场景，支持复现和检测不低于 80% 的多设备 UX 问题场景。检测范围包括大图大字、页面截断、视频图片拉伸、未适配横屏、折叠状态适配和避让异常。

### 2.3 系统目标

系统需要同时满足以下目标：

1. 支持高级指令和低级指令两种页面导航方式；
2. 支持手机、平板、折叠、双折叠和三折叠设备；
3. 支持竖屏、横屏、折叠、展开、半折和分屏状态；
4. 通过视觉识别发现问题，通过页面结构和设备状态确认问题；
5. 记录从任务输入到最终结论的完整证据；
6. 以统一指标评价页面到达、UX 问题发现和响应时间。

### 2.4 设计原则

系统按照任务驱动、观察后行动、导航检测分离、多证据判定和模块化扩展原则设计。

任务驱动要求应用、设备、指令、目标页面和问题类型均由任务定义。观察后行动要求每次动作完成后重新采集页面状态。导航检测分离要求页面是否到达与页面是否存在问题分别判定。多证据判定要求视觉候选与页面节点、窗口区域和设备状态结合。模块化扩展要求新增应用、设备或问题类型时不改变任务主流程。

## 3 需求分析

### 3.1 用户角色

| 角色 | 工作内容 |
|---|---|
| 测试设计人员 | 编写任务、指令、目标页面规则和问题类型 |
| 测试执行人员 | 配置设备和应用并执行检测任务 |
| UX 质量人员 | 复核问题类型、问题区域和证据 |
| 验收人员 | 检查指标、报告和逐任务结果 |
| 系统维护人员 | 管理设备、模型、规则和运行配置 |

### 3.2 业务流程

测试人员首先定义应用、设备和任务，然后选择高级指令或低级指令。系统连接设备并启动应用，GUIAgent 按任务要求执行动作。每次动作后，系统重新采集截图和页面结构，并检查目标页面规则。目标页面确认后，系统按照指定屏态执行 UX 检测，最后生成问题明细和验收汇总。

### 3.3 功能需求

| 编号 | 功能 | 需求说明 | 输出 |
|---|---|---|---|
| FR-01 | 任务管理 | 加载、校验、编号和调度任务 | 任务实例 |
| FR-02 | 应用管理 | 启动应用、恢复初始状态和关闭会话 | 应用状态 |
| FR-03 | 设备管理 | 识别设备、分辨率、方向和折叠状态 | 设备档案 |
| FR-04 | 指令执行 | 执行高级指令和低级指令 | 动作轨迹 |
| FR-05 | 页面观察 | 采集截图、页面结构和窗口信息 | 页面快照 |
| FR-06 | 页面确认 | 判断是否到达目标页面 | 页面结果 |
| FR-07 | 多屏态检测 | 在不同设备状态下执行同一页面检测 | 屏态结果 |
| FR-08 | 问题发现 | 识别目标页面中的 UX 问题 | 问题候选 |
| FR-09 | 问题分类 | 判断问题类型、对象和区域 | 问题明细 |
| FR-10 | 证据归档 | 保存任务、动作、快照和判定依据 | 任务证据包 |
| FR-11 | 统计报告 | 计算验收指标并生成报告 | 汇总报告 |
| FR-12 | 场景扩展 | 通过配置和规则扩展应用、设备和问题类型 | 扩展配置 |

功能需求围绕一次完整检测任务形成闭环：任务管理定义检测对象和验收边界，运行时控制按阶段推进任务，设备与观察能力取得真实页面状态，模型和规则完成问题分析，报告模块将过程证据组织成验收结果。

任务与环境管理负责建立可重复的起始条件。系统读取应用包、启动入口、设备档案、指令和检测要求，为任务生成唯一标识；启动被测 APP、处理任务允许的权限弹窗、清理上一项任务遗留的焦点和临时窗口，并采集初始快照。设备档案统一记录设备类型、系统版本、分辨率、窗口大小、方向、折叠状态和系统占用区域，同时提供坐标转换与问题分层所需的信息。

导航与页面确认分为高级指令和低级指令两条路径。高级指令由 GUIAgent 根据任务目标规划动作，低级指令由系统按照给定顺序执行；两条路径共享动作校验、动作后观察、页面确认和结果归档流程。每个动作均保留动作前、动作后两个观察点，系统结合截图、页面结构和页面规则判断页面是否发生预期变化，不以设备命令返回成功作为页面到达依据。页面观察同时采集截图和页面结构，使用统一快照编号关联控件文本、稳定标识、父子层级、边界和可操作属性。

多屏态检测与问题分析在目标页面确认后执行。系统按任务要求切换横屏、折叠、展开、半折或分屏状态，每次切换后重新获取窗口和页面快照。视觉识别负责发现疑似异常区域，结构分析负责确认区域对应的页面对象、容器边界和窗口关系，问题分类据此区分大图大字、截断、拉伸、横屏适配和避让异常。

证据归档与报告生成贯穿任务全程。任务原文、设备档案、动作参数、动作前后快照、模型响应、问题区域、规则判断和报告索引共同组成任务证据；系统在逐任务结果校验后，按指令级别、设备类型、屏幕状态和问题类型汇总指标，并支持从汇总数字定位到具体任务和截图。

场景扩展通过配置和规则接入。新增 APP 通过任务和页面规则接入，新增设备通过设备档案和屏态控制接入，新增 UX 问题通过问题类型、识别要求和判定规则接入，任务执行、快照关联和报告结构保持稳定。

| NFR-02 | 页面到达 | 低级指令准确率 95%，高级指令准确率 80% |
| NFR-03 | 问题发现 | 到达检测页面后，UX 问题发现准确率不低于 95% |

| NFR-06 | 稳定性 | 单任务异常不影响批量任务继续执行 |
| NFR-07 | 可追溯性 | 结果能够回溯到任务、设备、动作和页面快照 |
| NFR-08 | 可扩展性 | 支持新增设备、屏态、模型和问题类型 |
| NFR-09 | 安全性 | 凭据与敏感数据按权限管理 |

### 3.5 准确性与性能

页面到达准确性考察 GUIAgent 是否把应用带到任务规定的页面；UX 问题发现准确性考察系统在页面已经确认后，是否正确发现问题并给出对应类型。两项结果分别统计，避免导航错误混入 UX 检测结果。性能指标分为动作级和任务级：动作级衡量一次点击、滑动、输入或按键从发出到完成动作后观察的时间，任务级衡量三级目标页面确认后完成 UX 检测和报告生成的时间。

### 3.6 稳定性与可追溯性

任务之间相互隔离，单项任务异常不得改变后续任务的初始条件；设备、应用、模型和报告模块均返回明确状态，运行时据此决定继续、恢复或结束。汇总报告中的任务数量、成功数量和指标能够回到逐任务结果，逐任务问题能够回到对应截图、页面结构和动作轨迹，动作轨迹能够回到任务输入和设备环境。

### 3.7 可扩展性与安全性

新增应用不复制整套运行逻辑，新增问题类型不修改页面导航流程，新增设备不改变任务和报告字段，统一接口和配置管理负责扩展。认证信息由环境变量或安全配置中心提供，报告只记录服务标识和版本信息；测试截图和页面结构按项目权限存储，导出的验收材料只包含任务验证所需内容。

### 3.8 需求约束

系统检测入口必须是已经确认的目标页面，页面确认规则由任务提供，不能仅凭模型自然语言判断。截图、页面结构和窗口信息必须属于同一页面状态，坐标必须绑定到当前页面快照和当前屏态，验收统计按照任务书定义的页面到达率和问题发现准确率执行。

## 4 可行性分析

### 4.1 技术方案选择

| 方案 | 适用能力 | 局限 | 采用方式 |
|---|---|---|---|
| 纯视觉分析 | 发现图片文字、视觉变形和布局表现 | 难以解释控件层级和滚动关系 | 作为问题候选入口 |
| 纯页面结构分析 | 获得节点、边界、文本和层级 | 无法覆盖图片文字和 Canvas 内容 | 作为结构证据 |
| 视觉与结构融合 | 同时利用页面外观和组件关系 | 需要统一坐标和快照 | 作为核心检测方案 |
| 固定脚本导航 | 单步路径稳定、执行确定 | 页面变化后维护成本高 | 支持低级指令 |
| 纯模型自由导航 | 适应性强、适合自然语言目标 | 动作约束和过程一致性不足 | 不作为单独方案 |
| GUIAgent 任务编排与运行时控制层 | 兼顾目标理解、动作约束和过程记录 | 需要任务和页面规则 | 作为核心导航方案 |

### 4.2 技术可行性

HarmonyOS 设备具备应用启动、输入事件、截图、窗口信息和 UI 自动化能力，可以支持页面导航和多屏态采集。页面结构能够提供控件文本、稳定标识、节点层级、位置、大小和可操作属性，适合用于页面确认和问题对象定位。

视觉语言模型能够理解页面截图中的文字、图标、图片、视频和整体布局，适合发现人眼可见的 UX 异常。结构化验证可以补充模型无法直接判断的容器边界、滚动关系、窗口占用区域和组件层级。

系统使用统一的页面快照和坐标空间关联视觉结果、页面节点和设备状态，能够实现从问题候选到问题结论的连续处理。设备适配层隔离不同设备的连接、方向和折叠控制，运行时控制层负责统一任务流程。因此，系统技术路线具备可实施性。

### 4.3 多设备适配可行性

手机、平板和折叠设备的差异可以抽象为设备类型、显示窗口、屏幕方向和折叠状态。设备适配层对外提供统一的启动、点击、滑动、输入、截图、页面结构获取和屏态切换接口，上层任务不需要感知具体控制命令。

多设备 UX 问题主要表现为内容、容器、窗口和系统区域之间的关系变化。系统使用归一化坐标描述动作和问题区域，再根据当前设备的窗口尺寸转换为像素坐标；使用关键内容和稳定控件比较屏态变化。因此，同一检测流程能够覆盖手机、平板、折叠、双折叠和三折叠设备。

### 4.4 业务可行性

高级指令适合描述完整业务目标，低级指令适合描述确定的单步操作，符合测试人员和验收人员的实际工作方式。系统把页面导航和 UX 检测分开统计，能够明确区分“没有到达目标页面”和“到达页面后没有发现问题”。

任务采用配置驱动方式，不需要为每个 APP 重写完整检测流程。应用入口、任务目标、目标页面和问题类型通过任务文件定义，通用运行时负责执行和归档，适合覆盖 TOP 225 应用的典型场景。

### 4.5 实施可行性

系统按任务管理、运行时控制、设备适配、页面观察、页面确认、模型服务、UX 判定和报告生成进行分层。各层通过统一数据对象通信，便于独立开发、联调和替换。

页面导航和 UX 检测都具有明确输入和输出。新增问题类型只需增加问题规则、识别要求和报告字段，新增设备只需增加设备档案和屏态控制，不需要改变任务和报告主结构。

### 4.6 运行和维护可行性

系统支持真机和模拟器运行，任务可以按应用、设备或屏态批量执行。每次任务生成独立任务证据包，方便定位问题、重复运行和验收复核。

设备参数、模型参数、页面规则和问题类型集中配置，运行时控制层保持稳定。后续维护主要集中在设备兼容、问题规则更新和任务场景扩展，维护边界清晰。

### 4.7 标准和合规可行性

系统的多设备 UX 检测范围参考 HarmonyOS 设计规范、折叠屏 UX 设计原则和应用生态治理应用测试要求。页面截图、设备环境、问题列表、执行时间和逐任务证据构成报告主体，与 HarmonyOS 测试服务的报告组织方式一致。

系统只采集测试任务所需的应用页面和设备信息。账号、密钥和设备认证信息由运行环境管理，不进入任务报告和导出材料。

### 4.8 可行性结论

系统所需的设备控制、页面观察、自然语言导航、视觉识别、结构分析和报告生成能力具备成熟技术基础。GUIAgent 与任务编排和运行时控制层的组合能够满足高级指令、低级指令、多设备 UX 检测和验收统计要求。方案在技术、业务、实施、运行、维护和合规方面可行。

## 5 总体架构

### 5.1 架构分层

| 层次 | 组成 | 主要职责 |
|---|---|---|
| 任务层 | 任务文件、页面规则、问题类型 | 定义检测目标和验收条件 |
| 运行时控制层 | 任务编排、状态管理、超时控制 | 组织导航、检测和结果生成 |
| Agent 决策层 | GUIAgent、导航决策、动作规划 | 理解指令并选择下一步动作 |
| OpenCode 编排层 | OpenCode 框架 + MCP stdio 工具 | 接收 Agent 动作指令，调用 MCP 工具，管理会话状态 |
| 设备与观察层 | HDC、UI 自动化、截图、页面结构 | 执行动作并采集页面状态 |
| 模型服务层 | 导航模型、UX 识别模型 | 提供结构化动作和问题候选 |
| UX 判定层 | 对象绑定、边界分析、状态对比 | 确认问题类型和影响区域 |
| 证据与报告层 | 运行目录、统计和报告 | 保存证据并输出验收结果 |

### 5.2 运行时控制层

运行时控制层是系统的任务编排和过程控制核心。它负责创建任务上下文、调用设备和模型服务、维护任务状态、限制动作和模型调用时间、触发页面确认、组织屏态检测以及写入报告。

运行时控制层不包含具体应用页面逻辑，不替代 GUIAgent 的目标理解，也不替代 UX 判定层的问题分析。应用差异由任务规则表达，设备差异由设备适配层处理，问题差异由 UX 问题规则处理。

### 5.3 Agent 决策层

Agent 决策层接收任务目标和页面观察，输出下一步结构化动作。它负责理解高级指令、选择导航路径、识别可操作控件和处理页面变化。低级指令模式下，Agent 负责将自然语言单步动作转换为可执行动作参数。

Agent 每次只选择一个动作。动作执行后，系统重新采集页面快照，Agent 根据新的页面状态继续决策。Agent 的自然语言回答不作为页面到达或 UX 问题结论，所有结论均由页面确认和 UX 判定模块生成。

### 5.4 设备与观察层

设备与观察层提供应用启动、点击、滑动、输入、按键、返回、截图、页面结构获取、窗口信息获取和屏态切换接口。该层负责坐标转换、设备连接、系统栏识别和屏幕状态维护。

### 5.5 模型服务层

模型服务层将导航和识别分成两个接口。导航接口输入任务目标、当前观察和动作历史，输出结构化动作；识别接口输入目标页面快照和检测类型，输出问题候选、区域和说明。模型服务层统一处理请求格式、图片格式、坐标格式、响应解析和调用记录。

### 5.6 UX 判定层

UX 判定层接收视觉候选、页面节点、窗口信息、屏态和问题规则，完成问题对象绑定、边界关系分析、媒体比例计算、跨屏态对比和最终结论生成。判定结果同时提供问题类型、问题区域、严重程度和证据引用。

### 5.7 技术选型

系统在编排、运行时、设备控制、模型调用和辅助验证方面采用如下技术选型。各层通过统一的任务上下文、页面快照和归一化坐标空间协作，上层不感知具体命令实现细节。

| 类别 | 选型 | 说明 |
|---|---|---|
| 编排框架 | OpenCode | 开源多模态代理编排框架，基于 stdio MCP 协议组织会话、调度工具并维护过程状态 |
| 语言运行时 | TypeScript / Node.js | 实现编排适配、设备命令封装、坐标转换和结果归档 |
| 设备控制层 | HDC（HarmonyOS Device Connector） | 通过主机侧 Shell 执行截图、页面结构获取和点击等设备操作 |
| MCP 工具层 | harmony_open_app、harmony_tap、harmony_swipe、harmony_type_text、harmony_press_key、harmony_report_result | 封装六个标准设备与结果工具，坐标空间归一化至 [0,1000] × [0,1000] |
| 模型层 | Qwen3.6 27B 视觉语言模型 | 用于页面导航决策；截断识别使用同族微调模型 |
| 辅助工具 | TextTruncVerifier（Python） | 用于文本截断三阶段验证中的第三阶段 slide 验证 |

OpenCode 编排层位于 Agent 决策层与设备与观察层之间。Agent 输出结构化动作后，OpenCode 按 MCP 协议调用对应工具，完成应用启动、点击、滑动、文本输入、按键和结果上报，并维护会话状态。设备控制层将上述工具映射为 HDC 命令；动作坐标在工具层使用 [0,1000] × [0,1000] 整数坐标，由设备适配层转换为当前窗口像素坐标后执行。导航决策与 UX 问题识别共用 Qwen3.6 27B 视觉语言模型。文本截断判定在视觉识别和布局验证之后，由 TextTruncVerifier 完成第三阶段 slide 验证。

## 6 页面找寻与任务执行设计

### 6.1 任务组成

任务由应用信息、设备信息、初始状态、任务目标、指令级别、指令内容、目标页面规则、屏态要求和检测问题类型组成。

应用信息包括包名、版本和启动入口；设备信息包括设备类型和目标屏态；初始状态描述任务开始时的应用页面和窗口状态；目标页面规则描述完成导航后必须满足的页面特征。

### 6.2 高级指令

高级指令定义完整任务目标，不规定每个具体动作。GUIAgent 根据当前页面和任务目标规划路径，选择与目标相关的控件和操作。每个动作执行后重新观察页面，并检查目标页面规则。

高级指令的评价重点是任务理解和路径规划。系统记录任务目标、每轮观察、动作选择、页面变化和目标页面确认结果，最终以是否正确到达指定页面作为页面到达结果。

### 6.3 低级指令

低级指令定义任务中的具体动作，例如打开应用、点击菜单、滑动列表、选择条目、输入文本和返回。系统按照指令顺序执行，并在每一步校验目标对象、动作参数和动作后页面状态。

低级指令的评价重点是控件定位和动作执行。系统记录每条指令的原文、解析后的动作、执行参数、动作耗时、动作前快照和动作后快照。

### 6.4 动作执行规则

动作执行前检查动作类型、目标控件、坐标范围、输入内容和当前屏态。点击动作必须落在目标控件可操作区域；滑动动作必须在窗口范围内；输入动作必须绑定当前焦点；屏态切换动作必须确认窗口发生变化。

动作完成后重新采集截图和页面结构，判断页面是否发生预期变化。动作命令返回成功但页面未变化时，运行时重新观察并交由 GUIAgent 选择后续动作。

### 6.5 页面确认

页面确认使用任务中定义的页面标题、关键文本、稳定控件标识、页面路径、控件组合和排除条件。必需条件全部满足且排除条件均不成立时，页面确认到达。

页面确认优先使用页面结构中的稳定信息，同时结合截图区域和窗口状态。对于内容相似的页面，至少使用两个相互独立的页面特征，避免只凭单段文本判断页面。

### 6.6 三层界面

三层界面由应用入口、二级功能页面和三级目标页面组成。系统分别记录每一层的进入时间、页面特征和关键动作。三级目标页面确认完成后，启动 UX 检测计时。

三层界面既用于描述业务路径，也用于定义端到端检测边界。页面导航时间和 UX 检测时间分别记录，报告中给出完整链路和分阶段耗时。

## 7 多设备适配设计

### 7.1 设备分类

| 设备 | 屏幕状态 | 适配重点 |
|---|---|---|
| 手机 | 竖屏、横屏 | 字体、系统栏、键盘和横屏布局 |
| 平板 | 竖屏、横屏、分屏 | 分栏、导航位置、内容密度 |
| 折叠屏 | 折叠、展开、半折 | 页面连续、布局重排和操作可用 |
| 双折叠屏 | 单屏、双屏展开 | 显示区域、跨屏内容和导航连续 |
| 三折叠屏 | 单屏、双屏、三屏展开 | 多断点布局、媒体比例和操作区域 |

### 7.2 设备档案

设备档案包括设备型号、系统版本、设备类型、物理分辨率、逻辑分辨率、像素密度、屏幕方向、窗口大小、系统栏区域和支持的屏态。

任务开始时加载设备档案，屏态变化后更新窗口和系统区域。设备档案用于坐标转换、截图归档、问题分类和报告分层。

### 7.3 坐标和窗口

模型和报告使用归一化坐标描述问题区域，设备执行使用当前窗口的像素坐标。转换过程考虑截图宽高、窗口偏移、系统栏、屏幕旋转和折叠状态。

每个动作坐标和问题区域均绑定到当前页面快照。屏幕方向或折叠状态变化后重新计算坐标，禁止沿用上一屏态坐标。

### 7.4 屏态切换

屏态切换由设备适配层完成。切换后系统读取新的窗口大小和屏态信息，等待页面布局稳定，重新采集截图、页面结构和系统区域。

每个屏态独立执行页面确认和 UX 检测。屏态结果既可以单独输出，也可以按任务汇总；汇总结果保留各屏态的原始问题明细。

### 7.5 跨屏态比较

跨屏态比较以关键内容、关键控件和页面状态为对象。系统比较其可见性、相对位置、大小比例、操作区域和页面层级。

允许页面根据窗口尺寸进行分栏、换行、挪移和布局重排，不允许关键内容消失、控件不可操作、业务状态丢失、内容跨折痕或系统区域遮挡。

## 8 核心算法设计

### 8.1 算法总体思路

UX 检测采用“候选发现、对象绑定、规则判定、跨状态复核”的四步方法。视觉模型负责从目标页面中发现可能的问题区域；对象绑定负责确定问题对应的文字、图片、视频或组件；规则判定负责根据问题类型检查边界、比例和避让关系；跨状态复核负责比较横屏、折叠和窗口变化前后的页面表现。

该算法将模型的开放式识别转换为结构化问题结果。模型结果提供召回能力，确定性规则提供问题解释和结果一致性。

### 8.2 输入标准化

算法输入包括页面截图、页面节点树、窗口边界、系统栏和键盘区域、设备档案、屏态和任务要求的问题类型。

系统将截图和页面结构绑定到同一页面快照，统一节点坐标、窗口坐标和图像坐标。对于经过缩放的模型输入，模型返回的区域先还原到原始截图，再进入对象绑定和规则判定。

### 8.3 候选发现

候选发现分为全局布局分析和局部对象分析。全局分析关注页面分栏、内容密度、窗口利用、系统区域和屏态变化；局部分析关注文字、图标、图片、视频、按钮、输入框和固定栏。

每个候选包含问题类型、问题区域、影响对象、现象描述和候选置信度。候选置信度用于排序和复核，不直接替代最终问题判定。

### 8.4 对象绑定

系统根据候选区域与页面节点的相交关系、节点类型、文本内容、父子关系和窗口区域确定问题对象。文字候选优先绑定文字或输入节点，媒体候选绑定图片或视频节点，避让候选同时绑定被遮挡对象和占用区域。

当一个候选覆盖多个对象时，系统根据边界一致性、中心距离和层级关系选择主要对象或拆分为多个问题。对象绑定结果写入问题证据，供问题规则和报告使用。

### 8.5 截断判定算法

截断判定比较对象的内容边界、可见边界、父容器边界和窗口边界。系统判断对象是否在自身容器中被裁切，是否被滚动视口限制，是否被固定栏遮挡，以及滚动或卡片切换后是否仍保持同一裁切关系。

文字、图标、图片和组件分别记录截断方向，包括左、右、上、下和多边截断。对象自身内容被裁切时归入截断；内容完整但被其他层覆盖时归入避让或遮挡；正常换行、正常省略和可滚动展示不归入截断。

文本截断检测在上述判定原则下，采用视觉候选、布局验证和 Slide 验证组成的三阶段处理流程。三阶段依次提高证据完整性，前一阶段的结果作为后一阶段的输入，最终形成可追溯的截断结论。

第一阶段为视觉候选（image-only）。视觉语言模型仅接收目标页面截图，按 HarmonyOS UX 检测要求识别疑似文本截断区域，输出候选结果。每个候选包含问题类型、现象描述、置信度、区域坐标和判定证据。该阶段用于提高召回，不直接作为最终结论。

第二阶段为布局验证（layout-based）。视觉语言模型同时接收页面截图和 ArkUI 布局结构（layout dump）。布局结构提供节点边界 bounds、文本内容 text 和容器层级关系，其中节点 bounds 采用 [x1,y1][x2,y2] 像素坐标。系统据此验证候选区域对应的节点是否确实存在边界裁切、容器裁切或窗口裁切，并过滤正常换行、正常省略和可滚动展示造成的误报。

第三阶段为 Slide 验证（slide-based）。对布局验证后仍标记为截断的高置信候选，系统调用 TextTruncVerifier，对对应文本节点截取局部图像（slide），再次判断文字末尾是否存在省略号或视觉截断证据。该阶段输出 true_truncation、not_truncation 或 unknown。三阶段结论一致时，形成高置信截断问题；阶段之间存在分歧时，标记为需复核。

### 8.6 媒体比例判定算法

媒体比例判定获取图片或视频的显示区域宽高比，并与资源比例或任务定义的设计比例比较。系统区分保持比例的裁剪、留白和填充展示，以及宽高被非等比改变造成的画面变形。

媒体比例异常结果包含原始比例、显示比例、变形方向、显示区域和影响屏态。横屏播放和展开屏展示同时检查播放器控制区域与媒体内容区域。

### 8.7 大图大字判定算法

大图大字指应用界面中，文字或图片的显示尺寸明显超出其所在容器的设计槽位，或在多设备适配过程中未根据屏幕分辨率、像素密度和安全区域进行合理缩放，从而导致文字遮挡相邻控件、图片溢出容器边界、操作区域被压缩或布局层级关系被破坏的问题。横屏、展开、分屏等屏态变化后出现的字号或图片尺寸过大，同样属于此类问题。

判定过程检查内容边界、父容器边界、相邻交互区域和窗口安全区域。系统重点判断内容是否超出设计槽位、覆盖相邻控件、破坏阅读顺序或使主要操作不可用。不同设备、不同像素密度和不同安全区域下，应对文字和图片进行合理缩放；缩放缺失或缩放过度，使内容与容器槽位、相邻控件或操作区域失去正确关系时，纳入大图大字问题。

字号或图片尺寸大于普通页面本身不构成问题。只有当其影响阅读完整性、层级清晰度或操作可用性，导致内容不完整、层级关系错误、操作区域被挤压或不同屏态下布局无法使用时，才判定为大图大字问题。

### 8.8 横屏和折叠适配算法

适配检测的核心问题是：同一页面在不同屏态下是否保持内容完整、操作可用和业务连续。系统在竖屏、横屏、折叠、展开、半折、分屏等各屏态下分别采集同一任务页面的快照，并建立跨状态的对象对应关系。对应关系基于稳定控件标识（accessibilityId 或 id 属性）、关键文本内容和页面路径，不以坐标位置为唯一依据，以应对布局重排后同一控件坐标发生变化的情况。

对应关系建立后，系统比较各屏态下对象的可见性、归一化位置、相对尺寸、层级关系和可操作性。合理适配表现为：页面在宽屏下切换为多栏布局、内容密度提升、导航栏位置迁移等；问题适配表现为：关键内容（标题、正文、图片、主按钮）消失或溢出窗口、业务状态（已选项、输入内容、播放位置）在屏态切换后丢失、主要操作控件落入系统导航区或折痕区域、页面层级关系错乱或关键视觉元素跨越折叠折痕边界。

折叠屏的半折状态（Flex 模式）还需额外检查：上下屏区域的内容分配是否合理、折痕遮挡区域的控件是否仍可操作、视频或图片是否被折痕分割。三折叠屏的双屏和三屏展开状态需要确认多个显示区域之间的内容连续性与导航路径可达性。

判定结论中，适配问题按影响屏态、影响对象、变化类型（消失/溢出/遮挡/状态丢失）和严重程度分别记录，并附变化前后屏态的截图对比。

### 8.9 避让判定算法

避让异常指应用 UI 中，被测页面未能为系统占用区域留出足够的安全边距，导致内容或交互控件被系统区域覆盖或挤出可用显示区域的问题。系统占用区域包括状态栏、导航栏（手势导航区）、虚拟键盘、悬浮通知、固定底部导航栏、折叠折痕区域和圆角裁切区域。

避让判定分三步进行。第一步，从设备档案和当前窗口信息中提取所有系统占用区域的像素边界，并记录各占用区域的类型和当前显示状态（例如键盘是否弹出、底栏是否展开）。第二步，对当前页面快照中的交互控件和主要内容节点，逐一计算其边界矩形与各系统占用区域的相交关系；相交面积超过节点可操作区域 10% 的，标记为候选避让异常。第三步，结合节点类型和业务重要性对候选结果进行分级：输入框、确认按钮、提交操作被遮挡判定为严重；正文、标题被遮挡判定为普通；装饰性图标或背景元素被遮挡判定为轻微。

键盘场景重点检查：键盘弹出后，输入框是否仍在可视区域内；光标位置与校验提示是否被键盘遮挡；提交按钮或下一步按钮是否可点击。底栏场景重点检查：页面底部可滚动内容的最后一项是否被底部导航栏遮挡；固定底部操作栏是否与系统导航手势区域重叠。全屏媒体场景重点检查：播放控制区域是否位于系统手势识别区内；字幕或提示信息是否落入安全区域边界之外。

判定结论记录遮挡对象、占用区域类型、相交像素面积、严重程度和所在屏态，并附带截图标注。

### 8.10 结果融合

结果融合按“视觉候选、页面对象、问题规则、屏态证据”的顺序处理。视觉候选与页面对象无法对应时，保留候选并标记为需复核；页面结构与视觉表现一致时，形成明确问题结论；不同证据冲突时，以当前页面快照和任务规则为准。

页面级结果为存在问题、未发现问题或需复核。问题级结果包含问题类型、对象、区域、严重程度、原因和证据引用。

## 9 数据与接口设计

### 9.1 任务接口

任务接口接收应用标识、设备状态、任务目标、指令级别、指令内容、目标页面规则和 UX 问题类型。系统返回任务运行编号、执行状态和结果路径。

高级指令任务至少包含任务目标和目标页面规则；低级指令任务包含按顺序排列的单步动作描述。任务规则支持关键文本、页面标题、稳定控件标识、页面路径和排除条件。任务输入的典型数据结构如下：

```json
{
  "id": "task-001",
  "app": "com.example.app",
  "instruction_level": "high",
  "task": "打开设置，进入 Wi-Fi 页面，查看当前连接状态",
  "target_page": {
    "required": ["Wi-Fi", "已连接"],
    "stable_id": "wifi_status_page",
    "exclude": ["蓝牙", "移动网络"]
  },
  "device": { "type": "phone", "screen_states": ["portrait", "landscape"] },
  "ux_checks": ["truncation", "large_element", "avoidance"]
}
```

### 9.2 观察接口

观察接口返回截图路径、页面结构路径、窗口边界、系统区域、设备型号、屏幕方向、折叠状态和采集时间。截图和页面结构使用同一快照编号。观察对象的典型数据结构如下：

```json
{
  "snapshot_id": "snap-0012",
  "screenshot": "snapshots/snap-0012.png",
  "layout_dump": "snapshots/snap-0012-layout.json",
  "window": { "x": 0, "y": 0, "width": 1080, "height": 2340 },
  "system_bars": { "status_bar_height": 96, "nav_bar_height": 80 },
  "device": "Mate60Pro",
  "screen_state": "portrait",
  "fold_state": "unfolded",
  "captured_at": 1726283400000
}
```

### 9.3 动作接口

动作接口支持启动、点击、长按、滑动、输入、按键、返回和屏态切换。动作对象包含动作类型、目标标识、坐标、输入内容、开始时间、结束时间和动作后快照引用。动作记录的典型数据结构如下（JSONL，每行一条）：

```json
{"step": 3, "action": "tap", "target_id": "btn_wifi", "x": 540, "y": 620, "snapshot_before": "snap-0011", "snapshot_after": "snap-0012", "started_at": 1726283398800, "ended_at": 1726283399200, "duration_ms": 400}
{"step": 4, "action": "swipe", "x1": 540, "y1": 1500, "x2": 540, "y2": 800, "snapshot_before": "snap-0012", "snapshot_after": "snap-0013", "started_at": 1726283400100, "ended_at": 1726283400650, "duration_ms": 550}
```

坐标使用归一化坐标系（[0,1000] × [0,1000]），由设备适配层转换为当前窗口像素坐标后执行。

### 9.4 模型接口

模型层以 Qwen3.6 27B 视觉语言模型为导航决策基座，并以同族视觉模型的微调版本承担截断识别。导航与检测通过不同输入和输出约定区分用途，互不耦合。

导航决策由 Qwen3.6 27B 完成。输入为任务目标与当前页面截图，动作坐标使用归一化坐标空间；输出为结构化动作，包括点击（tap）、滑动（swipe）、输入（type）、按键（key）和结果上报（report）。导航模型典型输出如下：

```json
{"action": "tap", "x": 540, "y": 320, "target": "Wi-Fi 设置入口", "reason": "当前在系统设置首页，Wi-Fi 选项位于列表第二项"}
```

UX 检测由截断检测微调模型完成，必要时由 Qwen3.6 27B 补充其他问题类型的候选识别。输入为目标页面截图，必要时附加页面布局结构（layout dump）；输出为问题类型、问题区域、现象描述和置信度。UX 识别模型典型输出如下：

```json
{
  "page_state": "issues_found",
  "issues": [
    {
      "type": "truncation",
      "description": "第三列卡片标题文字末尾被容器右边界截断，约 4 个汉字不可见",
      "region": [620, 340, 980, 390],
      "confidence": 0.91,
      "evidence": "文字末尾无省略号但视觉明显被裁切"
    }
  ]
}
```

模型接口统一使用结构化响应。原始响应和解析结果分别保存，报告引用解析结果，问题复核可以回看原始响应。

### 9.5 结果接口

任务结果包含任务编号、页面到达状态、屏态结果、问题列表、动作耗时、端到端耗时、证据索引和报告路径。问题结果包含问题编号、问题类型、设备状态、区域、严重程度、原因和证据。

### 9.6 运行数据与证据组织

| 文件 | 内容 |
|---|---|
| task.json | 任务目标、指令、目标页面和检测要求 |
| environment.json | 应用版本、设备型号、系统版本和屏态 |
| actions.jsonl | 每一步动作、参数、执行结果和耗时 |
| snapshots/ | 截图、页面结构和窗口信息 |
| model/ | 导航和 UX 识别的原始响应及解析结果 |
| issues/ | 问题类型、问题区域、判定说明和证据引用 |
| report.json | 任务结果、指标和报告索引 |

任务证据包按任务运行编号隔离。报告使用相对路径引用截图、页面结构和问题文件，保证整个证据包移动后仍可复核。

## 10 模型能力与训练数据

### 10.1 模型角色说明

系统使用两个相互独立的模型，分别承担导航决策和 UX 问题识别。

| 模型角色 | 基座 | 用途 | 训练状态 |
|---|---|---|---|
| 导航模型 | Qwen3.6 27B 视觉语言模型 | 理解任务目标、观察页面截图、输出结构化动作 | 使用预训练基座，以 HarmonyOS 轨迹进行持续 SFT 迭代 |
| 截断检测模型 | 微调视觉语言模型 | 识别页面截图中的文字截断问题 | 已基于人工标注截断数据完成 SFT 训练 |

两个模型通过不同接口调用，互不耦合。导航模型负责把应用带到目标页面；截断检测模型负责在目标页面确认后执行 UX 识别。

### 10.2 轨迹数据与 SFT 训练

#### 轨迹收集

轨迹由系统在任务执行过程中自动生成。每条轨迹对应一个任务，包含初始截图、逐步动作和最终页面状态。轨迹以对话格式组织，便于直接用于模型训练。

```json
{
  "id": "hmos/task_0001",
  "messages": [
    {"role": "system", "content": "系统提示词，包含工具定义"},
    {"role": "user", "content": "The user query: {instruction}\n<image>"},
    {"role": "assistant", "content": "Thought: ...\n<tool_call>harmony_tap x=540 y=320</tool_call>", "loss": true},
    {"role": "tool", "content": "<image>"},
    {"role": "assistant", "content": "Thought: ...\n<tool_call>harmony_report_result success=true</tool_call>", "loss": true}
  ],
  "images": ["screenshot_step0.png", "screenshot_step1.png"]
}
```

#### 数据清洗

收集到的轨迹在入库前进行三级过滤：模型自判完成（`harmony_report_result` 返回 success）作为第一道过滤；步数明显超出同类任务中位数的轨迹降权；设备崩溃、应用无响应等环境故障归为环境异常，不作为训练负样本。

#### SFT 训练流程

导航模型采用分阶段 SFT 训练：第一阶段以通用移动端轨迹为主做基础训练，第二阶段掺入 HarmonyOS 专属轨迹做持续微调，使模型适应 HarmonyOS ArkUI 组件特征、应用结构和操作习惯。截断检测模型单独训练，以人工标注的截断标注（截图 + 边界框）为训练数据，不参与导航轨迹训练。

### 10.3 截断检测模型

截断检测模型基于视觉语言模型微调，输入为页面截图（可选附加 ArkUI layout dump），输出为截断区域边界框、截断类型和置信度。训练数据包含人工标注的文字截断、图片截断、组件截断和溢出样本，标注格式采用 Labelme 矩形框，并记录截断方向（上/下/左/右）和严重程度。

模型训练与 UX 检测三阶段 pipeline 对应关系如下：第一阶段（image-only）由截断检测模型承担，利用训练获得的截断特征识别能力输出候选；第二阶段（layout-based）和第三阶段（slide 验证）作为后处理规则补充，降低误报率。

## 11 性能与可靠性设计

### 11.1 动作响应时间

动作响应时间从运行时发送动作请求开始，到设备动作完成并返回动作后页面观察结果为止。系统记录每个动作的开始时间、结束时间和阶段耗时，统计平均响应时间和单步最大响应时间。

### 11.2 端到端检测时间

三层界面端到端时间从三级目标页面确认完成开始，到 UX 检测结果和报告写入完成为止。计时包含页面快照、模型识别、问题判定和结果生成。

### 11.3 时延控制

系统通过并行采集截图和页面结构、复用稳定页面快照、共享页面节点索引、限制重复检测和增量写入报告控制时延。时延优化不能跳过页面确认、问题判定和必要证据保存。

### 11.4 任务稳定性

系统按任务隔离运行上下文。单个任务的设备异常、应用异常、动作异常或模型异常只影响当前任务，不影响其他任务的执行和结果保存。

### 11.5 异常恢复

设备连接中断时重新建立设备会话；应用退出或停留在加载页时重新启动并恢复任务入口；页面出现弹窗时先处理影响任务的弹窗；页面无变化时重新观察并重新规划动作。

截图、页面结构和窗口信息不属于同一页面状态时，系统重新采集完整快照。屏态切换完成后，只有在窗口和页面布局稳定时才进入 UX 检测。

## 12 安全与数据管理

### 12.1 凭据管理

模型服务密钥、测试账号、设备认证信息和应用登录信息由运行环境安全保存，不写入任务、日志、截图和报告。

### 12.2 测试数据

页面截图、页面结构、动作轨迹和问题报告保存在项目指定目录。涉及账号、手机号、地址和用户内容时，报告导出按照项目数据管理要求进行脱敏。

### 12.3 访问控制

测试执行人员负责运行任务，UX 质量人员负责问题复核，验收人员负责查看汇总和证据，维护人员负责更新设备和规则配置。不同角色按照项目权限访问运行目录。

### 12.4 结果完整性

任务、动作、快照、问题和报告使用任务编号与快照编号关联。报告生成时检查文件引用和任务编号，确保汇总结果与逐任务证据一致。

## 13 验收设计

### 13.1 验收范围

验收从任务加载开始，覆盖应用启动、页面导航、目标页面确认、多设备状态执行、UX 问题发现、问题类型判断、响应时间记录和报告生成。

设备范围包括手机、平板、折叠、双折叠和三折叠设备；屏态范围包括竖屏、横屏、折叠、展开、半折和分屏；问题范围包括大图大字、页面截断、视频图片拉伸、横屏未适配和避让异常。

### 13.2 功能验收

| 验收项目 | 检查内容 | 通过条件 |
|---|---|---|

| 多屏态检测 | 各屏态独立执行 | 每个屏态均有快照和结果 |

| 指标 | 计算方式 | 通过标准 |

| 单步最大响应时间 | 所有动作耗时最大值 | ≤5 秒 |
| 三层界面端到端时间 | 目标页面确认至结果生成 | ≤10 秒 |

## 14 部署与运行

### 14.1 运行环境

系统由测试主机、HarmonyOS 真机或模拟器、GUIAgent 运行时、设备自动化工具、页面观察组件、模型服务和结果存储组成。测试主机负责任务调度与报告生成，设备运行被测应用，模型服务提供导航决策和 UX 识别。

系统运行所需的主要技术组件如下。

| 组件 | 要求 |
|---|---|
| 测试主机 | macOS，Node.js 18 及以上，Python 3.9 及以上 |
| 设备控制 | hdc（HarmonyOS Device Connector）命令行工具 |
| AI 编排 | OpenCode，采用 stdio MCP 协议 |
| 模型服务 | DashScope API，调用 Qwen3.6 27B 视觉语言模型（联网调用） |
| 辅助验证 | TextTruncVerifier Python 工具 |
| 坐标空间 | 0–1000 归一化坐标系 |

### 14.2 运行配置

运行配置包括应用包信息、启动入口、设备清单、屏幕状态、任务文件、页面规则、问题类型、模型版本、坐标空间、动作时限和报告路径。

### 14.3 标准运行步骤

1. 加载任务和运行配置；
2. 连接并识别目标设备；
3. 启动应用并建立初始页面快照；
4. 执行高级或低级指令；
5. 确认目标页面；
6. 执行任务要求的设备和屏幕状态；
7. 采集页面快照并执行 UX 检测；
8. 判断问题类型和问题区域；
9. 保存逐任务结果；
10. 生成验收汇总报告。

### 14.4 版本管理

任务配置、设备档案、页面规则、模型适配器和问题规则按版本管理。每次运行记录相应版本，保证报告能够对应到具体的任务和环境。
