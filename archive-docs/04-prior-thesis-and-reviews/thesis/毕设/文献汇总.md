@陆勇雍 工作：Beyond browsing: Api-based web agents
印象：【ArXiv】【知名高校出品：卡内基梅隆大学CS】
本论文希望解决什么问题？
- 仅通过 API 执行在线任务的 API 调用Agent，类似于传统的编码Agent
- 可以通过 Web Browse和 API 与在线数据交互的混合Agent。
本论文是怎么解决的该问题？
开发了基于 API 的新Agent，它们通过 API 调用直接与 Web 服务交互，此方法无需通过模拟点击与 Web 页面 GUI 交互。当API 可用且文档齐全时，Agent可以直接与 Web 服务交互。对于 API 支持有限的网站，Agent会无缝切换到 Web 浏览模式，模拟人工交互以确保任务完成。
1.在网站上手动查找官方 API 文档来获取 API
- 充足的 API 和文档 ：只需按原样使用 API/文档即可。
- 足够的 API，足够的文档 ：检查网站的前端或后端代码，以提取Agent仍可使用的未记录的 API 调用。然后，根据网站 API 的实现，利用 LLM （GPT-4o） 生成这些 YAML 或 README 文件，包括输入参数、预期输出和示例 API 调用。
- API 不足 ：可能需要创建新的 API。最初，Reddit 只提供 18 个 API，缺乏常见在线论坛所具有的主要功能，例如帖子投票。认识到这一限制，我们手动引入了 13 个额外的 API，包括一个用于投票后 的 API，我们尽最大努力尝试模仿 Reddit 官方网站。
2.在Agent中使用API：
- 小型 API 集的一步式文档 ：直接将完整文档合并到提供给Agent的提示中。
- 大型 API 集的两阶段文档检索 ：由于Agent输入的大小限制，采用了一个两阶段的文档检索流程，在第一阶段，提供任务的描述，包括所有可用 API 终端节点的列表以及每个 API 的非常简短的描述。例如，{“GET /api/{id}/commits”： “Get a list of commits in a project”}。在第二阶段，如果模型确定它需要有关特定 API 终端节点或某些 API 终端节点的详细信息，则可以使用名为get_api_documentation 的工具获取API。
3.BROWSING + API CALLING 混合Agents
集成了基于Browsing 和基于 API 的方法，并开发了一种能够交错 API 调用和 Web browsing的混合Agent，根据任务要求和可用资源动态切换。对于提供全面 API 支持的网站，Hybrid Agent 可以利用有据可查的终端节点来执行任务，而不是通过 Web 浏览；对于 API 支持有限或 API 记录不佳的网站，混合Agent可能更多地依赖 Web 浏览来完成某些任务。
本论文有什么缺陷？
获取API可能需要创新api或通过llm生成api
api调用必然比gui更快
本论文有什么亮点？
首次提出混合gui+api
