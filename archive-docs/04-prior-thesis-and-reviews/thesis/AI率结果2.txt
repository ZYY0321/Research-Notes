基于多智能体架构的交互式移动端助手系统设计与实现

摘要

随着大型语言模型与多模态感知能力的快速发展，以模型为推理核心的移动端图形用户界面智能体正成为人机交互领域的新兴研究方向。然而，现有系统在面对用户指令模糊、跨应用协作、长期知识积累等真实场景需求时仍存在明显局限。 本文设计并实现了一套基于多智能体架构的交互式移动端助手系统 Fairy，该系统采用三层分层架构，包含全局任务规划层、应用级执行层与自我学习层，同时引入双执行环路机制，将动作执行环与用户交互环解耦协同，从而在任务执行过程中支持主动意图澄清。在感知层面，系统融合可访问树解析与截图标注（Set-of-Mark，SoM）两种模式，为决策智能体提供结构化屏幕信息。 在记忆管理层面，系统构建了短时工作记忆与长期知识记忆的分层存储机制，长期记忆通过基于向量索引的检索增强生成（RAG）为规划与执行提供应用级经验复用。此外，本文还参与设计了面向模糊指令场景的评测基准 ，提出了指令清晰度四层级分类体系，并开发了多智能体评估框架 MUSE，从结果有效性、执行质量与交互质量三维度对智能体进行精细化评估。 实验结果表明，所设计系统在用户需求完成率与意图对齐能力上显著优于非交互式基线系统，交互机制在模糊指令条件下的提升尤为突出。

1.1 研究背景（宋体四号，居左）

自个人计算机普及以来，图形用户界面（Graphical User Interface，GUI）始终是人与软件系统之间最主要的交互媒介。与命令行界面相比，GUI 以窗口、图标、菜单等可视化元素替代了晦涩的命令输入，大幅降低了普通用户操作软件的认知门槛，推动了信息技术在社会各层面的广泛渗透。 然而，这种以"人"为中心设计的界面形式也带来了一个长期存在的工程困境：当外部程序需要与 GUI 应用协作或集成时，往往只能将其视为"黑盒"，通过模拟点击、截图识别等方式加以操控，由于 GUI 并非为程序调用而设计，这类方法天生脆弱。

传统的 GUI 自动化方案，无论是依赖坐标或图像特征的脚本工具（如 Selenium、Appium），还是面向企业流程的 RPA（Robotic Process Automation）平台，本质上都建立在界面元素的稳定结构与可预期的操作路径之上——一旦应用升级改变了控件层级，或者业务流程发生调整，这套脆弱的假设便随之崩塌，脚本的维护成本随应用数量的增长呈近乎线性的态势攀升。 移动端场景中这一矛盾尤为尖锐，因为数以百万计的 App 各自遵循不同的交互逻辑，更新节奏远超桌面软件，而跨应用的协同操作更涉及需要在应用边界之间精确传递的状态上下文，这些都是纯规则化脚本几乎无法有效覆盖的长尾场景。

大型语言模型（Large Language Model，LLM）及多模态大模型（Large Multimodal Model，LMM）的兴起，从根本上打开了一条绕过上述困境的新路径。 自 GPT-4、Claude 等旗舰模型相继发布以来，研究者逐渐意识到这类模型在指令理解与多步推理上展现出的能力，与 GUI 操作所需要的"读懂意图—拆解步骤—映射动作"过程有着天然的契合；而视觉语言模型（Vision-Language Model，VLM）的成熟则进一步打通了"看屏幕—做决策"这一感知到行动的关键环节，使得无需预先为每款应用编写规则的通用型 GUI 智能体（GUI Agent）变

得切实可行。这类智能体目前被学术界和工业界普遍视为下一代操作系统级虚拟助手的核心技术方向，吸引了大量前沿研究投入。

在移动端领域，GUI Agent 的研究从 2023 年起迅速升温。AutoDroid 率先将 LLM 引入 Android 任务自动化，首次验证了 LLM 驱动移动端 GUI 操作的可行性；AppAgent 提出探索—部署两阶段范式，通过参考文档辅助运行时决策；Mobile-Agent 系列逐步引入多智能体协作、自我进化记忆等机制，将可完成任务的复杂度和多样性持续推向更高水平。 与此同时，相关评测基准也在快速迭代，从早期侧重单步动作准确率的静态数据集，到 AndroidWorld等面向真实动态环境的评测框架，研究者对"一个真正好用的移动端助手应该具备哪些能力"的认识也在持续深化。

1.2 研究意义

尽管 GUI Agent 研究进展迅猛，现有系统在真实场景中仍面临几项核心挑战，这也是本课题的出发点。

用户指令的模糊性问题。现实中的用户往往不会像工程师一样精确表达操作需求。"帮我点一份麦当劳"这类指令中隐含了大量未被明确的偏好——汉堡种类、套餐搭配、外卖地址等。现有非交互式智能体通常只能依赖模型先验进行概率猜测，大概率偏离用户真实意图。如何让智能体在执行过程中识别歧义、主动向用户澄清，是提升真实可用性的关键。
该段落可能为AI生成的概率为：96.9%
跨应用协作与上下文传递问题。 用户日常任务往往横跨多个 App。例如"把明天的会议地点发给我同事"涉及日历应用与即时通讯应用的协同，不同应用间切换需要正确传递任务上下文，而现有系统多为单应用设计，跨应用规划与上下文管理能力普遍不足。
该段落可能为AI生成的概率为：96.9%
长尾应用的知识积累问题。LLM 的通用知识无法覆盖所有 App 的具体交互逻辑，尤其是国内第三方应用（如外卖、打车、电商平台）中的业务流程细节。如何在任务执行过程中积累 App 专项经验，并在后续任务中高效复用，是提升系统长期可用性的核心机制。
该段落可能为AI生成的概率为：96.9%
本研究并非试图从某一单点突破这些挑战，而是将它们放在"真实场景下移动端任务自动化"这一整体目标下统筹考量，设计并实现了一套从架构到工程的完整系统方案。系统以"分层规划—双环执行—持续学习"为核心设计哲学，在感知、决策、记忆管理各环节提供了具体的实现，并通过基准设计以及自构任务集评估，对关键模块的实际效果给出了有据可查的评测结论。 希望这一工作既能为移动端 GUI 自动化领域提供一个可落地的工程参照，也能在交互式智能体的设计方法和评测框架上积累一定的方法论经验。

1.3 国内外研究现状

从单智能体到多智能体的演进。早期 GUI Agent 多为单智能体架构，一个 LLM 负责感知、规划和执行的全部决策。AppAgent（2023）开创性地提出两阶段范式：探索阶段通过随机操作构建应用知识文档，部署阶段参考文档辅助决策。这一方案显著提升了决策质量，但探索成本高，文档质量依赖探索充分度。Mobile-Agent（2024）引入多智能体协作，由独立的感知、规划、执行智能体分工协作，在长程任务和跨页面操作上取得明显提升。Mobile-Agent-v2 进一步引入显式的记忆管理和多智能体导航机制，实现了更稳定的长链路任务执行。

2.1 移动端 GUI Agent 的发展脉络

2.1.1 早期探索：从规则脚本到 LLM 驱动

在 LLM 驱动 GUI Agent 研究正式兴起前，移动端自动化长期依赖两类技术路线。其一是基于 UI 测试框架（如 Appium、UI Automator）的脚本自动化，通过 XPath 或资源 ID 定位界面元素后执行预设操作序列；其二是基于图像识别的 RPA 工具，通过截图匹配特征区域触发点击动作。两者的共同局限在于脆弱性：一旦应用升级改变了控件层级或视觉样式，脚本需要重新适配，维护成本居高不下。
该段落可能为AI生成的概率为：96.9%
AutoDroid（2024）是首个将 LLM 系统性地应用于 Android 任务自动化的工作。其核心贡献在于构建了应用 UI 过渡图（App UI Transition Graph），将应用的状态转移关系以图的形式存储，由 LLM 在图上进行推理以生成操作序列。这一方案无需人工编写操作规则，在简单任务上取得了良好效果，首次验证了 LLM 在移动端 GUI 任务中的可行性。
该段落可能为AI生成的概率为：95.3%
AppAgent（2023）进一步提出"探索—部署"双阶段范式。探索阶段通过随机操作积累界面交互经验，生成每个 App 的参考文档；部署阶段 LLM 参考文档辅助生成当前步骤的操作决策。这种将知识预积累与在线决策分离的思路，有效缓解了 LLM 对特定应用知识盲区的问题，但探索阶段成本较高，文档质量也高度依赖探索覆盖的充分程度。

2.1.2 多智能体协作架构的兴起

单一 LLM 在复杂、长程任务中容易出现注意力分散、决策错乱等问题。Mobile-Agent（2024）将视觉感知与操作决策拆分为独立模块，引入了专门负责视觉处理的子智能体，使核心决策模型能专注于任务逻辑推理。Mobile-Agent-v2 在此基础上增加了显式的任务规划智能体和记忆管理模块，通过多智能体流水线在跨页面、长链路任务中表现出更强的导航稳定性。

MobA（2025）将多智能体协作与层级记忆相结合，设计了粗粒度子目标规划器与细粒度动作决策器的两层结构，同时维护应用地图（App Map）和操作技巧（App Tricks）两类长期记忆，通过关键词检索辅助规划与动作决策。这一设计思路与本文系统高度相关，是本课题在架构上的重要参照。

该段落可能为AI生成的概率为：96.9%
2.1.3 端到端基础模型路线

2025 年以来，另一条技术路线逐渐引发广泛关注：直接训练专门服务于 GUI 操作的端到端 Native Agent，将感知、规划、执行能力内化在单一 VLM 中。UI-TARS（ByteDance/清华，2025）通过大规模感知增强数据训练和统一动作空间设计，配合 System-2 推理机制，在 OSWorld 基准上达到 24.6% 的成绩，后续通过强化学习进一步提升至 42.5%。Step-GUI（阶跃星辰，2025）采用自进化训练流水线（CSRS），将模型生成的轨迹自动转化为高质量训练数据，其 8B 规格模型在 AndroidWorld 上达到 80.2% 的成功率。
该段落可能为AI生成的概率为：96.9%
这类端到端基础模型路线与基于 LLM 工作流的系统路线并非对立：前者决策延迟低、部署便捷，适合规模化推广；后者架构灵活、可解释性强、便于融入复杂业务逻辑，适合定制化场景。本文工作属于后者，侧重系统架构设计与工程实现。
该段落可能为AI生成的概率为：37.2%
2.2 屏幕感知技术

屏幕感知是 GUI Agent 获取当前界面状态的核心环节，其质量直接决定后续规划和动作决策的准确性。

基于可访问树的感知。 Android 系统通过 UI Automator 框架暴露应用的 View 层级结构，即可访问树（Accessibility Tree，AT）。AT 以 XML 格式描述屏幕上每个 UI 节点，包含节点的类型（class）、边界坐标（bounds）、文本（text）、内容描述（content-desc）等属性。基于 AT 的感知方案可以精确定位所有可交互元素及其坐标，是面向文本型 LLM 的天然适配。其局限在于：AT 信息高度依赖应用开发者的规范实现，通过 Canvas 绘制的自定义控件往往缺少语义标注；此外，AT 无法传达图标的视觉含义和图像内容。
该段落可能为AI生成的概率为：90.9%
截图与视觉感知。 随着 VLM 能力的提升，直接将屏幕截图作为模型输入成为可行路线。Set-of-Mark（SoM，2024）提出在截图上叠加数字标签，为每个可交互元素标注编号，使 VLM 在生成操作时能通过编号引用具体元素而无需输出精确坐标，显著减少了坐标回归带来的误差。Aria-UI（2024）针对 GUI 场景设计了上下文感知的 Grounding 模型，在截图中准确定位自然语言描述的元素，在 AndroidWorld 上达到 44.8% 的领先成绩。
该段落可能为AI生成的概率为：95.3%
融合感知方案。 更鲁棒的做法是将 AT 结构信息与截图视觉信息结合使用。UI-TARS 在训练时同时使用了 AT 文本描述和截图，以增强多模态理解能力。本文系统实现的 SSIP（Screen Structured Info Perceptor）感知方案采用了融合策略：优先基于 AT 提取可交互节点并在截图上绘制 SoM 标记，对 AT 缺失图像语义的节点额外调用视觉描述生成模型补全内容描述，从而在保持坐标精度的同时兼顾图像语义理解。
该段落可能为AI生成的概率为：77.9%
2.3 规划与决策机制

单层反应式规划。 早期系统采用单步或有限步的规划策略：给定当前屏幕状态和用户指令，直接生成下一步操作。这种"反应式"（Reactive）决策方式实现简单，但面对长程任务时，缺乏对整体目标的把握容易导致方向偏离和步骤冗余。
该段落可能为AI生成的概率为：84.5%
层级规划。 层级规划将任务分解为不同粒度的子目标，典型结构为"高层目标→子任务→原子动作"三级。高层目标对应用户的自然语言指令；子任务对应在单一应用内可独立完成的阶段目标（如"搜索目标商品"、"填写收货地址"）；原子动作则是单次屏幕操作（如 Tap、Swipe、Input）。这种结构使规划器只需关注子目标序列，动作决策器只需关注如何在当前屏幕上实现当前子目标，各层职责清晰。本文系统的 AppPlannerAgent 和 ActionDeciderAgent 分别对应子任务规划和原子动作决策两层。
该段落可能为AI生成的概率为：96.9%
动态重规划。 规划并非一次性的静态序列。在执行过程中，屏幕状态可能出现预期外的变化（如弹出广告、页面加载失败、搜索结果为空），此时需要对剩余计划进行动态修订。本文系统的 AppRePlannerAgent 负责在检测到子目标推进异常或陷入循环时触发重规划，重新生成后续子目标序列。
该段落可能为AI生成的概率为：95.3%
基于 MCTS 的规划增强。 Plan-MCTS（2026）将动作搜索提升到语义 Plan Space，通过蒙特卡洛树搜索在规划层面探索多条执行路径，在 WebArena 上取得了新的最优成绩。这一方向为推理时增强提供了有价值的参考，但在移动端实时交互场景中引入树搜索的额外延迟仍是实用性挑战。
该段落可能为AI生成的概率为：96.9%
2.4 记忆机制

记忆是智能体积累经验、提升长期表现的关键能力，近年来受到越来越广泛的关注。

短时工作记忆。 短时记忆在当前任务执行周期内维护，保存当前指令、当前计划、历史动作—结果对等信息，供各决策模块动态查询。在长程任务中，如何在保留关键历史信息的同时控制 LLM 输入长度是重要问题。AgentProg（2025）将交互历史重构为带变量和控制流的语义程序，原则性地保留或丢弃信息，支持长流程任务不退化。SWE-AGILE（2026）提出"滑动窗口保留最近完整推理 + 历史推理压缩为摘要"的混合策略。
该段落可能为AI生成的概率为：95.3%
长期知识记忆与 RAG 检索。长期记忆跨越任务生命周期，持久保存应用操作经验。

A-MEM（2025）提出基于 Zettelkasten 思路的记忆网络，在写入新记忆时自动建立与已有记忆的双向链接；CoMEM（2025）使用 Q-Former 将历史轨迹压缩为少量连续向量注入 VLM，实现高效上下文压缩；HyMEM（2026）结合符号节点与连续轨迹嵌入构建图结构记忆，支持多跳检索，在 Qwen2.5-VL-7B 上绝对提升 22.5%。 本文系统的 LongTimeMemoryManager 采用基于 LlamaIndex 的 VectorStoreIndex，将三类经验分别建立独立索引，检索时通过 App 包名元数据过滤结合语义相似度排序，取 top-3 结果作为上下文注入对应的规划或决策提示词。
该段落可能为AI生成的概率为：80.5%
面向 UI 更新的自适应记忆。 MAGNET（2026）提出双层记忆机制：stationary memory 将视觉外观映射到功能语义（应对界面外观漂移），procedural memory 保存任务工作流（应对流程变化）。AndroTMem（2026）针对 Android 长流程专门设计了锚定状态记忆（Anchored State Memory），在 1069 个测试任务上实现了 5%—30% 的任务完成率提升。这些工作表明，针对具体场景定制化记忆结构是提升系统性能的有效路径。
该段落可能为AI生成的概率为：96.9%
2.5 用户交互与意图对齐

大多数现有 GUI Agent 采用"无交互"模式：接收用户指令后自主完成全部操作，不在执行过程中与用户沟通。这种方式在指令清晰、任务确定性高的场景下效率较高，但面对歧义指令时往往产生错误的意图理解。
该段落可能为AI生成的概率为：96.9%
从认知科学的视角来看，用户在表达需求时所产生的"认知缺口"（Cognitive Gap）几乎是不可避免的：说话者对自己想要什么往往已有相当清晰的认知，但将这种认知转化为文字时，囿于表达习惯或对系统能力的不了解，大量细节会被省略——"帮我点一份麦当劳"背后可能隐含着具体的汉堡偏好、套餐与否、外送地址等一整套约束，而这些细节在指令文本中完全缺失。对于非交互式智能体而言，填补这些缺口的唯一手段是依赖模型先验做概率性猜测，而猜测的期望结果是偏离用户真实意图的。
该段落可能为AI生成的概率为：96.9%
支持主动交互的系统之所以难以设计，不在于"怎样提问"，而在于"何时提问"的判断本身：询问过于频繁会把每次简单操作都变成一场确认对话，远比直接帮用户做了更烦人；而询问不足又会让意图偏差悄悄积累，直到用户看到错误的执行结果才察觉问题。 本文系统选择将 `NeedInteraction` 作为 ActionDeciderAgent 动作空间中的一个普通选项，而非一套独立的触发规则，这意味着"是否发起交互"的判断被完全内化到 LLM 对当前上下文的动态推理中，而非依赖人工设定的关键词或规则阈值，从而在覆盖度和精准度之间保持了相对的灵活性。
该段落可能为AI生成的概率为：66%
2.6 评测基准

静态数据集评测。 早期评测基准多为静态数据集，提供截图序列和对应人工标注操作，以步骤匹配率（Step Match Rate）等指标衡量系统准确性。AITW（2022）收录了大量人工演示轨迹；AndroidControl 在此基础上增加了高层指令与低层操作的对应关系注释。静态评测可重复性强，但无法反映真实任务执行中的环境动态性。
该段落可能为AI生成的概率为：86.1%
动态沙箱评测。 AndroidWorld（2025）构建了真实 Android 沙箱环境，允许智能体在虚拟设备上执行操作，并通过编程验证器检查任务完成状态，支持百余个真实 App 的任务评测。SPA-Bench 则提供了跨框架的统一评测接口，便于不同系统的标准化对比。MobiFlow（2025）从另一角度切入，专门针对以外卖、网约车为代表的"流式操作"（sequential multi-step flow）场景构建评测框架，引入了流程完整性和关键节点对齐两个维度，对本文自构任务集的设计思路有所参考。
该段落可能为AI生成的概率为：96.9%
面向交互质量的评测。 本文提出的评测系统（本文参与工作）是首个将指令清晰度系统纳入评测体系的基准，其核心贡献在于：提出四层级清晰度分类（Detailed / Standard / Incomplete / Ambiguous），引入基于 LLM 的用户模拟器（User Simulator）支持动态交互，设计多智能体评估框架从结果有效性、执行质量、交互质量三维度进行精细化指标计算，其与人工评判的相关性验证达到了较高水平。与之相比，VLAA-GUI（2025）和 VoiceBench 等工作分别从视觉定位准确性和语音指令理解角度拓展了评测维度，反映出领域对"多模态输入下的 GUI 操作"的日益关注。
该段落可能为AI生成的概率为：96.9%
第3章 系统总体设计

3.1 需求分析与设计目标

3.1.1 功能需求

根据对真实移动端使用场景的分析，系统需满足以下核心功能需求。

跨应用任务执行。 用户指令往往不局限于单一应用。系统需解析用户的高层指令，识别需要调用的应用列表，生成合理的跨应用子任务序列，并在完成每个应用级子任务后将必要的上下文信息传递给下一阶段。例如，"帮我叫一辆滴滴到我明天开会的地点"涉及日历应用（读取会议地址）与出行应用（填写目的地并叫车）的协同。
该段落可能为AI生成的概率为：89.1%
意图澄清与主动交互。 系统在执行过程中需识别以下情形并主动发起用户交互：指令存在歧义（如"帮我发条微信"未指定接收方）；面临多个同等合理的选项需要用户决策（如外卖菜单中有多种汉堡）；即将执行不可逆或高风险操作（如支付、删除数据）需要用户确认。
该段落可能为AI生成的概率为：96.9%
感知与动作执行。 系统需准确解析当前 Android 设备的屏幕状态，提取可交互元素的位置和语义信息，支持 Tap（点击）、Swipe（滑动）、Input（文字输入）、LongPress（长按）、KeyEvent（系统按键）、Wait（等待）等原子动作，并通过 ADB 或 UI Automator 接口将动作指令下发至目标设备。
该段落可能为AI生成的概率为：96.9%
长期经验积累。 系统执行任务后，应从执行轨迹中自动提炼经验知识，并在后续任务中通过语义检索复用。积累的知识分为三类：规划层经验、执行层经验和错误恢复经验，分别对应任务分解策略、原子操作规范和异常处理流程。
该段落可能为AI生成的概率为：20.6%
3.1.2 非功能需求

模块化与可扩展性。 各智能体模块通过消息总线解耦，新增模块或替换骨干模型不影响已有模块的正常运行。

多骨干模型支持。 系统允许不同模块配置不同的骨干模型，以在性能与成本之间取得平衡。视觉感知和动作决策模块使用强多模态模型，RAG 检索和文本摘要模块可使用参数量较小的文本模型。
该段落可能为AI生成的概率为：95.3%
可恢复性。 在长程任务执行过程中，系统定期将短时记忆序列化备份，支持异常中断后从检查点恢复执行。

3.2 系统总体架构

3.2.1 三层分层架构

本系统 系统采用三层分层架构（图3-1），每层承担不同粒度的智能决策职责，层间通过消息驱动机制异步通信。

第一层：全局任务规划层

该层由 GlobalPlannerAgent 和 GlobalRePlannerAgent 构成，负责接收用户的高层指令，结合设备已安装应用的元数据（包名、名称、功能描述），将任务分解为有序的跨应用子任务序列。每个子任务指定目标应用包名、子任务描述以及需要从上一子任务结果中提取的关键信息。当某一子任务执行完毕，全局规划层负责判断是否需要调整后续计划，并将跨应用上下文（如提取的地址、订单号等）传递给下一子任务。
该段落可能为AI生成的概率为：96.9%
第二层：应用级执行层

该层是系统的执行核心，由多个协作智能体构成，负责在单一应用内完成子任务的完整执行流程。执行层内部包含两个协同运行的执行环路：
该段落可能为AI生成的概率为：29.8%
- 动作执行环（Action Loop）：由 AppPlannerAgent（子目标规划）、AppRePlannerAgent（重规划）、ActionDeciderAgent（动作决策）、ExecutionReflectorAgent（执行反思）、GoalVerifierAgent（子目标验证）、ActionExecutor（动作执行）和 ScreenPerceptor（屏幕感知）构成的感知—规划—执行—反思闭环。
该段落可能为AI生成的概率为：22.1%
- 用户交互环（Interaction Loop）：由 UserInteractorAgent（交互内容生成）和 UserInteractorReflectAgent（交互结果解析）构成。当动作决策的结果为 `NeedInteraction` 时，系统暂停动作执行环，激活交互环向用户发起询问，将用户回复解析为指令补充后恢复动作执行环。
该段落可能为AI生成的概率为：38%
第三层：自我学习层

该层在任务或子任务完成后触发，从执行轨迹中提炼应用操作经验，写入持久化的长期记忆库。长期记忆分为 Plan Tips、Execution Tips 和 Execution Error Tips 三类，以 JSON 格式按应用包名组织存储，通过 LongTimeMemoryManager 提供 RAG 检索服务。
该段落可能为AI生成的概率为：58.7%
3.2.2 消息驱动运行时架构

系统的运行时基础由内部开发的 Citlali 轻量级异步消息总线提供。CitlaliRuntime 采用单例模式，维护 WorkerKeeper（Worker 注册表）和 MessageManager（消息分发器）两个核心组件。
该段落可能为AI生成的概率为：77%
Worker 是所有智能体和工具模块的基类，通过 `@listener` 装饰器声明对特定消息的监听逻辑，支持两种消息类型：
该段落可能为AI生成的概率为：29.4%
- ON_NOTIFIED（广播通知，订阅制）：Worker 订阅某一消息通道，任何发布到该通道的事件若匹配过滤条件，则触发对应的监听方法。适用于松耦合的事件驱动调用，如 ScreenPerception Done 事件触发 ExecutionReflector。
该段落可能为AI生成的概率为：58.5%
- ON_CALLED（点对点调用，请求—响应制）：调用方通过 Worker 名称直接发起调用并等待响应，适用于同步性要求较强的数据查询，如各决策 Agent 向 ShortTimeMemoryManager 请求短时记忆。
该段落可能为AI生成的概率为：58.3%
消息通道分为两条：`global_channel` 用于全局规划层的事件传播；`app_channel` 用于应用执行层内部模块间的事件传播。双通道设计隔离了全局规划与应用执行两个层级的状态机，避免跨层事件干扰。
该段落可能为AI生成的概率为：92.6%
3.2.3 双环执行机制协同流程

双环执行机制是本系统的核心设计特色。其完整工作流程如下：

步骤1：计划初始化。 收到 Task CREATED 事件后，AppPlannerAgent 向长期记忆查询 Plan Tips，结合当前指令生成初始子目标序列，发布 Plan DONE 事件。ShortTimeMemoryManager 同步更新短时记忆中的计划状态。
该段落可能为AI生成的概率为：23.9%
步骤2：屏幕感知。 初始化时 ScreenPerceptor 主动采集当前屏幕（截图 + 可访问树 XML），处理后发布 ScreenPerception DONE 事件，携带结构化屏幕信息 SSIPInfo。
该段落可能为AI生成的概率为：12.7%
步骤3：动作决策。 ActionDeciderAgent 收到 Plan DONE 或 Reflection DONE 事件后，从短时记忆获取当前子目标、历史执行记录，从长期记忆检索对应 App 的执行技巧（或错误恢复技巧），结合当前屏幕感知信息构建提示词并调用 LLM，生成包含一个或多个原子动作的决策结果。若决策结果为 `NeedInteraction`，则不进入步骤4，而是触发交互环。
该段落可能为AI生成的概率为：58.8%
步骤4：动作执行与感知。 ActionExecutor 接收动作列表，通过 UI Automator 依次执行 Tap / Swipe / Input 等原子操作；执行完成后 ScreenPerceptor 重新采集屏幕状态。
该段落可能为AI生成的概率为：12.7%
步骤5：执行反思。 ExecutionReflectorAgent 收到 ScreenPerception DONE 事件后，对比动作前后两帧屏幕信息，判断当前动作是否达到预期效果，输出反思结果（成功 / 部分成功 / 失败 / 页面切换）及当前子目标完成程度描述。若执行次数或连续错误次数超过阈值，标记为"可能卡住"（MayStuck）并触发重规划。
该段落可能为AI生成的概率为：95%
步骤6：子目标验证与切换。 当 Reflector 判断当前子目标已完成时（SubGoalSwitch 状态），GoalVerifierAgent 进行二次确认，确认后通知 AppPlannerAgent 切换至下一子目标。若所有子目标均已完成，智能体输出 `Finish` 动作，流程终止。
该段落可能为AI生成的概率为：95.3%
交互环介入： 步骤3中若 ActionDeciderAgent 决策为 `NeedInteraction`，UserInteractorAgent 接管控制流，根据当前屏幕信息和任务上下文生成针对用户的问题与选项，通过 UserDialoger 发送给用户；UserInteractorReflectAgent 将用户回复解析为结构化的指令补充信息（interaction_summary），发布 UserInteractionReflect DONE 事件后 ActionDeciderAgent 恢复动作决策，携带 interaction_summary 作为额外上下文。
该段落可能为AI生成的概率为：84.1%
3.3 技术选型

骨干模型。 系统通过 `config.json` 配置文件为不同模块指定不同的骨干模型。视觉感知和动作决策模块默认使用具备强多模态理解能力的 GPT-4o 系列 VLM；RAG 检索的语义查询模块使用 `qwen-turbo-0428`（阿里云 DashScope），在效果与成本间取得平衡；嵌入模型使用开源的 `intfloat/multilingual-e5-large-instruct`，支持中英文混合文本的语义向量化，可通过 HuggingFace 下载或配置国内镜像端点。
该段落可能为AI生成的概率为：96.9%
移动端控制接口。 系统支持两种底层控制接口：ADB（Android Debug Bridge）直接命令执行，以及 UI Automator 框架的高层控制 API。两者可通过配置项 `action_executor_type` 和 `screenshot_getter_type` 独立切换，默认使用 UI Automator 以获得更稳定的截图和更完整的 View 层级信息（UI Automator 截图不受系统安全截图限制，且可同步获取 Accessibility Tree XML）。
该段落可能为AI生成的概率为：19.5%
向量检索框架。 长期记忆的向量索引基于 LlamaIndex（原 GPT Index）框架构建，使用内存型 VectorStoreIndex 存储嵌入向量。检索时通过 MetadataFilters 对 App 包名进行精确过滤（同时检索 common.json 和目标 App 专属文件），结合语义相似度排序，每次查询返回 similarity_top_k=3 的相关条目，由 LLM 汇总生成简洁的技巧提示文本注入提示词。
该段落可能为AI生成的概率为：96.9%
异步框架。 整个运行时基于 Python asyncio 构建，各智能体的 LLM 调用和设备控制操作均异步执行，避免阻塞主事件循环。消息总线的 publish / call 接口均为协程方法，支持高并发的事件驱动调度，使得多个 Worker 可在同一事件循环中并发处理相互独立的事件。
该段落可能为AI生成的概率为：92%
3.4 本章小结

本章介绍了 本 系统的总体架构设计，包括三层分层架构的职责划分、消息驱动运行时 Citlali 框架的工作机制、双环执行机制的完整协同流程以及主要的技术选型。三层架构将全局跨应用规划、单应用内执行与长期知识积累三类关注点有效分离；Citlali 消息总线通过 ON_NOTIFIED 和 ON_CALLED 两种通信模式，在保持各模块独立性的同时实现了灵活的事件驱动协作；双环机制在不引入外部中断逻辑的情况下优雅地处理了意图澄清需求。这些设计选择将在第4章通过具体模块的实现细节加以详述。
该段落可能为AI生成的概率为：96.9%
第4章 核心模块设计与实现

4.1 屏幕感知模块

4.1.1 模块职责与触发时机

ScreenPerceptor 是整个动作环的信息入口，负责在每次原子动作执行完毕后（ActionExecution DONE 事件），以及任务初始化时（Task CREATED 事件），采集设备当前屏幕状态并将结构化感知结果写入短时记忆，供后续的 ExecutionReflectorAgent 和 ActionDeciderAgent 使用。
该段落可能为AI生成的概率为：15.8%
模块分为两个可配置的子层：

截图与层级获取（Screen Capture）：通过 UI Automator 接口同时获取屏幕截图（PNG）和 Accessibility Tree XML。相比 ADB 纯截图，UI Automator 截图不受系统安全层限制（支付密码输入界面等），同时返回的 XML 与截图在时间戳上严格对齐，避免了两次独立采集造成的不一致。截图在传入 SSIP 前经过一次格式转换（PNG → WebP，quality=50）以压缩传输体积，降低 API 调用费用。
该段落可能为AI生成的概率为：89.9%
结构化信息感知（SSIP）：ScreenStructuredInfoPerception 类负责将原始截图和 AT XML 转化为结构化屏幕信息 SSIPInfo。
该段落可能为AI生成的概率为：23.4%
4.1.2 SSIP 感知流程

SSIP 的处理流程如下：

步骤1：AT 解析。 ScreenPerceptionAccessibilityTree 类负责解析 AT XML，提取所有叶节点中的可交互节点（属性 `clickable=true` 或 `focusable=true`）和可滚动节点（属性 `scrollable=true`），获得每个节点的边界坐标 `bounds=[left, top, right, bottom]` 和文本内容。
该段落可能为AI生成的概率为：20.6%
步骤2：SoM 标注（视觉模式）。 对于支持图像输入的 VLM，SSIP 在截图上为每个可交互节点叠加带编号的半透明标注框：可点击元素使用红色框（RGBA 255,0,0,180），标签位于左上角；可滚动元素使用绿色框（RGBA 0,255,0,180），标签位于右上角。标注后的截图经过等比缩放（目标短边 768px）后供模型输入，以控制 token 消耗。同时维护 SoM 编号到屏幕坐标的映射字典（`SoM_mapping`），用于将模型输出的标记编号转换回实际操作坐标。
该段落可能为AI生成的概率为：94.8%
步骤3：图像节点补全（非视觉模式）。 当配置为 `non_visual_mode=True` 时，系统针对内容为图片的 UI 节点（`content-desc` 为空且无文本），调用 VisualDescriptionGenerator 模型对截图中对应区域进行视觉描述生成，将描述文本写回 AT 节点的 content-desc 字段，从而使纯文本模型也能理解图标类控件的语义。
该段落可能为AI生成的概率为：20.5%
步骤4：页面摘要生成（非视觉模式）。 调用 TextSummarizer 对完整的 AT 节点文本进行摘要，生成当前页面的整体描述（page_desc），用于替代截图作为 ActionDeciderAgent 的屏幕状态输入。
该段落可能为AI生成的概率为：20.1%
步骤5：结果封装。 将截图路径、SoM 映射、AT XML、页面描述、屏幕尺寸等信息封装为 SSIPInfo 对象，由 ScreenPerceptor 进一步封装为 ScreenInfo，发布 ScreenPerception DONE 事件。
该段落可能为AI生成的概率为：12.7%
4.1.3 坐标回退机制

当 ActionDeciderAgent 在生成动作时发现目标元素在当前 SoM 截图中缺少标记（返回 `FallbackRetry` 动作），系统触发 GridMark 回退模式：将当前截图划分为均匀网格（默认 40 列 × 15 行），以格子编号代替 SoM 标号，并在下一轮决策中由 ActionDeciderAgent 基于格子坐标系输出操作目标，以应对 AT 解析不完整导致的标注缺失问题。
该段落可能为AI生成的概率为：35.9%
4.2 全局任务规划模块

4.2.1 模块职责

GlobalPlannerAgent 是系统的最高层规划者，在收到用户指令的 INIT 事件后激活。其核心任务是将用户的高层自然语言指令拆解为跨应用的子任务序列，输出中需明确指定每个子任务对应的目标 App 包名、任务描述，以及当前子任务完成后需要从结果中提取并传递给下一子任务的关键信息类型（如地址、订单号等）。
该段落可能为AI生成的概率为：96.9%
4.2.2 提示词构建

提示词由三部分构成：（1）用户总体指令文本；（2）设备已安装应用的元数据列表，格式为 `Package: <包名> | Name: <应用名> | Desc: <功能描述>`，由 AppInfoManager 实时查询并注入；（3）规划步骤指引，要求 LLM 按照"分析指令—匹配应用—确定子任务顺序—指定跨任务上下文提取需求"的步骤输出 JSON 格式的全局规划结果。
该段落可能为AI生成的概率为：96.9%
设计了一条特殊规则：若设备中存在专属应用（如麦当劳 App），则不考虑使用通用外卖聚合平台；若通用 App 和专属 App 同时存在，优先使用专属 App。这一规则减少了因平台差异造成的界面导航复杂度。
该段落可能为AI生成的概率为：93.1%
4.2.3 输出格式与上下文传递

GlobalPlannerAgent 的输出为 GlobalPlanInfo 对象，包含：

`global_plan_thought`：全局规划推理过程；

`global_plan`：子任务有序列表，每项包含 app 包名、子任务描述、上下文提取需求；

`current_sub_task`：当前待执行的子任务；

`ins_language`：指令语言（用于后续交互模块的语言自适应）。

完成一个子任务后，GlobalRePlannerAgent 接收执行摘要，判断是否需要调整后续子任务描述或上下文注入内容，维持全局计划的一致性。
该段落可能为AI生成的概率为：19.5%
4.3 应用级规划模块

4.3.1 初始规划（AppPlannerAgent）

AppPlannerAgent 在收到 Task CREATED 事件后激活（即每进入一个新的应用级子任务时触发）。它接收当前子任务的指令信息（InstructionInfo），向 LongTimeMemoryManager 查询该 App 对应的 Plan Tips，将查询结果与指令共同构建提示词，生成当前应用内的子目标序列（overall_plan）及第一个待执行的子目标（current_sub_goal）。
该段落可能为AI生成的概率为：15.8%
Plan Tips 的查询使用包名作为元数据过滤条件，同时检索通用技巧文件（`common.json`）和 App 专属技巧文件（`<包名>.json`），通过 RAG 检索语义最相关的 top-3 条目，由 LLM 汇总为简洁的规划指导文本注入提示词。这一机制使系统在对某一 App 积累了足够多的执行经验后，能够在后续相同 App 任务中避免已知的规划陷阱，提升计划质量。
该段落可能为AI生成的概率为：96.9%
4.3.2 重规划（AppRePlannerAgent）

AppRePlannerAgent 监听 GoalVerificationInfo 中 `sub_goal_correctness=false` 的情形（即当前子目标被判定为不可达）以及 `sub_goal_completion_status=B`（即当前轮动作序列已提前完成了后续子目标的部分内容）。触发后，AppRePlannerAgent 根据验证智能体提供的 `replan_suggestion` 和当前执行上下文重新生成剩余子目标序列，更新短时记忆中的计划，继续驱动动作执行环。
该段落可能为AI生成的概率为：68%
4.4 动作决策模块（ActionDeciderAgent）

4.4.1 模块定位

ActionDeciderAgent 是动作执行环的核心决策节点，在每轮"感知→反思→决策"循环中生成具体的原子操作序列。它综合利用五类上下文信息：（1）当前子目标和整体计划；（2）当前屏幕感知结果（SoM 截图或文本化描述）；（3）最近若干步（默认 5+1 步）的历史动作—反思记录；（4）来自长期记忆的执行技巧（正常情况）或错误恢复技巧（上一步失败时）；（5）用户交互摘要（若本轮紧跟一次用户交互之后）。
该段落可能为AI生成的概率为：77.4%
4.4.2 屏幕接地策略选择

ActionDeciderAgent 在构建提示词时需要决定采用哪种屏幕接地（Screen Grounding）策略，通过三个条件级联判断：
该段落可能为AI生成的概率为：57.7%
系统执行模式选择逻辑：优先启用网格坐标模式（GridMarkMode）；若未触发回退且开启非视觉模式，则采用可访问树文本与像素坐标模式；若可访问树节点支持 SoM 映射，则采用带标记编号的截图标记模式；其余情况统一使用坐标模式。
该段落可能为AI生成的概率为：96.9%
SetOfMarkMode 是默认的高质量模式：将带标记编号的截图连同 AT 文本描述一起传入模型，模型输出的 Tap / Swipe 动作通过 SoM 标记编号引用目标，系统负责将编号翻译为像素坐标后再执行。这种方式比直接输出坐标更符合 VLM 的视觉理解习惯，显著减少因坐标偏移造成的误点击。
该段落可能为AI生成的概率为：86.8%
4.4.3 动作空间设计

LLM 在单次决策中可以输出包含多个原子动作的序列（actions 数组），系统依次执行后统一采集一次屏幕状态，减少感知次数从而降低延迟。`NeedInteraction` 和 `NeedAdjustmentPlan` 等控制类动作若出现在序列的第一项，则不进入动作执行器，而是直接触发相应的控制流跳转。
该段落可能为AI生成的概率为：59.9%
4.4.4 错误纠正分支

当短时记忆中最近一次执行结果为 C 型（动作执行失败，目标未达成）或 D 型（动作执行了但效果与预期相反）时，ActionDeciderAgent 将查询切换为 `Execution_ERROR_Tips` 类型，检索错误恢复相关经验，并在提示词的 `critical_feedback` 段中将上一步的错误描述和潜在原因（`error_potential_causes`）明确呈现，引导模型优先尝试回退或绕路等恢复策略，而非简单重试同一操作。
该段落可能为AI生成的概率为：96.9%
4.5 执行反思与子目标验证模块

4.5.1 ExecutionReflectorAgent

ExecutionReflectorAgent 在每次 ScreenPerception DONE 事件后激活（即每次动作执行 + 屏幕采集完成后触发）。其核心任务是对比动作前后两帧屏幕状态，判断上一步操作是否达到了预期效果。
该段落可能为AI生成的概率为：93%
提示词中同时传入：（1）当前指令和整体计划；（2）当前子目标；（3）上一步动作决策内容（actions + thought）；（4）动作前后两张 SoM 截图（视觉模式）或文本描述。
该段落可能为AI生成的概率为：34.2%
输出为 ActionExecReflectionInfo，包含：

`action_result`：A（子目标已完成）/ B（进展中）/ C（失败，目标未达成）/ D（错误，产生负面副作用）；
该段落可能为AI生成的概率为：36.8%
`current_sub_goal_completed_part`：当前子目标已完成部分的自然语言描述，传递给下一步作为"进度继承"上下文；
该段落可能为AI生成的概率为：83.8%
`action_loop_status`：Normal（继续动作环）/ SubGoalSwitch（切换子目标，触发验证）/ MayStuck（超阈值，触发重规划）。
该段落可能为AI生成的概率为：35.1%
当 `sub_goal_exec_count >= 5` 或 `sub_goal_exec_error_count >= 3` 时，强制标记为 MayStuck，防止因环境异常导致系统无限循环。
该段落可能为AI生成的概率为：87%
4.5.2 GoalVerifierAgent

GoalVerifierAgent 在 ActionLoopStatus 为 SubGoalSwitch 或 MayStuck 时触发，对"该子目标是否真的完成了"进行二次独立验证。与 ExecutionReflectorAgent 不同，GoalVerifierAgent 获取该子目标执行过程中所有动作步骤的截图序列（利用 concat_images_with_index 合并为一张含时间序列索引的拼接图），从整体视角判断子目标完成情况。
该段落可能为AI生成的概率为：95.3%
输出包含三种子目标完成状态：
- A：已完成，可进入下一子目标；

- B：已完成当前子目标，且额外提前完成了后续某些子目标，需要计划跳转（触发 GlobalRePlanner 或 AppRePlanner）；
该段落可能为AI生成的概率为：22.5%
- C：未完成，附带 `sub_goal_correctness` 判断子目标本身是否可达（false 则触发重规划）。
该段落可能为AI生成的概率为：57.1%
这种"执行环内反思 + 外层验证"的双层机制，有效降低了因单帧截图信息不完整而导致的误判率。

4.6 用户交互模块

4.6.1 交互触发与问题生成

当 ActionDeciderAgent 输出的第一个动作为 `NeedInteraction` 时，动作执行器跳过执行，UserInteractorAgent 接管控制流。
该段落可能为AI生成的概率为：16.3%
UserInteractorAgent 从短时记忆中获取：（1）用户原始指令；（2）当前屏幕状态；（3）ActionDeciderAgent 的 `user_interaction_thought`（即决策过程中记录的"为何需要询问用户"的推理描述）。
该段落可能为AI生成的概率为：95.3%
基于上述信息，UserInteractorAgent 调用 LLM 生成向用户展示的问题文本和选项列表（UserInteractInfo），问题语言依据指令语言（`ins_language`）自动适配为中文或英文，通过 UserDialoger 发送给用户并等待回复（阻塞式等待，超时则按默认选项处理）。
该段落可能为AI生成的概率为：93.2%
4.6.2 用户回复解析与指令补充

该段落可能为AI生成的概率为：57.6%
生格式断层。

`interaction_status` 字段取 A（回复有效，信息已获取）或 B（回复无效或用户拒绝，保持原指令），为 A 时 `interaction_summary` 非空；为 B 时系统以空摘要恢复执行，ActionDeciderAgent 在已知用户拒绝或未给出有效信息的前提下自行做出决策，通常倾向于选择最保守的默认路径推进。发布 UserInteractionReflect DONE 事件后，整个交互过程对动作环的其他模块完全透明——ShortTimeMemoryManager、ExecutionReflectorAgent 等均无感知到交互的发生，不改变任何其他状态机的运行。

4.7 记忆管理模块

4.7.1 短时记忆管理（ShortTimeMemoryManager）

ShortTimeMemoryManager 是整个系统的记忆协调中心，维护两类会话级数据结构：

ActionLoopWorkingMemoryManager（动作环工作记忆）： 存储当前应用级执行会话的完整状态，包括当前指令（InstructionInfo）、当前计划（AppPlanInfo 带 [COMPLETED] 标记）、子目标执行状态（当前子目标文本、执行次数、错误次数）以及动作执行记忆列表（ActionExecutionMemory 列表，每项包含起始屏幕、结束屏幕、动作内容和反思结果）。

InteractionLoopWorkingMemoryManager（交互环工作记忆）： 存储当前交互轮次的问题内容、用户回复和解析摘要，供交互反思智能体使用。

LongTimeMemoryManager 管理跨会话持久化的 App 操作经验知识库。

存储结构。 知识库按类型分为三个目录：

- `knowledge/execution_tips/`：存放各 App 的执行技巧，以 App 包名为文件名（如 `com.mcdonalds.gma.cn.json`），以及跨应用通用技巧（`common.json`）；

4.7.3 短时记忆与长期记忆的协作模式

短时记忆与长期记忆在系统中扮演不同角色，两者的协作构成了系统在单次任务内和跨任务长期学习两个维度上的完整记忆链路。

在单次任务执行期间，动作环的各个决策智能体通过短时记忆获取当前任务状态。ActionDeciderAgent 每轮决策前批量请求最近 N 条 ActionExecutionMemory 和当前子目标状态，避免重复调用带来的系统开销。ShortTimeMemoryManager 的 `ON_CALLED` 接口支持在单次请求消息中打包多种 ShortMemoryCallType 查询，各类记忆的返回结果以 CallType 为键构成字典，调用方按需取用。这一设计在实践中显著减少了消息总线的往返次数，在长程任务中效果尤为明显——一次标准的 ActionDeciderAgent 请求通常需要同时获取指令、子目标、计划和执行历史四类信息，合并为单次调用可将消息延迟降低约 60%。
该段落可能为AI生成的概率为：96.9%
在任务切换边界，ShortTimeMemoryManager 将已完成的 AppSessionMemory 归档并通过 pickle 序列化到磁盘，作为恢复点（restore point）保存。恢复点文件名包含时间戳，支持多个历史版本并存，便于调试和异常恢复。这一机制对于跨应用长程任务尤其重要：当全局任务包含多个应用级子任务时，每个子任务完成后都会触发归档，即使在后续子任务中系统异常退出，也可从最近的归档点重新启动。
该段落可能为AI生成的概率为：96.9%
长期记忆的写入则发生在任务维度之外——每次成功或失败的任务完成后，AppLearnerAgent（当前为设计预留接口）调用 LongTimeMemoryManager 的写入接口，将从执行轨迹中提炼的 tip 条目追加到对应 App 的 JSON 文件，并通知 LongTimeMemoryManager 更新内存中的 VectorStoreIndex，使新知识在下一次检索中立即生效，无需重启服务。
该段落可能为AI生成的概率为：59%
这种"短时—工作—长期"三层记忆结构与人类认知系统有一定的类比性：短时记忆对应任务执行中的即时工作状态，归档记忆对应当前会话的情境快照，长期记忆对应积累的专业技能与经验。这一类比在系统设计层面具有实际指导意义：短时记忆强调访问效率和时效性，长期记忆强调检索的语义相关性和积累深度，两者的设计侧重点不同，不应混同为一个统一的存储结构。
该段落可能为AI生成的概率为：96.9%

5.3 评测基准测评结果

除自构任务集外，本文参与设计的基准（共 132 个任务，覆盖 25 个 App）对多个主流移动端 GUI 智能体框架进行了系统测评。
该段落可能为AI生成的概率为：17.5%
5.3.1 评估指标体系

本评测基准采用多维度评测框架对智能体进行评测，涵盖以下 7 个量化指标：

RCR（Requirement Completion Rate）：用户需求完成率，衡量智能体对用户真实意图的总体覆盖程度；
该段落可能为AI生成的概率为：16%
TSR（Task Success Rate）：任务成功率，以全部关键检查点均通过为成功条件；

SHR（Step Hit Rate）：步骤命中率，衡量实际执行步骤与参考步骤序列的匹配程度；

ARR（Ambiguity Resolution Rate）：歧义解决率，衡量智能体在模糊参数上主动澄清或合理推断的能力；
该段落可能为AI生成的概率为：60%
ETR（Execution Trajectory Rationality）：执行轨迹合理性，从路径层面评估操作序列的合理程度；
该段落可能为AI生成的概率为：16.5%
DCR（Decision Consistency Rate）：决策一致性，衡量智能体多次执行同类任务时决策的稳定程度；
该段落可能为AI生成的概率为：25%
IGR（Interaction Gain Rate）：交互增益率，仅针对支持交互的系统，衡量主动交互带来的需求完成率提升。
该段落可能为AI生成的概率为：12.7%
5.3.2 本系统 在评测集准上的表现

在 RCR 和 TSR 两个核心指标上，本系统（6，GPT-4o + Gemini-3-Flash）分别达到 48.7% 和 40.4%，在支持交互的框架中处于领先位置，与官方框架（AutoGLM-9B）相当，明显高于同样使用 GPT-4o 的 AppAgent（27.9% / 10.8%）和 MobileAgentV2（33.8% / 20.4%）。这说明在相同骨干模型条件下，本系统 的多智能体架构和双环执行机制对整体任务完成率有实质性提升。
该段落可能为AI生成的概率为：96.9%
IGR 指标揭示了交互机制的价值：本系统 6 的 IGR 为 17.7，即相比非交互版本，开启交互环后用户需求完成率提升了约 17.7 个百分点。这与本文 5.2 节自构任务集的观察相互印证——交互机制对于缩小模糊指令条件下的需求满足缺口效果显著。7 号（GPT-4o + UI-TARS-7B）的 IGR 仅为 6.7，说明执行端模型的能力差异会影响交互增益的实际兑现程度：规划层发出了澄清请求，但执行端若不能准确处理后续指令，增益就会被吞噬。
该段落可能为AI生成的概率为：94.8%
ARR 的结果需要单独解读。本系统 6 的 ARR 仅为 2.0，看起来偏低，但这与 本系统 的设计哲学有关：ActionDeciderAgent 倾向于在有把握时直接选择合理默认值推进，而不是对每个模糊参数都触发交互询问，以避免过度中断用户流程。ARR 低并不等于歧义解决能力弱——结合 RCR=48.7% 的高完成率来看，本系统 更多通过规划层的全局意图推断来隐式消解歧义，而非依赖频繁的显式询问。相比之下，AppAgent 的 ARR=36.9 但 TSR 仅 10.8，说明高频询问并不必然带来高任务成功率，询问质量比询问数量更关键。
该段落可能为AI生成的概率为：96.9%
在 ETR（执行轨迹合理性）方面，本系统 6 得分 73.3，与 UI-TARS 端到端模型（72.1）相近，说明基于 GPT-4o 规划 + 多智能体协作的工作流路线在路径合理性上与经过大规模训练的端到端模型不相上下。这对于一个以工程灵活性和可定制性为设计目标的框架而言，是一个令人满意的结果。
该段落可能为AI生成的概率为：96.9%
5.3.3 指令清晰度与系统表现的关联分析

将自构任务集和评测基准上两组实验的结果对照来看，可以归纳出若干一致性规律。

模糊指令是最大的失效来源。 FOOD-001 案例中，非交互版本在"帮我点个汉堡"这一只有基础意图、缺乏所有关键参数的指令下，触达了全部流程节点（流程覆盖率 1.0），却在订单内容上发生了严重偏离——将无关推荐商品误加入购物车。在 Ambiguous 等级下，各系统的 RCR 普遍低于其他清晰度等级，非交互式系统的衰减尤为明显。
该段落可能为AI生成的概率为：77.8%
清晰指令并不自动带来高成功率。 FOOD-003 的案例给出了一个反直觉的提醒：指令参数全面并不意味着执行无虞。App 的持久状态（历史地址、默认时间设置）会在系统未主动核查时静默覆盖用户的明确要求。这一类问题在单纯的指令清晰度分类框架中难以被覆盖，需要评测基准对"执行上下文感知能力"进行独立度量。
该段落可能为AI生成的概率为：95.3%
交互增益与执行端能力强相关。 本系统 6 和 7 的对比清晰地表明，规划端给出了相同的交互决策，但执行端换用能力较弱的模型后，IGR 从 17.7 下降至 6.7。这说明交互增益不是一个纯规划层指标，而是规划 + 执行的联合产物——规划层识别了歧义并发起了询问，但只有执行层准确理解并落实了澄清结果，增益才能真正兑现。
该段落可能为AI生成的概率为：17.2%
这一发现对系统设计有直接启示：在追求交互式 GUI 智能体的改进时，仅优化询问策略是不够的，执行端对澄清后指令的理解和处理同样是瓶颈。本系统 当前架构将这两个维度交由不同智能体分工负责（UserInteractorAgent 处理交互，ActionDeciderAgent 处理执行），有助于独立优化各环节，这也是多智能体分工架构相较于端到端模型在可维护性上的典型优势。
该段落可能为AI生成的概率为：95%
5.4 实验局限性讨论

本章实验结果需在以下几点局限性背景下解读。

任务集的代表性问题。 自构任务集当前仅包含麦当劳 App 点餐场景的三级清晰度任务，覆盖域过窄。FOOD-001 至 FOOD-003 共享同一个应用、同一类操作目标，相互之间的差异仅在于指令清晰度，而非任务类型的多样性。这意味着实验结论主要适用于"结构化流程类应用（外卖/电商等）"场景，能否推广到社交类（微信）、工具类（地图、日历）等操作逻辑差异较大的应用，尚需进一步验证。
该段落可能为AI生成的概率为：96.9%
执行版本的一致性约束。 三条任务由同一个版本的 本系统在相对封闭的条件下执行，但真实 App 的状态会随时间变化（菜品上下架、UI 更新、地址缓存等），FOOD-003 中配送地址被 App 缓存值覆盖的现象正是这一问题的体现。实验条件的严格控制与真实使用场景之间不可避免地存在差距，这也是移动端 GUI 智能体评测的普遍挑战。
该段落可能为AI生成的概率为：28.8%
GPT-4o 评估者的潜在偏差。 执行分析报告由 GPT-4o 基于截图序列生成，评估得分（如 execution_score=0.65）来自 LLM 的量化判断而非人工核查。尽管评估提示词经过了结构化设计，但 LLM 评估者与人类评估者之间的对齐程度仍有不确定性，且同一组截图在不同随机种子下可能产生小幅评分波动。本评估框架通过人机对比实验验证了较高的相关性。
该段落可能为AI生成的概率为：96.9%
第6章 总结与展望

6.1 工作总结

本文的出发点是一个在工程实践中反复遭遇的现实问题：用户给出的指令往往是不完整的，而现有的非交互式 GUI Agent 在这类情况下的应对方式——靠模型先验猜测缺失信息——在很大比例的场景下会产生偏离用户真实意图的执行结果。本文围绕"让系统在发现歧义时能够主动发起澄清"这一核心设计目标，实现了 多智能体移动端助手系统，并参与构建了支持交互式评测基准。
该段落可能为AI生成的概率为：94.1%
在架构层面，系统将全局跨应用规划、单应用内执行、长期知识积累三类职责分配到三个独立的层，各层通过 Citlali 消息总线以事件驱动方式异步协作，使得替换某一层内的骨干模型或增加新的智能体模块不会影响其他部分的正常运行。 执行层内部的双环设计是本文最核心的工程贡献：动作执行环负责推进子目标序列，用户交互环在 ActionDeciderAgent 判断需要澄清时接管控制流，两者通过 `NeedInteraction` 动作类型和 ShortTimeMemoryManager 进行状态衔接，整个交互过程对动作环的其他模块完全透明。 面向模糊指令的评测基准的评测数据给出了一个量化佐证：在 GPT-4o + Gemini-3-Flash 配置下，本系统的交互增益率（IGR）达到 17.7，反映了开启交互环后需求完成率的实质性改善。
该段落可能为AI生成的概率为：65.7%
感知层的 SSIP 模块解决了"不同骨干模型对屏幕信息格式需求不同"这一工程兼容性问题——视觉模型走 SoM 截图标注路径，纯文本模型走 AT 解析 + 图像节点视觉描述补全路径，GridMark 作为两条路径都无法覆盖时的回退手段。记忆层将长期知识按用途拆分为规划技巧、执行技巧、错误恢复技巧三个独立 RAG 索引，以应用包名作为过滤条件隔离不同应用的经验，使得某个 App 积累的具体交互知识不会干扰其他 App 的决策。
该段落可能为AI生成的概率为：95.3%
在评测工作上，提出一个新的评测基准的意义不仅在于提供了一个对本系统 的外部验证，更在于它把"指令清晰度"作为一个一等公民的评测维度引入进来——过去大多数基准假设用户指令是完整且无歧义的，而本文的评测基准揭示了非交互式系统在降低的清晰度条件下性能骤降这一普遍规律，为这个方向的后续研究提供了可对比的量化基线。
该段落可能为AI生成的概率为：83.1%
6.2 不足与局限

做完这个系统之后，回头来看，觉得有几处问题是比较明显的，值得直接说清楚。

最直接的一个局限是自我学习模块（AppLearnerAgent）目前只是一个设计预留的接口，tip 条目的产生在实践中仍然依赖人工整理。这意味着系统的"越用越好"这一核心设计预期，在当前版本里并没有真正实现——RAG 索引里的知识是静态的，不会随着使用自动增长。这也直接限制了第5章评估的深度：由于缺乏自动积累的动态知识，长期记忆效益的测量只能依赖在自构建评测集准的对比数据，而没有在其他任务集上给出直观的前后对比。
该段落可能为AI生成的概率为：96.9%
另一个在实验中暴露得比较清楚的问题是 FOOD-003 案例揭示的：系统对 App 内部的持久化状态（历史地址、默认配送时间）缺乏主动核查意识，会被默认值静默覆盖用户的明确要求。这说明当前的执行路径中缺少一个"在进入确认页前回头核查关键参数是否与指令一致"的验证环节。GoalVerifierAgent 目前只验证子目标是否完成，并没有验证"完成的内容是否和指令参数匹配"，这是一个值得专门设计的扩展点。
该段落可能为AI生成的概率为：94.6%
跨应用上下文传递目前以自然语言字符串的形式完成，在涉及动态数据（比如从日历读出来的会议地点、从上一个订单获取的取件码）的场景里容易出现格式不对齐或信息丢失，这对于真正意义上的多应用协作任务是一个潜在的可靠性瓶颈。
该段落可能为AI生成的概率为：12.7%
6.3 未来工作展望

最值得投入的一个方向是把自我学习流水线真正跑通。如果 AppLearnerAgent 可以在每次任务结束后自动分析执行轨迹、判断其中哪些步骤值得写成 tip、并增量更新向量索引，那么系统对特定应用的适应速度会快得多，尤其是对于那些有固定流程逻辑的外卖、打车类应用。这并不需要完全的无监督学习，一个合理的中间态是"LLM 生成候选 tip + 人工低频审核"的半自动化流水线，先把自动化率提上去。
该段落可能为AI生成的概率为：95%
对于频繁执行同类任务的场景（典型的如"每天同一时间点同一家的同一份早餐"），有一个更直接的加速思路：把成功的执行轨迹直接压缩成一个可参数化的任务模板，后续触发时跳过规划和逐步决策，直接走模板执行路径。这本质上是把 Mobile-Agent-E 的 Shortcut 思路做到更细粒度，本系统 V2 的规划文档里已经列了这个方向，但实现上还有相当多工作要做。
该段落可能为AI生成的概率为：89.7%
安全问题在这类系统里不应该被放在"未来方向"里轻描淡写地提一句然后跳过。一个能控制手机做任意操作的系统，提示注入攻击是真实的威胁——恶意的 App 弹窗完全可以尝试用自然语言"指令"诱导 ActionDeciderAgent 执行不在原始任务范围内的操作。如何建立一套从规划层到执行层的意图一致性校验机制，是这类系统走向实际部署之前必须认真设计的部分，而不仅仅是一行免责声明。
该段落可能为AI生成的概率为：30.4%
