智能手机代理也就是我们常说的AI助手，正变得越来越重要，他们能帮我们高效的控制手机，完成各种日常任务。随着大型语言模型和多模态大模型的崛起，车类代理的能力显著提升，但问题来了，这么多代理谁更厉害？怎么才能公平的比较他们，这就需要一个可靠的基准。



现有的评估方法说实话有点跟不上趟，很多基准只关注英文系统应用，比如邮件日历这些，但咱们日常用的很多是中文应用，还有各种花里胡哨的第三方APP，广告弹窗满天飞，这些复杂场景在现有基准里基本看不到，而且评估的代理数量也少得可怜，通常不到5个，这怎么能全面反映技术进步？



更重要的是很多自动化评估方法，要么依赖人工费时费力，要么依赖特定数据，比如Android view hierarchy，但在webview这种场景下就失效了，扩展性很差。所以我们推出了18奔驰一个全新的智能手机代理基准，它的目标很明确，就是要建立一个全面的平台，用来公平系统的评估，至少10种不同的智能手机代理。



我们希望通过spa bench能够更清晰的看到当前技术的瓶颈在哪里，未来的方向又该是什么？Space主要有三大亮点，第一我们构建了一个极其丰富的任务集，覆盖了英文和中文应用，包括单应用和跨应用的场景，难度还分了等级，总共340个任务。第二，我们设计了一个即插即用的框架，可以轻松集成超过10种不同的代理，而且支持快速部署和测试。第三，我们开发了一套自动化评估流水线，能自动衡量代理的性能，无需人工干预



还能评估资源消耗。



咱们先细说说spa并nhh的第一个核心贡献，这个庞大的任务集，它包含了340个精心设计的任务，其中150个是单应用任务，比如在某个APP里查找信息设置参数，另外20个是跨应用任务，比如先在地图上找地点，再用导航APP规划路线。特别值得一提的是，我们不仅包含了英文应用，还加入了大量中文应用，以及58个真实的第三方应用，这大大增加了评估的难度和真实性，但应用任务还分了三个难度级别，从简单到复杂逐步递进。



为了保证评估的准确性，我们还为每个任务都标注了人类执行的步骤和截图，作为后续评估的黄金标准。



第二个核心贡献是我们的即插即用代理框架，这个框架非常灵活，目前已经整合了11种不同的智能手机代理，未来想加入新的代理也非常方便。最关键的是每个代理都在一个独立的隔离的环境中运行，互不干扰，保证了测试的纯净度。我们利用Android的模拟器来实现大规模并行测试，一台机器就能同时运行多个模拟器实例，通过快照技术，每次测试前都能快速恢复到预设的初始状态，比如登录状态，已安装的应用等



这样就避免了重复繁琐的配置工作，大大提高了测试效率。



第三个核心贡献是我们的自动化评估流水线，这套流水线定义了7个关键指标来衡量代理的性能，首先是任务完成度相关的指标，成功信号，就是任务到底成没完成，步骤比例，看代理执行了多少不必要的动作，终止原因，分析任务为什么结束，是自己认为完成了还是超步数了或者出错了，还有提前终止和超时终止这两个信号，分别衡量代理是否过早或过晚的结束了任务。



其次是资源消耗指标，时间花费和API成本，特别是对于使用云端模型的代理，API调用成本是个重要考量，我们采用了一种混合评估方法，结合了代理的动作序列和最终达到的状态，这样既能捕捉到执行过程中的错误，也能判断最终结果是否符合要求，而且这种方法不需要为每个任务单独编写验证逻辑，具有很强的可扩展性。



这张表直观地展示了spa编制与其他几个主流智能手机代理基准的对比，可以看到space在多个方面都处于领先地位。比如它覆盖了更多的第三方应用，跨应用任务中文应用，并且任务难度分级，评估的代理数量也更多，提供的评估指标维度也更丰富，我们还提供了手工构建的验证数据，确保了评估结果的可靠性。



最重要的是spa bench能够同时利用动作和状态信息进行成功检测，这在其他一些基准中是缺失的，可以说spa提供了一个更全面更严格的评估环境，这些高质量的任务是怎么来的呢？主要是由我们的人工标注员创建的，对于单应用任务，我们选择了大家常用的APP，也参考了之前的研究，然后根据每个APP的核心功能，按照详细的标注指南来设计任务，每个任务都有清晰的描述，明确的难度级别，以及人类执行该任务的完整步骤截图



这就是我们前面提到的黄金步骤。



对于跨应用任务，我们主要参考了国外odyssey这个数据集，但对其任务描述和执行轨迹进行了必要的调整和重新收集。为了保证任务质量，我们有一套严格的验证流程，标注员会互相检查，确保任务清晰，轨迹准确，关键组件有效。这些任务还会在不同的设备，不同的安卓的版本和APP版本上反复测试，确保他们在真实环境中也能顺利执行。



这张图展示了我们的代理框架架构，核心是一个worker machine，它负责接收任务描述分配给不同的worker process。每个worker process就像一个独立的测试单元，它连接着一个安卓的模拟器和一个待评估的agent，agent会根据观察到的屏幕信息，比如截图生成操作指令，比如点击滑动，然后发送给模拟器执行，模拟器执行后会返回新的观察结果，形成一个交互循环。



每次开始一个新的实验循环，模拟器都会从一个预设的快照状态恢复，确保所有代理都在相同的起跑线上。这个框架最大的优点是易于扩展，想加入新的代理，只需要将其接入框架即可，不需要做太多改动，评估的关键在于如何判断任务是否成功。对于单应用任务，我们采用了粗略到精细的两阶段检测，首先用我们预先标注的关键组件进行快速匹配，如果代理的最终截图里没有这些关键组件，那肯定是失败了。



如果通过了粗略检测就进入精细检测阶段，由一个mlm模型来综合评估整个执行轨迹，判断任务是否真正完成，这种方法在保证效率的同时也取得了很高的准确率。F一分数接近0.9，对于更复杂的跨应用任务，我们采取了不同的策略，我们先用ml将整个任务分解成一系列子任务，比如现在apple a完成什么，再在APP B完成什么，然后我们根据应用切换的顺序，将代理的执行轨迹分割成对应子任务的片段



再逐个评估每个子任务是否成功，这种分而治之的方法同样有效，F一分数达到了0.845，我们用C本对多种代理进行了全面的实验，总体来看，M三a代理的表现最为突出，在所有任务集上都取得了最高的成功率。



一个普遍现象是代理们在处理英文任务时表现更好，而中文任务的成功率明显偏低，这反映了中文应用的复杂性和当前模型在中文理解上的挑战。另一个重要的发现是采用代理工作流设计的代理，比如M3at3a等明显优于那些直接作为模型的代理，后者很多连基本任务都难以完成，这说明模块化设计和实时交互的重要性，跨应用任务的难度也远，超单应用任务大多数代理在这方面都遇到了很大的困难。



深入到单应用任务层面，英文任务中M3at三a和mobile agent V二表现最好，成功率在40%~64%之间，这些表现较好的代理通常都配备了反思模块，这有助于他们在遇到困难时调整策略，而不是卡住不动。



相比之下，像agent和凹凸的这样的代理表现较差，可能是因为他们在原始实现中依赖外部知识库，但在我们的基准测试中没有提供。在中文单应用任务中，mobile agent V二的表现超过了T三a，这可能是因为T三a依赖的a11Y数布局在中文APP中显得过于复杂，导致信息过载。



总体而言中文任务的成功率下降，这主要是因为中文APP本身布局更复杂，动画广告更多，而且当前的llm在中文理解和处理上仍有局限性，实验结果还揭示了核心模型和输入方式的巨大影响，使用像GPT4O这样的专有模型的代理，其性能明显优于基于微调模型的代理，同样采用代理工作流的代理，其表现也远超那些直接作为模型的代理，这表明那些在固定UI场景下训练的微调模型



虽然在特定任务上表现不错，但在面对真实世界中动态变化的UI时，泛化能力很差。



另一方面代理工作流通常会结合视觉模块，比如OCR或标记文档来获取界面信息，但这些布局文档有时并不完整，或者结构过于复杂，反而给模型带来了负担，这凸显了接地能力，也就是将模型输出的动作准确映射到界面上的坐标，是端到端完成任务的关键。尤其是对微调模型来说，这是一个巨大的挑战，跨应用任务的结果令人深思。



几乎所有代理在这个任务上的成功率都非常低，大部分都低于10%。即使是表现最好的M3a，也只完成了40个跨应用任务，中的6个，这充分说明了跨应用任务的难度。这类任务不仅需要更多的步骤，还需要更强的推理能力和在不同应用间切换时保持记忆的能力，比如你可能需要先在ma里找到某个信息，然后在APP里搜索相关内容，最后在FC里保存结果，在这个过程中代理必须记住之前的步骤和上下文



即使是专门为跨应用任务设计的AutoCAD，也常常在应用切换时迷失方向，无法完成整个流程，这表明当前的代理在处理需要长期记忆和跨环境推理的复杂任务时，仍然存在很大的不足。



除了成功率，我们还分析了其他指标，在步骤效率方面，采用代理工作流的代理通常表现更好，成功率越高，平均步骤比例就越低，这意味着他们在完成任务时更少走弯路。M三a在这方面尤其突出，它的平均步骤比例甚至低于人类执行的步骤，这可能得益于它能定义一些组合动作，或者利用一些捷径。在任务终止方面，我们发现成功率高的代理，其自我报告完成率src也高，最大步数到达率MS R则低



但有趣的是提前终止率PT和超时终止率otr之间存在一种权衡关系，ptrd的代理往往ot会比较高，反之亦然。



比如cx的代理他的PT二最低，但ot二却最高，这说明代理内部判断任务是否完成的机制还需要进一步优化。既要避免过早结束，也要避免不必要的拖延。



错误处理机制对代理的鲁棒性至关重要。我们发现那些缺乏有效错误处理机制的代理，一旦遇到执行错误，比如解析模型输出失败，或者无法访问某个必要的文件，就容易直接崩溃或提前终止，导致任务失败。因此开发更好的错误检测和恢复策略。比如尝试不同的操作路径，请求澄清等，对于提高成功率非常关键。



最后我们来看成本和效率，直接作为模型的代理，虽然没有API成本，但成功率太低，实用性堪忧。在代理工作流中，凹凸周围的每部成本最低，但速度慢，成功率也不高。M三a和T三a速度快，成功率也高，但每部的偷啃成本较高。Mobile agent V二成本适中，但执行时间最长，这些数据告诉我们，目前的代理在效率和成本之间很难找到平衡点，如果用户需要等待几十秒甚至几分钟



或者花费几美元才能完成一个简单的任务，那还不如自己动手，这限制了代理在实际生活中的应用价值。



通过spa编制的评估，我们总结了几个关键的发现和未来的研究方向。



首先UI理解和动作接地是核心难题，尤其是在处理复杂动态的中文界面时，其次我们需要更多样化的训练数据，涵盖不同的语言指令格式和应用场景。



第三，记忆保持能力亟待加强，尤其是在处理长序列跨应用的任务时。第四，代理需要更强的反思和错误处理能力，能够从失败中学习，而不是一错再错。第五，任务终止的判断机制需要更精准，减少过早或过晚结束的情况。最后也是非常重要的一点，就是执行效率和成本必须优化，才能让代理真正走进用户的生活。未来我们需要在这些方面持续努力，开发更强大的视觉感知模块，构建更全面的微调数据集，探索新的记忆机制



强化反思和错误处理能力，改进任务终止判断，以及最关键的是优化执行时间和成本，让智能手机代理真正变得实用高效经济。
