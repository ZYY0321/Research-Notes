SPA-BENCH 论文全文详细阐述
标题与作者信息
标题：SPA-BENCH: A COMPREHENSIVE BENCHMARK FOR SMARTPHONE AGENT EVALUATION
发表信息：作为会议论文发表于 ICLR 2025
作者单位：华为诺亚方舟实验室、哈尔滨工业大学（深圳）、天津大学、伦敦大学学院 AI 中心
摘要（ABSTRACT）
智能手机代理在帮助用户高效控制设备方面愈发重要，基于多模态大语言模型（MLLM）的方法成为关键方向。公平比较这些代理至关重要，但面临任务范围多样、不同实现代理集成及通用评估流程设计等挑战。本文提出 SPA-BENCH，一个综合智能手机代理基准，用于在模拟真实环境的交互中评估基于（M）LLM 的代理。其三大贡献包括：

多样化任务集：覆盖中英文系统及第三方应用，聚焦日常高频功能；
即插即用框架：支持与安卓设备实时交互，集成超 10 个代理并可灵活扩展；
新型评估流程：自动评估多维度性能，包含 7 项与任务完成度和资源消耗相关的指标。实验揭示了移动 UI 理解、动作接地、记忆保持和执行成本等挑战，并提出未来研究方向。SPA-BENCH 开源地址：https://ai-agents-2030.github.io/SPA-Bench/。
1 引言（INTRODUCTION）
大语言模型的应用扩展
LLM 和 MLLM 的发展推动了 AI 代理在多领域的应用，智能手机控制是重要方向。代理主要分为两类：
代理即模型：微调或预训练（M）LLM 用于代理任务；
代理工作流：依赖现成模型和模块化设计。
代理与手机交互的信息来源包括屏幕观察、Android 视图层级 XML 数据或两者结合。
现有基准的局限性
现有研究采用动作、状态或混合评估方法，但存在三大不足：
聚焦英文系统和谷歌套件应用，缺乏广告等复杂场景；
评估代理数量通常少于 5 个，且多为同代理变种；
自动化检测依赖手工验证逻辑或不可访问数据（如 WebView 应用无 XML 数据）。
SPA-BENCH 的设计
包含 340 个任务（150 单应用 + 20 跨应用 × 中英文），集成 11 个代理至统一框架，结合自动化评估流程。实验表明代理工作流类代理性能优于代理即模型类，但受时间和成本限制仍难以实际部署。
2 相关工作（RELATED WORK）
智能手机代理
早期代理（如 Siri）依赖系统 API，近年（M）LLM 代理通过 UI 交互实现通用性，按 UI 观察方式分为文本、视觉或混合方法。SPA-BENCH 评估三类代理以全面比较。
智能手机代理评估
成功率是最常用指标，自动化检测分为动作、状态和混合方法。现有方法多依赖手工逻辑，仅支持英文简单应用，而 SPA-BENCH 的混合方法支持更广泛场景且无需手工干预。
基准对比
与其他基准相比，SPA-BENCH 支持第三方应用、跨应用、中文任务，任务数量 340 个，代理 11 个，指标 7 项，且无需手工验证逻辑。
3 SPA-BENCH 任务（SPA-BENCH TASK）
任务概述
应用覆盖：39 个英文应用 + 29 个中文应用，分 8 类（如工具、社交、购物），含 58 个第三方应用；
任务构成：150 单应用任务 + 20 跨应用任务 / 语言，单应用分 3 难度级（L1≤5 步，L2≤10 步，L3≤15 步），跨应用难度由涉及应用数决定（L1=2 应用，L2=3 应用）。
任务构建方法
人类注释：
单应用任务：定义清晰目标、人类执行轨迹（相邻截图仅 1 动作）、最终状态关键文本组件（如 “通知历史已开启”）；
跨应用任务：注释任务描述和轨迹，因最终状态灵活。
验证流程：测试不同安卓设备、版本和应用版本，确保任务可行。
难度分级示例
单应用任务（Deliveroo）：
L1：搜索麦当劳；
L2：搜索麦当劳并查找薯条；
L3：添加小份和中份薯条至购物车并确认。
跨应用任务：如 “用 LinkedIn 搜索客服职位，在 Keep 创建笔记记录公司名”（L1，2 应用）。
4 代理框架（AGENT FRAMEWORK）
统一即插即用框架
工作机管理任务分配和结果收集，每个工作进程连接安卓模拟器和代理，支持多进程并行；
代理通过截图观察和点击、输入等动作交互，实验前恢复模拟器快照（如已安装应用、登录状态）。
模拟器与一致性保障
安卓模拟器支持并行测试，24 核 CPU 可同时运行 8 个模拟器；
快照机制保存系统状态，减少重复设置，但部分应用数据需手动重置（如订阅频道）。
5 自动化评估流程（AUTOMATED EVALUATION PIPELINE）
七项评估指标
完成度相关：
成功信号：二进制指标，单应用与跨应用采用混合检测；
步骤比率：成功任务中代理步骤与人类 “黄金步骤” 的比值；
终止原因：自我报告完成、达到最大步骤、执行错误；
过早终止信号：代理误判完成但实际未成功；
逾期终止信号：代理未识别完成而继续执行。
消耗相关：
6. 耗时：任务执行时间（秒）；
7. API 成本：API 调用费用（美元），仅适用于专有 MLLM 代理。
成功检测方法
单应用检测：粗到细流程
粗检测：OCR 提取截图文本，匹配人类注释的关键组件（如 “通知历史”）；
细检测：若粗检测通过，用 GPT-4o 评估任务描述、截图及动作，英文 F1=0.926，中文 F1=0.884。
跨应用检测：分阶段评估
子任务生成：MLLM 按应用拆分任务，人类审核；
轨迹分割：按应用顺序分割截图，若分割无效则任务失败；
顺序检测：逐个评估子任务，依赖前序成功，F1=0.845。
6 实验（EXPERIMENTS）
成功率概览
M3A 代理在所有任务集成功率最高；
代理普遍英文任务表现优于中文，代理工作流类优于代理即模型类，跨应用任务难度高于单应用。
单应用任务分析
英文任务中 M3A、T3A、MobileAgentV2 表现最佳（成功率 0.640-0.433），中文任务中 MobileAgentV2 因依赖 OCR 和截图，步骤令牌数（12,400）低于 T3A（22,000）；
中文任务成功率低因（M）LLM 中文能力有限，且应用 UI 更复杂（如广告、动画）。
跨应用任务挑战
多数代理仅 M3A 能完成少量跨应用任务（6/40），需多步骤推理和应用切换记忆；
代理常因上下文丢失或动作错误失败，如 OdysseyAgent 在应用切换时遗忘前序操作。
效率与成本瓶颈
代理工作流类中 AutoDroid 成本最低（$0.008 / 步），但耗时 34 秒 / 步；
M3A 和 T3A 效率高但成本约 $0.10 / 步，MobileAgentV2 耗时 56.1 秒 / 步，均难以达到人类使用效率。
7 关键洞察与未来方向
改进方向
UI 理解：增强视觉感知模块处理复杂中文 UI；
数据集多样性：包含多语言、跨应用场景；
记忆机制：支持长序列任务的上下文保持；
错误处理：添加反射模块和自纠正策略；
执行效率：优化模型输入减少令牌成本。
结论
SPA-BENCH 揭示现有代理最高成功率不足 70%，代理工作流类在动作接地和泛化性上占优，但成本和耗时限制实际应用。未来需改进记忆、错误处理和效率，推动智能手机代理实用化。
