Abstract
智能手机智能体在帮助用户高效控制设备方面日益重要，基于（多模态）
大语言模型（MLLM）的方法正成为关键竞争者。公平比较这些智能体至
关重要但极具挑战性，需要涵盖多样化的任务范围、整合不同实现方式的
智能体，并建立可泛化的评估流水线以全面评估其优劣。本文提出 SPA￾Bench，一个全面的 SmartPhone Agent Benchmark，旨在交互式环境
中评估（M）LLM-based 智能体的表现，该环境模拟真实世界条件。SPA￾Bench 提出三项核心贡献：（1）涵盖系统应用与第三方应用的多样化任
务集，支持中英文双语，聚焦日常使用中的常见功能；（2）即插即用框架，
支持与安卓设备的实时智能体交互，集成超过十种智能体，并具备灵活扩
展能力；（3）一种新颖的评估流水线，可自动从多个维度评估智能体性
能，涵盖与任务完成度和资源消耗相关的七项指标。我们在多种任务和智
能体上的广泛实验揭示了诸如解析移动用户界面、动作定位、记忆保持及
执行成本等方面的挑战。我们提出了未来研究方向以缓解这些困难，推动
迈向真实场景下的智能手机智能体应用。SPA-Bench 已开放获取，地址为
https://ai-agents-2030.github.io/SPA-Bench/。

随着基于 (M)LLM 的智能手机智能体数量的增长，公平的性能比较变得至关重要，这有助
于识别其优势与不足，从而日益凸显基准测试的需求 (Chan et al., 2023; Liu et al., 2023a;b;
Wu et al., 2023b)。在智能手机智能体基准测试方面，现有研究采用三种主要方法来评估智
能体：基于动作 (Xing et al., 2024)、基于状态 (Rawles et al., 2024a; Zhang et al., 2024; Lee
et al., 2024; Wang et al., 2024c)，或两者的混合方法 (Wang et al., 2024c)。每种方法都面临
特定挑战：基于动作的评估可能涉及多个正确动作序列，而基于状态的方法则难以确定动作
后的适当状态。混合方法虽可缓解这些局限性，但难点在于如何有效利用动作和状态信息。
尽管有这些努力，当前研究 (Rawles et al., 2024a; Xing et al., 2024; Zhang et al., 2024; Lee
et al., 2024; Wang et al., 2024c) 仍存在若干关键局限性：(1) 研究重点仍主要集中在英文环
境下的系统及 Google 套件应用程序（apps），这些应用通常没有广告或弹窗等干扰因素，从
而避免了引入复杂性和随机性；(2) 被评估的智能体数量通常少于五个，部分研究仅包含同
一智能体的相似变体；(3) 自动化成功检测方法经常需要人工干预（例如，为每个任务手工
设计验证逻辑），或依赖在某些情况下可能无法获取的数据（例如 Android View Hierarchy
数据，在 WebView 应用中不可用 (Xing et al., 2024)）。
本文中，我们提出了 SPA-Bench，一个专为评估超过 10 个智能手机控制智能体在日常任
务中的表现而设计的 SmartPhone Agent Benchmark。如图 1 所示，SPA-Bench 包含 340
项任务，涵盖 150 项单应用任务和 20 项跨应用任务，涉及英文、中文及第三方应用程序。
该基准将 11 个智能体整合到基于其原始实现的统一框架中。此框架与自动化评估流水线相
连，能够衡量智能体性能，并可应用于本基准之外的其他任务，无需人工干预。我们的实验
表明，遵循 Agentic 工作流的智能体优于属于“模型即智能体”类别的智能体，但前者由于
时间和成本约束，仍难以在真实场景中部署。此外，我们还对智能手机智能体面临的挑战及
未来发展方向进行了详细讨论，涵盖构建感知型移动界面、推理机制以及用户友好型应用等
主题。
总而言之，我们的综合基准带来了多项关键贡献：(1) 多样化的任务集合，包含 340 个难
度递增的任务，并附有真人轨迹标注。该集合涵盖中英文应用，包括单应用和跨应用场景，

2 相关工作
智能手机智能体。智能手机智能体旨在以类人的方式自动化移动应用上的任务。早期的智能
体，如 Siri 和 Google Assistant，依赖系统级 API 和定制化方案，限制了其通用性。最近，
基于（M）LLM 的智能体应运而生，利用用户界面（UI）实现更通用的方法。这些智能体以
（M）LLM 作为其“大脑”，同时需要“手”（动作）和“眼”（观察）来与智能手机交互。它
们基于现成或微调的模型，执行类人的操作（例如，点击、输入和滑动）。根据其观察 UI 的
方式，近期工作可分为基于文本、基于视觉以及结合型方法。基于文本的方法 (Wen et al.,
2024; Rawles et al., 2024a) 依赖 UI 文档数据（如 XML）或把视觉信息转换为文本，基于视
觉的方法 (Wang et al., 2024b;a; Zhan & Zhang, 2023; Hong et al., 2024; Bai et al., 2024; Lu
et al., 2024) 使用截图来捕捉完整的视觉上下文，而结合型方法 (Yang et al., 2023b; Rawles
et al., 2024a) 则整合文本和视觉输入以获取更丰富的信息。SPA-Bench 对三类智能体进行
全面评估，以提供其能力的综合比较。
智能手机智能体评估。对智能手机智能体进行有效评估对于识别其局限性并指导改进至关
重要。成功率是衡量任务完成情况的最常用指标，部分研究还考虑了效率。成功检测方法通
常分为两类：人工检测 (Yang et al., 2023b; Wang et al., 2024b;a)，准确率高但资源消耗大；
自动化检测，成本较低但准确率存在差异。当前的自动化方法主要依赖于手工设计的验证逻
辑，因此在无人干预的情况下难以扩展。这些方法仅限于评估仅支持英文的应用程序以及较
简单的应用程序（例如系统应用、Google 套件和开源应用），对其他第三方应用的覆盖范围
有限。这些自动化方法可进一步分为基于动作的方法、基于状态的方法以及混合方法。基于
动作的方法 (Xing et al., 2024) 将智能体的动作与人类示范进行比较，但难以应对正确动作
序列的非唯一性问题。基于状态的方法 (Rawles et al., 2024a; Zhang et al., 2024; Lee et al.,
2024) 评估是否达到了关键状态，但可能忽略细微动作。混合方法 (Wang et al., 2024c) 结
合状态和动作数据以实现更精确的成功检测。SPA-Bench 引入了两种混合方法，用于评估
单应用和跨应用任务。与其它自动化方法相比，我们的方法支持更广泛的应用程序和任务类
型。它们不依赖于手工设计的验证逻辑，因此无需人工干预即可灵活适应。表 1 对比了我们
的工作与其他基于自动化评估的智能手机智能体基准，突出了我们在多个维度上对各类智
能体在多样化任务中的全面评估能力。

3 SPA-Bench 任务
3.1 概述
SPA-Bench 构建了一个涵盖英文和中文应用的智能手机智能体任务集合，包含 39 个英文
应用和 29 个中文应用，根据核心特征分为八个类别（见附录 B.1）。该集合包含每种语言各
150 个单应用任务和 20 个跨应用任务。这些任务聚焦于反映日常使用的应用核心功能，为
评估智能手机智能体的性能提供了真实场景。引入多样化的中文应用及第三方应用增加了
任务复杂性，主要由于智能体在理解中文和导航更复杂的用户界面时面临的困难。所有任务
的完整列表见附录 B.2。

3.2 任务构建
我们的任务主要由人工标注者构建。对于单应用任务，我们选取了常用的应用程序，并补充
了相关工作中使用过的应用程序 (Yang et al., 2023b; Wang et al., 2024b)。基于每个应用的
核心特征，按照标注指南创建任务，具体包括：(1) 清晰的 任务描述，反映任务的目标和难
度等级。对于受先前工作启发的描述，我们进行了标准化处理，并分配了适当的难度等级。
(2) 人工执行轨迹，以一系列截图形式呈现。任意两个相邻截图之间仅允许执行一个操作（例
如点击、输入）。人工执行过程中的总操作数作为我们实验中的“黄金步骤”。为确保可复现
且无偏的基准，我们指导人工标注者避免无关操作，并禁止使用受推荐算法或用户特定历史
等因素影响的动态快捷方式。(3) 最终状态的关键组件，即如果任务成功完成，则必须出现

4.2 基于快照的模拟器用于一致性测试
该框架将 Android 模拟器集成作为物理设备的可扩展替代方案，能够复现大部分 Android
功能，实现并行测试和快速实验部署。例如，一台 24 核 CPU 搭配 64GB 内存的设备可根
据智能体的资源需求，同时支持多达八个模拟器或工作进程。
为确保一致性，可从快照中快速加载模拟器，这些快照能够捕获并恢复系统状态（例如已安
装的应用程序、登录凭证和本地设置）。通过保留预先配置的设置（例如用于消息任务的预

5 自动化评估流水线
5.1 指标
我们定义了七个关键指标以进行全面评估：
完成相关指标. (1) 成功信号–任务成功的二元指示。对于单应用和跨应用任务，我们开发了
两种不同的混合方法，利用动作和状态信息，允许存在多种有效执行路径。这些方法消除了
对人工评估者和手工设计的评估逻辑的需求（详细内容见第 5.2 节）。(2) 步骤比率–通过比
较智能体步骤与人类步骤（即第 3.2 节中的“黄金步骤”）来衡量执行效率。仅当任务成功
时（即成功信号为“true”）才考虑此指标。比率越高，表示存在越多不必要的动作，效率
越低。(3) 终止原因–解释任务终止的原因，包括智能体自我报告的完成 (即智能体基于自身
判断主动终止任务，认为任务已成功完成)、达到配置的最大步骤限制，或执行错误（例如
无效动作）。(4) 过早终止信号–仅在终止原因为自我报告完成时适用的二元指示。当成功信
号为“false”时设为“true”，表示智能体错误地认为任务已完成。这种过早停止会降低成功
率，因为智能体在任务未完成前就误判为成功。(5) 延迟终止信号–仅在终止原因为达到最大
步骤限制时适用的二元指示。当成功信号为“true”时设为“true”，表示智能体错误地认为
任务未完成。这导致额外步骤，降低效率，因为智能体在任务结束前采取了多余的动作。
消费相关指标. (6) 耗时–任务执行所花费的时间，以秒为单位记录。(7) API 成本–使用 API
所产生的货币成本，以美元为单位衡量。然而，这两个指标仅适用于使用专有 MLLM 的智
能体，因为对于本地部署的微调模型，耗时高度依赖于计算资源，且不存在外部 API 调用
带来的货币成本。

核心模型与输入模态的影响。使用专有模型（如 GPT-4o）的智能体与基于微调模型的智能
体之间在成功率上存在显著差距。遵循 Agentic 工作流的智能体显著优于“智能体作为模
型”类别的智能体，后者常常无法完成任何任务。这与先前研究中报告的高动作匹配得分形
成对比 (Zhan & Zhang, 2023; Hong et al., 2024; Bai et al., 2024; Lu et al., 2024)，表明微调
智能体通常针对固定 UI 情景下的文本动作生成进行优化。尽管此类优化在离线环境中可能
实现高准确率，但在动态、真实世界场景中往往失效。例如，当动作坐标与真实值之间的距
离在屏幕距离的 14% 容差范围内时，点击动作被视为成功 (Rawles et al., 2024b)，但这种
容差在实际操作中可能导致对可操作元素的误判。此外，依赖预设情景限制了智能体在未见
UI 上下文中的泛化能力，也使其难以从因错误动作导致的偏离状态中恢复。 另一方面，采
用 Agentic 工作流的智能体 通常配备来自视觉模块的输入，如标记文档和标记集合 (Yang
et al., 2023a)。这些布局文档有时不完整，未能捕捉界面中所有可用的 UI 元素；在某些情
况下，其复杂性对于模型处理而言过于繁琐，如上述 T3A 案例所示。这凸显了接地能力方
面的关键差距，而接地能力对于端到端任务完成至关重要，但对于微调模型而言仍具挑战
性 (Zheng et al., 2024)。
跨应用任务中的复杂性与记忆保持。对于跨应用任务，除 M3A 外，大多数智能体在英文和
中文应用中总共完成的任务不超过 4 个。尽管 M3A 表现更优，完成了 40 个任务中的 6 个，
但整体性能仍然较低，反映出跨应用任务的复杂性。这些任务需要更多步骤、推理能力，并
能够在不同应用间切换的同时保留先前动作的记忆。在某些情况下，智能体可能几乎完成任
务，但因细微错误或遗漏要求而在最后失败，尤其是在长序列或多上下文场景中。即使专门
针对跨应用任务设计的 OdysseyAgent (Lu et al., 2024) 也难以端到端完成任务。它有时能
在单个应用内很好地处理子任务，但在应用间转移时却出现问题，凸显了在不同环境中保持
上下文和推理的挑战。这些发现表明，当前智能体，包括表现最佳的智能体，在多步骤跨应
用任务上仍存在困难，常常丢失上下文或忘记先前的动作。这突显了对更好记忆机制、增强
的跨应用推理能力以及复杂多上下文环境高级处理能力的需求 (Shinn et al., 2023; Li et al.,
2023b; Pan et al., 2024)。这些能力对于用户期望自主智能体处理的任务至关重要。

任务终止与成功率。关于任务终止，较高的成功率通常与较高的自我报告完成率（SRC）和
较低的最大步数达到率（MSR）相一致。智能体在认为任务已完成、达到步数限制或遇到错
误时会终止任务。然而，智能体并不总是能准确判断任务是否完成，导致成功率与 SRC 率
之间存在差异。这一现象可通过分析过早终止率（PTR）和过期终止率（OTR）进一步揭
示。如第 5.1 节所述，PTR 会影响成功率，而 OTR 则影响任务效率。值得注意的是，一种
模式显现出来：具有较低 PTR 的智能体往往具有较高的 OTR。这种权衡可能源于智能体
内部决策阈值的设计。例如，SeeAct 的 PTR 最低（0.100），但 OTR 最高（0.276）。这表
明智能体内部成功检测器的敏感性存在权衡，需在过早终止风险与过度延长任务完成之间
的倾向之间取得平衡。理想的成功检测器应同时最小化过早终止和过期终止，以优化任务准
确率和效率。
通过错误处理机制提升鲁棒性。错误处理机制对于提高成功率和确保可靠性能至关重要。缺
乏这些机制的智能体更容易出现失败，导致执行过程中出现错误时过早终止。常见问题包括
由于智能体无法正确将模型输出解析为有效动作而引发的解析错误。例如，输出可能缺少解
析模块所要求的特定短语，如 “Thought: ”。 一些智能体在无法访问必要输入（如 XML 文
件）时也会遇到失败。这些问题凸显了需要更好的错误检测与恢复策略，使智能体能够纠正
错误并提高其整体成功率。
实际应用中的成本与效率限制。尽管 被归类为模型即智能体的智能体 不产生 token 成本，
其执行时间随设备性能变化，但其较低的成功率使其难以部署。在 具有 Agentic 工作流的
智能体 中，AutoDroid 是成本最低的，因其基于文本输入，每步仅需 $0.008。然而，其执
行时间较长（每步 34 秒），且成功率仅为 0.327。M3A 和 T3A 虽然更快（每步低于 20
秒）且成功率更高，但由于 UI 元素生成的输入较为复杂，每步的 token 成本约为 $0.10。
MobileAgentV2 每步成本为 $0.067，相对更经济，但其复杂的视觉感知流水线导致执行时
间最长（每步 56.1 秒）。这些结果凸显了效率与效果之间的权衡。T3A 等智能体尽管实现了
相对较高的成功率和较快的执行速度，仍因高昂的货币成本而无法达到人类水平的可用性。
这些限制主要源于两个关键因素：一是 UI 信息收集与动作执行之间的延迟，当动态内容出
现时容易引发不准确；二是智能体的执行速度较慢且成本高于人类用户。若用户需要长时间
等待或支付数美元，他们不太可能依赖自主智能体完成任务，尤其是当他们自己只需几步即

6.3 关键见解
为了提升自主智能手机智能体的性能，未来的研究可能需要关注若干核心维度，包括用户界
面理解与动作定位、数据集多样性、记忆保持、反思与错误处理机制、内部任务终止识别以
及执行效率。
首先，整合更先进的视觉感知模块对于提升智能体对复杂用户界面布局的理解以及在各种
情景下实现精确动作定位至关重要。尽管使用 a11y 树和 OCR 的智能体在英文任务中表现
出相对较好的性能，但在中文任务中的效果仍受限，因为中文任务通常包含更多视觉上复杂
且动态的内容。目前，一些智能体在这些动态环境中难以准确地定位动作，常常无法识别可
操作元素，或无法将生成的动作映射到正确的坐标。未来的设计应着重构建更稳健的视觉模
型，使其能够准确理解这些环境，并在交互场景中实现端到端的任务完成。
多样化微调数据集对于提升智能体的泛化能力同样至关重要。数据集应包含多种任务指令
格式、语言以及单应用和跨应用场景，以更好地模拟真实世界条件。这将确保智能体能够应
对更广泛的交互场景，特别是在语言和用户界面复杂性各异的多语言环境中。
记忆保持机制也可以得到改进，尤其是在处理跨越多个应用的长周期多步骤任务时。当前的
智能体在执行复杂任务或应用间转移时常常丢失上下文，导致任务执行不完整。引入带记忆
的网络或情景记忆架构，可以使智能体在应用转移过程中保持上下文，这在跨应用场景中尤
为重要，因为智能体通常在这些场景中表现不佳。这些场景与需要长时间连续性和上下文召
回的实际任务非常相似。
反思与错误处理能力是另一个亟待改进的关键领域。许多智能体无法从错误中学习，反复犯
同样的错误而缺乏自我修正能力。引入类似 M3A 中的强大反思模块，可使智能体更有效地
评估自身过往行为，并动态调整策略。此外，错误处理机制——如错误识别、恢复环、自我
修正和备用策略——在不可预测的动态环境中对维持性能至关重要。智能体必须能够检测
并解决诸如无效模型输出、不可操作的用户界面元素或解析错误等问题，而非过早终止运行
或陷入无产出的动作循环。
在任务终止阶段，智能体必须仔细权衡过早终止和延迟终止的问题。一些智能体仍然难以准
确判断任务是否真正完成。例如，SeeAct 虽然表现出较低的过早终止率，但同时也存在较
高的延迟终止率。这表明，尽管 SeeAct 避免了过早结束任务，却常常无法识别任务已完成，
从而导致效率低下。一个设计良好的内部成功检测机制可以同时减少两类终止错误，从而提
高任务的准确率和效率。
最后，实际部署时需优化执行时间和成本。依赖多个模块的智能体（如 MobileAgentV2）需
要减少开销并简化执行流程，以缩短任务完成时间。与 T3A 相比，基于多模态大模型的智
能体还可专注于减小输入上下文大小，降低 token 成本，同时保留任务完成所需的关键信
息。结合轻量级模型的速度与效率以及更复杂模型鲁棒性的混合模型方法，可能为平衡性能
与成本提供一种有前景的解决方案。

7 结论
在本文中，我们提出了 SPA-Bench，这是一个用于评估智能手机智能体在多样化任务上表
现的综合性基准。该评估涵盖了英文和中文应用、单应用与跨应用场景以及不同难度级别。
我们的实验表明，即使表现最佳的智能体也仅能成功完成不足 70% 的任务，且在复杂中文
应用中的动作定位与泛化能力方面，遵循 Agentic 工作流的智能体 与 模型即智能体类别的
智能体 之间存在显著性能差距。尽管部分智能体在简单任务中表现出色，但其较长的执行
时间和高昂的成本限制了其在现实场景中的实用性。我们的研究结果凸显了对更优记忆机
制、稳健的错误处理、准确的自我评估器、推理与 UI 理解的更好融合，以及优化执行时间
与成本以实现真实部署的迫切需求。此外，基于微调模型的智能体应适应多样化的应用场
景，并聚焦于长序列决策而非孤立动作。通过构建 SPA-Bench 这一公平且可扩展的基准，
我们旨在加速开发出更高效、实用且用户友好的智能手机智能体。

A 局限性和未来工作
考虑到构建任务既耗时又耗费资源，SPA-Bench 目前包含 300 个单应用任务和 40 个跨应
用任务，中英文任务各占一半。我们计划扩展任务集的范围，并增加任务呈现的多样性（例
如，如附录 G中的初始示例所探索的，加入模糊的任务描述并模仿各种人类语气）。由于某
些应用难以通过模拟器操作，我们还旨在设计更易于实验的任务。此外，我们将多次执行实
验以确保鲁棒性。
关于我们的智能体框架，我们计划通过支持更广泛的智能体来拓展研究范围。这将包括但不
限于本地部署的智能体、基于云的智能体，以及能够操作其他智能设备（如安卓平板和 iOS
设备）的智能体。
在评估方法方面，特别是针对单应用成功检测，我们计划引入更精确的方法，并扩展对跨应
用成功检测的支持。此外，我们将定义一个更细粒度的指标，以评估智能体完成任务的详细
情况，而不仅仅依赖于简单的二元成功信号。

C.3 日志和错误
尽管任务描述和截图轨迹仍是主要的输入/输出，我们还记录了执行的动作、性能指标（步

网络故障）。预期错误源于智能体的局限性，例如无法生成有效动作，或某些功能受限。非
预期错误指不可预见的问题，如网络故障、Android 系统异常或验证码挑战。该框架会自动
重试此类任务，以避免因非预期错误而惩罚智能体，从而确保对其能力与局限性的公平、准
确评估。

D 单应用程序成功检测
D.1 粗略检测：关键部件匹配
仅凭一张截图，PaddleOCR 用于提取文本，然后将其转换为小写并连结，以减少不准确情
况。该文本将与最终状态的关键组件进行匹配（由第 3.2 节中人工标注者定义）。匹配从最
后一张截图开始，向后移动直到找到匹配项或到达第一张截图。如果未找到匹配项，则标记
任务失败，跳过精细检测。
D.2 精细检测：多模态大模型评估
如果粗粒度检测成功，则使用基于 GPT-4o 的多模态大语言模型评估器进行细粒度检测。评
估器接收任务描述、截图以及已执行的动作，以评估任务是否成功。动作信息可以以文本形
式或连结的截图形式呈现。用于多模态大语言模型评估器的提示详见附录 D.4。
D.3 方法评估与结果
为验证单应用成功检测流水线的有效性，我们将其检测结果与人工评估结果进行了对比，分

试了两种推理模式和三种动作模式以触发多模态大模型，并开展了消融实验以评估粗粒度
检测的影响。

D.4 提示模板
D.4.1 系统提示
你是一位评估智能手机操作任务的专家。你的主要职责是根据一系列按执行顺序提供的截图以及相应的任务描述，判断该
任务是否已成功完成。
### Guidelines:
1. ** 无假设 **：仅根据提供的截图进行评估。不要推断或假设未明确显示的细节。
2. ** 子任务完成 **：只有当所有子任务均成功完成后，该任务才算成功。例如，对于“访问网站 github.com。将此
网站添加到书签列表”这一任务，仅当截图显示已成功导航至 github.com 并将其添加到书签列表时，该任务才视为成
功。
3. 子任务失败的常见原因：
- ** 不完整 **：如果子任务未执行或未完成，则视为失败。例如前述任务中，访问网站但未将其添加到阅读列表，即导
致任务失败。
- 执行错误：如果截图与指令的任何部分不匹配，则子任务失败。
- ** 错误的名词/实体 **：如果子任务是“访问网站 github.com”，但截图显示的是 google.com，则该子任务失败。相
似的实体（例如“iPhone 11”与“iPhone 12”，或“驾车导航”与“步行导航”）被视为不同，若未正确执行，将导致任
务失败。
- 错误的动词/动作：如果子任务是“点赞”，但截图显示的是转发帖子，则由于动作错误，子任务失败。
4. ** 额外动作 **：如果中间截图显示所有子任务均成功，则视为任务成功，即使后续显示有额外动作。只要这些动作
不影响任务完成或导致原任务失败，此规则依然适用。
5. ** 筛选子任务 **：如果子任务涉及基于特定标准进行筛选，确保已应用筛选（即特定的应用程序功能）。如果将筛
选视为额外的搜索条件，则子任务失败。
6. 任务顺序：除非任务之间存在明确的依赖关系，否则子任务可以按任意顺序完成。
7. ** 中途完成的子任务 **：在流程中途中完成的子任务可能不会反映在最终截图中；只要符合任务要求，仍应视为已
完成。
8. ** 纠正措施 **：最初看似失败的子任务，只有在后续动作完全符合原始任务要求的情况下，才应被视为成功。
9. ** 中间步骤 **：只要最终结果符合任务要求，即使某个子任务不是一次完成的，也是可以接受的；这视为成功。
10. ** 关注概览 **：专注于整体目标，避免让细微的、不相关的内容分散对主要评估的注意力。
11. ** 界面差异 **：注意细微的界面差异（例如，不同字体样式或颜色表示选中的标签页）。

E 跨应用成功检测
E.1 子任务生成
对于跨应用任务，每个子任务都与单一应用程序相关联，且任意相邻的子任务必须使用不同
的应用程序。然而，只要在两次出现之间至少有一个不同的应用程序，同一应用程序可以多
次出现。除了“应用”和“任务描述”之外，每个子任务还包含“历史”和“记忆”字段。“历
史”字段是一个布尔值，表示该子任务是否需要从前序任务中获取信息，并在任务描述中以
高亮短语的形式体现。这些信息被称为“记忆”，由将与高亮的“历史”短语匹配的短语组
成。此类子任务由多模态大语言模型生成，随后由人工进行审查以确保质量。子任务的示例
如下，详细提示见附录 E.5。
E.2 第一阶段：轨迹分裂
第一阶段仅根据应用转移将整个轨迹分割为多个片段，为检测子任务成功做准备。此前的子
任务生成步骤为每个任务提供了一个有序的应用程序列表，表明了成功完成任务所需的操
作顺序。大语言模型结合该应用程序列表与完整的执行截图序列，对轨迹进行分割，使得每
个部分仅包含与对应应用程序操作相关的截图。如果分割无效，例如某个应用缺失或顺序错
误，则由于一个或多个应用出现错误，该任务被标记为失败。
E.3 阶段 2：顺序子任务成功检测
当分割结果有效时，即有序列表中的每个应用都具有一组唯一的截图，阶段 2 将被激活。子
任务按顺序进行检查，只有当前一个子任务标记为成功时，才会对下一个子任务进行评估。
如果某个子任务标记为成功，则其“记忆”字段中的短语（除非该字段为空）将作为后续子
任务的历史参考依据。该记忆由另一个多模态大语言模型生成，该模型根据所需短语总结当
前截图，并将相关信息附加到记忆集合中以供将来使用。如果后续子任务的“历史”字段标
记为 true，则会提取必要的短语，并与存储的信息进行匹配，以协助评估其成功与否。结合
历史数据、部分任务截图和动作详情，用于判断子任务是否成功。由于每个子任务仅涉及单
一应用，因此采用与单应用成功检测相同的多模态大语言模型评估方法。只有当所有子任务
均通过时，整个任务才被视为成功；否则，一旦有任何子任务标记为失败，任务即刻失败。

E.5.5 子任务生成
你被要求将一条智能手机控制指令拆分为一系列子任务，每个子任务对应特定的应用程序操作。对于每个子任务，应定义：
1. **app**：子任务中使用的应用程序的名称。
2. **task**：一个描述要执行动作的字符串。除非必要（例如，仅打开应用程序时），否则不要在任务描述中包含应用

短语一致（即，当 history 为 True 时）。
3. **history**：一个布尔值（True 或 False），表示此子任务是否依赖于前一个子任务的数据。
4. **memory**：如果适用，请指定当前子任务生成或检索的一条信息，该信息将传递给下一个子任务。如果不需要记忆，

- 请使用与任务描述相同的语言进行拆分任务。
- 如果同一应用程序有多个连续的子任务，则将其合并为一个子任务（即，相邻的子任务不应属于同一应用程序）。如果
在两者之间至少有一个其他应用程序的子任务，则同一应用程序的子任务是可以接受的。
默认情况下，每个子任务应相互独立，除非明确需要从前一个子任务获取数据（此时设置 `"history": True`）。

通过三个案例研究，展示了智能体执行任务的代表性场景。这些包括：(1) 由于对 XML 文
件中 UI 结构的误解，AppAgent 采取了无效动作；(2) MobileAgent 出现屏幕动态变化但未
执行任何动作、因缺乏反思导致的重复动作以及与任务描述无关的行为；(3) M3A 所采用的
组合动作。
H.1 AppAgent 在 contact_2 任务上
(a) 带注释的截图 (b) 解析后的 XML 文件
图 11: AppAgent 执行任务 contact_2 时，上一次动作之前的截图和 XML 文件。
模型生成了无效动作 tap(2)。任务描述：“将其中一个联系人的姓氏修改为 ‘Three’。
将联系人电话号码的标签更新为 Work。将公司设置为 ‘Huawei’。添加电子邮件
agent.benchmark.2024@gmail.com。将电子邮件标签设为 Work”。
如图 11 所示，在任务 contact_2 的最后一步中，AppAgent 因对 UI 结构的误读而遭遇了
关键错误。模型错误地解析了 XML，将整个弹出菜单视为单一元素，而非识别出每个独立
可操作的组件，这导致智能体可交互的控件数量减少。此外，智能体执行了一个无效动作
tap(2)，其目标是一个不可点击的元素。这一问题表明，不完善的可操作动作检测机制可能
会限制智能体在复杂 UI 层级中导航以及执行细粒度交互的能力。

H.2 MobileAgent 在 expedia_3 任务上
如图 12 和图 13 所示，MobileAgent 执行任务 expedia_3 时揭示了几个值得注意的点：(1)
尽管第二张和第三张截图之间的转移（用红色边框标出）缺少有效动作，但界面仍发生了变
化，表明在等待期间正在加载内容（即动态变化的屏幕）。(2) 智能体在界面无变化的情况下
生成了重复动作，但在多次迭代后出现了一次修正（用蓝色边框标出）。(3) 有趣的是，在任
务执行初期，智能体最初尝试与 ChatGPT 对话，这与任务描述无关。当智能体尝试执行与
任务相关的内容时，已浪费了多个步骤，导致完成任务的机会不足。
