Abstract
基于语言模型（LLM）的移动智能体因其能够直接与手机图形用户界面
（GUI）交互，并具备自主管理日常任务的潜力，正日益受到关注。尽管
其在学术界和工业界均展现出广阔前景，但由于应用程序状态无穷无尽
且可行动作序列的定义模糊，针对现有移动智能体性能的基准测试研究仍
十分有限。为应对这一挑战，我们提出了一种高效且用户友好的基准——
MobileAgentBench，旨在减轻大量手动测试带来的负担。我们首先在 10
个开源应用中定义了 100 项任务，并按多个难度级别进行分类。随后，我
们评估了若干现有的移动智能体，包括 AppAgent 和 MobileAgent，以全
面而系统地比较它们的性能。所有相关材料均可在我们的项目网页上获取：
https://MobileAgentBench.github.io，为推动学术与工业领域的发展贡
献力量。
1 引言
随着大模型 (LLMs) [1] 的出现，研究人员在机器人 [4, 20]、游戏 [22, 8] 和手机 [26, 19] 等
领域开发了多种自主智能体。其中，移动智能体因其有望提升用户体验并提供随时随地的智
能辅助而受到广泛关注。
人们几十年来一直梦想着智能个人助手（IPAs）[6]，它们能够完全自动化日常任务。自苹果公
司于 2011 年推出其数字助手 Siri [3] 以来，几乎所有领先的科技公司都推出了自己的 IPAs，
包括微软的 Cortana [15]、亚马逊的 Alexa [2] 和谷歌助手 [9]。尽管这些数字助手通过自然语
言接口（NLI）提供了免提的人机交互体验，但它们只能完成相对简单的任务，例如设置闹
钟或发送短信 [13]。对于第三方应用，开发者必须遵循并实现应用程序编程接口和协议，以
便当用户发出特定命令时，系统能够调用相应的功能。这限制了这些数字助手的可用性。

大模型在解决理解用户意图这一长期挑战方面发挥了重要作用。所展示的推理能力 [17] 突
显了基于大模型的自主智能体作为下一代智能个人助手（IPAs）的巨大潜力，这类助手不受
编程接口限制，能够直接操作图形用户界面（GUI）[21, 26]。GUI 可以表示为文本形式的视
图树供大模型使用，或以截图图像形式利用多模态大模型（MLLM）[27]。智能体的动作空间
由一系列函数构成，用以模拟人类操作，如点击、输入、滑动等。通过这种方式，大模型智
能体理论上可以实现人类用户所能完成的任何操作，且无需对现有应用程序进行任何修改。
基于大语言模型的智能手机智能体展现出光明的未来，吸引了越来越多的研究者关注这一主
题。然而，用于评估这些智能体性能的基准测试范围仍然有限。在现有的基准测试中，存在
几个普遍问题：1. 可扩展性与易用性。研究人员需要充分理解复杂的数据库结构和工具，才
能在基准测试中扩展自定义任务或将其集成到自己的代码库中 [28]。2. 鲁棒性与灵活性。仅
考虑标注的任务完成路径 [19, 24]。然而，可能存在多种成功完成任务的路径，这可能会破
坏任务成功判断逻辑。3. 真实环境。一些基准测试基于截图集合来评估智能体性能，而非
真实设备。如果智能体执行异常动作并进入未定义状态，则评估将失败 [19]。
为解决上述问题，我们提出了一种稳健的基准测试平台——MobileAgentBench，旨在评估移
动大语言模型智能体在安卓生态系统中的能力。与以往基准相比，MobileAgentBench 具有
使用简便且侵入性极低的优势。具体而言，对于标准智能体，集成过程仅需添加少于十行代
码。该基准在易用性和通用性方面表现优异，支持在多种安卓操作系统版本上执行广泛的测
试任务，并可在真实设备上运行。
在本次初始版本中，我们提供了涵盖十个开源应用的 100 个内置基准测试任务。值得注意的
是，MobileAgentBench 与传统方法不同，其扩展过程更为简化。第三方开发者仅需使用少
量 Python 代码即可指定任务成功的条件，无需掌握大量 Android 开发知识。这种易用性使
MobileAgentBench 更有利于非 Android 开发领域的开发者和研究人员。此外，我们引入了
一种创新的方法来确定任务终止状态，使得该基准对追踪多种潜在成功路径的复杂性具有较
强的抗性。这一方法确保了 MobileAgentBench 能够提供可靠且精确的基准测试结果。
所提出基准与现有基准的对比列于表 1 中，其中完全自主表示该基准无需人工监督或判断，
真实环境表示任务可在实际设备上运行，成功条件灵活性表示考虑了所有可能的成功路径，
低代码侵入性表示将基准集成到现有智能体中不需要显著的代码修改。
我们的贡献总结如下：
• 我们提出了一种面向移动端大模型智能体的基准测试框架。该新方法解决了现有基准测
试中的常见问题，使评估过程完全自主且可靠。
• 我们实现了 100 个不同难度级别的基准测试任务。该基准可即插即用，既便于开发新智能
体，也便于评估现有智能体。

2 相关工作
2.1 移动大语言模型智能体
LLM 时代之前的研究采用强化学习 (RL) 来解决自主 GUI 导航问题 [10]。最近，大语言模
型（LLM）和多模态大语言模型（MLLM）的进展使得它们成为主导的智能体范式，因其具
备更强的 UI 理解与推理能力。早期研究主要聚焦于网络智能体，这些智能体能够在浏览器
内实现任务自动化 [7, 29]。近年来，越来越多的研究开始探索移动设备上的智能体，尤其是
在 Android 平台，因为 Android 智能手机是最广泛使用的个人计算设备。
移动端大模型智能体采用相似的算法。完整的输入提示通常包含四个主要部分：用户提示（任
务描述）、当前 UI 视图层次结构（VH）描述、动作函数列表以及历史信息。具体而言，动
作列表主要包括点击、滑动、输入等常见 UI 操作。若使用多模态大模型（MLLM），当前屏
幕截图也是输入的一部分。LLM/MLLM 根据当前状态和历史状态进行思考，并调用正确的
函数逐步执行给定任务。智能体最终解析模型的响应，并通过 Android 调试桥接（ADB）向
Android 设备发送控制信号。1

尽管高层思想相似，研究人员已开发出不同的技术以提升性能和效率。在这些工作中，An￾droidArena [24] 将长且复杂的视图层次结构 XML 转换为压缩表示，并为 UI 元素分配唯一
的结点 ID，从而缩短提示长度并提高系统效率。MobileAgent [21] 发现 GPT-4V 缺乏 UI
元素定位能力，因此采用光学字符识别（OCR）模型来定位和识别文本视图。此外，它使用
CLIP [18] 和 Grounding DINO [14] 模型检测图标。AppAgent [26] 使用 SoM [25] 提示来定位
UI 元素，并将任务分为两个阶段：探索和部署。在探索阶段，智能体自动与应用交互，并将
观察结果总结为文档。在部署阶段，它采用检索增强生成（RAG）[12] 技术利用总结的知识，
以提高成功率。CogAgent [11] 提出了其自身高度高效的 18B 参数多模态大模型（MLLM），
可在单个商用 GPU 上加载。此外，Octopus v2 [5] 提出了一个紧凑的 3B 参数模型，能够高
效且隐私保护地在设备端运行移动 LLM 智能体。
2.2 移动大模型智能体的基准测试
由于移动 LLM 智能体是一个新兴的研究领域，可用的基准测试选择非常有限。一些研究依
赖于手动验证任务执行状态来评估性能 [26]，这既繁琐又耗时。为了加速智能体的开发，我
们需要一个完全自主的基准测试系统，能够报告各种指标，尤其是任务成功率。然而，自动
判断任务是否成功完成并非易事。主要挑战源于 GUI 导航任务的动态特性——智能体可能
执行随机动作，导致应用程序进入未知状态。
AITW [19] 是移动大模型智能体的流行基准。它规模较大，但基于静态截图图像。将每个应
用状态（截图）视为一个结点，每个动作视为一条边，我们可以根据截图和人工标注的动作
构建状态转移图（STG）。如果智能体执行了未考虑的序列动作，导致 STG 进入不存在的结
点，则立即失败，即使该智能体最终能够完成任务也是如此。
唯一解决方案是在真实设备上识别任务成功。一种方法是将智能体的动作与标注的真实值
（GT）进行匹配。逐步匹配算法不够准确，因为智能体可能并未以与真实值完全相同的顺序
完成任务。AndroidArena [24] 提出了一种自适应方法，用于计算智能体动作序列与真实值

“上一页”按钮、再次点击“下一页”按钮，虽然未到达正确页面，但该序列仍是 GT 的子序

接的 UI 表示，例如，由按钮触发的网络请求结果可能不会直接反映在当前的 UI 页面上。因
此，仅检查 UI 状态是不够的，我们需要将动作（如点击事件）纳入考虑。LlamaTouch [28] 通过
将坐标映射到 UI 元素来匹配点击动作，基于视图的边界框。然而，这种方法并不总是准确。
查找正确视图以响应点击事件的过程称为命中测试，只有由 Android UI 系统执行时才准确。
这是因为应用开发者可以修改可触摸区域，使其与视图边界不同，以获得更好的用户体验。

3 移动智能体基准测试
3.1 方法
MobileAgentBench 在真实 Android 设备上运行，支持物理设备和模拟器。它会先设置环境，
然后调用智能体执行函数。当智能体操作设备时，MobileAgentBench 会实时判断任务是否
成功，且不会产生任何副作用。当智能体停止运行或超过最大步数后，MobileAgentBench 会
自动切换到下一个任务。整个过程完全自动化，无需人工干预。
任务成功判断机制通过匹配最终的 UI 状态实现，而非检查动作序列。这是因为完成任务可
能存在多种路径，但最终的成功状态是唯一的。例如，如果任务是进入设置情景，智能体可
能在正确找到目标设置情景之前误打开任意页面。由于随机性，匹配动作序列较为困难。相
比之下，检查当前顶层页面是否为设置情景则简单且可靠。无论智能体执行何种操作，只要
检测到设置情景页面，即视为成功。使用 ADB 和 UIAutomator 获取视图层次（VH）信息。
每个任务对应一个 Python 文件，用于定义任务成功标准，便于第三方开发者扩展和自定义

由于某些任务在当前 UI 页面上无法直接体现，仅检查视图层次信息是不够的。例如编辑笔
记并保存更改的操作：点击保存按钮后，应用可能仅弹出一个临时提示框表示保存成功，并
停留在当前页面。当基准测试检查当前视图状态时，无法判断是否已点击保存按钮。作为基
准测试，它不能跳转到其他页面，因为这可能会改变应用状态，影响智能体后续动作。由于我
们希望实时判断任务是否成功，以统计智能体执行的步数，因此在智能体停止后检查其他页
面的 UI 状态是不可行的。此外，部分智能体即使任务已完成也无法正常停止。为此，我们引
入应用事件，特别是按钮点击动作信号来解决此问题。对于上述任务，我们可以利用视图层
次结构检查笔记是否正确编辑，随后若接收到保存按钮的点击信号，则标记该任务为成功。
为了准确接收应用程序事件信号，我们使用 Android 可访问性服务开发了一个 Android 应
用。Android 可访问性服务最初是为帮助残障人士设计的，它在后台运行，并在 Android 系
统触发可访问性事件时调用回调函数。此类事件包括用户（智能体）交互引起的大多数 UI
状态转移，例如按钮点击、窗口切换等，这满足了所提出基准的需求。

3.3 使用
基准 API 的设计旨在用户友好且尽可能减少侵入性。对于一个标准智能体，集成仅需添加
少于 10 行代码。列表 1 展示了基准使用的伪代码。首先，我们需要导入基准 Python 库并

智能体将迭代执行动作以完成任务。在智能体执行每个动作之前和之后，都会调用协调器函
数，以便收集诸如耗时和大模型输出等信息。程序从协调器的运行函数开始。它会使用每个
任务提示调用智能体入口函数，并在任务完成后自动切换到下一个任务。任务的成功状态会
实时判断。

4 实验与智能体评估
4.1 指标
我们定义了 6 个指标，以全面基准测试移动智能体：
• 成功率（SR）：SR = Nsuccess/Mtasks ，其中 Nsuccess 为基准系统判断成功的任务数
量，Mtasks 为总基准任务数量。该指标反映了智能体端到端正确完成任务的能力。
• 逐步效率（SE）。SE = Sactual/Smin，其中 Sactual 为智能体成功完成任务所实际采
取的步数，Smin 为极小点步数。该指标告诉我们智能体是否存在不必要的或冗余的
动作，并反映了智能体的效率。失败的任务不计入计算。
• 延迟。指在一次动作前后平均花费的秒数。该指标告诉我们用户在两次动作之间需
要等待多久。
• token。LLM 输入和输出的 token 数量。为简化起见，我们使用 GPT-4V (gpt-4-
vision-preview) 标准 [16] 来计算所有模型的 token 数量，从而对 LLM 成本进
行粗略估算。对于文本，1 个 token 代表 4 个字符。对于图像，会将其划分为多个
512× 512 的瓦片，每个瓦片对应 170 个 token。此外，每张图像还额外应用 85 个
基础 token。
• 假负例（FN）率。F N = Nearly/Mfailure ，其中 Nearly 为提前终止的任务数量，
Mfailure 为失败任务的总数。该指标表示智能体错误地认为任务已完成并提前停止
的可能性。
• 假正例（FP）率。F P = Nlate/Msuccess ，其中 Nlate 为延迟停止的任务数量，Msuccess
为成功完成的任务总数。与漏报率（FN Rate）对称，该指标揭示了智能体错误认为
任务未成功完成的可能性。
4.2 环境设置
五个流行的移动端大模型智能体，AndroidArena [24]、AutoDroid [23]、AppAgent [26]、Co￾gAgent [11] 和 MobileAgent [21]，均使用所提出的基准进行评估。我们选择 Google Pixel 3a
模拟器和 Android 14 操作系统来运行基准测试应用。此外，由于部分依赖库不支持较新的
安卓系统，AutoDroid 使用 Android 9 操作系统。
由于 AndroidArena、AutoDroid 和 AppAgents 中未使用本地神经网络，这些智能体在配备
M1 Max 芯片的 Apple Macbook Pro 上运行。CogAgent 和 MobileAgent 需要本地模型引用，
因此在配备单个 Nvidia RTX 4090 GPU（24 GB 显存）的工作站上运行。
7
AppAgent 的自我探索功能已开启。在执行任务时，它可以参考之前总结的文档。由于 GPU
内存限制，我们使用 4 比特量化加载 CogAgent 模型。CogAgent 以原始版本实现，i.e.，给
定当前屏幕截图，请求下一步动作。不提供历史信息。

每个智能体在不同难度等级下的任务成功率如图 4a 所示。从图 4a 可以看出，大多数智能

任务时的成功率更高。这是因为我们将最大执行步数设置为最小步数的两倍，这使得智能体
在处理简单任务时可用于纠正早期动作的步数非常有限。例如，对于一个只需 1 步的简单任
务，智能体只能使用 1 个额外步骤来纠正并完成任务。然而，对于中等和困难任务，有显著
更多的空间来纠正先前的动作。

文本的 GPT-3.5 模型，其表现仍优于一些使用更先进 GPT-4V 模型的其他智能体。这表明，
文本视图层次结构包含了 GUI 导航任务中最关键的信息。然而，我们认为视觉截图对于其
他类型的任务仍然有帮助，例如当任务涉及识别屏幕上的图像，或当文本视图层次结构不可
用时。
5 局限性和未来工作
尽管所提出的 MobileAgentBench 具有高效、易用的优点，并解决了现有移动大模型智能体
基准的诸多问题，但作者希望在未来改进两个主要局限性。首先，虽然使用 Python 代码片
段作为任务成功条件的配置对人工智能/机器学习领域的研究人员来说较为便捷，但对于非
技术背景的用户仍存在困难。未来工作将探索无需编写任何代码即可自动构建任务配置的新
方法。此外，由于 UIAutomator 的使用导致在动态屏幕内容情况下无法获取视图层次结构，
因此该工具仅在主线程空闲时才能 dump 视图层次结构，若应用程序包含持续动画或视频，
则会失败。因此，未来可考虑用其他框架替代 UIAutomator 以获取视图信息，这将是一个
有前景的方向。
6 结论
本文提出了一种新的基准——MobileAgentBench，用于评估 Android 平台上的移动大语言
模型智能体。该基准包含 100 个内置测试任务，研究人员可自动在真实 Android 设备上测试
和评估现有及新型智能体。扩展基准以支持自定义任务也非常简便，仅需基本的 Python 编
程技能。通过利用 Android 无障碍服务，并仅检查最终应用状态，MobileAgentBench 能够
准确检测任务完成情况。我们报告了 5 个流行智能体在多个指标下的评估结果，这些结果可
作为推动未来移动大语言模型智能体发展的强大基准。
