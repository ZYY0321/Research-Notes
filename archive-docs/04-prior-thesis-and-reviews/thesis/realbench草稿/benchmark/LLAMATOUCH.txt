摘要
新兴的大语言/多模态模型推动了移动智能体的演化，
尤其是在移动 UI 任务自动化方面。然而，现有的评估
方法依赖人工验证或现有数据集来比较智能体预测的
动作与预定义动作序列，存在扩展性差且不够真实的
问题。为克服这些局限，本文提出 LlamaTouch，一个
用于设备端移动 UI 任务执行及真实、可扩展的任务评
估的测试平台。通过观察到任务执行过程仅涉及 UI 状
态的转移，LlamaTouch 采用一种新颖的评估方法，仅
检验智能体是否遍历了所有手动标注的关键应用/系
统状态。LlamaTouch 包含三项关键技术：(1) 设备端

1 引言
移动智能体使用户能够通过自然语言与智能手机进行
交互，从而减轻繁琐且复杂的手机操作负担。这些智
能体对视觉或手部功能障碍者尤其有益，或在无法使
用屏幕的场景下（如驾驶时）具有重要意义。知名的
移动智能体，如 Apple Siri [6] 和 Google Assistant [14]，
已成为智能手机上不可或缺的服务。近年来，大语言
模型（LLMs）和多模态 LLMs 的出现，推动了研究人员
构建更强大的移动智能体 [16, 19, 29, 30]。这些智能体
的核心能力在于理解用户的自然语言指令，并在移动
界面中执行相应的动作，即所谓的 移动 UI 任务自动
化，例如：“将来自 Bob 的最后一封邮件转发给 Alice”。
尽管近期基于大语言模型的移动智能体声称具备
强大的任务自动化能力，但其评估方法存在一定缺陷。
与在固定静态数据集上进行评估的传统机器学习模型
不同，移动智能体需要以智能手机的动态且不确定的
状态（例如网络连接、动态内容）作为输入。此外，移
动设备采用触摸和手势交互方式（如滑动、捏合），导
致输入具有多样性和模糊性。这种变异性使得基于静
态动作的匹配算法变得复杂。因此，仅通过数据集中
确定性的智能手机状态来评估移动智能体，无法揭示
其真实能力 [18, 25, 26]。
一般来说，评估移动 UI 自动化任务有两种方法，
但它们都无法同时实现高保真度和可扩展性。(1) 最直
观的方法是请求人类验证任务的完成情况。然而，人
工评估难以复现 [9]，且所需的人力随智能体数量、任
务数量和评估平台数量的增加而显著上升。(2) 多数
先前工作 [15, 25, 26, 30, 35, 37] 采用的最流行的方法
是在已建立数据集上的确切动作匹配，类似于传统的
机器学习评估方式。其核心思想是让标注者生成一个
能够成功完成任务的正确动作序列作为数据标签，然
后将智能体生成的动作与这些标签进行比对。尽管该
方法允许一定程度的容差，例如屏幕上点击位置的差
异 [25]，但它无法覆盖完成 UI 自动化任务的所有可能
路径，甚至包括“无限”多的执行路径。因此，这会
导致假负例率显著升高。例如，对于任务“在 Expedia
上预订一辆 6 月 1 日至 7 日洛杉矶的租车，每日预算
不超过 60 美元”，三个筛选动作的顺序可以互换。若
仅将其中一种执行路径作为参考，则可能错误地验证
一个实际上已完成的任务。此外，基于大语言模型的
智能体已知具备自我纠正错误动作的能力 [23]，这对
提升 UI 任务自动化能力至关重要，但在静态数据集
中却无法进行评估。这些局限性在 § 2.2中得到了进一
步验证。
本文提出了 LlamaTouch，这是首个在真实移动环
境中评估移动智能体的测试平台，且不牺牲真实性与
可扩展性。LlamaTouch 的核心思想是将任务执行迹与
标注者识别出的若干“关键状态”进行比对，而非与
静态迹中的预定义动作序列进行匹配。例如，任务 “打
开应用 Microsoft Excel（若未安装则先安装），进入登录
页面，…” 的关键状态应包括：(1) 应用程序 “Microsoft
Excel” 已打开，以及 (2) 应用程序处于登录页面。其
他操作，如应用安装，被视为非关键操作，应被忽略。
在任务执行过程中，LlamaTouch 使移动智能体仅能从
静态数据集中获取任务描述，而设备状态则直接从真
实的移动设备中获取。移动智能体生成的动作会直接
作用于这些设备上，所有用户界面交互数据均被记录
为任务执行迹。在评估阶段，LlamaTouch 将任务执行
迹与标注的关键状态进行比对，以判断任务是否已完
成。
为了确保评估的准确性和可扩展性，LlamaTouch
集成了两种有效的方法。(1) LlamaTouch 在屏幕级别
和单个 UI 组件级别采用细粒度的标签机制，对关键状
态进行标注。它结合像素级截图和文本化的屏幕层级
结构，明确突出重要的 UI 组件。借助 LlamaTouch 提供
的丰富标注原语，减少了人工通过启发式方法识别和
标注评估所需关键状态属性的工作量，例如文本框内
的文本应完全匹配。这些标注的 UI 状态随后用于准确
的评估。(2) 在评估过程中，LlamaTouch 采用多层级状
态匹配算法，对多样化的标注 UI 状态结合模糊匹配与
确切匹配。它使用 (i) 近似屏幕匹配，使 LlamaTouch 能
够适应动态移动环境和变化的屏幕内容，以及 (ii) 混
合 UI 状态匹配，用于检测并匹配关键的屏幕信息。
数据集与测试平台。我们提出一个大规模数据集，
其中包含预先标注的关键状态，用于评估真实移动环
境中的移动 UI 自动化任务。该数据集涵盖了 496 个不
同的任务，涉及众多流行的 Android 应用。我们还配套
提供了一个易于使用的测试平台，使移动智能体能够
与真实的 Android 环境无缝交互。该测试平台提供了
一组简洁且广泛使用的 API，确保与大多数移动智能
体的兼容性。移动智能体可轻松集成至 LlamaTouch，
并利用我们的数据集在真实场景中测试其在移动 UI
任务自动化方面的能力。
评估。我们通过利用 Google Android 模拟器 [12]
和一台 Google Pixel 5 智能手机，实现了 LlamaTouch
作为真实的 Android 环境。目前，LlamaTouch 内置了
四个智能体，包括 AutoUI [37]、AppAgent [36]、Auto￾Droid [30] 和 CoCo-Agent [21]，以及 496 个多样化任
务。以人工验证结果作为任务完成的真实值，LlamaTouch
在真实环境中的任务完成检测上达到了近 80% 的准
确率，而基于动作的先前评估方法则无法实现这一点。

贡献总结如下。
• 我们观察到，在使用静态数据集评估移动 UI
任务自动化智能体时，存在假负例率较高的问
题。为解决这一问题，我们提出了一种评估设
计，仅比较关键状态，而非具体的动作序列。
• 我们设计了一种使用多种标注原语标注关键
状态的方法。该方法结合了直观的视觉截图与
语义精确的视图层次结构，实现了对 UI 组件
的细粒度且准确的定位与标注。
• 我们设计了一种新颖的任务评估方法，该方法
在不同 UI 状态层级上同时采用确切匹配和模
糊匹配。该方法能够实现对移动智能体的准确
评估，并能很好地适应动态执行环境。
• 我们提出了 LlamaTouch，这是首个能够在真
实移动环境中忠实且有效评估移动 UI 任务自
动化智能体的测试平台。该平台包含 496 个任
务，每个任务均配有由人类标注的关键状态。

2 背景与动机
2.1 移动 UI 任务自动化的智能体
智能体简化了用户在智能手机上的繁琐且乏味的操作。
移动智能体在移动 UI 任务自动化方面的演进可划分
为三个阶段。(1) 基于 API 的智能体，如 Google As￾sistant [14] 和 Apple Siri [6]，通过预定义的应用程序
编程接口与应用程序交互。这种方法在结构化和可预
测的任务中表现可靠，但能力有限。(2) 基于学习的
智能体 [18, 25, 26, 37] 利用深度学习技术从以往的移
动交互迹中学习，但其能力仍受限于训练数据。(3) 最
近，大模型和多模态大模型彻底革新了移动智能体的
能力 [15, 22, 29, 30]。这些模型凭借其庞大的知识库，
能够理解复杂的现实世界手机屏幕。由这些模型驱动
的智能体可以准确解析自然语言指令，并将其转化为
智能手机屏幕上的可执行动作。这一演化标志着移动
智能体在灵活性和适应性方面实现了显著飞跃。
移动 UI 任务自动化智能体通常由以下组件构成。
控制器是移动智能体的大脑。它解析任务指令和用户
界面上下文，并生成将在当前用户界面上下文中执行
的动作。常用的控制器包括针对特定应用定制的深度
学习模型 [18, 25, 26, 37]、大模型（如 GPT-4、Llama）[16,
29, 30]，以及多模态大模型（如 GPT-4V）[15, 35, 36]。
输入：UI 表示。现有的移动智能体将任务描述和 UI
表示作为其控制器的输入。UI 表示主要有两种基本类
型：截图和视图层次结构（VH）。截图是当前屏幕的
视觉捕获。VH 提供屏幕上存在的 UI 元素的文本树状
结构，包括它们的属性，如类型、位置和文本内容。在
截图和 VH 的基础上，一些控制器进一步提取 UI 语义
以增强对 UI 的理解。例如，Yan 等人 [35] 在 OCR 工
具检测到的每个文本和图标上方叠加数字标签；AX￾Nav [27] 将截图转换为边界框和标签，使其可被大模
型理解。基于 VH 的进一步处理，例如将其转换为简
单的 HTML 表示，也被广泛使用 [29, 30]。
输出：动作。控制器的输出包含在当前屏幕上执行的
动作，例如点击、滑动和输入文本。动作参数可根据
智能体的设计和输入格式抽象为不同层次。(1) 屏幕上
的具体坐标 [15, 25, 26, 37]：这相当于对屏幕的直接操
作，类似于人类的操作。(2) 图标标记 [35, 36]：输出目
标将指定 UI 表示中的特定图标或图形元素。(3) HTML
索引 [16, 29, 30]：通过接收 HTML 表示，控制器将给
出具体的 HTML 索引作为动作目标，该索引对应屏幕
上的特定元素（图标或文本）。
2.2 移动用户界面任务自动化基准
如表 1 所示，提出了多种数据集和环境来评估移动智
能体在 UI 自动化任务中的表现，但它们均未能同时
实现忠实性与可扩展性。
一些工作如Rico [10]、PixelHelp [18] 和AITW [25]，
提供了包含任务描述、UI 表示和动作序列的静态数据
集。移动智能体在静态 UI 表示上预测具体动作，并与
数据集中的真实动作进行对比。尽管这种方法简单直
接，但其不足以揭示移动智能体的真实性能，原因如
下：(1) 确切动作匹配不准确。功能正确的动作可能因
动作参数不同而被判定为错误。图 1a 展示了两种情
况。首先，对于点击动作，数据集中定义的可点击区
域可能较窄，而实际上该区域可能涵盖整个 UI 组件
（用红色边界框标记）。其次，在大多数搜索任务中，
不同的文本输入可能导致相同的正确搜索结果（用绿
色边界框标记）。这一问题已在先前文献中被观察到，
但仍未得到解决 [25, 35]。(2) 对不同执行路径缺乏容
差。在真实环境中，任务通常可根据不同设备/应用状

3 LLAMATOUCH 设计
图 2 展示了使用 LlamaTouch 进行设备端任务执行和
迹评估的工作流，利用了精心构建的 LlamaTouch 数
据集。与以往的评估方法相比，LlamaTouch 具有以下
优势。
• 面向设备的移动 UI 任务执行实践（§ 3.1）。大
多数先前的评估方法都是在移动 UI 交互数据集上进
行模拟。LlamaTouch 则使移动智能体能够在真实的移
动环境中运行，实现 UI 任务自动化，从而揭示其在真
实场景中的真实能力。
• 细粒度的关键应用状态标注 (§ 3.2)。通过观察
UI 自动化任务执行过程中应用程序内关键 UI 元素的
状态转移，LlamaTouch 使标注者能够显式标注应被检

了以往静态评估方法对迹的确定性的关注，降低了评
估中假阴性出现的概率。
• 可靠且可扩展的任务评估 (§ 3.3)。LlamaTouch
通过比较在真实世界移动环境捕获的移动智能体任务
执行迹与标注的关键状态，来评估移动智能体的性能。
通过在不同应用状态上结合确切匹配和模糊匹配算法，
LlamaTouch在不失可扩展性的前提下实现了可靠的任
务评估。

标注原语。LlamaTouch 包含一组用于基本状态标
注的原语。这些原语表示屏幕上的基本信息，并指明
如何匹配这些信息。标注者有责任明确识别并使用原
语来表示对验证任务执行结果具有信息性和确定性的
应用状态。表 2 全面展示了这些原语及其应用场景。目
前，LlamaTouch 包含六种类型的原语和九个关键词用
于标注。根据其所表示的应用状态类型，这些原语可
划分为三类。
• UI 状态。 UI 状态标注的目的是提取并比较两
个屏幕是否包含相同或相似的信息。由于一个屏幕可
能包含不同类型的组件，LlamaTouch 使用四种主要原
语来覆盖所有这些 UI 组件的比较逻辑。(1) 屏幕信息
和 (2) 文本框用于比较整个屏幕或特定文本框的内容
是否相似。屏幕信息主要用于检查两个 UI 表示是否
位于同一屏幕（即应用程序的同一页面）。文本框原
语用于标注可能包含动态内容的文本框，例如网页购
物应用中的搜索框或网站的 URL。(3) 活动的功能类似
于 屏幕信息：可用于近似检测两个 UI 表示是否位于
应用程序的同一屏幕。(4) UI 组件用于确定性地标注
UI 组件的状态，包括文本框、按钮、图像等。例如，
如果需要匹配某个文本框的内容，则应使用 exact 关
键字对该文本框进行标注。对于要求屏幕上不出现某
些 UI 组件的情况，可以使用 exclude 关键字进行标
注。
• 系统状态。LlamaTouch 中的系统状态标注主要
受到先前构建的数据集 AITW [25] 中任务的启发。例
如，像“安装应用 YouTube Kids”这样的任务可以通过
shell 命令直接检测系统状态（如 pm list packages），
而无需涉及复杂的 UI 状态。目前，LlamaTouch 支持通
过编程方式检查应用程序的安装状态。关键词可以轻
松扩展和自定义，以检测其他系统或应用程序状态。
• 动作。尽管标注的原则是在任务执行过程中检
测应用状态的转换，但有时需要对特定的 UI 表示进行
操作以验证智能体的行为，特别是当 UI 中显示的状态
标识符不足时。LlamaTouch 提供了 click 和 type 关
键字，涵盖了最常见的动作。

3.3 忠实且可扩展的任务评估
标注的关键状态 (§ 3.2) 和捕获的任务执行迹 (§ 3.1) 在
LlamaTouch 中联合用于评估。LlamaTouch 通过遍历关
键状态，判断任务执行迹是否按顺序匹配所有标注的
状态。若匹配成功，则认为任务已完成。为实现忠实的
评估，最大的挑战在于如何确保任务执行迹与关键状
态相匹配。从真实世界移动环境中捕获的任务执行迹
可能包含动态的屏幕内容；因此，必须将静态数据集
中的标注关键状态适配到真实世界中捕获的多变屏幕，
同时仅在关键信息上实现精确匹配。为解决此问题，LlamaTouch
采用多层次状态匹配算法，结合对整个屏幕和分离的
UI 组件的模糊匹配与确切匹配，以确保评估的准确
性。该算法首先根据 UI 表示和活动对两幅屏幕进行
近似匹配。随后，在已匹配的屏幕之间，基于标注的
基本单元，将每个标注的关键状态与目标屏幕中的迭
代 UI 组件进行比较。只有当所有标注的关键状态均
找到匹配项时，才认为任务完成。所有标注基本单元
的匹配理念如下。
近似屏幕匹配用于确保在屏幕内容动态变化较高
的情况下，两个屏幕仍位于应用程序的同一功能页面。
这是屏幕内确切/模糊内容匹配的前期处理步骤。为实
现此目的，LlamaTouch 采用了 § 3.2 中提出的两种标
注原语：activity 和 screen info。
1. 应用程序活动匹配。活动代表用户与应用程序
交互的入口点 [3]。这是明确标识，用于判断两个屏
幕是否属于同一应用程序。具有不同功能的屏幕通常
拥有唯一的活动名称，即使它们位于同一应用程序中。
例如，主设置页面的活动为“com.android.settings.Settings”，
而Wi-Fi设置页面的活动为 “com.wifiadmin.settings.WifiSettingsActivity”。
通常，确切的应用程序活动匹配作为基础过滤过程，用
于识别两个屏幕是否位于同一页面上。然而，某些特
定的应用程序设计哲学可能导致应用程序的不同功能
页面具有相同的活动名称[2]。在这些情况下，LlamaTouch
会引入 屏幕信息以实现精确的屏幕匹配。
2. 模糊屏幕信息匹配在活动名称无法区分应用程
序的功能页面时被使用。为了更好地比较两个屏幕，关
键是要从屏幕中提取出仅有的关键信息。总之，LlamaTouch
将文本屏幕 VH 简化为一种简单的 HTML 表示，如
先前工作 [29, 30] 所示，同时保留每个 UI 组件的类
型。LlamaTouch 使用其句子嵌入的余弦相似度来比较
两个屏幕的简化 HTML 表示。当两个屏幕的余弦相似
度超过预定义阈值（例如我们实验中的 0.85）时，即认
为它们相似。模糊屏幕信息匹配的设计有助于LlamaTouch
在处理动态屏幕内容时保持评估过程的忠实性。
混合 UI 状态匹配将在近似屏幕匹配过程后应用
于匹配的屏幕。此阶段将检查多种标注的 UI 状态，包
括 UI 组件、动作和系统状态的模糊匹配与确切匹配。
1. 确切的 UI 组件匹配要求在两个被比较的屏幕
上，一个带注释的 UI 组件完全相同，包括所有属性，
如 VH 中的 class、text 和 selected。这在评估文本框的
内容、按钮的状态（例如是否选中）或屏幕上的可选择
图标时特别有用。给定一个需要确切匹配的目标 UI 组
件，LlamaTouch 将遍历匹配屏幕的 VH 中的结点，直
到找到匹配的 UI 组件为止。如果在可用屏幕上未找
到匹配的结点，则确切的 UI 组件匹配失败。在我们的
数据集中，确切的 UI 组件匹配占标注的基本状态的
51%（1,379 个中的 698 个）。
2. 模糊文本框匹配对于比较屏幕上文本框内的内
容至关重要，尤其是在内容可能存在细微差异的情况
下。语义相似且意图相同的搜索关键词，若符合特定
任务描述，则应视为匹配，因为它们将产生相同的结
果。例如，图 1b 显示，在 Google Play 商店中搜索 “Mi￾crosoft Excel” 和“Excel” 均会显示目标应用。LlamaTouch
会提取标注文本框的内容，然后使用与 模糊屏幕信息
匹配相同的方法，将其与匹配屏幕中的结点进行比较。
3. 动作匹配。尽管 LlamaTouch 的初衷是在任务
执行过程中检测状态转移，但在某些情况下仍需评估
屏幕上执行的具体动作，例如点击特定的 UI 组件或输
入正确的验证码。LlamaTouch 直接比较标注动作及其
参数与匹配屏幕上的对应动作。与先前研究 [25] 不同，
LlamaTouch 使用从屏幕 VH 中提取的目标 UI 组件的
XPath [1] 作为点击动作的参数。这种方法相比使用精
确坐标，在动作空间中提供了更大的容差。
4. 系统状态匹配在涉及确定性系统状态的特定任
务中，通常比仅比较 UI 状态更高效且更准确，例如已
安装的应用程序。LlamaTouch 当前支持检查应用程序
是否已安装。此类系统状态在真实移动设备上的任务
执行过程中被记录（§ 3.1）。LlamaTouch 将检查注释的
系统状态是否与任务执行迹线中的最后一屏状态相同，
该状态同样由 AgentEnv 记录。
通过多级状态匹配算法，LlamaTouch 在真实世界
任务执行迹线上实现了高评估准确率，同时保持了在
静态数据集上评估的可扩展性。上述评估逻辑已被良
好封装至 LlamaTouch 评估器中。要使用该评估器进行
评估，智能体只需定义如何加载每个任务的任务执行
迹线，如图 2 右侧所示，评估器将自动完成评估并报告
任务完成率等指标。§ 5 中的实验展示了 LlamaTouch
的忠实评估能力。

评估方法。我们使用以下方法来评估智能体是否完成
了任务。
• 分步动作匹配 在评估移动智能体于已建立的
数据集上被广泛使用 [25, 26, 30, 37]。它将智
能体在真实环境中的生成动作序列与数据集
中真实动作序列进行比较。当两个动作序列完
全一致时，任务被视为完成。我们采用 AITW
UIST ’24, October 13–16, 2024, Pittsburgh, PA, USA Zhang et al.
中的动作匹配算法 [25]：仅当两个动作的动作
类型和参数均相同时，才认为它们匹配。
• 基于最长公共子序列（LCS）的动作匹配 在 An￾droidArena [34] 中被提出。它建立在逐步动作
匹配的基础上，能够容忍真实动作之间的冗余
动作。当执行动作序列包含真实动作序列为子
序列时，认为两个动作序列匹配。
• LlamaTouch 通过将智能体执行迹与我们标注
的关键状态进行比较，来检查任务是否已完成。
• 人类 根据智能体执行的迹来验证任务是否完
成。人类被指示不仅要关注每个 UI 表示上的
动作（及其参数），还要关注任务执行过程中
整个应用状态的转移。人类验证的结果被视为
真实值，用于比较三种评估方法的准确率。
5.2 指标
我们主要比较（1）不同移动智能体的端到端任务
完成率（TCR）以及（2）不同评估方法的准确率，以
人工验证结果作为真实值。
端到端 TCR. 在真实移动环境中执行任务会产生两种
结果：任务完成和任务未完成。在分步动作匹配中，仅
当两个动作序列完全相同时，才认为任务已完成。基
于 LCS 的动作匹配评估真实动作序列是否为智能体
生成动作序列的子序列；若是，则认为任务已完成。在
LlamaTouch 中，当智能体执行迹经过真实数据集中所
有关键状态时，即认为任务完成，使用 § 3.3 中提出的
算法。某一评估方法的端到端 TCR 计算方式为：评估
为完成的任务数量除以数据集中的总任务数量。
评估准确率。在本研究中，我们使用智能体执行迹的
人员验证结果作为任务完成的真实值。假设 푁 表示包
含所有任务的真实值数据集。对于 푁 中的任务 푛 ，我

对同一智能体执行迹进行评估时，结果表示为 퐸푛 ，其
取值同样可以是 “True” 或 “False”。因此，准确率公式

6 LLAMATOUCH 的局限性
支持基于 WebView 的应用。LlamaTouch 的一个局限
性在于，其评估过程需要 Android 的 VH 来实现近似
的 UI 布局匹配和精确的 UI 组件匹配 (§ 3.2)。一些使
用 WebView [13] 构建的 Android 应用无法访问其 VH，
导致 LlamaTouch 无法评估智能体在这些应用上的表
现。然而，仅少数应用是基于 WebView 构建的，这促
使 LlamaTouch 采用 VH 的解决方案。当需要评估基于
WebView 的应用时，应引入更具优势的技术，例如屏
幕相似度检测 [31, 32]、基于 OCR/模型的屏幕元素识
别 [7, 33]，以对 LlamaTouch 进行改造。我们将在未来
工作中考虑这一点。
识别关键状态时的偏差。LlamaTouch 需要人类或
其他自主智能体（例如 GPT-4V）在预定义的 UI 交互迹
中识别并标注关键状态。然而，这一过程可能因对应
用执行情况和未见情境的知识有限而引入偏差，导致
准确率下降。例如，对于任务“在 Google Play 商店中删
除 YouTube”，预定义的迹可能明确导航至“YouTube”
应用页面并点击“卸载”按钮，这在任务执行过程中
可能被标注为一个关键状态。然而，该过程可能忽略
了该应用实际上可能根本未安装的情况。在这种情况
下，尽管任务已完成，但并不会出现“点击卸载按钮”
的显式动作。此类偏差可能导致任务完成率检查的准
确率降低。然而，我们认为通过引入专家审核，这一
局限性可以被消除并得到优化。此外，针对每个任务
描述，在不同潜在的任务执行路径上引入多样化的关
键状态，能够更好地提升 LlamaTouch 评估设计的鲁
棒性。
7 结论
在本工作中，我们提出了 LlamaTouch，这是首个用于
评估移动智能体在移动 UI 任务自动化中忠实性与可
扩展性的测试平台。LlamaTouch 使移动智能体能够在
真实的移动环境中进行测试。在评估阶段，它将任务
执行迹与标注的必要状态进行匹配。LlamaTouch 能够
容忍不同的任务执行路径和动态执行环境，显著减少
了以往评估方法中出现的假负例。其评估准确率较高，
与人工验证相当，同时保持了在静态数据集上评估的
可扩展性。通过在真实世界移动设备上执行任务，我
们也揭示了当前移动智能体在移动 UI 自动化任务中
的能力局限。
