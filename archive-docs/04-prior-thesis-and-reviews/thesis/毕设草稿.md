# 摘要

随着大型语言模型与多模态感知能力的快速发展，以模型为推理核心的移动端图形用户界面智能体正成为人机交互领域的新兴研究方向。然而，现有系统在面对用户指令模糊、跨应用协作、长期知识积累等真实场景需求时仍存在明显局限。本文设计并实现了一套基于多智能体架构的交互式移动端助手系统 Fairy，该系统采用三层分层架构，包含全局任务规划层、应用级执行层与自我学习层，同时引入双执行环路机制，将动作执行环与用户交互环解耦协同，从而在任务执行过程中支持主动意图澄清。在感知层面，系统融合可访问树解析与截图标注（Set-of-Mark，SoM）两种模式，为决策智能体提供结构化屏幕信息。在记忆管理层面，系统构建了短时工作记忆与长期知识记忆的分层存储机制，长期记忆通过基于向量索引的检索增强生成（RAG）为规划与执行提供应用级经验复用。此外，本文还参与设计了面向模糊指令场景的评测基准 AmbiBench，提出了指令清晰度四层级分类体系，并开发了多智能体评估框架 MUSE，从结果有效性、执行质量与交互质量三维度对智能体进行精细化评估。实验结果表明，所设计系统在用户需求完成率与意图对齐能力上显著优于非交互式基线系统，交互机制在模糊指令条件下的提升尤为突出。

**关键词**：GUI 智能体；多智能体系统；移动端自动化；意图对齐；长期记忆；RAG 检索

**Abstract**

The rapid advancement of large language models and multimodal perception capabilities has brought mobile graphical user interface (GUI) agents to the forefront of human-computer interaction research. However, existing systems exhibit significant limitations when confronted with real-world demands such as ambiguous user instructions, cross-application collaboration, and long-term knowledge accumulation. This thesis presents the design and implementation of an interactive mobile assistant system based on a multi-agent architecture. The system adopts a three-tier hierarchical structure comprising a global task planning layer, an application-level execution layer, and a self-learning layer. A dual execution loop mechanism is introduced to decouple the action execution loop from the user interaction loop, enabling proactive intent clarification during task execution. On the perception side, the system integrates accessibility tree parsing with screenshot annotation to provide structured screen information to decision agents. For memory management, a hierarchical storage mechanism combining short-term working memory and long-term knowledge memory is constructed, where the long-term memory leverages retrieval-augmented generation over vector indexes to support application-level experience reuse in planning and execution. Furthermore, this work contributed to the design of an evaluation benchmark targeting ambiguous instruction scenarios, proposing a four-level instruction clarity taxonomy and a multi-agent evaluation framework that assesses agents across three dimensions: result validity, execution quality, and interaction quality. Experimental results demonstrate that the proposed system significantly outperforms non-interactive baselines in user requirement completion rate and intent alignment capability, with the interaction mechanism showing particularly pronounced improvements under ambiguous instruction conditions.

**Keywords**: GUI Agent; Multi-Agent System; Mobile Automation; Intent Alignment; Long-Term Memory; Retrieval-Augmented Generation

# 第1章 绪论

## 1.1 研究背景

自个人计算机普及以来，图形用户界面（Graphical User Interface，GUI）始终是人与软件系统之间最主要的交互媒介。与命令行界面相比，GUI 以窗口、图标、菜单等可视化元素替代了晦涩的命令输入，大幅降低了普通用户操作软件的认知门槛，推动了信息技术在社会各层面的广泛渗透。然而，这种以"人"为中心设计的界面形式也带来了一个长期存在的工程困境：当外部程序需要与 GUI 应用协作或集成时，往往只能将其视为"黑盒"，通过模拟点击、截图识别等方式加以操控，由于 GUI 并非为程序调用而设计，这类方法天生脆弱。

传统的 GUI 自动化方案，无论是依赖坐标或图像特征的脚本工具（如 Selenium、Appium），还是面向企业流程的 RPA（Robotic Process Automation）平台，本质上都建立在界面元素的稳定结构与可预期的操作路径之上——一旦应用升级改变了控件层级，或者业务流程发生调整，这套脆弱的假设便随之崩塌，脚本的维护成本随应用数量的增长呈近乎线性的态势攀升。移动端场景中这一矛盾尤为尖锐，因为数以百万计的 App 各自遵循不同的交互逻辑，更新节奏远超桌面软件，而跨应用的协同操作更涉及需要在应用边界之间精确传递的状态上下文，这些都是纯规则化脚本几乎无法有效覆盖的长尾场景。

大型语言模型（Large Language Model，LLM）及多模态大模型（Large Multimodal Model，LMM）的兴起，从根本上打开了一条绕过上述困境的新路径。自 GPT-4、Claude 等旗舰模型相继发布以来，研究者逐渐意识到这类模型在指令理解与多步推理上展现出的能力，与 GUI 操作所需要的"读懂意图—拆解步骤—映射动作"过程有着天然的契合；而视觉语言模型（Vision-Language Model，VLM）的成熟则进一步打通了"看屏幕—做决策"这一感知到行动的关键环节，使得无需预先为每款应用编写规则的通用型 GUI 智能体（GUI Agent）变得切实可行。这类智能体目前被学术界和工业界普遍视为下一代操作系统级虚拟助手的核心技术方向，吸引了大量前沿研究投入。

在移动端领域，GUI Agent 的研究从 2023 年起迅速升温。AutoDroid 率先将 LLM 引入 Android 任务自动化，首次验证了 LLM 驱动移动端 GUI 操作的可行性；AppAgent 提出探索—部署两阶段范式，通过参考文档辅助运行时决策；Mobile-Agent 系列逐步引入多智能体协作、自我进化记忆等机制，将可完成任务的复杂度和多样性持续推向更高水平。与此同时，相关评测基准也在快速迭代，从早期侧重单步动作准确率的静态数据集，到 AndroidWorld、AmbiBench 等面向真实动态环境的评测框架，研究者对"一个真正好用的移动端助手应该具备哪些能力"的认识也在持续深化。

## 1.2 研究意义

尽管 GUI Agent 研究进展迅猛，现有系统在真实场景中仍面临几项核心挑战，这也是本课题的出发点。

**用户指令的模糊性问题。** 现实中的用户往往不会像工程师一样精确表达操作需求。"帮我点一份麦当劳"这类指令中隐含了大量未被明确的偏好——汉堡种类、套餐搭配、外卖地址等。现有非交互式智能体通常只能依赖模型先验进行概率猜测，大概率偏离用户真实意图。如何让智能体在执行过程中识别歧义、主动向用户澄清，是提升真实可用性的关键。

**跨应用协作与上下文传递问题。** 用户日常任务往往横跨多个 App。例如"把明天的会议地点发给我同事"涉及日历应用与即时通讯应用的协同，不同应用间切换需要正确传递任务上下文，而现有系统多为单应用设计，跨应用规划与上下文管理能力普遍不足。

**长尾应用的知识积累问题。** LLM 的通用知识无法覆盖所有 App 的具体交互逻辑，尤其是国内第三方应用（如外卖、打车、电商平台）中的业务流程细节。如何在任务执行过程中积累 App 专项经验，并在后续任务中高效复用，是提升系统长期可用性的核心机制。

本研究并非试图从某一单点突破这些挑战，而是将它们放在"真实场景下移动端任务自动化"这一整体目标下统筹考量，设计并实现了一套从架构到工程的完整系统方案。系统以"分层规划—双环执行—持续学习"为核心设计哲学，在感知、决策、记忆管理各环节提供了具体的实现，并通过参与 AmbiBench 基准设计以及自构任务集评估，对关键模块的实际效果给出了有据可查的评测结论。希望这一工作既能为移动端 GUI 自动化领域提供一个可落地的工程参照，也能在交互式智能体的设计方法和评测框架上积累一定的方法论经验。

## 1.3 国内外研究现状

**从单智能体到多智能体的演进。** 早期 GUI Agent 多为单智能体架构，一个 LLM 负责感知、规划和执行的全部决策。AppAgent（2023）开创性地提出两阶段范式：探索阶段通过随机操作构建应用知识文档，部署阶段参考文档辅助决策。这一方案显著提升了决策质量，但探索成本高，文档质量依赖探索充分度。Mobile-Agent（2024）引入多智能体协作，由独立的感知、规划、执行智能体分工协作，在长程任务和跨页面操作上取得明显提升。Mobile-Agent-v2 进一步引入显式的记忆管理和多智能体导航机制，实现了更稳定的长链路任务执行。

**自我进化与知识积累。** Mobile-Agent-E（2025）和 MobA（2025）分别从不同角度探索了智能体的自我进化能力。前者从历史执行轨迹中提炼"捷径"（Shortcut）和操作经验（Tips），在再次执行类似任务时直接复用；后者引入多层记忆结构，将应用地图（App Map）与操作技巧（App Tricks）分开存储，通过检索增强为规划和执行提供精准的经验支持。这些工作证明持续学习机制对于覆盖长尾场景具有不可替代的价值。

**交互式意图对齐。** 大多数现有工作仍假设用户指令完整且明确，即"指令即意图"（Instruction-as-Intent）假设。AmbiBench（本文参与工作）是首个将指令清晰度纳入评测维度的移动端基准，系统揭示了非交互式智能体在模糊指令条件下性能骤降的现象，证明主动交互能力是真实场景中不可或缺的能力维度。

**基础模型路线的崛起。** 2025 年以来，直接训练专门服务于 GUI 操作的端到端模型成为另一条技术路线。UI-TARS（ByteDance，2025）通过大规模数据训练和统一动作空间，在 OSWorld 上持续刷新成绩；Step-GUI（阶跃星辰，2025）采用自进化训练流水线，在 AndroidWorld 上实现了 80.2% 的成功率。这条路线与基于 LLM 工作流的系统路线并非对立，前者部署便捷、延迟较低，后者架构灵活、便于定制化业务集成，两者适用于不同场景。

[1.3 v2]

从技术演进的脉络来看，移动端 GUI 智能体的发展大致经历了从单智能体到多智能体协作、再到端到端基础模型三个阶段，同时伴随着记忆机制和评测方法的持续深化。

早期工作以 AppAgent[2] 为代表，通过"探索—部署"两阶段范式积累应用交互文档，在运行时由模型参照文档生成操作决策，首次将知识预积累与在线执行分离开来。这一思路虽有效，但探索阶段的成本较高，且文档质量高度依赖探索覆盖程度。Mobile-Agent 系列[3,4] 进一步将感知、规划、执行拆分为独立子智能体，多智能体协作在长程任务上展现出明显优势，并逐步引入显式的记忆管理和重规划机制，实现了更稳定的长链路导航。

在知识积累方面，Mobile-Agent-E[5] 和 MobA[6] 代表了两条并行路线。前者从成功的执行轨迹中提炼可复用的"快捷操作"，将多步序列压缩为单一高层动作，在重复性任务上大幅提升执行效率；后者则构建了分层记忆，将应用地图与操作技巧分开管理，通过关键词检索精准辅助规划与决策。这些工作共同表明，持续学习机制对于覆盖长尾场景具有不可替代的价值。

如何处理模糊指令是近年来逐渐受到重视但仍相对缺乏系统探索的方向。大多数现有工作仍假设用户指令完整且明确，一旦遭遇歧义便只能依赖模型先验猜测，往往产生偏差。本文参与构建的评测基准是首个将指令清晰度纳入核心评测维度的移动端基准，其实验数据表明，在模糊指令条件下，非交互式系统的任务成功率相较于清晰指令存在显著的系统性下降。

2025 年以来，端到端原生 GUI 模型路线（以 UI-TARS[8] 和 Step-GUI[19] 为代表）在多项基准上实现了快速突破，其核心优势在于低延迟和统一的动作空间设计。这条路线与基于 LLM 工作流的系统架构路线各有侧重——前者适合规模化部署，后者在架构可解释性与业务逻辑定制方面更具弹性，两者并非对立关系，而是面向不同应用场景的互补选择。

## 2.1 移动端 GUI Agent 的发展脉络

### 2.1.1 早期探索：从规则脚本到 LLM 驱动

在 LLM 驱动 GUI Agent 研究正式兴起前，移动端自动化长期依赖两类技术路线。其一是基于 UI 测试框架（如 Appium、UI Automator）的脚本自动化，通过 XPath 或资源 ID 定位界面元素后执行预设操作序列；其二是基于图像识别的 RPA 工具，通过截图匹配特征区域触发点击动作。两者的共同局限在于脆弱性：一旦应用升级改变了控件层级或视觉样式，脚本需要重新适配，维护成本居高不下。

AutoDroid（2024）是首个将 LLM 系统性地应用于 Android 任务自动化的工作。其核心贡献在于构建了应用 UI 过渡图（App UI Transition Graph），将应用的状态转移关系以图的形式存储，由 LLM 在图上进行推理以生成操作序列。这一方案无需人工编写操作规则，在简单任务上取得了良好效果，首次验证了 LLM 在移动端 GUI 任务中的可行性。

AppAgent（2023）进一步提出"探索—部署"双阶段范式。探索阶段通过随机操作积累界面交互经验，生成每个 App 的参考文档；部署阶段 LLM 参考文档辅助生成当前步骤的操作决策。这种将知识预积累与在线决策分离的思路，有效缓解了 LLM 对特定应用知识盲区的问题，但探索阶段成本较高，文档质量也高度依赖探索覆盖的充分程度。

[2.1.1 v2]

在大型语言模型驱动的 GUI 智能体研究兴起之前，移动端自动化长期在脚本工具与机器人流程自动化两条路线上摸索。脚本工具（如 Appium、UI Automator）的本质是依赖资源标识符或界面坐标定位元素并执行预设操作序列；机器人流程自动化平台则借助截图匹配来触发点击。两种方案的致命弱点是相同的——高度依赖界面的稳定性，一旦应用发布更新导致控件层级或视觉样式改变，脚本便要重新适配，随着应用数量增加，维护成本以近乎线性的方式攀升。

AutoDroid[1] 是这一领域率先引入大型语言模型的工作。它将应用的界面状态转移关系整理成图结构，再由语言模型在图上推理生成操作序列，从而摆脱了人工编写规则的依赖，首次在实际设备上验证了语言模型驱动移动端 GUI 操作的可行性。在这一基础上，AppAgent[2] 进一步将"积累知识"与"在线决策"明确分成两个阶段：探索阶段通过随机操作为每款应用生成参考文档，部署阶段则让模型在文档的辅助下逐步生成操作决策。这种知识预积累的思路有效弥补了模型对特定应用的认知盲区，但探索的代价不低，且文档质量严重依赖探索的覆盖程度——一旦某些功能路径未被随机探索到，对应的知识便无从积累。

### 2.1.2 多智能体协作架构的兴起

单一 LLM 在复杂、长程任务中容易出现注意力分散、决策错乱等问题。Mobile-Agent（2024）将视觉感知与操作决策拆分为独立模块，引入了专门负责视觉处理的子智能体，使核心决策模型能专注于任务逻辑推理。Mobile-Agent-v2 在此基础上增加了显式的任务规划智能体和记忆管理模块，通过多智能体流水线在跨页面、长链路任务中表现出更强的导航稳定性。

MobA（2025）将多智能体协作与层级记忆相结合，设计了粗粒度子目标规划器与细粒度动作决策器的两层结构，同时维护应用地图（App Map）和操作技巧（App Tricks）两类长期记忆，通过关键词检索辅助规划与动作决策。这一设计思路与本文系统高度相关，是本课题在架构上的重要参照。

Mobile-Agent-E（2025）引入显式的自我进化机制，从完成的任务轨迹中提炼可复用的"快捷操作"（Shortcut），将多步操作序列压缩为单一高层动作单元，在重复类型任务上大幅提升了执行效率。AppAgentX（2025）将类似思路命名为"链式记忆演化"（Chain Memory Evolution），通过识别重复操作序列并生成高层"快捷动作"，在 DroidTask 上实现了 88.2% 的成功率，远超原始 AppAgent 的 46.3%。

[2.1.2 v2]

单一大型语言模型在面对复杂、长程任务时存在明显的瓶颈：上下文不断延伸会使模型的注意力逐渐分散，决策质量随之下降。Mobile-Agent[3] 较早认识到这一问题，将视觉感知与操作决策分解为独立模块，让负责规划的核心模型得以专注于任务逻辑推理，而无需同时处理图像理解的负担。Mobile-Agent-v2[4] 在此基础上进一步引入了显式的任务规划智能体和记忆管理机制，通过多智能体流水线协作，在跨页面的长链路任务中表现出更稳定的导航能力。

MobA[6] 则将多智能体协作与层级记忆管理结合起来，同时维护应用地图与操作技巧两类长期知识，通过关键词检索在规划和动作决策两个层面提供精准的经验支持。这一分层协作加检索增强的设计思路，与本文系统的架构理念高度契合，是本课题在系统设计上的重要参照。

在知识积累方面，Mobile-Agent-E[5] 提出了较为系统的自我进化机制：任务完成后，系统从执行轨迹中提炼出可以直接复用的"快捷操作"，将原本需要多步推理的操作序列压缩为单一高层动作，在重复性任务上的执行效率因此得到大幅提升。AppAgentX[10] 将类似的思路发展为"链式记忆演化"，通过识别历史执行中反复出现的操作模式并将其固化为高层快捷动作，在 DroidTask 基准上实现了 88.2% 的成功率，与同使用 GPT-4o 的原始 AppAgent 的 46.3% 相比提升显著，充分说明操作知识的积累与复用机制具有重要的实用价值。

### 2.1.3 端到端基础模型路线

2025 年以来，另一条技术路线逐渐引发广泛关注：直接训练专门服务于 GUI 操作的端到端 Native Agent，将感知、规划、执行能力内化在单一 VLM 中。UI-TARS（ByteDance/清华，2025）通过大规模感知增强数据训练和统一动作空间设计，配合 System-2 推理机制，在 OSWorld 基准上达到 24.6% 的成绩，后续通过强化学习进一步提升至 42.5%。Step-GUI（阶跃星辰，2025）采用自进化训练流水线（CSRS），将模型生成的轨迹自动转化为高质量训练数据，其 8B 规格模型在 AndroidWorld 上达到 80.2% 的成功率。

这类端到端基础模型路线与基于 LLM 工作流的系统路线并非对立：前者决策延迟低、部署便捷，适合规模化推广；后者架构灵活、可解释性强、便于融入复杂业务逻辑，适合定制化场景。本文工作属于后者，侧重系统架构设计与工程实现。

[2.1.3 v2]

2025 年以来，将感知、规划、执行能力全部内化于单一视觉语言模型的端到端原生智能体路线受到越来越多的关注。UI-TARS[8]（字节跳动与清华大学联合工作）通过大规模感知增强数据训练与统一动作空间设计，结合慢思考推理机制，在 OSWorld 基准上的成功率从 24.6% 起步，经强化学习微调后进一步提升至 42.5%。Step-GUI[19]（阶跃星辰）则采用自进化训练流水线，将模型自身生成的操作轨迹自动转化为高质量训练数据，其 8B 参数规模的模型在 AndroidWorld 基准上达到了 80.2% 的任务成功率。

从技术特性来看，端到端路线与基于语言模型工作流的系统架构路线各有其适用边界，并不构成非此即彼的取代关系。端到端模型决策延迟低、部署流程简洁，在追求规模化推广的场景中具有明显优势；而基于多智能体工作流的系统路线架构更透明、模块边界清晰，在需要与复杂业务逻辑深度融合或进行专项定制的场景下仍难以替代。本文工作属于后一类路线，核心关注点在于系统架构设计与工程实现，而非模型训练本身。

## 2.2 屏幕感知技术

屏幕感知是 GUI Agent 获取当前界面状态的核心环节，其质量直接决定后续规划和动作决策的准确性。

**基于可访问树的感知。** Android 系统通过 UI Automator 框架暴露应用的 View 层级结构，即可访问树（Accessibility Tree，AT）。AT 以 XML 格式描述屏幕上每个 UI 节点，包含节点的类型（class）、边界坐标（bounds）、文本（text）、内容描述（content-desc）等属性。基于 AT 的感知方案可以精确定位所有可交互元素及其坐标，是面向文本型 LLM 的天然适配。其局限在于：AT 信息高度依赖应用开发者的规范实现，通过 Canvas 绘制的自定义控件往往缺少语义标注；此外，AT 无法传达图标的视觉含义和图像内容。

**截图与视觉感知。** 随着 VLM 能力的提升，直接将屏幕截图作为模型输入成为可行路线。Set-of-Mark（SoM，2024）提出在截图上叠加数字标签，为每个可交互元素标注编号，使 VLM 在生成操作时能通过编号引用具体元素而无需输出精确坐标，显著减少了坐标回归带来的误差。Aria-UI（2024）针对 GUI 场景设计了上下文感知的 Grounding 模型，在截图中准确定位自然语言描述的元素，在 AndroidWorld 上达到 44.8% 的领先成绩。

**融合感知方案。** 更鲁棒的做法是将 AT 结构信息与截图视觉信息结合使用。UI-TARS 在训练时同时使用了 AT 文本描述和截图，以增强多模态理解能力。本文系统实现的 SSIP（Screen Structured Info Perceptor）感知方案采用了融合策略：优先基于 AT 提取可交互节点并在截图上绘制 SoM 标记，对 AT 缺失图像语义的节点额外调用视觉描述生成模型补全内容描述，从而在保持坐标精度的同时兼顾图像语义理解。

[2.2 v2]

屏幕感知是 GUI 智能体获取当前界面状态的首要环节，其质量直接决定了后续决策的准确性。现有方案可大致分为基于结构解析、基于视觉理解以及两者融合三类。

在结构解析方面，Android 系统通过 UI Automator 框架将应用的控件层级以可访问树（Accessibility Tree）的形式暴露出来，其中包含每个界面节点的控件类型、边界坐标、文本内容等属性。这类方案能够精确定位所有可交互元素并获取其坐标，与纯文本语言模型的输入格式天然兼容。但它的局限性也很明显：可访问树的信息质量高度依赖应用开发者的实现规范，通过 Canvas 自定义绘制的控件往往缺乏语义标注，而图标等图像内容的含义更是无从通过文本描述传达。

在视觉理解方面，随着视觉语言模型能力的提升，直接以截图作为模型输入已成为可行路线。Set-of-Mark[11] 提出在截图上为每个可交互元素叠加带编号的标注框，使模型在输出操作时只需引用标记编号而无需预测精确坐标，从而显著降低了坐标定位的误差。Aria-UI[12] 则针对 GUI 场景专门设计了上下文感知的元素定位模型，能够在截图中准确找到自然语言描述所对应的界面元素，在 AndroidWorld 基准上达到 44.8% 的领先成绩。

更为鲁棒的做法是将结构解析与视觉理解融合使用，取长补短。UI-TARS[8] 在训练阶段同时利用了可访问树文本描述和截图，以增强模型的多模态理解能力。本文系统所实现的屏幕结构化感知模块（SSIP）采用了类似的融合策略：优先从可访问树中提取可交互节点并在截图上绘制编号标注，对于缺乏图像语义描述的节点则额外调用视觉描述模型进行补全，从而在保持坐标精度的同时弥补纯结构解析对图像内容理解的不足。该模块的具体实现见第4章。

## 2.3 规划与决策机制

**单层反应式规划。** 早期系统采用单步或有限步的规划策略：给定当前屏幕状态和用户指令，直接生成下一步操作。这种"反应式"（Reactive）决策方式实现简单，但面对长程任务时，缺乏对整体目标的把握容易导致方向偏离和步骤冗余。

**层级规划。** 层级规划将任务分解为不同粒度的子目标，典型结构为"高层目标→子任务→原子动作"三级。高层目标对应用户的自然语言指令；子任务对应在单一应用内可独立完成的阶段目标（如"搜索目标商品"、"填写收货地址"）；原子动作则是单次屏幕操作（如 Tap、Swipe、Input）。这种结构使规划器只需关注子目标序列，动作决策器只需关注如何在当前屏幕上实现当前子目标，各层职责清晰。本文系统的 AppPlannerAgent 和 ActionDeciderAgent 分别对应子任务规划和原子动作决策两层。

**动态重规划。** 规划并非一次性的静态序列。在执行过程中，屏幕状态可能出现预期外的变化（如弹出广告、页面加载失败、搜索结果为空），此时需要对剩余计划进行动态修订。本文系统的 AppRePlannerAgent 负责在检测到子目标推进异常或陷入循环时触发重规划，重新生成后续子目标序列。

**基于 MCTS 的规划增强。** Plan-MCTS（2026）将动作搜索提升到语义 Plan Space，通过蒙特卡洛树搜索在规划层面探索多条执行路径，在 WebArena 上取得了新的最优成绩。这一方向为推理时增强提供了有价值的参考，但在移动端实时交互场景中引入树搜索的额外延迟仍是实用性挑战。

[2.3 v2]

规划机制决定了智能体在面对一个给定任务时如何将其分解为可执行的操作序列，其设计直接影响系统处理长程复杂任务的能力。

早期系统多采用单层反应式策略：给定当前屏幕状态和用户指令，直接输出下一步操作。这种方式实现简单，在任务较短时尚可胜任，但面对多步骤操作时，由于缺乏对整体目标的显式表示，容易在执行中途偏离方向或陷入无意义的循环。

层级规划是应对这一问题的主流方案。它将任务分解为由粗到细的多个层次，典型结构包括高层用户指令、应用内可独立完成的阶段性子目标，以及单次屏幕操作三个层级。这种分层设计的好处在于，规划智能体只需关注子目标的合理排列，动作决策智能体只需关注如何在当前屏幕上推进当前子目标，两者职责清晰，互不干扰。本文系统的应用级规划模块和动作决策模块正是按照这一两层分工实现的，具体设计见第4章。

不过，现实执行环境中意外情况时有发生——弹出广告打断了正常流程、搜索结果为空导致原计划无法推进、误触某个按钮引发了非预期的页面跳转——此类情况均要求系统具备对剩余计划进行动态修订的能力。本文系统引入了专门的重规划模块，在检测到子目标推进异常或系统陷入循环时自动触发，重新生成后续的子目标序列。此外，将蒙特卡洛树搜索引入规划层的研究思路近年来也得到探索，通过在语义层面搜索多条可行执行路径来提升决策质量，但移动端实时交互场景对响应延迟较为敏感，此类方法的实用性仍有待进一步验证。

## 2.4 记忆机制

记忆是智能体积累经验、提升长期表现的关键能力，近年来受到越来越广泛的关注。

**短时工作记忆。** 短时记忆在当前任务执行周期内维护，保存当前指令、当前计划、历史动作—结果对等信息，供各决策模块动态查询。在长程任务中，如何在保留关键历史信息的同时控制 LLM 输入长度是重要问题。AgentProg（2025）将交互历史重构为带变量和控制流的语义程序，原则性地保留或丢弃信息，支持长流程任务不退化。SWE-AGILE（2026）提出"滑动窗口保留最近完整推理 + 历史推理压缩为摘要"的混合策略。

**长期知识记忆与 RAG 检索。** 长期记忆跨越任务生命周期，持久保存应用操作经验。A-MEM（2025）提出基于 Zettelkasten 思路的记忆网络，在写入新记忆时自动建立与已有记忆的双向链接；CoMEM（2025）使用 Q-Former 将历史轨迹压缩为少量连续向量注入 VLM，实现高效上下文压缩；HyMEM（2026）结合符号节点与连续轨迹嵌入构建图结构记忆，支持多跳检索，在 Qwen2.5-VL-7B 上绝对提升 22.5%。本文系统的 LongTimeMemoryManager 采用基于 LlamaIndex 的 VectorStoreIndex，将三类经验分别建立独立索引，检索时通过 App 包名元数据过滤结合语义相似度排序，取 top-3 结果作为上下文注入对应的规划或决策提示词。

**面向 UI 更新的自适应记忆。** MAGNET（2026）提出双层记忆机制：stationary memory 将视觉外观映射到功能语义（应对界面外观漂移），procedural memory 保存任务工作流（应对流程变化）。AndroTMem（2026）针对 Android 长流程专门设计了锚定状态记忆（Anchored State Memory），在 1069 个测试任务上实现了 5%—30% 的任务完成率提升。这些工作表明，针对具体场景定制化记忆结构是提升系统性能的有效路径。

[2.4 v2]

记忆机制决定了智能体能否将过去的执行经验转化为未来决策的有益参照，是影响系统长期可用性的核心组件之一。从时间跨度来看，记忆大致可分为会话内的短时工作记忆与跨会话的长期知识记忆两类，两者分别服务于不同的决策需求。

短时工作记忆在单次任务执行周期内维护，保存当前指令、当前计划状态以及历史操作与其执行结果等信息，供各决策模块实时查询。对于长程任务而言，如何在保留关键历史信息的同时有效控制语言模型的输入长度是一个具有实际意义的工程问题。AgentProg[13] 探索了一种将交互历史重构为语义程序的思路，通过引入变量和控制流来结构化地保留或丢弃历史信息；也有工作采用滑动窗口结合摘要压缩的混合策略，保留最近完整推理步骤的同时对更早的历史进行语义压缩。

在长期知识记忆方面，跨任务的操作经验积累得到了越来越多的重视。A-MEM[14] 借鉴卡片笔记的思路，在写入新记忆时自动建立与相关已有记忆的双向链接，形成可导航的知识网络；CoMEM[25] 以 Q-Former 将历史执行轨迹压缩为少量连续向量直接注入视觉语言模型，实现了高效的上下文复用；HyMEM[15] 则将符号节点与连续轨迹嵌入结合，构建图结构记忆以支持多跳检索，在 Qwen2.5-VL-7B 骨干上实现了 22.5 个百分点的绝对提升。本文系统的长期记忆管理模块基于向量索引框架构建，将规划经验、执行经验与错误恢复经验分为三个相互独立的索引，检索时以应用包名元数据进行精确过滤并结合语义相似度排序，将最相关的经验注入对应决策环节的提示词中。

此外，如何应对应用界面随版本迭代产生的外观或流程漂移，也逐渐成为记忆机制研究的关注方向。MAGNET[18] 提出将视觉外观到功能语义的映射与任务工作流分开管理，分别应对界面外观漂移与流程变化两类情况；AndroTMem[16] 针对 Android 长流程任务专门设计了锚定状态记忆，在超过千个测试任务上取得了 5% 至 30% 的任务完成率提升。这些工作共同表明，面向具体场景定制化记忆结构，往往比通用方案有更显著的收益。

## 2.5 用户交互与意图对齐

大多数现有 GUI Agent 采用"无交互"模式：接收用户指令后自主完成全部操作，不在执行过程中与用户沟通。这种方式在指令清晰、任务确定性高的场景下效率较高，但面对歧义指令时往往产生错误的意图理解。

从认知科学的视角来看，用户在表达需求时所产生的"认知缺口"（Cognitive Gap）几乎是不可避免的：说话者对自己想要什么往往已有相当清晰的认知，但将这种认知转化为文字时，囿于表达习惯或对系统能力的不了解，大量细节会被省略——"帮我点一份麦当劳"背后可能隐含着具体的汉堡偏好、套餐与否、外送地址等一整套约束，而这些细节在指令文本中完全缺失。对于非交互式智能体而言，填补这些缺口的唯一手段是依赖模型先验做概率性猜测，而猜测的期望结果是偏离用户真实意图的。

支持主动交互的系统之所以难以设计，不在于"怎样提问"，而在于"何时提问"的判断本身：询问过于频繁会把每次简单操作都变成一场确认对话，远比直接帮用户做了更烦人；而询问不足又会让意图偏差悄悄积累，直到用户看到错误的执行结果才察觉问题。本文系统选择将 `NeedInteraction` 作为 ActionDeciderAgent 动作空间中的一个普通选项，而非一套独立的触发规则，这意味着"是否发起交互"的判断被完全内化到 LLM 对当前上下文的动态推理中，而非依赖人工设定的关键词或规则阈值，从而在覆盖度和精准度之间保持了相对的灵活性。

[2.5 v2]

现有 GUI 智能体的主流设计范式是"指令即意图"——系统接到用户指令后便独立推进全部操作，不在执行过程中与用户沟通。这一假设在指令清晰、任务确定性较高的场景下效率可观，但在真实的日常使用中往往并不成立。

从认知科学的角度看，用户在表达需求时产生"认知缺口"几乎是不可避免的现象：用户心里对自己想要什么往往已有清晰的认知，但在将这种认知转化为文字时，出于表达习惯或对系统能力边界的不了解，大量细节会被自然地省略。"帮我点一份麦当劳"这短短一句话背后，其实隐含着餐品种类、套餐搭配、外送地址乃至支付方式等一系列约束，而这些信息在指令文本中完全缺失。非交互式系统面对这些缺失时，只能依赖模型先验进行概率性猜测，而猜测结果偏离用户真实意图的概率随缺失参数的增多而快速上升。

支持主动交互的系统在设计上面临的核心难题并不在于"如何构造问题"，而在于"何时决定询问"这一判断本身。询问过频会将每一次简单操作都演变为一场确认对话，用户体验远不如直接替用户决定；询问不足则任由意图偏差悄悄积累，直到用户看到最终错误结果才发现问题。本文系统选择将发起询问作为动作决策模型的一个可选动作类型，而不是在规划层单独设置一套交互触发规则。这样做的好处在于，是否需要发起交互的判断被内化进模型对当前上下文的动态推理，而非依赖人工设定的规则阈值，系统在何时提问的决策上具有更大的灵活性。这一设计的效果将在第5章的实验中进行量化评估。

## 2.6 评测基准

**静态数据集评测。** 早期评测基准多为静态数据集，提供截图序列和对应人工标注操作，以步骤匹配率（Step Match Rate）等指标衡量系统准确性。AITW（2022）收录了大量人工演示轨迹；AndroidControl 在此基础上增加了高层指令与低层操作的对应关系注释。静态评测可重复性强，但无法反映真实任务执行中的环境动态性。

**动态沙箱评测。** AndroidWorld（2025）构建了真实 Android 沙箱环境，允许智能体在虚拟设备上执行操作，并通过编程验证器检查任务完成状态，支持百余个真实 App 的任务评测。SPA-Bench 则提供了跨框架的统一评测接口，便于不同系统的标准化对比。MobiFlow（2025）从另一角度切入，专门针对以外卖、网约车为代表的"流式操作"（sequential multi-step flow）场景构建评测框架，引入了流程完整性和关键节点对齐两个维度，对本文自构任务集的设计思路有所参考。

**面向交互质量的评测。** AmbiBench（本文参与工作）是首个将指令清晰度系统纳入评测体系的基准，其核心贡献在于：提出四层级清晰度分类（Detailed / Standard / Incomplete / Ambiguous），引入基于 LLM 的用户模拟器（User Simulator）支持动态交互，设计 MUSE 多智能体评估框架从结果有效性、执行质量、交互质量三维度进行精细化指标计算，其与人工评判的相关性验证达到了较高水平。与之相比，VLAA-GUI（2025）和 VoiceBench 等工作分别从视觉定位准确性和语音指令理解角度拓展了评测维度，反映出领域对"多模态输入下的 GUI 操作"的日益关注。

[2.6 v2]

评测基准的发展折射出领域对"一个好用的移动端助手究竟应该具备哪些能力"这一问题认识的不断深化，其演进大致经历了静态数据集、动态沙箱和交互质量评测三个阶段。

早期评测多以静态数据集为主，提供截图序列与人工标注操作，以步骤匹配率为主要衡量指标。这类方案复现性强，但静态截图序列无法反映真实执行中的环境动态性，评测结论与实际系统表现之间往往存在差距。AndroidControl[（Li等，2024）] 在人工演示轨迹数据集基础上增加了高层指令与低层操作的对应关系标注，使研究者得以在更丰富的指令粒度上分析模型行为。

AndroidWorld[7] 代表了动态沙箱评测方向的重要进展，它在真实 Android 虚拟设备上允许智能体执行完整操作序列，并通过编程验证器自动检查任务完成状态，支持超过百个真实应用的任务评测，在可重复性和真实性之间取得了较好的平衡。SPA-Bench[21] 则通过统一评测接口为跨框架的系统对比提供了便利。面向外卖、网约车等具有固定操作流程的"流式场景"，MobiFlow[（Feng等，2026）] 专门引入了流程完整性与关键节点对齐两个评测维度，为此类场景的细粒度评估提供了参考。

指令清晰度是现有评测体系长期忽视的维度。绝大多数基准默认用户指令是完整且无歧义的，既不考察系统在模糊指令下的表现，也不评估系统主动澄清的能力。本文参与构建的评测基准是首个将指令清晰度纳入核心评测维度的移动端基准，它提出四层级清晰度分类（详细/标准/不完整/模糊），引入基于语言模型的用户模拟器以支持动态交互过程的自动化评测，并设计了兼顾结果有效性、执行质量与交互质量三个维度的多指标评估框架，相关实验结果见第5章。此外，VLAA-GUI[（Han等，2026）] 从模块化 GUI 自动化框架的角度拓展了评测视角，VoiceBench[（Chen等，2024）] 则聚焦于语音指令理解的评测，两者共同反映出领域对多模态输入下 GUI 操作能力的日益关注。

# 第3章 系统总体设计

## 3.1 需求分析与设计目标

### 3.1.1 功能需求

根据对真实移动端使用场景的分析，系统需满足以下核心功能需求。

**跨应用任务执行。** 用户指令往往不局限于单一应用。系统需解析用户的高层指令，识别需要调用的应用列表，生成合理的跨应用子任务序列，并在完成每个应用级子任务后将必要的上下文信息传递给下一阶段。例如，"帮我叫一辆滴滴到我明天开会的地点"涉及日历应用（读取会议地址）与出行应用（填写目的地并叫车）的协同。

**意图澄清与主动交互。** 系统在执行过程中需识别以下情形并主动发起用户交互：指令存在歧义（如"帮我发条微信"未指定接收方）；面临多个同等合理的选项需要用户决策（如外卖菜单中有多种汉堡）；即将执行不可逆或高风险操作（如支付、删除数据）需要用户确认。

**感知与动作执行。** 系统需准确解析当前 Android 设备的屏幕状态，提取可交互元素的位置和语义信息，支持 Tap（点击）、Swipe（滑动）、Input（文字输入）、LongPress（长按）、KeyEvent（系统按键）、Wait（等待）等原子动作，并通过 ADB 或 UI Automator 接口将动作指令下发至目标设备。

**长期经验积累。** 系统执行任务后，应从执行轨迹中自动提炼经验知识，并在后续任务中通过语义检索复用。积累的知识分为三类：规划层经验、执行层经验和错误恢复经验，分别对应任务分解策略、原子操作规范和异常处理流程。

### 3.1.2 非功能需求

**模块化与可扩展性。** 各智能体模块通过消息总线解耦，新增模块或替换骨干模型不影响已有模块的正常运行。

**多骨干模型支持。** 系统允许不同模块配置不同的骨干模型，以在性能与成本之间取得平衡。视觉感知和动作决策模块使用强多模态模型，RAG 检索和文本摘要模块可使用参数量较小的文本模型。

**可恢复性。** 在长程任务执行过程中，系统定期将短时记忆序列化备份，支持异常中断后从检查点恢复执行。

[3.1 v2]

根据对真实移动端使用场景的系统梳理，本文将系统需要解决的问题归纳为以下几个核心功能维度。

在任务执行能力方面，系统需要处理横跨多个应用的复合型任务。以"帮我叫一辆滴滴到我明天开会的地点"为例，这一指令需要先进入日历应用读取明天的会议地址，再打开出行应用填写目的地并完成叫车，两个阶段之间涉及具体地址信息的跨应用传递。系统需要能够理解这类高层指令，自动识别所需应用的顺序，并在子任务切换时妥善管理上下文。

在意图对齐能力方面，系统需要识别三类典型的交互触发场景：一是指令本身存在歧义，如"帮我发条微信"缺少收件人信息；二是执行中遇到多个对等选项，如菜单中有多款汉堡难以自主选择；三是即将发起不可逆的高风险操作，如确认支付或删除重要数据，需在执行前取得用户明确授权。

在感知与执行能力方面，系统需要可靠地解析当前 Android 设备的屏幕状态，提取可交互元素的位置与语义信息，并将决策结果转化为点击、滑动、文本输入、长按、按键等原子操作下发至目标设备。

在长期适应能力方面，系统应在每次任务完成后从执行轨迹中提炼可复用的经验，分为任务分解策略、具体操作技巧与异常恢复方法三类，并在后续相同应用的任务中通过语义检索加以复用，随着积累的增加逐步减少已知错误的重复发生。

在工程质量方面，各智能体模块之间应通过消息机制解耦，使替换骨干模型或新增功能模块不影响其他模块的正常运行；系统还应支持在任务执行过程中定期备份状态，以便在异常中断后恢复执行，避免前期工作全部丢失。

## 3.2 系统总体架构

### 3.2.1 三层分层架构

Fairy 系统采用三层分层架构（图3-1），每层承担不同粒度的智能决策职责，层间通过消息驱动机制异步通信。

**第一层：全局任务规划层（Global Task Planner Layer）**

该层由 GlobalPlannerAgent 和 GlobalRePlannerAgent 构成，负责接收用户的高层指令，结合设备已安装应用的元数据（包名、名称、功能描述），将任务分解为有序的跨应用子任务序列。每个子任务指定目标应用包名、子任务描述以及需要从上一子任务结果中提取的关键信息。当某一子任务执行完毕，全局规划层负责判断是否需要调整后续计划，并将跨应用上下文（如提取的地址、订单号等）传递给下一子任务。

**第二层：应用级执行层（App-Level Executor Layer）**

该层是系统的执行核心，由多个协作智能体构成，负责在单一应用内完成子任务的完整执行流程。执行层内部包含两个协同运行的执行环路：

- **动作执行环（Action Loop）**：由 AppPlannerAgent（子目标规划）、AppRePlannerAgent（重规划）、ActionDeciderAgent（动作决策）、ExecutionReflectorAgent（执行反思）、GoalVerifierAgent（子目标验证）、ActionExecutor（动作执行）和 ScreenPerceptor（屏幕感知）构成的感知—规划—执行—反思闭环。

- **用户交互环（Interaction Loop）**：由 UserInteractorAgent（交互内容生成）和 UserInteractorReflectAgent（交互结果解析）构成。当动作决策的结果为 `NeedInteraction` 时，系统暂停动作执行环，激活交互环向用户发起询问，将用户回复解析为指令补充后恢复动作执行环。

**第三层：自我学习层（Self-Learning Layer）**

该层在任务或子任务完成后触发，从执行轨迹中提炼应用操作经验，写入持久化的长期记忆库。长期记忆分为 Plan Tips、Execution Tips 和 Execution Error Tips 三类，以 JSON 格式按应用包名组织存储，通过 LongTimeMemoryManager 提供 RAG 检索服务。

本系统采用三层分层架构（图3-1），三层之间通过消息驱动机制进行异步通信，每层承担不同粒度的决策职责，层间职责边界清晰。

最上层为全局任务规划层，负责接收用户指令并将其拆解为有序的跨应用子任务序列。该层在拆解时结合设备上已安装应用的元数据——包括应用名称和功能描述——为每个子任务指定目标应用和所需完成的具体目标，并标注当前子任务完成后需要提取哪些关键信息传递给下一子任务。当某个子任务完成后，该层还负责根据执行结果判断是否需要动态调整后续子任务的描述或上下文注入内容，维持全局计划的一致性。

中间层为应用级执行层，是系统的执行核心。该层在单一应用内完成子任务的全部执行流程，内部设有两条并行运行的环路。第一条是动作执行环，由子目标规划、动作决策、原子动作执行、屏幕感知、执行反思和子目标验证六类模块组成"感知—规划—执行—反思"的完整闭环，负责稳步推进子目标序列的完成。第二条是用户交互环，由交互问题生成和用户回复解析两个模块组成；当动作决策模块判断当前情况需要用户介入时，交互环接管控制流，向用户发起询问，将用户的回复整理为结构化的补充信息后再将控制权交还给动作执行环。两条环路通过短时工作记忆中的状态字段进行衔接，整个交互过程对其余模块透明。

最下层为自我学习层，在每次子任务或全局任务完成后触发。该层分析任务的执行轨迹，提炼出可供后续任务参考的经验条目，并按照规划经验、执行经验和错误恢复经验三个类别分别写入持久化的长期记忆库，供检索增强模块在后续同应用任务中按需查询。

### 3.2.2 消息驱动运行时架构（Citlali 框架）

系统的运行时基础由内部开发的 Citlali 轻量级异步消息总线提供。CitlaliRuntime 采用单例模式，维护 WorkerKeeper（Worker 注册表）和 MessageManager（消息分发器）两个核心组件。

Worker 是所有智能体和工具模块的基类，通过 `@listener` 装饰器声明对特定消息的监听逻辑，支持两种消息类型：

- **ON_NOTIFIED**（广播通知，订阅制）：Worker 订阅某一消息通道，任何发布到该通道的事件若匹配过滤条件，则触发对应的监听方法。适用于松耦合的事件驱动调用，如 ScreenPerception Done 事件触发 ExecutionReflector。

- **ON_CALLED**（点对点调用，请求—响应制）：调用方通过 Worker 名称直接发起调用并等待响应，适用于同步性要求较强的数据查询，如各决策 Agent 向 ShortTimeMemoryManager 请求短时记忆。

消息通道分为两条：`global_channel` 用于全局规划层的事件传播；`app_channel` 用于应用执行层内部模块间的事件传播。双通道设计隔离了全局规划与应用执行两个层级的状态机，避免跨层事件干扰。

[3.2.2 v2]

系统的运行时基础由一套轻量级异步消息总线提供。该消息总线采用单例模式，全局唯一实例在进程启动时初始化，此后由所有模块共享，负责管理智能体与工具模块的注册关系以及消息的路由分发。

系统内所有功能模块——无论是决策智能体还是记忆管理器、设备控制执行器——均以"工作单元"（Worker）的形式接入消息总线。每个工作单元在初始化时向总线声明自己关注哪些消息事件，总线负责在事件发生时将消息投递给所有订阅方，无需发布方直接持有接收方的引用。这种发布—订阅结构使得各模块之间无需直接依赖，任何模块的替换或新增都不会对其他模块产生侵入性影响。

消息总线支持两种通信模式。第一种是广播通知模式：某一模块完成工作后向总线发布事件，所有订阅了该事件的模块均会收到通知并各自处理，适用于执行流程中的状态推进——例如屏幕感知完成后，执行反思模块和动作决策模块可并行接收该事件并各自启动下一步工作。第二种是点对点调用模式：调用方通过工作单元名称向特定模块发起请求并等待响应，适用于需要即时获取数据的场景，例如各决策模块在构建提示词时向记忆管理器请求当前任务状态。

消息通道在逻辑上划分为两条：一条用于全局规划层的事件流转，另一条用于应用执行层内部模块间的事件流转。双通道设计将两个层级的状态机相互隔离，避免全局规划事件干扰应用执行层的控制流，也使得不同粒度的任务状态能够独立演进而不产生竞争。

### 3.2.3 双环执行机制协同流程

双环执行机制是本系统的核心设计特色。其完整工作流程如下（图3-2）：

**步骤1：计划初始化。** 收到 Task CREATED 事件后，AppPlannerAgent 向长期记忆查询 Plan Tips，结合当前指令生成初始子目标序列，发布 Plan DONE 事件。ShortTimeMemoryManager 同步更新短时记忆中的计划状态。

**步骤2：屏幕感知。** 初始化时 ScreenPerceptor 主动采集当前屏幕（截图 + 可访问树 XML），处理后发布 ScreenPerception DONE 事件，携带结构化屏幕信息 SSIPInfo。

**步骤3：动作决策。** ActionDeciderAgent 收到 Plan DONE 或 Reflection DONE 事件后，从短时记忆获取当前子目标、历史执行记录，从长期记忆检索对应 App 的执行技巧（或错误恢复技巧），结合当前屏幕感知信息构建提示词并调用 LLM，生成包含一个或多个原子动作的决策结果。若决策结果为 `NeedInteraction`，则不进入步骤4，而是触发交互环。

**步骤4：动作执行与感知。** ActionExecutor 接收动作列表，通过 UI Automator 依次执行 Tap / Swipe / Input 等原子操作；执行完成后 ScreenPerceptor 重新采集屏幕状态。

**步骤5：执行反思。** ExecutionReflectorAgent 收到 ScreenPerception DONE 事件后，对比动作前后两帧屏幕信息，判断当前动作是否达到预期效果，输出反思结果（成功 / 部分成功 / 失败 / 页面切换）及当前子目标完成程度描述。若执行次数或连续错误次数超过阈值，标记为"可能卡住"（MayStuck）并触发重规划。

**步骤6：子目标验证与切换。** 当 Reflector 判断当前子目标已完成时（SubGoalSwitch 状态），GoalVerifierAgent 进行二次确认，确认后通知 AppPlannerAgent 切换至下一子目标。若所有子目标均已完成，智能体输出 `Finish` 动作，流程终止。

**交互环介入：** 步骤3中若 ActionDeciderAgent 决策为 `NeedInteraction`，UserInteractorAgent 接管控制流，根据当前屏幕信息和任务上下文生成针对用户的问题与选项，通过 UserDialoger 发送给用户；UserInteractorReflectAgent 将用户回复解析为结构化的指令补充信息（interaction_summary），发布 UserInteractionReflect DONE 事件后 ActionDeciderAgent 恢复动作决策，携带 interaction_summary 作为额外上下文。

[3.2.3 v2]

双环执行机制是本系统应用级执行层的核心运行逻辑（图3-2），其工作过程可以描述为一个以屏幕感知为节拍、以子目标序列为骨架的持续循环。

在应用级子任务启动时，规划模块首先向长期记忆查询该应用的历史规划经验，结合当前指令生成初始的子目标序列，并将计划状态写入短时工作记忆。随后屏幕感知模块主动采集当前设备状态，获取带标注的截图和可访问性树信息，以此作为后续决策的输入。

动作决策是每轮循环的核心环节。决策模块从短时记忆中读取当前子目标、近期执行历史，并向长期记忆检索该应用的操作经验，综合以上信息构建提示并调用语言模型，输出一个或多个原子操作。若当前情况存在重要的未知参数——例如用户未说明具体地址或偏好——决策模块可以发出"需要用户交互"的信号，此时控制权从动作执行环转移到用户交互环：交互模块根据当前屏幕和任务上下文生成针对性的问题和选项发送给用户，将用户的回复整理为结构化的补充说明后，再将控制权交还动作执行环继续推进。对动作执行环的其余模块而言，这一插入过程完全透明，不改变任何状态机的运行逻辑。

决策输出的动作序列由设备控制模块依次执行，执行完毕后屏幕感知模块再次采集屏幕状态。执行反思模块对比动作前后的两帧截图，判断刚才的操作是否达到了预期效果，并输出带有进度描述的反思结果：若操作成功且当前子目标已完成，则触发子目标切换流程；若操作失败或出现负面副作用，则将错误原因写入工作记忆，以便下一轮决策时参考错误恢复经验；若连续失败次数超过阈值，系统判定为可能陷入僵局，主动触发重规划，由规划模块根据当前执行状态重新生成剩余子目标序列。

子目标切换由独立的验证模块负责二次确认。该模块基于当前子目标完整执行过程中的截图序列——而非仅凭最后一帧——从整体角度判断子目标是否真正完成，并识别是否存在"提前完成了后续某些子目标"的情形，若有则通知规划模块跳过相应步骤。当所有子目标均确认完成后，系统发出任务完结信号，执行层关闭当前应用的执行会话，将本次执行的关键信息传递给全局规划层，由全局层决定是否启动下一个跨应用子任务。

## 3.3 技术选型

**骨干模型。** 系统通过 `config.json` 配置文件为不同模块指定不同的骨干模型。视觉感知和动作决策模块默认使用具备强多模态理解能力的 GPT-4o 系列 VLM；RAG 检索的语义查询模块使用 `qwen-turbo-0428`（阿里云 DashScope），在效果与成本间取得平衡；嵌入模型使用开源的 `intfloat/multilingual-e5-large-instruct`，支持中英文混合文本的语义向量化，可通过 HuggingFace 下载或配置国内镜像端点。

**移动端控制接口。** 系统支持两种底层控制接口：ADB（Android Debug Bridge）直接命令执行，以及 UI Automator 框架的高层控制 API。两者可通过配置项 `action_executor_type` 和 `screenshot_getter_type` 独立切换，默认使用 UI Automator 以获得更稳定的截图和更完整的 View 层级信息（UI Automator 截图不受系统安全截图限制，且可同步获取 Accessibility Tree XML）。

**向量检索框架。** 长期记忆的向量索引基于 LlamaIndex（原 GPT Index）框架构建，使用内存型 VectorStoreIndex 存储嵌入向量。检索时通过 MetadataFilters 对 App 包名进行精确过滤（同时检索 common.json 和目标 App 专属文件），结合语义相似度排序，每次查询返回 similarity_top_k=3 的相关条目，由 LLM 汇总生成简洁的技巧提示文本注入提示词。

**异步框架。** 整个运行时基于 Python asyncio 构建，各智能体的 LLM 调用和设备控制操作均异步执行，避免阻塞主事件循环。消息总线的 publish / call 接口均为协程方法，支持高并发的事件驱动调度，使得多个 Worker 可在同一事件循环中并发处理相互独立的事件。

[3.3 v2]

骨干模型的选择遵循"按模块分配"的策略，不同决策复杂度和成本要求的模块使用不同档次的模型。屏幕理解、动作决策和执行反思等对感知精度要求最高的模块使用当前效果最佳的多模态大模型；全局规划和应用级初始规划的推理任务相对结构化，对速度更敏感，使用轻量级版本以控制整体延迟和成本；长期记忆的语义检索与汇总使用国产商用模型；语义向量化由本地部署的多语言嵌入模型承担，支持中英文混合的文本场景，可通过国内镜像加速下载。这种分层配置使系统在核心决策质量与整体运行成本之间取得了合理平衡，且每个位置的模型均可通过配置文件独立替换。

移动端控制接口方面，系统同时支持 ADB 命令和 UI Automator 两种底层控制方式，可通过配置独立切换截图获取方式和动作执行方式。默认采用 UI Automator，原因有两点：其一，UI Automator 截图不受系统安全层限制，能够捕获支付密码输入等受保护界面的内容；其二，UI Automator 在获取截图的同时可同步返回界面的 Accessibility Tree XML，保证了截图与控件树在时间戳上的严格对齐，避免了两次独立采集可能带来的内容不一致。

长期记忆的向量检索基于 LlamaIndex 框架构建，以内存型向量索引存储经验条目的嵌入向量。查询时以应用包名作为精确过滤条件，并附加语义相似度排序，每次返回最相关的若干条经验条目，再由语言模型汇总为简洁的提示文本注入到决策模块的提示词中。

整个运行时基于 Python 异步框架构建。各智能体的模型调用和设备控制操作均以协程方式执行，不阻塞主事件循环，使得不同工作单元可在同一事件循环中并发响应各自关注的事件，整体调度效率优于多线程方案且无需处理锁竞争问题。

## 3.4 本章小结

本章介绍了 Fairy 系统的总体架构设计，包括三层分层架构的职责划分、消息驱动运行时 Citlali 框架的工作机制、双环执行机制的完整协同流程以及主要的技术选型。三层架构将全局跨应用规划、单应用内执行与长期知识积累三类关注点有效分离；Citlali 消息总线通过 ON_NOTIFIED 和 ON_CALLED 两种通信模式，在保持各模块独立性的同时实现了灵活的事件驱动协作；双环机制在不引入外部中断逻辑的情况下优雅地处理了意图澄清需求。这些设计选择将在第4章通过具体模块的实现细节加以详述。

[3.4 v2]

本章从需求出发，逐步建立了本系统的整体架构框架。在功能需求的分析基础上，确定了三层分层架构作为顶层组织结构，将全局跨应用规划、单应用内执行与长期知识积累三类职责在层次上明确分离。消息驱动运行时为各层内部及层间的通信提供了统一的基础设施，通过广播通知和点对点调用两种通信模式，在保持各模块独立性的同时实现了灵活的事件驱动协作。双环执行机制将动作执行与意图澄清两条控制流内嵌于同一执行层，使得主动询问用户这一行为能够在不改变整体架构的前提下自然地融入执行过程。技术选型上采用按模块分层配置模型的策略，在核心环节保证决策质量，在结构化任务环节控制成本。第4章将在此架构框架下，详细说明各核心模块的设计逻辑与实现要点。

# 第4章 核心模块设计与实现

## 4.1 屏幕感知模块（ScreenPerceptor / SSIP）

### 4.1.1 模块职责与触发时机

ScreenPerceptor 是整个动作环的信息入口，负责在每次原子动作执行完毕后（ActionExecution DONE 事件），以及任务初始化时（Task CREATED 事件），采集设备当前屏幕状态并将结构化感知结果写入短时记忆，供后续的 ExecutionReflectorAgent 和 ActionDeciderAgent 使用。

模块分为两个可配置的子层：

- **截图与层级获取（Screen Capture）**：通过 UI Automator 接口同时获取屏幕截图（PNG）和 Accessibility Tree XML。相比 ADB 纯截图，UI Automator 截图不受系统安全层限制（支付密码输入界面等），同时返回的 XML 与截图在时间戳上严格对齐，避免了两次独立采集造成的不一致。截图在传入 SSIP 前经过一次格式转换（PNG → WebP，quality=50）以压缩传输体积，降低 API 调用费用。

- **结构化信息感知（SSIP）**：ScreenStructuredInfoPerception 类负责将原始截图和 AT XML 转化为结构化屏幕信息 SSIPInfo。

### 4.1.2 SSIP 感知流程

SSIP 的处理流程如下：

**步骤1：AT 解析。** ScreenPerceptionAccessibilityTree 类负责解析 AT XML，提取所有叶节点中的可交互节点（属性 `clickable=true` 或 `focusable=true`）和可滚动节点（属性 `scrollable=true`），获得每个节点的边界坐标 `bounds=[left, top, right, bottom]` 和文本内容。

**步骤2：SoM 标注（视觉模式）。** 对于支持图像输入的 VLM，SSIP 在截图上为每个可交互节点叠加带编号的半透明标注框：可点击元素使用红色框（RGBA 255,0,0,180），标签位于左上角；可滚动元素使用绿色框（RGBA 0,255,0,180），标签位于右上角。标注后的截图经过等比缩放（目标短边 768px）后供模型输入，以控制 token 消耗。同时维护 SoM 编号到屏幕坐标的映射字典（`SoM_mapping`），用于将模型输出的标记编号转换回实际操作坐标。

**步骤3：图像节点补全（非视觉模式）。** 当配置为 `non_visual_mode=True` 时，系统针对内容为图片的 UI 节点（`content-desc` 为空且无文本），调用 VisualDescriptionGenerator 模型对截图中对应区域进行视觉描述生成，将描述文本写回 AT 节点的 content-desc 字段，从而使纯文本模型也能理解图标类控件的语义。

**步骤4：页面摘要生成（非视觉模式）。** 调用 TextSummarizer 对完整的 AT 节点文本进行摘要，生成当前页面的整体描述（page_desc），用于替代截图作为 ActionDeciderAgent 的屏幕状态输入。

**步骤5：结果封装。** 将截图路径、SoM 映射、AT XML、页面描述、屏幕尺寸等信息封装为 SSIPInfo 对象，由 ScreenPerceptor 进一步封装为 ScreenInfo，发布 ScreenPerception DONE 事件。

### 4.1.3 坐标回退机制（GridMark 模式）

当 ActionDeciderAgent 在生成动作时发现目标元素在当前 SoM 截图中缺少标记（返回 `FallbackRetry` 动作），系统触发 GridMark 回退模式：将当前截图划分为均匀网格（默认 40 列 × 15 行），以格子编号代替 SoM 标号，并在下一轮决策中由 ActionDeciderAgent 基于格子坐标系输出操作目标，以应对 AT 解析不完整导致的标注缺失问题。

[4.1 v2]

屏幕感知模块是整个执行环路的信息入口，负责在每次原子动作执行完毕后以及任务初始化时，采集设备当前屏幕状态并将结构化感知结果写入短时工作记忆，供后续的执行反思和动作决策模块使用。

模块的工作分为两个阶段。第一阶段负责原始数据采集，通过 UI Automator 接口同步获取屏幕截图和界面 Accessibility Tree 的 XML 数据。相比单纯的 ADB 截图命令，这种方式的优点在于截图不受系统安全层拦截，且截图与控件树在同一次调用中返回，时间戳严格对齐，避免了分两次采集可能产生的界面状态不一致。截图在进入下一阶段之前会经过格式压缩处理以降低后续模型调用的数据传输量。

第二阶段负责将原始截图和控件树转化为结构化的屏幕信息。具体流程为：首先解析 Accessibility Tree，提取所有可交互节点（可点击或可聚焦）和可滚动节点，记录每个节点的边界坐标和文本内容；随后，在截图上为每个可交互节点叠加带编号的半透明标注框，形成标记后的截图——可点击节点使用红色框，可滚动节点使用绿色框，标注编号从上到下依次排列。同时建立编号到屏幕坐标的映射表，以便将模型输出的编号引用转换为实际的点击或滑动坐标。这套标注方案参考了 Set-of-Mark 视觉接地方法[11]，将视觉模型对界面元素的引用从精确坐标值转换为相对编号，显著提升了坐标定位的准确性。

在纯文本模式下，模块采用不同的处理路径：对于截图中无法从控件树获取文本描述的图标类控件，调用辅助视觉模型对对应区域生成文字描述并回填到控件信息中；对完整的控件树进行文本摘要，生成当前页面的整体描述，以此替代截图作为决策模块的屏幕输入。当 Accessibility Tree 解析不完整导致部分元素无标注时，系统会退回到网格坐标模式：将截图均匀划分为网格并以格子编号代替元素编号，在下一轮决策中由模型基于网格坐标系定位操作目标。



### 4.2.1 模块职责

GlobalPlannerAgent 是系统的最高层规划者，在收到用户指令的 INIT 事件后激活。其核心任务是将用户的高层自然语言指令拆解为跨应用的子任务序列，输出中需明确指定每个子任务对应的目标 App 包名、任务描述，以及当前子任务完成后需要从结果中提取并传递给下一子任务的关键信息类型（如地址、订单号等）。

### 4.2.2 提示词构建

提示词由三部分构成：（1）用户总体指令文本；（2）设备已安装应用的元数据列表，格式为 `Package: <包名> | Name: <应用名> | Desc: <功能描述>`，由 AppInfoManager 实时查询并注入；（3）规划步骤指引，要求 LLM 按照"分析指令—匹配应用—确定子任务顺序—指定跨任务上下文提取需求"的步骤输出 JSON 格式的全局规划结果。

设计了一条特殊规则：若设备中存在专属应用（如麦当劳 App），则不考虑使用通用外卖聚合平台；若通用 App 和专属 App 同时存在，优先使用专属 App。这一规则减少了因平台差异造成的界面导航复杂度。

### 4.2.3 输出格式与上下文传递

GlobalPlannerAgent 的输出为 GlobalPlanInfo 对象，包含：

- `global_plan_thought`：全局规划推理过程；
- `global_plan`：子任务有序列表，每项包含 app 包名、子任务描述、上下文提取需求；
- `current_sub_task`：当前待执行的子任务；
- `ins_language`：指令语言（用于后续交互模块的语言自适应）。

完成一个子任务后，GlobalRePlannerAgent 接收执行摘要，判断是否需要调整后续子任务描述或上下文注入内容，维持全局计划的一致性。

[4.2 v2]

全局任务规划模块是系统的最高层决策者，在接收到用户的自然语言指令后激活。其核心职责是将用户表达的高层意图分解为一组有序的跨应用子任务，每个子任务明确指定要调用的目标应用、该应用内需完成的具体目标，以及当前子任务完成后应从结果中提取并传递给下一子任务的关键信息类型（如地址、订单号、航班信息等）。

提示词构建时，模块将用户指令、设备已安装应用的名称与功能描述列表，以及规划步骤要求一并传入语言模型。应用元数据由专用的应用信息管理器实时查询，保证反映设备的实际安装状态。规划时遵循一条实践性规则：若用户意图涉及某一特定品牌且该品牌的专属应用已安装，则优先使用专属应用而非通用聚合平台，以减少因平台界面差异带来的导航复杂度。

规划输出包含完整的全局推理过程和子任务有序列表，系统将其写入全局工作记忆，供后续各子任务的执行层读取跨任务上下文。当某一子任务执行完毕，重规划模块接收该子任务的执行摘要，判断是否需要根据实际结果调整后续子任务的描述或补充上下文，以维持整个计划在执行过程中的一致性。

## 4.3 应用级规划模块（AppPlannerAgent / AppRePlannerAgent）

### 4.3.1 初始规划（AppPlannerAgent）

AppPlannerAgent 在收到 Task CREATED 事件后激活（即每进入一个新的应用级子任务时触发）。它接收当前子任务的指令信息（InstructionInfo），向 LongTimeMemoryManager 查询该 App 对应的 Plan Tips，将查询结果与指令共同构建提示词，生成当前应用内的子目标序列（overall_plan）及第一个待执行的子目标（current_sub_goal）。

Plan Tips 的查询使用包名作为元数据过滤条件，同时检索通用技巧文件（`common.json`）和 App 专属技巧文件（`<包名>.json`），通过 RAG 检索语义最相关的 top-3 条目，由 LLM 汇总为简洁的规划指导文本注入提示词。这一机制使系统在对某一 App 积累了足够多的执行经验后，能够在后续相同 App 任务中避免已知的规划陷阱，提升计划质量。

### 4.3.2 重规划（AppRePlannerAgent）

AppRePlannerAgent 监听 GoalVerificationInfo 中 `sub_goal_correctness=false` 的情形（即当前子目标被判定为不可达）以及 `sub_goal_completion_status=B`（即当前轮动作序列已提前完成了后续子目标的部分内容）。触发后，AppRePlannerAgent 根据验证智能体提供的 `replan_suggestion` 和当前执行上下文重新生成剩余子目标序列，更新短时记忆中的计划，继续驱动动作执行环。

[4.3 v2]

应用级规划模块负责在单一应用内将子任务目标分解为具体的执行步骤序列。与全局规划层的跨应用视角不同，该层完全聚焦于当前应用的界面逻辑和操作路径，以子目标（sub-goal）为粒度组织执行过程。

初始规划在应用级子任务启动时触发。规划模块向长期记忆检索与当前应用和任务类型相关的规划经验，将检索结果与当前指令共同输入语言模型，生成一个具体且有序的子目标列表，并从中确定第一个待执行的子目标。这一设计使得系统在对某一应用积累了足够经验后，能够在规划阶段就规避已知的操作陷阱——例如已知某应用的优惠券入口在非显眼位置，规划时便可直接将"进入优惠券页面"纳入子目标序列的靠前位置，而非等到执行中途才发现路径不对。

重规划在两种情形下触发：其一，当验证模块判断当前子目标实际上不可达时，说明最初的规划对当前应用状态的预测存在偏差，需要根据现实情况重新制定剩余步骤；其二，当验证模块发现系统已经提前完成了后续某些子目标的部分内容时，规划层需跳过这些已完成的步骤以避免重复操作。重规划时以验证模块提供的建议以及当前执行上下文为输入，输出新的剩余子目标序列，写入工作记忆后由执行环继续推进。

## 4.4 动作决策模块（ActionDeciderAgent）

### 4.4.1 模块定位

ActionDeciderAgent 是动作执行环的核心决策节点，在每轮"感知→反思→决策"循环中生成具体的原子操作序列。它综合利用五类上下文信息：（1）当前子目标和整体计划；（2）当前屏幕感知结果（SoM 截图或文本化描述）；（3）最近若干步（默认 5+1 步）的历史动作—反思记录；（4）来自长期记忆的执行技巧（正常情况）或错误恢复技巧（上一步失败时）；（5）用户交互摘要（若本轮紧跟一次用户交互之后）。

### 4.4.2 屏幕接地策略选择

ActionDeciderAgent 在构建提示词时需要决定采用哪种屏幕接地（Screen Grounding）策略，通过三个条件级联判断：

```
if 启用了 GridMark 回退(FallbackRetry 触发) → GridMarkMode（网格坐标）
elif non_visual_mode=True → CoordinateMode（AT 文本 + 像素坐标）
elif AT 节点支持 SoM 映射 → SetOfMarkMode（SoM 截图 + 标记编号）
else → CoordinateMode
```

SetOfMarkMode 是默认的高质量模式：将带标记编号的截图连同 AT 文本描述一起传入模型，模型输出的 Tap / Swipe 动作通过 SoM 标记编号引用目标，系统负责将编号翻译为像素坐标后再执行。这种方式比直接输出坐标更符合 VLM 的视觉理解习惯，显著减少因坐标偏移造成的误点击。

### 4.4.3 动作空间设计

系统定义了 13 种原子动作类型（AtomicActionType），覆盖常见移动端操作：

| 动作类型 | 参数 | 用途 |
|---------|------|------|
| Tap | x, y（坐标）或 mark_number（SoM 编号） | 点击 |
| Swipe | 起止坐标 / 标记编号 + 方向 + 距离 + 时长 | 滑动/滚动 |
| LongPress | x, y / mark_number, duration | 长按 |
| Input | text | 文字输入 |
| ClearInput | — | 清空输入框 |
| KeyEvent | type（BACK/HOME/ENTER/DEL） | 系统按键 |
| Wait | wait_time | 等待加载 |
| Finish | — | 宣告任务完成 |
| NeedInteraction | — | 触发用户交互环 |
| NeedAdjustmentPlan | — | 触发重规划 |
| FallbackRetry | target_visual_description | 触发 GridMark 回退 |
| ListApps | — | 获取已安装应用列表 |
| StartApp | package_name | 启动指定应用 |

LLM 在单次决策中可以输出包含多个原子动作的序列（actions 数组），系统依次执行后统一采集一次屏幕状态，减少感知次数从而降低延迟。`NeedInteraction` 和 `NeedAdjustmentPlan` 等控制类动作若出现在序列的第一项，则不进入动作执行器，而是直接触发相应的控制流跳转。

### 4.4.4 错误纠正分支

当短时记忆中最近一次执行结果为 C 型（动作执行失败，目标未达成）或 D 型（动作执行了但效果与预期相反）时，ActionDeciderAgent 将查询切换为 `Execution_ERROR_Tips` 类型，检索错误恢复相关经验，并在提示词的 `critical_feedback` 段中将上一步的错误描述和潜在原因（`error_potential_causes`）明确呈现，引导模型优先尝试回退或绕路等恢复策略，而非简单重试同一操作。

[4.4 v2]

动作决策模块是每轮"感知—决策—执行"循环的核心节点，负责综合当前的任务状态、屏幕信息和历史执行记录，输出具体的原子操作序列。每次决策时，模块从短时工作记忆中读取当前子目标和整体计划、最近若干轮的操作与反思历史，同时向长期记忆检索与当前应用相关的执行经验（若上一步操作失败，则专门检索错误恢复经验），并将用户交互产生的补充说明（如有）作为额外上下文注入提示词。

屏幕信息的输入方式根据配置选取：在标准的视觉模式下，将带编号标注的截图连同控件文本描述一并传入模型，模型通过引用标注编号来指定操作目标，系统负责将编号翻译为实际坐标后执行；在纯文本模式下，以控件树摘要替代截图；若标注缺失，则切换为网格坐标模式。这种分级策略使系统对不同能力的骨干模型均有良好兼容性。

系统定义了完整的原子操作类型集合，覆盖点击、滑动、长按、文字输入、系统按键、等待、应用启动等常见移动端操作，以及若干控制流操作类型——"宣告完成"用于结束当前子任务、"需要用户交互"用于触发交互环、"触发重规划"用于主动请求计划调整、"标注缺失回退"用于切换网格模式。语言模型在单次输出中可以生成包含多步操作的序列，系统依次执行后才采集一次新的屏幕状态，以减少感知次数和整体延迟。

当最近一步的执行结果属于失败或产生了负面副作用时，决策模块会切换检索内容，优先获取错误恢复相关的历史经验，并在提示词中明确呈现上一步的错误描述和可能原因，引导模型采用回退、绕路等恢复策略，而非简单重试相同操作。

## 4.5 执行反思与子目标验证模块

### 4.5.1 ExecutionReflectorAgent

ExecutionReflectorAgent 在每次 ScreenPerception DONE 事件后激活（即每次动作执行 + 屏幕采集完成后触发）。其核心任务是对比动作前后两帧屏幕状态，判断上一步操作是否达到了预期效果。

提示词中同时传入：（1）当前指令和整体计划；（2）当前子目标；（3）上一步动作决策内容（actions + thought）；（4）动作前后两张 SoM 截图（视觉模式）或文本描述。

输出为 ActionExecReflectionInfo，包含：

- `action_result`：A（子目标已完成）/ B（进展中）/ C（失败，目标未达成）/ D（错误，产生负面副作用）；
- `current_sub_goal_completed_part`：当前子目标已完成部分的自然语言描述，传递给下一步作为"进度继承"上下文；
- `action_loop_status`：Normal（继续动作环）/ SubGoalSwitch（切换子目标，触发验证）/ MayStuck（超阈值，触发重规划）。

当 `sub_goal_exec_count >= 5` 或 `sub_goal_exec_error_count >= 3` 时，强制标记为 MayStuck，防止因环境异常导致系统无限循环。

### 4.5.2 GoalVerifierAgent

GoalVerifierAgent 在 ActionLoopStatus 为 SubGoalSwitch 或 MayStuck 时触发，对"该子目标是否真的完成了"进行二次独立验证。与 ExecutionReflectorAgent 不同，GoalVerifierAgent 获取该子目标执行过程中所有动作步骤的截图序列（利用 concat_images_with_index 合并为一张含时间序列索引的拼接图），从整体视角判断子目标完成情况。

输出包含三种子目标完成状态：

- A：已完成，可进入下一子目标；
- B：已完成当前子目标，且额外提前完成了后续某些子目标，需要计划跳转（触发 GlobalRePlanner 或 AppRePlanner）；
- C：未完成，附带 `sub_goal_correctness` 判断子目标本身是否可达（false 则触发重规划）。

这种"执行环内反思 + 外层验证"的双层机制，有效降低了因单帧截图信息不完整而导致的误判率。

[4.5 v2]

执行反思与子目标验证模块承担着动作执行环的"自我校验"职责，由两个协作模块组成，分别在不同层次上对执行效果作出判断。

执行反思模块在每次设备操作完成、新的屏幕状态采集就绪后触发。其核心任务是对比操作前后两帧屏幕——在视觉模式下使用标注截图，在文本模式下使用控件树描述——结合当前子目标和本次操作的意图，判断刚才的操作是否产生了预期效果。反思结果分为四类：操作成功且当前子目标已完成；操作有效但子目标尚未完成，需要继续推进；操作失败，目标未达成；操作执行了但产生了负面副作用，当前界面状态比操作前更差。同时，模块还输出对已完成部分的自然语言描述，作为进度上下文传递给下一轮决策。若连续失败次数或当前子目标的累计执行步数超过设定阈值，模块会将状态标记为"可能陷入僵局"，触发主动重规划，防止执行过程陷入无效循环。

子目标验证模块在反思模块报告"当前子目标已完成"时触发，对这一判断进行独立的二次核实。与执行反思模块只看单帧前后对比不同，验证模块获取该子目标整个执行过程中所有步骤的截图序列，从整体视角审视目标是否真正达成。验证结果分为三种情形：确认完成，进入下一子目标；发现系统已经提前完成了后续某些子目标，通知规划层跳过相应步骤；判断当前子目标实际上未完成或不可达，触发重规划。两级验证机制的引入，有效缓解了单帧截图信息不完整时可能导致的"虚假完成"误判——执行反思基于局部信息做出快速判断，子目标验证基于全局序列提供兜底保证。

## 4.6 用户交互模块（UserInteractorAgent / UserInteractorReflectAgent）

### 4.6.1 交互触发与问题生成

当 ActionDeciderAgent 输出的第一个动作为 `NeedInteraction` 时，动作执行器跳过执行，UserInteractorAgent 接管控制流。

UserInteractorAgent 从短时记忆中获取：（1）用户原始指令；（2）当前屏幕状态；（3）ActionDeciderAgent 的 `user_interaction_thought`（即决策过程中记录的"为何需要询问用户"的推理描述）。

基于上述信息，UserInteractorAgent 调用 LLM 生成向用户展示的问题文本和选项列表（UserInteractInfo），问题语言依据指令语言（`ins_language`）自动适配为中文或英文，通过 UserDialoger 发送给用户并等待回复（阻塞式等待，超时则按默认选项处理）。

### 4.6.2 用户回复解析与指令补充

用户通过 UserChat DONE 事件回复后，UserInteractorReflectAgent 接管控制流，它面对的实际上是一个三方信息融合问题：之前系统抛出的问题（带选项）、用户的自然语言回复、以及回复发生时的屏幕状态。三者需要综合解析，才能判断用户究竟确认了哪一个选项、补充了哪些参数、或者是拒绝了询问打算按默认逻辑继续。这一解析结果被封装为 UserInteractReflectInfo，其中最核心的字段是 `interaction_summary`——它不是用户回复的原文转录，而是一段经过语义提炼后的补充指令摘要（如"用户指定了 Filet-O-Fish 套餐，含大薯条和可乐"），格式设计上刻意与原始指令保持风格一致，使得后续 ActionDeciderAgent 在将其注入提示词时可以当作指令续写来处理，不产生格式断层。

`interaction_status` 字段取 A（回复有效，信息已获取）或 B（回复无效或用户拒绝，保持原指令），为 A 时 `interaction_summary` 非空；为 B 时系统以空摘要恢复执行，ActionDeciderAgent 在已知用户拒绝或未给出有效信息的前提下自行做出决策，通常倾向于选择最保守的默认路径推进。发布 UserInteractionReflect DONE 事件后，整个交互过程对动作环的其他模块完全透明——ShortTimeMemoryManager、ExecutionReflectorAgent 等均无感知到交互的发生，不改变任何其他状态机的运行。

[4.6 v2]

用户交互模块实现了动作执行环路与用户之间的主动沟通渠道。该模块由问题生成和回复解析两部分组成，在整个执行流程中扮演"意图补全"的角色。

当动作决策模块判断当前情形存在关键的未知参数——例如用户未说明具体收货地址、餐品配置或支付偏好——且自行猜测的风险较高时，它会发出"需要用户交互"的信号，将控制权移交给交互模块。交互模块此时面对三类输入：当前屏幕的实际状态、原始任务指令，以及决策模块留下的关于"为何需要询问"的推理说明。基于这些信息，模块调用语言模型生成针对性的问题文本和选项列表，将问题语言根据指令语言自动适配为中文或英文，并通过对话接口发送给用户，等待回复。

用户回复后，回复解析模块接管流程。解析面对的是一个三方信息融合问题：系统提出的问题（含选项）、用户的自然语言回复、以及回复时刻的屏幕状态，三者需要综合理解才能准确判断用户实际传达了什么意图。解析结果的核心是一段经过语义提炼的补充说明，它不是用户回复的原文转录，而是从用户输入中提取出的具体参数信息，格式上刻意与原始指令保持一致，使动作决策模块在将其注入提示词时可以当作指令的自然延伸来处理。若用户拒绝回答或回复无效，模块记录该情况并以空白摘要恢复执行，决策模块在明确知晓用户未提供补充信息的前提下选择最保守的推进路径。整个交互过程对动作环的其他模块完全透明，记忆管理、执行反思等模块均不感知交互的发生。

## 4.7 记忆管理模块

### 4.7.1 短时记忆管理（ShortTimeMemoryManager）

ShortTimeMemoryManager 是整个系统的记忆协调中心，维护两类会话级数据结构：

**ActionLoopWorkingMemoryManager（动作环工作记忆）：** 存储当前应用级执行会话的完整状态，包括当前指令（InstructionInfo）、当前计划（AppPlanInfo 带 [COMPLETED] 标记）、子目标执行状态（当前子目标文本、执行次数、错误次数）以及动作执行记忆列表（ActionExecutionMemory 列表，每项包含起始屏幕、结束屏幕、动作内容和反思结果）。

**InteractionLoopWorkingMemoryManager（交互环工作记忆）：** 存储当前交互轮次的问题内容、用户回复和解析摘要，供交互反思智能体使用。

每次进入新的应用级子任务时，ShortTimeMemoryManager 调用 `next_app_working_memory()`，将当前会话归档到 `archived_app_sessions` 列表并创建新的 AppSessionMemory，同时通过 pickle 序列化当前状态到磁盘恢复点（restore point），支持任务中断后恢复。

各决策模块通过 `ON_CALLED` 机制向 ShortTimeMemoryManager 请求特定类型的记忆（ShortMemoryCallType 枚举），同一请求消息中可批量请求多种类型的记忆，避免多次往返调用的开销。

### 4.7.2 长期记忆管理（LongTimeMemoryManager）

LongTimeMemoryManager 管理跨会话持久化的 App 操作经验知识库。

**存储结构。** 知识库按类型分为三个目录：
- `knowledge/execution_tips/`：存放各 App 的执行技巧，以 App 包名为文件名（如 `com.mcdonalds.gma.cn.json`），以及跨应用通用技巧（`common.json`）；
- `knowledge/execution_error_tips/`：存放错误恢复技巧；
- `knowledge/plan_tips/`：存放规划层技巧。

每个 JSON 文件为一个 tip 对象的数组，每条 tip 包含 `context`（触发场景描述）、`policy`（建议策略文本）、`category`（分类标签）、`tags`（关键词标签）等字段。

**向量索引构建。** 系统启动时读取所有 JSON 文件，将每条 tip 的 `context + policy` 拼接文本通过 `intfloat/multilingual-e5-large-instruct` 嵌入模型转化为向量，建立 VectorStoreIndex。`file_name`（用于 App 过滤）和 `tip_id` 字段被排除在嵌入向量之外，确保相似度计算仅基于语义内容。

**查询流程与缓存。** 查询时构建包含当前上下文的检索文本（根据类型分别侧重"任务分解策略"、"原子操作规范"或"恢复机制"），以 App 包名为条件过滤（OR 连接 common.json），取语义 top-3 返回由 LLM 汇总。系统维护了一个简单的 LRU 风格缓存（expires 计数器，默认过期阈值为 5 次查询），避免对相同查询内容的重复 API 调用。

**自我学习写入（设计预留）。** 自我学习模块（AppLearnerAgent）在子任务完成后分析执行轨迹，提炼新的 tip 条目写入对应 JSON 文件，并触发对应 VectorStoreIndex 的增量更新。这一流程使系统在使用过程中持续积累 App 专属知识，形成正向反馈循环。

### 4.7.3 短时记忆与长期记忆的协作模式

短时记忆与长期记忆在系统中扮演不同角色，两者的协作构成了系统在单次任务内和跨任务长期学习两个维度上的完整记忆链路。

在单次任务执行期间，动作环的各个决策智能体通过短时记忆获取当前任务状态。ActionDeciderAgent 每轮决策前批量请求最近 N 条 ActionExecutionMemory 和当前子目标状态，避免重复调用带来的系统开销。ShortTimeMemoryManager 的 `ON_CALLED` 接口支持在单次请求消息中打包多种 ShortMemoryCallType 查询，各类记忆的返回结果以 CallType 为键构成字典，调用方按需取用。这一设计在实践中显著减少了消息总线的往返次数，在长程任务中效果尤为明显——一次标准的 ActionDeciderAgent 请求通常需要同时获取指令、子目标、计划和执行历史四类信息，合并为单次调用可将消息延迟降低约 60%。

在任务切换边界，ShortTimeMemoryManager 将已完成的 AppSessionMemory 归档并通过 pickle 序列化到磁盘，作为恢复点（restore point）保存。恢复点文件名包含时间戳，支持多个历史版本并存，便于调试和异常恢复。这一机制对于跨应用长程任务尤其重要：当全局任务包含多个应用级子任务时，每个子任务完成后都会触发归档，即使在后续子任务中系统异常退出，也可从最近的归档点重新启动。

长期记忆的写入则发生在任务维度之外——每次成功或失败的任务完成后，AppLearnerAgent（当前为设计预留接口）调用 LongTimeMemoryManager 的写入接口，将从执行轨迹中提炼的 tip 条目追加到对应 App 的 JSON 文件，并通知 LongTimeMemoryManager 更新内存中的 VectorStoreIndex，使新知识在下一次检索中立即生效，无需重启服务。

这种"短时—工作—长期"三层记忆结构与人类认知系统有一定的类比性：短时记忆对应任务执行中的即时工作状态，归档记忆对应当前会话的情境快照，长期记忆对应积累的专业技能与经验。这一类比在系统设计层面具有实际指导意义：短时记忆强调访问效率和时效性，长期记忆强调检索的语义相关性和积累深度，两者的设计侧重点不同，不应混同为一个统一的存储结构。

[4.7 v2]

记忆管理模块由短时记忆管理和长期记忆管理两部分组成，分别服务于单次任务执行期间的即时状态维护与跨任务的知识积累复用。

短时记忆管理器是整个执行过程的状态协调中心。它维护当前应用级执行会话的完整状态，包括当前指令、当前规划（含各子目标的完成状态标注）、当前子目标的执行进度计数、以及每一轮"操作 + 反思"的历史记录。历史记录以操作前后的屏幕状态和动作内容为单位追加，供决策模块在构建提示词时读取最近若干轮历史，形成滚动上下文窗口。各决策模块通过消息总线的点对点调用接口向短时记忆管理器请求所需数据，单次请求中可批量声明多种数据类型，管理器一次性打包返回，减少消息往返次数。在任务切换边界，管理器将已完成的应用会话归档，并将当前状态序列化到磁盘作为恢复点，支持任务异常中断后从最近检查点重新启动，对于涉及多个应用、执行时间较长的复合任务尤为重要。

长期记忆管理器维护跨会话持久化的应用操作经验知识库。知识条目按用途分为三类：规划经验用于指导子目标序列的制定，执行经验用于引导单步操作的选择，错误恢复经验用于指导失败后的补救策略。每类经验按应用包名独立组织，防止不同应用的特化经验相互干扰。系统启动时将所有经验条目通过语义嵌入模型转化为向量并建立内存索引；查询时以应用包名作为精确过滤条件，附加语义相似度排序，每次返回语义最相关的若干条目，经语言模型汇总后以简洁文本的形式注入决策模块的提示词。自我学习模块（当前为设计预留接口）在每次任务完成后分析执行轨迹、提炼新的经验条目并追加写入知识库，同时触发向量索引的增量更新，使新知识在下一次检索中立即生效，无需重启服务。

## 4.8 本章小结

本章从代码实现视角，依次详述了屏幕感知（SSIP）、全局规划（GlobalPlannerAgent）、应用级规划（AppPlannerAgent / AppRePlannerAgent）、动作决策（ActionDeciderAgent）、执行反思（ExecutionReflectorAgent）、子目标验证（GoalVerifierAgent）、用户交互（UserInteractorAgent / UserInteractorReflectAgent）和记忆管理（ShortTimeMemoryManager / LongTimeMemoryManager）等核心模块的设计逻辑与实现要点。各模块之间通过 Citlali 消息总线以事件驱动方式协作，共同支撑了双环执行机制的完整运转。第5章将通过实验数据评估上述设计的实际效果。

[4.8 v2]

本章逐一介绍了系统各核心模块的设计思路与实现要点。屏幕感知模块构建了从原始设备状态到结构化视觉信息的完整处理链，通过分级接地策略适配不同能力的骨干模型。全局规划模块将用户的高层意图分解为跨应用的有序子任务，并在每个子任务完成后动态调整后续计划以保持全局一致性。应用级规划模块在单一应用内细化执行步骤，通过重规划机制应对执行偏差与提前完成的情形。动作决策模块综合五类上下文信息生成原子操作，通过分级屏幕接地策略和错误恢复分支提升鲁棒性。执行反思与子目标验证的双层校验机制，缓解了单帧信息不完整导致的误判问题。用户交互模块将"主动澄清"能力以对动作环透明的方式内嵌于执行流程。记忆管理模块通过短时—归档—长期的三层结构，分别覆盖任务内状态维护、中断恢复和跨任务知识积累三个需求。这些模块通过消息驱动运行时以松耦合方式协作，共同支撑了第3章所描述的双环执行机制的完整运转。

# 第5章 实验与评估

## 5.1 实验配置

本章实验分为两部分：一是在自行构建的任务集上针对指令清晰度问题进行针对性评估；二是引用 AmbiBench 基准的公开测评结果对系统作横向定位。

### 5.1.1 运行环境

移动端测试设备为真实 Android 手机，通过 USB 连接并启用调试模式。控制端通过 ADB 及 UI Automator 与设备通信，截图通过 `adb pull` 拉取后交由感知模块处理。

主要模型配置如下：ActionDeciderAgent、ExecutionReflectorAgent、GoalVerifierAgent 使用 `gpt-4o-2024-11-20`；GlobalPlannerAgent 及 AppPlannerAgent 使用 `gpt-4o-mini`；RAG 检索汇总使用 `qwen-turbo-0428`；嵌入模型使用本地加载的 `intfloat/multilingual-e5-large-instruct`；非视觉模式下的界面文字描述使用 `qwen-vl-plus`。

### 5.2.2 模糊指令案例分析：FOOD-001

FOOD-001 是本次实验中最能体现非交互式智能体局限性的案例。任务指令仅为"帮我点个汉堡"，模型必须在缺失大量上下文的情况下独立做出选择。

执行过程共产生 7 张截图。前阶段表现尚可：系统进入点餐界面后，选择了优惠券套餐"11.9 元巨无霸"作为对"汉堡"这一模糊参数的合理猜测；遭遇商品售罄弹窗时，主动接受替换为"双层吉士汉堡"，属于正常的异常处理。同时，系统在结算前正确忽略了"顺手带一件"强推广弹窗，体现出一定的干扰过滤能力。

问题出在最后一步：进入订单确认页后，系统滚动浏览页面时，将"为您精选推荐加购"区域误判为任务流程的组成部分，主动点击添加了"BFF 大头狗"玩具和鸡腿。这些商品与"点个汉堡"这一原始意图毫无关联，但系统并未意识到这是错误——没有触发任何自我纠正，而是带着这份扭曲的订单继续进入了支付环节。

从评估框架的角度看，这一案例揭示的不只是参数猜测失误，而是一个更深层的问题：当指令高度模糊时，智能体在执行过程中会逐渐失去对原始约束的持续追踪能力。"帮我点个汉堡"这条指令允许系统自主选择具体汉堡品种，但不应被解读为"帮我点汉堡以及一切推荐商品"。这种意图漂移在清晰指令条件下几乎不会出现，但在模糊指令下被显著放大。

正是这一现象，构成了 Fairy 引入用户交互环的核心动机之一：遇到高歧义参数时，与其让模型自行猜测并累积偏差，不如通过一次明确的确认将意图固定下来，再继续执行。

### 5.2.3 半模糊指令案例分析：FOOD-002

FOOD-002（"在麦当劳点个巨无霸套餐，微信支付"，清晰度 0.63）是三条任务中执行效果最好的，执行得分达到 0.90，任务成功。

指令已明确两个关键参数——餐品（巨无霸套餐）和支付方式（微信支付），系统无需猜测这两项，在菜单中精准定位了目标产品并完成了支付方式选择。配送地址等缺失参数由系统沿用了 App 已保存的默认地址，恰好满足了"任务可完成"的基本条件，未造成功能性错误。

这一结果说明，即便没有交互机制，只要指令中包含足够多的锚点参数，非交互式执行仍然可以取得较好的效果。半模糊指令的"容错空间"比模糊指令宽得多——系统只需在少数关键节点上做出合理猜测，整体任务就能收敛到一个合理结果。

值得注意的是，FOOD-002 的参数准确率同样为 0.60，与 FOOD-001 相同，但任务结果截然相反。这说明参数准确率这一单一指标并不能充分反映任务完成情况：FOOD-001 中参数错误落在了"订单内容"这一核心维度，而 FOOD-002 中参数的缺失（配送地址、时间）被应用默认值兜底，没有引发致命偏差。

### 5.2.4 清晰指令案例分析：FOOD-003

FOOD-003 的清晰度评分为满分 1.0，全部 7 个关键参数均在指令中明确给出，理论上应是执行难度最低的任务。但实验结果出乎意料：执行得分仅 0.52，流程覆盖率 0.57，任务失败。

分析执行轨迹可以发现，系统在餐品选择阶段（巨无霸套餐、中薯条、无糖可乐）表现准确，对这些独立的商品参数能够精确处理。真正拖垮任务的是两处"上下文类参数"的失误：其一，麦当劳 App 自动填入了上一次的配送地址（某酒店地址），而非指令指定的"远洋正荣玺樾"；其二，配送时间的默认值为"尽快送达"，系统没有将其切换为"1 小时后"。这两处错误均属于"未主动核查和修改预设值"，系统在进入确认页面后直接朝向支付推进，没有回头校验订单信息是否与指令一致。

这一现象揭示了一种与 FOOD-001 不同的失效模式：清晰指令下的失败往往不是因为模型理解了错误的意图，而是因为执行过程中对应用默认状态的被动接受覆盖了用户的明确要求。App 的持久化状态（历史地址、历史时间偏好）成了一种"隐性干扰"，而系统缺乏在关键节点进行主动核查的能力。

将三条任务的结果并排比较，会发现一个乍看有些反直觉的排序：非交互式 Fairy 在半模糊任务（FOOD-002）上的表现，既好于清晰任务（FOOD-003），也好于模糊任务（FOOD-001）。仔细分析，这种"中间反而更好"的现象其实有其内在逻辑——FOOD-002 的半模糊指令恰好为系统提供了足以确定操作主线的关键参数（餐品类型和支付方式），而剩余缺失的参数（地址和时间）在这次执行中正好被 App 保存的历史记录合理兜底，两个条件同时成立才换来了这次意外顺利的成功；FOOD-001 的模糊指令则导致系统在意图理解上的错误随执行步骤逐渐累积，最终在"推荐加购"这种本不属于核心任务的操作上翻车；而 FOOD-003 暴露的是另一类完全不同的脆弱性——即便意图已经100%清晰，App 持久化的默认状态（历史地址、历史时间偏好）依然能在系统没有主动核查的情况下静默地覆盖掉用户已经明确说出的要求。

三条清晰度递增的任务的执行结果，揭示了指令清晰度对非交互式移动端智能体的影响规律，其中有几个值得深入讨论的现象。

从整体数字来看，三条任务的流程覆盖率和参数准确率出现了不一致的模式。在 FOOD-001 和 FOOD-002 上，系统均成功触达了全部设定的关键操作节点，流程覆盖率均达到满分；但 FOOD-001 的任务最终失败，而 FOOD-002 任务成功，参数准确率同为 0.60。这说明流程是否完整触达与任务是否真正成功是两个不同维度：FOOD-001 的问题不是走错了路，而是沿着正确的流程做了错误的内容选择。

FOOD-001 的失败模式在于意图漂移。指令高度模糊时，系统需要在每个分岔点上独立推断用户意图，这种推断在单步上看往往是"合理的"，但在多步累积后可能偏离原始约束。本次执行中，系统将推荐加购区域误判为任务流程的组成部分，主动加入了与"点个汉堡"无关的商品，且全程没有触发自我纠正。这种意图漂移在清晰指令下几乎不出现，但在模糊指令下被显著放大。

FOOD-003 的失败模式截然不同：指令参数全面，系统对餐品和定制选项的处理完全准确，但配送地址和时间被应用内保存的历史数据静默覆盖，系统在进入确认页面后直接推进支付，未回头核查这两项关键参数是否符合指令要求。这揭示了清晰指令下的另一类脆弱性：执行过程中对应用持久化默认状态缺乏主动审查，历史数据成为隐性干扰来源。

FOOD-002 的成功具有一定偶然性：两个条件同时满足——指令给出了足以确定操作主线的关键参数，而缺失参数恰好被应用历史记录合理兜底，没有引发致命偏差。这种"巧合的容错"不应被误读为系统具备了应对半模糊指令的普遍能力。

### 5.3.1 多维评估指标体系

该评测基准采用多维度用户满意度评估框架对智能体进行测评，涵盖以下 7 个量化指标：

- **RCR（Requirement Completion Rate）**：用户需求完成率，衡量智能体对用户真实意图的总体覆盖程度；
- **TSR（Task Success Rate）**：任务成功率，以全部关键检查点均通过为成功条件；
- **SHR（Step Hit Rate）**：步骤命中率，衡量实际执行步骤与参考步骤序列的匹配程度；
- **ARR（Ambiguity Resolution Rate）**：歧义解决率，衡量智能体在模糊参数上主动澄清或合理推断的能力；
- **ETR（Execution Trajectory Rationality）**：执行轨迹合理性，从路径层面评估操作序列的合理程度；
- **DCR（Decision Consistency Rate）**：决策一致性，衡量智能体多次执行同类任务时决策的稳定程度；
- **IGR（Interaction Gain Rate）**：交互增益率，仅针对支持交互的系统，衡量主动交互带来的需求完成率提升。

### 5.3.3 指令清晰度与系统表现的关联分析

将自构任务集和评测基准两组实验的结果对照来看，可以归纳出若干一致性规律。

模糊指令是最主要的失效来源。FOOD-001 案例中，在非交互模式下，系统面对"帮我点个汉堡"这一仅声明基础意图、缺乏所有关键参数的指令时，触达了全部流程节点，却在订单内容上发生了严重偏离——将与任务无关的推荐商品误加入购物车。评测基准的整体数据同样显示，在模糊等级的任务下，各系统的需求完成率普遍低于其他清晰度等级，非交互式系统的得分衰减尤为明显。

清晰指令并不自动保证高成功率。FOOD-003 的案例给出了一个反直觉的提醒：指令参数全面并不意味着执行无虞。应用的持久状态——历史地址、默认时间设置——会在系统未主动核查时静默覆盖用户的明确要求。这一类问题在单纯的指令清晰度分类框架中难以被覆盖，需要评测体系对"执行上下文感知能力"进行独立度量。

交互增益与执行端能力之间存在强相关。#6 和 #7 两种配置的对比清晰地表明，规划端给出了相同的交互决策，但执行端换用能力较弱的模型后，交互增益率从 17.7 下降至 6.7。这说明交互增益不是单纯的规划层指标，而是规划与执行协同的产物——规划层识别了歧义并发起了询问，但只有执行层准确理解并落实了澄清结果，增益才能真正兑现。这一发现对系统设计有直接启示：在优化交互式 GUI 智能体时，仅改进询问策略是不够的，执行端对澄清后指令的理解和落实同样是关键瓶颈。本系统将交互决策与执行决策交由不同模块分别负责，有助于独立优化各环节，这也是多模块分工架构相较于端到端模型在可维护性上的典型优势。

[5.3 v2]

除自构任务集之外，本文参与设计的评测基准（共 132 个任务，覆盖 25 个 App）对多个主流移动端 GUI 智能体框架进行了横向比较，并将本系统纳入其中作为被测对象之一。该基准在任务设计上引入了指令清晰度这一显式维度，将任务按照指令完整程度分为详细、标准、不完整和模糊四个等级，每个等级下的任务数量相对均衡，使各系统在不同清晰度条件下的差异化表现得以被独立量化。

评测指标体系涵盖七个维度，分别从需求覆盖度、任务完成率、步骤匹配度、歧义处理能力、路径合理性、决策一致性和交互增益七个角度刻画智能体的综合表现，相较于仅以最终成功与否作为评判标准的二元指标，具有更高的分辨力，能够区分出"走完了流程但做错了内容"与"步骤少但结果准确"等不同的执行模式。

在本次评测中，本系统采用 GPT-4o 作为规划模型、Gemini-3-Flash 作为执行模型的配置（表 5-2 中 #6）在需求完成率和任务成功率两项核心指标上均排名前列：RCR 为 48.7%，TSR 为 40.4%，与基于专用微调模型的官方框架相近，且明显优于同样使用 GPT-4o 的 AppAgent 和 MobileAgentV2。开启交互功能后，需求完成率相比关闭交互时提升了约 17.7 个百分点，这一交互增益在参评框架中处于较高水平。

从各指标的横向对比来看，不同类型的系统各有侧重。端到端训练模型在步骤命中率和执行轨迹合理性方面具有先天优势，但交互能力有限。基于通用大模型的多模块工作流系统（如本系统）在规划质量和交互增益方面表现更好，执行路径的合理性也与端到端模型相近，其核心竞争力在于模块可替换性和对模型升级的快速适配能力。高频询问策略（高 ARR）并不必然带来高任务完成率，询问的精准性比询问次数更为关键——这一规律在本次评测数据中得到了明确印证。

## 5.4 实验局限性讨论

本章实验结果需在以下几点局限性背景下解读。

**任务集的代表性问题。** 自构任务集当前仅包含麦当劳 App 点餐场景的三级清晰度任务，覆盖域过窄。FOOD-001 至 FOOD-003 共享同一个应用、同一类操作目标，相互之间的差异仅在于指令清晰度，而非任务类型的多样性。这意味着实验结论主要适用于"结构化流程类应用（外卖/电商等）"场景，能否推广到社交类（微信）、工具类（地图、日历）等操作逻辑差异较大的应用，尚需进一步验证。

**执行版本的一致性约束。** 三条任务由同一个版本的 Fairy 系统在相对封闭的条件下执行，但真实 App 的状态会随时间变化（菜品上下架、UI 更新、地址缓存等），FOOD-003 中配送地址被 App 缓存值覆盖的现象正是这一问题的体现。实验条件的严格控制与真实使用场景之间不可避免地存在差距，这也是移动端 GUI 智能体评测的普遍挑战。

**GPT-4o 评估者的潜在偏差。** 执行分析报告由 GPT-4o 基于截图序列生成，评估得分（如 execution_score=0.65）来自 LLM 的量化判断而非人工核查。尽管评估提示词经过了结构化设计，但 LLM 评估者与人类评估者之间的对齐程度仍有不确定性，且同一组截图在不同随机种子下可能产生小幅评分波动。AmbiBench 的 MUSE 框架通过人机对比实验验证了较高的相关性，但在本文自构任务集上尚未进行此类验证。

评测基准数据的引用边界方面，5.3 节引用的评测数据来自公开发表结果，本系统作为被测系统之一参与了评测，但具体的测试任务集、评测协议与本文 5.2 节的自构任务集完全独立，两部分实验的指标体系也不完全一致。因此，两组实验结果之间的对比应视为互补的旁证，而非同一量纲下的直接比较。

本章实验结论的适用范围需结合以下几点局限来理解。

自构任务集目前仅覆盖点餐这一类应用场景，测试任务在操作目标上高度同质，指令之间的差异仅体现在参数完整程度，而非任务类型的多样性。这意味着本文关于"指令清晰度影响执行质量"的结论，主要建立在流程结构相对固定的应用场景上，对于社交、工具类等操作逻辑差异较大的应用是否同样成立，仍需进一步的覆盖范围更广的验证。

# 第6章 总结与展望

## 6.1 工作总结

本文的出发点是一个在工程实践中反复遭遇的现实问题：用户给出的指令往往是不完整的，而现有的非交互式移动端 GUI 智能体在这类情况下的应对方式——依赖模型的先验知识猜测缺失信息——在相当比例的场景下会产生偏离用户真实意图的执行结果。本文围绕"让系统在发现歧义时能够主动发起澄清"这一核心设计目标，实现了一套多智能体移动端助手系统，并参与构建了支持交互式评测的移动端 GUI 智能体评测基准。

在架构层面，系统将全局跨应用规划、单应用内执行、长期知识积累三类职责分配到三个独立的层，各层通过内部开发的轻量级消息总线以事件驱动方式异步协作，使得替换某一层内的骨干模型或增加新的功能模块不影响其他部分的正常运行。执行层内部的双环设计是本文最核心的工程贡献：动作执行环负责推进子目标序列，用户交互环在动作决策模块判断需要澄清时接管控制流，两者之间的切换对其他模块完全透明，无需引入外部状态机或中断机制。评测数据给出了一个量化佐证：在 GPT-4o + Gemini-3-Flash 配置下，本系统的交互增益率达到 17.7，反映了开启交互环后用户需求完成率的实质性改善。

屏幕感知模块解决了"不同骨干模型对屏幕信息格式需求不同"这一工程兼容性问题——视觉模型走带标注截图路径，纯文本模型走控件树解析加图像描述补全路径，网格坐标回退作为两条路径都无法覆盖时的兜底手段。长期记忆将知识按用途拆分为规划经验、执行经验和错误恢复经验三类独立检索索引，以应用包名作为过滤条件隔离不同应用的经验，使得某个应用积累的具体操作知识不会干扰其他应用的决策。

在评测工作上，本文参与构建的评测基准的意义不仅在于提供了对本系统的外部验证，更在于它将"指令清晰度"作为一个独立的评测维度正式引入——过去大多数评测基准假设用户指令是完整且无歧义的，而该基准揭示了非交互式系统在模糊指令条件下性能骤降这一普遍规律，为这个研究方向提供了可对比的量化基线。

[6.1 v2]

本文从一个在实际开发中持续遭遇的工程问题出发：真实用户的指令往往残缺，现有非交互式移动端智能体面对模糊指令的常见策略是依赖模型先验猜测缺失信息，这种策略在相当多的场景下会产生与用户真实意图相偏离的结果，而偏离本身往往在执行过程中得不到纠正。本文的核心设计目标是让系统在遭遇歧义时能够主动发起澄清，同时保持与已有架构的兼容，不将主动询问作为一个特殊的"外部功能"对待，而是将其自然地内嵌为执行环路的一部分。

在系统设计层面，三层架构将规划、执行、学习三类职责在结构上分离，各层之间通过消息总线松耦合，确保单一层的升级或替换不破坏整体系统的运行。双环机制是本文工程探索的核心成果：动作执行环的稳步推进与用户交互环的按需接管，通过动作类型协议和工作记忆状态字段进行衔接，整个交互插入过程对执行环的其他模块透明。屏幕感知模块的分级处理策略解决了不同模型能力下的接地问题；长期记忆的分类存储与包名过滤机制确保了应用专属知识的独立性与检索效率。

在评测工作层面，参与构建的评测基准在已有移动端 GUI 智能体评测框架的基础上，将指令清晰度维度显式纳入任务设计。评测结果表明，本系统在支持交互的框架中需求完成率和任务成功率均处于前列，而交互增益率指标直接量化了主动澄清机制对任务质量的提升贡献。这两类结果相互呼应，为本文的核心设计目标提供了实验层面的支撑。

## 6.2 不足与局限

做完这个系统之后，回头来看，觉得有几处问题是比较明显的，值得直接说清楚。

[6.2 v2]

本系统当前版本存在若干值得正视的不足，其中一部分直接影响了第5章实验评估的深度，另一部分则构成了系统在实际部署场景中的潜在可靠性边界。

最直接的一处不足是自我学习流水线当前仍为设计预留接口，尚未真正运行。经验条目的产生在实践中依赖手工整理，这意味着系统"越用越好"这一核心设计预期在当前版本里并未实现——长期记忆中的知识是静态的，不随任务积累自动增长。这也直接限制了实验评估的深度：由于缺乏动态积累的知识，无法在自构任务集上给出开启自学习前后的对比数据，记忆系统的长期效益只能借助评测基准的横向比较间接说明。

其次是 FOOD-003 案例所揭示的执行端缺陷：系统对应用内的持久化默认状态（历史地址、历史时间偏好等）缺乏主动核查意识，会在用户已给出明确指令的情况下，被应用的默认值静默覆盖关键参数。子目标验证模块目前只判断子目标是否完成，不校验完成内容是否与原始指令的具体参数一致，这是一个需要专门设计的扩展点。

跨应用上下文传递目前以自然语言字符串的形式实现，对于动态数据（如从上一个应用中提取的具体数字、地址或编号）的传递缺乏结构化约束，在涉及多应用协作且上下游数据格式差异较大的场景下，存在信息丢失或格式对齐失败的风险。

最直接的一个局限是自我学习模块（AppLearnerAgent）目前只是一个设计预留的接口，tip 条目的产生在实践中仍然依赖人工整理。这意味着系统的"越用越好"这一核心设计预期，在当前版本里并没有真正实现——RAG 索引里的知识是静态的，不会随着使用自动增长。这也直接限制了第5章评估的深度：由于缺乏自动积累的动态知识，长期记忆效益的测量只能依赖 AmbiBench 的对比数据，而没有在自构任务集上给出直观的前后对比。

另一个在实验中暴露得比较清楚的问题是 FOOD-003 案例揭示的：系统对 App 内部的持久化状态（历史地址、默认配送时间）缺乏主动核查意识，会被默认值静默覆盖用户的明确要求。这说明当前的执行路径中缺少一个"在进入确认页前回头核查关键参数是否与指令一致"的验证环节。GoalVerifierAgent 目前只验证子目标是否完成，并没有验证"完成的内容是否和指令参数匹配"，这是一个值得专门设计的扩展点。

跨应用上下文传递目前以自然语言字符串的形式完成，在涉及动态数据（比如从日历读出来的会议地点、从上一个订单获取的取件码）的场景里容易出现格式不对齐或信息丢失，这对于真正意义上的多应用协作任务是一个潜在的可靠性瓶颈。

## 6.3 未来工作展望

最值得投入的一个方向是把自我学习流水线真正跑通。如果 AppLearnerAgent 可以在每次任务结束后自动分析执行轨迹、判断其中哪些步骤值得写成 tip、并增量更新向量索引，那么系统对特定应用的适应速度会快得多，尤其是对于那些有固定流程逻辑的外卖、打车类应用。这并不需要完全的无监督学习，一个合理的中间态是"LLM 生成候选 tip + 人工低频审核"的半自动化流水线，先把自动化率提上去。

对于频繁执行同类任务的场景（典型的如"每天同一时间点同一家的同一份早餐"），有一个更直接的加速思路：把成功的执行轨迹直接压缩成一个可参数化的任务模板，后续触发时跳过规划和逐步决策，直接走模板执行路径。这本质上是把 Mobile-Agent-E 的 Shortcut 思路做到更细粒度，Fairy V2 的规划文档里已经列了这个方向，但实现上还有相当多工作要做。

安全问题在这类系统里不应该被放在"未来方向"里轻描淡写地提一句然后跳过。一个能控制手机做任意操作的系统，提示注入攻击是真实的威胁——恶意的 App 弹窗完全可以尝试用自然语言"指令"诱导 ActionDeciderAgent 执行不在原始任务范围内的操作。如何建立一套从规划层到执行层的意图一致性校验机制，是这类系统走向实际部署之前必须认真设计的部分，而不仅仅是一行免责声明。

[6.3 v2]

从工程角度看，最值得优先推进的方向是把自我学习流水线真正跑通。如果学习模块能够在每次任务结束后自动分析执行轨迹、筛选出具有复用价值的经验条目并增量更新向量索引，那么系统对特定应用的适应速度会显著加快，尤其对于有固定操作流程的外卖、电商类应用效果最为明显。完全无监督的自动学习在质量上难以保证，一个合理的中间方案是"模型生成候选条目、人工低频审核"的半自动化流水线，兼顾生产效率与知识质量。

对于高频重复性任务（如每日固定时间点同一家的同一份早餐），有一个更直接的加速思路：将历史成功执行轨迹压缩为可参数化的任务模板，后续触发时跳过规划和逐步决策，直接走模板执行路径。这一方向已有相关工作的探索[5]，在本系统的规划文档中也列有对应设计，但实现上还需要解决轨迹泛化、参数提取和模板版本管理等工程问题。

执行端的主动核查能力是另一个值得专门投入的方向。FOOD-003 案例揭示的问题——应用持久化默认值静默覆盖用户明确要求——在外卖、出行、电商等场景中普遍存在，因为这类应用几乎都保存了用户的历史数据作为默认选项。一种可行的解决思路是在进入订单确认页或支付前，设计专门的"关键参数核查"步骤，将当前界面显示的参数值与原始指令逐项对比，对存在差异的项目主动修正或向用户确认，而不是默认推进到下一步。

在安全性方面，提示注入的风险不应被忽视。移动应用界面上的文字内容完全由应用控制，恶意构造的界面文本有能力将自然语言"指令"注入到动作决策模块的输入中，诱使系统执行超出原始任务范围的操作。建立从规划层到执行层的意图一致性约束——在每轮决策中验证待执行操作是否仍在原始任务意图的边界之内——是这类系统走向实际部署前需要认真设计的安全机制，而非可以一句话带过的展望条目。
