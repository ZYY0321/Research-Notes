# 不管导师：架构怎么学、热点怎么追、CUA 选什么（2026-10-14）

先说结论：你迷茫的根源不是方向太多，而是**没有一个"每天都在用、能被检验"的主线**。下面三件事最后收敛成一句话：

> 用"可验证性（verifier / oracle / 环境）"做贯穿主线——软件工程给你判断"什么叫对"的硬功夫，AI 给你规模化的手段，CUA 是你手上已有数据的落点。

## 一、软件架构 / 壁垒知识怎么学

### 1. 什么才算"壁垒"
算法岗面试和真实工作里，别人短期学不会的是这三样：
1. **能判断一个系统对不对**：不变量、契约、状态机、测试 oracle。（你在 MobileGym++ verifier、UX-Agent 里已经摸到，但没成体系。）
2. **能把大系统拆清楚并改得动**：模块边界、依赖方向、数据流、并发与一致性。
3. **能读大型真实代码库**：vLLM、veRL、Android/ArkUI 框架这类。读得动别人的大代码，比自己写小项目值钱得多。

### 2. 学法：书只读少量经典，主要靠"读大仓库 + 写设计文档"
| 时间 | 读什么（只读这些，读透） | 配套动手 |
|---|---|---|
| 第 1–2 月 | *A Philosophy of Software Design*（Ousterhout，薄，讲复杂度和深模块） | 给自己的 `mobilegym-mock` 写一份 2 页设计文档：模块、依赖、状态在哪、不变量是什么 |
| 第 3–4 月 | *Designing Data-Intensive Applications*（DDIA）前 9 章 | 每章找 vLLM / veRL 里对应的东西（调度、批处理、一致性、故障恢复） |
| 第 5–6 月 | 一个大仓库精读：**veRL**（和你的 RL 方向直接相关） | 画出 rollout→reward→update 的数据流图；提 1 个真实 PR（哪怕修文档/小 bug） |
| 第 7–9 月 | 测试与验证：property-based testing、metamorphic testing（看 Hypothesis 文档 + Barr TSE 2015 oracle 综述） | 给自己的环境写 property 测试，把 verifier 从"写死规则"变成"性质" |
| 持续 | 每周 1 次 code review 习惯：读一个高星仓库的已合并 PR，问"为什么这么改" | 记到 `notes/code-reading.md` |

刻意不推荐：设计模式大全、UML、软件工程教科书——对你的目标回报很低。

### 3. 检验标准（每季度自测）
- 能不能 15 分钟白板讲清楚一个你没写过的大系统（如 vLLM 的 PagedAttention 调度）？
- 你写的 verifier 有没有被一个反例打穿过、你修好了吗？

## 二、AI 热点怎么追（不被淹没）

### 1. 信息源只留四个
1. arXiv 每日：只订 cs.SE + cs.CL 里关键词 `GUI agent | computer use | verifier | self-evolv | reward model`（用 arxiv-sanity 或 RSS）。
2. 每周看一次 Hugging Face Daily Papers 的前 10。
3. 关注 5–8 个做 CUA/Agent RL 的一线作者（UI-TARS、OSWorld、AndroidWorld、Agent RL 方向团队）的主页/X。
4. 顶会 accepted list（ICLR/NeurIPS/ACL/ICSE）出来时一次性扫标题。

### 2. 读法：三遍法 + 一张表
- 第一遍只看摘要+图1+表1，5 分钟，决定是否进表；
- 进表的填：**问题 / 关键假设 / 数据与环境 / 他没做什么（gap）/ 和我的数据能否接上**；
- 每月从表里挑 2 篇真复现（至少跑通 eval）。复现过的论文才算"读过"。

### 3. 判断一个热点值不值得追
三问：(1) 有没有公开可执行的 benchmark/环境？没有就难发、难复现；(2) 我手里有没有别人没有的资产（数据、环境、标注）？(3) 3 个月内能不能出第一个能看的结果？三个都是"是"才追。

## 三、CUA 可以选什么方向（按你的资产排序）

你手上别人没有的：MobileGym++ 可执行环境与 verifier、GUI-only vs Hybrid（GUI+Tool）成对轨迹（强模型/27B/9B，215 题）、Tool Saves/Tool Hurts 切片。

| 方向 | 一句话问题 | 你的资产匹配 | 风险 | 我的判断 |
|---|---|---|---|---|
| **A. 强模型能不能"教会"小模型（teachability benchmark）** | 给定强模型和一组任务，衡量它产出的轨迹/反馈让小模型提升多少，而不是强模型自己的分数 | 成对轨迹 + 可执行 verifier 现成，可直接测"蒸馏后 9B 涨多少" | 需要算力做多轮 SFT/RL；需要先查是否已有同名 benchmark | **首选**。热点（self-evolution / weak-to-strong 反向）+ 资产独有 |
| B. 工具什么时候帮倒忙（Hybrid 动作空间路由） | 为什么 27 题加了工具反而失败，学一个"何时用 GUI、何时用 API"的策略 | Tool Hurts 切片直接是动机图 | **已拥挤**：UI-TARS-2、MobileWorld、UltraCUA 都做了 GUI+工具混合（见 `literature/cua-table.md`） | 降级为 A 里的分析维度，不单独成篇 |
| C. 环境/verifier 自进化 | 让 agent 自己生成任务和 verifier，环境越用越难 | 你有 verifier 工程经验 | 赛道拥挤，大厂在做 | 跟踪，不主攻 |
| D. CUA 做 GUI 测试（UX-Agent 线） | Agent 主动交互来验证显示缺陷 | UX-Agent 全套 | 偏软工、数据量小 | 交给导师那条线，不占你 AI 主线 |

**文献核查（见 `literature/ai-posttraining-table.md`）**：没有找到 teachability 权重训练基准；"Small Models Struggle…"（Findings ACL 2025）和 DED（arXiv 2025）只在数学 CoT 上给出"强老师不一定好教""榜单分≠教学效果"的证据。Agent/GUI 轨迹上无人做，方向 A 空位成立。CUA 文献里 InfiGUI-R1 用了教师蒸馏，但没研究"哪个老师好教"。另外 UI-TARS-2 自认 "ORM still exhibits a relatively high false positive rate"，GUI-Shepherd 证明过程奖励优于结果奖励——可信 verifier 是公认卡点，你的 MobileGym++ 确定性校验正好可作为 A 的评测底座。

**建议**：主线 A，B 作为 A 里"教什么"的一个维度（教小模型何时用工具）。第一步（本月）：
1. 检索确认没有现成的"teachability / teacher-quality benchmark for agents"（交给子代理机械检索，判断我来做）；
2. 用现有轨迹做最小实验：强模型轨迹 SFT 9B vs 27B 轨迹 SFT 9B，看"更强的老师是否更好教"——如果不是，这本身就是论文的动机图。

## 四、一年节奏（替代旧 roadmap 第二节）
- **10–12 月**：架构第 1 阶段 + 热点表建立 + 方向 A 最小实验出图。
- **1–3 月**：方向 A 正式实验，DDIA + 读 veRL；年后投一篇 workshop 或 arXiv 占位。
- **4–6 月**：A 投主会（NeurIPS/ICLR 时间线）；给 veRL 提 PR；导师那边 UX-Agent 扩数据投 SE。
- **7–9 月**：秋招。简历三条：可执行环境与 verifier、teachability 一作、大仓库贡献。
