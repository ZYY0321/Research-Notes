# OctoNest：一条通道死了，该在这台设备上换方式，还是换一台设备

## 一段话介绍
用户的事常常横跨手机和电脑：发票在手机上，文件在笔记本上，报销系统在浏览器里。OctoNest 让每台设备自己在 API、命令行和界面之间换，只有本地确实走不通才把证据交回去，由上层改派设备。评测不靠随机弹窗，而是事先规定这次故障还留不留同一台设备上的退路。和已经拥有三种通道的 UFO 3-Hybrid 比，完美通过率高 18 个百分点；如果设备代理只能在一开始选一次通道、后面不许改，完美通过率掉到大约三分之一。

## 动机
作者用一个对照说明两种失败不是一回事（§1）："a write operation blocked by a CLI’s read-only sandbox may still be completed through the GUI on the same device, whereas a device-wide network disconnection may make a network-dependent subtask infeasible on that device."

教学例子：命令行克隆仓库被沙箱拦住，同一台电脑用浏览器下载仍能完成；整机断网则必须改到另一台还能上网的机器。

## 方法（或资源构成）
每台设备有自己的模态集合。Device Agent 每步做三选一：用某个模态执行一条指令、宣布子任务完成、或带着证据上交。执行器返回三元组：成败标记、产出、观察（§2.5）。失败之后，Device Agent 可以改指令，也可以换模态；换模态就是设备内切换。本地预算用尽或判断没有可行续法，才升级。

CAPEBench（§3.1）跑在两台 Linux 和两台 Android 上，用真实应用和本地文件。每台设备只开放一部分 API，逼模型用剩下的通道。模态级扰动保留同设备的另一条路；设备级扰动让本机做不完，但留一台同类型的同伴；混合扰动两件都要。指标有三个：完成度是服务和文件后置条件满足的百分比；遵循度是在允许的设备上、按原意做完的标准步骤比例；完美通过是每一标准步骤都按原意做完的回合比例。效率用每回合 token，以及「得到一次完美通过期望要花的 token」（不成功的回合也算进分子）。

主实验的文本模型是 DeepSeek-V4-Pro，视觉模型是 Kimi K2.5，超时 30 分钟。对照是 CRAB（界面或 API）、TopoClaw（混合）、UFO 3 的界面、API 和作者扩展的 Hybrid。

## 实验
- 想回答：分层换路是否提高端到端质量；收益来自设备内改通道，还是来自上层改计划；基准能不能把这两种控制缺陷分开。
- 主结果（表 1，全量 158）：OctoNest 完成度 75.51、遵循度 76.82、完美通过 41.14。UFO 3-Hybrid 是 65.00、65.46、22.78。每回合 token OctoNest 更高（764,552 对 702,893，+8.8%，区间跨过 0），但每次完美通过的 token 从 3,084,917 降到 1,858,449（−39.8%，区间不跨 0）。CRAB 的完美通过是 0。
- 分条件（表 2，相对 UFO 3-Hybrid）：无扰动时完美通过 30.43 对 52.17。只废一种模态时，完成度很接近（82.98 对 84.64，文中写 +2.0%），完美通过差一截（38.10 对 54.76，文中写 +43.8%）。混合扰动下完美通过 10.53 对 31.58，仍低于三分之一（§3.2）。
- 消融在固定的 82 题上（表 3），所以不能和表 1 的 41.14 直接比。拿掉 Device Agent，完美通过 18.29；一次性 Device Agent 14.63；把三种模态揉进同一个代理 18.29；计划不许改 21.95；设备只回报「失败了」不给证据 30.49；完整系统在这个子集上是 43.90。
- 作者还定义了边界匹配（该留在本机还是该去同伴机器）和受影响步骤的恢复（受影响的标准步骤全部按原意做完）。这两项画在图 5，HTML 没有给出百分比。文字说：模态故障时 OctoNest 一直留在原设备，受影响步骤恢复更高；设备故障时边界匹配略低，但受影响步骤恢复更高，对照系统有更多回合到达了正确的机器却仍然做不完（§3.4）。
- 能支持的结论：在这套受控故障里，三种通道都给了仍不够，必须允许执行中改通道；只废模态和废整机，打掉的是不同的模块。
- 支持不了的结论：不能说模型从画面里自己发现「点击没生效」。成败来自执行器返回的标记。图 5 没有表内数字，不能写成精确的换路成功率。

## 局限
- 作者承认的：v2 HTML 没有单独 Limitations。§3.2 写混合条件下完美通过仍低于三分之一。§3.3 写只给失败标记时，审计轨迹里换设备和在原设备重试大约一半一半，许多任务在第二次失败后中止。
- 我看到的：表 1 和表 3 的完美通过率分母不同（158 对 82），正文没有把这句写在表 3 的标题里，只在段内说明。主比较锁定 DeepSeek-V4-Pro 和 Kimi K2.5，没有报告换基座。故障是环境里预先关掉通道，不是模型自己的点击偏差。

## 品味判断（本模板最重要的一节）
1. 问题来自跨设备系统通常一机一种通道，失败后只能重试或改派。换一个能起多台虚拟机、并能按配置关掉 API 或命令行的团队可以做这套扰动。难的是把「通道可行性」和「设备可行性」写成可评分的标准步骤，而不是再堆一个混合动作空间。
2. 最有力的是表 2 的模态条件：完成度几乎一样，完美通过差一截。这句话说明「平均做对了一些后置条件」盖住了「整条路有没有换对」。配上表 3：不许根据反馈改通道，完美通过从 43.90% 到 14.63%。
3. 可模仿的实验：同一批任务做两套干预。套 A 关掉默认通道、留同设备的另一条（界面点击失败就只留命令行或快捷键）。套 B 关掉该设备上所有通道、留另一台机器。分别报「是否还留在原通道」「是否改到允许的通道」「受影响步骤是否按原意做完」。对照系统必须同样拥有这些通道，否则分数差只是「多了一条路」。
4. 文中和 UFO 3、CRAB、TopoClaw 比了。它引用 ToolCUA、CoAct-1 作为单设备混合动作的前作，但没有在 OSWorld 上和「未训练就开放命令行」的掉点实验放在一起。那类结果在 HybridCUA（arXiv 2609.38008）里。

## 和 CUA 评测 / 换路鲁棒性的关系（公开层面）
这篇测的是「已知这条通道被关掉之后，系统会不会改走剩下的路」，失败标记由执行器交给模型。它和「平时就混用几条路把总分做高」不是同一个实验：对照已经有三种通道，差在失败后还能不能改。
