# ReTrace：恢复是否成功，要看后面同样的动作还会不会得到同样的结果

## 一页读懂

| 读深度 | 全文（arXiv HTML；图 4–8 的曲线没有逐点读数） |

| 品味 | A。判据换成「后续动作是否等价」，于是会出现「恢复尝试让任务成功率下降」这种只看最终分看不到的结果。 |

## 一段话介绍
ReTrace 问的不是模型会不会把用户的任务做完，而是它能不能把环境救回到出错之前的那个状态。作者规定：救回来之后，如果把原来后半段动作再做一遍，结果必须和没出过错时一样。只看截图像不像不算数，因为文件被覆盖、窗口被挡住这类变化，画面上可以很像，后面一点就露馅。他们在 OSWorld 和 WindowsAgentArena 上发现，专门练过单向做任务的开源模型几乎不会自己去修状态；硬让它们修，任务成功率还可能下降。通用模型在被明确要求恢复时好很多，但端到端也只是小幅上涨。

## 动机
作者把现有补救分成三类，并认为都不适合拿来研究模型自己的恢复（§1）：环境重置在真实系统和网站上经常不可用，整段重放太贵，基于 API 的回退基本限于网页。原文把要研究的能力说成："autonomous model-level recovery, in which the agent itself restores a prior state without relying on such ad hoc mechanisms."

教学例子：整理文件夹时任务看起来完成了，但有一份不该动的文件被覆盖。最终检查如果只问「文件夹是否整齐」，会把这次覆盖算成成功。

## 方法（或资源构成）
先让模型做出成功轨迹，再把动作序列重放 N 次。只留下三次连续重放都被标准答案判成功的轨迹，用来压低环境随机性。附录表 6 说这一步保留了 64.4% 的恢复轨迹。然后选一个中间状态当恢复目标，把模型扰动到错误状态，再让它去救。

判据有两部分：画面匹配，以及转移一致。人工评测里，12 名标注员、每种对照 50 条，ReTrace 的裁决比去掉任一部分、也比 GPT-5.4 更接近人。标注员之间平均一致率 82%，Cohen’s kappa 0.45（§5.4.2）。作者称这是可靠一致。

恢复政策分隐式和显式。隐式是出错后继续往前做。显式则在上下文里放上直到目标状态的历史，或者用一个语言模型把这段历史摘要成「恢复目标上下文」。

## 实验
- 想回答三件事：理想的恢复（直接送回从前的正确状态）是不是比从头重来更省重试次数；现有模型有没有自己恢复的能力和倾向；恢复质量会不会变成任务成功率。
- 理想恢复（§4，图 3）：在同样的重试预算下，从上一正确状态接着做，比整段环境重置更早把 Success@K 做高。预算变大后差距缩小，因为反复重开也会碰上成功。
- 自主恢复（§5.4.2）：Claude-Sonnet-4.6 和 GPT-5.4-CUA 的恢复能力有限；EvoCUA-32B 平均恢复率低于 1%。隐式恢复时，模型写出的理由和「真的在做恢复」的提示不太像，作者据此认为它们很少尝试恢复（图 6，没有给相似度的表内数字）。显式恢复比隐式平均高 17.86 个百分点，Linux 和 Windows 合在一起（图 4、图 5）。涨幅主要在通用模型上；后训练过的专用模型涨得少。
- 端到端：表 2 的文字说，带恢复的几种设置都高于 Qwen3.5-9B 的无恢复基线，端到端平均增益 2.12%（§6.2）。HTML 里紧挨表 2 标题的一块数字是基线 39.38±1.17，带恢复目标上下文 41.06±3.05（+1.68），0∼R 为 44.26±1.90（+4.88）。我把 2.12 当作正文对多种设置的平均，不把它说成表 2 的某一格。
- 表 3 显示恢复可以伤任务分：UI-TARS-1.5-7B 和 EvoCUA-32B 下降，Sonnet 和 Qwen3.5-9B 上升。图 8 说多给几次恢复机会，恢复本来就弱的 EvoCUA 更容易越修越偏。
- 定性（表 4）：救回来的画面若和目标不一致，模型会盯着鼠标正好悬停的按钮，跳过本该先做的拖拽；或者终端挡住了字体菜单，模型仍假装菜单开着。
- 能支持的结论：在他们过滤后的确定性轨迹上，最终任务成功不能代替状态恢复；弱的恢复尝试会把轨迹带得更偏。
- 支持不了的结论：不能说模型发现界面点击失效后改用了命令行。恢复的目标是回到先前状态，不是换一条完成任务的通道。17.86 这个差来自图，不是一张带置信区间的表。

## 局限
- 作者承认的（Limitations）：框架用来测量恢复，不直接把恢复训出来。显式设置只能引出模型里已经有的能力，补不了界面理解、状态跟踪或动作规划的缺陷。专用模型修不准时，会额外把轨迹带偏、降低任务成功。用错误状态做后训练不在本文范围内。
- 我看到的：kappa 0.45 通常只算中等一致，和 82% 的原始一致率要一起读；作者写成 reliable agreement。轨迹先滤成三次重放都成功，环境里真正随机的弹窗、时间戳被排除了，恢复问题被做干净了，也更离开日常桌面。

## 品味判断（本模板最重要的一节）
1. 问题来自「反思、重置、网页后退」都被当成推理时的补丁，没有人把「状态有没有救回去」单独评分。换一个能重放 OSWorld 动作的团队可以做。难的是坚持用后续动作等价，而不是看最终奖励。
2. 最能说服人的是表 3 的下降格，加上 EvoCUA 恢复率低于 1%。如果恢复总是帮任务分，审稿人会怀疑只是多给了步骤。下降说明判据抓到了「修坏了」。
3. 可模仿的实验：只在三次重放都成功的轨迹上选一个中间点，注入一种副作用（覆盖文件、打开错误窗口）。恢复之后不看任务分，先重放后半段，后半段结果不一致就判恢复失败。再把同一条轨迹的任务成功率并列报出，专门留下「任务分升了但状态没对齐」和「任务分降了」两类。
4. 它没有和 CUA-Recovery、RoTS 的「觉察率 × 事后成功率」对齐。那两篇问的是发现错误后能不能把任务做完；这篇问的是能不能把状态救回等价的未来。两套数不能互相代替。

## 和 CUA 评测 / 换路鲁棒性的关系（公开层面）
换路如果只把最终成功率做高，可能是绕过了坏状态，而不是修好了它。这篇的判据要求后续动作结果一致，用来区分「换了一条路把分做上去」和「把默认通道留下的副作用清掉」。它自己没有做通道切换实验。

## 原文摘录
- §1: "We formalize successful recovery as Transition-Consistent Recovery: a recovered state matches its target if executing identical downstream actions from both states yields identical outcomes."
- §5.4.2: "the strongest open-source model, EvoCUA-32B, exhibits a near-complete inability to restore previous states, with an average recovery rate below 1%."
- Limitations: "inaccurate recovery by specialist agents with weaker recovery capabilities may induce additional trajectory drift and reduce task success."
