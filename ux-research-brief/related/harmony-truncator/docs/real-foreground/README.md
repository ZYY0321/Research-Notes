## 修复后的最新结果

基本平色紧框文字已修复：原先拒绝的4项现在给出测量，全部符合冻结目视框4px容差。15项合计12项可测、3项插画背景拒绝。算法增加了上下边沿及周界同色检查，不直接降低全局背景门槛。新输出见[修复结果](repaired-results.json)，人工112例回归见[回归结果](synthetic-regression.json)。下方表格保留修复前结果供对照。

## 方法与样本

先按UI树顺序，对可见、bounds与origBounds相同、宽20—950px且高15—150px的非空Text去重，按首尾及两个等间隔位置抽样。最初16项中5项为系统时间或电量，查看后排除，留下11项应用文字。另定向选取健康生活3项插画背景文字与商城1项红底浅字，单独记录为补充组。这个尺寸筛选偏向较小文字组件，不是对所有页面的随机抽样。

先查看不含预测结果的原图裁片，用助手目视方式标出文字紧框并保存，再调用foreground默认参数。目视框容许4px误差；这是粗粒度人工式核验，不是独立人类标注，也没有精确的逐像素真值。使用的参考框、原截图摘要和输出均保存在[结果JSON](results.json)，裁片可逐一打开复核。

## 实际发现

1. 灰色提示“暂无任务，请添加任务”可测，目视框差4px；它说明实际较浅文字有成功例子。没有测量字体对比度并达到统一的低对比定义，因此不把它与人工基准中的极低对比组视为同一强度。
2. 普通平色背景也有拒绝：成就、全部、亚瑟王、通信录。文字在较紧框内占比高，主背景颜色不足70%，触发unsupported_background。拒绝的主因不是界面花哨。
3. 健康生活“目标进度”“健康生活”“%”的完整组件框横跨插画，背景占比约46.9%、44.1%、61.6%，全部拒绝。只有文字左侧一小块比较简单，算法仍按整个组件框分析。
4. 商城红底“手机”可测，差1px。当前样本没有独立确认的纯渐变背景文字组，也没有与人工色块例严格对应的真实文字加独立装饰组；插画背景是已有真实复杂背景例，不能替代这两类的专门统计。

## 对项目的影响

现有方法对这批支持的文字框能给出可用结果，但覆盖偏保守；“大多数应用不花，所以大多数目标都能测准”的推断证据不足。规划对unknown的回退和最后审核仍有实际必要。本次不放宽70%阈值，避免为了增加覆盖把插画也框成文字。后续若改进，优先处理紧框粗体文字的背景判定，再用这批冻结标注回归。

本轮只补测量证据和文档，没有重新构建应用、修改注入算子或调用UX-Agent。完整原始抽样、排除项及盲标材料在项目artifacts/real-foreground-20261122目录。
