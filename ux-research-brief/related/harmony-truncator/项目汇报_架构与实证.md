# Harmony Truncator：架构、缺陷机制与实测汇报

2026-11-23。本文供讨论实现路线、构造合理性与参数设计；逐函数学习见[完整源码讲解](完整源码与实验零基础详解.md)。配套的[19种算子图树与代码附录](汇报附录_19种算子图树与代码.md)逐项给出真实运行截图、关键树字段、源码改动与原件位置。

## 1. 项目解决什么问题，目前做到哪里

项目输入是**能构建的鸿蒙应用源码、工具链配置、人工指定的页面路径**。程序先构建正常应用、走到页面并采集截图和UI树，再修改对应源码，生成包含多个显示变化的HAP，运行后保留新截图、新树、修改位置和审核记录。

主要研究对象是UX-Agent关注的截断与可恢复内容：真正的文字／图像裁切、可滑动恢复的露边，以及只裁掉组件留白的难负例。样本最终标签依据运行画面、恢复证据和审核决定。

目前已有5款既有开源应用的构建与注入采集记录：OhBill、Healthy_life、MultiShopping、CloudMusic、Wechat_HarmonyOS。后者是开源仿微信工程。算子注册表保留19条实现：16条属于当前截断研究范围，另外3条是历史遮挡实现。日常静态campaign默认启用12条。

本轮修复了两项实际问题：窄包装改变百分比padding，导致预期裁切落空；小Scroll默认滚动条干扰内容手势。修复后原有6个目标重新构建，目标边界与区域像素均保持一致；短文本、横向长文本、纵向多行恢复复测通过。详见[修复与完整回归](docs/verification/scroll-fix.md)。

### 2.2 实际是谁调用谁，哪里串行

![实际调用顺序](docs/images/report/02-call-flow.png)

当前入口是`campaign.campaign()`，其中逐个应用调用`run_combined_application()`。**应用、页面、目标、算子均按循环串行处理**，共用设备还有锁；图中多个模块表示职责拆分。

1. **预检配置。** `validate_campaign()`检查算子名字、研究范围、重复选择和配置层级。例如页面里误放`max_total`或`verify_recovery`会直接报错，避免配置静默不生效。目前campaign统一使用combined；单目标可把`max_total`设为1。
2. **准备正常来源。** `prepare_application()`默认尝试插桩，给可定位的源码位置／循环实例添加追踪信息；插桩或其构建失败时，保存原因并退回原工程一次。已有正常包或已插桩来源按其既有身份复用。`scan()`调用SDK的源码解析器，扫描工程文件，不靠截图推测源码行。
3. **按recipe到达页面。** 每次点击／滑动前从当前UI树重新定位组件并计算坐标。截图前后分别取得树，检查目标是否稳定。动态商品列表按能识别的业务键或实例信息绑定，找不到对象或内容变更会记录原因。
4. **汇合源码和运行态。** `bind_candidates()`把源码site与树节点对应；`load_baseline()`校验截图、源码及样式依赖，把目标、祖先、树记录、像素框和设备密度装入Baseline。campaign中每个绑定目标加载一次，后续多个算子复用。
5. **形成候选计划。** 先用注册表的components做类型初筛；随后对每个“目标×可用算子”调用`plan_from_baseline()`。源码约束、关联父容器、实际尺寸与前景等检查在此继续进行，每对通常生成1份参数与补丁。
6. **全应用组合。** 所有配置页面的候选汇总后，`select_combination()`选择有限的缺陷组，`compose()`合成一个计划；`batch()`准备副本并构建一次组合HAP，再依次回放各页。当前实现会对scroll-recovery成员补做有界恢复取证。

源码中的公共组件可能在多个配置页面出现。组合层把同一次修改记入每个受影响页面的预算；没有配置、没有采到的页面尚不在这个检查范围内。

### 2.3 算子本身承担哪些操作

策略表`operator_strategies.py`为每个机制登记四类处理：

|处理|输入→输出|例子|
|---|---|---|
|`select`|正常测量→裁入量与依据|高度裁切考虑文字底部padding；留白算子只选尾部空白|
|`parameterize`|像素框、裁入量、方向→源码参数|`vp = px / density`；右侧裁切缩宽，底部裁切缩高|
|`stabilize`|计划参数→布局稳定约束|自身Text裁切保留原占位；宽度裁切同时保留高度|
|`render`|site与参数→替换源码|固定子尺寸，生成Row／Scroll，或修改目标及关联容器|

公共入口负责数据准备与协议，具体行为由策略函数完成。共用的`source_edits`负责属性替换、追加以及margin／alignSelf迁移；`mutation_patches()`把目标、关联容器和必要状态字段作为同一缺陷组的补丁组织起来。写入时检查原文与区间，按从后到前的顺序替换，避免前面的长度变化破坏后续坐标。

这套结构已把选参、几何和源码模板分开，也复用了相同机制的规则。新机制涉及特殊关联节点或新的页面影响范围时，仍可能需要扩展规划／组合层的分支，这是下一步架构评审可以关注的边界。

## 3. 参数与组合算法：值得讨论的具体设计

![组合选择算法](docs/images/report/03-selection.png)

### 3.1 组合选择是带平衡权重的贪心过程

程序不枚举所有目标与算子的乘法组合。它先按seed打乱site顺序，优先处理目前接受数量较少的组件类型；对该site的算子候选逐项检查冲突，再在适用分数达到当前最高分80%的候选中抽取一个。抽取权重为：

```text
1 / ((1 + 本轮已选该算子的次数) × (1 + 本轮已选该机制族的次数))
```

选入后更新各页占用范围和频次，继续处理下一个site。该site的其他算子候选一并移出本轮选择；不会在同一源码目标叠加多个互斥改法。有关联父节点的补丁以整组参与选择。

冲突包含：目标或关联补丁源码区间重叠、页面影响范围重叠、触及路径按钮／滑动区域、页面数量预算、影响面积预算，以及同一selector在其他配置页出现歧义。适用分数主要奖励局部修改，对容易重排的parent-clip等降低权重。

### 3.2 目前默认值及其含义

|设计项|当前值|考虑与讨论点|
|---|---|---|
|每应用缺陷组上限|12|控制一个包的总改动量；并非12个页面|
|每页上限|3|减少相互干扰，方便逐个审核；简单页是否应更少|
|累计影响面积上限|屏幕面积30%|使用预测布局影响框；大容器会使候选较难进入|
|随机种子|0，可配置|同输入可复现；不保证每类算子严格均分|
|局部适用分数候选范围|最高分的80%以上|兼顾局部性和机制多样性；可能放弃总体更多的组合|
|有前景测量时的常规裁入|边缘内容跨度20%，搜索参考区间15%—30%|文字纵向采用边缘行带，包含到组件边缘的距离|
|无前景测量时的常规回退|组件跨度35%，参考区间25%—45%|记录回退依据，再看实际画面；留白难负例没有这项回退|
|宽度／单行限宽规则|保留可见文字跨度约65%，参考55%—75%|同时处理宽度约束、padding与原高；需检查重新换行|
|留白难负例|至少4px尾部留白，默认收掉其中一半|保留实际字形；背景或字体变动后需重新检查|
|滚动方向|一条可测文字行带→横向；多条→纵向|测不到行带时再看换行符，最后默认横向并记录依据|
|滚动补测预算|默认每目标2次，可指定1—4次|先找目标附近避开可点击区的轨迹，覆盖到内容或无进展就停止|

这些是当前可复现的工程规则，尚未通过大规模参数消融选出最优值。最值得讨论的是数量／面积预算、裁切强度、贪心顺序是否过早排除了后续更合适的组合。

## 4. 算子覆盖与真实运行例子

完整逐项材料见[19种算子附录](汇报附录_19种算子图树与代码.md)。附录使用真实HAP运行采集，包含每项的图、目标／父节点字段和关键源码。19项中，视口宽度不匹配、固定宽视口、首次宽度缓存这3项的现有示例来自专项ArkUI工程，其余示例选自既有开源应用。

|机制组|算子|主要改动|
|---|---|---|
|自身文字约束|line-clip、height-clip、width-clip|限行／限宽，或改变自身可见高度、宽度|
|省略表达|ellipsis-width、ellipsis-lines|限宽或限行，并使用Ellipsis；标签结合设计与恢复判断|

|屏幕与视口约束|window-edge-clip、viewport-width-mismatch、freeze-viewport-width、cache-viewport-width|移动到窗口边界，或制造相关视口尺寸与窗口的失配|
|难负例|scroll-recovery、whitespace-clip|同轴滑动可恢复，或只裁组件留白|
|历史遮挡实现|overlay-occlusion、sibling-translate-occlusion、sibling-position-occlusion|新增覆盖层，或移动已有兄弟；已排除在当前campaign范围之外|

### 5.2 独立源码故障说明开发中确实会出现相应约束错误

## 6. 应用构造、审核重建与跨批统计

以下每个真实应用选取一个可复查的组合包，汇总其构建／采集记录。选择包含历史多页包，便于讨论跨页影响；数据不是把重复实验目录全部累加。

|应用|所选包的源码缺陷组|配置页面|页面出现次数|可观察内容|
|---|---:|---:|---:|---|
|OhBill|3|1|3|图标留白、月份裁切初态、图表底部裁切|
|Healthy_life|4|1|4|图像留白、两处文字高度、重复Builder图标平移|
|MultiShopping|11|5|12|商品、详情、规格弹窗、评价和列表；公共修改跨页出现|
|CloudMusic|4|3|4|设置文字高度、省略、内容放大及历史覆盖例|
|Wechat_HarmonyOS|3|1|3|宽度裁切、平移与省略|
|合计|25|11|26|5个包，5款应用|

这里的“组”是计划中的独立源码修改单位，包含正例候选、难负例和历史遮挡；最终接受数量由逐目标审核另算。Healthy_life本轮为回归显式加入第4项，普通campaign的默认每页3项没有改变。MultiShopping的11组出现在页面上12次，体现了源码修改数与页面观测数的区别。完整目录及HAP哈希见[统计原件](docs/verification/report-app-statistics.json)；各机制画面和代码直接复用附录。

![审核重建和跨批统计](docs/images/report/04-review-statistics.png)

人工审核以缺陷组ID、图树和包哈希为依据。`rebuild_reviewed()`读取审核文件，生成只移除不合适缺陷的派生计划；关联补丁整组移除，其余参数保留，然后从正常来源重建并重新采集所有配置路径。父审核、原包、新包和多轮历史被一起记录。它由相应命令触发，执行次数受操作者控制。

`run-summary`可以读取多个批次，按应用尝试、页面、独立包和失败阶段汇总；`dataset-audit`检查交付样本的数量、分布、重复与标签一致性。统计覆盖率使用实际配置的页面或启用的算子作分母。执行统计保留失败和重建尝试，交付统计再根据审核结果选取最终版本。

## 7. UX-Agent运行到了哪一步，发现了什么

使用原UX-Agent实现，历史评测固定提交`565033c`，仅配置模型渠道与模型；没有为提高命中率修改其提示词、布局判断或滑动算法。替代模型为`qwen/qwen3.8-flash`。以下是已有实验结果，本轮修复没有追加付费模型调用。

|批次与口径|实际执行|结果|
|---|---|---|
|首次离线图像＋布局|26份独立画面，28个目标观察|保存模型原答与布局结果；没有实时滑动|
|实时模型→布局→滑动|26个状态、28个目标，26次HTTP成功|实际执行6次swipe；其余由无候选或已有布局结论跳过|
|实时批次的目标／边缘定位评价|28目标，其中26个可计分|TP=1、FP=3、FN=6、TN=16，另2个未计分；P=25%，R≈14.3%|
|原生PNG按钮控制组|7个初始页面、8目标；一次SSL失败单独重试|TP=2、TN=6；Agent实际滑动0次|

TP是正确报出缺陷，FP是把正常目标报错，FN是漏报，TN是正确保留正常目标。定位口径要求预测关联到审核目标及预期边缘；更换评价口径时不能直接沿用这张表。原生PNG按钮组是较小、受控的子集，其结果单独列出。

实验推动了构造端几项实际完善：图像采集改用原生PNG，避免编码伪影影响细字；补充同一内容与完整覆盖检查；将“有裁切初态”和“操作后恢复”分别保存；保留错误边缘、无候选、身份变化和路径失败的原始记录。模型没有报错的样本也要看真实图树，避免把漏检当作构造失败。

评测细节见[历史实测报告](docs/experiments/实测报告.md)中2026-11-18实时评测和2026-11-19原生PNG部分。目标逐项账本分别位于`artifacts/operator-target-evaluation-20261118/target-evaluation.json`及`artifacts/native-png-production-20261118/agent/completed-target-evaluation.json`。

## 8. 本轮修复后的质量与待讨论事项

**回归结果。** 两款应用486组真实基线候选中，458组完全一致，24组只增加关闭滚动条，4组因百分比padding窄包装而明确拒绝。4次HAP构建之后各自322项测试全部通过；Python安装包构建后也通过322项测试。原有6个目标重新采集的bounds、origBounds和区域像素完全一致。短文本、横向长文本、纵向多行分别实测移动41px、692px、102px并覆盖完整字形。两次hdc读取超时保留为失败记录，同包重试后完成纵向核验。

**建议集中讨论以下问题：**

1. **机制代表性。** 现有现实依据能支撑哪些错误类别？数量较少时，是否以若干充分讲清的典型例子作为当前阶段目标，暂不要求每个算子都有商业对应。
2. **干扰预算。** 每页3组、总数12组、面积30%是否符合使用场景？图标／文字／大图是否需要不同预算，还是先保持统一规则。
3. **强度与选择偏差。** 20%边缘内容裁入、65%宽度保留和80%分数阈值是否过于固定？组件频次平衡会不会改变真实缺陷分布，适合用哪些小规模消融检验。
4. **布局支持边界。** layoutWeight、复杂共享样式、动态数据、父子百分比等约束目前采取解析、保护或拒绝。优先扩展哪一类，才能增加有效候选而不引入不可控重排。
5. **审核成本与统计口径。** 将构建、页面到达、内容变化、恢复证据和最终接受分别统计；讨论哪些诊断可减少人工检查，哪些保留人工判断。
6. **补测优先级。** 三种视口专项已有真实ArkUI运行证据，后续可补到更多既有开源应用；复杂背景前景测量、未配置页面的共享影响和设备命令偶发超时仍是明确的工程边界。

当前主链已经覆盖源码、运行态、补丁、组合包、动态取证、审核重建和跨批统计。后续完善宜围绕有效候选率、实际样本质量和审核成本展开，用已有回归集检查收益与退化。
